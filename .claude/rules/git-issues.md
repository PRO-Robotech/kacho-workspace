## Волна — единица запроса на слияние

Указание владельца 2026-09-21, дословно: «Каждую волну формируй в отдельный мр»: предмет
запроса — сведённая волна, а не полоса. База запроса волны — ветка эпика, запрос эпика — в
`main` (решение владельца 2026-09-22).

gi-wave-is-the-mr-unit · сводить полосы волны в одну ветку, гнать проверки на СВЕДЁННОМ, открывать ОДИН запрос волны в ветку эпика · `gh pr list -R <репо> --state open --base <ветка эпика> --label <метка линии> --json number,headRefName` — не длиннее строки · red: второй открытый запрос линии при незакрытой волне
gi-wave-closed-when-request-lands · волна закрыта ровно тогда, когда её единственный запрос ВЛИТ либо СНЯТ (решение владельца 2026-09-21) · `gh pr list -R <репо> --state open --base <ветка эпика> --label <метка линии> --json number` — не пуст, значит открыта · red: «волна закрыта» выведено из памяти сессии или задания
gi-wave-pr-names-its-roster · называть состав в теле запроса поимённо (полоса, ветка, голова) и сверять с историей сведённой ветки · `git log --oneline <база>..<голова>` против перечня полос задания · red: запрос несёт одну полосу при готовых несведённых головах соседних
gi-wave-verdict-from-the-assembled · вердикт снимай со сведённой головы; зелёное полосы до сведения в вердикт волны не засчитывается · конвейер запроса на той же headSha (`testing-verdict.md#pr-red-belongs-to-revision-headsha`) · red: волна отправлена на зелёном полосы, снятом на её базе

## Текст коммита: ёмко, информативно, не поэма

Мера — поймёт ли это через полгода тот, кто откроет `git log` без контекста.

gi-subject-72 · заголовок до 72 символов, повелительно-описательно, ОДНО утверждение, без точки · ЗАВЕСТИ gi-commit-msg-hook · red: второе утверждение через тире или точку с запятой; точка в конце
gi-blank-line-required · пустая строка между заголовком и телом обязательна · ЗАВЕСТИ gi-commit-msg-hook · red: `git log --oneline` показывает склеенное с телом
gi-body-says-why · тело до 12 строк и говорит ПОЧЕМУ изменение верно; чинится дефект — чем он проявлялся · ЗАВЕСТИ gi-commit-msg-hook (длина) · red: пересказ диффа «добавил X, поправил Y»
gi-body-excludes · в тело не идут: ход работы (его место — задача), разбор дефекта по шагам (репозиторий публичный), число без предиката · `security-disclosure.md` §«Публичные артефакты» плюс признак восстановимости · red: «улучшено на 30%» без предиката; шаги воспроизведения дефекта
gi-closes-last-line · `Closes #<N>` — последней строкой · ЗАВЕСТИ · red: номер задачи в середине абзаца
gi-two-subjects-two-commits · два предмета в одном коммите — это два коммита; заголовок, которому нужна точка с запятой, сообщает об этом сам · ЗАВЕСТИ · red: один коммит о двух предметах
gi-commit-form-by-hook · форму сообщения судит хук `commit-msg`, а не ревью: рецензент формой круга не открывает · ЗАВЕСТИ gi-commit-msg-hook (воркспейс — #770; corelib#25, kaname#356; kacho — задачи нет) · red: форма коммита — замечание ревью; принят заголовок длиннее 72 знаков

## Волна: сборка — агрегат (решение владельца 2026-09-24 «тестирование агрегатами а не каждую таску отдельно»)

gi-wave-assemble-only · в ветку волны задачи приходят только сборкой k — задачей и веткой от ветки волны: сданные задачи вливаются в неё `git merge --no-ff` каждая, состав доказан до прогона, PR сборки в волну — коммитом слияния; PR задачи в волну и догон волны в ветку задачи отменены · `gh pr list -R <репо> --base <волна> --state merged --json headRefName` — только ветки сборок · red: PR задачи в волну; сборка схлопнута; задача в волне мимо сборки; в ветке задачи слияние волны
gi-asm-one-round · на сборку один раз: прогон на голове её PR (`testing-verdict.md#asm-verdict-runs-on-head`), ОДИН рецензент каждой задетой роли (задача с ✅ роли — только дельта), `check-verifier` по задачам-проверкам, `wave-reviewer`; возвраты — в ветки задач, одно пересведение и один повторный прогон, затем посадочный и вливание; ⛔ или красное после них — PR сборки закрывается, задачи без ⛔ идут в сборку k+1 · `gh run list -R <репо> --branch <ветка сборки> --json headSha,workflowName` — не больше двух голов на процесс · red: прогон или круг ревью на задаче; третий прогон сборки; вливание до ✅ посадочного
gi-pr-manual-dispatch · PR открыт, а триггера PR в базу нет (kacho#2793, corelib#31, kaname#394) — тем же заходом `gh workflow run <файл> --ref <ветка>` КАЖДОГО процесса с `pull_request` и `workflow_dispatch`; свод без `workflow_dispatch` не встаёт, вердикт — по процессам · `gh run list -R <репо> --commit <headSha> --json workflowName,status,conclusion` · red: PR без проверок ждёт несуществующего триггера; запущен не каждый процесс PR

## Трекер — GitHub Issues: когда заводится задача

gi-feature-issue-first · фича (ресурс, API, раздел UI, кросс-доменное поведение) → задача ПЕРВОЙ, ветка с её номером, PR `Closes #<N>`, ссылка на PR — комментарием в задаче · ЗАВЕСТИ · red: ветка или PR, которым не предъявить задачу
gi-batch-one-per-session · фиксы и мелкий UX — ОДНА batch-задача на сессию («<область> bugfix batch — YYYY-MM-DD»); важное и влияющее на безопасность — своей задачей (gi-security-finding-issue-now) · ЗАВЕСТИ · red: десять задач на сессию фиксов; находка о безопасности пунктом batch-задачи
gi-security-finding-issue-now · находку, важную и влияющую на безопасность, заводи задачей в трекере НЕМЕДЛЕННО, тем же заходом, в репозитории предмета (решение владельца 2026-09-20 «не забывай по ходу создавать задачи в гитхаб ишуе если это важное и влияет на безопасность») · scripts/tooling-gate/check-19-landing-route-is-one-mr-per-wave.sh — норма; срок — вниманием · red: находка о безопасности доехала до конца волны отчётом, задачи нет
gi-security-issue-high-level-only · немедленность — о СРОКЕ, не об объёме: в задачу — высокоуровневая часть со ссылкой на дифф фикса, прочий разбор не коммитится, на рабочий каталог задачи не ссылаются · `security-disclosure.md` §«Публичные артефакты» плюс признак восстановимости · red: шаги воспроизведения уязвимости в публичной задаче; ссылка на `tmp/issue-<N>`
gi-trivia-no-issue · опечатка, однострочник, docs — без задачи, достаточно коммита · ЗАВЕСТИ · red: задача на однострочник
gi-retro-backfill · существенный кусок без задачи заводится ретроспективно; тривию не бэкфиллить · ЗАВЕСТИ · red: в истории работа, которой нечего предъявить
gi-find-own-issue · находка по дороге заводится СВОЕЙ задачей, а не чинится в чужом PR · ЗАВЕСТИ · red: PR несёт правку не своего предмета
gi-zero-findings-aloud · ноль соседних находок — законный ответ, но названный вслух: «смотрел, чисто» отличимо от «не смотрел» только сказанным · ЗАВЕСТИ · red: отчёт без находок и без названного осмотренного места

## Разметка тела задачи

gi-epic-label-and-list · крупное или многодоменное — эпик (метка `epic`): цель, решения, декомпозиция, порядок по ГРАФУ ЗАВИСИМОСТЕЙ, DoD; дочерние — списком задач `- [ ] #<N>` в теле · ЗАВЕСТИ · red: эпик без дочерних; порядок взят по номеру вместо графа
gi-task-body-four · тело задачи несёт четыре вещи: что · DoD · затронутые каталоги · артефакт · ЗАВЕСТИ · red: задача без DoD либо без артефакта
gi-blocked-by-label · блокер — строкой `Blocked by #<N>` И меткой `blocked`: словами без метки его не видит соседняя сессия · ЗАВЕСТИ · red: блокер прозой, метки нет
gi-role-line · исполнитель — строкой `**Роль:** <agent>` в теле: поля исполнителя у задачи нет, назначение — assignee, если учётка есть · ЗАВЕСТИ · red: роль выводится из текста, а не названа

## Состояние — метками, снимается ТЕМ ЖЕ действием

gi-state-by-labels · состояние — метками (`status:in-progress`, `status:test`) плюс сам факт open/closed; своего поля состояния не изобретать · ЗАВЕСТИ · red: состояние прозой в теле вместо метки
gi-label-same-action · метка описывает ТЕКУЩЕЕ состояние: закрыл — снял тем же заходом; сдал на проверку — ЗАМЕНИЛ, а не добавил вторую · `gh issue list -R <репо> --state closed --label status:test --limit 100 --json number -q '.[].number'` и то же для `status:in-progress` — пусто · red: закрытая задача с `status:test`
gi-open-label-needs-artifact · `status:test` на открытой законен ровно пока есть артефакт, ждущий ствола · ЗАВЕСТИ · red: метка без артефакта — «кто-то что-то делал», то есть ничего
gi-stale-label-blocks-capture · перепись выше прогоняется при завершении накопительной линии: пережившая метка ЗАПРЕЩАЕТ брать задачу, которую никто не ведёт, и запрет невидим · ЗАВЕСТИ · red: свободная задача выглядит чужой работой

gi-close-with-artifacts · закрывать С АРТЕФАКТАМИ В КОММЕНТАРИИ: PR-URL, лог прогона, ссылки · ЗАВЕСТИ · red: закрыто словом «сделано»
gi-pr-link-comment · ссылка на PR кладётся комментарием в задачу тем же заходом, которым PR открыт · ЗАВЕСТИ · red: PR есть, задача о нём не знает

Дословно: «не забывай агрегировать мр = волна». Позднее решения 2026-09-17 «заливай сразу в мастер» и отменяет его посадку PR прямо в `main` без накопительной ветки со слиянием сразу по зелёному CI; отменённый текст основанием не служит.

gi-wave-one-mr · волна уходит в ветку эпика ОДНИМ MR со сведённой ветки — форма `gi-wave-is-the-mr-unit`; предметы рядом сверяет `wave-reviewer` · scripts/tooling-gate/check-19-landing-route-is-one-mr-per-wave.sh — норма; порядок — вниманием `git-operator` · red: два PR одной волны открыты
gi-no-pr-per-lane · PR на полосу и отправка веток полос по отдельности запрещены: полоса доезжает до ствола сборкой · check-19 tooling-gate — литералы снятого маршрута; поведение git — вниманием `landing-reviewer` · red: ветка полосы получила свой PR
gi-wave-mr-ready-predicate · MR волны вливай при ЧЕТЫРЁХ условиях, ни одно не выводится из другого: состав сборки доказан · прогон на сведённом зелёный · `wave-reviewer` прошёл · приёмка посадки одобрила ту же sha · ЗАВЕСТИ · red: MR влит при зелёном каждой ветки по отдельности
