# Разметка задач и комментариев GitHub Issues, перевод этапности

Трекер — **GitHub Issues того репозитория, где живёт предмет**; общее — в
`PRO-Robotech/kacho-workspace`, работа через `gh issue …`. Номера `KAC-<N>` в истории —
свидетельство о сделанном, а не указание на трекер; вперёд связывает только это правило.

## Текст коммита: ёмко, информативно, не поэма

Читают люди — в списке из полусотни строк, в `git blame`, в обзоре PR: много букв означает
«не прочитают вовсе». Мера — вопрос: поймёт ли это через полгода тот, кто откроет `git log`
и не помнит контекста.

gi-subject-72 · заголовок до 72 символов, повелительно-описательно, ОДНО утверждение, без точки · ЗАВЕСТИ gi-commit-msg-hook · red: второе утверждение через тире или точку с запятой; точка в конце
gi-blank-line-required · пустая строка между заголовком и телом обязательна · ЗАВЕСТИ gi-commit-msg-hook · red: `git log --oneline` показывает склеенное с телом
gi-body-says-why · тело до 12 строк и говорит ПОЧЕМУ изменение верно; чинится дефект — чем он проявлялся · ЗАВЕСТИ gi-commit-msg-hook (длина) · red: пересказ диффа «добавил X, поправил Y»
gi-body-excludes · в тело не идут: ход работы (его место — задача), разбор дефекта по шагам (репозиторий публичный), число без предиката · `security-disclosure.md` §«Публичные артефакты» плюс признак восстановимости · red: «улучшено на 30%» без предиката; шаги воспроизведения дефекта
gi-closes-last-line · `Closes #<N>` — последней строкой · ЗАВЕСТИ gi-closes-last-line · red: номер задачи в середине абзаца
gi-two-subjects-two-commits · два предмета в одном коммите — это два коммита; заголовок, которому нужна точка с запятой, сообщает об этом сам · ЗАВЕСТИ gi-two-subjects-two-commits · red: один коммит о двух предметах
gi-commit-form-by-hook · форму сообщения (строки выше) судит хук `commit-msg`, а не ревью: рецензент формой круга не открывает · ЗАВЕСТИ gi-commit-msg-hook (воркспейс — хук #770 без длины; corelib#25, kaname#356; kacho — задачи нет) · red: форма коммита — замечание ревью; принят заголовок длиннее 72 знаков

## Волна: сборка — агрегат (решение владельца 2026-09-24 «тестирование агрегатами а не каждую таску отдельно»)

gi-wave-assemble-only · в ветку волны задачи приходят только сборкой: «сборка k волны N» — задача и ветка от ветки волны, сданные задачи (коммит в ветке задачи) вливаются в неё `git merge --no-ff` каждая, состав доказан до прогона, PR сборки в волну вливается коммитом слияния (`gh pr merge --merge`), не схлопыванием; PR задачи в волну и догон волны в ветку задачи отменены · `gh pr list -R <репо> --base <волна> --state merged --json headRefName` — только ветки задач сборки; у слияния сборки в волну два родителя, `git log --first-parent --merges <волна>..<голова сборки>` называет её задачи · red: PR задачи в волну; сборка схлопнута; задача пришла в волну мимо сборки; в ветке задачи слияние волны
gi-asm-one-round · на сборку один раз: прогон конвейера на голове PR сборки (`testing-verdict.md#asm-verdict-runs-on-head`), ОДИН рецензент каждой задетой роли (задача с ✅ роли на своей голове — только дельта), `check-verifier` по задачам-проверкам, `wave-reviewer`; возвраты — в ветки задач, затем одно пересведение и один повторный прогон; затем посадочный и вливание; ⛔ или красное после них — PR сборки закрывается, задачи без ⛔ идут в сборку k+1 · `gh run list -R <репо> --branch <ветка сборки> --json headSha,workflowName` — на процесс не больше двух голов · red: прогон или круг ревью на задаче; третий прогон сборки; вливание до ✅ посадочного
gi-pr-manual-dispatch · открыл PR, а триггера PR в базу нет (kacho#2793, corelib#31, kaname#394) — тем же заходом `gh workflow run <файл> --ref <ветка>` КАЖДОГО процесса с `pull_request` и `workflow_dispatch` (воркспейс — `ci.yaml`: у него только `workflow_dispatch`); свод без `workflow_dispatch` (kacho `required-verdict.yml`) не встаёт, вердикт — по процессам · `gh run list -R <репо> --commit <headSha> --json workflowName,status,conclusion` — у каждого процесса прогон на голове · red: PR без проверок ждёт триггера, которого нет; запущен не каждый процесс PR

## Трекер — GitHub Issues: когда заводится задача

gi-feature-issue-first · фича (ресурс, API, раздел UI, кросс-доменное поведение) → задача ПЕРВОЙ, ветка с её номером, PR `Closes #<N>`, ссылка на PR — комментарием в задаче · ЗАВЕСТИ gi-feature-issue-first · red: ветка или PR, которым не предъявить задачу
gi-batch-one-per-session · фиксы и мелкий UX — ОДНА batch-задача на сессию («<область> bugfix batch — YYYY-MM-DD») · ЗАВЕСТИ gi-batch-one-per-session · red: десять задач на одну сессию фиксов
gi-trivia-no-issue · опечатка, однострочник, docs — без задачи, достаточно коммита · ЗАВЕСТИ gi-trivia-no-issue · red: задача на однострочник
gi-retro-backfill · существенный кусок без задачи заводится ретроспективно; тривию не бэкфиллить · ЗАВЕСТИ gi-retro-backfill · red: в истории работа, которой нечего предъявить
gi-find-own-issue · находка по дороге заводится СВОЕЙ задачей, а не чинится в чужом PR · ЗАВЕСТИ gi-find-own-issue · red: PR несёт правку не своего предмета
gi-zero-findings-aloud · ноль соседних находок — законный ответ, но названный вслух: «смотрел, чисто» отличимо от «не смотрел» только сказанным · ЗАВЕСТИ gi-zero-findings-aloud · red: отчёт без находок и без названного осмотренного места

## Разметка тела задачи

gi-task-body-four · тело задачи несёт четыре вещи: что · DoD · затронутые каталоги · артефакт · ЗАВЕСТИ gi-task-body-four · red: задача без DoD либо без артефакта
gi-blocked-by-label · блокер — строкой `Blocked by #<N>` И меткой `blocked`: словами без метки его не видит соседняя сессия · ЗАВЕСТИ gi-blocked-by-label · red: блокер прозой, метки нет
gi-role-line · исполнитель — строкой `**Роль:** <agent>` в теле: поля исполнителя у задачи нет, назначение — assignee, если учётка есть · ЗАВЕСТИ gi-role-line · red: роль выводится из текста, а не названа

## Состояние — метками, снимается ТЕМ ЖЕ действием

gi-state-by-labels · состояние — метками (`status:in-progress`, `status:test`) плюс сам факт open/closed; своего поля состояния не изобретать · ЗАВЕСТИ gi-state-by-labels · red: состояние прозой в теле вместо метки
gi-label-same-action · метка описывает ТЕКУЩЕЕ состояние: закрыл — снял в том же заходе; сдал на проверку — ЗАМЕНИЛ одну на другую, а не добавил вторую · `gh issue list -R <репо> --state closed --label status:test --limit 100 --json number -q '.[].number'` и то же для `status:in-progress` — вывод обязан быть ПУСТ · red: закрытая задача с `status:test`
gi-open-label-needs-artifact · `status:test` на открытой законен ровно пока есть артефакт, ждущий вливания её волны в ветку эпика (`gi-close-cascade`) · ЗАВЕСТИ gi-open-label-needs-artifact · red: метка без артефакта — «кто-то что-то делал», то есть ничего
gi-stale-label-blocks-capture · перепись выше прогоняется при закрытии волны и при завершении накопительной линии: пережившая метка ЗАПРЕЩАЕТ брать задачу, которую никто не ведёт, и запрет невидим · ЗАВЕСТИ gi-stale-label-blocks-capture · red: свободная задача выглядит чужой работой

## Каскад закрытия: задача, волна, эпик, `main` (решение владельца 2026-09-26)

Дословно, 2026-09-26: «не не не задачи закрываются сразу как только закрывается верхнестоящая задача. таск -> волна -> эпик -> main». Норма «задачи волны открыты до посадки эпика в `main`» им отменена; тела агентов и база диспетчера ссылаются сюда.

gi-close-cascade · уровень закрывается, когда влит в следующий (задача → волна → эпик → `main`), и закрытие верхнего тем же заходом закрывает всех его дочерних · `gh api --paginate repos/<репо>/issues/<волна>/sub_issues --jq '.[]|select(.state=="open")|.number'` у закрытой волны — вывод ПУСТ · red: волна закрыта, её задачи открыты; задача влитой волны ждёт `main`
gi-cascade-task-test · ветка задачи влита в сборку или в волну — тем же действием `status:in-progress` ЗАМЕНЁН на `status:test`; задача сборки k, чей PR влит в волну, — так же · ЗАВЕСТИ gi-cascade-task-test · red: задача в сборке с `status:in-progress`
gi-cascade-wave-closes-tasks · запрос волны влит в ветку эпика — `git-operator` тем же заходом закрывает волну и каждую её задачу записью: коммит работы задачи, коммит слияния запроса волны, исход предиката снятия с командой; метки состояния снимаются тем же действием · перепись `gi-close-cascade` и `gi-label-same-action` · red: закрывающая запись без коммита работы задачи; волна закрыта, задачи оставлены на потом
gi-cascade-no-auto-close · `Closes #<N>` GitHub исполняет только при вливании в ветку по умолчанию: ни PR сборки в волну, ни запрос волны в ветку эпика задачу не закроют, каскад — явное действие · ЗАВЕСТИ gi-cascade-no-auto-close · red: задачи влитой волны ждут авто-закрытия
gi-cascade-remainder · поставлено не всё — остаток заводится задачей следующей волны, исходная закрывается с волной и ссылкой на остаток; непоставленная (коммита её работы в запросе волны нет) переводится в следующую волну, не закрывается; PR сборки закрыт тупиком — её задачи идут в сборку k+1, задача сборки k закрывается записью о тупике; запрос волны снят — волна закрывается, её задачи переводятся · ЗАВЕСТИ gi-cascade-remainder · red: непоставленная задача закрыта с волной; остаток без своей задачи
gi-cascade-epic-main · эпик закрывается посадкой своего запроса в `main`; к ней его волны закрыты · `gh api --paginate repos/<репо>/issues/<эпик>/sub_issues --jq '.[]|select(.state=="open")|.number'` при посадке — вывод ПУСТ · red: эпик влит в `main` с открытой волной

## Снятие влитой ветки — шаг вливания, а не уборка (решение владельца 2026-09-26)

Дословно, 2026-09-26: «старые ветки которые вмержились не удаляются локально и внешне. Обнови рул если не ххватает инфы сделай обязательным.» Отсюда снятие — обязательный шаг режима merge у `git-operator` на каждом уровне каскада; тела агентов и база диспетчера ссылаются сюда.

gi-prune-same-pass · ветка, влитая в следующий уровень каскада (`gi-close-cascade`), снимается ТЕМ ЖЕ заходом, что вливание: голова сборки и ветки задач, сведённые в неё, — при вливании PR сборки в волну; ветка волны — при вливании её запроса в ветку эпика; ветка эпика — при посадке в `main`; снимается на origin, во всех клонах и её копия · перепись конца сессии `gi-prune-session-zero` · red: влитая ветка пережила заход своего вливания
gi-prune-remote · запрос вливается с `--delete-branch` (`gh pr merge <N> --merge --delete-branch`); влит без него — голова снимается тем же заходом; у веток задач сборки PR нет, их снимают явно: `flock -w 1800 ~/.cache/heavy-slots/interim.lock git push origin --delete <ветка>…` · настройка хостинга `delete_branch_on_merge=true` во всех четырёх репозиториях (kacho, kaname, corelib, kacho-workspace; замер 2026-09-26) снимает голову PR и только её; по каждой снятой `git ls-remote --heads origin <ветка>` пуст · red: голова влитого PR или ветка задачи влитой сборки лежит на origin
gi-prune-every-clone · локальная ветка снимается во ВСЕХ клонах (воркспейс, `project/kacho`, `project/kaname`, `project/corelib`): `git fetch --prune`; копия — `git worktree remove <копия>` при чистом дереве (`git -C <копия> status --porcelain` пуст); затем `git branch -D <ветка>`; грязная копия не снимается и идёт автору, `--force` не применяется · `scripts/branch-audit.sh <клон>` по каждому клону · red: ветка или копия влитой ветки в любом клоне; копия снята с незакоммиченным
gi-prune-commit-predicate · снимается только ветка, чья голова — предок сохраняемой цели: `git merge-base --is-ancestor <голова> origin/<цель>` с кодом 0 (цель задачи и сборки — волна, волны — эпик, эпика — `main`); работа в единственном экземпляре и ветка, в чьей копии идёт работа, не снимаются · `scripts/branch-audit.sh <клон> <ветка>…` тем же заходом перед снятием; пока #821 не влита, ветки эпика и волны вне набора стволов переписи — `BRANCH_AUDIT_TRUNK=origin/<цель>` · red: снята ветка, чья голова не предок цели; снятие по вердикту прошлого захода
gi-prune-session-zero · в конце сессии влитых ноль по каждому клону: раздел «ВЛИТЫ» `scripts/branch-audit.sh <клон>` пуст, `bash .claude/hooks/branches-clean.sh` молчит; сигнал хука «ВЛИТЫЕ ЛОКАЛЬНЫЕ ВЕТКИ» — поручение `git-operator` немедленно, а не фон · хук `branches-clean` на `UserPromptSubmit`: воркспейс и `project/kacho`, только предки `origin/main`, то есть нижняя граница; `project/kaname`, `project/corelib` и влитое в ветку эпика хук не осматривает — там вниманием, переписью конца сессии · red: сессия закрыта с влитой веткой; сигнал хука отложен как фон
gi-no-branch-revival · ветку, удалённую при вливании, заново не заводят и такого указания не пишут: работа уже в приёмнике, ссылка на неё — висяк · `git grep -n -P 'восста[н]\S*[^\n]{0,80}вет[к]|вет[к][^\n]{0,80}восста[н]' -- .claude scripts CLAUDE.md ':!.claude/backup'` — ни одного попадания о ветке · red: указание вернуть ветку, снятую при вливании
