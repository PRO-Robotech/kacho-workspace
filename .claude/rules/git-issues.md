gi-two-subjects-two-commits · два предмета — два коммита; заголовку нужна точка с запятой — это сказано им самим · ЗАВЕСТИ · red: один коммит о двух предметах

## Волна: сборка — агрегат (решение владельца 2026-09-24 «тестирование агрегатами а не каждую таску отдельно»)

gi-wave-assemble-only · в ветку волны задачи приходят только сборкой k — задачей и веткой от ветки волны: сданные задачи — `git merge --no-ff` каждая, состав доказан до прогона, PR сборки в волну — коммитом слияния; PR задачи в волну и догон волны в ветку задачи отменены · `gh pr list -R <репо> --base <волна> --state merged --json headRefName` — только ветки сборок · red: PR задачи в волну; сборка схлопнута; задача в волне мимо сборки; в ветке задачи слияние волны
gi-asm-one-round · на сборку один раз: прогон на голове её PR (`testing-verdict.md#asm-verdict-runs-on-head`), ОДИН рецензент каждой задетой роли (задача с ✅ роли — дельта), `check-verifier` по задачам-проверкам, `wave-reviewer`; возвраты — в ветки задач, одно пересведение и один повторный прогон, затем посадочный и вливание; ⛔ или красное после них — PR сборки закрыт, задачи без ⛔ — в сборку k+1 · `gh run list -R <репо> --branch <ветка сборки> --json headSha,workflowName` — не больше двух голов на процесс · red: прогон или круг ревью на задаче; третий прогон; вливание до ✅ посадочного
gi-pr-manual-dispatch · триггера PR в базу нет (kacho#2793, corelib#31, kaname#394) — тем же заходом `gh workflow run <файл> --ref <ветка>` КАЖДОГО процесса с `pull_request` и `workflow_dispatch`; свод без `workflow_dispatch` не встаёт, вердикт — по процессам · `gh run list -R <репо> --commit <headSha> --json workflowName,status,conclusion` · red: PR без проверок ждёт несуществующего триггера; запущен не каждый процесс PR

## Трекер — GitHub Issues: когда заводится задача

gi-feature-issue-first · фича (ресурс, API, раздел UI, кросс-доменное поведение) → задача ПЕРВОЙ, ветка с её номером, PR `Closes #<N>` · ЗАВЕСТИ · red: ветка или PR, которым не предъявить задачу
gi-batch-one-per-session · фиксы и мелкий UX — ОДНА batch-задача на сессию («<область> bugfix batch — YYYY-MM-DD»); безопасность — своей задачей (gi-security-finding-issue-now) · ЗАВЕСТИ · red: десять задач на сессию фиксов; находка о безопасности пунктом batch-задачи
gi-security-finding-issue-now · находку, важную и влияющую на безопасность, заводи задачей НЕМЕДЛЕННО, тем же заходом, в репозитории предмета (решение владельца 2026-09-20 «не забывай по ходу создавать задачи в гитхаб ишуе если это важное и влияет на безопасность») · tooling-gate check-19 — норма; срок — вниманием · red: находка доехала до конца волны отчётом, задачи нет
gi-security-issue-high-level-only · немедленность — о СРОКЕ, не об объёме: в задачу — высокоуровневая часть со ссылкой на дифф фикса, разбор не коммитится, рабочий каталог не называется · `security-disclosure.md` §«Публичные артефакты» · red: шаги воспроизведения уязвимости в публичной задаче; ссылка на `tmp/issue-<N>`
gi-trivia-no-issue · опечатка, однострочник, docs — без задачи, достаточно коммита · ЗАВЕСТИ · red: задача на однострочник
gi-retro-backfill · существенный кусок без задачи заводится ретроспективно; тривию не бэкфиллить · ЗАВЕСТИ · red: в истории работа, которой нечего предъявить
gi-find-own-issue · находка по дороге заводится СВОЕЙ задачей, а не чинится в чужом PR · ЗАВЕСТИ · red: PR несёт правку не своего предмета
gi-zero-findings-aloud · ноль соседних находок — законный ответ, названный вслух: «смотрел, чисто» от «не смотрел» отличимо лишь сказанным · ЗАВЕСТИ · red: отчёт без находок и без названного осмотренного места

## Разметка тела задачи

gi-epic-label-and-list · крупное или многодоменное — эпик (метка `epic`): цель, решения, декомпозиция, порядок по ГРАФУ ЗАВИСИМОСТЕЙ, DoD; дочерние — sub-issue; перечень `- [ ] #<N>` в теле необязателен, заведён — равен sub-issue · `scripts/cascade-census.sh`: расхождение — 1 · red: эпик без дочерних; тело и sub-issue расходятся; порядок по номеру, а не по графу
gi-task-body-four · тело задачи несёт четыре вещи: что · DoD · затронутые каталоги · артефакт · ЗАВЕСТИ · red: задача без DoD либо без артефакта
gi-blocked-by-label · блокер — строкой `Blocked by #<N>` И меткой `blocked`: без метки его не видит соседняя сессия · ЗАВЕСТИ · red: блокер прозой, метки нет
gi-role-line · исполнитель — строкой `**Роль:** <agent>` в теле; назначение — assignee, если учётка есть · ЗАВЕСТИ · red: роль выводится из текста, а не названа

## Каскад закрытия: задача, волна, эпик, `main` (решение владельца 2026-09-26)

Дословно, 2026-09-26: «не не не задачи закрываются сразу как только закрывается верхнестоящая задача. таск -> волна -> эпик -> main». Норма «задачи волны открыты до посадки эпика в `main`» им отменена; команды — `git-operator.md` §«Вливание и снятие».

gi-close-cascade · уровень закрывается, влитый в следующий (задача → волна → эпик → `main`), и тем же заходом закрывает дочерних · `scripts/cascade-census.sh <репо> <волна>` — 0 (расхождение sub-issue и тела, открытый дочерний — 1, дочерних ноль — 2), судит tooling-gate check-20 · red: волна закрыта, задачи открыты; задача ждёт `main`; «открытых ноль» без дочерних
gi-cascade-task-test · ветка задачи влита в сборку или волну, PR сборки — в волну: тем же действием `status:in-progress` ЗАМЕНЁН на `status:test` · ЗАВЕСТИ · red: задача в сборке с `status:in-progress`
gi-cascade-wave-closes-tasks · запрос волны влит в эпик — `git-operator` тем же заходом закрывает волну и каждую задачу записью: коммит работы, коммит слияния, исход предиката снятия · перепись `gi-close-cascade` · red: запись без коммита работы; задачи оставлены на потом
gi-cascade-no-auto-close · `Closes #<N>` исполняется лишь в ветке по умолчанию; в волне и эпике каскад — явное действие · ЗАВЕСТИ · red: задачи влитой волны ждут авто-закрытия
gi-cascade-remainder · остаток — задачей следующей волны; непоставленная (её коммита в запросе нет) переводится; сборка закрыта тупиком — задачи в k+1, её задача закрыта записью о тупике; запрос волны снят — задачи переводятся · ЗАВЕСТИ · red: непоставленная закрыта с волной; остаток без задачи
gi-cascade-epic-main · эпик закрывается посадкой в `main`, его волны к ней закрыты · `scripts/cascade-census.sh --children-closed <репо> <эпик>` перед посадкой — 0 (без ключа открытый эпик законно 0; ключ судит check-20) · red: эпик влит с открытой волной; готовность прочитана без ключа

## Снятие влитой ветки — шаг вливания, а не уборка (решение владельца 2026-09-26)

Дословно, 2026-09-26: «старые ветки которые вмержились не удаляются локально и внешне. Обнови рул если не ххватает инфы сделай обязательным.»

gi-prune-same-pass · влитая ветка снимается ТЕМ ЖЕ заходом, что вливание (сборка и её задачи, волна, эпик): origin, все клоны, копия · перепись `gi-prune-session-zero` · red: влитая пережила заход своего вливания
gi-prune-remote · вливание с `--delete-branch`; ветки задач сборки и не снятую голову — `git push origin --delete` под `interim.lock` · `git ls-remote --heads origin <ветка>` пуст · red: голова влитого PR или ветка задачи влитой сборки на origin
gi-prune-every-clone · локально — во ВСЕХ клонах (воркспейс, `project/kacho`, `project/kaname`, `project/corelib`), чистая копия — `git worktree remove`; грязная — автору, без `--force` · `scripts/branch-audit.sh <клон>` · red: влитая или её копия в любом клоне; снята копия с незакоммиченным
gi-prune-commit-predicate · при ВЛИВАНИИ снимаются голова, РАВНАЯ влитой (`--match-head-commit`), и её предки: `git merge-base --is-ancestor <голова> origin/<цель>` — 0; окно свежести не стоп · `BRANCH_AUDIT_FRESH_MIN=0 scripts/branch-audit.sh <клон> <ветка>…` · red: снята не-предок либо сдвинутая; влитая оставлена окном
gi-prune-census-predicate · снятие ПО ПЕРЕПИСИ (конец сессии, хук, исходник переноса) судит байты: ветка из «ВЛИТЫ» того же захода (признаки 1, 5, 6а, 6б), на origin — при голове переписи; строки (6в) не в счёт; стоп — единственный экземпляр, живая копия, окно свежести · `scripts/branch-audit-inject.sh` C, O, X, CM, CN; origin — I, AS, CH (#821, #851) · red: снята ветка вне «ВЛИТЫ» того же захода; голова origin снята сдвинутой
gi-prune-session-zero · в конце сессии влитых к снятию ноль по каждому клону и цели каскада (`main`, ветки открытых эпиков и волн), локально И на origin, `release/*` и исходник переноса тоже; цели, ветку по умолчанию и без своего коммита, пока она на origin, в копии или в окне, перепись не снимает; сигнал хука — немедленно · `scripts/branch-audit.sh` с `BRANCH_AUDIT_TRUNK`, `BRANCH_AUDIT_KEEP` — `к снятию 0` (инъекция CA–CN); хук `branches-clean` (G–I) — нижняя граница (#851) · red: сессия закрыта с влитой; живая волна снята; цель вне `BRANCH_AUDIT_KEEP`; локальная без своего коммита оставлена бессрочно
gi-no-branch-revival · ветку, удалённую при вливании, заново не заводят и такого указания не пишут · предикат — архив правила, раздел «Предикат gi-no-branch-revival»: пусто · red: в тексте оснастки есть указание на повторное заведение снятой ветки
