# Skill: hardening-audit-loop — массированный аудит до сходимости

Выработан на реальном прогоне: **11 итераций, кривая `10→5→2→1→0`** подтверждённых
находок по 8 code-heavy репо. Нашёл+починил HIGH BOLA (cross-project disclosure),
cache-poisoning, existence-oracle'ы, класс «missing per-call deadline» во всех
peer-клиентах, doc-truthfulness-ловушки, чужой-облако имя, stdlib-vuln, O(N²)-кэш.
Это нормативный harness: аудируй ТАК; отклонение — осознанно.

Companion-конспект (прозой): `obsidian/kacho/KAC/audit-loop-prompt.md`.

> даты последовательность агентов выставляет только диспетчер, а исполнитель не запускает

>

## 0. Когда применять / когда НЕТ

**Применять:**
- «Сделай полный/массированный аудит-рефакторинг», «доведи до 100% чистого и
  безопасного», «пройди по безопасности/утечкам/структуре/читаемости».
- Периодический hardening-sweep области или всего монорепо перед релизом.
- После крупного мёржа — проверить, не внесён ли класс дефектов из инвариантов ниже.

**НЕ применять:**
- Точечный известный багфикс → обычный TDD-флоу (RED→GREEN), не весь harness.
- Новая фича/RPC/ресурс → сначала APPROVED Given-When-Then (`acceptance-author` →
  `acceptance-reviewer`), это другой флоу (ban #1).
- Нужен < 1 раунда работы (один файл, одна строка) → просто почини, не разворачивай цикл.

**Кто что читает.** Петлю ведёт **диспетчер**: он раздаёт роли раунда агентам и по их
возвратам решает, что дальше (§2). Исполнитель берёт этот скил инструментом `Skill` ради
**своей** роли: `security-auditor` — §3 (определение дефекта) и §4 (роли «поиск» и
«опровержение»), `qa-test-engineer` — §2 шаг 6 (красный кейс края), `go-implementer` — §4 (роль
чинящего), `vault-scribe` — §5 (trail раунда).
Своей роли исполнитель не выходит и следующего агента не запускает — называет его заказом
в возврате (`CLAUDE.md` §«Контракт возврата»).

## 1. Harness — петля до сходимости

```
┌─ раунд N ── ведёт диспетчер, каждая клетка = запуск агента ─────────────┐
│ поиск       security-auditor, режим «поиск», на КАЖДУЮ область          │ → находки
│             отдельным запуском, 6 измерений, множество виденного входом │
│ дедуп       свежие = находки \ виденное  (ключ область:файл:краткое)    │ ← диспетчер сам
│ опроверж.   security-auditor, режим «опровержение», РОВНО одна находка  │ → подтверждённые
│             на запуск; держим real && тяжесть ∉ {LOW, INVALID}          │
│ ── 0 подтверждённых? → сухой раунд → СХОДИМОСТЬ, стоп ──────────────────│
│ красный     qa-test-engineer: видимая через край — newman-кейс до фикса │ → кейсы
│ фикс        go-implementer, один на область, строгий TDD, свой коммит   │ → ветки
└─────────────────────────────────────────────────────────────────────────┘
   → git-operator (push, PR) → ci-watcher (вердикт конвейера) →
     git-operator (вливание, снятие ветки) → виденное ∪= ключи → раунд N+1
```

**Стоп-критерий**: один «сухой» раунд (0 подтверждённых после опровержения) ⇒ сходимость.
Ищущие каждый раунд свежие (без памяти о прошлых) — поэтому множество виденного живёт
**у диспетчера** и приходит агенту входом задания, иначе раунд топчется на голове списка
(`.claude/agents/security-auditor.md`, режим «поиск»).

**Критично для сходимости**: дедуп новых находок против **виденного** (всё, что уже
поднимали), а НЕ против подтверждённого. Иначе отклонённые опровержением находки всплывают
каждый раунд и петля не сходится.

**Всё подтверждённое — в том же раунде (non-negotiable)**: фикс берёт ВСЁ подтверждённое
(все области, все измерения, и LOW когда включена низкая планка, §4). Никакого частичного
фикса, никакого «follow-up-тикет / out-of-scope / на потом» — отложить подтверждённый дефект
= внести тех-долг (ban #11). Единственная легитимная отсрочка — фикс, физически требующий
другого репозитория (`kaname`): он берётся **следующим раундом** по графу сборки
(`polyrepo.md`), а не откладывается бессрочно; часть внутри своего дерева всё равно делается
сразу. Стоп только по «сухому» раунду, а не «нашли, но часть оставили».

## 2. Как ведётся раунд

**Внешнюю петлю ведёт ДИСПЕТЧЕР**: раунд — это последовательность запусков существующих
агентов, а не один вызов чего-то, что запускает агентов внутри себя. Вложенных запусков нет
(`disallowedTools: Agent` у каждого исполнителя), поэтому и множество виденного, и счёт
раундов, и решение о сходимости живут **в контексте диспетчера**: он получает их только
блоками ВОЗВРАТ и передаёт дальше заданием.

**Шаг за шагом (диспетчер):**

1. Инициализация: виденное = пусто, раунд = 1, подтверждённое за все раунды = пусто.
2. **Поиск.** На каждую область — свой запуск `security-auditor` в режиме «поиск». В задании:
   область и пути, ревизия, планка тяжести, множество виденного (ключ `область:файл:краткое`).
   Из возврата берутся находки, объём осмотренного и ревизия; «ноль находок» засчитывается
   только вместе с объёмом (`.claude/rules/testing.md` §Гейт на класс).
3. **Дедуп.** Диспетчер сам вычитает виденное из поднятого. Сам он ничего не разведывает:
   вычитание идёт по ключам из возвратов, а не по дереву.
4. **Опровержение.** На каждую свежую находку — **отдельный** запуск `security-auditor` в
   режиме «опровержение», с одной находкой целиком и без перечня остальных. Держим
   `подтверждена` и тяжесть ∉ {LOW, INVALID} — планку называет задание (§4).
5. Подтверждённых ноль → **сухой раунд, сходимость достигнута**, дальше §5 (отчёт и trail).
   Стоп.
6. **Фикс.** Находка, видимая через край, — сперва красный newman-кейс `qa-test-engineer`
   (`# verifies <issue>`, `testing-newman.md#flow-bug-regression`): кейс края пишет тестировщик,
   не чинящий. Затем на каждую область — `go-implementer` со строгим TDD (красный по нужной
   причине → фикс → зелёный; кейс края он зеленит, не правя) и всем подтверждённым по этой
   области сразу. Ветка `fix/audit-rN`, **коммитит агент сам**; push, PR и вливание — не его шаг.
7. **Посадка.** `git-operator` — push и `gh pr create`; `ci-watcher` — вердикт конвейера
   (флейки `gh run rerun --failed`: rate-limit 429, ошибка потока прокси, таймаут выкачивания
   образа testcontainers — это **не** находка и не красное); зелёный конвейер → `git-operator`
   вливает и снимает ветку.
8. Виденное ∪= ключи раунда, раунд++, вернуться к шагу 2.

Роли раунда не переставляются местами и не совмещаются в одном запуске: ищущий и
опровергающий — разные запуски одного агента **именно потому**, что у опровержения вход
«одна находка без соседей», а у поиска — область целиком.

**Область — не список из головы.** Набор берётся предикатом на рабочей ревизии:
`ls -d project/kacho/services/*/ project/kacho/gateway project/kacho/pkg project/kacho/internal`
(на `project/kacho@b5fa093341f` это шесть служб — `compute`, `geo`, `nlb`, `registry`,
`storage`, `vpc` — плюс край, общие пакеты и гейты продукта). `kaname` — отдельный
репозиторий и отдельный раунд. Стенд, UI и `proto/` — по необходимости отдельными областями.

> **Отозвано 2026-09-17: «репо-набор (code-heavy): `kacho-corelib · iam · vpc · compute · geo ·
> nlb · api-gateway · registry`».** Список назывался поимённо и относился к полирепо; разработка
> идёт в одном репозитории продукта (`CLAUDE.md` §«Топология»), а поимённый список областей
> устаревает молча — поэтому здесь предикат.

## 3. Девять инвариантов Kachō — определение «дефекта»

Ищущий меряет код против них. Источник истины — правила, **закреплённые за
`security-auditor`** (`00-kacho-core`, `security`, `security-hardening`,
`security-disclosure`, `rag`, `writing` — колонка «закреплено за агентами» в
`.claude/rules/MANIFEST.md`); правило вне этого набора берётся из git на рабочей ревизии и
называется координатой, а не пересказывается. Находка обязана привязываться к одному из
инвариантов + нести **конкретный failure-сценарий**:

1. **AuthN+AuthZ на КАЖДОМ RPC обоих листенеров** (public и :9091); «internal =
   trusted» — запрещённое допущение (`security.md`).
2. **Object-scoped authz** там, где метод оперирует конкретным объектом по
   caller-supplied id (BOLA / existence-oracle / cross-project disclosure — HIGH).
3. **Per-call deadline на КАЖДОМ внешнем вызове** — `context.WithTimeout`, не полагаться
   на inbound ctx; `retry.OnUnavailable` не ограничивает один зависший вызов
   (`architecture.md`). Все sibling-методы клиента — один configured-timeout.
4. **No leak**: pgx/SQL-текст в INTERNAL → фикс. opaque-текст; инфра-топология — только
   в `Internal*` (`security.md`).
5. **Doc-truthfulness**: комментарий обязан совпадать с кодом;
   misleading-security-comment = trap (`architecture.md`).
6. **Within-service инвариант — на DB-уровне** (FK/UNIQUE/EXCLUDE/CHECK/CAS/xmin/
   SKIP-LOCKED), не software TOCTOU (`data-integrity.md`).
7. **Ban #2** — ни одного упоминания чужих облаков в коде/доках/env/именах.
8. **Concurrency**: гонки, second-writer-wins, wg-drain, O(N²)/unbounded рост.
9. **LEAN**: dead/vestigial код/ветки/типы — удалять вместе с тестами (ban #11).

## 4. Три роли — и какой агент каждую несёт

Роль называется **заданием**: агент без названного режима и планки работу не начинает.

- **Ищущий** — `security-auditor`, режим «поиск», запуск на область: скептик-аудитор,
  6 измерений, **только высокая и средняя тяжесть**, «не выдумывай мелочи и вкусовщину»,
  обязателен конкретный сценарий отказа + направление фикса + «видна через край: да | нет». Читает узкие файлы предмета и
  `obsidian/kacho/{resources,rpc,edges}/`, а не 50-килобайтный README. В возврате — объём
  осмотренного и ревизия.
- **Опровергающий** — `security-auditor`, режим «опровержение», запуск на **одну** находку:
  по умолчанию находка ложна, пока не подтверждена **по коду**; проверяется защита выше по
  стеку и «так задумано»; тяжесть правится в обе стороны и называется исправленной. Диспетчер
  отбрасывает `LOW`/`INVALID` — **поэтому LOW «так задумано» не чинятся**.
- **Чинящий** — `go-implementer`, запуск на область: **строгий TDD** — падающая проба **по
  нужной причине** (красный) → фикс в корне → зелёный. Безопасность, утечку и гонку запирать
  на уровне **наблюдаемого** (вычищенный принципал; повторяемый код вместо `PermissionDenied`;
  применённый per-call deadline; вызов возвращается ~за таймаут под фальшивым блокером с
  `-race`), а не только по gRPC-коду (`testing.md`). Красный Go — его; красный кейс края —
  `qa-test-engineer` (шаг 6), чинящий его не пишет. Doc-truth: к корректному поведению
  приводятся **и** комментарий, **и** код. Чинит **ВСЕ** переданные ему подтверждённые
  находки своей области одной веткой (§1) — не выбирает подмножество и не откладывает; только
  ложноположительное и кросс-репозиторное помечает возвратом, а не форсит. Ветка
  `fix/audit-rN`, **коммит свой**; push и PR — заказ `git-operator` в возврате.

Формулировки ролей живут **здесь**: это единственное их место с 2026-09-17 (прежде — промты в
bundled-скрипте, отозвано вместе с запуском раунда через Workflow). Задание агенту
составляется по абзацу его роли, а не пересказом по памяти.

**Планка тяжести**: по умолчанию держим тяжесть ∉ {LOW, INVALID} — LOW «так задумано» не
чинятся (экономия на мелочах). Когда владелец просит «учитывать и LOW» / «вычистить всё,
включая мелочи» — планка **называется в задании обеим ролям**: (а) ищущий репортит и LOW,
но только РЕАЛЬНЫЕ (конкретное, пусть мелкое, следствие — не форматирование и не вкусовщина);
(б) опровергающий паркует ложноположительное в `INVALID`, **не** в LOW; (в) диспетчер держит
всё, кроме `INVALID`. Правило «всё подтверждённое — в том же раунде» (§1) действует и на LOW:
включил LOW → чинишь и LOW сразу.

## 5. Сходимость и отчёт

- Декларация «хватит / 100% выполнено» — **только** после сухого раунда (0 подтверждённых на
  максимальной планке) И зелёного конвейера на стволе по каждой затронутой области; вердикт
  конвейера приносит `ci-watcher`, диспетчер его не добывает сам.
- **Разбивка по тяжести**: считать подтверждённые высокой и средней (плюс низкой, если планка
  §4 её включала). При планке по умолчанию низких 0 — так устроен фильтр, и выдавать это за
  охват нельзя; при включённой низкой планке — честно назвать и её число.
- **Trail** (обязателен, `vault.md`): `obsidian/kacho/KAC/audit-hardening-<date>.md` —
  таблица сходимости по раундам, список PR по областям, «Затронутые сущности vault», DoD.
  Пишет его `vault-scribe` по возвратам раунда, диспетчер заказывает его **после каждого
  вливания**, а не одним разом в конце.
- **Абсолютная «100%-чистота» асимптотична** — честная формулировка: «systematic
  adversarially-verified аудит сошёлся к нулю находок на максимальной планке», а не
  «дефектов больше не существует».

## 6. Грабли петли

- **Раунд, собранный в один запуск.** Сложить поиск, опровержение и фикс в одного агента —
  значит потерять опровержение: тот, кто нашёл, подтверждает своё. Роли — разные запуски, и
  ставит их диспетчер.
- **Состояние петли в голове исполнителя.** Множество виденного, номер раунда и решение о
  сходимости живут у диспетчера; исполнителю они приходят заданием, а возвращаются возвратом.
  Что не попало в блок ВОЗВРАТ — до следующего раунда не доедет.
- Дедуп против **виденного**, не против подтверждённого (§1) — иначе не сходится.
- Ищущий читает узкие записки vault, а не 50-килобайтный README (`vault.md`).
- Флейк конвейера ≠ находка: `gh run rerun --failed` (429 golangci-action, ошибка потока
  proxy.golang.org, таймаут выкачивания образа testcontainers). Отличать флейк от красного —
  предмет `ci-watcher` (`testing-verdict.md`).
- commitlint: комментарии и сообщения проб не должны матчить `#\d` (regex ссылки на issue) —
  формулировать словами.
- Чинящий трогает **только прод-код своей области**; кросс-репозиторный фикс (`kaname`) —
  пометкой в возврате, отдельным раундом по графу сборки (`polyrepo.md`).
- Никаких `Co-Authored-By` и прочих трейлеров атрибуции; никакого прямого push в `main`
  (`git-issues.md`).
