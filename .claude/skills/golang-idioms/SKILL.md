# Skill: golang-idioms — горутины, тестовые ловушки, пул, бенчмарк

**Мой вопрос:** что в диффе работает на зелёном прогоне и ломается под нагрузкой, отменой или
сборкой мусора? Каждая норма — строкой `id · норма · держатель · red`, где red — признак,
видимый в диффе, и `потому что` — одной фразой. Держатель «вниманием» значит: машинного
держателя нет, и находку несёт рецензент.

Что здесь НЕ повторяется, потому что уже стоит в чек-листе `go-style-reviewer`: `ctx` не хранится в
структурах; `context.WithTimeout` на каждом внешнем вызове; `defer cancel()` и `defer rows.Close()`
сразу после создания; `errors.Is`/`errors.As` и `%w`.

Версия Go продукта — по `go.mod`: в `kacho`, `kaname` и `corelib` стоит `go 1.26.0` и
`golang.org/x/sync v0.22.0` (измерено `git show origin/main:go.mod` @ kacho `ffbe930dbe`, kaname
`8a84dcff6`, corelib `798523a`, 2026-10-08). Минимальная версия названа у каждой нормы, которая от
неё зависит; ниже неё норма не применяется.

## §1. Горутина и канал

gi-goroutine-exit · у каждой запущенной горутины есть путь завершения — `ctx.Done()` в каждом `select` с отправкой или приёмом, закрытие входного канала или явный сигнал — и тот, кто её дожидается · вниманием; `goleak` ниже · red: `go func` с отправкой в канал без `select` на `ctx.Done()`; вызывающий читает из канала меньше, чем в него пишут
— потому что горутина, заблокированная на отправке, не собирается сборщиком: она живёт до конца процесса вместе со всем, что держит.

gi-chan-closed-by-writer · канал закрывает единственный пишущий, обычно `defer close(ch)` в той же горутине; читатель не закрывает никогда; в сигнатуре направление (`<-chan T`, `chan<- T`) · компилятор — за направлением; вниманием — за закрытием · red: `close(ch)` на стороне читателя; два места с `close` одного канала; `chan T` в возвращаемом значении
— потому что отправка в закрытый канал и повторное закрытие — паника, а знать, что отправок больше не будет, может только пишущий.

gi-goleak · пакет, чей дифф запускает горутины, несёт `goleak.VerifyTestMain(m)` в `TestMain` либо `defer goleak.VerifyNone(t)` в тесте этого пути · ЗАВЕСТИ gi-goleak — `go.uber.org/goleak` нет ни в одном из трёх `go.mod` (измерено выше; файлов с `goleak` — 0); первая полоса с такой нормой заводит зависимость тем же изменением · red: новый `go ` в непробном коде пакета, в тестах которого нет `goleak`
— потому что `-race` ловит гонку, а не утечку: висящая горутина проходит любой прогон зелёным.

```go
// red: пишущий без выхода, вызывающий берёт одно значение из десяти
go func() { for i := 0; i < n; i++ { ch <- i } }()
// норма: пишущий закрывает и выходит по отмене; вызывающий отменяет
go func() {
	defer close(ch)
	for i := 0; i < n; i++ {
		select {
		case ch <- i:
		case <-ctx.Done():
			return
		}
	}
}()
```

## §2. Группа горутин и первая ошибка

gi-errgroup-first-error · когда нужна первая ошибка и отмена остальных, — `g, ctx := errgroup.WithContext(ctx)`, и в `g.Go` уходит этот `ctx`; `sync.WaitGroup` остаётся там, где ошибок нет (с Go 1.25 — `wg.Go`) · вниманием · red: `WaitGroup` плюс мьютекс плюс срез ошибок; `errs[0]` после `wg.Wait()`; в `g.Go` замкнут внешний `ctx`, а не полученный из `WithContext`
— потому что ручной сбор ждёт всех даже после первого отказа, и соседи, висящие на внешнем вызове, держат запрос до его дедлайна.

gi-errgroup-limit · число одновременных горутин на вход неограниченного размера ограничено `g.SetLimit(n)` с именованной константой · вниманием · red: `g.Go` или `go` в цикле по срезу из запроса без предела; самодельный семафор рядом с `errgroup`
— потому что размер входа выбирает клиент, а число соединений пула и дескрипторов — нет.

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(maxParallelFetch)
for _, id := range ids {
	g.Go(func() error { return get(ctx, id) }) // Go 1.22+: id своя на итерации
}
return g.Wait()
```

## §3. Тестовые ловушки

gi-test-fatal-own-goroutine · `t.Fatal`, `t.FailNow`, `t.Skip` и `require.*` вызываются только из горутины теста; из порождённой ошибка уходит каналом или через `t.Error` · `go vet` анализатор testinggoroutine — за методами `t`; в `kacho` — `govet` в `.golangci.yml`, файлы `_test.go` из него не исключены (прочитано @ `ffbe930dbe`); `require.*` анализатор не видит — вниманием · red: `t.Fatal` или `require.` внутри `go func` в тесте
— потому что `FailNow` завершает лишь ту горутину, где вызван: тест идёт дальше, и падение приходит позже и не там.

gi-parallel-loopvar · с Go 1.22 переменная цикла своя на каждой итерации, и `t.Parallel()` в `t.Run` её не теряет; `tt := tt` — признак кода старше 1.22, а не дефект · `copyloopvar` в `.golangci.yml` `kacho` (прочитано @ `ffbe930dbe`) снимает лишнюю копию · red: находка рецензента о «потере переменной цикла» в модуле с `go ≥ 1.22` — ложная; дефект — `t.Parallel()` в подтесте, разделяющем изменяемую фикстуру с соседом
— потому что семантику переменной цикла задаёт строка `go` в `go.mod`, а не привычка.

```go
// red: FailNow из чужой горутины — vet: call to (*testing.T).Fatal from a non-test goroutine
go func() { if err := work(); err != nil { t.Fatal(err) } }()
// норма
errc := make(chan error, 1)
go func() { errc <- work() }()
if err := <-errc; err != nil { t.Fatal(err) }
```

## §4. Пул объектов

gi-pool-no-alias · в `sync.Pool` возвращается только буфер, на который не ссылается ничего из результата: байты копируются (`bytes.Clone`, `string(b.Bytes())`) до `Put`; перед `Put` — `Reset` · вниманием · red: `return b.Bytes()` при `defer pool.Put(b)`; срез или указатель из пулового объекта уходит в ответ, канал или кэш
— потому что следующий `Get` перепишет эти байты у чужого запроса, а прогон без нагрузки этого не покажет: пул может отдать и новый объект.

```go
defer bufPool.Put(b)
return b.Bytes()            // red: следующий Get перепишет
return bytes.Clone(b.Bytes()) // норма
```

## §5. Нулевое значение и копирование

gi-nil-map-write · карта в поле типа создаётся конструктором или ленивой инициализацией под тем же мьютексом; запись в нулевую карту не допускается · вниманием · red: тип с полем `map[...]` без конструктора, создающего её, и запись в поле; `var m map[K]V` с последующей записью
— потому что чтение нулевой карты молча отдаёт нулевое значение, а запись — паника на первом же вызове.

gi-lock-by-value · тип с `sync.Mutex`, `sync.RWMutex`, `sync.WaitGroup`, `sync.Once` или `atomic.*` передаётся и принимается только указателем; методы — с приёмником-указателем · `go vet` анализатор copylocks; в `kacho` — `govet` в `.golangci.yml` · red: приёмник по значению у такого типа; такой тип в `range` по значению или аргументом по значению
— потому что копия несёт свой замок, и критическая секция перестаёт быть общей.

```go
func (c Counter) Inc(k string)  // red: vet: Inc passes lock by value
func (c *Counter) Inc(k string) // норма; m создаётся в NewCounter
```

## §6. Горячий путь

gi-bench-allocs · дифф, добавляющий цикл с аллокацией на пути запроса или в общем фундаменте, несёт бенчмарк этого пути с `b.ReportAllocs()`; число `allocs/op` до и после — в описании изменения · ЗАВЕСТИ gi-bench-allocs — бенчмарк `kacho` один на дерево (`git grep -l 'func Benchmark' origin/main -- '*.go'` → 1 @ `ffbe930dbe`) · red: `append` без предвыделения, `fmt.Sprintf` или конструирование в цикле по входу запроса, бенчмарка в том же PR нет
— потому что «не медленно» без числа — мнение, а аллокация на элемент растёт вместе с размером ответа.

С Go 1.24 тело бенчмарка — `for b.Loop()`: подготовка до цикла не входит в замер, и компилятор не
выбрасывает результат. Ниже 1.24 — `for i := 0; i < b.N; i++` с `b.ResetTimer()` после подготовки.

```go
func BenchmarkRender(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() { // Go 1.24+
		_ = Render("alice")
	}
}
```

## §7. Как проверены примеры

Каждая пара red/норма этого скила собрана в одноразовом модуле вне дерева (go1.26.8, `x/sync
v0.22.0`, `goleak v1.3.0`, 2026-10-08): `go vet` по нормам — код 0, по red — код 1 с двумя
находками (copylocks, testinggoroutine); `go build ./...` — 0; `go test -race` по нормам — пять
тестов зелёные, по red — `goleak` нашёл утечку, запись в nil-map дала панику, `FetchAll` на
`WaitGroup` не отменил соседа и упал по `-timeout 5s`, буфер пула перезаписан вторым вызовом;
бенчмарк — `1 allocs/op`. Модуль снят; пример, который правится, перепроверяется тем же набором
команд, а не прочтением.
