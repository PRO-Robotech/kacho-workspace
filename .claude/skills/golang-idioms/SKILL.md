# Skill: golang-idioms — горутины, тестовые ловушки, пул, бенчмарк

**Мой вопрос:** что в диффе работает на зелёном прогоне и ломается под нагрузкой, отменой или
сборкой мусора? Каждая норма — строкой `id · норма · держатель · red`, где red — признак,
видимый в диффе, и `потому что` — одной фразой. Держатель «вниманием» значит: машинного
держателя нет, и находку несёт рецензент.

Что здесь НЕ повторяется, потому что уже стоит в чек-листе `go-style-reviewer`: `ctx` не хранится в
структурах; `context.WithTimeout` на каждом внешнем вызове; `defer cancel()` и `defer rows.Close()`
сразу после создания; `errors.Is`/`errors.As` и `%w`. Не повторяется и запуск слушателей процесса
(публичный, внутренний, ожидание остановки): это `evgeniy` §9 K.4 и AP-7, `godzila` §14 и AP-7 —
горутина `srv.Serve` без распространения отказа. Здесь — горутины пути запроса и фоновых работ.

Версия Go продукта — по `go.mod`: в `kacho`, `kaname` и `corelib` стоят `go 1.26.0`,
`toolchain go1.26.8` и `golang.org/x/sync v0.22.0` (измерено `git show origin/main:go.mod` @ kacho
`ffbe930dbe`, kaname `8a84dcff6e`, corelib `3665139773`, 2026-10-08).

Версия у нормы бывает двух родов, и путать их нельзя. Наличие API (`wg.Go` — 1.25, `b.Loop` —
1.24) задаёт **инструментарий**: под go1.24.13 `wg.Go` не собирается всегда (`wg.Go undefined`), а
под go1.26.8 модуль со строкой `go 1.23` собирается с обоими (код 0) — строку `go` видит лишь
`go vet` (анализатор stdversion, код 1: `sync.Go requires go1.25 or later`). Семантику переменной
цикла задаёт, наоборот, **строка `go`** в `go.mod` (§3).

## §1. Горутина и канал

gi-goroutine-exit · у каждой запущенной горутины есть путь завершения — `ctx.Done()` в каждом `select` с отправкой или приёмом, закрытие входного канала или явный сигнал — и тот, кто её дожидается · вниманием; `goleak` ниже · red: `go func` с отправкой в канал без `select` на `ctx.Done()`; вызывающий читает из канала меньше, чем в него пишут
— потому что горутина, заблокированная на отправке, не собирается сборщиком: после пяти `runtime.GC()` она на месте всегда (20 прогонов из 20) и живёт до конца процесса вместе со всем, что держит.

gi-chan-closed-by-writer · канал закрывает единственный пишущий, обычно `defer close(ch)` в той же горутине; читатель не закрывает никогда; в сигнатуре направление (`<-chan T`, `chan<- T`) · компилятор — за направлением (отправка в `<-chan T` — ошибка сборки всегда); вниманием — за закрытием · red: `close(ch)` на стороне читателя; два места с `close` одного канала; `chan T` в возвращаемом значении
— потому что отправка в закрытый канал и повторное закрытие — паника всегда (по 20 прогонов из 20), а знать, что отправок больше не будет, может только пишущий.

gi-goleak · пакет, чей дифф запускает горутины, несёт `goleak.VerifyTestMain(m)` в `TestMain` либо `defer goleak.VerifyNone(t)` в тесте этого пути · ЗАВЕСТИ gi-goleak — `go.uber.org/goleak` нет ни в одном из трёх `go.mod` и ни в одном `.go`-файле (`git grep -l goleak origin/main -- '*.go' '*go.mod'` → 0 в каждом @ ревизиях выше); в `go.sum` всех трёх он есть — транзитивно, импорта нет; первая полоса с такой нормой заводит зависимость тем же изменением · red: новый `go ` в непробном коде пакета, в тестах которого нет `goleak`
— потому что `-race` ловит гонку, а не утечку: тест с висящей горутиной под `-race` зелёный всегда (20 прогонов из 20), а тот же тест с `goleak.VerifyNone` красный всегда (20 из 20).

```go
// red: пишущий без выхода, вызывающий берёт одно значение из десяти
go func() { for i := 0; i < n; i++ { ch <- i } }()
// норма: пишущий закрывает и выходит по отмене; вызывающий отменяет
go func() {
	defer close(ch)
	for i := 0; i < n; i++ {
		select {
		case ch <- i:
		case <-ctx.Done():
			return
		}
	}
}()
```

## §2. Группа горутин и первая ошибка

gi-errgroup-first-error · когда нужна первая ошибка и отмена остальных, — `g, ctx := errgroup.WithContext(ctx)`, и в `g.Go` уходит этот `ctx`; `sync.WaitGroup` остаётся там, где ошибок нет (при инструментарии от 1.25 — `wg.Go`) · вниманием · red: `WaitGroup` плюс мьютекс плюс срез ошибок; `errs[0]` после `wg.Wait()`; в `g.Go` замкнут внешний `ctx`, а не полученный из `WithContext`
— потому что ручной сбор ждёт всех даже после первого отказа, и соседи, висящие на внешнем вызове, держат запрос до его дедлайна: `FetchAll` на `WaitGroup` без дедлайна упирается в таймаут теста всегда (20 из 20), на `errgroup.WithContext` возвращает первую ошибку меньше чем за секунду всегда (20 из 20).

gi-errgroup-limit · число одновременных горутин на вход неограниченного размера ограничено `g.SetLimit(n)` с именованной константой · вниманием · red: `g.Go` или `go` в цикле по срезу из запроса без предела; самодельный семафор рядом с `errgroup`
— потому что размер входа выбирает клиент, а число соединений пула и дескрипторов — нет.

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(maxParallelFetch)
for _, id := range ids {
	g.Go(func() error { return get(ctx, id) }) // строка go ≥ 1.22: id своя на итерации
}
return g.Wait()
```

## §3. Тестовые ловушки

gi-test-fatal-own-goroutine · `t.Fatal`, `t.FailNow`, `t.Skip` и `require.*` вызываются только из горутины теста; из порождённой ошибка уходит каналом или через `t.Error` · `go vet` анализатор testinggoroutine — за методами `t`, находка всегда; в `kacho` — `govet` в `.golangci.yml`, файлы `_test.go` из него не исключены (прочитано @ `ffbe930dbe`); `require.*` vet не видит, его видит `testifylint` проверкой `go-require` (включена по умолчанию; golangci-lint 2.12.2 — код 1 всегда), а в `.golangci.yml` `kacho` `testifylint` не включён — ЗАВЕСТИ gi-test-fatal-own-goroutine: `testifylint` в `linters.enable` · red: `t.Fatal` или `require.` внутри `go func` в тесте
— потому что `FailNow` завершает лишь ту горутину, где вызван: строки теста после неё исполняются всегда (20 из 20), и провал засчитан лишь по завершении теста, когда его следствия уже прошли.

gi-parallel-loopvar · при строке `go ≥ 1.22` переменная цикла своя на каждой итерации, и `t.Parallel()` в `t.Run` её не теряет; `tt := tt` — признак кода старше 1.22, а не дефект · `copyloopvar` в `.golangci.yml` `kacho` (прочитано @ `ffbe930dbe`) находит лишнюю копию всегда (код 1) · red: `t.Parallel()` в `t.Run`, тело которого пишет в переменную, объявленную вне `t.Run` (карта, срез, поле общей фикстуры) — `-race` даёт `DATA RACE` в 16 из 20 прогонов (приёмка мерила 14 из 20); зелёный прогон дефекта не опровергает
— потому что семантику переменной цикла задаёт строка `go` в `go.mod`, а не привычка (три замыкания в цикле дают `3 3 3` при `go 1.21` и `0 1 2` при `go 1.22` — всегда): находка «потеряна переменная цикла» при `go ≥ 1.22` ложная, а общая изменяемая фикстура параллельных подтестов — нет.

```go
// red: FailNow из чужой горутины — vet: call to (*testing.T).Fatal from a non-test goroutine
go func() { if err := work(); err != nil { t.Fatal(err) } }()
// норма
errc := make(chan error, 1)
go func() { errc <- work() }()
if err := <-errc; err != nil { t.Fatal(err) }
```

## §4. Пул объектов

gi-pool-no-alias · в `sync.Pool` возвращается только буфер, на который не ссылается ничего из результата: байты копируются (`bytes.Clone`, `string(b.Bytes())`) до `Put`; `Reset` — после `Get`, до первой записи · вниманием · red: `return b.Bytes()` при `defer pool.Put(b)`; срез или указатель из пулового объекта уходит в ответ, канал или кэш
— потому что следующий `Get` перепишет эти байты у чужого запроса. Зелёный прогон дефекта не опровергает: без `-race` перезапись видна в 200 вызовах из 200 в 20 прогонах из 20, под `-race` пул намеренно роняет часть `Put`, и перезапись видна лишь в части вызовов — от 137 до 162 из 200 в 20 прогонах (приёмка мерила 146–152); исход вероятностный.

```go
defer bufPool.Put(b)
return b.Bytes()            // red: следующий Get перепишет
return bytes.Clone(b.Bytes()) // норма
```

## §5. Нулевое значение и копирование

gi-nil-map-write · карта в поле типа создаётся конструктором или ленивой инициализацией под тем же мьютексом; запись в нулевую карту не допускается · вниманием · red: тип с полем `map[...]` без конструктора, создающего её, и запись в поле; `var m map[K]V` с последующей записью
— потому что чтение нулевой карты молча отдаёт нулевое значение, а запись — паника на первом же вызове (то и другое — всегда, 20 из 20).

gi-lock-by-value · тип с `sync.Mutex`, `sync.RWMutex`, `sync.WaitGroup`, `sync.Once` или `atomic.*` передаётся и принимается только указателем; методы — с приёмником-указателем · `go vet` анализатор copylocks, находка всегда; в `kacho` — `govet` в `.golangci.yml` · red: приёмник по значению у такого типа; такой тип в `range` по значению или аргументом по значению
— потому что копия несёт свой замок, и критическая секция перестаёт быть общей: восемь горутин, зовущих `Inc` с приёмником по значению, дают под `-race` `DATA RACE` в 20 из 20 прогонов — исход вероятностный, зелёный прогон дефекта не опровергает.

```go
func (c Counter) Inc(k string)  // red: vet: Inc passes lock by value
func (c *Counter) Inc(k string) // норма; m создаётся в NewCounter
```

## §6. Горячий путь

gi-bench-allocs · дифф, добавляющий цикл с аллокацией на пути запроса или в общем фундаменте, несёт бенчмарк этого пути с `b.ReportAllocs()`; число `allocs/op` до и после — в описании изменения · ЗАВЕСТИ gi-bench-allocs — бенчмарк `kacho` один на дерево (`git grep -l 'func Benchmark' origin/main -- '*.go'` → 1 @ `ffbe930dbe`) · red: `append` без предвыделения, `fmt.Sprintf` или конструирование в цикле по входу запроса, бенчмарка в том же PR нет
— потому что «не медленно» без числа — мнение, а аллокация на элемент растёт вместе с размером ответа.

При инструментарии от 1.24 тело бенчмарка — `for b.Loop()`: по документации (`go doc
testing.B.Loop`) подготовка до цикла не входит в замер, а аргументы и результаты вызовов в теле
удерживаются живыми, и компилятор тело не выбрасывает. Под инструментарием ниже 1.24 —
`for i := 0; i < b.N; i++` с `b.ResetTimer()` после подготовки.

```go
func Render(name string) string { return fmt.Sprintf("hello, %s", name) }

func BenchmarkRender(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() { // инструментарий от 1.24
		_ = Render("alice")
	}
}
```

## §7. Как проверены примеры

Каждое утверждение об исходе инструмента или прогона в этом скиле измерено в одноразовом модуле
вне дерева (go1.26.8, `x/sync v0.22.0`, `goleak v1.3.0`, `testify v1.11.1`, golangci-lint 2.12.2,
2026-10-08). Детерминированное записано словом «всегда», вероятностное — числом «N из M» с
оговоркой, что зелёный прогон дефекта не опровергает. Прогоны — по 20 на исход:

- `go vet` по нормам — код 0; по red — код 1 с двумя находками (copylocks, testinggoroutine);
  `require.NoError` в порождённой горутине vet не находит, `golangci-lint run --default=none
  --enable=testifylint` — код 1, находка `go-require`; `--enable=copyloopvar` на `tt := tt` — код 1;
- `go build` с отправкой в `<-chan int` — код 1; под go1.24.13 `wg.Go` — `wg.Go undefined`; под
  go1.26.8 при строке `go 1.23` сборка — код 0, `go vet` — код 1 (stdversion);
- `go test -race` по нормам — пять тестов зелёные, 20 из 20;
- по red, каждый тест отдельно `-test.run` (20 из 20, если не сказано иначе): тест с утечкой без
  `goleak` — зелёный, с `goleak.VerifyNone` — красный; горутина на месте после `runtime.GC()`;
  чтение nil-map — ноль, запись — паника; отправка в закрытый канал и повторное закрытие —
  паника; строка после `t.Fatal` из чужой горутины исполнена; `FetchAll` на `WaitGroup` —
  таймаут `-test.timeout 2s`; подтесты, читающие одну лишь переменную цикла, — зелёные;
- вероятностные, под `-race`: параллельные подтесты с общей картой — `DATA RACE` в 16 из 20;
  `Inc` с приёмником по значению из восьми горутин — `DATA RACE` в 20 из 20; буфер пула перезаписан
  в 137–162 вызовах из 200 (20 прогонов); без `-race` — 200 из 200 в 20 прогонах из 20;
- `BenchmarkRender` с `Render` из §6 — `1 allocs/op` в 20 из 20 (`go test -run XXX -bench
  BenchmarkRender -benchtime 200000x`); тело `return "hello, " + name` тем же бенчмарком —
  `0 allocs/op` в 20 из 20: `-gcflags=-m` печатает у встроенного вызова `"hello, " + name does
  not escape`, буфер склейки остаётся на стеке — число принадлежит телу, а не форме бенчмарка;
- переменная цикла: три замыкания дают `3 3 3` при `go 1.21` и `0 1 2` при `go 1.22`.

Модуль снят; пример, который правится, перепроверяется тем же набором команд, а не прочтением.
