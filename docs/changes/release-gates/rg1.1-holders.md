## Держатель и точная команда запуска варианта

Планируемые файлы продукта для регрессий в пакете `tools_regression`: `services/storage/tools/release_gates_rg11_scan_test.go` для S1, `services/storage/tools/release_gates_rg11_integration_test.go` для S2 и `services/storage/tools/release_gates_rg11_make_test.go` для S3. Разные стадии имеют разные файлы. Они используют исходники проверяемой ревизии; копии во временных фикстурах сохраняют исходные байты кроме объявленной дельты.

Каждая строка таблицы ниже называет самостоятельный обязательный subtest. Имя `TestRG11_NN/suffix` задаёт команду из корня продукта однозначно:

```sh
go test ./services/storage/tools -run '^TestRG11_NN$/^suffix$' -count=1 -v
```

В этой записи `NN` и `suffix` заменяются ровно значениями строки таблицы; например, `RG1.1-07/ordinary_go2` запускается командой `go test ./services/storage/tools -run '^TestRG11_07$/^ordinary_go2$' -count=1 -v`. Полный набор запускается `go test ./services/storage/tools -run '^TestRG11_' -count=1 -v`. До создания файла эти команды не являются доказательством: успешный `go test` с `no tests to run` означает пустой охват и не проходит приёмку.

Держатель требует захваченный `=== RUN` и конечный исход **каждого** ожидаемого subtest. `SKIP`, отсутствие имени, отсутствие вывода и незапущенный процесс учитываются как «не выполнилось» с причиной. Ни общий PASS пакета, ни основной ID без вариантов не заменяют эту сверку.

## F-TREE и фикстуры скана

**F-TREE** строится отдельной временной рабочей копией фиксированной ревизии продукта с Git-индексом, отслеживаемыми чартами, `trivy.yaml` и настоящими скриптами. Shared audit/worktree другой полосы не используется как площадка инъекции. Перед запуском сохраняются полные байты файла, его SHA-256, `git status --porcelain -- trivy.yaml` и diff пути. После завершения дочернего процесса повторяются те же наблюдения. **F-TREE-DIRTY** отличается только добавленным комментарием, названным в acceptance.

**F-SCAN-REAL:** существующая оснастка продукта — job `trivy` в `.github/workflows/security-scan.yml`, шаг `гейт заглушек умеет краснеть (инъекция в обе стороны)`. Он вызывает `bash deploy/scripts/assert-scan-stubs-hide-nothing-inject.sh`; предшествующие шаги используют `aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25`. Захваченный action.yaml этого pin задаёт default `v0.70.0`; это версия для воспроизведения данной полосы. Версия из исторического комментария сканирующего гейта не подменяет pin CI.

Обязательные зависимости: настоящий бинарь trivy, Bash, Git, Python 3 с PyYAML, стандартные утилиты вызываемого shell-скрипта; доступные правила misconfiguration Trivy либо пригодный кэш этих правил; исходный набор отслеживаемых чартов. Внешний `helm` самими двумя Python-гейтами не вызывается и не объявляется искусственной предпосылкой. Доступность БД не требуется.

До прогона положительных вариантов выполняются `command -v trivy`, `trivy --version`, `python3 -c 'import yaml; print(yaml.__version__)'`, `git --version`, `bash --version`; результаты идут в свидетельство. На локальной машине 2026-09-11 системный PATH не находил trivy. Затем оркестратор подготовил официальный бинарь вне репозитория; автор повторно исполнил его `--version` и получил код 0, `Version: 0.70.0`. Это подтверждает доступность инструмента, а не результат доказательства скана. В evidence сохраняются фактический путь, версия и checksum использованного бинаря; путь конкретной машины не является контрактом продукта.

Для локального воспроизведения `RG1_TRIVY_BIN_DIR` задаётся абсолютным каталогом подготовленного бинаря, `RG1_TRIVY_CACHE_DIR` — отдельным каталогом **данного прогона** вне Git-дерева. Положительная полоса запускается из корня своей временной копии продукта:

```sh
env PATH="$RG1_TRIVY_BIN_DIR:$PATH" TRIVY_CACHE_DIR="$RG1_TRIVY_CACHE_DIR" \
  go test ./services/storage/tools -run '^TestRG11_01$/^real_clean$' -count=1 -v
```

Те же переменные передаются варианту `dirty_present_repeat`. Перед признанием Given готовым настоящий `trivy config` должен загрузить check bundle в этот отдельный cache и дать непустой осмотр чартов; затем сохраняются digest bundle и версия инструмента. Общий cache машины содержит более ранний bundle и без явной подготовки не используется. Отказ загрузки правил оставляет положительные варианты «не выполнилось».

**F-SCAN-ABSENT:** две копии одного исходного окружения различаются только доступностью команды `trivy`. Контролируемый PATH содержит необходимые утилиты и во второй копии не содержит trivy; ни Python, ни `cp`, ни `mktemp` не удаляются вместе с ним. Тот же настоящий скрипт возвращает исход, а держатель проверяет файл после выхода. Эта полоса может исполняться до установки trivy, но не заменяет F-SCAN-REAL.

**F-SCAN-FAILURE:** изолированная процессная фикстура прогоняет настоящий shell-скрипт. Управляемый ответ сканирующей пробы выбирается по фактической инъекции в текущем `trivy.yaml`; только в негативном близнеце один ответ после изменения файла заменён кодом 2. Остальные ответы, путь, окружение и начальные байты равны законному близнецу. Фикстура записывает факт вызова после изменения файла. Её результаты свидетельствуют лишь о сохранности при отказе; реальный смысл сканирования держит F-SCAN-REAL. Подставной успех не считается результатом настоящего trivy.

## F-PG-CAPTURE — настоящий производитель перед подстановкой

Существующий producer: `pkg/pgtest/pgtest.go`, функция `newDatabase`; вызывающий его существующий тест: `pkg/pgtest/pgtest_test.go`, `TestOneContainerManyDatabases`. Для получения отказного сообщения не надо поднимать всю продуктовую БД или стенд. Нужен доступный Docker daemon; недоступность создаётся у источника образа Postgres, а не поломкой запуска Go.

У текущей зависимости `testcontainers-go v0.44.0` переменная `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX` читается конфигурацией и добавляется к образу `postgres:16-alpine`. Команда ниже отправляет запрос за образом к недоступному локальному registry. Предусловие: на 127.0.0.1:1 нет registry и подставленный образ отсутствует в Docker. Не удалять существующие образы ради создания этого состояния; при коллизии выбрать свободный локальный порт и сохранить его в метаданных опыта.

Команды подготовки захвата выполняются **из корня изолированной копии продукта**; `RG1_CAPTURE_DIR` — заранее созданный абсолютный каталог свидетельств вне Git-дерева. Сначала компиляция без запуска проб, чтобы её время и ошибки не стали «отказом Postgres»:

```sh
docker info --format '{{.ServerVersion}}'
go test -c -o "$RG1_CAPTURE_DIR/pgtest.test" ./pkg/pgtest
```

Затем захват настоящего stdout/stderr и кода дочернего `go test`:

```sh
rg1_capture_rc=0
env TESTCONTAINERS_RYUK_DISABLED=true \
  TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX=127.0.0.1:1/rg1 \
  timeout 45s go test ./pkg/pgtest -run '^TestOneContainerManyDatabases$' -count=1 -v \
  >"$RG1_CAPTURE_DIR/pgtest-unavailable.log" 2>&1 || rg1_capture_rc=$?
printf '%s\n' "$rg1_capture_rc" >"$RG1_CAPTURE_DIR/go-test.exit"
```

Валидация capture требует одновременно: код `go test` равен 1, в журнале есть запуск названного теста и сообщение **настоящего** pgtest о недоступности; SHA-256 журнала, SHA продукта, команда, версия Go и Docker сохранены. Код timeout 124, ошибка сборки, panic до производителя, отсутствие сообщения или пустой журнал означают негодную подготовку — fixture остаётся не создана, RED объявлять нельзя. Сам захват на момент написания этой ведомости ещё не предъявлен. Команда не гарантирует заранее, что внешняя предпосылка конкретной машины выполнена.

До TDD RED доставка использует сохранённый захват, а не пересобранный вручную похожий текст. После проверки provenance содержимое захвата копируется как будущая fixture продукта `services/storage/tools/testdata/rg11/pgtest-unavailable.log`, рядом сохраняются `go-test.exit` и `capture.json` с перечисленными метаданными. Эти пути **планируются**; регрессия отказывается работать при их отсутствии или несовпадении SHA-256.

Если нужно проверить отдельно код тестового бинаря, уже собранный `pgtest.test` можно запустить с теми же env и `-test.run '^TestOneContainerManyDatabases$' -test.v`; ожидаемый код производителя 75 записывается отдельно. Он не подставляется вместо дочернего go-кода 1 в цепочку make.

## F-CI — подстановка до xargs с настоящим вызывающим

Фикстура копирует корневой Makefile, `deploy/scripts/classify-integration-outcome.sh`, `deploy/scripts/pgtest-unavailable-mark.sh` и извлекает исполняемый integration-step из YAML проверяемой ревизии. Она подставляет только значение `matrix.svc=vpc` и необходимые переменные окружения (`CI=true`, `SVC=vpc`, `GITHUB_ACTIONS=true` для CI-полосы). Текст шага не переписывается под ожидаемый результат и исполняется с его shell-флагами.

Точка подстановки — существующая переменная `GO` корневого Makefile. Подставной дочерний исполнитель для `list` отдаёт один действительный integration-путь VPC; для `test` воспроизводит захваченный журнал и дочерний код из F-PG-CAPTURE. Аргументы его вызова записываются. Настоящие `xargs`, pipefail/tee, классификатор, make и шаг остаются на полном пути. Проба доставки не предъявляется как реальный прогон базы или всех VPC-тестов.

**F-CI-GREEN** задаёт непустой список пакетов и успешный дочерний результат как процессный законный близнец доставки. **F-CI-ORDINARY** вычисляет дельту по отношению к captured результату: удалена только строка с признаком недоступности; дочерний код 1 сохранён. Вариант `ordinary_go2` меняет относительно `ordinary_go1` только код на 2. **F-CI-EMPTY** меняет только ответ `list` на пустой. **F-CLASSIFIER-CLI** запускает настоящий классификатор с двумя аргументами, передавая существующий журнал законному близнецу и отсутствующий файл негативному.

Для каждой полной полосы свидетельство называет границы `go test → xargs/конвейер → классификатор → make → CI`. Наблюдения независимого ревью на исходной ревизии уже установили `1/2 → 123 → 123 → 2 → 2` для обычного отказа; это основание исправленного expectation, не будущий PASS теста. Прямые проверки входных кодов классификатора 1/2 не выдаются за полный путь.

## F-WORKFLOW — реальный reader и временные корпуса

Планируемая строящая фикстура в `release_gates_rg11_make_test.go` создаёт через временный каталог `.github/workflows/rg11.yml` и ровно нужные `Makefile` в корне, `deploy` и `services/storage`. YAML валиден; исходная строка wrapper взята из исполняемого шага `.github/workflows/ci.yaml`; формы продолжений сверены с `.github/workflows/e2e-newman.yml`. Цель `helm-deps` объявляется только в `deploy/Makefile`, `rg1-nonexistent-target` нигде не объявляется. Это вход гейта; сами make-цели не запускаются.

Корпус передаётся существующему reader `collectMakeInvocations(t, fixtureRoot)` из `services/storage/tools/ci_gate_wiring_test.go`; разрешение целей выполняет тот же проверяющий путь, который обслуживает `TestEveryCIMakeCommandResolves`. Держатель не реализует второй parser или второй способ определения наличия цели. Для наблюдения ожидаемого отказа полный проверяющий запускается отдельным тестовым процессом с корнем временного корпуса: его stdout/stderr и код захватываются. Подача root в такой процесс — планируемая тестовая оснастка, не существующая CLI-ручка продукта.

**F-WORKFLOW-CWD** строит три независимых корпуса с одним значением рабочего каталога на step, job defaults или workflow defaults. В каждом есть положительный и отрицательный близнец с той же формой `../../.github/scripts/stand-up.sh --dir ../../deploy`. **F-WORKFLOW-EMPTY** получает базовую фикстуру и меняет только состав файлов либо единственную команду на комментарий, согласно варианту.

**F-WORKFLOW-LIVE** берёт полный набор `.yml`/`.yaml` из `.github/workflows/` одного фиксированного checkout. До изменения сохраняется перепись исходного reader на этом же корпусе; отдельная опись каждого исполняемого wrapper-step содержит workflow/job/step/каталог/цель и SHA корпуса. Старый и новый reader судят одни байты. Общий счёт сверяется в единице acceptance; строки комментариев и физические продолжения не становятся отдельными командами. Вариант `zero_wrapped` меняет только захваченный счёт обёрток на ноль при неизменном независимом перечне и должен быть отвергнут держателем переписи.

**F-WORKFLOW-PLAIN** берёт действительные формы обычных команд из того же корпуса: `-C`, сервисный цикл, redirect и `NAME=value`. Их законный результат сверяется до/после; негативный близнец меняет только одну цель. **F-HOLDER-ABSENT** проверяет саму пригодность свидетельства: отдельно отсутствие запущенного процесса и отсутствие захваченного вывода при остальных метаданных законного близнеца. Оба состояния имеют именованные варианты и не могут дать успешный outcome.

## Запись результатов

Для каждого варианта сохраняются полная команда, рабочая ревизия, SHA-256 входов, построение Given и его исход, вычисленная дельта к близнецу, stdout/stderr, код процесса и конечная категория. Повторный прогон после исправления ссылается на тот же вариант. Реальное сканирование, capture настоящего producer и синтетическая доставка имеют раздельные свидетельства.

Эта ведомость отвечает на вопрос «где и как будет проверено». Запись о том, что проверка исполнена и что она получила, появляется только после захвата; ни PLANNED, ни существование команды такой записью не являются.
