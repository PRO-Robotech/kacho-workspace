## D1 — снимок становится пригодным до первой мутации (#2175)

Изменяется `deploy/scripts/assert-scan-stubs-hide-nothing-inject.sh`. Порядок подготовки фиксируется так:

1. Проверить наличие trivy. При отсутствии вернуть существующий код 2 и понятную причину; резервный файл и восстановление ещё не требуются.
2. Создать принадлежащий данному процессу временный файл через `mktemp` и проверить успешный код команды и существование полученного файла. `TMPDIR` задаётся площадкой прогона вне репозитория. Строка пути без успешного создания не считается владением файлом и не используется как адрес восстановления.
3. Скопировать исходный рабочий `trivy.yaml` в снимок с проверкой результата. Подтвердить байтовое равенство через `cmp`. Готовность определяется успешным копированием и сравнением, а не непустым именем или размером файла. Законное нулевое содержимое, если оно было у исходника, не отождествляется с отсутствием снимка.
4. Только после подтверждения снимка разрешить восстановление и установить EXIT-обработчик до первой инъекции.

Ошибка создания, копирования или проверки снимка даёт код 2 и отдельную диагностику подготовки. Исходный файл не меняется, сканирующая инъекция не запускается. Частичный принадлежащий процессу snapshot удаляется, потому что рабочий оригинал ещё цел; из него не выполняется восстановление. Shell не продолжает выполнение после отказа подготовки даже при прежнем отсутствии `set -e`.

Имена и пути файлов всегда передаются аргументами с quoting; указанный пользователем TMPDIR не интерпретируется как shell-код. Новая настройка продукта для snapshot не вводится: проверка отказов подставляет существующие внешние команды только в изолированной процессной фикстуре.

## D2 — один путь восстановления, ошибки не исчезают на EXIT (#2175)

Эталон — снимок рабочего файла, полученный D1. HEAD и индекс нужны только для наблюдения исходной чистоты/грязи, не для восстановления. Внутренние возвраты конфигурации между пробами и финальный EXIT используют один проверяемый helper восстановления.

Helper копирует снимок в конфигурацию и проверяет результат и байтовое равенство. Ошибка копирования либо сравнения останавливает дальнейшие инъекции. EXIT сохраняет исходный код тела, выполняет завершающую проверку и не превращает отказ тела в успех. При пригодном восстановлении остаются коды тела 0/1/2. При собственном отказе восстановления конечный код — 2, вывод явно называет невозможность восстановить файл и координату сохранённого snapshot.

При отказе восстановления снимок **не удаляется**, его исходные байты доступны для восстановления оператором. Неуспешное восстановление не объявляется завершённым; повторная обработка EXIT не скрывает уже полученный отказ. После успешного восстановления принадлежащий процессу снимок удаляется. Повторные успешные вызовы helper допустимы и не меняют эталон.

Гарантия при отказе записи в сам файл ограничена честно: процесс может не суметь вернуть рабочие байты, поэтому выдаёт отказ и оставляет пригодный snapshot. Обещания успешного восстановления при недоступном для записи ресурсе здесь нет. Это отличается от D1: до первой мутации сохранность исходного файла обеспечена отсутствием записи вообще.

Основные процессы, их завершение и проверку исходных байтов держат canonical варианты S1. Дополнительные технические subtest в `release_gates_rg11_scan_test.go` закрывают собственные ошибки механизма:

| Будущий subtest | Один изменённый факт против законного близнеца | Проверяемое следствие |
|---|---|---|
| `TestRG11SnapshotPrepare/create_failure` | `mktemp` возвращает отказ | rc2, оригинал цел, сканирующие пробы не вызваны |
| `TestRG11SnapshotPrepare/copy_failure` | копирование рабочего оригинала в snapshot возвращает отказ | rc2, оригинал цел, restore из snapshot не вызван |
| `TestRG11SnapshotPrepare/partial_snapshot` | копирование оставляет неполные байты и возвращает отказ | те же следствия, неполные байты не попадают в конфигурацию |
| `TestRG11SnapshotPrepare/snapshot_success` | законный близнец подготовки | снимок равен рабочему оригиналу, путь инъекции достижим |
| `TestRG11SnapshotRestore/copy_failure` | запись при восстановлении возвращает отказ | rc2, явная причина, пригодный snapshot сохранён |
| `TestRG11SnapshotRestore/restore_success` | законный близнец восстановления | исходные байты возвращены, snapshot убран, код тела сохранён |

Команда технических проб: `go test ./services/storage/tools -run '^TestRG11Snapshot' -count=1 -v`. Это дополнительные process-регрессии обеспечения E1/E2, не новые GWT и не замена реальной Trivy-полосы. Подставной сканирующий исполнитель фиксирует вызов; его ответ не считается результатом настоящего скана.

### Явная CI-полоса настоящего сканера

Файл `release_gates_rg11_scan_test.go` получает build tag `rg11trivy`; его canonical команды и технические Snapshot-пробы запускаются с `GOFLAGS=-tags=rg11trivy`. Это выбирает отдельный набор в job, где создана его предпосылка. Ни `t.Skip`, ни успешный выход теста при отсутствующем сканере не вводятся. Обычный `make test-unit` без тега не является держателем этих вариантов и не объявляет их исполненными.

В job `trivy` файла `.github/workflows/security-scan.yml` сохраняются существующий прямой scan-proof и его routing. Добавляются установка Go через уже используемый этим workflow pin `actions/setup-go@b7ad1dad31e06c5925ef5d2fc7ad053ef454303e` с `go-version-file: go.mod` и отдельный обязательный шаг запусков `TestRG11_01`…`TestRG11_04` плюс `TestRG11Snapshot` с указанным тегом. Нового внешнего источника установки не вводится: используются два уже закреплённых в workflow action — Go и Trivy. Условие шага сохраняет независимость проверки от предыдущего scan-вердикта: `!cancelled()`, как у существующего proof.

Шаг задаёт отдельный TRIVY_CACHE_DIR внутри RUNNER_TEMP, сначала выполняет настоящий сканирующий гейт для подготовки и фиксации bundle, затем запускает Go-проверки на временных копиях. Отказ подготовки останавливает эту полосу с причиной.

**GOFLAGS — обязательная проверяемая часть F-SCAN окружения.** Перед запуском caller проверяет наличие выбранного тега, а после запуска проверяет фактический набор. CI использует `go test -json` с непотерянным кодом процесса и сохраняет поток вне репозитория; проверяющая часть того же шага разбирает события JSON, относящиеся к пакету Storage tools. Ожидаемое множество именованных subtest — все пять S1-вариантов canonical holders и все технические Snapshot-варианты таблицы D2. Каждый обязан иметь событие `run` и завершающий `pass`; `skip`, `fail`, отсутствующее имя или пустой поток дают отказ caller. Совпадение имени внутри поля `output` не считается событием выполнения. Код 0 у `go test` с `no tests to run` это условие не удовлетворяет.

Для локальных canonical команд без изменения их текста требуется то же окружение GOFLAGS и та же сверка полного перечня при сдаче S1. Команда, вызванная без GOFLAGS и вернувшая 0 с пустым выбором, не подтверждает ни одного принятого варианта. Проверяющая часть CI-step удерживается технической процессной пробой `TestRG11ScanExecution`: полный законный поток проходит, поток с одним снятым обязательным вариантом и пустой поток отвергаются. Её ответы не засчитываются как результаты реального сканирования. Применимость тега и проверка фактического выбора входят в независимый design-review по E7; одобренная ведомость не переписывается ради этой реализации окружения.

На исходной базе оркестратор уже подготовил F-SCAN-REAL настоящим Trivy 0.70.0 и отдельным cache: `assert-scan-stubs-hide-nothing.py` завершился rc0; SHA-256 захваченного вывода — `4c194d16b54f7762b9af50fda2ece81ee2d173538dcfa206d73c6cdc9d60df5c`. Bundle загружен в этом прогоне, digest `sha256:1583562f8b90ed2a071b99f0e5ffff6b57e4ceb6ca3e4796577b4e6a339eb74c`. Автор замысла прочитал result/provenance. Это подготовка предмета, не запуск инъекционного proof и не RED/GREEN #2175. Подготовленный cache допустимо использовать в регрессии с явным provenance; общий случайный cache машины не подставляется.

В существующей ветви, которая распознаёт собственный признак pgtest при ненулевом входном коде и возвращает 75, при **точном** `GITHUB_ACTIONS=true` добавляется одна error-аннотация. Динамический журнал не интерполируется в управляющий синтаксис GitHub Actions.

Решение о категории и emitter находятся вместе. Нулевой вход возвращается прежде этой ветви; невалидный CLI отказывает до классификации; обычный ненулевой код без признака передаётся как есть. При незаданном GITHUB_ACTIONS или ином его значении печатается только прежний человекочитаемый текст, управляющей аннотации нет. Копий emitter в вызывающем CI-step не остаётся.

В `.github/workflows/ci.yaml` integration-step вызывает `make test-integration` напрямую. Ветка ожидания 75 после make и ложное описание этого ожидания снимаются. Комментарий объясняет фактическую доставку категории из классификатора, а не предполагаемый код оболочки. Корневой Makefile, его отбор пакетов, xargs, бюджеты и способ вызова классификатора для этой задачи не меняются.

## D5 — обёртка извлекается по исполняемой команде (#2550)

Изменяется общий reader в `services/storage/tools/ci_gate_wiring_test.go`. Для обычных команд сохраняется существующий способ извлечения и чтения make-аргументов. Новый путь распознаёт canonical `.github/scripts/stand-up.sh`, разрешённый относительно cwd шага, при прямом вызове или явном `bash`; совпадение одного basename не достаточно.

Reader сначала применяет существующую нормализацию продолжений и выражений GitHub. Для кандидата обёртки используется узкое quote-aware чтение shell-токенов: одинарные/двойные кавычки и escape позволяют отделить label целиком; разделители внутри кавычек не заканчивают команду. Оболочка и её подстановки не исполняются. Новая библиотека shell-интерпретации не вводится.

Аргументы `--label` и `--dir` читаются как пары ключ/значение, разделитель `--` отделяет исполняемую команду. Случай `--self-test` без дочернего make не входит в перепись. После разделителя требуется действительный токен `make`; его аргументы передаются существующему reader целей. Отсутствующий обязательный аргумент либо неразбираемая форма распознанного wrapper выдаёт диагностируемый отказ чтения с координатой, не молчаливый пропуск. Label и shell-redirect не превращаются в цели.

Каждый извлечённый wrapper имеет span исходной нормализованной команды. Этот span исключается из обхода обычных make-команд, поэтому продолжение после `--` не даёт повторного счёта. Признак `wrapped` принадлежит извлечённой записи и используется переписью; одна цель конкретного вызова даёт одну запись. Разные действительные вызовы не схлопываются лишь потому, что называют одну цель.

Проверка полного shell-языка, вычисляемых имён целей, пробелов внутри имени каталога/цели и Makefile include не вводится: принятые пределы reader заданы acceptance. Предел не разрешает молча пропустить увиденный canonical wrapper.

## D6 — эффективный каталог следует порядку запуска (#2550)

Базовый cwd выбирается из step working-directory, затем job defaults, workflow defaults и корня. Значение `--dir` обёртки разрешается через чистое соединение пути с этим cwd так, как настоящий относительный `cd`; без `--dir` остаётся cwd. Для канонического распознавания пути самой обёртки используется тот же исходный cwd.

Если дочерний make несёт один поддерживаемый флаг `-C`, его относительный путь разрешается от cwd после обёртки; абсолютный не присоединяется повторно. Повторные `-C` у распознанного wrapper отвергаются явной диагностикой неподдерживаемой формы, а не разрешаются по последнему значению с потерей промежуточного cwd. Список целей и существующий resolver Makefile остаются общими с обычным путём. Динамический cwd, который reader не может разрешить по поддерживаемому объявлению, даёт отказ с координатой; корень не подставляется вместо неизвестного каталога.

Проверка цели относится только к эффективному Makefile. Отсутствие каталога, отсутствие Makefile и отсутствие цели имеют диагностируемые причины с workflow/job/step и эффективным каталогом. Наличие цели в другом Makefile не участвует в решении. Представление относительных путей нормализуется, чтобы `services/storage/../../deploy` и `deploy` давали одну координату результата.

## D7 — перепись и процессная проверка используют один reader (#2550)

Запись переписи сохраняет поля canonical единицы `(workflow, job, step, dir, target)`; `wrapped` добавляет происхождение, не новую единицу счёта. В отчёте выводятся общее число записей и число записей под stand-up. Оба вычисляются из одного извлечённого набора **до** проверки существования целей, поэтому отказ не уменьшает охват.

До правки reader F-WORKFLOW-LIVE сохраняет полный набор исходного reader на фиксированном корпусе, а не только число. После правки сравнение требует сохранности прежнего множества и точного появления перечня обёрток. Initial выявил четыре такие записи на исходной базе; это ожидаемая дельта данного корпуса, не постоянный порог на будущие workflow. Равенство нового общего числа прежнему считается провалом регрессии расширения на этом корпусе.

Тесты временных корпусов вызывают тот же collector и resolver. Для этой цели полное тело проверки выделяется в test-only helper, принимающий root; `TestEveryCIMakeCommandResolves` вызывает его с настоящим repoRoot, а subprocess технической фикстуры — с временным root. Второй parser или второй предикат наличия цели в регрессии не пишется. Test-only helper не создаёт production CLI-флага и не меняет runtime-сервис.

Пустой набор workflow и ноль обнаруженных команд завершают проверку отказом. В корпусе, где независимая опись содержит wrapper, нулевой wrapper-счёт роняет регрессию охвата. Общее ненулевое число не заменяет это требование. Отсутствие запущенного процесса и захваченного вывода проверяет держатель свидетельства как отдельные непригодные исходы; они не считаются находками о Makefile.

## D8 — граница диффа и независимое владение

Реализация продукта ограничена скриптом scan-proof, дополнительной проверкой S1 в существующем trivy-job `security-scan.yml`, корневым integration-классификатором, одним integration-step в `ci.yaml`, общим make-reader Storage и тестовыми файлами/фикстурами canonical holders. Новых RPC, схем, миграций, сервисных зависимостей и общей runtime-библиотеки нет.

Registry reader провязки `services/registry/tools/auditlistfilter/ci_wiring_test.go` — read-only: его узкий предмет не заменяется общим проверяющим целей Storage. Самостоятельный IAM-классификатор `services/iam/.github/scripts/classify-integration-outcome.sh` также read-only: его семантика не выводится из выбранного корневого классификатора. Корневой `Makefile` и `.github/scripts/stand-up.sh` читаются как действующий контракт вызывающего/каталога; их поведение в RG1.1 не меняется. Эти четыре конкретных пути имеют нулевой дифф относительно базы в post-diff review. Общий helper между ними не вводится.

Три реализации ведутся в разных product worktree и разных ветках от одной базы накопительной `release/gates-resolution`. Изменения общих файлов между ними не перекрываются: #2175 владеет scan-proof, trivy-job и scan-тестом, #2580 — classifier/CI-step/integration-тестом/testdata, #2550 — Storage reader/make-тестом. Новые test-only helper каждой стадии размещаются в её собственном файле с уникальными именами; общего нового helper между полосами нет.

Все `t.TempDir`, TMPDIR, capture, логи и кэш Trivy находятся вне рабочего Git-дерева. Инъекции работают только в копиях, которыми владеет процесс. Родительская копия и чужие worktree не являются scratch-каталогом. Одна процессная фикстура не запускает параллельно писателей своего `trivy.yaml`; разные экземпляры получают разные пути. Фикстура не наследует случайный GITHUB_ENV/GITHUB_OUTPUT/GITHUB_STEP_SUMMARY другого задания: для нужного CI-входа значения задаются локально процессу.

## Применимые ревью и переход

До TDD маршрут требует отдельную class-exposure **revalidation на SHA-256 этого замысла**, затем независимый design-review с внешним событием. Initial остаётся отдельным свидетельством об одобренной приёмке. Изменение замысла требует новой пересверки на новое содержимое.

К готовому диффу применимы Go-style review тестовой Go-оснастки, проверка конструкции регрессий integration-tester и общий wave-reviewer, затем convergence/landing по контуру. Proto- и DB-review неприменимы при подтверждённом отсутствии соответствующих файлов в финальном диффе; distributed runtime-предмета для system-design-review нет. Изменение границы диффа требует пересмотра применимости до посадки.

Технические решения в D1–D8 выбраны. Команды подготовки и ещё не выполненные проверки являются шагами [маршрута](rg1.1-route.md), а не неразрешёнными вопросами замысла. Этот DRAFT не выдаёт за состоявшиеся revalidation, design approval или RED.
