## Точная граница реализации

В `PRO-Robotech/kacho`, в `.github/workflows/security-scan.yml`, существующий job `trivy` получает предусмотренный D2 шаг с **`id: rg11-scan-preservation`**. Это идентификатор планируемого вызывающего шага, а не утверждение, что шаг уже добавлен либо запущен.

Внутри `run` именно этого шага располагается Python-проверка JSON-событий Go. Граница её heredoc имеет буквальное имя **`RG11_SCAN_EVENTS`**. Запуск Go, сохранение его кода/вывода и проверка событий относятся к одному CI-step. Размещение не переносит проверку полноты в отдельный шаг, чьё отсутствие могло бы остаться незамеченным caller.

Техническая регрессия `TestRG11ScanExecution`, предусмотренная D2, привязывается к шагу по `id: rg11-scan-preservation` и к телу проверки, выделенному границей `RG11_SCAN_EVENTS` из его `run`. Испытуемым остаётся проверка действительного caller из YAML проверяемого продукта. Вторая копия её предиката в тесте не заменяет исполнение этого тела. Отсутствие шага, исполняемого блока или однозначной границы не считается успешной проверкой caller.

## Сохраняемый контракт D2

Обязательное окружение F-SCAN, сохранение кода процесса, полный набор S1/Snapshot и исходы проверки полноты определены замыслом. Canonical ID/вариант → команда → фикстура остаются в [ведомости держателей](rg1.1-holders.md). Эта заметка не меняет их и не создаёт второго перечня ожидаемых имён.

Размещение должно сохранить проверку настоящих `run`/`pass`, отказ для пустого или неполного потока и невозможность принять неподготовленную tagged-полосу за исполненную. Названный step id либо найденный heredoc сами по себе этих свойств не доказывают. Их фактическое исполнение и однофактные отрицательные контроли предъявляются отдельным результатом регрессии и последующим post-diff review.
