## Acceptance-reviewer: CHANGES REQUESTED

**AR1 — граница гарантии не определена конструктивно.** Наблюдаемая модель
обещает: неподдержанное кодирование не даёт CLEAN. При этом среди носителей
названы произвольные тексты скриптов, ошибок и журналов. Неизвестное кодирование
без структурной метки невозможно отличить от законной строки в общем случае.
Утверждение design «не обещает понимать произвольную человеческую фразу» этого
не исправляет: нормативная гарантия acceptance шире механизма.

Нужно выбрать проверяемую границу: закрытая структура носителей/явных encoding
tags и отказ на неизвестный tag, либо безопасная публикационная проекция,
удаляющая непрозрачный свободный текст. Пример отрицательного Given должен
называться конкретной формой, а законный близнец — тем же носителем с допустимым
содержимым. Не ограничивать исходное требование #1810 лишь узнаваемым JWT:
arbitrary client secret также входит в предмет.

**AR2 — метаданные тоже являются входом публикации.** «Безопасная координата»
не определена: относительное имя файла, JSON key, имя теста, текст ошибки и имя
артефакта могут нести то самое запрещённое значение. CI-NP-02 проверяет значения,
но не задаёт положительно производимую безопасную координату. Добавить GWT:
canary в этих метаданных; stdout/stderr, manifest и итоговый пакет его не несут;
несекретные координаты сохраняют пригодную связь с исходом. Возможное решение —
выведенные контролируемые ordinals/IDs и фиксированные reason codes, а не сырые
имена. Это требование к результату, автор выбирает механизм.

**AR3 — полный положительный прогон нужно назвать положительным.** CI-NP-07
сейчас доказывает исполненность состава и 0 опубликованных credentials, но
допускает красный продуктовый verdict. Для заказанной root финальной полноты
дописать явный успешный verdict полного identity и всех объявленных platform
shards, без ослабления CI-NP-01: тестовый красный в синтетике должен оставаться
красным и может иметь успешно очищенный пакет. Это разные свидетельства.

Покрытие остального scope достаточное: все carriers/raw/base64, scanner отсутствует
или пуст, parsed workflow binding, независимый download scan, dynamic retention,
точный content-verified containment, prelanding repeat, два pinned потребителя.
10 сценариев, все имеют GWT. Контракт RPC/БД здесь не применяется.

## Design-review: предварительный CHANGES REQUESTED

**DR1 — фактические upload bytes.** Поток говорит «digest сверяется перед
передачей загрузчику». Если загрузчик потом заново открывает mutable pathname,
между проверкой и чтением остаётся окно. Нужен конкретный исполняемый boundary:
кто читает окончательные bytes и кто отправляет именно их. Закрытый архив и
отсутствие следующих шагов сами не доказывают это свойство. Опыт CI-NP-04 должен
подменять содержимое после последнего check, до фактического чтения uploader;
увиденные транспортом bytes сравниваются с проверенными, а не только с pathname.

**DR2 — предметы AR1/AR2 должны быть выражены механизмом.** Перечень узнаваемых
токенов и рекурсивный декодер не закрывают произвольную упаковку. Сначала принятие
конструктивной publication schema/projection, затем точные правила её исполнения.

Corelib как единственный владелец и запуск из опубликованного Go module archive
по пину — допустимый замысел при фактической single-repo проверке обоих consumers.
Удаление частного Kaname-алгоритма должно следовать за доступным общим инструментом.
Снятые 485 metadata / 0 bodies верно названы NOT_INSPECTED, удаление не разрешено
одним наличием metadata. Неизвестные/изменённые пакеты сохраняют третью категорию.
