## 1. Что решает этот замысел и чего не решает

Решает: форма контракта и её хранение; где объявлен признак «отбор по меткам» и как проба Р4 судит
его; порядок проверки входа `notify-api`; как база держит уникальность, «ровно одну ветвь», порядок
набора видов; как приём `notify-sender` находит кандидатов селектора внутри своей транзакции и почему
это не порождает ни одного вызова; как сборка мгновенного письма спрашивает выдачу о каждой строке;
средство записи вызовов СЛ3 и судящий его вычислитель; строка консоли.

Не решает (не его предмет): механизм аудитории, ограды, барьера поколения, схлопывания, всплеска,
потолка пары и сетки `notice` — NTF-3 Р7, Р9, Р13, Р30 и замысел NTF-3 З19, З22, З34 без изменений;
поток изменений фундамента — без изменений (приёмка §0.1).

## 2. Решения

### З1. Контракт — третья ветвь `oneof` цели (Р1, Р2; приёмка §3 строка «контракт»)

- В сообщение цели подписки NTF-3 (поле `target` сообщения `NotificationSubscription`, `oneof` с
  ветвями `resource`, `project`) добавляется ветвь `label_selector` типа `LabelSelectorTarget`
  с полями `module = 1` (`string`), `resource_types = 2` (`repeated string`), `match_labels = 3`
  (`map<string, string>`). Номер ветви в `oneof` — следующий свободный номер сообщения цели на голове
  после S2-B7 NTF-3; полоса контракта печатает его и он больше не меняется (`api-outcome-remove`:
  переиспользования номеров нет).
- Комментарии полей — часть контракта: у `resource_types` — «набор; сервер хранит и отдаёт по
  возрастанию строки вида; пустой набор не означает „все виды“ и отвергается» (`api-repeated-order`,
  `api-empty-means-empty`, `api-field-two-questions`: заполняют Create-ответ, `Get`, `List`); у
  `match_labels` — «равенство по каждой паре, конъюнкцией; от 1 до 16 пар; пустое значение пары
  допустимо»; у `module` — «ключ модуля каталога `notify` с ячейкой `(RESOURCE_CHANGE, EMAIL)`».
- Правки подписки нет ни у одной ветви (NTF-3 Р11), поэтому `update_mask`-дисциплина к ветви не
  применяется, а неизменность полей держится отсутствием глагола, а не проверкой.
- Ни одного нового метода, ни одной новой службы, ни одного нового REST-пути: край отдаёт ветвь
  тем же маршрутом `POST /notify/v1/subscriptions` после регенерации `pkg/api` (`api-edge-rebuild`).
- Каждое поле ветви имеет читателя в прод-коде `notify-api` (З3) и `notify-sender` (З7) —
  `api-accepted-ignored`; гейт `TestEveryDescriptorFieldHasAReader` судит собранную волну, поэтому
  контракт и сервер садятся одной волной (`tasks.md` §1 «Неделимая цепочка»).

### З2. Признак «отбор по меткам» — объявление в таблице видов сборки и проба Р4 (Р4)

- **Объявление.** У каждой записи таблицы видов сборки `notify` (дом `services/notify/kinds`,
  производитель — S2-B7 NTF-3, NTF3-80…86) — булево поле признака. Признак **пишется руками в
  исходнике таблицы** (или во входе её генератора, если таблицу собирает шаг `bundle`), а **не
  вычисляется** из дескрипторов или каталога прав при сборке: вычисленный признак сделал бы пробу Р4
  тавтологией (она сравнивала бы функцию с самой собой). Читатель признака в прод-коде один —
  проверка входа З3 п.3; второго перечня видов с метками в не-тестовом дереве `notify` нет
  (держатель — УК7-01).
- **Проба `TestNotifyLabelSelectableKindsMatchTheirProducers`** (интеграционное дерево
  `services/notify/internal/integration/`, обвязка службы доступа NTF-3 на пине kacho):
  - знаменатель — записи таблицы видов сборки; пустая таблица — красный «пустой обход: таблица видов»;
  - **(а)** вычисляется над набором дескрипторов файлов пяти модулей
    (`kacho.cloud.{compute,vpc,loadbalancer,registry,storage}.v1` — пакеты сгенерированного `pkg/api`,
    собранные в `descriptorpb.FileDescriptorSet` через реестр файлов): найти метод публичной службы
    (имя файла без `internal_`) с опцией `required_relation = "v_get"` и
    `scope_extractor.object_type = <вид>` и именем `Get`; его выходное сообщение должно нести поле
    `labels` с типом `map<string,string>`. Нет метода либо поля — (а) ложно с производителем
    `proto <файл>:<метод>`;
  - **(б)** — ответ `ListPermissionCatalog` службы доступа обвязки (вызывающий `usr-A`, К17 приёмки),
    токен вида — `<module>.<resources[].name>` строки манифеста `services/<модуль>/manifest.yaml` с
    этим `objectType`; токена в ответе нет либо `label_selectable = false` — (б) ложно с производителем
    `каталог прав: <токен>`; ответ без модулей таблицы — красный «пустой обход: каталог прав»; вид
    без строки манифеста — красный «пустой обход: манифест <вид>»;
  - предикат «признак ⇔ (а) ∧ (б)»; печать «осмотрено видов: N, с отбором: M, без отбора: K» и
    строки «без отбора» с причиной;
  - инъекции СЛ2 работают над **копиями**: таблица видов с переключённым признаком; копия
    `FileDescriptorSet` без поля `labels` у названного сообщения; подмена ответа каталога — ответ
    обвязки дословно с переключённым `label_selectable` у названного токена. Продуктовых ручек и
    флагов ради инъекций не заводится.
- **Цена названа.** Проба читает каталог у живой службы доступа обвязки — она интеграционная и
  требует обвязки NTF-3; это сказано приёмкой (Р4) и принимается.

### З3. Проверка входа `notify-api` для ветви селектора — порядок закрыт (Р3)

- Ветвь проверяется первым кодом use-case создания, **до** любого вызова наружу и до записи
  (`hard-format-before-authz`). Порядок — дословно Р3: (1) обязательность трёх полей; (2) модуль по
  каталогу сборки (неизвестный; известный без ячейки `(RESOURCE_CHANGE, EMAIL)`); (3) виды — по
  порядку элементов запроса: «не вид этого модуля» (включая `*`) → «без отбора по меткам» (признак
  З2) → повтор; (4) `channel` — функция NTF-3 Р11 без изменений; (5) число пар > 16;
  (6) `validate.Labels("target.label_selector.match_labels", …)` corelib — тексты и поле
  `<field>.<key>` дословно.
- Отказ — одна функция построения `INVALID_ARGUMENT` с `BadRequest.fieldViolations[0]` той же формы,
  что у ветвей NTF-3; первый отказ возвращается, дальше проверка не идёт.
- Тексты отказов — константы пакета проверки, каждая с пробой на точный текст (§5).
- Граница 16 — константа пакета проверки с комментарием-ссылкой на её основание (правило роли службы
  доступа, приёмка §1.3); ручки у неё нет (Р2: «отдельной ручки не имеет»). Граница числа видов
  отдельной константы не имеет — она следствие «вид этого модуля, с отбором, без повтора».
- Каталог модулей и видов берётся из таблиц сборки `notify` (NTF-3 Р29, З2), не из службы доступа и
  не из модулей: проверка входа сетевых вызовов не делает.

### З4. Создание селектора не спрашивает права (Р7)

- Use-case создания ветвится по ветви цели **до** вызова порта прав: ветви `resource` и `project`
  зовут `Check(v_get)` (NTF-3 Р11, без изменений), ветвь `label_selector` порт прав не зовёт вовсе;
  недоступность службы доступа на ней не наблюдаема.
- Запись каталога прав метода `Create` (освобождение «объект — вызывающий», NTF-3 Р25) не меняется;
  меняется только столбец «вызов службы доступа» по ветви — это замещение строки NTF-3 Р25 (приёмка
  §4), его вносит автор NTF-3 (§9 Е2).
- Держатель: NTF7-02 со средством СЛ1 — тестовая обёртка порта прав `notify-api`, считающая вызовы
  и пропускающая их в службу доступа обвязки без изменений (обёртка живёт в тестовом дереве и
  подставляется через тот же конструктор use-case, которым корень передаёт порт; ручки «записи» в
  продукте нет).

### З5. Хранение ветви в `kacho_notify` — новая миграция (Р8; приёмка §3 строка «база»)

Таблица `subscription` NTF-3 (замысел NTF-3 §6: `id`, `owner`, `target_key`, `channel`, `created_at`,
`UNIQUE (owner, target_key, channel)`) дополняется **новой** миграцией (`ban05`: применённые не
правятся):

- колонки ветви: `label_module text`, `label_resource_types text[]`, `label_match jsonb` — все три
  `NULL` у ветвей `resource`/`project`, все три заданы у селектора;
- **«ровно одна ветвь цели»** — `CHECK`: три колонки либо все `NULL`, либо все заданы; и признак
  ветви в `target_key` (приставка ветви селектора) равен «колонки заданы» — несогласованная строка
  не вставляется (`db-check`);
- **форма селектора в базе** — `CHECK`: `label_module <> ''`; `cardinality(label_resource_types) >= 1`
  и массив равен своей отсортированной форме без повторов (неизменяемая функция схемы — сравнение
  массива с его упорядоченным уникальным вариантом); `jsonb_typeof(label_match) = 'object'`, число
  ключей от 1 до 16, каждое значение — строка (неизменяемая функция схемы). Проверка входа З3 —
  первая линия с текстами Р3; `CHECK` — механизм базы, который ловит обход проверки входа
  (`23514` → `INTERNAL` фиксированным текстом по дому SQLSTATE: до базы такая строка дойти не может,
  поэтому это дефект, а не отказ клиенту);
- **ключ цели селектора вычисляет база.** `target_key` строки селектора — значение неизменяемой
  функции схемы от трёх колонок ветви; `CHECK (target_key = <функция>(label_module,
  label_resource_types, label_match))` у строк селектора; вставка ставит `target_key` тем же
  выражением. Функция **инъективна**: виды — идентификаторы закрытого каталога (`[a-z_]`), метки —
  каноническая текстовая форма `jsonb` (порядок ключей нормализован типом, значения экранированы), с
  приставкой ветви и разделителями, которых в идентификаторах видов и в имени модуля быть не может.
  Поэтому уникальность NTF-3 `UNIQUE (owner, target_key, channel)` держит дубль ветви селектора
  (NTF7-07) **тем же** ограничением, что у ветвей `resource`/`project`: второго механизма
  уникальности нет (ТВ-Л3). Go-функция ключа цели NTF-3 (`subscriptions.TargetKey`, замысел NTF-3 З24)
  ветви селектора не собирает: ключ один, и его производитель — база (держатель — УК7-02:
  `git grep -n 'label_selector/' -- services/notify ':!*_test.go' ':!*/migrations/*'` → 0);
- **кандидаты — дочерняя таблица** `subscription_label_kind (owner, module, resource_type,
  subscription_id)`, `PRIMARY KEY (owner, module, resource_type, subscription_id)`,
  `subscription_id REFERENCES subscription(id) ON DELETE CASCADE` (same-DB, `ban04` не задет). Это
  индекс «по владельцу, модулю и виду» DoD 10.1 п.3: поиск кандидатов З7 — диапазон первичного ключа.
  Строки пишет **тот же оператор**, что строку подписки (CTE: вставка подписки `RETURNING`, затем
  вставка `unnest(label_resource_types)`); пути правки подписки нет (NTF-3 Р11), снятие — каскадом.
  Поэтому набор строк дочерней таблицы равен массиву по построению; держатель — УК7-03 (после каждого
  создания в пробах S1 — сверка множеств, расхождение — красный);
- потолок `KACHO_NOTIFY_SUBSCRIPTIONS_PER_USER` — счётчик CAS NTF-3 (З24) без изменений: ветвь
  селектора проходит через ту же транзакцию создания (NTF7-08);
- `23505` по `UNIQUE (owner, target_key, channel)` → `ALREADY_EXISTS`
  `NotificationSubscription for this target already exists` — тем же отображением, что у ветвей
  NTF-3 (дом SQLSTATE один, `sqlstate-to-grpc`);
- `created_at` — часы процесса, усечение до секунды (`api-timestamp-truncate`); `now()` в умолчании
  колонки нет (замысел NTF-3 §6).

Итоговую форму SQL судит `db-architect-reviewer`; замысел называет механизмы, а не текст миграции.

### З6. Чтение подписки — порядок набора по построению (Р2; NTF7-09)

`Get`/`List`/ответ создания отдают `resource_types` из колонки `label_resource_types`, которая
упорядочена и без повторов по `CHECK` (З5) — порядок «по возрастанию строки вида» обеспечен базой, а
не сортировкой при выдаче. `match_labels` — `map` (порядок у отображения не наблюдаем). Ветвь
`label_selector` не несёт ничего о ресурсах (Р10).

### З7. Кандидаты селектора — в транзакции приёма, только среди владельцев строк аудитории (Р5, Р6)

- **Место.** Транзакция приёма `notify-sender` NTF-3 (замысел NTF-3 З19, З34): `inbox_clock` →
  вставка записи `ON CONFLICT DO NOTHING RETURNING` → строки `inbox_audience` **только у вставленной**
  записи → кандидаты мгновенных писем → `INGESTED`. Ветвь селектора добавляет к шагу «кандидаты» один
  оператор; сетевых вызовов в транзакции нет (как у NTF-3).
- **Оператор.** Совпавшие владельцы — одним запросом: дочерняя таблица З5 по ключу
  `(owner = ANY(<владельцы строк аудитории этой записи>), module = M, resource_type = K)` ⋈ подписка
  `channel = 'EMAIL'`, условие меток — `label_match <@ <метки>` (для `CREATED` и `DELETED`) либо
  `label_match <@ <метки> OR label_match <@ <прежние метки>` (для `UPDATED`). `jsonb <@` на плоском
  объекте строк — ровно «каждая пара селектора есть в метках с тем же значением» (Р5 `S ⊆ L`), включая
  пустое значение.
- **Факты — одно значение.** `<метки>` и `<прежние метки>` — тот же разобранный из строки ленты
  набор фактов, который приём передаёт в `ListEventAudience` (S2-B9 NTF-3: «факты — без
  преобразования»); для `DELETED` это факты поколения `g_E − 1`, по которым судится аудитория снятия.
  Второго разбора атрибутов строки нет; состояния ресурса у модуля и у службы доступа приём не читает;
  меток в `kacho_notify` не хранится (параметр запроса, не колонка).
- **Объединение ветвей.** Кандидаты селектора объединяются с кандидатами ветвей `resource`/`project`
  (S2-B6 NTF-3) **по адресату**: строка мгновенного письма ключуется `(адресат, запись события)`,
  вставка — `ON CONFLICT DO NOTHING`; поэтому совпадение одного события с несколькими подписками одного
  адресата даёт одну строку кандидата и одно письмо (Р9, NTF7-23) механизмом базы, а не подсчётом в Go.
- **Вопроса вне аудитории у ветви селектора нет** (Р6): владельцы, которых нет в строках аудитории
  записи, в запрос не попадают (условие `owner = ANY(...)`), поэтому ни `Resolve{event}`, ни чтение
  их подписок не происходит. `Resolve{event, via_subscription}` для ветвей `resource`/`project` — путь
  NTF-3 до транзакции, без изменений (близнец NTF7-21, NTF7-31).
- **Стоимость.** Число кандидатов на событие ≤ число строк аудитории; вызовов к службе доступа от
  ветви селектора — 0 при любом числе подписок (NTF7-31). Барьер поколения (`DEFER(audience_pending)`)
  откладывает строку целиком до транзакции приёма — кандидатов селектора до применения поколения не
  возникает (NTF7-20).
- **Ячейки настроек** `(модуль, RESOURCE_CHANGE, EMAIL)` и `(notify, OWN_ACTIONS, EMAIL)` — та же
  функция ячеек NTF-3 Р10 на шаге сборки письма, без ветвления по ветви цели (NTF7-24, NTF7-25).

### З8. Сборка мгновенного письма спрашивает выдачу о каждой строке (Р9 «Письмо из нескольких строк»)

Замещение NTF-3 Р13 (приёмка §4, строка NTF-3 Р13/NTF3-97) — для **всех трёх** ветвей, одной
функцией сборки мгновенного письма:

- **Сборка** — строки пары «адресат + ресурс» одного окна схлопывания. Сборка собирает множество
  **различных** `enqueued_at` своих строк и зовёт `ResolveSend(<модуль>, resource-event, enqueued_at)`
  по одному разу на значение (строки с равным `enqueued_at` судит один ответ). Ответы живут в
  локальной переменной одной сборки; между сборками (в том числе разных адресатов одной строки) не
  переиспользуются — кэша нет (NTF7-31 близнец: N(k) = 2).
- **Исходы.** `ALLOW` — строка входит в письмо; `REVOKED` — строка получает терминальную отметку
  `DENIED(revoked)` (NTF-1 Р5) и из письма выводится; отложенный ответ (`UNAVAILABLE`,
  `DEADLINE_EXCEEDED` → `DEFER(platform_unavailable)`) — **вся** сборка откладывается до следующего
  прохода без расхода попыток, частичного письма нет; прочие исходы — клетки NTF-1 Р5/NTF-3 Р7 без
  изменений.
- **Письмо — из строк `ALLOW`**, число правок — по ним (форма NTF3-96/97). Ни одной строки `ALLOW` —
  письма нет, и **вопрос адреса `Resolve{self}` не задаётся**: он идёт после решения выдачи, а не до
  (NTF7-32 близнец «после `V2`»).
- **Порядок вызовов** внутри сборки: `ResolveSend` по всем различным `enqueued_at` → при наличии
  `ALLOW` — `Resolve{self}` → постановка письма. Ни одного вызова метода из множества (З) Р5.
- Отметка «событие ушло мгновенным письмом адресату», счётчики схлопывания, всплеска, потолка и
  сетки `notice` — механизм NTF-3 З22 без изменений; письмо считается один раз (Р9).
- Метрики — те же счётчики NTF-3 Р13; новой оси с метками нет (DoD 10.2 п.3); ветвь цели в метки
  метрик не идёт.

### З9. Запись вызовов СЛ3 и вычислитель предиката Р5 — тестовое дерево

- **Запись.** Клиентский перехватчик gRPC (унарный и потоковый), подставляемый в соединения
  `notify-sender` к службам установки **через параметры соединения, которые интеграционная обвязка
  передаёт корню в процессе**; запись — адрес, полное имя метода, тело запроса, код и тело ответа
  (исход, `ErrorInfo.reason`), момент по управляемым часам С6, порядковый номер. Перехватчик ни вызов,
  ни ответ не меняет. Если у корня `notify-sender` такого параметра нет — полоса записи заводит его
  как параметр конструктора корня (не переменную окружения и не ручку), продуктовая сборка передаёт
  пустой набор; второго пути сборки корня не появляется.
- **Вычислитель.** Одна функция тестового дерева судит запись по множествам Р5: (Ф) — методы лент,
  числом не судятся; (О) — решающие ответы, `N(k)` по ключу, переданный сценарием; (П) — закрытый
  перечень отложенных ответов по методу, форма (п1) «каждый раньше решающего того же ключа» и (п2)
  «после `N(k)`-го решающего — ни одного»; (З) — нулём; вызов метода (О) вне (О) и (П) — красный с
  печатью вызова. Перечни (П) и (З) — константы вычислителя с координатами строк Р5 приёмки в
  комментарии; метод, не названный ни в одном множестве, печатается отдельно и исход не меняет.
- **Пустой обход** — запись без единого вызова (О) при ненулевом ожидаемом `N(k)` — красный, а не
  зелёный (держатель — УК7-05 с инъекцией «перехватчик не подставлен»).
- СЛ3 используется NTF7-27, NTF7-31, NTF7-32; С7 NTF-3 (подмена справочника в режиме пересылки) —
  NTF7-14, NTF7-21.

### З10. Средства обвязки S2 (приёмка §5)

- Используются средства NTF-3 §8 по номеру (С1, С6, С7, С9, С13, С21, С22, С23, С25, С26) — их
  производитель S2-B9/S2-B11 NTF-3; NTF-7 их не дублирует.
- **NTF7-32.** `Revoke`/`Restore` выдачи шаблона — через **внутренний** слушатель службы доступа
  обвязки личностью администратора кластера (`usr-ca`, кортеж `system_admin` на `cluster` — С1),
  удостоверение ступени `acr = 2` — **штатным путём повышения ступени** службы доступа обвязки (решения
  владельца 2026-10-08 (1) и диспетчера 2026-10-09 (б)); ступень каталога не понижается ни в обвязке,
  ни на стенде. Новой машинной учётки нет. Нет штатного пути в обвязке на голове полосы — `блокер` с
  ТЗ производителю пути, а не обход. Полоса службы доступа обвязки `notifications.cutoff-guard = 30s`
  (К26) — конфигурация обвязки; отсечка C и `enqueued_at` — чтение баз обвязки (К27).
- **Предусловие «не выполнилось».** Где приёмка требует различных `enqueued_at` (NTF7-27) или
  `enqueued_at(V1) < C + 30s ≤ enqueued_at(V2)` (NTF7-32), проба сверяет условие до «Тогда» и при
  невыполнении печатает «условие не создано» с величинами — исход «не выполнилось», а не красный.

### З11. Консоль — строка «Метки» и разбор ветви клиентом (Р11)

- **Разбор ответа.** Клиент `/notify/v1/*` в `shared` (NTF-6 C1, `ui-future/shared/src/api/notify.ts`)
  принимает третью ветвь `target.labelSelector` с формой `{module: string, resourceTypes: string[],
  matchLabels: Record<string,string>}`; иная форма ветви — отказ формы NTF-6 З6 (не молчаливый
  пропуск). Разбор садится **той же волной**, что сервер ветви, если на базе волны клиент уже есть
  (иначе после посадки сервера консоль получала бы отказ формы на списке подписок пользователя с
  селектором); если клиента на базе нет — разбор третьей ветви входит в задание NTF-6 C1 (`tasks.md`
  §1 «Неделимая цепочка»).
- **Строка.** «Метки · <displayName модуля из каталога> · <подписи видов в порядке ответа> ·
  `k=v`, …» (пары — по возрастанию ключа) и подпись канала из каталога; подпись вида — переходом спеки
  (NTF-6 Р10, Р10а), вид без спеки — строкой `resourceType`. Ключи и значения — только текстовыми
  узлами (NTF-6 Р8): ни `innerHTML`, ни разметки из данных. «Отписаться» — существующее действие
  строки подписки NTF-6 (`DELETE /notify/v1/subscriptions/{id}`).
- Формы заведения селектора нет (§6 приёмки) — действие карточки шлёт только `target.resource`
  (NTF-6 Р10, без изменений).
