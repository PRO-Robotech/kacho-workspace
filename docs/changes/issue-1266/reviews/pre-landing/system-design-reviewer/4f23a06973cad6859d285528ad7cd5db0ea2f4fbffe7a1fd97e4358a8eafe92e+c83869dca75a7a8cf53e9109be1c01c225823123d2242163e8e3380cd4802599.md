## Важные замечания (не блокируют, остаются в записи ревью)

1. **kaname `internal/repo/kaname/pg/access_key_login_repo.go:66-71@9a78fc2`**: `IssueChallenge` замещает испытание двумя операторами, `DELETE … WHERE form_context=$1 AND consumed_at IS NULL`, затем `INSERT`. Инвариант «одно живое испытание на контекст» держит частичный UNIQUE `access_key_login_challenges_live_context_idx`, так что целостность не страдает. Но при двух одновременных выдачах на один контекст вторая получает 23505 (→ AlreadyExists, проход по ошибке хранилища) вместо замещения. Двойное нажатие «начать вход ключом» при этом даёт отказ. Требование, если полоса будет в этом месте: одна инструкция `INSERT … ON CONFLICT (form_context) WHERE consumed_at IS NULL DO UPDATE SET challenge=EXCLUDED.challenge, issued_at=now(), expires_at=…`, плюс проба с двумя горутинами на один контекст. Сейчас проба `TestF13_03_SecondChallengeReplacesTheFirst` только последовательная. Корректности ПО и безопасности находка не касается, поэтому задачей не становится.
2. **kacho `gateway/internal/handler/logout_handler.go:200@fd9f179`**: `Verify` вызывается на `r.Context()` без своего срока. Это осознанное решение приёмки KA1 (Р4, ред. 9, KA1-37): срок держит клиент чтения JWKS, `KACHO_JWKS_FETCH_TIMEOUT_SECONDS`. Запись нужна для полноты оси «дедлайн на каждом внешнем вызове». Предел есть, но не локальный, и при смене клиента JWKS он может пропасть молча. Перепись `TestEveryIdentityAdapterVerbIsBounded` этот вызов не покрывает.
3. **kacho `gateway/internal/restmux/mux.go:446@fd9f179`**: таблица маршрутов сторожа (`routeTable`) регистрируется тем же циклом через `Register*HandlerFromEndpoint`. Поэтому на каждую службу у неё свой клиент моста, обработчики которого не исполняются никогда (`forwardMatchedRoute`). Клиент ленивый (`grpc.NewClient`), соединение без вызова не открывается, так что цена нулевая. Замечание о ясности, а не о свойстве.
