# CI-EBT-1 — DRAFT наблюдаемого интерфейса

Предмет — публичный Go-тест, существующий на Kacho b5fa:
`TestExcludingBuildTagLeavesThePackageBuildable` в internal/repohygiene.
Новый shell/CLI, общий TestMain и изменение кода завершения всего пакета не вводятся.
Этот документ — часть DRAFT, не самостоятельное routine approval.

## Вход

Корень определяется существующим repoRoot от cwd процесса; состав — git-индекс
этого корня. Внешняя среда, включая GOWORK, не переписывается gate. Временные
фикстуры будущего holder получают собственные git-корни и только явно заданную
среду. Имя тега выводится прежним алгоритмом из шапки, а не принимается новой ручкой.

## Выход

Сохраняются человекочитаемая перепись и полные диагностические записи. На каждом
завершившемся пути gate печатает ровно одну строку с префиксом
`excluding-build-tag-result: ` и JSON-объектом следующего закрытого состава:

| Поле | Значение |
|---|---|
| status | CLEAN, FINDING или NOT_EXECUTED |
| go_files_read | число успешно прочитанных содержимых Go-файлов из индексного корпуса; результат parse не входит в этот счётчик |
| candidate_files | число уникальных исключаемых файлов |
| packages_checked | число уникальных пакетов, для которых начата проверка обычной конфигурации; это не число успешных пакетов |
| vet_runs | число реально стартовавших процессов vet; не число успешных сборок |
| load_runs | число реально стартовавших процессов загрузчика Go |
| findings | число доказанных находок исключения |
| not_executed | число невыполненных требуемых проверок по identity (phase, pkg, file, tag) |

Счётчики — целые неотрицательные значения, bool/дробь/отсутствие не считаются
значением. Процесс, который не удалось запустить, не увеличивает vet_runs/load_runs.
Стартовавший процесс ещё не означает полученный compiler verdict: результат
процесса и причина отдельно сохраняются в диагностике. На чистом corpus без кандидатов оба счётчика вызовов 0.

Свёртка: not_executed > 0 даёт NOT_EXECUTED; иначе findings > 0 даёт FINDING;
иначе CLEAN требует непустой успешно прочитанный Go-корпус и завершённость всех
необходимых проверок. Пустой corpus создаёт отдельную невыполненную предпосылку.
Частичная находка сохраняется при общем NOT_EXECUTED, не вычитается из findings.

CLEAN завершает публичный тест успешно. FINDING и NOT_EXECUTED завершают его
через Go testing FAIL; итоговый процесс ненулевой, SKIP не применяется. Читающий
статус holder различает семантическую причину по JSON и реальной диагностике,
а не предполагает отдельный exit code 3 у go test.

## Диагностическая запись

Для каждой невыполненной внешней проверки видимы стадия, пакет, тег при наличии,
argv, причина завершения/запуска и исходные потоки. Стадии: corpus,
platform-discovery, baseline-load, baseline-vet, tagged-load, tagged-vet.
Файл и строка называются там, где их действительно предъявил инструмент;
для невозможности exec не сочиняется компиляторная координата.

Каждая находка называет пакет, исключаемый файл, тег и настоящий полный текст
компилятора. Сведения об очередной неуспешной загрузке не превращаются в
утверждение, что исключённый символ потерян. Сообщение прежней red-инъекции о
потере падучести недопустимо как описание сорванного baseline.

Команды, JSON-loading profile и deadline-политика определены замыслом, а точные
дополнительные диагностические контроли — отдельным proposal. Ни одна строка
интерфейса не утверждает, что новый вывод уже существует на main.

## Точная единица неполноты и чтения

Для baseline/global record file и tag отсутствуют; один отказ baseline одного
пакета считается один раз, независимо от числа его кандидатов. Для tagged record
file — конкретный исключаемый файл, tag — конкретный тег; две проверяемые записи
одного пакета под тем же тегом остаются двумя прежними per-candidate вызовами.
Не вводятся memoization, дедупликация tagged-конфигурации либо новая оптимизация.
Дедупликация not_executed действует только по полной указанной identity и не по
тексту ошибки или числу stdout/stderr-строк.

Исторический b5fa присваивал GoFilesRead=len(indexed .go) до чтения. Это число
перечисленного корпуса, а не доказательство полного чтения на частичном отказе.
Новый контракт считает успешное чтение содержимого файла до разбора шапки:
успешный ReadFile увеличивает счётчик, parse failure не отнимает прочитанное;
неуспешное чтение не увеличивает. На полном lawful corpus число не меняется.
Точная readiness/census таблица находится в scenario-matrix.json; это ожидания
нового контракта, а не подмена исторических captures.
