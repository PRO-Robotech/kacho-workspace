# CI-EBT-1 — диагностические контроли, DRAFT revision 2

Это дополнительные проверки механизма, **не** новые принятые acceptance IDs и
**не** утверждение покрытия CI-EBT-01–11. Исполняемые holder-контроли пока не написаны; операционная конструктивность DC-03 отдельно проверена автором и root, как зафиксировано ниже.
Нужен отдельный readback reviewer до разрешения соответствующего holder.
Ни один механизм ниже не подменяет executable Go и не сочиняет его успешный ответ.

## DC-01 — неизвестная форма диагностического текста

Сначала настоящий Go на CI-EBT-02 производит load-success и compiler failure с
координатой. Этот реальный capture и его provenance становятся положительным
входом чистого классификатора результата: ожидается FINDING. Контроль меняет
только ввод классификатора — префикс диагностической строки vet на явно
неподдержанный префикс, сохраняя статус процесса, body и координату. Ожидается
NOT_EXECUTED с полным сохранённым текстом; второй контроль даёт пустой output при
том же неуспешном статусе. Он тоже NOT_EXECUTED, не CLEAN/FINDING.

Граница доказательства: это проверка отказа decoder/classifier, а не совместимости
с неизвестным будущим Go. Изменённые bytes никогда не подписываются как фактический
вывод Go и не подаются через поддельный go в PATH. Реальную достижимость compiler
FINDING на публичном крае отдельно держит CI-EBT-02.

## DC-02 — весь поток loader JSON обязателен

Положительный вход чистого loader decoder — точный реальный stdout Go-list
CI-EBT-01, сохранённый после успешного процесса. Три независимо однофактных
отрицательных входа: пустой поток; добавлен непустой хвост после последнего JSON;
в одном объекте заявлен Error при rc0. Каждый требует NOT_EXECUTED, а не игнорирования
остатка или доверия rc. Объекты Error/DepsErrors/Incomplete не синтезируют успешный
compiler verdict. Реальные отказы loader с настоящим Go держат CI-EBT-07/08.

Как и DC-01, это отрицательные parser-входы, не утверждение о реально изданном Go
ответе. Holder обязан маркировать их отдельно от actual-process captures.

## DC-03 — настоящий зависший вызов, без counterfeit Go

Предлагаемый OS-level контроль общего command runner использует реальный Go-list
и собственный временный модуль, чей go.mod доступен через FIFO. Положительная
сторона: собственный writer предъявляет через FIFO ровно байты корректного go.mod,
загрузчик завершается и полученный JSON непустой. Отрицательная: при идентичных
команде, модуле и FIFO writer не предъявляет данные, настоящий дочерний Go остаётся
на чтении, наступает объявленный deadline. Нужно захватить фактическую identity
дочернего процесса и подтвердить его завершение, NOT_EXECUTED и отсутствие
оставшихся собственных потомков. Host-wide сигналы, чужие PID и изменение Go
installation запрещены.

Конструктивность уточнена настоящим Go 1.26.8 и независимо повторена root.
Однократная запись недостаточна: Go открывает go.mod дважды. Законный writer
предъявляет ровно один правильный документ и EOF каждому отдельному чтению,
дожидаясь закрытия предыдущего reader fd. В измеренной конструкции два чтения
по 46 байт; before/negative/restored используют тот же FIFO inode и argv.
Без writer настоящий Go блокируется в openat; own cancellation завершает его,
трасса подтверждает конец процесса, очистка удаляет только собственный корень.

только отдельному чистому command-runner control и не доказывает, что публичный
gate применяет production deadline: его достижимость проверяется дополнительно.

## Как читать покрытие

DC-01/02 дают отрицательную полноту parser, CI-EBT-02/07/08 — настоящие ответы Go
и публичную достижимость. DC-03 имеет доказанную операционную конструкцию, но исполнительный
holder, runner status и публичный production deadline ещё не проверены. Нельзя записать «все
диагностические отказы покрыты» по одним 11 acceptance-сценариям или по этой прозе.
