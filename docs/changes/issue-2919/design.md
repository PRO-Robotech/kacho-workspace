## 0а. Сверка соседей в момент «перед одобрением замысла» (правило опоры §1 приёмки; CX4V-49)

**Предикат** — ровно тот, что назван в §1 приёмки. Предмет — записи
`docs/specs/reviews/<приёмка соседа>/*.yaml` с `verdict: APPROVED`, кроме закреплённой записи
(исключена по имени файла). Коммит добавления такой записи — потомок коммита добавления
закреплённой записи:

```sh
pin=<отпечаток закреплённой редакции>; pc=<коммит добавления закреплённой записи>
for f in docs/specs/reviews/<приёмка соседа>/*.yaml; do
  [ "$(basename "$f" .yaml)" = "$pin" ] && continue
  grep -q '^verdict: APPROVED' "$f" || continue
  a=$(git log --diff-filter=A --format=%h -- "$f" | tail -1)
  git merge-base --is-ancestor "$pc" "$a" && echo "$(basename "$f" .yaml) $a"
done
```

Ревизия — воркспейс `3b45bfb3b`. Сверка по строкам берёт коммиты, на которых файл соседа имеет
отпечаток закреплённой и последней одобренной редакции (`git log --format=%h -- <файл>` и
`git show <коммит>:<файл> | sha256sum` по каждому коммиту).

## 2. Решения

Решения пронумерованы З1…З26. Каждое называет механизм и держатель. Держатель — сценарий приёмки
либо проба, заказанная записью разбора (§11а). Где держателя нет и заказ не принят, сказано
«вниманием».

### З1. Раскладка notify: пакеты, два корня, граница импорта

- **Два корня — два развёртывания** (Р22). `services/notify/cmd/notify` — это `notify-sender`, корень
  заводит NTF-1. `services/notify/cmd/notify-api` — это `notify-api`. Кто заводит второй корень, решает
  З18 «Порядок посадки относительно NTF-3». У каждого корня свой загрузчик ручек (З22) и свой реестр
  метрик (З13).
- **Пакеты NTF-4** — все под `services/notify/internal/`:

  | пакет | что держит | кто импортирует |
  |---|---|---|
  | `addresskey` | чтение каталога ключа отпечатка, функция отпечатка, контрольное значение (З2, З3) | оба корня, `deliver`, `feedback`, `suppression`, `apiserver` |
  | `secretreload` | перечитыватель объекта секрета, один тип на оба объекта (З4) | оба корня |
  | `returnaddr` | токен возврата, назначения `b`/`u`/`c`, сборка адреса (З5) | `deliver`, `feedback`, `canary` |
  | `sentlog` | журнал отправленных (З6) | `deliver`, `feedback`, `reputation` |
  | `pop3` | клиент POP3 поверх неявного TLS (З7) | `feedback` |
  | `feedback` | сеанс ящика, разбор, классификация, применение (З7, З8) | корень `notify-sender` |
  | `suppression` | хранилище подавлений, правила Р5, подметальщик (З9) | `deliver`, `feedback`, `apiserver` |

  NTF-4 правит в местах, названных решениями ниже.

  таблицы выше серверного gRPC не импортируют.

    `notify-sender` с координатой (DoD S3 п.8).
  - Дополнительно проба печатает, достижим ли `apiserver` от `cmd/notify`. Ожидаемый ответ — «нет».

### З2. Ключ отпечатка: объект, чтение, функция отпечатка; замещение ключа сетки NTF-1 (Е11 NTF-1)

- **Объект ключа отпечатка — это объект ключа сетки NTF-1** с тем же постоянным именем
  `<установка>-recipient-key` и тем же значением values `notify.recipientKey` (32 байта, отказ рендера
  `required`, шаблон ключа не порождает — З28 NTF-1).
  - NTF-4 меняет у объекта две вещи. Форма подачи: том целиком, а не `secretKeyRef` (Р11, NTF4-117
    случай (4)). Число монтирующих: два, `notify-sender` и `notify-api` (Р15, Р22).
  - *Почему не новый объект.* Смена имени дала бы окно, в котором старые поды ссылаются на снятый
    объект, а поды нового набора — на новый. Кроме того, байты ключа пришлось бы переносить. У нового
    имени нет читателя, которому оно нужно: «объект ключа отпечатка» приёмки — роль объекта, а не имя.
- **Чтение.** `KACHO_NOTIFY_ADDRESS_KEY_DIR` задаёт каталог монтирования (Р16).
  - Файл ключа — `<каталог>/recipientKey`. Это ключ данных объекта, имя — постоянная `addresskey.FileName`.
  - Чтение идёт через разрешённый каталог `..data` (З4), содержимое проверяется правилом NTF-1: ровно 32 байта.
  - Каталог без файла, файл другой длины, нечитаемый файл — отказ старта с именем ручки. Содержимого
    файла текст отказа не называет (CX4V-62).
- **Функция отпечатка — одна, и строится один раз на процесс** (CX4V-07, CX4T-07, CX4S-07 (а)).
  - `addresskey.New(key []byte, normalize NormalizePort) (*Func, error)` строит значение `*Func`. Оно
    создаётся в корне развёртывания ровно один раз и передаётся конструкторам. Второго вызова `New` в
    не-тестовом дереве нет.
  - Держатель единственности — AST-гейт `addresskeysingular_test.go` (УК4-06): вызовов `addresskey.New`
    вне `cmd/notify`, `cmd/notify-api` и тестов 0, по одному в каждом корне.
  - Перечитыватель объекта ключа `New` не зовёт и контрольного значения не считает (З4, CX4V-07
    вариант (б)). Поэтому гейт УК4-06 на законном дереве молчит, а вызов `New` в `secretreload`
    — его инъекция.
  - `Func.Of(address.Normalized) (Print, error)` вычисляет `HMAC-SHA256(key, n.Value())`, то есть ту же
    конструкцию, что ключ сетки NTF-1 (З24 NTF-1). Поэтому З11 приёмки («ключ сетки — отпечаток Р15»)
    исполняется без смены значения ключа сетки. Нулевое значение `address.Normalized` даёт ошибку
    `addresskey.ErrUnset`, которая оборачивает `address.ErrUnset`, и отпечатка не делает (Р15). Для
    строки ленты это `INVALID(recipient_invalid)`, для сообщения обратной связи — `recipient_mismatch`.
  - `Func.OfRaw(s string) (Print, error)` = порт нормализации + `Of`. Порт зовут разбор
    `Final-Recipient`/`Original-Rcpt-To`/`From` и `Lookup`. Строку, которую порт не разобрал, функция
    возвращает ошибкой, и отпечатка сырой строки не бывает (CX4S-07 (г)).
  - `Print` — массив `[32]byte`. Функция его в текст не превращает: в журнал и в метки он не попадает (§3 И12).
- **Порт нормализации — параметр конструктора, а не поле конфигурации** (CX4T-38).
  - Тип порта — `func(string) (address.Normalized, error)`. Значение этого типа можно получить только
    из `address.Normalize` NTF-1, потому что тип `address.Normalized` непрозрачен (редакция 13 NTF-1).
  - В обоих корнях значение порта одно — `address.Normalize`.
  - Держатель (а)/(б) — AST-предикат `normalizeportvalue_test.go` (УК4-07). Он находит каждый вызов
    `addresskey.New` вне тестов и утверждает, что второй аргумент — идентичность функции
    `address.Normalize` (`types.Func` из пакета `notify/address`), а не значение, выведенное из
    конфигурации. Инъекция — второй аргумент через переменную пакета → находка.
- **Ключ не выходит из значения** (CX4V-62).
  - Поле ключа в `Func` неэкспортируемо. Экспортируемого доступа к байтам нет.
  - Поскольку `fmt` и `slog` печатают неэкспортируемые поля (М18), у `Func` есть методы `String`,
    `GoString`, `Format` и `LogValue`. Все они отдают `addresskey.Func{redacted}`. `MarshalJSON` и
    `MarshalText` возвращают ошибку.
  - Держатель — модульная проба `redaction_test.go`. Она печатает значение через `fmt` (`%v`, `%+v`,
    `%#v`), `slog` (текст и JSON) и `json` и проверяет `NotContains` байтов испытательного ключа в hex и
    base64 с контролем непустого захвата. Сквозная проба журнала и самоотчёта — УК4-19.
- **Замещение ключа сетки NTF-1 — одномоментно и без смены байтов** (снимает Е11 замысла NTF-1).
  Форма выбрана «одномоментно», окна перехода с учётом под двумя ключами нет.
  - Ключ и конструкция HMAC те же, поэтому отпечаток адреса не меняется. Строки сетки
    `recipient_net` остаются действующими, и сетка на адресата **не** начинается заново. Следствие
    З24 NTF-1 («сетка заново на длину самого длинного окна») наступает, только если оператор в том
    же переходе сменит байты ключа. Тогда у установки нет контрольного значения (его заводит этот
    переход, З3), и первое записанное значение будет от нового ключа. Прочее следствие — как в З24
    NTF-1: потолок потока и окна источника не затронуты.
  - **Ограда ключа сетки NTF-1 снимается вместе с её предметом.** Снимаются таблица
    `recipient_key_fence`, первый оператор транзакции резерва, запись ограды при старте, сторож
    `limits.ErrRecipientKeySuperseded`, константа `limits.FenceLockTimeout` и аннотация
    `checksum/recipient-key`.
    - Довод. Ограда держит «реплик с разными ключами на одной базе не бывает» для ключа, который
      ротируется перекатом. У NTF-4 ключ не ротируется (Р11). Процесс, чей ключ не даёт записанного
      контрольного значения, не стартует. Перечитывание со сменой ключа отвергается (З3). Значит, на
      базе с контрольным значением у всех работающих процессов один ключ, и ограда второй раз
      держит то же свойство — два места об одном предмете.
    - Аннотация `checksum/recipient-key` после Р11 только запускала бы перекат, который не может
      завершиться: новые поды не стартуют при `maxUnavailable: 0`.
    - Снятие делает новая миграция `DROP TABLE recipient_key_fence`. Применённая миграция NTF-1 не
      правится (ban #5).
    - **Снос встречает страж сноса** (CX4V-63). Мигратор notify до наката зовёт `dropguard.Gate`
      (corelib `migratorrun/runner.go:162` @`34bc810`). Страж считает строки в таблице, которую
      снесёт ещё не применённая миграция. В ограде на базе, где стартовала реплика NTF-1, одна
      строка: её пишет старт (З24 NTF-1). Без одобрения страж откажет в накате, и новые поды
      не встанут. На свежей базе таблицы ещё нет: страж относит снос к `AbsentAt`, и одобрение
      не нужно. Условия к коду и полосы — §11, строка CX4V-63.
    - Гейт раскладки NTF-1 D1 (`deploy/notify_secret_layout_test.go`) переписывается той же полосой
      на форму Р11: том целиком, два монтирующих, аннотации нет. Его прежние утверждения (только
      `secretKeyRef`, монтирующий один) стали бы красными на законном дереве (З21).
  - **Окно самого перехода** (стадия S1 NTF-4). Реплики NTF-1 (с оградой) и реплики NTF-4 (с
    контрольным значением) живут вместе в пределах переката (`maxSurge: 1`).
    - При тех же байтах ключа отпечатки одинаковы, и расхождения нет.
    - Реплика NTF-1, чья транзакция резерва читает ограду после миграции снятия, получает ошибку
      базы. По правилу NTF-1 это «не сторож»: резерва нет, `MAIL FROM` не начинается, `Ack` не
      шлётся, строку после конца аренды выдаёт реплика нового набора (З24 NTF-1, путь без `Ack`).
      Дублей и потерь нет. Счётчик `notify_reserve_db_errors_total` растёт на время переката, и это
      названный след перехода, а не дефект.
    - Миграция снятия ограды идёт в том же изменении, что таблица контрольного значения, и
      следующей по номеру (§6).
    - На базе со строкой ограды переход без одобрения сноса не начинается. init-контейнер
      `migrate` нового пода отказывает до наката, а старые реплики продолжают резервировать под
      оградой. С одобрением действует окно, описанное выше. Поэтому одобрение ставится до выкатки
      S1, а не после отказа (§11, CX4V-63).

### З3. Контрольное значение отпечатка: набор, запись, сверка

- **Закреплённый набор объявлен один раз, неизменяемым массивом** (CX4T-37 (а), (б)) —
  `addresskey.controlSet [6]string` в `addresskey/controlset.go`. Состав:
  1. `MixedCase.Local@Example.ORG` — заглавные буквы в локальной части и в домене;
  2. `user@bücher.example` — Unicode-домен;
  3. `user@xn--bcher-kva.example` — его A-label;
  4. `user@straße.example` — домен с `ß`;
  5. `user@STRASSE.example` — заглавные буквы в домене, сводимые профилем;
  6. `postmaster@example.org`.

  Рядом с массивом стоит комментарий о следствии правки. Любая правка набора, порядка или склейки
  меняет контрольное значение, и каждая установка перестаёт стартовать после обновления. Правка
  допустима только вместе с переносом записей — это вне объёма (§9 приёмки).
- **Значение** = `SHA-256("kacho-notify/address-key-check/v1" ‖ 0x00 ‖ Of(n₁) ‖ … ‖ Of(n₆))`, где
  `nᵢ = порт(controlSet[i])` в порядке массива. Обхода отображения нет, склейка — фиксированная
  длина 32 байта на элемент (CX4T-37 (б)). Считает значение тот же экземпляр `Func`, которым
  ключуются таблицы (CX4T-37 (г)). В базе хранятся 32 байта значения, а не ключ и не отпечатки
  набора.
- **Таблица — одна строка на установку, ограничение на уровне схемы** (CX4V-55):
  `address_key_check (singleton boolean PRIMARY KEY DEFAULT true CHECK (singleton), value bytea NOT
  NULL CHECK (octet_length(value) = 32), written_at timestamptz NOT NULL)` (§6).
- **Запись и сверка — одна функция** `addresskey.Establish(ctx, pool, fn *Func, now) error`. Её
  зовут оба корня на старте, после миграций и до подъёма слушателей, до первого `Claim` и до
  перечитывателя. Второй реализации в `cmd/notify-api` нет. Функция делает три шага:
  1. `INSERT INTO address_key_check (singleton, value, written_at) VALUES (true, $v, $now) ON CONFLICT DO NOTHING RETURNING value`;
  2. если строк ноль, та же функция читает `SELECT value FROM address_key_check` и сравнивает с
     `$v` через `hmac.Equal`;
  3. при несовпадении возвращает ошибку `addresskey.ErrControlMismatch`. Её текст — «контрольное
     значение отпечатка адреса не совпало с записанным: ключ из KACHO_NOTIFY_ADDRESS_KEY_DIR или
     профиль нормализации отличаются от тех, которыми заведена база». Ключа, отпечатков и адресов
     набора в тексте нет (Р11, CX4V-62).

  Проверки «строки нет — вставляю» до вставки нет. Перезаписи нет ни на одном пути: `UPDATE` и
  `DELETE` по этой таблице в не-тестовом дереве — 0 операторов, это утверждает AST-гейт
  `addresskeycheckwriters_test.go` (УК4-08) по литералам SQL в `services/notify`. Гонку двух
  развёртываний держит NTF4-116 (50 повторов под `-race`, (а) и (б)). Проигравший вставку читает
  значение, записанное выигравшим, потому что конфликт ждёт коммита (CX4V-20, CX4S-20).
- **Строка читается один раз при старте** (CX4V-54). После `Establish` в базу за этой строкой не
  ходит никто. Перечитывание объекта ключа сверяет новое поколение с дайджестом байтов ключа, от
  которых построен `Func` и которые `Establish` сверил с базой (З4, CX4V-07 вариант (б)).
  Поэтому исхода «база не ответила» у перечитывания нет, и закрытый набор трёх исходов Р11 не
  меняется.
- **Отказ старта** — ненулевой код до подъёма слушателей (NTF4-114, NTF4-106), текст выше.
- **Проба «золотого значения»** (CX4T-37 (в), УК4-05): `controlvalue_golden_test.go` считает
  контрольное значение при постоянном испытательном ключе (32 байта `0x00…0x1f`) и сравнивает с
  литералом hex в той же пробе.
  - Литерал заводит полоса один раз, выводом той же функции на дереве с набором выше. Проба
    печатает вычисленное значение, чтобы литерал брался из вывода, а не руками.
  - Правка набора, порядка, склейки, функции отпечатка или профиля IDNA на пине corelib краснит
    пробу в CI до посадки.
  - Инъекции: переставлены элементы 2 и 3; снят элемент 6; значение над постоянной строкой. Все
    три красные.

### З4. Перечитыватель секретов: один тип, состояние на объект

- **Один тип `secretreload.Watcher[T]`**, параметризованный объектом (CX4V-53). У каждого объекта
  свой экземпляр и своё состояние: действующий набор (`atomic.Pointer[T]`), дайджест действующего
  набора, исход последней попытки, каталог последнего разрешённого поколения и время последнего
  принятого набора.
  - У `notify-sender` два экземпляра: `mail` (объект секрета почты) и `address_key`. У `notify-api`
    один: `address_key`.
  - Экземпляры друг друга не читают, поэтому исход одного не меняет действующего набора другого (Р11).
- **Такт** — таймер внедрённых часов с периодом `KACHO_NOTIFY_SECRET_RELOAD_INTERVAL` (З23).
  Попытка на такте происходит, если выполнено хотя бы одно из условий:
  - поколение сменилось — `..data` указывает на другой каталог;
  - последний исход — «отложен»;
  - последний исход — «отвергнут».
- **Поколение разрешается один раз.** `os.Readlink(<каталог>/..data)` даёт абсолютный путь
  поколения. Все файлы читаются из этого пути, а не через `..data` повторно, поэтому набор из
  двух поколений не собирается (CX4S-18).
- **«Тот же набор» — по содержимому** (CX4T-39). Дайджест —
  `SHA-256(Σ (len(name) ‖ name ‖ len(bytes) ‖ bytes))` по файлам поколения в порядке имён. Путь,
  имя каталога `..data` и `mtime` в дайджест не входят. Совпадение с дайджестом действующего набора
  даёт исход «принят» без подмены. При этом признак `secret_reload_rejected` у объекта снимается.
- **Проверка набора целиком, затем атомарная подмена указателя.** Исходы закрыты — `accepted`,
  `rejected`, `deferred` (Р11). Функция проверки объекта возвращает значение закрытого типа
  `secretreload.Outcome`. Ветки «прочее» нет: `switch` по трём значениям исчерпывающий, и
  `exhaustive` линтера держит его:
  - `mail`: разбор всех файлов (слоты SMTP/POP3, ключ и селектор DKIM, кольцо ключа токена). Ошибка
    разбора даёт `rejected`, причина — `unparsable`. Селектор не сменился — `accepted`. Селектор
    сменился — проверка `dkim` Р10 через `dnscheck` с таблицей З14: запись есть и ключ совпадает —
    `accepted`; записи нет или ключ другой — `rejected`, причина — `dkim`; ответа нет — `deferred`;
  - `address_key` (CX4V-07, вариант (б)): читается только файл `addresskey.FileName` разрешённого
    поколения, и дайджест этого объекта считается над ним одним. Файла нет или в нём не 32 байта —
    `rejected`, причина — `unparsable`. Дайджест совпал с действующим — `accepted` по общему правилу
    выше, `Func` не пересобирается. Дайджест не совпал — сразу `rejected`, причина —
    `control_mismatch`, без построения `Func` и без счёта контрольного значения.
    - Довод. Данных у объекта одно поле, и другой дайджест значит другие байты ключа. HMAC с другим
      ключом над закреплённым набором даёт другое контрольное значение. Значит, исход «принят» у
      этой ветки недостижим, и функция отпечатка ей не нужна.
    - `deferred` у этого объекта недостижим построением: шага DNS в его функции проверки нет
      (CX4V-53).
- **Строка WARN** — одна на переход признака объекта из 0 в 1: имя объекта и причина, без
  содержимого (CX4V-62).
- **Признак `secret_reload_rejected` реплики вычисляется при чтении**, а не пишется событием
  (CX4V-53). Это `prometheus.GaugeFunc`, который отдаёт `OR` по исходам последней попытки каждого
  экземпляра этого процесса. Принятое перечитывание одного объекта поэтому не снимает признака,
  поднятого другим. Держатель — УК4-17: `mail` отвергнут, затем `address_key` принят → признак 1;
  близнец — `mail` принят → 0.
- **Каждое соединение фиксирует набор при установке** (CX4S-18). SMTP-сессия строки, соединение
  попытки контрольного письма и POP3-сеанс берут `Load()` указателя один раз, до `Dial`, и
  держат значение до конца соединения. Подмена во время соединения на него не действует.
- **Смешанное поколение** (УК4-16) — проба на временном каталоге. Файлы нового поколения
  записываются по одному, и между записями `..data` переключается на промежуточный каталог. Попытка
  на каждом шаге читает либо полный прежний набор, либо полный новый, но не смесь. Инъекция —
  чтение каждого файла через `..data` → смешанный набор, проба красная.

### З5. Токен возврата и адрес с токеном

- **Назначение — закрытый тип.** `returnaddr.Purpose` — структура с неэкспортируемым байтом.
  Значений три — `PurposeBounce` (`b`), `PurposeUnsubscribe` (`u`), `PurposeCanary` (`c`) —
  объявлены в одном месте (CX4T-36 (а)). Нулевое значение даёт ошибку `returnaddr.ErrPurposeUnset`,
  и адреса не получается. Строкой назначение не передаётся.
- **Раскладка токена** (Р2): байт назначения, байт версии ключа кольца, 8 байт полезной нагрузки и
  16 байт кода аутентичности — всего 26 байт.
  - Полезная нагрузка у `b` и `u` — `id` строки журнала (`bigint`, З6), у `c` — номер выпуска (З12).
    Оба в порядке big-endian.
  - Код аутентичности = первые 16 байт `HMAC-SHA256(ключ кольца версии v, назначение ‖ v ‖ нагрузка ‖ ns)`.
    Для `c` вместо `ns` пустая строка.
  - Текст токена — Crockford base32 без выравнивания: 42 символа при любом значении, это меньше 48 (Р2).
- **Разбор — одна функция на три назначения** (CX4S-06). Шаги по порядку:
  1. длина ровно 42 символа — до декодирования;
  2. приведение к верхнему регистру;
  3. декодирование строгим алфавитом;
  4. версия ключа из кольца. Неизвестная версия даёт `bad_token`;
  5. для `b` и `u` — чтение строки журнала по `id` (З6): `ns` для кода берётся из строки, а не из сообщения;
  6. сверка кода через `hmac.Equal` (постоянное время).

  Ошибка любого шага даёт `bad_token` без паники. Назначение читается из проверенного токена. Токен
  в нижнем регистре применяется так же, как в верхнем (УК4-03).
- **Кольцо ключа токена** — `active` и `previous` в объекте секрета почты (Р11). Токен под
  `previous` принимается, пока не истёк срок журнала (З6).
- **Сборка адреса — одна функция** `returnaddr.Build(p Purpose, payload uint64, ns string) (string, error)`.
  Она собирает `<LOCAL_PART>+<токен>@<RETURN_DOMAIN>`. Второго места, где склеиваются локальная
  часть, `+` и токен, в `services/notify` нет (CX4T-36 (г)). Держатель — AST-предикат
  `returnaddrsingular_test.go` (УК4-09): литерал `"+"` в выражении склейки строк вне `returnaddr`
  по `services/notify`.
- **Куда уходит адрес.**
  - Envelope `MAIL FROM` — строкой в SMTP-сессию. В сборщик заголовков он не передаётся (CX4T-36 (в)).
  - `List-Unsubscribe` — результатом функции `notify/form` (`form.ParseHeaderText("<mailto:" + адрес + ">")`)
    над строкой, которую вернула `Build`, без промежуточной правки. Ошибка `notify/form` на этом
    пути даёт `INVALID(attrs_invalid)` без SMTP-сессии (CX4T-36 (б)).
  - Контрольное письмо — `RCPT TO` и `To` (З12).

  Преобразований в типы формы вне `notify/form` нет (CX4S-31, NTF1-B28).
- **Длина локальной части** проверяется загрузчиком: `…_LOCAL_PART` ≤ 15 октетов, при длине
  токена 42 и `+` получается 58 ≤ 64. Нарушение — отказ старта `return_address` (NTF4-79).

### З6. Журнал отправленных

- **Таблица `sent_log`** (§6): `id bigint GENERATED ALWAYS AS IDENTITY`, `ns`, `feed_row_id`,
  `template`, `class`, `recipient_fp bytea(32)`, `message_id`, `created_at`, `accepted_at` (`NULL` —
  ретранслятор `DATA` не принял), `UNIQUE (ns, feed_row_id)`. Сырого адреса нет (Р3).
- **Запись до `MAIL FROM`** — в клетке 10 (З10), отдельной короткой транзакцией:
  `INSERT … ON CONFLICT (ns, feed_row_id) DO UPDATE SET ns = EXCLUDED.ns RETURNING id`.
  - Повтор той же строки ленты переиспользует строку журнала (CX4S-05 (г)).
  - Ошибка базы — это путь «без `Ack`», как ошибка резерва NTF-1: `MAIL FROM` не начинается.
- **Отметка `accepted_at`** ставится после `250` на `DATA`. Своей метрики у неудачи отметки нет
  (CX4V-64, вариант (а)): перечень Р12 закрыт, и NTF-4 метрик вне него не заводит. Неудача видна
  строкой журнала уровня ERROR с `id` строки журнала отправленного и без адреса и отпечатка (З25).
  Исход строки ленты от неё не меняется: письмо принято, `Ack SENT` уходит, и его считает счётчик
  исходов NTF-1 `notify_outcomes_total`. Такое письмо не входит в знаменатель долей (З13), и это
  названная цена.
- **Контрольное письмо и его номера в журнал не пишутся** (CX4S-05 (д)).
- **Срок** — `KACHO_NOTIFY_SENT_LOG_RETENTION`. Уборка удаляет строки с
  `created_at <= $now − срок` партиями. Сообщение о письме старше срока — `stale` (Р3).
- **Исполнитель уборки по сроку** (CX4V-65) — проход подметальщика З9, то есть держатель одиночки
  (З11) на том же таймере. Отдельного таймера, ручки и исполнителя нет. Проход убирает
  `sent_log` (с ним каскадом `feedback_event`), `feedback_message` и `canary_issue` (§6). Каждая
  партия — своя транзакция, открытая продлением аренды. Предел партии и «сейчас» — §11, строка
  CX4V-65.
- **Окно долей не длиннее срока журнала** — зависимая граница Р16 приёмки (редакция 22, RA-02):
  `…_REPUTATION_WINDOW > …_SENT_LOG_RETENTION` — отказ старта. Поэтому уборка по сроку не
  укорачивает окно долей молча (§11, CX4V-65).

### З7. Сеанс ящика: POP3, аренда внутри сеанса, фиксация по сообщению

- **Клиент POP3 — свой, пакет `pop3`**, поверх `crypto/tls` (неявный TLS, проверка сертификата
  неотключаема) и `net/textproto`.
  - Команды: `USER`, `PASS`, `STAT`, `UIDL`, `RETR`, `DELE`, `QUIT`.
  - Коды ответа разбираются по RFC 2449/3206 в закрытый тип: `[AUTH]`, `[IN-USE]`, `[SYS/TEMP]`,
    `[SYS/PERM]`, «без кода». Прочие коды в `[…]` считаются «без кода» — это строка таблицы З16, а не корзина.
  - Модуль не нужен: протокол из семи команд меньше зависимости (М17).
- **Порядок сеанса** — только у держателя аренды. Сеанс запускает такт, а исполняет горутина
  держателя вне функции такта; такт её не ждёт (З11, К1 ревью замысла `80dea362`):
  1. аренду перед запуском сеанса продлевает такт (З11). Сама горутина сеанса начинается с запуска
     независимого продления (ниже), своего продления в начале у неё нет (пересверка `1a5cf53f`);
  2. вход по таблице слотов (З16);
  3. `STAT`. При пустом ящике — сразу `QUIT`;
  4. `UIDL` — перечень сообщений на момент открытия. Пришедшие позже читает следующий сеанс (Р21);
  5. по каждому сообщению перечня — `RETR` через `io.LimitReader(MAX_MESSAGE_BYTES + 1)`. Объём
     больше предела — `unparsed(too_large)` независимо от размера в `LIST` (CX4S-22);
  6. дайджест `SHA-256` байтов сообщения;
  7. **одна транзакция на сообщение** (Р21):
     - первым оператором — продление аренды с условием «держатель = я, эпоха = E, срок > $now» (З11).
       Ноль строк — отката и конец сеанса;
     - `INSERT INTO feedback_message (digest, …) ON CONFLICT DO NOTHING RETURNING`. Ноль строк —
       результат `duplicate`, эффектов нет;
     - эффекты разбора (З8, З9);
     - метка `last_poll_success_at = $now` в строке состояния (З13);
  8. `DELE` — только после коммита (CX4S-02 (д));
  9. после перечня — `QUIT`: удаление фиксирует сервер в состоянии UPDATE.
- **Независимое продление** (CX4S-02 (а)–(в)). Пока сеанс открыт, отдельная горутина продлевает
  аренду тем же условным обновлением каждые `LEASE_TTL / 3`.
  - Таймер — внедрённые часы (З23).
  - Соединение — своё, из пула. Транзакция фиксации его не занимает.
  - Ноль строк отменяет контекст сеанса и ставит срок на сетевое соединение
    (`conn.SetDeadline(time.Now())`). Заблокированный `RETR` прерывается.
  - Решение о праве фиксировать принимает только условие в транзакции фиксации (CX4S-02 (г)).
    Горутина лишь ускоряет выход.
  - После потери аренды `QUIT` не посылается: соединение закрывается. Удаление по `DELE`
    фиксируется только после `QUIT`, так что незафиксированное в ящике остаётся (Р21). `DELE`
    посылается только для зафиксированных сообщений, поэтому потерь нет.
  - Держатель — NTF4-104 и заказ УК4-02: одно сообщение, чтение которого П10 растягивает шагами
    часов Δ < TTL/3 на суммарно больше TTL. Ожидаемо: применено, эпоха та же, `[IN-USE]` 0.
    Близнец — продление, сведённое к вызову в начале сеанса, даёт красный.
- **Срок каждой сетевой операции** (К1 ревью замысла `80dea362`, строка Д26 · 7 (1), (2)). Без него сервер
  ящика, который принял TCP и замолчал (завис `RETR`, соединение полуоткрыто), держал бы сеанс вечно:
  независимое продление шло бы, смены держателя не было бы, очередь ящика стояла бы.
  - Установка соединения — `net.Dialer{Timeout: pop3.opTimeout}`. Рукопожатие TLS и каждая команда
    `USER`, `PASS`, `STAT`, `UIDL`, `RETR`, `DELE`, `QUIT` вместе с чтением ответа идут под
    `conn.SetDeadline(time.Now().Add(pop3.opTimeout))`, который ставится перед командой.
  - При чтении ответа `RETR` срок продлевается на каждом чтении, вернувшем байты: долгое, но идущее
    чтение не прерывается, молчание прерывается.
  - `pop3.opTimeout` = 10 с — постоянная кода (§8), не ручка. Она не больше наименьшей трети срока
    аренды: нижняя граница `…_LEASE_TTL` — 30 с (Р16).
  - Срок считает сетевой стек по реальному монотонному времени, а не внедрённые часы (З23). Поэтому
    NTF4-104, который растягивает сеанс шагами управляемых часов при быстром ответе двойника, срока
    не задевает.
  - Срок сработал — соединение закрывается без `QUIT`, контекст сеанса отменяется, горутина
    независимого продления выходит до возврата сеанса. Сеанс кончается временным сбоем опроса (путь
    POP3 З16): метки `last_poll_success_at` нет, незафиксированные сообщения остаются в ящике (Р21),
    повторное чтение ничего не меняет (Р14). Следующий такт открывает новый сеанс.
  - Сервер, который отдаёт байты хотя бы раз за `pop3.opTimeout`, но не доводит сообщение до конца,
    сеанс держит. Это названная цена, и она видна: вычисление признаков сеанса не ждёт (З11), поэтому
    без фиксаций `feedback_stale` поднимается по Р12.
  - Держатель — заказ УК4-37 (§11а).
- **Идемпотентность по дайджесту** (Р14). Строка `feedback_message` хранит размер, дайджест,
  результат и причину. Содержимого нет. Повторное чтение после обрыва до `QUIT` ничего не меняет
  (NTF4-10).

### З8. Разбор и классификация сообщения

- **Вид — закрытая таблица**, одна функция `feedback.KindOf`, проверки идут в порядке (Р2):
  1. адрес доставки с токеном `c` — вид `canary`, до ветки `unparsed`;
  2. `multipart/report; report-type=delivery-status` с токеном `b` — `dsn`;
  3. `report-type=feedback-report` с токеном `b` — `arf`;
  4. адрес доставки с токеном `u` — `unsubscribe`;
  5. сообщение на адрес `rua` без токена с вложением агрегатного отчёта — `dmarc_aggregate`;
  6. иначе — `unknown`, результат `unparsed`.
- **Откуда токен** — одно место на вид (Р2):
  - `dsn`, `unsubscribe`, `canary` — адрес доставки. Его даёт заголовок `Delivered-To`/`X-Original-To`,
    и порядок источников объявлен в `feedback.deliveryAddressHeaders`. Строки, которые туда кладёт
    П10 и приёмник стенда, названы в корпусе образцов;
  - `arf` — `Original-Mail-From` машиночитаемой части, иначе `Return-Path` вложенного письма, иначе `bad_token`.
- **Получатель** — `Final-Recipient` (DSN), `Original-Rcpt-To` (ARF), `From` письма отписки (Р2,
  условие 3). Сверка идёт через `Func.OfRaw` против `recipient_fp` строки журнала. Неразбираемый
  адрес даёт `recipient_mismatch` (Р15).
- **Классификация отказа — одна таблица и одна функция на оба пути** (CX4S-09).
  `feedback.Classify(action, status string, syncRCPT bool) Kind` по Р4. Ключ таблицы —
  `(Action, класс кода, расширенный код)`, по строке на каждое условие Р4. Для синхронного 5xx на
  `RCPT` без расширенного кода есть своя строка. Ветки по умолчанию, которая подавляет, нет:
  неразобранный код попадает в строку `unclassified`, а она только считает.
- **Ограничения разбора** (CX4S-22, Р14):
  - MIME — стандартные `mime/multipart` и `net/mail`. Глубина вложенности ≤ 8
    (`feedback.maxMIMEDepth`), число частей ≤ 64 (`feedback.maxMIMEParts`) — постоянные кода, не ручки;
  - распаковка отчёта DMARC — `compress/gzip`, `archive/zip`. Ограничители на каждое вложение и на
    сумму: `MAX_MESSAGE_BYTES × MAX_EXPANSION_RATIO`. Архив внутри архива даёт `unparsed(nested_archive)`;
  - XML — `encoding/xml.Decoder` со `Strict = true` и пустым `Entity`. Токен `xml.Directive`
    (`<!DOCTYPE…>`) даёт `unparsed(xml_directive)`. Внешние сущности не разрешаются, ссылки не разыменовываются.
- **Корпус образцов** — `services/notify/internal/feedback/testdata/corpus/`. У каждого образца
  один ожидаемый исход. Держатель сверяет корпус с таблицей в обе стороны: у каждой строки таблицы
  есть образец, у каждого образца — строка (DoD S1 п.3). В корпус входит DSN, доставленный
  повторно с другими трассировочными заголовками (УК4-11).

### З9. Подавление: запись, событие, видимость, уборка

- **Схема** (CX4S-10, §6):
  - таблица `suppression` с колонками `id` (`nsp-…`), `recipient_fp`, `reason`, `scope`,
    `template_ns`, `template_name`, `created_at`, `last_event_at`, `expires_at`;
  - `template_ns` и `template_name` — `NOT NULL`, пустая строка означает «область шире шаблона»;
  - `UNIQUE (recipient_fp, reason, template_ns, template_name)`;
  - `CHECK` причины и области по таблице Р5;
  - `CHECK ((scope = 'NOTICE_TEMPLATE') = (template_ns <> '' AND template_name <> ''))`;
  - `CHECK ((expires_at IS NULL) = (reason IN ('COMPLAINT','UNSUBSCRIBE')))`.

  Отказ `CHECK` (23514) сервис отображает в `INTERNAL` фиксированным текстом: вход клиента эти
  поля не задаёт. Держатель — интеграционная проба «вставка в обход правила → 23514» (УК4-12).
- **Применение события — одна функция** `suppression.Apply(tx, fp, reason, ns, tmpl, now)` в
  транзакции сообщения (З7). Шаги:
  1. `DELETE … WHERE ключ AND expires_at IS NOT NULL AND expires_at <= $now` — истёкшая, ещё не
     выметенная запись считается отсутствующей (CX4S-11);
  2. `INSERT … ON CONFLICT (ключ) DO UPDATE SET last_event_at = $now, expires_at = <по причине> RETURNING id, (xmax = 0)`.
     Новая строка даёт `applied` с новым `id` и `createdAt = $now`. Обновлённая действующая даёт `refreshed`.

  Держатель — заказ УК4-13: `SOFT_BOUNCE` истёк, подметальщик не срабатывал, новый порог → новый
  `id`. Гонку по одному адресу держит NTF4-31 (8 горутин).
- **Событие уникально по паре** (CX4S-05 (а)). Таблица `feedback_event (sent_log_id, kind, recipient_fp, occurred_at, PRIMARY KEY (sent_log_id, kind))`.
  - `INSERT … ON CONFLICT DO NOTHING`. Ноль строк — событие уже записано: результат `duplicate`,
    ни счётчики, ни подавление не меняются.
  - Порог мягких отказов (Р5) считает уникальные события `soft` адреса в окне
    `occurred_at > $now − SOFT_WINDOW` (CX4S-05 (б)).
- **Видимость** — условие `expires_at IS NULL OR expires_at > $now` стоит в каждом чтении: `Get`,
  `Lookup`, `Delete`, выдача (Р5). От подметальщика видимость не зависит.
- **Подметальщик** — `DELETE … WHERE expires_at <= $now` партиями по таймеру
  `KACHO_NOTIFY_SUPPRESSION_SWEEP_INTERVAL` на внедрённых часах. Работает у держателя одиночки
  (З11): одна реплика на установку.
- **Причина исхода** — функция `suppression.Pick(records, class, ns, tmpl) (Reason, bool)`. Она
  перебирает закрытый порядок `hard_bounce → complaint → unsubscribe → soft_bounce` (Р5) и
  фильтрует записи по области: `ALL_CLASSES` — любой класс; `NOTICE` — только `notice`;
  `NOTICE_TEMPLATE` — только `notice` той же пары.
- **Метки счётчика жалоб — только из строки журнала, подтверждённой токеном** (CX4S-21).
  - Пара `(ns, шаблон)` вне сборки notify ряда не порождает: счётчик — типизированная функция над
    закрытым перечнем пар сборки.
  - Подавление по такой жалобе применяется.
  - Событие считается в `notify_feedback_messages_total{kind="arf",result="applied"}`. Держатель — NTF4-33 и DoD S7 п.3.
- **Класс письма — только из сборки** (CX4S-15). `suppression.Pick` получает класс из
  `deliver.Resolved.tmpl.Class` (З22 NTF-1), колонку `class` строки ленты не читает. Держатель —
  заказ УК4-14: строка объявляет `security` у шаблона класса `notice` → `INVALID(class_mismatch)`
  клеткой 2 NTF-1 до подавления. Близнец — класс строки совпадает, подавление по `NOTICE` срабатывает.

### З10. Выдача строки: клетка подавления, исход один раз на выдачу, ответ на `Ack`

- **Клетка 6а в `deliver.Decide`** (З22 NTF-1; Р8; CX4S-08). NTF-4 вставляет одну клетку в
  объявленный список клеток NTF-1 — после клетки 6 (`INVALID(attrs_invalid)`) и до клетки 7 (право):

  | № | клетка | исход | что дальше не судится |
  |---|---|---|---|
  | 6а | действующая запись подавления для отпечатка адресата подавляет класс или пару строки (`suppression.Pick`) | `SUPPRESSED(reason)` | всё: ни `ResolveSend`, ни резерва сетки и потолка, ни SMTP-сессии |

  - Клетка 5 NTF-1 (`INVALID(recipient_invalid)`) идёт раньше. Без разобранного адреса нет
    отпечатка, и записи подавления для такой строки не читаются (Р17).
  - Место до права (7) выбрано по тому же доводу NTF-1, что для клеток 2–6. Строку, которую
    отправить нельзя, notify не носит в kaname.
  - Место до сетки (9) требует Р8: слот сетки и потолка подавленная строка не расходует
    (NTF4-101, близнец NTF4-102).
  - Чтение записей — один `SELECT` с условием видимости `$now` (З9) через порт
    `deliver.SuppressionReader`. Его значение в корне — `suppression.Store`.
- **Порядок действует на каждой выдаче** (CX4S-08 (а)). `Decide` вызывается на каждой выдаче
  строки, в том числе повторной после `DEFER`. Отсюда подавление, появившееся между выдачами,
  срабатывает на повторе. Держатель — заказ УК4-15: `DEFER(recipient_net)`, затем запись
  `HARD_BOUNCE`, затем повторная выдача → `SUPPRESSED(hard_bounce)`, SMTP-сессий 0.
- **Решение «подавлено» ни на одном пути не превращается в SMTP-сессию** (CX4S-08 (б)). Шаг
  `Step` клетки 6а — вариант закрытого типа `deliver.StepAck`. Сессию открывает только вариант
  `StepSend` клетки 10, а исчерпывающий `switch` по шагу держит линтер `exhaustive`.
- **Исход решается один раз на выдачу** (CX4S-30, Р17). Исход с причиной записывается в запись
  обработки строки у исполнителя (З24 NTF-1: «признак освобождён живёт в записи обработки строки»)
  до первого `Ack`. Повтор `Ack` этой выдачи шлёт значение из записи и `Decide` не зовёт.
  Держатель — NTF4-110 с инъекцией «повтор пересчитывает причину», близнец NTF4-111.
- **Ответ на `Ack` — закрытая таблица Р17** (CX4S-30 (б), (в)). Функция
  `deliver.ReadAckAnswer(err) AckAnswer` возвращает одно из закрытых значений:
  - успех;
  - `OUTCOME_ALREADY_RECORDED` — исход уже записан, строка закрыта;
  - `LEASE_LOST` — строка не этой выдачи;
  - транспортный сбой — повтор в пределах аренды;
  - вне таблицы — строка остаётся за уборщиком источника. Своего счётчика у этой ветки нет
    (CX4V-64, вариант (а)): ответ вне таблицы — род «отказ» классификатора `deliver/peeranswer`
    NTF-1, и сигнал ему даёт NTF-1 — `misconfigured` со счётчиком `notify_misconfigured_total`
    (З23, З27 NTF-1). Второго счётчика об одном событии нет.

  Различение идёт по коду gRPC и по `reason` из `ErrorInfo` — это классификатор чужого ответа
  NTF-1 (`deliver/peeranswer`, З23 NTF-1). Второго классификатора нет. Ни одна ветка не открывает
  SMTP-сессию и не шлёт `DEFER`.
- **Отказ источника принять `SUPPRESSED`** (CX4S-08 (в)). Ответ «вне таблицы» оставляет строку до
  `expires_at` без SMTP-сессии.
- **Синхронный 5xx на `RCPT`** (CX4S-09, Р4). SMTP-путь клетки 10 классифицирует ответ функцией
  `feedback.Classify(…, syncRCPT=true)`. Для рода `hard` запись подавления фиксируется **отдельной
  транзакцией до `Ack`**. Сбой `Ack` её не откатывает. Повторная выдача той же строки находит
  действующую запись и даёт `refreshed`, а не вторую запись. Исход строки — `RECIPIENT_REJECTED`
  при любом коде (клетка NTF-1, NTF1-G14).
  - Отпечаток адресата берётся из `deliver.Resolved.recipient`, уже разобранного в клетке 5.
  - Событие `feedback_event` заводится с `sent_log_id` строки журнала этой выдачи (З6).
- **Класс** — только `deliver.Resolved.tmpl.Class` (CX4S-15, З9).

### З11. Одиночка установки: аренда с эпохой

- **Таблица `feedback_lease`** — одна строка (§6): `holder text`, `epoch bigint`,
  `lease_until timestamptz`, `first_acquired_at timestamptz NOT NULL`.
  - `holder` — идентичность реплики: имя пода плюс 128 бит случайного числа, выбранного при старте
    процесса. Перезапущенный под поэтому не наследует аренду прежнего процесса.
- **Взятие** — одна из двух форм, каждая одним оператором:
  - первое взятие на установку:
    `INSERT (singleton, holder, epoch, lease_until, first_acquired_at) VALUES (true, $me, 1, $now + ttl, $now) ON CONFLICT DO NOTHING RETURNING epoch`;
  - иначе: `UPDATE … SET holder = $me, epoch = epoch + 1, lease_until = $now + ttl WHERE lease_until <= $now RETURNING epoch`.

  Выигрывает ровно одна реплика (Р21). `first_acquired_at` пишет только `INSERT`, а `UPDATE` его
  не трогает (CX4T-46): смена держателя момента отсчёта первого выпуска не переписывает.
  Держатель — заказ УК4-10: держатель сменяется каждые I/2 до первого выпуска; выпуск 1 — на первом
  такте не раньше первой аренды + I.
- **Продление** — `UPDATE … SET lease_until = $now + ttl WHERE holder = $me AND epoch = $e AND lease_until > $now`.
  Эпоху продление не меняет (CX4S-01 (а), NTF4-95). Оно выполняется:
  - в начале каждого такта опроса, до входа в ящик;
  - первым оператором каждой транзакции держателя;
  - независимой горутиной сеанса (З7).
- **Каждая запись держателя — под условием аренды** (CX4S-01 (б)). Первый оператор транзакции —
  продление. Ноль строк — отказ всей транзакции, и держатель прекращает действовать до следующей
  попытки взять аренду. Список писателей закрыт:
  - фиксация сообщения;
  - заведение номера выпуска;
  - отметка «принят»;
  - метка опроса;
  - переходы признаков установки;
  - проход подметальщика, в том числе уборка по сроку журнала: `sent_log` (каскадом
    `feedback_event`), `feedback_message`, `canary_issue` (З6, CX4V-65).

  Держатель — AST-гейт `leaseguardedwrites_test.go` (УК4-01а). Каждая функция пакетов `feedback`,
  `canary`, `reputation`, `suppression` (подметальщик) и `sentlog` (уборка по сроку), открывающая
  транзакцию на запись, первым вызовом в ней зовёт `lease.Renew`. Исключение одно — запись строки
  журнала и отметка `accepted_at` на пути письма (З6): их пишет реплика, выдающая строку, а не
  держатель. Гейт знает их по идентичности функции, а не по имени. Инъекция — фиксация без
  продления → находка с координатой.
- **Допущение о часах названо** (CX4S-01 (в)). Реплика, чьи часы ушли вперёд, берёт аренду раньше,
  чем держатель видит её истёкшей. Корректность от этого не зависит. Взятие меняет эпоху, и
  следующая запись прежнего держателя с условием его эпохи даёт ноль строк. От расхождения часов
  зависит только число отказов `[IN-USE]` у двойника или ящика, когда два сеанса на миг
  пересекаются. Держатель — заказ УК4-01: два экземпляра с разными управляемыми часами. Ожидаемо:
  фиксаций вне эпохи 0, эпоха растёт на каждой смене.
- **Действия держателя — только на такте** (CX4T-45). Выпуск контрольного письма и вычисление
  признаков установки (`feedback_route`, `feedback_stale`, доли) вызываются только внутри функции
  такта `lease.Tick`. Отдельных таймеров на `…_CANARY_INTERVAL` и `…_CANARY_DEADLINE` нет. Держатель —
  заказ УК4-18: I не кратно P, выпуск на такте, а не в t0 + I.
- **Порядок в такте, сеанс вне такта** (К1 ревью замысла `80dea362`, строка Д26 · 7 (4)). `lease.Tick`
  исполняет по порядку: продление; переходы признаков (З13); выпуск контрольного письма, если он
  назрел (З12); запуск сеанса ящика, если прежний сеанс завершился. Сеанс исполняет горутина
  держателя, таких горутин на процесс не больше одной, и такт её не ждёт. Поэтому долгий или
  зависший сеанс переходов признаков не задерживает: задержка вычисления не больше `POLL_INTERVAL`
  плюс срок попытки контрольного письма (`canary.AttemptTimeout`, не больше `LEASE_TTL / 3`, З12).
  Ноль строк продления на такте отменяет контекст сеанса так же, как ноль строк независимого
  продления (З7).
- **Жизненный цикл горутины сеанса** (CX4V-66, строка Д26 · 7 (5), (6)).
  - Контекст горутины сеанса — производный от контекста работы держателя. Функция работы держателя
    возвращается только после выхода горутины сеанса и горутины независимого продления; пул базы
    корень закрывает после её возврата. При молчащем сервере ящика возврат наступает не позже
    `pop3.opTimeout` плюс запас: срок операции З7 действует и при остановке. Держатель — заказ
    УК4-37 (в).
  - Признак «сеанс идёт» снимает сама горутина при выходе — канал завершения, который она
    закрывает отложенным вызовом, а не такт по своему расчёту. Такт читает его без ожидания и не
    запускает новый сеанс, пока прежний не вышел, в том числе после потери аренды и повторного
    взятия с новой эпохой. Держится прогоном УК4-37 под `-race` и вниманием рецензента: гейта на «не
    больше одной» нет.
- **Уровень изоляции транзакций держателя** (CX4V-66, строка Д26 · 7 (7)). Каждая транзакция
  держателя на запись — от такта, сеанса и подметальщика — открывается с явным
  `pgx.TxOptions{IsoLevel: pgx.ReadCommitted}`, как `Establish` (строка Д26 · 2), а не с умолчанием
  роли. Под `repeatable read` вторая транзакция на `UPDATE` строки `feedback_lease` получила бы
  отказ сериализации (40001), а не ожидание, и утверждение следующего пункта о строчном замке было бы
  ложным. С редакции 6 сеанс и такт пересекаются на каждом такте, поэтому условие нужно. Держатель —
  заказ УК4-37 (г); УК4-01а судит первый вызов `lease.Renew`, а не уровень изоляции.
- **Таймеров вне такта два, и решений о выпуске и признаках они не принимают** (М1 ревью замысла `80dea362`):
  независимое продление сеанса (З7) и таймер подметальщика `…_SUPPRESSION_SWEEP_INTERVAL` (З9,
  строка Д26 · 6). Транзакции держателя от такта, сеанса и подметальщика сериализует строчный замок
  аренды: первый оператор каждой из них — условное обновление строки `feedback_lease` (см. выше).
- **Сравнение с `singlepass`** (CX4S-28, М7). `singlepass.TryAcquire` — сессионный рекомендательный
  замок: он живёт, пока жив сеанс соединения. У него нет эпохи, по которой запись прежнего
  держателя отвергается после смены, и нет срока в базе, переживающего падение процесса. Аренде Р21
  нужны оба свойства:
  - условие эпохи в каждой транзакции фиксации — одна реплика в ящике, даже когда часы расходятся;
  - состояние в базе, которое переживает смену держателя (`first_acquired_at`).

  Поэтому аренда — второй механизм, **частный для notify** (`services/notify/internal/lease`). В
  corelib она не переносится, пока второго потребителя нет. Своего рекомендательного замка notify
  не заводит. Шапка пакета называет `singlepass` и довод выше.

### З12. Контрольное письмо

- **Состояние в базе** (Р10, Р21). Последовательность `canary_issue_seq`, таблица `canary_issue (issue bigint PK, created_at, accepted_at NULL)` и строка состояния `feedback_state` (З13) с полями:
  - `expected_issue bigint NULL`;
  - `expected_accepted_at timestamptz NULL`;
  - `last_accepted_at timestamptz NULL`;
  - `last_canary_read_at timestamptz NULL`.

  «Ожидаемого выпуска нет» — `expected_issue IS NULL`, а не нулевое время (CX4S-03 (в)).
- **Выпуск — на такте держателя.** Условие выпуска на такте: `$now ≥ база + I`, где база —
  `last_accepted_at`, а если его нет — `feedback_lease.first_acquired_at` (Р10, CX4T-46). Попытка,
  которую ретранслятор не принял, базу не двигает, поэтому следующий такт повторяет её с новым
  номером (Р10). Шаги:
  1. транзакция: продление, затем `nextval('canary_issue_seq')` и вставка `canary_issue`. Номер
     заводится до отправки (CX4S-03 (б));
  2. отправка **отдельной функцией** `canary.Send(ctx, set, issue) Result` с закрытым результатом
     `{accepted, not_accepted}` (CX4S-03 (а)). Контекст вызова несёт срок попытки
     `context.WithTimeout(ctx, attemptTimeout)` (К1 ревью замысла `80dea362`; CX4V-67, строка
     Д26 · 7 (3)). Срок вышел на любой стадии — `not_accepted`, база не двигается. Держатель —
     заказ УК4-38;
  3. при `accepted` — транзакция: продление, `UPDATE canary_issue SET accepted_at = $now`, затем
     `expected_issue = n`, `expected_accepted_at = $now`, `last_accepted_at = $now`. Отметка ставится
     только после ответа `250` на `DATA`.
- **Срок попытки против срока аренды** (CX4V-67, вариант (а) пересверки `1a5cf53f`).
  - `attemptTimeout = canary.AttemptTimeout(smtpSessionTimeout, leaseTTL)` =
    `min(smtpSessionTimeout, leaseTTL / 3)`. Первый аргумент — ручка NTF-1 `notify.smtp.sessionTimeout`
    из разобранной структуры NTF-1, второй — `…_LEASE_TTL` из разобранной конфигурации NTF-4. Функция
    одна, корень `cmd/notify` зовёт её один раз при сборке и передаёт значение в `canary`; второго
    вычисления нет (§8).
  - Довод. `canary.Send` идёт внутри такта синхронно, и аренду во время вызова никто не продлевает:
    независимое продление живёт, только пока открыт сеанс ящика (З7), а сеанс идёт отдельно и может
    быть закрыт. Шаг 1 продлевает аренду первым оператором, так что к началу вызова до истечения
    остаётся `LEASE_TTL`. Вызов кончается не позже `LEASE_TTL / 3`, и шаг 3 застаёт аренду живой.
    Без границы релей, отвечающий дольше остатка аренды, отдавал бы аренду другой реплике на каждом
    выпуске: клетка (д), ожидаемый выпуск не заводится, `feedback_route` не поднимается никогда.
  - Отношение то же, что у соседних полос этого механизма: `pop3.opTimeout ≤ LEASE_TTL / 3` (З7) и
    срок вызова `Claim` в NTF-1 (CX1-72). Замысел NTF-1 правка не затрагивает.
  - Цена названа и видна. Релей, который отвечает на `DATA` дольше `LEASE_TTL / 3` (не меньше 10 с при
    наименьшем сроке аренды), даёт `not_accepted` на каждой попытке: база не двигается,
    `notify_feedback_canary_issues_total{result="not_accepted"}` растёт на каждом такте выпуска (Р12),
    держатель и эпоха прежние.
- **`canary.Send` не зовёт классификатор исходов строк NTF-1** и не касается размыкателя и сигнала
  `misconfigured` (CX4S-03 (а)).
  - Функция стоит на примитиве сессии NTF-1 `smtp.Session` (подключение, TLS, вход по таблице слотов
    З16, `MAIL FROM`, `RCPT`, `DATA`). Примитив возвращает стадию и код ответа, а сводит их в
    `{accepted, not_accepted}` сама `canary.Send`.
  - Классификатор З26 NTF-1 и размыкатель живут в пути строк (`deliver` и цикл источника), и
    `canary` их не импортирует. Держит это граница импорта в AST-гейте `canaryimports_test.go` (УК4-20).
  - Если реализация NTF-1 посадит размыкатель внутрь `smtp.Session`, полоса контрольного письма
    выносит его в путь строк, прежде чем звать примитив. Это место названо здесь, как требует CX4S-03 (а).
- **Клетка (д)** (CX4S-03 (д)). `250` на `DATA` получен, а транзакция отметки не записалась
  (аренда потеряна, база не ответила). Такая попытка считается `accepted` в
  `notify_feedback_canary_issues_total`, но ожидаемым выпуском не становится. Следующий держатель
  или такт повторяет выпуск с новым номером. Письмо этого номера, если оно дойдёт, — `stale`.
  Держатель — заказ УК4-04: инъекция срыва отметки после `250` → счётчик `accepted` +1,
  `expected_issue IS NULL`, следующий такт заводит номер n + 1.
- **Прочтение** (Р2). Сообщение вида `canary`: токен `c` проверен, номер равен `expected_issue` →
  в транзакции сообщения:
  - `expected_issue = NULL`, `last_canary_read_at = $now`;
  - переход `feedback_route` 1→0 условным обновлением (З13);
  - результат `applied`.

  Номер не равен ожидаемому — `stale`, состояние не меняется (CX4S-03 (г)).
- **`feedback_route`** — вычисляется в функции такта держателя. Если
  `expected_issue IS NOT NULL AND $now ≥ expected_accepted_at + D` и признак равен 0 — переход 0→1
  условным обновлением, строку WARN пишет выигравший. Новый принятый выпуск признака не снимает
  (Р10): шаг 3 выше `feedback_route` не трогает. Держатель — NTF4-107 с инъекцией «признак =
  текущий ожидаемый просрочен».
- **Контрольное письмо** не пишется в журнал, не проходит сетку и потолок NTF-1 (оно не идёт через
  `Decide`) и не входит в знаменатель долей (Р10, CX4S-05 (д)).

### З13. Признаки установки и реплики, метрики NTF-4

- **Строка состояния `feedback_state`** — одна на установку: `last_poll_success_at` и поля
  контрольного письма (З12). **Таблица признаков `install_flag`**:
  `(kind, ns, template, value smallint CHECK (value IN (0,1)), changed_at, PRIMARY KEY (kind, ns, template))`.
  Для признаков, не относящихся к шаблону, `ns` и `template` — пустые строки. Ряды `complaint_rate`
  заводятся по одному на пару `notice` из сборки при старте держателя, вставкой
  `ON CONFLICT DO NOTHING`.
- **Оба перехода — условным обновлением** (CX4S-04 (а), (в)): `UPDATE install_flag SET value = $to, changed_at = $now WHERE kind = … AND ns = … AND template = … AND value = $from RETURNING 1`.
  - Строку WARN пишет только выигравший переход 0→1.
  - Переход 1→0 строки WARN не пишет.
  - Вычисляет и пишет держатель одиночки на своём такте в транзакции, открытой продлением (З11).
- **Правила снятия** — по Р12:
  - `hard_bounce_rate` и `complaint_rate`:
    - числитель — уникальные события рода в окне `occurred_at > $now − REPUTATION_WINDOW`
      (`feedback_event`, CX4S-05 (б));
    - знаменатель — строки `sent_log` с `accepted_at` в том же окне (CX4S-05 (в));
    - доля выше порога — переход 0→1, не выше — 1→0;
  - `feedback_stale`: `$now − last_poll_success_at > POLL_STALE_MAX` — переход 0→1. Следующая
    фиксация — переход 1→0 в той же транзакции, что метка опроса. Правило вычисляется на каждом
    такте и сеанса ящика не ждёт (З11), так что зависший сеанс признак не глушит (УК4-37 (б));
  - `feedback_route` — по З12.

  Переход 1→0 по каждому признаку держит заказ УК4-04а: доля опускается ниже порога, выходом
  событий из окна по часам процесса → признак 0 на обеих репликах; повторное нарушение → вторая
  строка WARN.
- **Не-держатели читают признаки** каждым тактом `POLL_INTERVAL` одним `SELECT` из `install_flag` и
  `feedback_state` (CX4S-04 (б)). Новой ручки нет. Проба, сверяющая равенство признака на
  репликах, ждёт схождения в пределах такта (CX4S-04 (г)); держатель — DoD S7 п.2а.
- **Признаки реплики** — `dns_posture`, `rotation_incomplete`, `secret_reload_rejected`,
  `notify_mail_dns_posture{check}`, `notify_credential_slot_in_use`, `notify_feedback_poller_active`.
  Это `GaugeFunc` над состоянием процесса. Строку WARN пишет реплика, где случился переход.
- **Реестр метрик строит корень развёртывания** (CX4V-52, М3). Функция
  `reputation.Register(reg prometheus.Registerer, set reputation.Set)` получает набор явно:
  - `SenderSet` — весь перечень Р12;
  - `APISet` — только `notify_reputation_breach{kind="secret_reload_rejected"}`,
    `notify_secret_reload_attempts_total{object="address_key", result}` и
    `notify_secret_generation_applied_timestamp{object="address_key"}`.

  Регистрации при импорте пакета (`init`, `promauto`, пакетная переменная с регистрацией) в
  `services/notify` нет. Держатель — AST-гейт `metricsregistration_test.go` (УК4-21) по
  идентичности `promauto.*` и `prometheus.MustRegister` вне функции, получившей `Registerer`
  параметром. Число рядов у `notify-api` утверждает NTF4-113, состав наборов обоих развёртываний
  против объединения Р12 и перечня NTF-1 по реестру корня — УК4-34 (CX4V-64, строка Д26 · 5). Все ряды перечня объявляются со
  старта: счётчики и признаки — 0, метки времени — 0 (Р12).
- **Метки — закрытые перечни** (Р12). Счётчики вызываются типизированными функциями над
  перечислениями пакета, свободной строки в метке нет. Адреса, домена и отпечатка в метках нет —
  держатель DoD S7 п.3 (инъекция метки адреса).

### З14. DNS: проверки, классификация ответа, резолвер

- **Проверки Р10** — функции пакета `dnscheck`: `dkim`, `spf`, `dmarc`, `alignment`, `mx` и
  проверка `return_address` (длина, З5). Исход каждой — закрытый тип
  `{ok, violated(причина), noanswer}`.
- **Род ответа DNS — закрытая таблица без корзины** (CX4S-17). Функция `dnscheck.classifyErr(err) Answer`:

  | ошибка | род |
  |---|---|
  | `nil` | ответ получен |
  | `*net.DNSError` с `IsNotFound` | записи нет |
  | `*net.DNSError` с `IsTimeout` или `IsTemporary` | ответа нет |
  | `*net.DNSError` без трёх признаков | ответа нет (своей строкой: сервер ответил не по протоколу) |
  | иная ошибка (отмена контекста, сеть) | ответа нет |

- **TXT склеивает стандартный резолвер** без разделителя (М16). Несколько записей `v=spf1` или
  `v=DMARC1` — нарушение. Несколько записей DKIM под одним селектором — тоже нарушение.
  Двойник П7 отдаёт запись DKIM несколькими строками TXT — заказ УК4-22.
- **Организационный домен** считает одна функция `dnscheck.OrgDomain(address.Domain) (address.Domain, error)`
  на `golang.org/x/net/publicsuffix.EffectiveTLDPlusOne` (М17).
- **Сравнения доменов — только в нормализованной форме** (CX4S-07 (б), Р10). По месту:
  - домен `From` (ручка NTF-1) и домен возврата (`KACHO_NOTIFY_RETURN_DOMAIN`) приводятся
    `address.NormalizeDomain` в загрузчике один раз. Дальше они живут значениями `address.Domain`.
    Их ASCII-форма гарантирована и границей ручки, но сравнение идёт по результату
    `NormalizeDomain`, так что второго пути нет;
  - `d=` подписи — домен `From`, то же значение;
  - адрес `rua` — `address.Normalize` над `mailto:`-частью;
  - получатели обратной связи — порт нормализации (З2).

  Вызова пакета IDNA в `services/notify` нет. Держатель — гейт NTF1-B27.
- **Резолвер — порт конструктора `*net.Resolver`**, а не ручка (Р10). В корне это резолвер пода
  (`net.DefaultResolver`). Проба передаёт резолвер с `Dial` на П7.
- **Срок одного запроса** (М3 ревью замысла `80dea362`, строка Д26 · 9). Каждый вызов резолвера идёт под
  `context.WithTimeout(ctx, dnscheck.queryTimeout)`; `dnscheck.queryTimeout` = 5 с — постоянная кода
  (§8), не ручка. Срок считает сетевой стек по реальному времени (З23). Истёкший срок — строка
  «ответа нет» таблицы выше, своей строки у него нет. Число выбрано так, что в наименьший
  `…_DNS_BOOT_DEADLINE` (10 с; ручка NTF-1, Р19 NTF-1 — из Р16 её перенесло решение Д96) входят две попытки, а проверка кончается задолго до следующей
  перепроверки (`…_DNS_RECHECK_INTERVAL` ≥ 1 мин). Держатель — заказ УК4-40.
  - В строку «ответа нет» идёт только истечение собственного срока запроса при живом родительском
    контексте (`errors.Is(err, context.DeadlineExceeded)` и `parent.Err() == nil`). Отмена родителя
    при остановке процесса исходом проверки не является: признак перепроверки не меняется, отказа
    старта с именем проверки нет, проверка просто прекращается (пересверка `1a5cf53f`, строка
    Д26 · 9). Держатель — близнец УК4-40 «родитель отменён во время молчания П7».
- **Старт.** Повтор при «ответа нет» до `KACHO_NOTIFY_DNS_BOOT_DEADLINE` на внедрённых часах.
  Нарушение — отказ старта с именем проверки. До прохождения всех проверок `/readyz` отвечает «не готов».
- **Перепроверка** каждые `KACHO_NOTIFY_DNS_RECHECK_INTERVAL`. Исход перепроверки при временном
  отказе назван (CX4S-17): «ответа нет» признака `notify_mail_dns_posture{check}` не меняет —
  остаётся прежнее значение. Признак мигает только от ответа, а не от сбоя резолвера.
  `dns_posture` = OR по проверкам (Р12).
- **Проверка `dkim` при перечитывании секрета почты** — та же функция с той же таблицей (З4).

### З15. Подпись DKIM и сборщик заголовков

- **Подпись — свой пакет `dkim`** на `crypto/rsa` (`SignPKCS1v15`, SHA-256): канонизация
  `relaxed/relaxed` (RFC 6376 §3.4.2, §3.4.4), теги `v`, `a=rsa-sha256`, `c`, `d`, `s`, `h`, `bh`,
  `b`. Перечень `h=` берётся из Р9, `from` в нём повторён дважды, `list-unsubscribe` — только если
  заголовок есть.
  - Модуль не берётся (М17): подпись — сотня строк стандартной библиотеки, а зависимость пришлось бы
    вести `govulncheck` на пути каждого письма.
  - **Проверяет подпись в пробах независимая реализация** — тестовая зависимость
    `github.com/emersion/go-msgauth/dkim` (только `_test.go`). Иначе подпись и проверка одного кода
    сходились бы при общей ошибке канонизации.
- **Подпись — последний шаг над окончательным письмом** (CX4S-16). После неё идёт только
  dot-stuffing транспорта. Сборщик письма NTF-1 отдаёт байты с `Message-ID`, `Date`,
  `List-Unsubscribe` и телом в CRLF. `dkim.Sign` добавляет заголовок `DKIM-Signature` в начало
  письма и байты не меняет.
- **Заголовки NTF-4 собирает сборщик NTF-1** (CX4S-31, CX4T-31). `List-Unsubscribe` приходит в него
  значением `form.HeaderText` из `notify/form` (З5). Второй функции сборки заголовков или адреса
  возврата notify не заводит. Держатель — гейт NTF1-B28.
- **Держатели** — NTF4-41 и NTF4-70 (сквозные, проверка подписи полученного письма и её инъекционный
  близнец с изменённым байтом тела).

### З16. Слоты кредов и таблица ответа на вход

- **Таблица объявлена один раз** — `mailslots.LoginTable` (CX4S-19). Она отдаёт только **смысл**
  ответа — закрытый тип `LoginMeaning`:
  - `accepted`;
  - `password_rejected` — повод пробовать `previous`;
  - `transient`;
  - `misconfigured`;
  - `in_use`;
  - `indistinct` — POP3 `-ERR` без кода: одна попытка `previous`.

  Строки — ровно таблица Р11.
- **Перевод смысла в исход** — у вызывающего пути (CX4S-19). Путь строк переводит в
  `DEFER(platform_unavailable)` и `misconfigured` (клетки NTF-1). Путь контрольного письма — в
  `not_accepted`. Путь POP3 — во временный сбой опроса. Таблица исходов строк не знает.
- **Слот меняется только успешным входом.** Состояние слота хранится на протокол и реплику:
  `current`/`previous` и время последней попытки `current`. После успеха через `previous` реплика
  ходит слотом `previous` и пробует `current` не чаще раза за такт `SECRET_RELOAD_INTERVAL` и при
  каждом принятом новом наборе (Р11). Соединение попытки контрольного письма идёт по той же таблице
  (Р11).
- **Корпус ответов SMTP и POP3** — в пробе: у каждой строки таблицы один ожидаемый смысл, сверка в
  обе стороны (DoD S6 п.1).

### З17. `InternalSuppressionService`: сценарии, операции, аудит, права

- **Раскладка** — `services/notify/internal/apiserver/suppression/{get,lookup,delete}.go`. На каждый
  глагол — сценарий с тонким обработчиком gRPC, по регламенту слоёв kacho.
- **Порядок первых выражений** (CX4S-13):
  - `Get` и `Delete`: `suppressionId` пуст → `INVALID_ARGUMENT` `"suppression_id: required"`, затем
    `corevalidate.ResourceID(…, "nsp")` → `INVALID_ARGUMENT` `invalid suppression id '<значение>'`,
    `reason = INVALID_RESOURCE_ID` (NTF4-82). Держатель пустого `suppressionId` — заказ УК4-23;
  - `Lookup`: `address` пуст → `INVALID_ARGUMENT` `"address: required"`; не разбирается портом →
    `INVALID_ARGUMENT` `"address: not a valid email address"`. Значение адреса в текст не
    подставляется, полосы `reason` у этого отказа нет (NTF4-29).

  Права спрашивает звено прав до обработчика (Р18: права → формат → …).
- **Порядок `Lookup`** — `ORDER BY created_at, id`, и он назван в комментарии поля proto (§5).
  Метки времени усечены до секунды на каждой записи (`.Truncate(time.Second)`), `expiresAt` при
  `NULL` не заполняется (Р7).
- **`Delete`** (CX4S-14):
  1. синхронно: формат, затем чтение с условием видимости. Нет записи → `NOT_FOUND`
     `"Suppression <id> not found"`, `reason = RESOURCE_NOT_FOUND`, операция не создаётся (NTF4-83…85);
  2. создание операции (`ids.NewID` с префиксом `nop`, Х1) с принципалом из доверенной пары
     извлечения (`grpcsrv`), а не из заголовка (CX4S-14 (в));
  3. `operations.RunSync(ctx, repo, op, fn)`. Функция `fn` исполняет одну транзакцию: `DELETE FROM suppression WHERE id = $1 AND (expires_at IS NULL OR expires_at > $now) RETURNING id`.
     Одна строка → запись аудита в той же транзакции, коммит. Ноль строк → `fn` возвращает
     **необёрнутый** `status.Error(codes.NotFound, …)` с `ErrorInfo{reason: RESOURCE_NOT_FOUND}`,
     записи аудита нет (CX4S-14 (а), (б), NTF4-86). Обёрнутый статус `status.FromError` подменил бы
     сообщением `internal worker error` (`operations/worker.go:657` @`34bc810`, приёмка §1.1, строка «операции»);
  4. `RunSync` пишет терминальный исход отдельно после `fn`. Если процесс упал между коммитом снятия
     и терминальной отметкой, операцию разрешает **сверщик операций** `operations.NewReconciler` в
     корне `notify-api`, как у шести служб kacho (М6; CX4S-14 (г)). Resolver сверщика не вводит
     исходов сверх Р18 и выбирает один из трёх случаев:
     - есть запись аудита с `operation_id` этой операции — снятие закоммичено, операция `done` без
       ошибки;
     - записи аудита нет, а действующая запись подавления есть — сверщик исполняет ту же `fn`
       (снятие и аудит одной транзакцией);
     - нет ни записи аудита, ни действующей записи — операция завершается `NOT_FOUND` тем же
       текстом и `reason`, что проигрыш гонки (Р18).

     Держатель — заказ УК4-24: процесс гасится между коммитом снятия и терминальной отметкой, а
     также до коммита; в обоих случаях сверщик доводит операцию до формы Р18, записей аудита 1.
- **Граница `OrphanGrace`** (М2 ревью замысла `80dea362`, строка Д26 · 8). Сверщик берёт только операции, чей
  `modified_at` старше `OrphanGrace` (`operations/reconciler.go:185-189` @`34bc810`). Корень
  `notify-api` передаёт `OrphanGrace` явно постоянной `reconcileOrphanGrace` = 5 мин (§8), а не
  умолчанием corelib. Она строго больше верхней границы `…_HANDLING_BUDGET` (60 с, Р16): иначе сверщик
  разрешил бы ещё живой `RunSync`, чья `fn` идёт в пределах бюджета вызова. Держатель — заказ УК4-39.
  - Use-case `Delete` передаёт в `RunSync` контекст обработчика как есть — без
    `context.WithoutCancel` и без `context.Background()`. `RunSync` применяет контекст вызывающего
    напрямую (`operations/worker.go:657` @`34bc810`), а срок `HandlingBudget` ставит носитель
    `servicecontract` (`contract.go:657` @`34bc810`); отвязанный контекст оставил бы границу
    «`fn` идёт в пределах бюджета» без носителя (пересверка `1a5cf53f`, строка Д26 · 8 (2)).
    Держится вниманием рецензента: УК4-39 сравнивает постоянные, а не путь контекста.
- **Порт чтения обёрнут для барьера пробы** (CX4S-14 (д)). Чтение шага 1 идёт через порт
  `suppression.Reader`. Обёртка пробы NTF4-86 ставит барьер между чтением и снятием.
- **Запись аудита** — таблица `suppression_audit` в `kacho_notify`. Вывоз делает `audit.Shipper`
  corelib в поток записей службы. Колонки:
  - `event_type = 'suppression.delete'`;
  - `suppression_id`;
  - `operation_id` — операция снятия, её читает сверщик операций;
  - `actor` — субъект пересланного принципала;
  - `forwarder` — SAN пира, переславшего принципал;
  - `at`.

  Колонки актора и пересылающего разделены (CX4S-26). Адреса и отпечатка в строке нет (NTF4-33).
  Держатель колонки пира — заказ УК4-25: вызов через клиент П11 с SAN края → `forwarder` = SAN края.
- **Идентификаторы** — только `ids.NewID("nsp")` и `ids.NewID("nop")` (CX4S-27). Своего генератора
  и перечня префиксов нет. Префиксы — правка Х1. Держатели — DoD S1 п.4, `prefix_routing_test.go`.
- **Права — из аннотаций proto, одно место** (CX4S-32).
  - Аннотации `permission`, `required_relation`, `scope_extractor` на трёх методах (§5) — единственный
    источник имени разрешения и уровня.
  - Таблицу прав края порождает `gateway/scripts/gen-permission-catalog.sh` из proto, её держит
    `permission-catalog-check`.
  - Запись каталога kaname (Х2) копирует имя и уровень дословно. Каталог kaname генератор края не
    читает (М14), поэтому сверку делает команда, названная здесь и в DoD Х2: `jq -r '.[] | select(.name | startswith("notify.suppressions.")) | "\(.name) \(.relation)"' <kaname>/internal/apps/kaname/seed/embedded/permission_catalog.json | sort`
    против `grep -A2 'permission: "notify.suppressions' proto/kacho/cloud/notify/v1/*.proto`.
    Правка Х2 заводит эту сверку пробой kaname на пине kacho proto.
  - Расхождение закрыто отказом: `Check` по незнакомому разрешению даёт `PERMISSION_DENIED`, и
    матрица NTF4-24…27 краснеет.
  - Вопрос `Check` задаёт `notify-api` своей учёткой `kacho-notify-api` (CX4V-32). Матрица глагол ×
    роль та же, допуск учётки держат NTF4-120/121.

### З18. `notify-api`: корень, носитель Х5, самоотчёт, оси, миграции, порядок относительно NTF-3

- **Форма хоста — третье значение оси `HostForm`** замысла NTF-1 (З15 NTF-1).
  - `servicecontract.HostForm` получает `HostInternalOnly` с обязательной причиной:
    `Spec.HostFormReason string`, непустая при `HostInternalOnly`. Нулевое значение — `HostPair`
    (Х5, CX4S-29 (в)). Неизвестное значение и `HostInternalOnly` без причины — отказ конструктора.
  - Разбор оси — исчерпывающий `switch` без `default`.
  - Второго поля формы нет: зависимость Е1 замысла NTF-1 снимается этим решением.
- **Сборка сервера одного слушателя — одна функция** (CX4S-29 (а), (б), (д), (е); Х5).
  - `servicehost.buildServer(creds, listener)` — это нынешнее замыкание `build(creds, on)` из
    `serverPair` (`serve.go:204-212`), вынесенное в функцию. Пара зовёт её дважды, форма
    `HostInternalOnly` — один раз с `ListenerInternal`. Цепочки `unaryChain` и `streamChain` те же.
  - Выбор формы стоит в одном месте `Serve`. В форме `HostInternalOnly` публичный `*grpc.Server` не
    создаётся вовсе: проверок на `nil` публичного сервера в `handOut`, `servedOf` и `listenAndServe`
    не добавляется, потому что в этой ветке их вызывающий не существует.
  - `PublicAddr`, `PublicCreds`, публичный регистратор и публичная половина `Admission` при
    `HostInternalOnly` — отказ конструктора с именем поля.
  - Отказы старта О2–О11 судят служимый набор внутреннего сервера так же, как в паре.
  - Падение внутреннего слушателя в этой форме — ненулевой исход `Serve`, и процесс не завершается
    кодом 0 (CX4S-29 (г)).
  - Держатели — integration-проба Х5 в corelib и `TestBothListenersRefuseIdenticallyOnTheWire`,
    расширенная на форму с инъекцией «цепочка без звена прав» (DoD S3 п.8б).
- **Самоотчёт посадки** (CX4T-43, CX4V-29, CX4V-43).
  - `observability.BootPosture` получает поле формы слушателя `ListenerForm` (нуль — `pair`,
    `internal_only`) рядом с элементом `NoServedServices` NTF-1.
  - Ключ `listener_form` печатает `none` тогда и только тогда, когда запись несёт `NoServedServices`.
    Запись с `NoServedServices` и ненулевым `ListenerForm` конструктор записи отвергает.
  - Обе величины корень берёт **одной функцией corelib** `servicehost.PostureOf(d *Descriptor) (observability.ListenerForm, bool)`
    из того же значения дескриптора, которое передаётся в `servicehost.Serve`:
    `HostPair` → (`pair`, ложь), `HostNoGRPC` → (`pair`, истина), `HostInternalOnly` →
    (`internal_only`, ложь). Отсюда `none` у `notify-sender` приходит из `NoServedServices` той же
    записи, а не из его конфигурации (CX4V-43). Сочетание, которое конструктор отвергает, из
    дескриптора не выражается, а отказ конструктора — второй рубеж для прямой сборки записи (проба Х5).
  - Корень формы литералом не присваивает. Держатель — AST-предикат `bootpostureform_test.go` (УК4-26):
    полей `ListenerForm` и `NoServedServices` вне `servicehost.PostureOf` в не-тестовом дереве kacho
    нет.
  - Что значит «поднял» в момент строки: «принял дескриптор, который носитель исполнит». Строка
    пишется после `servicecontract.New` и до `Serve`, из дескриптора, переданного в `Serve`.
  - У NTF-1 (З15) самоотчёт печатал `HostForm` одним полем. Ключ формы остаётся один —
    `listener_form`, а `HostNoGRPC` печатается `none` (§13, Е2 — согласование с замыслом NTF-1).
- **Транспорт внутреннего слушателя** (CX4T-40). `notify-api` строит
  `grpcsrv.TLSServer{Enable: true, CertFile, KeyFile, ClientCAFiles}` в коде из трёх ручек.
  - `Enable` из окружения не читается, и ручки `…_ENABLE` в загрузчике нет (М8: нулевое `Enable`
    означает insecure).
  - Проверка границ файловых ручек зовёт `grpcsrv.TLSServerTransportCreds` и требует успеха — тот же
    разборщик, которым поднимается слушатель. Своего разбора PEM нет. Текст отказа называет ручку.
  - Файлы читаются один раз при старте, и продление сертификата действует только после перезапуска
    пода — так же, как у служб kacho. Образец — `kacho-geo`: `Certificate` cert-manager с
    `renewBefore` 720 ч (`charts/kacho-geo/templates/certificate.yaml:41`, `values.yaml:131`
    @`1d42a6728bf`, М21), перечитывания файлов и автоматического перезапуска нет. Запас `renewBefore`
    оставляет месяц на плановый перекат. Это же сказано в шапке `apiserver`.
- **Оси дескриптора** — по таблице Р20 (CX4V-35). `DBSSLMode` берётся из группы NTF-1 (н3), `Authz`,
  `CheckEdge` и `PeerCheck` — из (н4) и учётки `kacho-notify-api`.
- **Изъятия осей — с фактом в причине и с держателем** (CX4V-42, CX4T-42). Причины — дословно из
  таблицы Р20: «серверных стримов notify не служит»; «права на `Suppression` спрашиваются на объекте
  `cluster`, доставлять и гейтить нечего»; «пообъектно сужаемой списочной выдачи нет». Какой гейт
  покраснеет, когда зарегистрированный метод опровергнет факт:
  - `Narrowers` — `TestScopeFilteredRowsBelongToADomainThatEnforcesThem` (М12). Метод пакета
    `kacho.cloud.notify.v1` с `scope_filtered` при непровязанной карте notify даёт находку;
  - `HideExistence`, `Emits`, `Registers`, `Delivery`, `BootGate`, `StreamBudget` — гейта в дереве
    нет (М12). NTF-4 заводит его: проба `services/notify/cmd/notify-api/descriptor_exemptions_test.go`
    (УК4-27) строит дескриптор корня и для каждого изъятия проверяет его факт по регистрациям
    слушателя:
    - `HideExistence`, `Emits`, `Registers`, `Delivery`, `BootGate` — у всех методов
      зарегистрированных сервисов аннотация `scope_extractor.object_type = "cluster"`;
    - `StreamBudget` — ни одного серверного стрима в дескрипторах зарегистрированных сервисов.

    Метод, опровергающий факт, — находка с именем изъятия и метода. Инъекция — регистрация
    испытательного сервиса с методом на объекте не `cluster` → находка; близнец — дерево NTF-4, проба
    молчит и печатает число судимых методов.
- **Миграции** (CX4V-56, М4, М5). Решение — **мигрируют оба развёртывания, накат исключает сам себя и
  идемпотентен**.
  - У пода каждого развёртывания есть init-контейнер `migrate` — корень `services/notify/cmd/migrator`
    (NTF-1). Выкатка любого из двух развёртываний первой поэтому не оставляет второе на старой схеме.
  - Корень мигратора notify до `migratorrun.Runner.Up` берёт сессионный рекомендательный замок
    `pg_advisory_lock(hashtext('kacho_notify.migrate'))` на отдельном соединении с
    `lock_timeout = 5m` (постоянная кода) и отпускает его после `Up`.
  - Накат `goose` идемпотентен: применённая версия второй раз не применяется.
  - Замок заводится в корне notify, а не в `migratorrun`. Правка фундамента на все семь точек наката
    — отдельный предмет вне NTF-4. Параллельный накат реплик одного развёртывания в дереве сегодня
    тоже без замка (М4), и это названо в §12.
  - **`notify-api` сверяет схему при старте.** Функция `migrations.RequireApplied(ctx, pool)` для
    каждой версии, встроенной в бинарь (`migrations.FS`), спрашивает «применена ли» у
    `dropguard.GooseApplied` corelib — по последней строке версии в `goose_db_version`, а не по
    наличию любой строки с `is_applied` (CX4V-56, §11 строка Д26 · 3). Версия, встроенная и не применённая, — отказ старта с
    именем версии до подъёма слушателей. Рабочий запрос на отсутствующей таблице поэтому не падает.
    Держатель — заказ УК4-28: старт `notify-api` на схеме без таблиц NTF-4 → отказ с именем версии;
    близнец — схема после наката → готов.
  - **Цена названа.** У базы notify одна учётка (М5), так что процесс с входящей поверхностью держит
    права на изменение схемы, как любой процесс kacho сегодня. Раздельные роли базы по развёртыванию —
    предмет без механизма в дереве (М5); NTF-4 его не заводит (§12).
- **Порядок посадки относительно NTF-3** (CX4V-59). Порядок не закреплён: корень
  `cmd/notify-api` и развёртывание `notify-api` заводит та под-фаза, которая приходит первой (Р22).
  Кто второй, решает предикат в момент «перед стартом стадии S3»:
  `git -C kacho ls-tree origin/main services/notify/cmd/notify-api`. Его исход пишется в запись
  сверки стадии (§0а) полем `notify_api_root: present|absent`. Для обоих исходов назначено:
  - **NTF-4 первая.** S3 заводит корень, развёртывание, учётку, PDB, носитель Х5, загрузчик с
    (н1)–(н4) и 12 ручками NTF-4, строки закрытой записи З9 для двух регистраций NTF-4 с причиной и
    изъятия осей с держателем УК4-27. NTF-3 при посадке добавляет свои строки записи, свою часть ручек
    и пересматривает изъятия: её публичные сервисы опровергают факты «на объекте `cluster`» и «списка
    нет», и УК4-27 с `TestScopeFilteredRowsBelongToADomainThatEnforcesThem` краснеют, пока изъятия не
    сняты.
  - **NTF-3 первая.** S3 добавляет к существующему корню регистрации `InternalSuppressionService` и
    `OperationService` (если NTF-3 его не зарегистрировала), свои две строки записи З9 с причиной,
    свою часть ручек и строки таблицы осей. Изъятий, которые опровергает поверхность NTF-3, NTF-4 не
    вносит.

  В обоих случаях строки закрытой записи З9 — у каждой под-фазы свои, с причиной. Перечень ручек
  `notify-api` — объединение двух закрытых частей, и проба Р16 судит только часть NTF-4 и (н1)–(н4).
  Каждое изъятие оси сверяется с сервисами обеих под-фаз на ревизии посадки второй (держатель — УК4-27).
- **Регистрация сервисов** — только в `apiserver` (З1). Закрытая запись пробы З9 для `notify-api`
  несёт две строки NTF-4 с причиной и классом поверхности (З19).
- **Сверщик операций** — в корне `notify-api` (З17).
- **Реплики и PDB** — `replicas ≥ 2` и PDB `minAvailable ≥ 1` с селектором ровно своих подов (Р22,
  NTF4-118). Гейт `notify-availability-test.sh` судит оба развёртывания закрытым перечнем.

### З19. Край: одно соединение `notify`, маршруты, операции, признак поверхности

- **Соединение** — ключ `notify` в наборе соединений края, адрес — внутренний слушатель `notify-api`,
  mTLS края. Второго ключа нет (Д20 (3)).
- **Адрес без умолчания** (CX4S-24).
  - Ручки края — адрес `notify-api` и удостоверение mTLS к нему — объявляются парой. Половина пары в
    боевой посадке — отказ края в старте с именем ручки.
  - «notify в установке нет» — явное значение `KACHO_API_GATEWAY_NOTIFY=absent`. Его выводит один
    помощник зонтика `kacho.notify.present`, и тот же помощник решает рендер notify
    (`kacho.notifications.enabledFor` NTF-1 даёт перечень источников, а `present` = перечень непуст).
    Второго вывода признака нет.
  - Держатели — проба загрузчика края на три случая (DoD S3 п.8а) и заказ УК4-29: рендер-гейт
    «notify рендерится ⇔ край объявляет адрес» по всем профилям.
- **Регистрация на внутреннем mux** — `optsFor("notify")` в блоке `notifyInternalAddr`, только при
  объявленном notify (Р20).
- **Маршрут операций** — `prefixToBackend[ids.PrefixOperationNotify] = "notify"` (Х1).
- **Признак «только изнутри» объявлен одной декларацией рядом с соединением** (CX4S-25). Декларация
  соединения края несёт поле `InternalOnly: true` у записи `notify`. Перечень, который читает
  `resolveBackend`, выводится из этих деклараций, а не пишется вторым списком. Проверка
  `listenerorigin.IsExternal(ctx)` стоит до поиска соединения (Р20, NTF4-93).
  - Держатель — `internal_only_backend_test.go`. Заказ усиления (CX4S-25) исполнен этим решением:
    проба сверяет перечень с декларациями в обе стороны, а не по окончанию имени.
- **Отказ `Internal*` на внешнем gRPC-входе** держит звено отказа маршрута (NTF4-30, NTF4-112).
- **Признаки, которые не пускают `Internal*` notify наружу, — сколько их** (CX4V-51 (а)).
  - У прочих доменов признаков два:
    - имя — `HasInternalSuffix` в четырёх слоях края (М10);
    - построение — соединение `<домен>` ведёт на публичный слушатель, где сервисы `Internal*` не зарегистрированы.
  - У notify соединение одно, и ведёт оно на внутренний слушатель, где `InternalSuppressionService`
    зарегистрирован. Бэкенд признака происхождения не читает (М11). Значит, на пути запроса признак у
    notify один — имя.
- **Второй признак, не зависящий от имени, — способ (б)** (CX4V-51 (б)). Способ (а) — метка
  происхождения, которую край ставит, а `notify-api` читает от круга пересылающих, — отвергнут:
  он заводит новый проводной контракт края и второго носителя одного факта рядом с
  `listenerorigin`, а подменить имя сервиса можно только изменением дерева, и изменение дерева
  ловится до посадки. Механизм способа (б):
  - **Поверхность notify объявлена одним местом — закрытой записью пробы З9** (`services/notify/servesurface_ledger.go`,
    З15 NTF-1). Каждая строка регистрации `notify-api` несёт класс поверхности `public` или
    `internal`. Имя сервиса классом не служит. У двух строк NTF-4 класс `internal`, у строк NTF-3 — свои.
  - **Гейт** `internal/repohygiene/notifysurfaceparity_test.go` сверяет перечень публичных методов
    края для пакета `kacho.cloud.notify.v1` (`allowlist.AllowedMethods`) с методами строк `public`
    записи. Сверка в обе стороны, без `HasInternalSuffix`.
  - Дополнительно гейт утверждает: имя каждого сервиса строки `internal` начинается с `Internal`, а
    имя сервиса строки `public` — нет. Так имя и объявление держат друг друга.
  - **Инъекция** (CX4V-51 (в)): внутренний сервис пакета notify без `Internal` в имени,
    зарегистрированный на `notify-api` и записанный строкой `internal`. Существующая сверка края с
    дескрипторами (`parity_test.go`) требует метод в перечне, потому что имя без `Internal`. Если он
    в перечне — этот гейт красный: метод не `public`. Если его там нет — красный `parity_test.go`.
    Зелёного исхода у инъекции нет. **Близнец** — тот же сервис с `Internal` в имени: оба гейта молчат.
  - Итог по счёту: на пути запроса у notify один признак, как и прежде. Второй — объявление в дереве,
    которое судится в CI до посадки. Названный остаток: ошибка имени, прошедшая одновременно запись
    З9 с классом `public` и перечень края, — это правка двух объявлений, видимая в одном изменении
    ревью.
- **На ребре край→notify нет вызова отправки** (CX4V-50, CX4U-50 (а)). Множество методов, которые
  край маршрутизирует в notify, — это внутренний mux, перечень внешнего входа по пакету notify и
  `prefixToBackend`. Гейт `notifysurfaceparity_test.go` утверждает, что оно — подмножество методов
  регистраций закрытой записи `notify-api`, где глагола отправки нет. Инъекция — маршрут края на
  `InternalNotifyProbeService/Send` (корень `notify-probe`, не `notify-api`) → находка «метод вне
  записи `notify-api`». Так красное строки `poly-edge-gateway-notify` («маршрут края ведёт в процесс,
  держащий секрет почты») заменяют три свойства с признаками:
  - `notify-api` объекта секрета почты не монтирует — NTF4-117 (2);
  - публичного слушателя у notify нет — NTF4-108, форма `internal_only`;
  - край маршрутизирует в notify только методы записи `notify-api` — этот гейт.

  Строка правила с этим согласна (DoD S3 п.9, запись `cb947e50`, CX4V-48).

### З20. Гейт посадки: развёртывание против службы, подперечень

- **Правило гейта по счёту строк, а не по литералу** (CX4V-61). `assert-production-posture.sh`
  считает строки таблицы служб на службу (`declare -A rows_of; rows_of[$svc]++`) до обходов.
  - Служба с числом строк больше 1 судится по развёртыванию (первый столбец) в обоих перечнях,
    сравниваемых с `$svc` (`FORWARDER_NARROWING_REQUIRED`, `POSTURE_SKIP`).
  - Голое имя такой службы в любом из перечней — находка с именем перечня, элемента и всех
    развёртываний службы. Ни одна строка по нему не пропускается.
  - Литерала `notify` в правиле нет. Следующая служба с двумя развёртываниями судится так же без правки.
  - Держатель — NTF4-109 (и)–(м) с близнецами. Заказ УК4-30 — вариант со второй испытательной службой
    из двух строк без `notify` в имени: тот же исход.
- **Подперечень развёртываний без публичного слушателя** (CX4T-44, CX4V-44):
  - (а) до обходов гейт проверяет, что каждая запись подперечня — развёртывание таблицы служб.
    Запись без строки таблицы — находка с именем записи. Это пятый вариант NTF4-109 (УК4-31);
  - (б) `POSTURE_SKIP` исключает развёртывание из обоих перечней одинаково, и строка печатается
    «исключена»;
  - (в) записи подперечня адресуют развёртывание — первый столбец таблицы служб.
- **Форма** судится по Р20: `pair` или нет ключа → `public_mtls = true`; `internal_only` → запись в
  подперечне с этой формой, `public_mtls = false`, `internal_mtls = true`; `none` → запись в
  подперечне с этой формой и `NoServedServices` истинен; иное значение — находка.

### З21. Чарт notify: два развёртывания, два объекта, учётки, стенд

- **Развёртывания** — `deploy/helm/notify/templates/deployment-sender.yaml` (NTF-1, правится) и
  `deployment-api.yaml` (NTF-4 либо NTF-3 — З18). У обоих:
  - стратегия `RollingUpdate`, `maxUnavailable: 0`, `maxSurge: 1`;
  - проба готовности `/readyz`;
  - init-контейнер `migrate` (З18). Одобрение сноса стражу сноса приходит ключом values
    `migrator.dropApproved` (строка, по умолчанию пустая; Д28, строка Д26 · 4 (3)). Непустое
    значение рендерится дословно в `env` контейнера `migrate` каждого развёртывания чарта под
    именем `MIGRATOR_DROP_APPROVED` — постоянная `dropguard.ApprovalEnv` corelib, прежнее написание
    с приставкой платформы чарт не рендерит. Пустой или незаданный ключ — переменной у контейнера
    нет вовсе, а не переменная с пустым значением. Серверные контейнеры переменную не получают.
    Формат значения чарт не проверяет: его единственный разборщик — страж (`ParseApprovals`),
    нечитаемое значение он отвергает отказом наката. Держатель — УК4-36;
  - `replicas ≥ 2` и свой PDB.
- **Объекты секрета** (Д23, Р11, Р15).
  - Секрет почты — том целиком только у `notify-sender`. Путь — ручка NTF-1.
  - Объект ключа отпечатка (`<установка>-recipient-key`, З2) — том целиком у обоих, путь
    `/etc/kacho/notify/address-key`, и `KACHO_NOTIFY_ADDRESS_KEY_DIR` равна этому пути у каждого
    развёртывания.

    `checksum/recipient-key` нет (З2).
- **Учётки** — `kacho-notify` (декларация `notify.spiffe`, NTF-1) и `kacho-notify-api` (декларация
  `notifyApi.spiffe: {trustDomain, namespace, saName: kacho-notify-api}` в зонтике). Читатели
  `notifyApi.spiffe` — выпуск серверного и клиентского сертификатов `notify-api` и учётка
  развёртывания. Перечень источников notify и таблица звена идентичности kaname её не читают

  `notify-sender` — полный URI из `notify.spiffe`. Случай «равен ключу по началу, но длиннее» — ровно
  пара `kacho-notify` / `kacho-notify-api`, и его держит NTF1-M03 закреплённой редакции (равенство
  полного URI). NTF-4 опирается на это свойство, своего разбора SAN не заводит. В чарте `notify-api`
  не попадает ни в перечень источников, ни в таблицу звена идентичности (NTF4-117 (7), (8)).
- **Окружение `notify-api`** — ровно (н1)–(н4) NTF-1 и 12 ручек NTF-4 (NTF4-117 (9)).
- **Рендер-гейт** `deploy/tests/helm/notify-rollout-and-secret-mount-test.sh` — случаи (1)–(9)
  NTF4-117, три прежние инъекции DoD S6 п.2 и пустой рендер. Разбор — `yq` по отрендеренным
  объектам, печать числа объектов и профилей. Гейт NTF-1 D1 (`deploy/notify_secret_layout_test.go`)
  переписывается на ту же форму (З2). Утверждения о раскладке остаются у D1 — «отдельный объект,
  не поле секрета почты, постоянное имя», утверждения о форме монтирования — у нового гейта. Одного
  утверждения в двух гейтах нет.
- **Стенд** (П1) — только в профилях стенда:
  - приёмник ящика обратной связи — второй экземпляр приёмника стенда NTF-1 с POP3 поверх неявного
    TLS, сертификат от УЦ стенда, приём любой локальной части;
  - пересылка исходящего приёмника на домен возврата — по настроенному узлу и совпадению домена
    получателя;
  - зона DNS — экземпляр CoreDNS с плагином `file` для зоны стенда и `forward` для прочих имён;

  этот пункт в замысел, а не выбирает замену сама. Держатели — DoD S1 п.6 и NTF4-52 (нет в
  `values.prod.yaml`).

### З22. Ручки: одно объявление, два загрузчика, зависимые границы

- **Объявление ручек — одно значение в дереве** (CX4V-58). `services/notify/internal/config/knobs.go`
  объявляет таблицу `[]Knob{Name, Group, Stage, Bound}`.
  - `Group` — одно из закрытых значений `GroupNTF1Posture` (н1), `GroupNTF1Diag` (н2),
    `GroupNTF1DB` (н3), `GroupNTF1Kaname` (н4), `GroupNTF1Other`, `GroupNTF4`. Идентификаторы
    латиницей (ban #17), обозначения (н1)–(н4) — только в тексте.
  - Ручки NTF-1 объявляет NTF-1 (тег группы NTF-4 добавляет своей правкой — это классификация, а не
    второе объявление).
  - Загрузчик `notify-sender` объявляет все ручки групп NTF-1 и 21 ручку `GroupNTF4` стадии S1.
  - Загрузчик `notify-api` выбирает ручки NTF-1 по четырём тегам (н1)–(н4), а ручки NTF-4 — по
    закрытому перечню из 12 постоянных пакета. Имя вне объявления — ошибка сборки: постоянная не
    существует. Копии имени или границы в загрузчике `notify-api` нет: границы берутся из того же `Knob`.
- **Держатель Р16** — `required_knobs_test.go` (CX4S-23, CX4V-23):
  - вызовы чтения окружения судятся по идентичности (`os.Getenv`, `os.LookupEnv`, `os.Environ`,
    провайдеры окружения) во всём `services/notify`, кроме загрузчика;
  - проба печатает объём осмотренного и падает на пустом обходе;
  - две группы — две декларации, пересечение пусто, объединение сверено с загрузчиком каждого развёртывания;
  - 31 ручка NTF-4 по двум загрузчикам (Р16 после Д96; две ручки DNS объявляет NTF-1, Р19 NTF-1);
  - девять инъекций Р16; девятая — снятая граница окна долей и срока журнала (редакция 22
    приёмки, CX4V-65).
- **Зависимые границы — одной функцией после разбора обеих групп** (CX4T-41). Функция
  `config.checkCrossBounds(ntf1 NTF1Values, ntf4 NTF4Values) error` зовётся после разбора обеих групп
  и читает ручку NTF-1 (порт диагностического слушателя) из разобранной структуры NTF-1, а не из

  контрольного письма и пара «окно долей — срок журнала» (`…_REPUTATION_WINDOW ≤ …_SENT_LOG_RETENTION`,

- **Молчаливых умолчаний нет** (`sec-no-silent-default-for-guarded-knob`). Незаданная ручка — отказ с
  именем. Значение вне границы — отказ с именем и границей, значение секрета не печатается.

### З23. Время: одни часы процесса

- **Предикаты времени в SQL notify получают «сейчас» параметром** (CX4S-12, Р3). `now()`,
  `CURRENT_TIMESTAMP`, `clock_timestamp()` в SQL и миграциях `services/notify` не встречаются, в том
  числе в умолчаниях колонок: `created_at` и подобные пишутся параметром. Держатель — DoD S1 п.2 и
  однофайловый предикат `sqlnow_test.go` (УК4-33) по литералам SQL и файлам миграций.
- **Таймеры и тикеры — у внедрённых часов** notify. Порт часов заводит NTF-1 («внедряемые часы», З21
  NTF-1). NTF-4 им пользуется, второго порта не заводит: подметальщик, такт опроса, продление аренды,
  перечитывание, перепроверка DNS, повтор DNS при старте, срок журнала. `time.NewTicker`,
  `time.After`, `time.Sleep` в не-тестовых пакетах NTF-4 — находка того же предиката.
- **Монотонные и стенные часы.** Моменты для SQL — стенное время часов процесса в UTC. Длительности
  внутри процесса (срок сеанса, дедлайны) — монотонные, по правилу З21 NTF-1.
- **Сетевые сроки — реальное время** (К1, М3 ревью замысла `80dea362`). Срок операции POP3
  (`conn.SetDeadline`), попытки контрольного письма и запроса DNS (`context.WithTimeout`) считает
  сетевой стек по монотонному времени, а не внедрённые часы: это граница ожидания чужого сервера, а не
  решение по времени. Вызовов `time.NewTicker`, `time.After`, `time.Sleep` они не требуют, и
  предикат УК4-33 их не касается. Пробы, которые двигают управляемые часы (NTF4-104), этих сроков
  не задевают.

## 7. Последовательности

1. **Письмо.** `Claim` NTF-1 → `Decide` (клетки 1–6, **6а — подавление**, 7–9) → при `StepSend` —
   запись `sent_log`, адрес возврата `b` (и `u` у `notice`) → рендер → подпись DKIM → SMTP → `250` на
   `DATA` → отметка `accepted_at` → `Ack SENT`. При `StepAck(SUPPRESSED)` — `Ack` без сессии, исход
   записан в запись обработки.
2. **Синхронный отказ `RCPT`.** 5xx → `feedback.Classify(sync)` → при `hard` транзакция `Apply` и
   `feedback_event` → `Ack RECIPIENT_REJECTED`.
3. **Ящик.** Такт держателя → продление → вход по слотам → `STAT`/`UIDL` → на сообщение: `RETR` →
   дайджест → транзакция (продление, `feedback_message`, эффекты, метка опроса) → `DELE` → `QUIT`.
   Параллельно — независимое продление. Сеанс исполняет горутина держателя, такт её не ждёт;
   каждая сетевая операция — под сроком `pop3.opTimeout` (З7, З11).
4. **Контрольное письмо.** Такт → `$now ≥ база + I` → номер под арендой → `canary.Send` → `250` →
   отметка «ожидаемый». Прочтение — сообщение `canary` → `applied` и `feedback_route` 1→0.
5. **Признаки.** Такт держателя → доли, `feedback_stale`, `feedback_route` → условные переходы → WARN
   у выигравшего. Не-держатели читают строки каждым тактом.
6. **Перечитывание.** Такт `SECRET_RELOAD_INTERVAL` → поколение → дайджест → проверка → подмена
   указателя или исход `rejected`/`deferred`.
7. **Старт `notify-sender`.** Загрузчик → миграции (init-контейнер с замком) → `Establish` (З3) →
   проверки DNS до `BOOT_DEADLINE` → `/readyz` → цикл `Claim` и такт аренды.
8. **Старт `notify-api`.** Загрузчик → миграции (init-контейнер с замком) → `RequireApplied` →
   `Establish` → `servicecontract.New` (Х5) → самоотчёт из `PostureOf` → `servicehost.Serve`.
9. **Снятие.** Край (внутренний слушатель) → `notify-api`: звено прав → формат → чтение → операция →
   `RunSync` (снятие и аудит одной транзакцией) → `Operation`. Опрос операции — через край,
   `prefixToBackend[nop]`.

## 10. План перехода

Прода нет (Д12). Порядок:

1. Х1 → S1 → Х3, Х4 → S2 → Х2, Х5 → S3 → S5, S6, S7. S5–S7 после S3 идут параллельно, их общие пути
   названы в `tasks.md`.
2. **S1 несёт замещение ключа сетки** (З2):
   - объект ключа — том целиком у `notify-sender`;
   - `Establish`;
   - таблица `address_key_check` и следом `DROP TABLE recipient_key_fence` с записью сноса в
     `dropguard.json` notify и её производителем (CX4V-63);
   - одобрение сноса `MIGRATOR_DROP_APPROVED` до выкатки на каждой установке, где стартовала
     NTF-1 (в ограде строка). На свежей базе оно не нужно (З2, §11 CX4V-63). Значение ставится
     ключом values `migrator.dropApproved` чарта notify, который рендерит его в env
     init-контейнера `migrate` обоих развёртываний (З21, Д28; Е7 снята), и снимается тем же ключом
     после применения;
   - снятие ограды и аннотации;
   - правка гейта D1 NTF-1.

   Окно переката названо в З2.
3. **S3 заводит или дополняет `notify-api`** по предикату З18.
4. Откат. До S1 — прежние образы и чарт. После `DROP TABLE` ограды откат S1 прежними образами
   невозможен: старт NTF-1 пишет строку в ограду, которой уже нет, и отказывает в старте. Откат
   S1 — это новая миграция, которая заводит ограду заново, и несёт её образ новее S1, а не
   прежний. В ограде была строка, и страж сноса её считает (З2, CX4V-63). Эта строка — отпечаток
   ключа сетки, а не данные арендатора: её значение выводится из ключа, и код, который оградой
   пользуется, пишет её при старте. Поэтому одобренный снос не теряет ничего, что нельзя вывести
   заново.

## 12. Что замысел не делает

- Не меняет наблюдаемого поведения приёмки. Где механизм мог бы выбрать исход, выбор назван
  ссылкой на сценарий.
- Не ротирует ключ отпечатка и не меняет профиль нормализации (Р11, §9 приёмки).
- Не заводит раздельных ролей базы по развёртыванию: механизма в дереве нет (М5). Процесс
  `notify-api` держит права учётки базы notify, как любой процесс kacho. Предикат снятия остатка:
  в дереве появился механизм ролей базы по развёртыванию (`git grep -c 'CREATE ROLE' -- deploy` > 0) —
  тогда `notify-api` получает роль без прав на схему, а мигрирует только `notify-sender`.
- Не ставит замок в общий `migratorrun`. Параллельный накат реплик одного развёртывания в дереве
  идёт без замка (М4) — это вопрос всех семи точек наката, а не NTF-4.
- Не заводит метки происхождения на проводе края (способ (а) CX4V-51 отвергнут, З19).
- Не переносит аренду в corelib (З11).
- Не заводит входящей HTTP-поверхности, отписки в один щелчок и приостановки шаблона (§9 приёмки).
- Не правит `.claude/rules/` и спека-книгу. Задача владельцу спека-книги — DoD S7 п.4, её ставит
  диспетчер.
