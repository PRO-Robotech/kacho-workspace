# 08. Реализация в Kubernetes

Что именно создаётся в кластере, из чего это выводится, что считается успешной выкаткой и
как флот обслуживается. Клиент ничего из этого не видит и не может назвать в API.

---

## 1. Единица размещения

Пространство имён — на пару **(приложение, окружение)**, имя выводится из идентификаторов,
не из имён: переименование приложения не должно двигать пространство имён.

Не на приложение: иначе шумный непрод ест квоту production и делит с ним сетевую политику.

---

## 2. Объекты пространства имён

Создаются один раз при создании окружения.

| Объект | Существенное |
|---|---|
| Метки принадлежности | Аккаунт, проект, приложение, окружение. Единственный источник арендной принадлежности для метрик, журналов и учёта потребления |
| Профиль безопасности подов | `baseline` плюс собственный жёсткий набор по умолчанию, см. §6 |
| Квота ресурсов | Потолок окружения: процессор и память по запросам и лимитам, число подов и сервисов. Балансировщиков и постоянных томов — ноль |
| Диапазон лимитов | Значения по умолчанию и максимумы на контейнер |
| Сетевая политика | Запрет по умолчанию на вход и выход. Разрешено: вход со шлюза, DNS, выход через шлюз исходящего трафика, точечные правила привязок |
| Политика взаимной аутентификации сетки | Строгий режим |
| Политика авторизации сетки | Только со шлюза и внутри своего пространства имён |
| Ограничение области конфигурации прокси | Без него каждый прокси получает эндпоинты всего кластера: на масштабе это память и время сходимости |
| Класс приоритета | По уровню окружения: production вытесняет непрод, не наоборот |
| Служебная учётная запись | Своя, без автоматического монтирования токена |

**Запас квоты обязателен.** Квота окружения выставляется не «в потолок тарифа», а с запасом
как минимум на одну реплику самого крупного компонента. Иначе скользящее обновление не может
создать дополнительный под, раскат стоит до предельного срока и уезжает в отказ — причём
отказ релиза, которого клиент не запускал, если перекат инициирован платформой.

## 3. Объекты компонента

| Объект | Для каких типов | Существенное |
|---|---|---|
| Рабочая нагрузка | все | Образ **строго по digest**; своя служебная учётная запись; пространства имён пользователей; жёсткий контекст безопасности; ресурсы из размера; распределение по узлам; предельный срок раската; аннотация с **хешем конфигурации** |
| Разовое задание команды релиза | все, где задана `release_command` | Тот же образ по digest, те же переменные и секреты, тот же контекст безопасности; **свой предельный срок**, отдельный от предельного срока раската; без сервиса, маршрута и проб; выполняется до создания новой рабочей нагрузки |
| Сервис | `WEB`, `STATIC` | |
| Источник несекретных переменных | все | |
| Источник секретов | все | Материализуется оператором внешних секретов из хранилища |
| Автомасштабирование | все, если задан верхний предел | Метрика — **по контейнеру приложения**, не по поду |
| Бюджет прерывания | все | Всегда, в форме «не более одного недоступного» |
| Маршрут | `WEB`, `STATIC` | Стандартный ресурс маршрутизации; сетка — реализация шлюза |
| Съём метрик | все | |
| Сертификат | `WEB`, `STATIC` с пользовательским доменом | Технический адрес покрыт групповым сертификатом |

### 3.1 Про хеш конфигурации

Аннотация с хешем конфигурации в шаблоне пода **обязательна для каждого компонента**. Без
неё правка конфигурации не меняет шаблон пода, под не перекатывается, процесс продолжает
жить со старым окружением — а система при этом рапортует успех. Этот класс дефекта у нас уже
был, и проверка посадки его не поймала, потому что читала конфигурацию, а не живой процесс.

### 3.2 Статический компонент

Рендерится как обычная веб-нагрузка, но образ подаёт платформа: результат сборки —
содержимое каталога вывода, которое кладётся в образ раздачи вместе с настройкой
запасного пути для одностраничных приложений. Отдельного рантайма не заводится.

### 3.3 Фоновый обработчик

Тот же рендер минус сервис, минус маршрут, минус HTTP-проба. Готовность определяется
фактом запуска и отсутствием перезапусков, а не ответом на пробу.

### 3.4 Команда релиза

`release_command` компонента (переопределяемая на окружении через `release_command_override`)
рендерится в **разовое задание**: один запуск на релиз, **до переключения трафика**, на том
же образе по digest и с той же конфигурацией — переменные и секреты приходят из тех же
источников, что и у рабочей нагрузки. Это место для миграций схемы: они выполняются один раз,
а не в каждой реплике при старте.

Задание не получает ни сервиса, ни маршрута, ни проб — его наблюдаемый исход один: код
возврата. Предельный срок у задания **свой**: миграция идёт минуты там, где раскат
укладывается в секунды, и общий срок означал бы либо преждевременный отказ, либо ожидание
без границы.

Состояние релиза на время выполнения — `RELEASING`, порядок `QUEUED` → `RELEASING` →
`DEPLOYING` → `ACTIVE`. Отказ задания заканчивает релиз кодом `RELEASE_COMMAND_FAILED`,
истечение срока — `RELEASE_COMMAND_TIMEOUT`; в обоих случаях новая рабочая нагрузка не
создаётся, **предыдущий релиз не трогается и трафик не переключается**. Журнал задания
адресуется отдельно (`release_log_ref`) — разбор упавшей миграции не должен смешиваться с
журналом приложения.

Задание выполняется на **каждом** релизе, включая продвижение между окружениями и откат:
образ тот же, а состояние базы у целевого окружения своё, и пропуск команды на откате оставил
бы схему впереди кода. Идемпотентность команды — на стороне клиента. Для типов `WORKER` и
`STATIC` команда релиза допустима, но по умолчанию пуста.

## 4. Маршрутизация

Контракт — стандартный ресурс маршрутизации (Gateway API), реализация — сетка. Стандартный
контракт развязывает продукт от вендора сетки и от версии её собственных ресурсов.

**Технический адрес.** Зона — отдельный домен второго уровня, **не** поддомен корпоративной
зоны и не зона, где живут cookie основного сайта; заявка в список публичных суффиксов
подаётся немедленно, это внешний процесс на недели. Имя выводится из неизменяемой метки
окружения; освобождённые имена держатся в карантине.

**Публикация — записью на приложение**, указывающей на адрес шарда, а не одной записью зоны.
Групповой сертификат при этом сохраняется — он с записью на приложение совместим. Без записи
на приложение разнести приложения по нескольким шлюзам позже нельзя, не сменив уже выданные
адреса.

## 5. Режим сетки — решение, а не умолчание

Режимов два: с прокси в каждом поде и **без прокси в поде**. Это первичное решение, а не
деталь установки: на малых размерах прокси сопоставим с самим приложением, то есть половина
проданной памяти уходит на инфраструктуру, а плотность узлов вдвое ниже расчётной.

**Предпочтительный режим — без прокси в поде.** Всё, что мы просим от сетки — взаимная
аутентификация, авторизация по источнику, метрики ребра — закрывается им; за прокси в поде
остаётся то, чего мы не заказывали, и цена в каждом поде каждого клиента.

**Окончательный выбор — по стендовой проверке, до этапа Э4.** Проверяется не документация
вендора, а связка на **целевой версии** кластера: режим без прокси совместно с
пространствами имён пользователей (§6) и с Gateway API как контрактом маршрутизации (§4).
Отрицательный результат означает возврат к прокси в поде — и тогда обязательна **явная
строка размера** на прокси, а не растворение его в себестоимости.

Строки бюджета, которые остаются в силе при любом исходе:

| Что учитываем | Почему |
|---|---|
| Память и процессор прокси — отдельная строка размера (режим с прокси) | На малых размерах прокси сопоставим с самим приложением: плотность узлов вдвое ниже расчётной |
| Ответ на вопрос «чья это квота» | Либо клиентская квота, либо себестоимость. Умолчания быть не может: это первичное решение хостера |
| Готовность к приёму трафика — отдельная строка бюджета времени | «Под запущен» ≠ «конфигурация сетки доехала»; между этим есть секунды в любом режиме |
| Нативный порядок запуска (режим с прокси) | Иначе приложение стартует раньше прокси и первые соединения падают |
| Автомасштабирование считает по контейнеру приложения | Иначе порог в тарифе означает не то, что написано |

**Замер памяти пода на малом размере обязателен до публикации тарифа** — в том режиме,
который выбран проверкой. Тариф, посчитанный до замера, придётся пересматривать уже по
выданным клиентам.

## 6. Изоляция подов

| Контроль | Значение |
|---|---|
| Пространства имён пользователей | Включены. Root в контейнере отображается на непривилегированный идентификатор на узле |
| Повышение привилегий | Запрещено |
| Возможности процесса | Сброшены все |
| Профиль системных вызовов | По умолчанию среды выполнения |
| Файловая система корня | Только на чтение там, где приложение это переносит |
| Хостовые пространства и пути | Запрещены полностью |

**Пространства имён пользователей решают задачу эскалации, а не сокращения поверхности
системных вызовов.** Побег через уязвимость ядра остаётся межарендной компрометацией. Это
записано как осознанный размен, а не как эквивалентная замена песочнице.

**Предусловия** (проверяются на каждом кластере, см. `06` §5): ядро не ниже 6.3, containerd
не ниже 2.0, `runc` не ниже 1.2 либо `crun` не ниже 1.9, файловая система под каталогом
подов поддерживает отображение идентификаторов, Kubernetes с включённой поддержкой.
Тенантский пул **однороден** по всем параметрам.

При невыполнении предусловий — откат на профиль с обязательным запуском не от root и
**явная диагностическая ошибка** для образов от root. Молчаливого понижения безопасности не
происходит никогда.

## 7. Пулы узлов

| Пул | Назначение | Особенности |
|---|---|---|
| Тенантский рантайм | Приложения клиентов | Отдельный, с меткой недопуска, однородный по возможностям |
| Сборка | Только сборка | Отдельный: там выполняется произвольный код клиента |
| Платформенный | Наши контроллеры | Клиентские нагрузки не допускаются |

**Тёплый запас ёмкости** — явный параметр эксплуатации, а не побочный эффект. Автоскейлер
поднимает узел минутами, что не укладывается в целевые показатели; запас держится подами
низкого приоритета, вытесняемыми настоящей нагрузкой. Размер запаса и его стоимость —
статья себестоимости, а не «как-нибудь получится».

**Реестр — зависимость пути запуска, а не хранилище.** Каждый старт пода тянет образ, поэтому
реестр записывается в зависимости пути запуска с **собственным показателем доступности не ниже
показателя доступности входа платформы**. Обязательны:

| Мера | Что закрывает |
|---|---|
| Зеркало или сквозной кэш реестра **на кластер** | Веер обращений при штатных событиях — обновление узла, замена узла, рост автомасштабирования — не выходит за пределы кластера |
| Предзагрузка типовых базовых образов на узлы тенантского пула | Первый старт на свежем узле не упирается в полную выкачку слоёв; попадание в кэш перестаёт зависеть от того, кто стартовал раньше |

Без этого источником отказов становится наш собственный регламент безопасности: обновление
узлов — штатное и частое событие, и именно оно даёт веер.

## 8. Что считается успешной выкаткой

По условиям кластера, не по таймеру:

1. **команда релиза завершилась успешно** — задание отработало с нулевым кодом возврата в
   пределах своего срока (если `release_command` пуста, условие выполнено тривиально);
2. контроллер увидел нашу ревизию;
3. нужное число реплик доступно;
4. раскат в состоянии «новый набор доступен»;
5. эндпоинты опубликованы;
6. **конфигурация сетки доехала** и проба отвечает;
7. для веб- и статических компонентов маршрут принят шлюзом;
8. для пользовательского домена сертификат готов.

Порядок здесь существенный: первое условие проверяется **до** создания новой рабочей
нагрузки, поэтому его невыполнение (`RELEASE_COMMAND_FAILED`, `RELEASE_COMMAND_TIMEOUT`)
заканчивает релиз, не тронув предыдущий и не переключив трафик.

Истечение предельного срока раската переводит релиз в отказ с указанием, сколько реплик
поднялось. Ожидание не длится вечно.

## 9. Обслуживание флота

| Событие | Правило |
|---|---|
| Обновление узла | Бюджет прерывания создаётся всегда в форме «не более одного недоступного». Наивная форма «хотя бы один доступный» на одной реплике заблокировала бы вытеснение навсегда |
| Дренаж узлов | **Ограничение скорости — сколько узлов дренируется одновременно** — явный параметр эксплуатации. Без него штатное обслуживание превращается в веер обращений к реестру и всплеск планирования; при неудачном совпадении с автомасштабированием это отказ старта, а не замедление |
| Зависшее вытеснение | Предельный срок ожидания и явное поведение по его истечении: принудительное вытеснение с записью события в историю приложения |
| Отсрочка завершения | Достаточная для дренажа эндпоинтов; иначе соединения в полёте получают отказ |
| Обновление версии рендера | Не автоматически. Ближайший естественный релиз либо управляемая миграция с ограничением скорости, сначала непрод |
| Обновление базового слоя бэкпаков | Пересборка инициируется платформой, помечается инициатором, **не расходует квоту клиента**, в production применяется по согласию |
| Обновление базового слоя для `Dockerfile` | Платформа его не меняет — базовый слой принадлежит клиенту; платформа сигнализирует об устаревании |

Обновление кластера, которое может быть заблокировано клиентской нагрузкой, — это
неприменённое исправление безопасности. Предельный срок вытеснения обязателен.

### 9.1 Обслуживание платформенных компонентов

Флот состоит не только из клиентских подов. Главный вопрос по каждому компоненту один и тот
же: **требует ли его обновление перезапуска пода клиента**.

| Компонент | Что делает обновление | Требует перезапуска пода клиента |
|---|---|---|
| Сетка | В режиме без прокси обновляются узловой и внеподовый компоненты; в режиме с прокси — версия прокси **в каждом поде** | Без прокси — **нет**; с прокси — **да**, веерный перекат всего флота. Это отдельный довод в пользу режима §5 |
| Шлюз | Контроллер и точка входа | Нет. На время переката — просадка входа, покрывается несколькими экземплярами и дренажем соединений |
| Оператор внешних секретов | Контроллер материализации | Нет. Уже материализованные секреты живут; задерживается только подхват изменений и ротация |
| Менеджер сертификатов | Контроллер выпуска | Нет. Задерживаются выпуск и продление; заранее продлённый сертификат снимает срочность |
| Наш оператор | Контроллер намерения | Нет. Тянущая доставка догоняет после старта, релизы в это время стоят в очереди, а не отказывают |
| Версия Kubernetes | Плоскость управления, затем узлы | **Да** на шаге узлов — через дренаж по правилам выше, с ограничением скорости |

**Любой веерный перекат флота идёт по дисциплине миграции версии рендера**: ограничение
скорости, сначала непрод, возможность остановки на любом шаге. Причина обновления роли не
играет — обновление, которое трогает шаблон пода каждого клиента, это релиз, которого клиент
не запускал, и правило для него одно.

Дежурному нужен отдельный сигнал **«идёт веерная миграция: доля флота»**. Без него всплеск
перезапусков и просадка показателей читаются как авария продукта, и разбор уходит в сторону.

## 10. Бюджет пространств имён на кластер

Первой ломается не база состояния кластера, а память контроллеров и всплеск запросов при их
перезапуске: оператор, оператор секретов, менеджер сертификатов, контроллер шлюза, управление
сеткой.

Порог заводится **явным параметром эксплуатации**, измеренным холодным стартом всех
перечисленных контроллеров на заполненном кластере. Кластер присутствует в модели с самого
начала (`02` §9): добавить шардирование позже — это миграция схемы и смена уже выданных
адресов.
