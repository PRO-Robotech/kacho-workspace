# 03. Публичный API: структуры методов

Что принимает и возвращает каждый метод, кто вправе его вызвать, синхронный он или нет,
какие ошибки объявлены. Правила валидации отдельных полей — в `04`.

---

## 1. Общие принципы

| Аспект | Правило |
|---|---|
| Точка входа | `https://api.beget.com`. Отдельного публичного эндпоинта у платформы нет |
| Аутентификация | Bearer JWT существующей авторизации Beget. Анонимный доступ отсутствует везде |
| Авторизация | Каждый метод проверяет доступ к проекту и к конкретному ресурсу. Недоступный ресурс отвечает как несуществующий: различимый ответ был бы оракулом существования |
| Формат | JSON, `snake_case`, идентификаторы UUID v4, время RFC 3339 |
| Чтение | Синхронно, возвращает ресурс |
| Мутации | **Асинхронно**: возвращают `Accepted { resource, operation }` и создают `Operation` |
| Списки | `offset`, `limit`, `filter`, `sort` — семантика существующего Cloud API |
| Идемпотентность | Заголовок `Idempotency-Key` **обязателен** для создания релиза, сборки, привязки и домена; необязателен для остальных мутаций. Срок жизни ключа — 24 часа. Повтор возвращает ту же операцию, а не создаёт вторую |
| Окружение | `environment_id` — **всегда необязательный** параметр; отсутствует → окружение приложения по умолчанию. Обязательным не станет никогда: иначе включение мультиокружений было бы ломающим изменением |
| Ошибки | Уточнённый код продукта плюс безопасное сообщение; сообщения — часть контракта, меняются осознанно (`04` §7) |

**`Operation` не является источником истины ресурса.** После завершения состояние читается
из ресурса, а не из операции.

### 2.5 Интеграция с Git-провайдером

| Метод | Путь | А | И |
|---|---|---|---|
| `GitIntegrationService.getList` | `GET /v1/cloud/application/git-integration` | | |
| `GitIntegrationService.createInstallUrl` | `POST …/git-integration/install-url` | | |
| `GitIntegrationService.get` | `GET …/git-integration/{integration_id}` | | |
| `GitIntegrationService.listRepositories` | `GET …/git-integration/{integration_id}/repository` | | |
| `GitIntegrationService.remove` | `DELETE …/git-integration/{integration_id}` | ✓ | |

**Владелец интеграции — аккаунт, а не проект.** Установка ставится на организацию и
переиспользуется всеми проектами аккаунта: поэтому в путях нет `service_id`, а `getList`
отдаёт интеграции аккаунта целиком. Ресурс `GitIntegration` (`id`, `account_id`, `provider`
со значением `GITHUB`, `installation_id`, `account_login`, `status`, `secret_ref`,
`expires_at`, `created_at`) описан в `02`.

Статус установки виден в ответах `get` и `getList` и проходит `PENDING_APPROVAL` → `ACTIVE`
⇄ `DEGRADED` → `REVOKED`. Вызов, упирающийся в неготовую или потерявшую доступ установку,
отвечает объявленным кодом, а не «внутренней ошибкой» и не тишиной:
`INTEGRATION_PENDING_APPROVAL` (нетерминальный — владелец организации ещё не одобрил
установку), `INTEGRATION_REVOKED`, `INTEGRATION_TOKEN_EXPIRED`,
`INTEGRATION_REPO_ACCESS_LOST`, `INTEGRATION_RATE_LIMITED`.

Приём событий от провайдера — не публичный API, а отдельный обработчик, см. §4.6.

## 3. Общие структуры ответа

**Успешно принятая мутация**

```
Accepted {
  resource   — созданный или изменённый ресурс в текущем (обычно переходном) состоянии
  operation  — идентификатор, статус, стадия
}
```

**Отказ валидации** (синхронный, до создания операции)

```
Error {
  code     — уточнённый код продукта, см. 04 §7
  message  — безопасное сообщение, часть контракта
  field    — имя поля, если отказ относится к полю
  details  — дополнительные данные, зависят от кода
}
```

Синхронно отвергается всё, что можно проверить без обращения к внешним системам. Всё
остальное становится отказом операции.

## 4. Детальные структуры нетривиальных методов

### 4.1 CloudService.create — создание приложения

`POST /v1/cloud`

**Вход** (блок параметров приложения; общие поля запроса — существующие)

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `project_id` | UUID | да | Существующий проект |
| `name` | string | да | Отображаемое имя |
| `region_id` | string | нет | По умолчанию — регион проекта |
| `git.repository_url` | string | нет¹ | Ссылка на репозиторий |
| `git.integration_id` | UUID | нет | Установка приложения провайдера |
| `git.ref` | string | нет | По умолчанию — ветка по умолчанию репозитория |
| `git.context_dir` | string | нет | Для монорепозитория |
| `upload_id` | UUID | нет¹ | Альтернатива репозиторию |
| `variables` | map | нет | Несекретные значения |
| `service_bindings` | список | нет | `{service_kind, target_service_id, variable_prefix}` |

¹ Ровно одно из `git.repository_url` и `upload_id`, либо ни одного — тогда приложение
создаётся пустым и источник задаётся потом.

**Что происходит одной транзакцией:** приложение, окружение `production`, компонент (если
задан источник), источник, привязки, первая сборка, первый релиз, операция, задания и
события исходящей очереди.

**Выход:** `Service` с состоянием `CREATING` и идентификатором операции.

**Побочные эффекты:** создаётся namespace окружения; для приватного репозитория без
интеграции провайдера генерируется ключ доступа, источник переходит в `PENDING`, и первая
сборка не запускается до подтверждения доступа.

**Объявленные отказы:** нехватка квоты проекта · недоступный проект · неверная ссылка на
репозиторий · превышен потолок приложений тарифа · услуга привязки не принадлежит проекту.

### 4.2 DeploymentService.create — выкатка

`POST /v1/cloud/application/{service_id}/deployment`

**Вход**

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `environment_id` | UUID | нет | По умолчанию — окружение приложения по умолчанию |
| `component_id` | UUID | нет | По умолчанию — все включённые компоненты |
| `source_ref` | string | нет | Ветка, тег или SHA. По умолчанию — из источника с учётом переопределения окружения |
| `build_id` | UUID | нет | Выкатить уже собранное, без новой сборки |
| `image_digest` | string | нет | Выкатить конкретный артефакт приложения |
| `reason` | string | нет | Комментарий в историю |

`source_ref`, `build_id` и `image_digest` взаимоисключающи.

**Выход:** `Accepted` со списком созданных сборок и релизов и одной операцией на всё
действие.

**Команда релиза.** Если у компонента задан `release_command` (либо
`release_command_override` в конфигурации окружения), релиз проходит стадию `RELEASING`
**до переключения трафика**: `QUEUED` → `RELEASING` → `DEPLOYING` → `ACTIVE`. Запуск ровно
один на релиз, в том же образе, с теми же переменными и секретами, со своим предельным
сроком; ссылка на его журнал лежит в `release_log_ref` релиза. **Отказ команды не трогает
предыдущий релиз**: трафик не переключается, предыдущая версия остаётся активной, релиз
завершается кодом `RELEASE_COMMAND_FAILED` или `RELEASE_COMMAND_TIMEOUT`. Команда
выполняется на **каждом** релизе, включая продвижение и откат, — за её идемпотентность
отвечает клиент.

**Предусловия:** нет активного раската на той же паре (компонент, окружение) — иначе отказ
с указанием идущего релиза, а не молчаливое вытеснение · профиль кластера совместим ·
квота проекта позволяет.

### 4.3 DeploymentService.promote — продвижение

`POST /v1/cloud/application/{service_id}/deployment/promote`

**Вход:** `from_environment_id` (обяз.), `to_environment_id` (обяз.), `component_id` (нет,
по умолчанию все), `reason`.

**Что делает:** для каждого компонента берёт digest его активного релиза в исходном
окружении и создаёт новый релиз в целевом с **тем же** digest и **конфигурацией целевого
окружения**. Пересборки нет.

**Объявленные отказы:** в исходном окружении нет активного релиза компонента · форма
компонентов различается (не должно случаться, но проверяется) · профиль целевого кластера
несовместим · артефакт удалён сборщиком мусора.

### 4.4 SourceService.set — подключение источника

`PUT /v1/cloud/application/{service_id}/component/{component_id}/source`

**Вход:** `type`, `integration_id`, `repository_url`, `ref`, `context_dir`,
`credential_kind`, `https_token` (только на запись), `upload_id`.

**Выход:** метаданные источника. Приватная часть ключа и токен **никогда не возвращаются**.
При генерации ключа доступа возвращается его публичная часть и `access_status = PENDING`.

**Побочные эффекты:** проверка доступа к репозиторию выполняется сразу и синхронно, её
результат ложится в `access_status`. Секрет вебхука создаётся автоматически.

### 4.5 ServiceBindingService.create — привязка базы данных

`POST /v1/cloud/application/{service_id}/binding`

**Вход:** `environment_id` (нет), `component_id` (нет), `service_kind` (да),
`target_service_id` (да), `variable_prefix` (нет).

**Что делает:** запрашивает у услуги-владельца учётные данные для этого приложения, кладёт
их в Vault по пути окружения, создаёт переменные с `origin = SERVICE_BINDING`, открывает
точечное правило исходящего доступа к адресу услуги и порождает релиз с новой ревизией
конфигурации.

**Объявленные отказы:** услуга не принадлежит тому же проекту · услуга не поддерживает
выдачу отдельных учётных данных · услуга недоступна · префикс переменных занят.

**Почему ссылка, а не копия:** ротация учётных данных на стороне базы не должна ломать
приложение. Переменные с этим происхождением не редактируются вручную — ручная правка
пережила бы ротацию ровно до первой смены пароля.

### 4.6 Приём событий провайдера — не публичный метод

`POST /v1/cloud/application/hook/{provider}` — обработчик, вызываемый Git-провайдером.

**Проверки в строгом порядке, до любой работы:** подпись тела совпадает с секретом
установки → событие не обрабатывалось ранее (ключ: идентификатор события провайдера плюс
SHA коммита) → установка известна и не отозвана → ветка совпадает с настроенной для
окружения с включённой автовыкаткой.

Ответ провайдеру — всегда быстрый и без деталей: обработчик не должен рассказывать
постороннему, существует ли у нас такое приложение.

**Исчерпание лимита провайдера — временный отказ, а не отказ в правах.** Ответ провайдера об
исчерпанном лимите на последующих вызовах его API (чтение репозитория, выпуск токена
установки) классифицируется кодом `INTEGRATION_RATE_LIMITED` и повторяется с ростом и
разбросом; интеграция при этом переходит в `DEGRADED`, а не в `REVOKED`. Спутать это с
`INTEGRATION_REPO_ACCESS_LOST` — значит отозвать рабочую установку из-за чужой квоты.

### 4.7 LogService.get — чтение журналов

**Вход:** `environment_id`, `component_id`, `deployment_id`, `replica_id`, `since`, `until`,
`level`, `contains`, `limit`, `cursor`.

Язык запросов хранилища наружу не отдаётся ни в каком виде. Фасад строит запрос сам по
перечисленным параметрам.

**Выход:** страница строк плюс курсор плюс **счётчик отброшенных строк** за период, если
приложение упиралось в потолок приёма. Молчаливая потеря журналов — худший вид потери.

### 4.8 UsageService.get — потребление

**Выход:** потребление за период по статьям (процессорное время, память, минуты сборки,
время команды релиза, исходящий трафик, объём журналов), включённая квота проекта, прогноз
до конца периода, разбивка по окружениям и компонентам.

Счётчик виден клиенту **с первой поставки**, даже пока подсчёт работает в теневом режиме и
счета выставляются по тарифу: первая когорта не должна привыкнуть, что сборки и трафик
бесплатны.

### 4.9 BudgetService.update — потолок расходов проекта

`PUT /v1/cloud/application/budget`

Бюджет принадлежит **проекту**, а не приложению: ресурс `Budget` описан в `02`.

**Вход**

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `project_id` | UUID | да | Проект, для которого задаётся потолок |
| `limit_amount` | число | да | Потолок расходов за расчётный период |
| `currency` | string | да | Валюта потолка; совпадает с валютой счёта проекта |
| `enforcement` | enum | да | `NOTIFY` \| `STOP_NON_PRODUCTION` \| `STOP_METERED` |
| `thresholds` | список чисел | нет | Проценты потолка, на которых уходит уведомление; по умолчанию 50, 80, 100 |

**Выход:** `Budget` целиком — заданные поля плюс расчётные `current_spend`, `forecast`,
`status`.

**Что делает режим энфорсмента**

| Режим | Действие при достижении потолка |
|---|---|
| `NOTIFY` | Только уведомления по порогам; ничего не останавливается |
| `STOP_NON_PRODUCTION` | Останавливаются непроизводственные окружения; боевое работает |
| `STOP_METERED` | Останавливаются сборки, непрод и исходящий трафик; **боевой сайт продолжает работать** |

**Предусловие:** остановка боевого сайта бюджетом недоступна ни в одном режиме. Она
возможна **только** через `overdraft_policy = STOP_ALL` у плана проекта — то есть явным
выбором клиента в другом ресурсе, а не побочным эффектом потолка расходов. Режим, который
потребовал бы остановки production, отвергается.

**Объявленные отказы:** `BUDGET_LIMIT_TOO_LOW` — потолок ниже уже накопленного потребления
периода или ниже минимального платежа плана · `BUDGET_ENFORCEMENT_UNSUPPORTED` — запрошенный
режим не поддерживается планом проекта.

**Наполнение упирается во внешний блокер 0.5** (биллинг Beget). В Э1 замораживается **форма
ресурса**, а не срок наполнения: метод без модели недопустим — это тот же класс, за который
в первом раунде удалён режим выделенного балансировщика.

## 5. Дисциплина обновления

`PATCH`-методы принимают маску изменяемых полей.

| Ситуация | Ответ |
|---|---|
| В маске неизвестное поле | Отказ с именем поля |
| В маске неизменяемое поле | Отказ `<поле> неизменяемо после создания` |
| Маска пуста | Применяются все изменяемые поля тела; неизменяемые из тела игнорируются |
| Поле изменяемое | Применяется, валидируется теми же правилами, что при создании |

Проверка неизменяемости идёт **до** проверки состава маски: иначе неизменяемое поле будет
отвергнуто как «неизвестное», и клиент получит неверную причину.

## 6. Опрос состояния

| Мутация | Что опрашивать | Успех | Отказ |
|---|---|---|---|
| Создание приложения | операция, затем услуга | операция успешна, приложение активно | операция в отказе |
| Выкатка, продвижение, откат | операция, затем релиз | операция успешна, релиз активен | отказ или отмена |
| Создание домена | операция, затем домен | домен активен, сертификат готов | отказ или деградация |
| Привязка услуги | операция, затем привязка | привязка активна | отказ |
| Удаление чего угодно | операция, затем ресурс | операция успешна, ресурс отвечает как несуществующий | операция в отказе |

Рекомендуемый интервал опроса — 2–5 с с ростом и разбросом. Публичного потокового API
состояния нет; поток есть только у журналов.

**Ни одно ожидание не длится вечно.** У каждой стадии есть предельный срок и терминальный
исход; операция, у которой истёк срок стадии, переходит в отказ с указанием стадии.

## 7. Что сознательно отсутствует в контракте

| Чего нет | Почему |
|---|---|
| Режим выделенного балансировщика | Был объявлен полем, которого никто не читает. Поле удалено с резервированием номера: принять параметр и молча выбросить — не исход |
| Произвольный язык запросов к метрикам и журналам | Изоляция арендаторов и защита от взрыва кардинальности |
| Идентификаторы Kubernetes в любом виде | Namespace, узел, под, маршрут, кластер — детали реализации |
| Чтение значения секрета после записи | Только на запись, никогда на чтение — включая пути поддержки |
| Автоматический откат при отказе раската | Скрыл бы ошибку новой версии. Предыдущий релиз и так остаётся активным |
| Публичное потоковое состояние ресурсов | Опрос операции достаточен; поток есть у журналов |
