# 05. Пользовательские сценарии и реакция системы

Основной путь и 79 сценариев отклонений. Формат каждого сценария одинаков: **когда** он
наступает, **что делает система**, **что видит клиент**, **каким становится состояние** и
**почему именно так** — последнее нужно, чтобы через год никто не «упростил» поведение,
не поняв причины.

Коды отказов и тексты — `04` §7. Здесь описано поведение, а не формулировки.

---

## 1. Основной путь

### 1.1 Подключение и первый адрес

| # | Клиент | Система | Клиент видит |
|---|---|---|---|
| 1 | Выбирает «Приложение» в каталоге услуг, ставит интеграцию с GitHub, выбирает репозиторий из списка | Создаёт одной транзакцией: приложение, окружение `production`, компонент, источник, сборку, релиз, операцию, задания и события. Создаёт namespace окружения | Приложение создаётся, идёт сборка |
| 2 | — | Контроллер сборки берёт задание, резолвит ветку в конкретный коммит, забирает исходники | Стадия «получение исходников», виден коммит |
| 3 | — | Определяет способ сборки, публикует **план с источником каждого значения** | «Go 1.24, бэкпак, запуск `./server`, порт 8080, размер small» и ссылка «поправить» — **сборка при этом уже идёт** |
| 4 | — | Собирает, публикует образ, читает манифест обратно по digest, подписывает, прикладывает состав | Стадии со временем, живой журнал сборки |
| 5 | — | Оператор берёт задание материализации, пишет якорный объект, разворачивает рабочую нагрузку, сервис, конфигурацию, секреты, маршрут | «Выкатка» |
| 6 | — | Дожидается готовности реплик, публикации эндпоинтов и принятия маршрута шлюзом | «Готово» |
| 7 | Открывает адрес | — | Работающий сайт по HTTPS на техническом адресе |

Ни одного вопроса по пути. Обязательное решение о продукте ровно одно — какой репозиторий.

### 1.2 Дальнейший цикл

| Событие | Реакция |
|---|---|
| `git push` в настроенную ветку | Проверка подписи события → устранение дублей → сборка → выкатка. Статус возвращается в pull request |
| Изменение переменной | Новый релиз с тем же образом и новой ревизией конфигурации |
| «Откатить» | Новый релиз на образ предыдущего успешного. Без сборки, обычно без скачивания |
| «Продвинуть в production» | Новый релиз в целевом окружении с **тем же** образом и конфигурацией целевого окружения |

## 2. A. Подключение источника

### A1. Публичный репозиторий по ссылке
**Когда** — клиент вставил адрес публичного репозитория без интеграции провайдера.
**Система** — проверяет доступ синхронно, резолвит ветку по умолчанию, запускает сборку.
**Клиент видит** — сразу стадию получения исходников.
**Итог** — источник `OK`.

### A2. Приватный репозиторий через интеграцию провайдера
**Когда** — установлена интеграция, репозиторий выбран из списка.
**Система** — использует токен установки, ключ доступа не нужен, вебхук создаётся автоматически.
**Итог** — источник `OK`, автовыкатка включена.
**Почему** — это основной путь, а не запасной: он единственный не требует от клиента ручных действий в чужом интерфейсе.

### A3. Приватный репозиторий без интеграции
**Когда** — указан адрес приватного репозитория, интеграции нет.
**Система** — генерирует ключ доступа, показывает публичную часть, ставит источник в **нетерминальное** ожидание, сборку не запускает, предлагает кнопку «проверить» и сама перепроверяет по таймеру ограниченное время.
**Клиент видит** — не красную ошибку, а шаг: «добавьте ключ в настройки репозитория».
**Итог** — источник `PENDING`, приложение в провизионировании.
**Почему** — иначе штатный первый заход главного коммерческого сегмента начинается с отказа, при том что система знает, что делать дальше.

### A4. Клиент так и не добавил ключ
**Когда** — ожидание доступа длится дольше предельного срока.
**Система** — переводит источник в `DENIED`, операцию — в терминальный отказ, приложение остаётся созданным и пустым.
**Клиент видит** — «доступ не подтверждён», ключ и инструкция на месте, кнопка «повторить».
**Почему** — вечных ожиданий не бывает; при этом приложение не удаляется, чтобы клиент вернулся и доделал.

### A5. Ветки, указанной клиентом, не существует
**Система** — отдельный код «ветка не найдена», а не общее «источник недоступен»; перечисляет несколько существующих веток.
**Почему** — «нет ветки» и «нет доступа» требуют разных действий, и клиент должен различать их без обращения в поддержку.

### A6. Адрес репозитория резолвится в приватный диапазон
**Когда** — арендатор указал имя, указывающее на внутренний адрес, или пытается повторное связывание DNS.
**Система** — резолвит **сама**, отбрасывает адрес после резолва, соединяется только по закреплённому адресу, отказ терминальный.
**Клиент видит** — «адрес репозитория недопустим», без подробностей о том, что именно во внутренней сети.
**Почему** — это самый охраняемый узел продукта; подробность в сообщении здесь помогает только атакующему.

### A7. Репозиторий с подмодулями
**Система** — по умолчанию подмодули не клонирует; сборка идёт без них. Если сборка падает на отсутствующем подмодуле, отказ прямо называет причину и предлагает включить их.
**Почему** — рекурсивный клон означает клон по адресам, которых мы не проверяли; включение — осознанное действие с квотой.

### A8. Загрузка архива вместо репозитория
**Система** — выдаёт временную ссылку на загрузку, проверяет контрольную сумму, распаковывает с полным набором проверок (пути, ссылки, коэффициент сжатия, число записей).
**Итог** — сборка от неизменяемой версии объекта.
**Почему** — это путь для тех, у кого нет Git; безопасность распаковки при этом не мягче, чем у Git.

### A9. Установку ставит сотрудник без прав владельца организации
**Когда** — сотрудник запускает установку приложения провайдера на организацию, где право установки есть только у владельца.
**Система** — создаёт `GitIntegration` (владелец — **аккаунт**, поле `account_id`; `provider` = `GITHUB`, `installation_id` и `account_login` от провайдера) в статусе `PENDING_APPROVAL` с **нетерминальным** кодом `INTEGRATION_PENDING_APPROVAL`. Список репозиториев не запрашивается, источник остаётся в ожидании, сборка не запускается; система перепроверяет состояние установки по таймеру ограниченное время.
**Клиент видит** — «запрос отправлен владельцу организации», ссылку на страницу подтверждения и кнопку «проверить», а не красную ошибку.
**Итог** — интеграция `PENDING_APPROVAL`, приложение в провизионировании.
**Почему** — в организации из двух человек и более это штатный первый заход, а не исключение. Терминальный отказ здесь означает, что клиент бросает подключение ровно в тот момент, когда всё уже сделано верно и осталось чужое действие. Владелец интеграции — аккаунт, поэтому одобрение получают один раз на все проекты аккаунта, а не по разу на приложение.

### A10. Владелец организации отозвал установку
**Когда** — установка удалена на стороне провайдера: пришло событие либо первый же вызов вернул отказ.
**Система** — переводит `GitIntegration` в `REVOKED`, отдаёт терминальный `INTEGRATION_REVOKED`, снимает автовыкатку по вебхуку **во всех проектах аккаунта**, освобождает `secret_ref`. **Работающие релизы не трогаются.** Предлагает поставить установку заново.
**Клиент видит** — «доступ к репозиториям отозван в организации», перечень затронутых приложений и одну кнопку переустановки.
**Итог** — интеграция `REVOKED`, приложения работают, новые сборки не запускаются.
**Почему** — отзыв установки — событие уровня аккаунта, и клиент должен увидеть его один раз со списком последствий, а не по отдельному непонятному отказу в каждом приложении. Гасить работающие сайты из-за потери доступа к исходникам недопустимо: образы уже собраны и от провайдера не зависят.

### A11. Токен установки истёк
**Когда** — токен установки короткоживущий, `expires_at` прошёл, обновление у провайдера не удалось.
**Система** — переводит интеграцию в `DEGRADED`, отказ `INTEGRATION_TOKEN_EXPIRED`; при первом успешном обновлении возвращает `ACTIVE` сама, без действий клиента. Если же из области установки убран конкретный репозиторий, интеграция остаётся `ACTIVE`, а отказ несёт отдельный код `INTEGRATION_REPO_ACCESS_LOST` с именем репозитория.
**Клиент видит** — состояние интеграции и какое именно приложение осталось без источника.
**Почему** — «перестала работать вся установка» и «убрали один репозиторий из её области» требуют разных действий: в первом случае чинится установка, во втором — её область. Один общий код заставил бы переустанавливать интеграцию там, где достаточно добавить репозиторий.

### A12. Исчерпан лимит запросов провайдера
**Когда** — серия событий по нескольким приложениям аккаунта упирается в лимит API провайдера.
**Система** — классифицирует `INTEGRATION_RATE_LIMITED` как **временный** отказ: задание возвращается в очередь с отступом до времени сброса, которое провайдер сообщает в ответе. Интеграция уходит в `DEGRADED`, а не в `REVOKED`, и возвращается в `ACTIVE` сама после сброса лимита; операция не закрывается, релиз не отменяется.
**Клиент видит** — «ожидание лимита провайдера, повтор в HH:MM», а не «нет доступа».
**Итог** — работа продолжается после сброса лимита.
**Почему** — по ответу провайдера исчерпание лимита похоже на отказ в правах, но требует противоположного действия: здесь надо подождать, там — чинить установку. Терминальный отказ подталкивал бы клиента ломать работающую интеграцию из-за временного явления.

## 3. B. Определение способа сборки

### B1. Есть `Dockerfile`
**Система** — собирает из него, порт берёт из объявления в образе, команду — из образа.
**Итог** — план сборки с источником каждого значения.

### B2. Нет `Dockerfile`, один стек
**Система** — бэкпаки, команда из `Procfile` или из процесса запуска бэкпака.

### B3. Несколько стеков в одном контексте
**Когда** — типовой «бэкенд на Python и фронтенд на Node в корне».
**Система** — **не гадает**: отказ с перечислением найденного и двумя выходами — указать контекст или указать сборщик.
**Почему** — молчаливый выбор здесь означает, что клиент получит собранное не то и будет искать ошибку в своём коде.

### B4. Монорепозиторий
**Система** — контекст задаётся полем в манифесте или при подключении источника; каждый компонент имеет свой контекст.
**Почему** — без поля контекста монорепозиторий, который в 2026 является нормой, необъявим вообще.

### B5. Ничего не распознано
**Система** — отказ, называющий, что искали и чего не нашли, со списком поддерживаемых маркеров и предложением добавить `Dockerfile`.

### B6. Ошибка в `beget.yaml`
**Система** — проверяет манифест **сразу после резолва коммита**, до тяжёлой сборки; отказ называет строку и поле.
**Почему** — узнавать про опечатку в манифесте через две минуты компиляции — впустую потраченные минуты сборки, которые к тому же тарифицируются.

### B7. Секрет положили в манифест
**Система** — отказ с именем ключа и указанием, куда его перенести. Значение при этом **не** попадает ни в журнал, ни в сообщение об ошибке.

### B8. Сборка падает
**Система** — отказ со стадией, кодом выхода, **последними строками журнала** и ссылкой на полный журнал. Журнал хранится по правилам срока хранения тарифа.
**Почему** — отказ сборки без хвоста журнала бесполезен: клиент всё равно пойдёт его искать, только сначала напишет в поддержку.

## 4. C. Запуск и выкатка

### C1. Приложение стартовало и отвечает
**Система** — релиз активен только когда сошлись все условия: ревизия увидена контроллером, реплики доступны, эндпоинты опубликованы, маршрут принят шлюзом.
**Почему** — «под запустился» не означает «трафик доходит».

### C2. Приложение падает при старте
**Система** — отличает по наличию перезапусков; отказ несёт код завершения и хвост журнала контейнера. **Предыдущий релиз остаётся активным.**
**Почему** — автоматический откат скрыл бы ошибку новой версии; клиент должен увидеть, что именно сломалось.

### C3. Приложение живо, но не слушает порт
**Когда** — контейнер работает, перезапусков нет, проба не проходит дольше бюджета старта.
**Система** — отдельный код с точной подсказкой: какой порт ожидается, что надо слушать переменную, где переопределить порт.
**Почему** — это самая частая ошибка новичка, и система в этот момент знает правильный ответ. Отдать вместо него таймаут — упущенная возможность.

### C4. Приложение упирается в лимит памяти
**Система** — отдельный код: **называет лимит**, показывает пик потребления и предлагает следующий размер одним действием.
**Почему** — лимит поставила платформа. Отдать код завершения 137 без объяснения значит отправить клиента искать утечку там, где её нет.

### C5. Фоновый обработчик завершился
**Система** — для этого типа компонента завершение с ненулевым кодом — отдельный класс: нет слушающего сокета и не должно быть, проба HTTP не применяется.
**Почему** — иначе воркер вечно диагностируется как «не слушает порт».

### C6. Медленный старт
**Когда** — приложению нужны десятки секунд на прогрев.
**Система** — щедрая проба старта по умолчанию; пока она идёт, релиз в состоянии выкатки, а не в отказе. Бюджет старта настраивается.

### C7. Повторная выкатка того же образа
**Система** — новый релиз, но образ не скачивается заново, слои уже на узлах.
**Итог** — самый быстрый путь; на нём же основаны откат и продвижение.

### C8. Раскат не сходится в срок
**Система** — по истечении предельного срока раската релиз переходит в отказ с указанием, сколько реплик поднялось. Ожидание не длится вечно.

### C9. Отмена идущей выкатки
**Система** — отменяет до публикации образа; после публикации отменять нечего. Отменённый релиз не становится активным, предыдущий не трогается.

### C10. Команда релиза выполнена успешно
**Когда** — у компонента задана `release_command` либо окружение переопределило её через `release_command_override`.
**Система** — после публикации образа и **до переключения трафика** делает **один** запуск на релиз: тот же образ, те же переменные и секреты, свой предельный срок. Релиз проходит `QUEUED` → `RELEASING` → `DEPLOYING` → `ACTIVE`; журнал запуска доступен по `release_log_ref`. Для компонентов типа `WORKER` и `STATIC` команда допустима, но по умолчанию пуста.
**Клиент видит** — отдельную стадию «команда релиза» с живым журналом, до неё выкатка не начинается.
**Итог** — релиз `ACTIVE`, время запуска тарифицируется по статье «время команды релиза».
**Почему** — приложение с миграциями не доходит до адреса ни в одном сценарии, если такой стадии нет. Вписать миграцию в стартовую команду означает N параллельных миграций на N репликах; один запуск на релиз — единственная форма, при которой это верно, а поле в манифесте (`release:` внутри компонента) — единственный способ объявить её вместе с кодом.

### C11. Команда релиза завершилась с ошибкой
**Когда** — запуск вернул ненулевой код выхода.
**Система** — отказ `RELEASE_COMMAND_FAILED` с кодом выхода, последними строками журнала и ссылкой на полный по `release_log_ref`. Выкатка **не начинается**, трафик **не переключается**, **предыдущий релиз остаётся активным**.
**Клиент видит** — почему упала именно команда, а не приложение.
**Итог** — релиз в терминальном отказе, боевой трафик на прежней версии.
**Почему** — неудачная миграция при уже переключённом трафике даёт худший из исходов: новый код на не доведённой схеме и откат, который нужно делать вручную под нагрузкой. Порядок «сначала команда, потом трафик» — единственное, что делает отказ безопасным.

### C12. Команда релиза не уложилась в предельный срок
**Когда** — запуск идёт дольше собственного предельного срока команды.
**Система** — прерывает запуск, отказ `RELEASE_COMMAND_TIMEOUT` с указанием срока; трафик не переключается, предыдущий релиз остаётся активным. Срок отдельный от сроков сборки и раската и настраивается.
**Клиент видит** — названный срок и хвост журнала на момент прерывания.
**Почему** — ожиданий без конца не бывает, а срок ставит платформа — значит, она обязана его назвать. Иначе долгая миграция выглядит как зависшая выкатка, и клиент начинает чинить не то.

### C13. Продвижение и откат запускают команду заново
**Когда** — «продвинуть в production» или «откатить».
**Система** — выполняет команду релиза на **каждом** релизе, включая продвижение и откат: это новый релиз с конфигурацией целевого окружения, а платформа не знает, что команда делает. За идемпотентность отвечает клиент — штатные средства миграций это умеют.
**Клиент видит** — ту же стадию `RELEASING` и в продвижении, и в откате.
**Почему** — пропустить команду при продвижении значит выкатить в production код, чья схема не применена. Пропустить при откате — вернуть версию, которой нужен обратный шаг. Решать за клиента, что запуск можно не делать, платформа не вправе: у неё нет содержания команды.

---

## 5. D. Конфигурация, секреты, привязки

### D1. Изменение переменной
**Система** — новая ревизия конфигурации → новый релиз с тем же образом → скользящее обновление. Хеш конфигурации входит в шаблон пода.
**Почему** — без хеша в шаблоне под не перекатывается и продолжает жить со старым окружением, а система при этом рапортует успех. Этот класс дефекта у нас уже был.

### D2. Запись секрета
**Система** — значение уходит в хранилище секретов, в базе остаются только метаданные и ссылка. **Прочитать значение обратно нельзя ни одним методом**, включая пути поддержки.

### D3. Попытка прочитать секрет
**Система** — такого метода не существует. В списке переменных секрет виден ключом и признаком, без значения.

### D4. Привязка базы данных
**Когда** — клиент выбирает существующую услугу базы данных того же проекта.
**Система** — запрашивает у услуги отдельные учётные данные, кладёт в хранилище секретов по пути окружения, создаёт переменные с признаком «управляется привязкой», **открывает точечное правило исходящего доступа к адресу услуги**, порождает релиз.
**Почему** — без правила исходящего доступа приватный адрес базы попадает под общий запрет приватных диапазонов, и клиент получает молчаливый таймаут подключения. Это прямо противоречило бы обещанию «любой отказ несёт причину».

### D5. Попытка руками изменить переменную от привязки
**Система** — отказ: переменная управляется привязкой.
**Почему** — ручная правка пережила бы ротацию учётных данных ровно до первой смены пароля.

### D6. Ротация учётных данных на стороне базы
**Система** — привязка хранит ссылку, а не копию; новые данные приезжают, порождается релиз с новой ревизией конфигурации.
**Если услуга недоступна** — привязка деградирует, но **приложение продолжает работать со старым значением**: привязка не гасит рантайм.

## 6. E. Окружения и продвижение

### E1. Одно окружение
**Система** — окружение создано, но в интерфейсе не показано. Простой клиент про них не знает.

### E2. Создание второго окружения
**Система** — новое окружение уровня «непрод» с обязательной долей квоты и низким приоритетом вытеснения; namespace, свой технический адрес, свои переменные.
**Клиент видит** — селектор окружения появляется только теперь.

### E3. Наследование переменных
**Система** — несекретные переменные уровня приложения наследуются; **секреты не наследуются** в непрод и требуют явного действия.
**Почему** — наследование секретов «за компанию» — типовой способ увезти боевой ключ туда, где доступ шире.

### E4. Продвижение в production
**Система** — берёт образ активного релиза исходного окружения и создаёт релиз в целевом с **тем же** образом и конфигурацией целевого окружения. Пересборки нет.
**Почему** — это единственная причина, по которой принята вся модель окружений: иначе в production уезжает не тот бинарь, который проверяли.

### E5. Продвижение при несовместимом профиле кластера
**Система** — сверяет профиль **до** создания релиза и отказывает заранее.
**Почему** — образ, собранный под узлы с пространствами имён пользователей, не должен молча уехать на узлы без них: там он получит отказ уже после начала выкатки.

### E6. Разная ветка в разных окружениях
**Система** — окружение может переопределить ветку источника. Продвижение при этом остаётся про образ, а не про ветку.

## 7. F. Домены и сертификаты

### F1. Технический адрес
**Система** — выдаётся автоматически при создании веб- или статического компонента, покрыт групповым сертификатом, работает сразу.

### F2. Домен под управлением Beget
**Система** — проверяет владение по аккаунту, сама создаёт запись DNS, запрашивает сертификат. Ручных шагов нет.

### F3. Внешний домен
**Система** — выдаёт цель проверки, ждёт изменения DNS клиентом, затем публикует маршрут и запрашивает сертификат. Проверка повторяется по расписанию ограниченное время.

### F4. Сертификат не продлевается
**Система** — домен переходит в деградацию, **но маршрут продолжает работать** на действующем сертификате; сигнал клиенту и дежурному заранее, до истечения.
**Почему** — гасить работающий адрес из-за проблемы с продлением — худшее, что можно сделать.

### F5. Попытка привязать имя из технической зоны платформы
**Система** — отказ.
**Почему** — иначе арендатор объявляет своим адрес соседа.

---

## 8. G. Масштабирование и нагрузка

### G1. Рост нагрузки при включённом автомасштабировании
**Система** — растит число реплик по загрузке **контейнера приложения**, не пода целиком.
**Почему** — прокси сетки потребляет процессор; при подсчёте по поду порог «70%» означает не то, что написано в тарифе.

### G2. Автомасштабирование упирается в квоту
**Система** — реплики не создаются, но это **не отказ релиза**: клиент получает видимое событие «не удалось вырасти до N, работает M», метрику и предложение поднять тариф; дежурный получает сигнал.
**Почему** — правило «поды в ожидании не оставляем никогда» верно только на пути допуска деплоя; внутри кластера отвергать некому. Честнее показать деградацию, чем молчать при ложном обещании.

### G3. Нехватка ёмкости при выкатке
**Система** — отказ **до** размещения, с причиной. Поды в ожидании не оставляются.

### G4. Оператор и автомасштабирование спорят за число реплик
**Система** — число реплик исключено из применяемого патча, когда автомасштабирование включено; сверка дрейфа его не трогает.
**Почему** — иначе оператор вернёт одну реплику приложению, которое только что выросло под нагрузкой: ошибки ровно на пике при зелёных журналах оператора.

## 9. H. Отказы платформы

### H1. Реестр образов недоступен
**Система** — повтор с отступом, затем терминальный отказ с причиной. Уже работающие приложения не трогаются.

### H2. Хранилище секретов недоступно
**Система** — новые релизы не создаются, отказ с причиной. **Работающие поды продолжают работать** с ранее доставленными значениями.
**Почему** — недоступность хранилища не должна превращаться в аварию работающих приложений.

### H3. Падение исполнителя сборки
**Система** — аренда задания истекает, задание возвращается в очередь, **та же операция продолжается**. Новая операция не создаётся.

### H4. Обслуживание узла
**Система** — бюджет прерывания создаётся всегда в форме «не более одного недоступного»; отсрочка завершения с дренажом эндпоинтов. Однорепличное приложение получает секунды простоя.
**Клиент видит** — событие обслуживания в истории приложения и рекомендацию держать две реплики в production.
**Почему** — наивная форма бюджета на одной реплике заблокировала бы вытеснение навсегда и остановила обновление кластера, в том числе выкатку исправлений безопасности.

### H5. Обновление версии рендера платформы
**Система** — версия рендера зафиксирована в каждом релизе; существующие релизы **не переносятся автоматически**. Новая версия применяется при следующем естественном релизе либо отдельной управляемой операцией с ограничением скорости, сначала на непроде.
**Почему** — иначе апгрейд оператора веером перекатывает весь флот: шквал скачиваний в один реестр, массовое перепрограммирование маршрутов и отказы релизов, которых клиент не запускал.

## 10. I. Удаление и очистка

### I1. Удаление приложения
**Система** — сносит якорные объекты, дальше сборка мусора кластера; затем каскад по внешним артефактам: репозиторий образов, кэш сборки, путь в хранилище секретов, арендатор наблюдаемости, загруженные архивы, записи DNS. У статуса удаления есть **предельный срок и терминальный исход**.
**Почему** — незавершённое удаление — это и утечка данных, и монотонный рост затрат.

### I2. Удаление окружения
**Система** — запрещено для окружения по умолчанию и для последнего. Остальные удаляются с полной очисткой.

### I3. Удаление компонента с активными релизами
**Система** — отказ с предложением сначала отключить компонент в окружениях.

### I4. Подрезка истории
**Система** — глубина отката определяется **обоими** условиями: последние N успешных релизов **и** не старше срока хранения. Образ, на который ссылается достижимый релиз, не удаляется.
**Почему** — только по числу история растёт вечно у активных клиентов; только по сроку — исчезает у неактивных ровно тогда, когда откат и нужен.

---

## 11. J. Квоты, бюджет, злоупотребления

### J1. Достигнута включённая квота проекта
**Система** — работающее продолжает работать; ограничения включаются лестницей: непрод и предпросмотр → сборки → исходящий трафик → production **только по явно выбранной клиентом политике** и с предупреждением.
**Почему** — обратный порядок означает, что биллинг вызывает аварию боевого сайта. Для хостера это дороже перерасхода.

### J2. Исчерпан потолок сборок
**Система** — новые сборки отклоняются с причиной и датой обновления счётчика; уже идущие доводятся до конца.

### J3. Приложение заливает журналы
**Система** — потолок приёма на реплику; лишнее отбрасывается, но **счётчик отброшенных строк виден клиенту** в том же ответе, где журналы.
**Почему** — молчаливая потеря журналов заставляет искать несуществующий баг в приложении.

### J4. Исходящий спам или майнинг
**Система** — почтовые порты закрыты по умолчанию и открываются заявкой; потолки трафика и пакетов на окружение; при срабатывании — приостановка с **актором, сигналом, видимым текстом и процедурой оспаривания**.
**Почему** — у хостера в той же автономной системе живёт почта: попадание диапазонов в списки блокировок бьёт по услугам, не имеющим к платформе отношения.

### J5. Пробный доступ исчерпан
**Система** — приложение продолжает работать, новые не создаются, предлагается тариф.

### J6. Клиент выставил потолок расходов, и потолок сработал
**Когда** — у проекта задан `Budget` (`project_id`, `limit_amount`, `currency`, `enforcement`, `thresholds`), и `current_spend` дошёл до предела.
**Система** — на порогах `thresholds` шлёт уведомления и показывает `forecast` — оценку выхода на предел; при достижении предела действует по `enforcement`: `NOTIFY` — только уведомляет, `STOP_NON_PRODUCTION` — гасит непрод и предпросмотр, `STOP_METERED` — останавливает сборки, непрод и исходящий трафик. **Боевой сайт при этом работает.** Предел ниже уже потреблённого либо ниже минимального платежа отклоняется синхронно кодом `BUDGET_LIMIT_TOO_LOW`; режим, не поддержанный планом проекта, — кодом `BUDGET_ENFORCEMENT_UNSUPPORTED`.
**Клиент видит** — `status` бюджета, текущее потребление против предела, что именно остановлено и что продолжает работать.
**Итог** — метрируемое остановлено, боевой сайт отвечает.
**Почему** — «я включил защиту, и она не сработала» — худшая форма претензии в категории, хуже, чем «дорого». Поэтому метод потолка не может существовать без ресурса за ним: метод-фантом без модели — тот же класс, за который в первом раунде удалён режим выделенного балансировщика.

### J7. Клиент явно выбрал остановку всего
**Когда** — у плана проекта задано `overdraft_policy = STOP_ALL`.
**Система** — **только в этом случае** остановка доходит до боевого сайта: предупреждение заранее, видимое событие в момент остановки, возобновление одним действием после пополнения. Никакое значение `enforcement` у `Budget`, включая `STOP_METERED`, до production не достаёт.
**Клиент видит** — что боевой сайт остановлен по его собственной политике, а не по решению платформы.
**Почему** — это та же лестница, что в J1: биллинг не вправе устраивать аварию боевого сайта без явно выбранной клиентом политики. Форма ресурса фиксируется сразу, полнота учёта приезжает вместе с биллингом Beget — замораживается **форма**, а не срок наполнения.

## 12. K. Параллелизм и гонки

### K1. Две выкатки одного компонента в одно окружение
**Система** — второй запрос отклоняется с указанием идущего релиза. Инвариант держится уникальным индексом в базе, а не проверкой в коде.
**Почему** — проверка «прочитал и решил» проигрывает гонку; молчаливое вытеснение по принципу «кто последний, тот и прав» недопустимо для релиза.

### K2. Повтор запроса с тем же ключом идемпотентности
**Система** — возвращает **ту же** операцию, второй релиз не создаётся.

### K3. Несколько событий push подряд
**Система** — устранение дублей по идентификатору события и SHA коммита; при быстрой серии — актуальным считается последний коммит, устаревшие задания отменяются до начала тяжёлой работы.
**Почему** — иначе очередь забивается сборками, результат которых уже никому не нужен, и клиент платит за них минутами сборки.

### K4. Клиент правит переменные во время выкатки
**Система** — правка порождает новую ревизию конфигурации; новый релиз создаётся после завершения текущего, а не вместо него.

## 13. L. Доступ, приватность, поддержка

### L1. Обращение к чужому приложению
**Система** — отвечает так же, как на несуществующее.
**Почему** — различимый ответ позволяет перечислить чужие ресурсы.

### L2. Отзыв доступа сотрудника
**Система** — доступ прекращается для интерфейса, API и CLI одновременно; идущие операции завершаются, новые от этого лица не принимаются.

### L3. Диагностика приложения поддержкой
**Система** — доступ поддержки ограничен по сроку, пишется в журнал действий и **виден владельцу**. Значения секретов недоступны никому через продуктовый путь. Прямой доступ в кластер — аварийный, с записью.
**Почему** — без этого у поддержки на первый же день нет инструмента, кроме доступа уровня кластера, который равен чтению всех секретов всех клиентов.

### L4. Запрос «кто это выкатил»
**Система** — журнал действий только на добавление: кто выкатил, кто читал журналы и переменные, кто менял привязки, включая действия поддержки.

### L5. Выгрузка собственного образа
**Система** — короткоживущий токен на чтение конкретного образа по digest.
**Почему** — отсутствие замка на артефакте — норма рынка, а удержать клиента этим всё равно нельзя; зато на этапе покупки снимает возражение.
