# 02. Доменная модель

Ресурсы, их поля, изменяемость, статусы, машины состояний и инварианты. Это словарь, на
котором говорят все остальные документы комплекта.

---

## 1. Идентификаторы

| Вид | Форма | Правила |
|---|---|---|
| Публичный идентификатор ресурса | UUID v4 | Единственная внешне адресуемая идентичность. Неизменяем на всю жизнь ресурса. Операции смены идентификатора не существует |
| Внутренний идентификатор | на усмотрение реализации | Наружу не выходит никогда: ни в ответе, ни в ошибке, ни в журнале действий, ни в метке Kubernetes, доступной клиенту |
| `dns_label` | `<слаг-имени>-<6 случайных символов>`, нижний регистр, метка DNS | Генерируется один раз при создании окружения и веб-компонента. **Неизменяем**, даже если приложение переименовали: иначе выданный адрес ломается при переименовании |
| Имя (`name`) | человекочитаемая строка | Косметическая метка, уникальная в своей области. **Никогда не участвует в адресации**: ни в URL, ни в ссылках между ресурсами, ни в области прав |

`service_id` — это одновременно идентификатор `CloudService` и `Application`. Отдельного
публичного идентификатора приложения не существует.

Правило «адресуемся по неизменяемому идентификатору, а не по имени» — не стилистика.
Имена меняются и коллизят; привязка адреса, гранта или ссылки к имени означает, что
переименование ломает выданное наружу.

## 2. Карта ресурсов

```
Beget Account ──────────────── GitIntegration      (установка Git-провайдера, §3.7)
      │
Beget Project ──────────────── ProjectPlatformPlan (квота и минимальный платёж, §3.15)
      │                        Budget              (потолок расходов проекта, §3.16)
      │
      └── Application (= CloudService, service_id)
            ├── Component            форма процесса, общая для всех окружений
            │     └── Source         откуда брать код
            ├── Environment          область конфигурации
            │     ├── ComponentEnvironmentConfig   переопределения на пару (компонент, окружение)
            │     ├── Variable                     переменные и секреты
            │     ├── ServiceBinding               привязка услуги Beget (база данных)
            │     ├── DomainBinding                адреса
            │     └── Deployment                   релизы
            ├── Build                сборка: принадлежит приложению, окружения не знает
            ├── Artifact             неизменяемый образ по digest
            └── Operation            состояние длительного действия
```

Три уровня отвечают на три разных вопроса, и их нельзя сливать:
**`Application`** — что это за сервис · **`Component`** — из каких независимых частей он
состоит · **`Deployment`** — какая версия какой части сейчас работает в каком окружении.

`GitIntegration` — единственный ресурс уровня **аккаунта**: установка приложения провайдера
ставится на организацию и переиспользуется всеми проектами аккаунта. `Budget` — ресурс уровня
**проекта**, там же, где живёт тариф: расходы считаются по проекту.

### 3.3 Component

Форма процесса. **Общая для всех окружений** — это инвариант, а не упрощение (§5.3).

| Поле | Тип | Изм. | Обяз. | Описание |
|---|---|---|---|---|
| `id` | UUID | И | — | |
| `application_id` | UUID | И | — | |
| `name` | string | И | да | Уникально в приложении. **Неизменяемо**: имя является ключом в манифесте, переименование разорвало бы связь с описанием в коде |
| `type` | enum | И | да | `WEB` \| `WORKER` \| `STATIC`. `CRON` — вне первой поставки |
| `dns_label` | string | И | — | Только для `WEB` и `STATIC` |
| `run_command` | string | М | нет | Пусто — берётся из образа или бэкпака |
| `release_command` | string | М | нет | Команда релиза: один запуск на релиз **до переключения трафика** (§4.5). Пусто — фазы релиза нет |
| `port` | int | М | нет | Только `WEB`. Пусто — контракт `PORT` |
| `health_check` | объект | М | нет | §3.4 |
| `default_size` | enum | М | да | `nano` \| `micro` \| `small` \| `medium` \| `large` |
| `default_scale` | объект | М | да | `{min, max, target_cpu_percent}` |
| `build_config` | объект | М | нет | `{context, dockerfile, builder}` |
| `static_config` | объект | М | нет | Только `STATIC`: `{output_dir, spa_fallback, index, not_found}` |
| `spec_revision` | int | В | — | Растёт при любом изменении формы. Вход рендера |
| `status` | enum | В | — | §4.3 |

`WORKER` не имеет `port`, `dns_label`, HTTP-пробы и маршрута. `STATIC` не имеет
`run_command`: платформа сама подаёт содержимое `output_dir` через свой образ раздачи.

`release_command` допустима для всех трёх типов, но **по умолчанию пуста** у `WORKER` и
`STATIC`: миграцию схемы обычно держат при веб-компоненте, а не размножают по обработчикам.
Запретить её этим типам нельзя — обработчик бывает единственной частью приложения, у которой
вообще есть доступ к базе.

### 3.7 GitIntegration — интеграция с Git-провайдером

**Владелец — аккаунт, а не проект.** Установка приложения ставится на организацию у провайдера;
привязка к проекту заставила бы владельца организации одобрять установку заново на каждый
проект — при том что у провайдера это один и тот же объект. Одна интеграция переиспользуется
всеми проектами аккаунта; `Source.git_integration_id` ссылается сюда.

| Поле | Тип | Изм. | Обяз. | Описание |
|---|---|---|---|---|
| `id` | UUID | И | — | |
| `account_id` | UUID | И | — | Владелец |
| `provider` | enum | И | да | `GITHUB`. Другие провайдеры — вне первой поставки |
| `installation_id` | string | И | да | Идентификатор установки на стороне провайдера |
| `account_login` | string | В | — | Организация или пользователь, на которых поставлена установка. Показывается при выборе репозитория |
| `status` | enum | В | — | §4.8 |
| `secret_ref` | string | В | — | Ссылка на Vault: закрытый ключ приложения и текущий токен установки. Наружу не выходит никогда |
| `expires_at` | timestamp | В | — | Срок действия текущего токена установки. Обновление фоновое, до истечения |
| `created_at` | timestamp | В | — | |

Коды отказа:

| Код | Класс | Когда |
|---|---|---|
| `INTEGRATION_PENDING_APPROVAL` | **нетерминальный** | Установка запрошена, владелец организации ещё не одобрил. Это ожидание, а не ошибка: сообщение объясняет, кто и что должен нажать |
| `INTEGRATION_REVOKED` | терминальный | Установка удалена на стороне провайдера. Сборки из этого источника отклоняются, работающие релизы не трогаются |
| `INTEGRATION_TOKEN_EXPIRED` | **нетерминальный** | Срок действия токена установки истёк, токен перевыпускается: интеграция уходит в `DEGRADED` и возвращается в `ACTIVE` сама. Терминальным становится только после исчерпания попыток обновления |
| `INTEGRATION_REPO_ACCESS_LOST` | терминальный | Репозиторий выведен из области установки |
| `INTEGRATION_RATE_LIMITED` | **временный** | Исчерпан лимит обращений к провайдеру |

**Исчерпание лимита провайдера классифицируется как временный отказ, а не как отказ в правах.**
Разница видна сразу: временный отказ повторяется по расписанию и не гасит интеграцию, отказ в
правах отправляет клиента переустанавливать приложение, которого он не ломал.

### 3.9 Artifact

Проекция образа, только на чтение. Ключ — digest.

| Поле | Тип | Описание |
|---|---|---|
| `digest` | string | Каноническая ссылка. Единственное, чем адресуется образ |
| `repository` | string | |
| `size_bytes` | int | |
| `build_id` | UUID | |
| `signature_status` | enum | `SIGNED` \| `UNSIGNED` \| `FAILED` |
| `sbom_ref` | string | Состав, приложен как связанный артефакт |
| `base_image_ref` | string | |
| `created_at` | timestamp | |

**Digest невоспроизводим пересборкой.** Отсюда следует: реестр является хранилищем
последней копии на всю глубину отката, а сборщик мусора не удаляет digest, на который
ссылается достижимый релиз.

который молча гасит боевой сайт, — худшая из возможных реализаций защиты от расходов.

|---|---|

| `BUDGET_ENFORCEMENT_UNSUPPORTED` | Запрошенный режим не поддерживается планом проекта или доступной телеметрией расходов |

**Полное наполнение упирается во внешний блокер 0.5** — фактическое потребление и расчёт
стоимости приходят из биллинга Beget. В Э1 замораживается **форма ресурса, а не срок
наполнения**: метод, принимающий потолок расходов и не имеющий читателя, — тот же класс, за
который в первом раунде удалён режим выделенного балансировщика. Клиент включает защиту,
получает успех и узнаёт о её отсутствии по счёту.

## 4. Статусы и машины состояний

### 4.1 Application

`PROVISIONING` → `ACTIVE` ⇄ `DEGRADED` → `DELETING` → удалён.
Плюс `SUSPENDED` (по решению платформы, §4.11) и `FAILED` (провизионирование не удалось).

`DEGRADED` — хотя бы одно окружение или компонент не в норме, но приложение отвечает.

Проекция в общий каталог: `PROVISIONING → CREATING`, `ACTIVE|DEGRADED → RUNNING`,
`SUSPENDED → SUSPENDED`, `FAILED|DELETING → STOPPED`.

### 4.2 Environment

`PROVISIONING` → `ACTIVE` ⇄ `DEGRADED` → `DELETING`. Плюс `FAILED`.

### 4.3 Component

`PROVISIONING` → `ACTIVE` ⇄ `UPDATING` ⇄ `DEGRADED` → `DELETING`. Плюс `FAILED`.

Статус компонента — сводка по окружениям, в которых он включён.

### 4.4 Build

```
QUEUED → FETCHING → DETECTING → BUILDING → PUSHING → SIGNING → SUCCEEDED
   │         │          │           │          │         │
   └─────────┴──────────┴───────────┴──────────┴─────────┴──→ FAILED
   └─────────┴──────────┴───────────┴──────────────────────→ CANCELLED
```

Стадия `SIGNING` включает построение состава и подпись. `SUCCEEDED` требует **подтверждённого
чтения манифеста обратно по digest**: успешное завершение процесса сборки без этого успехом
не считается.

Отмена возможна до `PUSHING`. После публикации отменять нечего — артефакт уже существует.

### 4.5 Deployment

```
QUEUED → RELEASING → DEPLOYING → ACTIVE → SUPERSEDED
   │         │           │
   └─────────┴───────────┴──→ FAILED
   └─────────┴───────────┴──→ CANCELLED
```

`RELEASING` — выполняется команда релиза: `Component.release_command`, переопределяемая в
`ComponentEnvironmentConfig.release_command_override`. Команда не задана — стадия проходится
мгновенно.

Семантика стадии: **один запуск на релиз**, до переключения трафика, в **том же образе**, с
**теми же переменными и секретами**, что у релиза, со **своим предельным сроком** (отдельным от
срока раската). Журнал — `Deployment.release_log_ref`, читается тем же способом, что журнал
сборки.

Отказ команды релиза (`RELEASE_COMMAND_FAILED`) и превышение предельного срока
(`RELEASE_COMMAND_TIMEOUT`) переводят релиз в `FAILED` **до** раската: **предыдущий релиз
остаётся `ACTIVE`, трафик не переключается**. В этом весь смысл отдельной стадии — неудачная
миграция не оставляет половину флота на новой схеме, а вписанная в стартовую команду миграция
выполняется столько раз, сколько реплик.

Команда релиза выполняется на **каждом** релизе, включая продвижение и откат (§6): одинаковое
поведение на всех путях дороже экономии одного запуска, а откат без обратной миграции — и вовсе
типовой сценарий. Идемпотентность команды — ответственность клиента; платформа её не угадывает.

Время команды релиза учитывается отдельной статьёй потребления — «время команды релиза»: это
работающий процесс, и прятать его в стоимость раската значит скрывать от клиента, за что он
платит.

Отказ раската **не трогает предыдущий релиз**: он остаётся `ACTIVE`. Автоматического отката
нет — он скрыл бы ошибку новой версии.

### 4.6 DomainBinding

`VERIFYING` → `PROVISIONING` → `ACTIVE` ⇄ `DEGRADED` → `DELETING`. Плюс `FAILED`.

`DEGRADED` — маршрут работает, но сертификат не продлевается. Отдельный статус нужен, чтобы
не гасить работающий адрес из-за проблемы с продлением.

### 4.7 ServiceBinding

`PENDING` → `ACTIVE` ⇄ `DEGRADED` → `DELETING`. Плюс `FAILED`.

`DEGRADED` — услуга недоступна или учётные данные отозваны. Приложение при этом продолжает
работать со старым значением: привязка не гасит рантайм.

### 4.8 GitIntegration

`PENDING_APPROVAL` → `ACTIVE` ⇄ `DEGRADED` → `REVOKED`.

`PENDING_APPROVAL` — установка запрошена, владелец организации ещё не одобрил. Состояние
**нетерминальное**: клиент видит, чего ждут и от кого, а не красную ошибку. `DEGRADED` —
интеграция жива, но временно не обслуживает: исчерпан лимит обращений к провайдеру
(`INTEGRATION_RATE_LIMITED`) либо не удалось обновить токен. Возврат в `ACTIVE` автоматический.
`REVOKED` — терминальное: установка удалена у провайдера либо токен истёк без возможности
обновления. Вывод отдельного репозитория из области установки интеграцию не отзывает — он
делает недоступным конкретный источник (`INTEGRATION_REPO_ACCESS_LOST`).

Переход в `REVOKED` **не гасит работающие релизы**: ломается доставка нового кода, а не
работающий сайт. Автоматический деплой по событию push останавливается, ручной деплой из
`UPLOAD` остаётся доступен.

### 4.9 Budget

`OK` → `WARNING` → `EXCEEDED` → `ENFORCED`. Возврат в `OK` — при поднятии потолка или начале
нового расчётного периода.

`WARNING` — пройден очередной порог из `thresholds`. `EXCEEDED` — потолок пройден при
`enforcement = NOTIFY`: платформа уведомляет и ничего не останавливает. `ENFORCED` — потолок
пройден при ограничивающем режиме: применены ограничения соответствующего режима.

Боевой сайт продолжает работать во всех состояниях бюджета. Единственный способ остановить
его расходами — `overdraft_policy = STOP_ALL` у плана проекта, и это отдельное решение
клиента.

### 4.10 Operation

`QUEUED` → `RUNNING` → `SUCCEEDED` \| `FAILED` \| `CANCELLED`.

Повторный запуск задания после падения исполнителя **не создаёт новую операцию**: аренда
истекает, задание возвращается в очередь, та же операция продолжается.

### 4.11 SUSPENDED — у приостановки есть актор

Переход в `SUSPENDED` обязан нести: кто (система защиты от злоупотреблений, биллинг,
поддержка, владелец), по какому сигналу, видимый клиенту текст с причиной и процедуру
оспаривания. Приостановка без актора — состояние, из которого никто не умеет выводить.

## 5. Инварианты

### 5.1 Выражаются на уровне БД, а не проверками в коде

| Инвариант | Механизм |
|---|---|
| Один активный раскат на пару (компонент, окружение) | Частичный уникальный индекс по паре при статусе `QUEUED`/`RELEASING`/`DEPLOYING` |
| Имя компонента уникально в приложении | Уникальный индекс |
| Имя окружения уникально в приложении | Уникальный индекс |
| Ровно одно окружение по умолчанию | Частичный уникальный индекс по приложению при `is_default = true` |
| Полное доменное имя уникально среди живых привязок | Частичный уникальный индекс |
| Ключ переменной уникален в своей области | Уникальный индекс по области |
| Повторный запрос с тем же ключом идемпотентности | Уникальный индекс по паре проект и ключ, возврат той же операции |
| Одна привязка на пару (окружение, вид услуги, префикс) | Уникальный индекс |
| Ресурс, релиз, операция, задание и события — одной транзакцией | Один writer-TX плюс transactional outbox |

Подробности схемы — `07`.

### 5.2 Неизменяемость

`Build` неизменяем после завершения: снимок источника, сборщик, план, версия базового слоя,
журнал и digest не меняются. `Deployment` неизменяем: digest и ревизии не меняются, любое
изменение порождает новый релиз. История не переписывается ни при откате, ни при продвижении.

### 5.3 Форма компонентов общая для всех окружений

Различаться могут: значения переменных и секретов, привязки услуг, домены, число реплик,
размер, ветка источника, включённость компонента, а также узкий слой переопределений
(§7.3). **Не могут:** набор компонентов, их типы, имена.

Как только форма разъезжается, продвижение теряет смысл — вы получили два отдельных
приложения, только запутаннее. Кому нужна принципиально другая форма, заводит второе
приложение; это правильный ответ, а не недоработка.

### 5.4 Сборка не знает окружений, релиз знает

Отсюда напрямую следует продвижение: тот же digest, конфигурация целевого окружения, без
пересборки. Это единственная причина, по которой вся модель окружений принята.

## 6. Продвижение и откат

| Действие | Что создаётся | Пересборка | Скачивание образа | Команда релиза |
|---|---|---|---|---|
| Деплой нового коммита | Сборка → новый digest → релиз | Да, тёплый кэш | Только новые слои | Да |
| Продвижение окружение → окружение | Релиз в целевом окружении с **тем же** digest | Нет | Обычно нет | Да |
| Откат | Релиз на digest предыдущего успешного | Нет | Обычно нет | Да |
| Изменение конфигурации | Релиз с тем же digest, новой ревизией конфигурации | Нет | Нет | Да |

Столбец команды релиза — не украшение: она выполняется **на каждом** релизе, включая
продвижение и откат (§4.5), с переменными и секретами **целевого** окружения. Исключение для
отката выглядело бы экономным ровно до первого отката, требующего обратной миграции.
Идемпотентность команды — ответственность клиента; пустая команда проходится мгновенно.

Предыдущий релиз получает `SUPERSEDED`, а не удаляется. Глубина отката — «последние N
успешных релизов И не старше срока хранения»; оба условия обязательны, иначе хранилище
растёт монотонно.

Продвижение и откат **сверяют совместимость профиля возможностей кластера** до создания
релиза: образ, собранный под пул с пространствами имён пользователей, не должен молча
уехать на пул без них.

## 7. Разрешение конфигурации

### 7.1 Три уровня с непересекающимся владением

| Уровень | Владеет |
|---|---|
| Автоопределение | Всем, что выводится из репозитория |
| `beget.yaml` | Формой кода: компоненты, контекст, чем собирать, команда, порт, проба, размер, диапазон масштабирования |
| API и интерфейс | Правдой окружения: переменные, секреты, привязки, домены, реплики, окружения |

### 7.2 Порядок разрешения переменной

`COMPONENT` → `ENVIRONMENT` → `APPLICATION` → значение по умолчанию из манифеста.
Побеждает самый узкий уровень. Секреты существуют только на уровнях окружения и компонента.

Переменные от привязки услуги имеют `origin = SERVICE_BINDING` и **не редактируются вручную**:
их перезапись руками пережила бы ротацию ровно до первой смены пароля.

Платформа резервирует за собой `PORT` и префикс `BEGET_`.

### 7.3 Узкий слой переопределений формы

`run_command`, `release_command`, `port`, `health_check` и `size` можно переопределить через API
на паре (компонент, окружение). Значение из API выигрывает у манифеста.

Причина, по которой этот слой существует, несмотря на принцип непересекающегося владения:
без него единственный способ исправить неверно определённый порт — коммит в репозиторий,
а деплой репозитория без права записи становится неисправимым в принципе.

### 7.4 План сборки печатает источник каждого значения

```
Стек:      Go 1.24        (найден go.mod)
Сборщик:   buildpack      (Dockerfile не найден)
Команда:   ./server       (launch-процесс бэкпака)
Порт:      8080           (значение по умолчанию, приложение должно слушать $PORT)
Размер:    small          (по умолчанию)
Контекст:  /              (по умолчанию)
```

Провенанс значения закрывает половину обращений по «приложение не слушает порт» бесплатно —
клиент видит, откуда взялась цифра, ещё до того как что-то сломалось.

## 8. Манифест `beget.yaml`

Файл целиком опционален. Все поля, кроме `type`, имеют значения по умолчанию.

```yaml
version: 1
components:
  web:
    type: web                        # web | worker | static
    context: ./apps/api              # подкаталог монорепозитория, по умолчанию корень
    build:
      dockerfile: Dockerfile         # пусто → бэкпаки
      builder: auto                  # auto | dockerfile | buildpack — снимает неоднозначность
    run: ./server
    release: ./bin/migrate           # команда релиза: один запуск до переключения трафика
    port: 8080
    health: { path: /healthz }
    size: small
    scale: { min: 1, max: 3 }
    env: { NODE_ENV: production }    # только несекретные значения по умолчанию
  worker:
    type: worker
    context: ./apps/worker
    run: ./worker
    size: micro
  site:
    type: static
    context: ./apps/web
    build: { output_dir: dist }
    spa_fallback: true
```

Ни одного упоминания Kubernetes. `Procfile` поддерживается как дополнительный источник
команды запуска и команды релиза.

Поле `release` — команда релиза (§4.5): один запуск на релиз, до переключения трафика, в том же
образе и с теми же переменными и секретами, что у релиза. Отсутствие поля означает, что фазы
релиза нет, а не что она пустует. Для `worker` и `static` поле допустимо, но по умолчанию не
заполняется.

**Приоритет автоопределения** при отсутствии манифеста:
1. `Dockerfile` в контексте → сборка из `Dockerfile`;
2. иначе маркеры языка → бэкпаки;
3. несколько маркеров разных языков в одном контексте → неоднозначность, требуется явное
   указание сборщика или контекста; отказ `SOURCE_AMBIGUOUS` с перечнем найденного.

Секрет в манифесте отвергается валидацией: `SECRET_IN_MANIFEST` с именем ключа.

## 9. Профиль возможностей кластера

Не клиентский ресурс, но часть модели: от него зависит, где можно разместить приложение.

| Поле | Описание |
|---|---|
| `cluster_id` | |
| `kubernetes_version`, `containerd_version`, `runc_version`, `kernel_version` | |
| `user_namespaces` | Поддерживаются ли |
| `runtime_classes` | Доступные классы рантайма |
| `region_id`, `zone_ids` | |
| `capacity` | Свободная ёмкость |

Оператор публикует профиль в сигнале жизни. Создание, продвижение и откат сверяют
совместимость **до** создания релиза. **Однородность тенантского пула по этим параметрам —
инвариант размещения:** смешанный пул означает, что одно и то же приложение ведёт себя
по-разному в зависимости от того, на какой узел попало, — а это прямой удар по
воспроизводимости опыта.
