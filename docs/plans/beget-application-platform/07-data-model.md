# 07. Схема данных

Таблицы, ключи, индексы и инварианты уровня базы. Правило простое: **инвариант внутри одной
базы выражается конструкцией базы, а не проверкой в коде.** Последовательность «прочитал —
решил — записал» проигрывает гонку всегда; вопрос только в том, когда это заметят.

---

## 1. Общие соглашения

| Аспект | Решение |
|---|---|
| Первичные ключи | UUID v4, они же публичные идентификаторы |
| Порядок строк | UUID **не задаёт порядок**: он случаен, поэтому «меньший идентификатор» не означает «поставлен раньше». Там, где порядок значим (`work_task`, `outbox`), рядом с `id` живёт `seq` — монотонный числовой ключ порядка (`bigint`, генерируемый базой). Внешним идентификатором остаётся UUID; `seq` наружу не выходит |
| Время | С часовым поясом, хранится с микросекундами, в ответе усекается до секунд |
| Мягкое удаление | Не используется. Удалённое удаляется; история живёт в отдельных таблицах истории |
| Перечисления | Отдельным типом, не свободной строкой |
| Денормализация | Только вычисляемые поля для чтения, помеченные как таковые |
| Внешние ключи | Внутри базы — обязательны. За границу услуги — невозможны, там ссылка по идентификатору плюс проверка на пути запроса |

## 2. Таблицы

### 2.1 Ядро

| Таблица | Ключ | Существенное |
|---|---|---|
| `application` | `service_id` | `project_id`, `region_id`, `name`, `default_environment_id`, статус |
| `environment` | `id` | `application_id` → каскад, `name`, `dns_label`, `tier`, `is_default`, `quota_share_percent`, `auto_deploy`, `expires_at`, `cluster_id` |
| `component` | `id` | `application_id` → каскад, `name`, `type`, `dns_label`, форма, `spec_revision`, `release_command` |
| `component_env_config` | (`component_id`, `environment_id`) | Переопределения, `release_command_override`, `enabled`, `config_revision` |
| `source` | `component_id` | Тип, адрес, ветка, контекст, вид учётных данных, ссылки на хранилище секретов, `access_status` |
| `git_integration` | `id` | **Владелец — аккаунт:** `account_id`, `provider` (`GITHUB`), `installation_id`, `account_login`, `status`, `secret_ref`, `expires_at`, `created_at` |

`cluster_id` у окружения — **внутреннее поле, наружу не выходит**: оно отвечает на вопрос
«на каком кластере это живёт», который задаёт каждое размещение, каждое продвижение со
сверкой профиля возможностей и каждый разбор инцидента. Без колонки этот вопрос приходится
задавать кластерам, то есть тогда, когда они уже недоступны.

`git_integration` принадлежит **аккаунту, а не проекту**: установка ставится на организацию
у провайдера и переиспользуется всеми проектами аккаунта. Статусы —
`PENDING_APPROVAL` → `ACTIVE` ⇄ `DEGRADED` → `REVOKED`; `PENDING_APPROVAL` (одобрение
владельцем организации ещё не получено) **нетерминален** и ожидание не является отказом.
Коды отказа — `INTEGRATION_PENDING_APPROVAL`, `INTEGRATION_REVOKED`,
`INTEGRATION_TOKEN_EXPIRED`, `INTEGRATION_REPO_ACCESS_LOST`, `INTEGRATION_RATE_LIMITED`.
Исчерпание лимита провайдера классифицируется как **временный** отказ, а не как отказ в
правах: перепутать эти два — значит показать клиенту «доступ отозван» там, где надо просто
подождать.

`release_command` компонента — необязательная изменяемая строка; переопределение на
окружение живёт в `component_env_config.release_command_override`. Для компонентов типа
`WORKER` и `STATIC` команда допустима, но по умолчанию пуста.

### 2.2 Сборки и релизы

| Таблица | Ключ | Существенное |
|---|---|---|
| `build` | `id` | `application_id`, `component_id`, снимок источника, план, сборщик, базовый образ, инициатор, статус, стадия, `cpu_seconds`, digest, отказ |
| `artifact` | `digest` | Репозиторий, размер, `build_id`, статус подписи, ссылка на состав |
| `deployment` | `id` | `environment_id`, `component_id`, `build_id`, `image_digest`, `cluster_id`, три ревизии (форма, конфигурация, рендер), причина, исходный релиз, `release_log_ref`, статус, отказ |

`cluster_id` у релиза — **снимок фактического кластера на момент релиза**, а не ссылка на
текущее значение у окружения: окружение может переехать, а вопрос «где именно исполнялся
этот релиз» задаётся спустя недели, при разборе.

`release_log_ref` — ссылка на журнал команды релиза. Команда выполняется **один раз на
релиз, до переключения трафика**, тем же образом и с теми же переменными и секретами, что
и рабочий процесс, со своим предельным сроком. Состояния релиза — `QUEUED` → `RELEASING` →
`DEPLOYING` → `ACTIVE`; отказ (`RELEASE_COMMAND_FAILED`, `RELEASE_COMMAND_TIMEOUT`) **не
трогает предыдущий релиз**, трафик не переключается. Команда выполняется на **каждом**
релизе, включая продвижение и откат, — за идемпотентность отвечает клиент. Потребление
пишется отдельной статьёй «время команды релиза».

### 2.3 Конфигурация

| Таблица | Ключ | Существенное |
|---|---|---|
| `variable` | `id` | Область, идентификаторы области, `key`, `is_secret`, значение либо ссылка на хранилище, `origin`, версия |
| `service_binding` | `id` | `environment_id`, `component_id`, вид услуги, `target_service_id`, префикс, ссылка на учётные данные, статус |
| `domain_binding` | `id` | `environment_id`, `component_id`, `fqdn`, вид, владелец DNS, проверка, статус, статус и срок сертификата |

### 2.4 Механика

| Таблица | Ключ | Существенное |
|---|---|---|
| `operation` | `id` | Область, тип и идентификатор ресурса, действие, статус, стадия, актор, ключ идемпотентности, отказ, ссылка на результат |
| `work_task` | `id` | `seq`, тип, состояние, полезная нагрузка, приоритет, ключ раздела, номер попытки, владелец аренды, срок аренды, `operation_id` |
| `outbox` | `id` | `seq`, тема, ключ раздела, полезная нагрузка, `sent_at`, номер попытки |
| `audit_log` | `id` | Только на добавление: актор, действие, ресурс, время, результат, признак доступа поддержки |
| `usage_record` | `id` | Проект, приложение, окружение, компонент, статья, объём, период |
| `project_platform_plan` | `project_id` | Тариф, признак пробного, включённая квота, потолки, политика овердрафта |
| `budget` | `project_id` | `limit_amount`, `currency`, `enforcement`, `thresholds` (проценты уведомлений), `current_spend`, `forecast`, `status` |
| `cluster` | `id` | Регион, зоны, профиль возможностей, ёмкость, время последнего сигнала |

`seq` в `work_task` и `outbox` — монотонный числовой ключ порядка (`bigint`, генерируемый
базой), отдельный от `id`. Он существует ровно затем, чтобы предикат «нет недоставленного
предшественника» опирался на порядок постановки, а не на случайное значение UUID (§4.1).

`budget` — уровень **проекта**, одна строка на проект. `enforcement` принимает `NOTIFY`,
`STOP_NON_PRODUCTION` или `STOP_METERED`; `STOP_METERED` останавливает сборки, непрод и
исходящий трафик, но **не боевой сайт**. Остановка production возможна **только** через
`overdraft_policy = STOP_ALL` у плана проекта — иначе бюджет превращается в способ уронить
себе продажи опечаткой в потолке. Коды отказа — `BUDGET_LIMIT_TOO_LOW`,
`BUDGET_ENFORCEMENT_UNSUPPORTED`.

Полное наполнение бюджета упирается во внешний блокер 0.5 (биллинг Beget): без фактических
расходов и прогноза заполнять нечем. В Э1 замораживается **форма ресурса, а не срок
наполнения**. Метод без модели недопустим — это тот же класс, за который в первом раунде
удалён режим выделенного балансировщика: клиент выставляет потолок, получает успех и уверен,
что защищён, а при исчерпании не происходит ничего.

## 3. Инварианты уровня базы

| Инвариант | Конструкция |
|---|---|
| Один активный раскат на пару (компонент, окружение) | Частичный уникальный индекс по паре при статусе в множестве незавершённых |
| Ровно одно окружение по умолчанию | Частичный уникальный индекс по приложению при `is_default` |
| Имя компонента уникально в приложении | Уникальный индекс |
| Имя окружения уникально в приложении | Уникальный индекс |
| Метка DNS глобально уникальна | Уникальный индекс, включая карантин освобождённых |
| Полное доменное имя уникально среди живых | Частичный уникальный индекс |
| Ключ переменной уникален в области | Уникальный индекс по области |
| Одна привязка на (окружение, вид услуги, префикс) | Уникальный индекс |
| Ключ идемпотентности уникален в проекте | Уникальный индекс, при конфликте возвращается существующая операция |
| Один бюджет на проект | Первичный ключ по `project_id`; повторная установка — обновление существующей строки, а не вторая |
| Порядковый номер очереди монотонен | `bigint` с генерацией базой (`identity`); запись значения извне запрещена, иначе порядок перестаёт быть порядком |
| Взаимоисключение полей размещения и типа | Ограничение-проверка |
| Ссылка на релиз ведёт на существующий артефакт | Внешний ключ на `artifact` с запретом удаления |
| Компонент нельзя удалить при активном релизе | Внешний ключ с запретом удаления |
| `scale.min ≤ scale.max` | Ограничение-проверка |
| Секрет не может быть в области приложения | Ограничение-проверка |

**Смена владения атомарна.** Захват задания — одним оператором обновления с условием на
текущее состояние и владельца аренды, а не «выбрал, проверил, обновил». Ноль изменённых
строк означает «не наш», и это нормальный исход, а не ошибка.

## 4. Очередь заданий

### 4.1 Выборка

Одним запросом, с блокировкой выбранной строки и пропуском занятых. В условии выборки —
всё, что должно соблюдаться, а не только сортировка:

1. состояние — ожидает, срок аренды истёк или отсутствует;
2. номер попытки меньше предела (отравленные не выдаются);
3. **число активных заданий этого аккаунта меньше его потолка** — справедливость очереди
   выражается здесь, а не в коде исполнителя;
4. **нет недоставленного предшественника того же раздела с меньшим порядковым номером
   `seq`** — порядок внутри одного объекта сохраняется между партиями и между экземплярами;
5. порядок — приоритет, затем `seq`.

Обязателен частичный индекс по паре (ключ раздела, `seq`) для недоставленных строк: без
него условие на предшественника превращает выборку в полный просмотр.

### 4.2 Почему условие на предшественника нужно именно в выборке

Группировка на стороне применения выглядит решением, но течёт: сортировка по номеру попытки
уводит подтянутого предшественника в другую партию, и порядок между партиями теряется. Это
не гипотеза — тот же класс дефекта у нас уже приводил к тому, что отзыв доступа применялся
раньше выдачи и запись выживала.

**И почему предшественник ищется по `seq`, а не по идентификатору.** UUID v4 случаен:
«меньший идентификатор» не означает «поставлен раньше». Предикат на идентификаторе
выглядит работающим — он честно ограничивает выборку одной строкой раздела, — но выбирает
из раздела **случайную** строку вместо самой ранней. Форма проверки есть, содержания нет:
ни один тест на «в партии не больше одной строки раздела» такого не поймает. Порядок обязан
опираться на значение, которое база выдаёт монотонно, — отсюда `seq` и запрет подставлять
его извне.

### 4.3 Осознанный размен

Устойчиво неудачный предшественник блокирует **свой** раздел; остальные продолжают идти.
Радиус — один объект. Взамен получаем сохранение порядка между экземплярами. Обязателен
сигнал на возраст самой старой недоставленной строки — иначе застрявший раздел молчит.

## 5. Транзакционность

**Одной транзакцией записи:** строка ресурса, строка операции, строки заданий, строки
исходящей очереди, запись в журнал действий.

Ни одно событие не отправляется до фиксации транзакции. Отправка «сразу, а строку потом» —
источник расхождений, которые ловятся не на тестах, а на проде.

---

## 6. Учёт потребления

Записи потребления пишутся **отдельно от рабочего пути**, из наблюдаемых источников:
процессорное время и память — по данным наблюдаемости, минуты сборки — из завершённых
сборок, время команды релиза — из завершённых заданий релиза, исходящий трафик — со шлюза,
объём журналов — с приёмника.

Записи с инициатором «платформа» помечаются и **не попадают в счёт клиента**: пересборка
базового слоя инициирована нами.

Источником счёта является таблица потребления, а не хранилище наблюдаемости: хранилище
метрик имеет срок хранения и прореживание, а счёт должен быть воспроизводим спустя месяцы.

## 7. История и подрезка

| Что | Правило |
|---|---|
| Релизы | Хранятся все; подрезаются по **обоим** условиям: старше срока хранения **и** вне последних N успешных |
| Сборки | Так же; журнал сборки — по сроку хранения тарифа |
| Артефакты | Не удаляются, пока на них ссылается достижимый релиз |
| Операции | По сроку хранения, дольше релизов |
| Журнал действий | Отдельный, длинный срок хранения; на добавление |
| Потребление | До окончания расчётного периода плюс срок разбора спорных случаев |

---

## 8. Порядок миграций

Расширение → перенос → сжатие. Каждая фаза отдельно и самостоятельно работоспособна.

1. **Расширение** — новые таблицы и столбцы добавляются как необязательные, старый код
   продолжает работать.
2. **Перенос** — данные заполняются, новый код начинает писать в новое и читать из нового,
   продолжая понимать старое.
3. **Сжатие** — старое удаляется отдельным выпуском, после того как ни один экземпляр
   старого кода не работает.

**Применённая миграция не редактируется.** Исправление — только новой миграцией.

**Изменение схемы при живом трафике** обязано отвечать на вопрос, что произойдёт, когда
одновременно работают старая и новая версии кода. Если ответ «ничего хорошего» — фаза
разбита неверно.

---

## 9. Отображение внутренних состояний наружу

Внутренние идентификаторы, если они появятся, **не выходят наружу**: ни в ответе, ни в
ошибке, ни в журнале действий, ни в метке, доступной клиенту. Отображение внутреннего
состояния во внешнее делает фасад; обратное отображение — единственное место, где внешний
идентификатор превращается во внутренний.

## 10. Аварийное восстановление

| Что теряем | Последствие | Требование |
|---|---|---|
| База control plane | Платформа не принимает изменений; работающее продолжает работать, потому что намерение материализовано в кластерах | Восстановление на момент времени; проверенная процедура |
| Блобы реестра | Деградация **не сразу, а часами**, по мере перезапусков и замен узлов; все точки отката превращаются в висячие ссылки, потому что пересборка даёт другой digest | Версионирование и репликация хранилища объектов |
| Хранилище секретов | **Невосстановимая потеря данных клиента**: значение только на запись, копии у клиента нет by design | Регулярно **проверяемая восстановлением** копия; материал распечатывания хранится отдельно от копии |
| Кластер целиком | Приложения этого кластера недоступны | Пересоздание из намерения control plane |

**Актив, который нельзя потерять при изменениях:** якорные объекты в кластерах содержат
намерение, то есть control plane частично восстановим из рантайма. Любое изменение,
делающее якорь неполным, лишает нас этого свойства.

Копия, которая ни разу не восстанавливалась, копией не является.
