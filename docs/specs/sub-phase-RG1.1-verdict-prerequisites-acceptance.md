## Обзор

Первая подитерация исправляет три наблюдаемых свойства проверок продукта: доказательство скана сохраняет конфигурацию при несозданной предпосылке, интеграционный шаг CI доставляет читателю третий исход, а проверка make-команд учитывает вызовы под `stand-up.sh` в действительном каталоге исполнения. Результат предназначен разработчику, запускающему эти команды, и читателю CI. Каждая задача ниже имеет собственные сценарии и предикат завершения; другие задачи `release:gates` относятся к последующим подитерациям.

## Условия воспроизведения и наблюдаемые величины

- Каждый сценарий использует отдельную временную копию входов. Содержимое `trivy.yaml` до запуска сохраняется как байтовый эталон; на грязном файле эталон берётся из рабочего файла, не из индекса Git. Параллельные редакторы одного файла не являются предусловием этих проб.
- Отрицательный сценарий называет законного близнеца и один изменённый входной факт. Код, аннотация и изменение файла являются результатами этого факта, а не дополнительными изменениями фикстуры.
- «Вход CI интеграции» означает исполняемую команду соответствующего шага `.github/workflows/ci.yaml` с `SVC=vpc`, `GITHUB_ACTIONS=true`, из корня продукта, под `bash --noprofile --norc -eo pipefail`. Она запускает `make test-integration`. Доставка третьего исхода проверяется через эту границу, а не одним прямым вызовом классификатора.
- Полный путь кодов различает границы: тестовый бинарь → дочерний `go test` → `xargs`/конвейер → классификатор → make → CI. При отказе дочернего `go test` с кодом `1` либо `2`, `xargs` передаёт дальше `123`; успешный дочерний код `0` даёт `0`. Код `75` тестового бинаря pgtest сам по себе не проходит через эти оболочки: третий исход восстанавливается классификатором по захваченному сообщению производителя.
- Для проверки доставки допускается воспроизводимая подстановка результата дочернего `go test` до входа в настоящий `xargs`. Рецепт make, классификатор и вызывающий шаг берутся из проверяемого дерева. Захват настоящего `pgtest`, строящие фикстуры и обязательные зависимости названы в [ведомости держателей RG1.1](../changes/release-gates/rg1.1-holders.md); захват производителя обязателен до объявления TDD RED доставки. Самостоятельно придуманная строка не служит доказательством. Такой опыт подтверждает доставку результата, а не успешный запуск реальной БД.
- «Гейт make-команд» означает `TestEveryCIMakeCommandResolves`, запускаемый из корня продукта командой `go test ./services/storage/tools -run '^TestEveryCIMakeCommandResolves$' -count=1 -v`. В изолированных пробах этому же проверяющему предоставляется временный корпус workflow и Makefile. Подъём стенда для чтения команд не требуется.
- Единица переписи make-гейта — проверяемая запись `(workflow, job, step, каталог, цель)`, включая каждое разрешённое значение уже поддерживаемого цикла. Счётчики «всего» и «под stand-up» используют одну единицу; несколько целей одной shell-команды дают несколько записей. Наличие строки с командой в комментарии не создаёт запись. Такая единица не называется числом физических строк shell.

У каждого самостоятельного варианта есть устойчивый суффикс и отдельный subtest в ведомости держателей. Она владеет координатами будущих проверок, их командами и построением Given; приёмка владеет наблюдаемым результатом. Планируемая координата не означает, что тест или фикстура уже существуют.

## S1 — сохранность конфигурации при доказательстве скана (#2175)

### Сценарий 01: законный прогон возвращает исходные байты

**ID:** RG1.1-01

**Given** во временной копии продукта `trivy.yaml` совпадает с индексом Git и сохранён его байтовый эталон.
**And** `trivy` и остальные предпосылки действующего доказательства доступны; контрольные сканы завершаются ожидаемыми исходами.

**When** из корня продукта запускается `bash deploy/scripts/assert-scan-stubs-hide-nothing-inject.sh`.

**Then** команда завершается кодом `0`.
**And** исполнены действующие пробы законной заглушки, гасящей заглушки, соседнего гейта покрытия, заглушки без предмета и пустого списка заглушок; число исполненных утверждений больше нуля.
**And** после завершения `trivy.yaml` побайтово равен эталону, а `git status --porcelain -- trivy.yaml` пуст.
**And** восстановление проверяется после завершения процесса, включая обработку его выхода.

### Сценарий 02: отсутствие trivy не меняет чистый файл

**ID:** RG1.1-02

**Given** выполнены предусловия RG1.1-01.
**And** единственное отличие — `trivy` отсутствует в `PATH`; необходимые shell-утилиты остаются доступны.

**When** запускается та же команда доказательства.

**Then** команда завершается кодом `2` и явно сообщает, что `trivy` не найден и доказательство не выполнено.
**And** после выхода `trivy.yaml` побайтово равен эталону; `git status --porcelain -- trivy.yaml` пуст.
**And** отсутствие исполненных сканирующих проб не объявляется успешным доказательством.

### Сценарий 03: обе полосы сохраняют уже имевшуюся локальную правку

**ID:** RG1.1-03

**Given** законная копия RG1.1-01 отличается ровно содержимым `trivy.yaml`: перед запуском к файлу добавлен допустимый YAML-комментарий `# RG1.1 local change`, и этот файл служит байтовым эталоном.

**When** в отдельных одинаковых копиях исполняются полоса с доступным `trivy` и её близнец без `trivy`, как в RG1.1-01 и RG1.1-02; каждая команда затем повторяется на той же своей копии.

**Then** коды обоих запусков в первой полосе — `0`, во второй — `2`.
**And** после каждого завершения файл равен исходному грязному эталону, комментарий сохранён.
**And** состояние и diff только этого пути равны состоянию до запуска: доказательство не добавляет своей правки и не убирает правку разработчика.

### Сценарий 04: провал утверждения после изменения конфигурации сохраняет файл

**ID:** RG1.1-04

**Given** выполнены предусловия RG1.1-01 и есть исходный байтовый эталон.
**And** единственное отличие — один вызов проверяемого сканирующего гейта после внесения инъекции возвращает неправильный для этой пробы код `2` вместо ожидаемого `1`; остальные результаты сохранены.

**When** исполняется действующее доказательство целиком.

**Then** доказательство завершается кодом `1`, называет провалившееся утверждение и полученный код `2`.
**And** после выхода `trivy.yaml` побайтово равен исходному эталону.
**And** этот опыт не засчитывается как успешная проверка сканера: подстановка проверяет сохранность при отказе.

**DoD S1:** исполняемая регрессия держит RG1.1-01…04, отсутствие инструмента воспроизведено отдельно от отказа утверждения; исходный дефект даёт падение проверки сохранности. Полоса с настоящим `trivy` сохраняет существующую проверку смыслов заглушек. В свидетельстве названы исполненные и неисполненные полосы и состояние файла после выхода.

## S2 — третий исход доезжает через make до читателя CI (#2580)

### Сценарий 05: Postgres недоступен, CI получает отдельную аннотацию

**ID:** RG1.1-05

**Given** выбран непустой набор integration-пакетов `vpc`.
**And** захваченный результат дочернего `go test` содержит код `1` и сообщение настоящего pgtest о недоступности Postgres; журнал и код относятся к одному запуску, построенному фикстурой `F-PG-CAPTURE` из ведомости держателей.
**And** законный близнец RG1.1-06 отличается доступностью Postgres; успешный результат является следствием доступной зависимости.

**When** выполняется вход CI интеграции.

**Then** `xargs`/конвейер передаёт `123`, классификатор возвращает `75`, `make` и шаг завершаются кодом `2`.
**And** в захваченном выводе исполняемого шага есть ровно одна GitHub Actions error-аннотация, чей заголовок содержит `УСЛОВИЕ НЕ СОЗДАНО`.
**And** аннотация объясняет, что Postgres для integration не поднялся, прогон недействителен и требует повторения после устранения причины.
**And** вывод не засчитывает пробы затронутого запуска в успешную верификацию, включая строки успеха, появившиеся до отказа предпосылки.
**And** аннотация произведена выполненным путём, а не комментарием, строкой в фикстуре вызывающего или ожидаемым текстом теста.

### Сценарий 06: успешный непустой прогон остаётся успешным

**ID:** RG1.1-06

**Given** выбран тот же непустой набор пакетов, Postgres доступен и пробы завершаются успешно с кодом производителя `0`.

**When** выполняется вход CI интеграции.

**Then** классификатор, `make` и шаг завершаются кодом `0`.
**And** аннотации `УСЛОВИЕ НЕ СОЗДАНО` нет.
**And** вывод позволяет установить непустой объём выбранных пакетов.

### Сценарий 07: обычный отказ не превращается в недоступность Postgres

**ID:** RG1.1-07

**Given** есть отказавший результат дочернего `go test` с кодом `1` и журналом RG1.1-05.
**And** единственное отличие от RG1.1-05 — в журнале нет признака недоступности Postgres; ненулевой код сохранён.

**When** выполняется вход CI интеграции.

**Then** цепочка `go test → xargs/конвейер → классификатор → make → CI` даёт `1 → 123 → 123 → 2 → 2`.
**And** аннотации `УСЛОВИЕ НЕ СОЗДАНО` нет; исход остаётся отказом без доказанного третьего исхода.
**And** в отдельном варианте этой же проверки меняется только код дочернего `go test` на `2`: цепочка даёт `2 → 123 → 123 → 2 → 2` и также не создаёт аннотацию недоступности Postgres. Прямой вызов классификатора с входными `1` или `2` здесь не заявляется.

### Сценарий 08: локальный вызов не печатает управляющую аннотацию CI

**ID:** RG1.1-08

**Given** результат производителя и непустой набор пакетов те же, что в RG1.1-05.
**And** единственное отличие — `GITHUB_ACTIONS` не задан.

**When** разработчик из корня продукта запускает `SVC=vpc make test-integration`.

**Then** дочерний `go test` возвращает `1`, `xargs`/конвейер — `123`, классификатор — `75`, команда make — `2`.
**And** человек получает текст `УСЛОВИЕ НЕ СОЗДАНО` с причиной недоступности Postgres.
**And** строк управляющего синтаксиса GitHub Actions `::error` нет.

### Сценарий 09: признак в журнале не перекрашивает успешный код

**ID:** RG1.1-09

**Given** вход классификации совпадает с RG1.1-05 по журналу, включая признак недоступности.
**And** единственное отличие — код производителя равен `0`; это защитная проба контракта классификации, не утверждение о возможном успешном подъёме недоступной БД.

**When** выполняется вход CI интеграции с этим подставным результатом.

**Then** классификатор, make и шаг возвращают `0`, аннотации `УСЛОВИЕ НЕ СОЗДАНО` нет.
**And** результат этой защитной пробы не используется как свидетельство работоспособности БД.

### Сценарий 10: пустой отбор и отсутствующий журнал не дают доказательства успеха

**ID:** RG1.1-10

**Given** законный вход RG1.1-06 и два независимых отрицательных варианта.

**When** в первом варианте единственное отличие — перечислитель пакетов успешно возвращает пустой список всех пакетов сервиса.

**Then** `make` и вход CI возвращают `2`; вывод называет пустой обход, а аннотации недоступности Postgres нет.

**When** во втором варианте прямой CLI классификатора вызывается с аргументами `1` и `missing.log`, где единственное отличие от существовавшего журнала — файл отсутствует.

**Then** классификатор возвращает `2` и сообщает о требуемом файле вывода; аннотации недоступности Postgres нет.
**And** ни один вариант не считается успешным прогоном integration. Случай «сервис осмотрен, но integration-пакетов у него нет» этим сценарием не переопределяется.

**DoD S2:** RG1.1-05…10 держатся исполняемыми пробами, включая захват выхода действующего CI-входа под его shell-флагами. Возврат исходного дефекта убирает ожидаемую аннотацию и роняет регрессию. Исполняемый шаг не содержит недостижимого ожидания `75` от make; комментарии описывают фактического производителя различения. Успех подставной доставки и результат настоящих integration-тестов учитываются раздельно.

## S3 — команды под stand-up проверяются в своём каталоге (#2550)

### Сценарий 15: относительный каталог разрешается от рабочего каталога шага

**ID:** RG1.1-15

**Given** временный workflow задаёт `working-directory: services/storage` и вызывает `../../.github/scripts/stand-up.sh --label "RG1.1 directory" --dir ../../deploy -- make helm-deps`; `deploy/Makefile` объявляет цель.

**When** исполняется гейт, а в независимых вариантах тот же рабочий каталог задаётся через job defaults и workflow defaults вместо step-поля.

**Then** во всех вариантах `go test` возвращает `0`, запись разрешается в `deploy` и учитывается как вызов под stand-up.
**And** в отрицательном близнеце каждого варианта меняется только цель на `rg1-nonexistent-target`: `go test` возвращает `1`, диагностика называет `deploy`.

### Сценарий 16: каталог без Makefile даёт явный отказ

**ID:** RG1.1-16

**Given** законный корпус RG1.1-11.
**And** единственное отличие — аргумент `--dir` заменён на существующий каталог `rg1-empty-dir`, в котором Makefile отсутствует.

**When** исполняется гейт.

**Then** `go test` возвращает `1`, находка называет workflow, каталог `rg1-empty-dir` и отсутствие Makefile.
**And** запись остаётся в обоих счётчиках; недоступный предмет проверки не считается успешно разрешённой целью.

### Сценарий 17: перепись текущего дерева увеличилась и сохраняет прежний охват

**ID:** RG1.1-17

**Given** один зафиксированный непустой корпус исполняемых workflow продукта, содержащий команды под stand-up и обычные make-команды.
**And** на этом же корпусе сохранена перепись исходного reader до исправления и независимый перечень действительных команд под stand-up с каталогом и целью.

**When** исполняется исправленный гейт на том же корпусе.

**Then** напечатаны обе величины — общее число проверенных записей и число записей под stand-up; вторая больше нуля и равна независимому перечню.
**And** общий охват увеличился ровно на пропущенные прежде записи обёртки; прежние записи сохранились без удвоения.
**And** каждая добавленная запись проверена против каталога фактического исполнения команды.
**And** обычные make-команды, в том числе действующие формы с `-C`, циклом сервисов, перенаправлением вывода и переменными `NAME=value`, сохраняют свой результат; комментарии с текстом make в перепись не попадают.
**And** при всех существующих целях гейт проходит, при замене одной обычной цели на `rg1-nonexistent-target` падает с её координатой. Проверка обёртки не вытесняет прежний контроль.

### Сценарий 18: пустой охват и неисполнившаяся проверка различимы

**ID:** RG1.1-18

**Given** законный корпус RG1.1-11.

**When** единственное отличие первого варианта — набор workflow-файлов пуст.

**Then** `go test` возвращает `1` с сообщением о нуле прочитанных workflow; успешного разрешения команд не объявлено.

**When** во втором независимом варианте workflow остаётся валидным, но его единственная make-команда заменена комментарием с тем же текстом.

**Then** `go test` возвращает `1` с сообщением о нуле найденных make-команд; текст комментария не создаёт ненулевой охват.

**When** в проверке расширения RG1.1-17 независимый перечень содержит вызов под stand-up, а захваченная перепись гейта сообщает ноль таких записей при непустом общем числе.

**Then** регрессия расширения падает: ненулевой общий обход не заменяет охват новой формы.
**And** если сам проверяющий процесс не запустился либо его вывод не захвачен, свидетельство получает исход «не выполнилось» с причиной; это не прохождение и не находка о корректности Makefile.

**DoD S3:** RG1.1-11…18 исполняются через проверяющий, который читает workflow продукта. Законные формы и однофактные замены цели подтверждены обеими полярностями. Перепись до/после относится к одному корпусу и одной единице. Устаревшее утверждение в шапке проверяющего об отсутствии корневого Makefile снято либо привязано к исторической ревизии.
