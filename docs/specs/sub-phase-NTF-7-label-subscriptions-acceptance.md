## §0 Обзор

Пользователь заводит подписку на уведомления, цель которой — не один ресурс и не проект, а
**селектор**: модуль, набор видов ресурсов этого модуля и набор меток `ключ = значение`. Такая
подписка доставляет мгновенным письмом события `resource-event` (`CREATED`/`UPDATED`/`DELETED`)
тех ресурсов названных видов, чьи метки на версию события содержат все пары селектора. Селектор —
только **отбор** событий внутри аудитории: письмо по селектору получает лишь тот, кто есть в строках
аудитории этой версии события (NTF-3 Р9, Р30, ограда Д133/Д134). Подписка права не даёт, ни один
вопрос о праве не обходит и второго вопроса о праве не порождает.

Почему не MVP: форма цели, проверки входа, уникальность и потолок, правило совпадения на каждом
роде изменения (включая «вышел из выборки» и снятие), доставка через ту же аудиторию и ту же
ограду, ограничение стоимости события числом строк аудитории, отображение в консоли и проба
объявления видов с метками — заводятся сразу в production-форме (`ban14-production-grade`); урезаний
внутри объёма нет, внешние границы — §6.

### 0.1 Что это НЕ

- **Не поток изменений ресурсов.** Единая подписка фундамента
  (`corelib.subscription.InternalSubscriptionService/Subscribe`) серверного отбора по меткам не
  получает: `api-sub-no-name-filter` и `sub-no-label-filter` действуют без изменений (в потоке
  событие несёт полное состояние, «вышел из выборки» и «удалён» были бы неразличимы). Здесь
  отбор делает `notify` над **фактами** события, а «вышел из выборки» — это событие `UPDATED`,
  отличимое от `DELETED` родом изменения (Р5).
- **Не новый вопрос о праве.** Ни нового отношения модели, ни нового метода службы доступа: аудитория
  события — контракт NTF-3 Р7, Р9, Р30 без правки; у подписки по меткам нет даже вопроса
  `Resolve{event, via_subscription}`, который NTF-3 Р11 задаёт подписчику ресурса или проекта (Р6).

### 1.3 Форма меток и форма селектора уже есть — их две, и они согласны

- Метки ресурса проверяет общий валидатор фундамента `validate.Labels` (corelib
  `validate/validate.go:216-235` @`1705d2b`): не больше 64 пар (`MaxLabels`, `:55`), ключ —
  `^[a-z][-_./\\@a-z0-9]{0,62}$` (`:47`), значение — не длиннее 63 символов (`:59`), пустое значение
  допустимо. Отказы: `too many labels (max 64)`; поле `<field>.<key>` — `invalid label key (1..63
  chars, lowercase letters, digits, _-./\@)` либо `label value exceeds 63 chars`.
- Селектор по меткам в модели прав — `Rule.match_labels` (kaname `role.proto:706`): равенство по
  каждой паре, конъюнкцией («AND-equality», `labels @> matchLabels`); если задан — непуст; не больше
  **16** ключей (`internal/domain/rule.go:48`); правило по меткам допустимо только на виде из набора
  §1.2 (`validateFeedGate`, `rule.go:333-350`).

Отсюда Р3: селектор подписки берёт **ту же** семантику и те же границы, что селектор правила роли
(самая узкая из двух форм — 16 ключей), и формат пар — от общего валидатора; третьей формы не
заводится.

### 1.4 Факты события уже несут метки — NTF-3 Р3, Р30

Строка `resource-event` несёт факты объекта на версию события: `labels`, у `UPDATED` — ещё
`previous_labels` (поколения `g_E − 1`); аудитория `DELETED` судится по фактам поколения `g_E − 1`
(NTF-3 Р3, Р30). Сегодня эти факты — «ключ вопроса об аудитории, а не данные показа: публичным API
`notify` не выдаются и в тело письма не попадают» (NTF-3 Р3). Р5 этого документа использует их ещё
и как ключ отбора подписки и сохраняет оба запрета (§4).

## §2 Решения — ратифицировать явно

### Требование владельца (дословно, 2026-10-08)

| ТВ | текст | куда ведёт |
|---|---|---|
| ТВ-Л1 | «подписка с отбором по меткам ресурсов — в ЭТОМ релизе» | вся под-фаза; снятие строки класса 3 §6 NTF-3 |
| ТВ-Л2 | получатель — тот, кто может читать ресурс (доступ на аккаунт / проект / модуль / ресурс / имя / метки); снимок на удаление; ограда Д133/Д134 действует; подписка по метке — отбор событий ресурсов модуля по меткам ресурса, без обхода проверки права на чтение | Р5, Р6, Р7 |
| ТВ-Л3 (2026-10-06, ТВ15 NTF-3) | «не должно быть обходных путей. все логика должна быть целевой и максимально ровной» | Р1 (одна служба, одна форма), Р6 (один источник адресатов) |
| ТВ-Л4 (2026-10-08 п.4) | «Делай все что бы минимизировать кол-во ошибок и ускорить время разработок без потери качества» | Р4 (признак сверяется с производителями пробой), Р6 (стоимость события ограничена тем, что уже посчитано) |

**Р1. Третья ветвь цели существующей подписки — `label_selector`; новой службы нет.**
- `NotificationSubscription.target` — `oneof` из трёх: `resource` и `project` (NTF-3 Р11, без
  изменений) и новый `label_selector{module, resource_types, match_labels}`. Пути, глаголы, ответ
  `Operation` с `done=true` на коммите, `channel`, потолок, снятие, выборка чужой подписки как
  несуществующей, пагинация — NTF-3 Р11, Р25 без изменений. Правки подписки нет ни у одной ветви
  (NTF-3 Р11: `POST`/`GET`/`DELETE`), поэтому все поля селектора неизменны по построению.
- REST: `POST /notify/v1/subscriptions` с телом
  `{"target": {"labelSelector": {"module": "storage", "resourceTypes": ["storage_volume"], "matchLabels": {"env": "prod"}}}, "channel": "EMAIL"}`.
Основание: ТВ-Л3 — второй службы и второго пути о том же предмете не заводится; Д8 «мгновенное
письмо — по собственной подписке».

**Р2. Форма селектора повторяет ветвь меток правила роли: модуль · виды · метки.**
- `module` — ключ модуля каталога `notify` (NTF-3 Р29: `compute`, `vpc`, `nlb`, `registry`, `storage`),
  у которого есть ячейка `(RESOURCE_CHANGE, EMAIL)` с политикой `SWITCHABLE`.
- `resource_types` — **набор** видов (тип модели) этого модуля; элементов от 1 до числа видов модуля с
  отбором по меткам (§1.2: `compute` 3, `vpc` 8, `nlb` 3, `registry` 1, `storage` 3) — верхняя граница
  следует из «вид этого модуля, с отбором, без повтора» (Р3 п.3) и отдельной ручки не имеет; каждый —
  из набора видов с метками (Р4); повтор вида — отказ; подстановки `*` нет (это не вид). Порядок
  значения не имеет; сервер хранит и отдаёт набор **по возрастанию** строки вида — порядок объявлен в
  комментарии поля (`api-repeated-order`). «Все виды модуля» выражается перечнем видов, а не пустым
  полем: пустое значение не означает «всё» (`api-empty-means-empty`).
- `match_labels` — `map<string,string>`, от 1 до 16 пар; совпадение — равенство по каждой паре,
  конъюнкцией: метки ресурса содержат все пары селектора (Р5). Пустое **значение** пары допустимо и
  совпадает только с меткой того же ключа с пустым значением.
Основание: `code-authoring` «унификация берёт самую узкую семантику» — форма и границы те же, что у
`Rule.match_labels` (§1.3); значение выразимо ровно одним способом.

**Р3. Проверка входа — до любого вопроса; порядок закрыт; тексты — часть контракта.**
Порядок для ветви `label_selector` (продолжает порядок NTF-3 Р11 «обязательность → тип и модуль по
каталогу → `channel` → формат»), первый отказ возвращается, дальше проверка не идёт:
1. обязательность: `target.label_selector.module: required`, `target.label_selector.resource_types:
   required` (пустой набор), `target.label_selector.match_labels: required` (пустой словарь);
2. модуль по каталогу: неизвестный ключ — поле `target.label_selector.module`, описание
   `unknown module '<m>'`; модуль каталога без ячейки `(RESOURCE_CHANGE, EMAIL)` (NTF-3 Р29: `notify`,
   `kaname`) — то же поле, описание `module '<m>' has no resource change notifications`;
3. виды по каталогу, по порядку элементов запроса: вид не этого модуля (в том числе `*`) —
   `'<t>' is not a kind of module '<m>'`; вид без отбора по меткам — `'<t>' has no label selection`;
   повтор — `duplicate '<t>'`; поле во всех трёх — `target.label_selector.resource_types`;
4. `channel` — как NTF-3 Р11 (`CONSOLE`, `CHANNEL_UNSPECIFIED`, вне перечисления — поле `channel`);
5. число пар: больше 16 — поле `target.label_selector.match_labels`, описание
   `too many labels (max 16)`;
6. форма пар — общий валидатор `validate.Labels("target.label_selector.match_labels", …)` (§1.3): поле
   `target.label_selector.match_labels.<key>` и его описания дословно.
Все отказы — `INVALID_ARGUMENT` с `BadRequest.fieldViolations[0] = {field, description}`; HTTP 400
(`api-http-status-table`). Подписка не создаётся, `Operation` нет.
Основание: `api-outcome-reject`, `api-name-holder` (обе стороны каждой оси), `hard-format-before-authz`.

**Р4. Признак «отбор по меткам» объявлен одним местом — таблицей видов сборки `notify`; проба сверяет его с производителями формулой.**
- В таблице видов ресурсов сборки `notify` — той, по которой NTF-3 Р11 проверяет `resource_type`
  «по каталогу» (дом `services/notify/kinds`, NTF-3 §11, производитель NTF3-80…86), — у каждого вида
  признак «отбор по меткам». Проверка Р3 п.3 читает только его; второго перечня в коде `notify` нет.
- Проба `TestNotifyLabelSelectableKindsMatchTheirProducers` для каждого вида таблицы вычисляет:
  - **(а)** у сообщения вида есть поле `labels` типа `map<string,string>`; сообщение вида — ответ
    метода `Get` публичной службы модуля с `required_relation = "v_get"` и
    `scope_extractor.object_type = <вид>` в дескрипторах `proto/kacho/cloud/<модуль>/v1/` (§1.5);
    нет такого метода — (а) ложно;
  - **(б)** у токена вида (`<module>.<name>` строки манифеста модуля с этим `objectType`, §1.5) в
    ответе `ListPermissionCatalog` службы доступа на пине `label_selectable = true`; токена в ответе
    нет — (б) ложно.
  **Предикат:** признак вида ⇔ (а) ∧ (б). Нарушение предиката в любую сторону — красный с именем
  вида, значениями признака, (а) и (б) и названием производителя каждого ложного члена
  (`proto <файл:метод>` либо `каталог прав: <токен>`). Вид без признака с ложным (а) либо (б) —
  законен и печатается отдельной строкой с причиной; на дереве это ровно `vpc_address_pool`
  ((а) и (б) ложны) и `registry_repository` ((а) и (б) ложны: метода `Get` с `v_get` у вида нет, токена
  в наборе нет).
- Проба печатает «осмотрено видов: N, с отбором: M, без отбора: K» и падает на пустом обходе: пустая
  таблица видов, вид без строки манифеста, пустой ответ каталога либо ответ без модуля таблицы —
  красный «пустой обход» с названием пустого производителя (`sub-gates-print-scope`, пустой вход —
  не всеразрешение).
- Проба — интеграционная: каталог прав спрашивается у службы доступа обвязки на пине (та же обвязка,
  что С1), вызывающий — `usr-A` (§5.1 К17); дескрипторы и манифесты — из дерева.
Основание: `api-accepted-ignored` — селектор на виде, у которого меток нет у владельца, принят бы и
не совпал ни разу; `doc-truthfulness` — одно место о предмете; ТВ-Л4 — расхождение ловится пробой, а
не ревью.

**Р5. Совпадение судится по фактам события, по роду изменения; метки у модуля и в зеркале не перечитываются.**
Для события `e` модуля `M`, вида `K`, с фактами из строки `resource-event` (NTF-3 Р3), подписка
`{module, resource_types, match_labels = S}` совпадает, если `module = M`, `K ∈ resource_types` и:
- `CREATED` — `S ⊆ labels(g_E)`;
- `UPDATED` — `S ⊆ labels(g_E)` **или** `S ⊆ previous_labels(g_E − 1)`: событие, которым ресурс
  вошёл в выборку **или вышел** из неё, доставляется; следующее после выхода — нет;
- `DELETED` — `S ⊆ labels` снятого объекта — факты поколения `g_E − 1`, по которым судится и
  аудитория снятия (**снимок на удаление**, NTF-3 Р6, Р30).
`S ⊆ L` — каждая пара `k = v` селектора есть в `L` с тем же значением (равенство, Р2). Факты берутся
только из строки события: состояния объекта и его меток `notify` не читает ни у модуля, ни у службы
доступа. Метки в `notify` не хранятся: совпадение вычисляется в транзакции приёма строки.

**Предикат вызовов** (держатель NTF7-27; им же судит запись СЛ3 и строка §9). Исходящие gRPC-вызовы
`notify-sender` к службам установки за проход приёма и сборки делятся на четыре множества. Каждый
вызов метода, названного в (О), — в том числе повтор — попадает ровно в одно из (О), (П); вызов
такого метода вне обоих делает предикат **красным** (печатается вызов и его ответ). Предикатом не
судится только вызов метода, не названного ни в одном множестве:
- **(Ф) методы лент — числом не судятся.** `corelib.subscription.InternalSubscriptionService/Subscribe`
  и `Claim`, `Ack` ленты (`corelib notify/feed`, NTF-1 Р4) к **любому** источнику перечня `notify`:
  модулям kacho и ленте `notification_feed:kaname` службы доступа (флаг службы доступа `true` в `G0`
  NTF-3). Их число задаёт не событие, а NTF-1 Р4: по сигналу, при (пере)открытии потока и по таймеру.
- **(О) обязательное множество — числом решающих ответов, по ключу.** Вызов засчитывается в (О),
  когда его ответ **решающий** — `OK` с исходом, после которого `notify` этот ключ для этого письма
  больше не спрашивает (NTF-3 Р7, Р24; NTF-1 Р5). У каждого ключа `k` (О) задаёт число решающих
  **N(k)** — по методам:
  - `ListEventAudience` — ключ (`object`, `source_version`, `page_token`), N(k) = 1: решающих ровно
    столько о версии события, сколько страниц у её аудитории при `KACHO_NOTIFY_DIRECTORY_PAGE_SIZE`
    (NTF-3 Р26), каждый с `object`, `source_version` и фактами своей строки (у `UPDATED` — и
    `previous_labels`), NTF-3 Р9, Р30;
  - `InternalNotificationRecipientService/Resolve` формы `self` — ключ `subject`; N(k) — число
    **отправленных** мгновенных писем этому адресату в судимом промежутке, по одному решающему на
    письмо (NTF-3 Р7, Р13); сборка, в которой нет ни одной строки `ALLOW`, письмом не становится и
    вопроса адреса не задаёт (Р9 «Письмо из нескольких строк»);
  - `InternalNotificationGrantService/ResolveSend` пространства модуля и шаблона `resource-event` —
    ключ (`namespace`, `template`, `enqueued_at`); решающий — исход `ALLOW`, а в сценарии, «Дано»
    которого отзывает и восстанавливает выдачу шаблона (NTF7-32), ещё и исход `REVOKED`: оба
    терминальны для строки — после них `notify` о ней в этой сборке не спрашивает (`REVOKED` →
    `DENIED(revoked)`, NTF-1 Р5). Сборка письма спрашивает `ResolveSend` о **каждой взятой в неё
    строке** с `enqueued_at` этой строки (Р9 «Письмо из нескольких строк»); строки одной сборки с
    равным `enqueued_at` судит один ответ (исход — функция ключа и записи выдачи, NTF-1 Р5). Поэтому
    на сборку решающих ровно столько, сколько **различных** значений `enqueued_at` у взятых в неё
    строк, а N(k) — число сборок промежутка, в которые взята строка с `enqueued_at = k`, вошла она в
    отправленное письмо или была выведена. Исход `NOT_YET_GRANTED` в `GL` не производится: он
    означает «записи выдачи нет» (NTF-1 Р5), а выдача пространства модуля заведена посевом манифеста
    установки до любого события (`G0` NTF-3, К1, строка «выдача пространства» `GL`); его появление —
    красное, а не повтор. Исход `REVOKED` вне NTF7-32 не производится (отзыва и `Restore` в `GL` нет):
    его появление в любом другом сценарии — красное.
- **(П) отложенные ответы — числом не судятся, формой судятся.** Вызов метода из (О), ответ на который
  — клетка «строка ждёт, попытка не тратится» соседних таблиц, и только из этого закрытого перечня:
  - `ListEventAudience` — `UNAVAILABLE` с `reason = OBJECT_GENERATION_NOT_APPLIED` → `DEFER(audience_pending)`
    (NTF-3 Р24, Р30 «Барьер поколения»). Он законен в любом сценарии: лента приходит по сигналу, а
    применитель намерений службы доступа асинхронен, поэтому строка может быть взята раньше, чем
    поколение её события применено, и средства, исключающего это построением, в `GL` нет;
  - `ListEventAudience` и `Resolve` — клетка «служба доступа не дала ответа по своей причине» таблицы
    кодов справочника NTF-3 Р7 целиком: `UNAVAILABLE` (с иным `reason` либо без), `DEADLINE_EXCEEDED`,
    `CANCELLED`, `RESOURCE_EXHAUSTED`, `ABORTED`, `INTERNAL`, `UNKNOWN`, `DATA_LOSS` →
    `DEFER(platform_unavailable)` без сигнала `misconfigured`;
  - `ResolveSend` — клетка «kaname недоступна» NTF-1 Р11: `UNAVAILABLE` либо `DEADLINE_EXCEEDED` →
    `DEFER(platform_unavailable)`.

  Форма (П), по каждому ключу `k`: (п1) у каждого вызова (П) с ключом `k` есть решающий вызов (О) того
  же метода с тем же ключом, записанный **позже**; у `ListEventAudience` — с теми же `object`,
  `source_version` и фактами; (п2) после N(k)-го решающего вызова по ключу `k` вызовов того же метода с
  тем же ключом нет — ни (О), ни (П). Отсюда штатный повтор не меняет числа: повтор с отложенным
  ответом — (П), повтор, получивший решающий ответ, — тот самый единственный решающий своего письма, а
  лишний решающий сверх N(k) — красный. Прочие коды и
  исходы (терминальные `INVALID_ARGUMENT`, `AUTHZ_REVISION_BELOW_HORIZON`, `PERMISSION_DENIED`,
  `UNAUTHENTICATED`, коды и исходы с сигналом `misconfigured`, `NOT_YET_GRANTED`, а `REVOKED` — вне
  NTF7-32, где он решающий (О)) в (П) не входят — предикат красный.
- **(З) запрещённое множество — нулём.** К модулю-владельцу события — все методы его публичной и
  внутренней службы ресурса (для тома: `kacho.cloud.storage.v1.VolumeService/*` —
  `volume_service.proto:18`, и `kacho.cloud.storage.v1.InternalVolumeService/*` —
  `internal_volume_service.proto:31` @`515e017c87`). К службе доступа — вопросы о праве и чтения
  отношений объекта: `InternalIAMService/Check` (`internal_iam_service.proto:62`),
  `AuthorizeService/Check`, `BatchCheck`, `ListSubjects`, `ExpandRelations` (`authorize_service.proto:69`,
  `:111`, `:141`, `:160`), `InternalNotificationRecipientService/Resolve` формы `event` о любом
  субъекте, кроме владельца подписки ветви `resource` или `project` вне аудитории (ниже), и
  `ListProjectAudience` (`internal_notification_recipient_service.proto:49`, `:68`),
  `InternalIAMService/CurrentAuthzRevision` (`internal_iam_service.proto:223`; `notify-sender` его не
  зовёт, NTF3-179 (г)) — все координаты kaname на пине.
- **Подписка ветви `resource` или `project` в судимом промежутке** (близнец NTF7-31): `Resolve` формы
  `event` о её владельце, которого нет в строках аудитории версии, переходит из (З) в (О) — ключ
  (`subject`, `object`, `source_version`), N(k) = 1, решающий — ответ `OK` с исходом (NTF-3 Р11
  «Доставка»); в (П) для него — `OBJECT_GENERATION_NOT_APPLIED` (форма `event` его производит, NTF-3
  Р24) и клетка «служба доступа не дала ответа» NTF-3 Р7 (перечень выше). О любом другом субъекте
  `Resolve{event}` остаётся в (З).
Подписки по меткам решающих вызовов `ListEventAudience` не добавляют (их число о версии — число
страниц её аудитории при любом числе подписок), решающие `Resolve{self}` и `ResolveSend` прибавляют
только вместе со сборкой письма — `ResolveSend` по одному на каждое различное `enqueued_at` строк
сборки, `Resolve{self}` по одному на сборку, ставшую письмом, — а вызовов из (З) не порождают ни
одного (держатели NTF7-27, NTF7-31, NTF7-32). Число вызовов (П) задаёт не подписка, а момент применения поколения и доступность службы
доступа — поэтому оно числом не судится.
Основание: ТВ-Л2; `sub-no-label-filter` — довод «вышел из выборки неотличим от удалён» здесь снят
родом изменения: выход — `UPDATED`, снятие — `DELETED`.

**Р6. Кандидат и адресат — только из строк аудитории приёма; вопроса вне аудитории у селектора нет; стоимость события ограничена аудиторией.**
- **Кандидаты.** На приёме события `notify-sender` ищет совпавшие подписки по меткам **только среди
  подписок владельцев строк аудитории** этого события (строки, которые NTF-3 Р9 пишет той же
  транзакцией из ответа `ListEventAudience`); подписки остальных пользователей не читаются вовсе.
  Число кандидатов на событие — не больше числа строк аудитории; число вопросов к службе доступа,
  которые порождают подписки по меткам, — **`0`** при любом числе подписок и подписчиков (держатель
  NTF7-31).
- **Адресат.** Совпавший кандидат получает мгновенное письмо (NTF-3 Р13): он в аудитории версии с
  оградой `R_E` — право читать объект есть, не менялось с `R_E`, не условное, не подстановочное, не
  только уровня кластера (NTF-3 Р30, Д133 (1), (3), (4)). Поколение не применено службой доступа —
  строка ждёт клеткой `DEFER(audience_pending)` целиком, писем по подписке до ответа нет (NTF-3 Р30
  «Барьер поколения»); токен ниже горизонта — `DENIED(audience_horizon)`, писем нет. `DELETED` —
  аудитория до снятия плюс держатели выдач на сам объект, снятых каскадом (Д133 (2)) — они в строках
  аудитории `DELETED` (NTF3-178).
- **Вопроса `Resolve{event, via_subscription = true}` у ветви селектора нет.** Правило одно для трёх
  ветвей: вопрос вне аудитории задаётся только подписке, **цель которой проверена на создании**
  вопросом о вызывающем (NTF-3 Р11: ресурс, проект — `Check(v_get)`). У такой подписки круг
  подписчиков вне аудитории ограничен теми, кто прошёл проверку цели; у селектора проверки цели нет
  (Р7), и вопрос вне аудитории спрашивал бы каждого подписчика облака, совпавшего метками, — чтобы
  найти единственный случай, когда ответ `ADDRESS`: право только уровня кластера (Д133 (3)).
- **Следствие названо.** Субъект, читающий объект только путём через `cluster` (администратор облака,
  `system_admin`), в аудитории не бывает (NTF-3 Р30) и письма по селектору не получает; события он
  получает по явной подписке на ресурс или на проект (NTF-3 Р11, NTF3-76, NTF3-176) — проверка цели у
  него проходит путём `super_admin` (`fga_model.fga:425` @пин). Выбор владельца об этом — §6 и вопрос
  владельцу.
Основание: ТВ-Л2 «без обхода проверки права на чтение»; Д129 (3) — адресат только из аудитории;
ТВ-Л3 — один источник адресатов; `ban14-production-grade` — стоимость события не растёт с числом
пользователей облака.

**Р7. Создание селектора не задаёт вопроса о праве и не зовёт службу доступа.**
У селектора нет объекта, существование которого можно скрыть: ветви `resource` и `project` спрашивают
«видна ли вызывающему цель» (NTF-3 Р11), а у селектора цель — правило отбора, которое ничего не
раскрывает: письмо всё равно получает только член аудитории (Р6). Поэтому на создании
`label_selector` клиент прав `notify-api` не вызывается (0 вызовов `Check`), а недоступность службы
доступа создание не отвергает (близнец NTF3-156 по одному факту — ветвь цели). Вопрос о праве на
проект как ось селектора отверг бы именно тех, кто читает по меткам или по типу (§1.6). Проверка
самого вызова — освобождение «объект — вызывающий» записи каталога прав метода `Create` (NTF-3 Р25)
без изменений; столбцы «вызов службы доступа» и «недоступна» этой записи для ветви селектора
замещаются (§4).
Основание: `hard-no-hand-rolled-authz` — вопрос, ответ на который ничего не меняет, был бы
самодельной проверкой; право решает модель на доставке.

**Р8. Уникальность и потолок — в базе; набор видов сравнивается как набор.**
- Дубль — тот же владелец, тот же модуль, тот же **набор** видов (порядок в запросе не важен), тот же
  словарь меток, тот же канал — `ALREADY_EXISTS` `NotificationSubscription for this target already
  exists` (текст NTF-3 Р11); держатель — уникальность в базе по канонической форме цели (набор
  видов упорядочен сервером до записи), параллельные создания дают ровно один успех (`db-unique`).
- Пересекающиеся селекторы (`{env: prod}` и `{env: prod, tier: gold}`; `[storage_volume]` и
  `[storage_volume, storage_snapshot]`) — разные подписки, обе законны; письмо от этого не
  удваивается (Р9).
- Потолок `KACHO_NOTIFY_SUBSCRIPTIONS_PER_USER` (границы `[10, 1000]`, NTF-3 Р11) один на все три
  ветви цели; счётчик — CAS NTF-3 Р11.

**Р9. Одно событие — одно письмо адресату, сколько бы подписок ни совпало.**
Мгновенное письмо собирается по паре «адресат + ресурс» в окне схлопывания NTF-3 Р13, а не по
подписке: совпадение события с подпиской на ресурс, на проект и с одним или несколькими селекторами
одного адресата даёт одно письмо; всплеск, потолок пары «модуль + адресат» и сетка `notice` считают
это письмо один раз. Разные ресурсы — разные пары, разные письма. Ячейка `(модуль, RESOURCE_CHANGE,
EMAIL)` выключена — писем по подписке нет (NTF-3 Р10); о собственном действии — по ячейке
`(notify, OWN_ACTIONS, EMAIL)` (Д129 (6)).

**Письмо из нескольких строк спрашивает выдачу о каждой строке.** **Сборка** — строки пары «адресат +
ресурс» одного окна схлопывания (NTF-3 Р13), взятые в неё совпадением с подпиской адресата; из сборки
выходит не больше одного письма. Сборка зовёт `ResolveSend(<модуль>, resource-event, enqueued_at
строки)` о **каждой** взятой строке — тем же правилом, что сборка сводки о каждой своей строке (NTF-3
Р12: «`ResolveSend(<модуль>, resource-event, enqueued_at строки)` = `ALLOW`»); строки сборки с равным
`enqueued_at` судит один ответ. Ответ одной сборки другой не переиспользуется: две сборки с одной строкой
(два адресата) спрашивают о ней каждая (NTF7-31, близнец). Строка с исходом `REVOKED` получает
терминальный `DENIED(revoked)` (NTF-1 Р5) и в письмо не входит; письмо собирается из строк с исходом
`ALLOW`, число правок в нём — по ним; ни одной такой строки — письма нет, и вопроса адреса
`Resolve{self}` о нём тоже нет (держатель обеих ветвей — NTF7-32 и его близнецы). Отложенный ответ о
любой строке (`DEFER(platform_unavailable)`) откладывает письмо целиком до решающего ответа о ней.
Один вызов на письмо отвергнут: отсечка `Restore` судится по `enqueued_at` строки (NTF-1 Р5) и может
лежать между строками одного письма; вызов по поздней строке пропустил бы раннюю, поставленную до
отсечки (fail-open), а вызов по ранней терял бы поздние, законные после отсечки. Правило — одной
функции мгновенного письма для трёх ветвей цели (DoD 10.2 п.1); NTF-3 Р13 этого не задаёт, замещение
— §4.

**Р10. Метки в письме и в ответе — только те, что прислал подписчик.**
Тело письма — шаблон `resource-event` модуля без изменений (NTF-3 Р3): меток ресурса в нём нет ни на
одном роде изменения, в том числе при выходе из выборки. Ответ подписки несёт селектор, который
прислал её владелец, и ничего о ресурсах. Факты событий публичным API `notify` не выдаются (NTF-3 Р3).

**Р11. Консоль показывает и снимает подписку по меткам; заводит её край.**
По прецеденту подписки на проект (NTF-6 Р10, NTF6-55): строка в «Мои подписки» экрана
`/notifications/settings` — «Метки · <displayName модуля из каталога> · <подписи видов> ·
`k=v`, …» и подпись канала из каталога; пары — в порядке ключей по возрастанию, ключ и значение
выводятся **только как текст** (NTF-6 Р8; значение метки ограничено лишь длиной, §1.3). Подпись вида
— переходом спеки (NTF-6 Р10, Р10а); вид без спеки выводится строкой `resourceType`. «Отписаться» —
`DELETE /notify/v1/subscriptions/{id}`. Формы заведения селектора в консоли нет (§6).

**Р12. Строка класса 3 §6 NTF-3 снимается этим документом.**
Предикат её возврата в работу («решение владельца о шаге подписки с отбором по меткам») выполнен
решением 2026-10-08 п.2; предмет переходит сюда. Строку в NTF-3 правит её автор следующей редакцией
вместе с замещениями §4 (DoD 10.4 п.3).

## §6 Что НЕ входит

Классы строк — как NTF-3 §6: чужой предмет; отложенная работа (с задачей); исключение решением (с
основанием и предикатом возврата).

| предмет | класс | основание · предикат возврата |
|---|---|---|
| серверный отбор по меткам в потоке изменений ресурсов (`InternalSubscriptionService/Subscribe`) | исключение решением | `sub-no-label-filter`, NTF-3 Д127 (в) · предикат — правка правила `.claude/rules/subscription.md` владельцем правила |

## §10 DoD

### 10.1 Стадия S1 — контракт и ведение

1. `proto`: ветвь `label_selector` в `oneof target`, комментарии полей (порядок набора, пустое не
   означает «всё»); `buf lint`, `buf breaking` против ветки эпика — зелёные; регенерация закоммичена.
2. `notify-api`: проверка входа Р3 в порядке Р3; создание без вопроса о праве (Р7); каноническая форма
   и уникальность (Р8); потолок общий; все отказы — с полем и описанием Р3.
3. Миграция `kacho_notify` (новая): колонки ветви, `CHECK` «ровно одна ветвь цели», уникальность
   канонической формы, индекс поиска подписок по владельцу, модулю и виду.
4. Таблица видов сборки — признак «отбор по меткам»; проба Р4 зелёная на дереве (20/18/2), красная на
   каждой из пяти инъекций и на пустом обходе, печатает объём осмотренного.
5. Пробы: интеграционные `notify-api` (NTF7-01…10, параллельные горутины в NTF7-07, 08); падающая
   проба — до кода (`ban12-tdd`); newman — кейсы NTF7-01, 03, 04, 06, 07 (пара HTTP-статус + `code`,
   `api-case-asserts-pair`) в коллекции подписок `notify`; новая коллекция — строкой ведомости
   производителя.
6. Край пересобран с контрактом; сквозная проба NTF7-01 через край зелёная.

### 10.2 Стадия S2 — доставка

1. `notify-sender`: отбор Р5 в транзакции приёма по фактам строки, кандидаты — только подписки
   владельцев строк аудитории (Р6); исходящие вызовы удовлетворяют предикату вызовов Р5 — (О)
   числом решающих ответов N(k) по ключу, (П) формой (п1), (п2), (З) нулём; `ResolveSend` — о каждой
   строке сборки с её `enqueued_at` (держатель NTF7-27), строка `REVOKED` из письма выводится, письмо —
   из строк `ALLOW`, ни одной — письма и вопроса адреса нет (Р9 «Письмо из нескольких строк»; держатель
   NTF7-32 и его близнецы); в том числе ни одного чтения состояния ресурса у модуля и ни одного вопроса
   `Resolve{event}` от ветви селектора; письмо — та же функция мгновенного письма NTF-3 Р13, что у
   ветвей `resource`/`project` (второй нет).
2. Пробы NTF7-12…27, NTF7-31 и NTF7-32 — интеграционные `notify` + модуль + служба доступа, зелёные; каждый
   близнец §8 — отдельным утверждением.
3. Метрики отправителя считают письма по подписке по меткам в тех же счётчиках, что NTF-3 Р13 (без
   новой оси с метками — метки не идут в метки метрик).
