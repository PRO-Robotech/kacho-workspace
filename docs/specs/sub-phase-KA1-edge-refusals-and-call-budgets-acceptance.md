## 0. Рамка

### 0.1 Обзор

Край отвечает на четыре вещи по-разному в зависимости от того, какой полосой пришёл
вызывающий и по какой причине ему отказано. Этот документ закрепляет **один** наблюдаемый
ответ на каждый из четырёх предметов: (1) наш авторитет отзыва не ответил — один ответ на
всех полосах; (2) удостоверение не принято — один отказ `401`, не зависящий от причины;
(3) вызов края к соседу ограничен **объявленным** бюджетом, и край отвечает отказом, а не
висит; (4) издатель токена сравнивается в канонической форме, одинаковой для объявления и
для предъявленного `iss`.

### 0.4 Решения, которые этот документ принимает

**Р1. Наш авторитет не ответил → `503 UNAVAILABLE`, один и тот же ответ на всех полосах,
носитель цел.** Полосы — предъявитель (оба читателя отзыва: авторитет нашей чеканки и запись
отзыва), наша браузерная сессия (оба вопроса: о сессии и об отсечке) и базовое удостоверение.
«Не ответил» включает: нет ответа в пределах бюджета (Р4), `UNAVAILABLE`, `UNIMPLEMENTED` на
вопрос, без которого полоса не может решить (о сессии, об отзыве, о годности базового
удостоверения), ответ не той формы. Тело — одно на все полосы:

```
HTTP/1.1 503 Service Unavailable
Content-Type: application/json

{"code":14,"message":"credential state could not be established"}
```

без `WWW-Authenticate` и без `Set-Cookie`. Нативная поверхность — `UNAVAILABLE`, тот же текст,
без деталей. Основания:

- `401` на нашу собственную неисправность посылает арендатора чинить исправное: консоль на
  прочем `401` уводит человека на экран входа (`ui-future/host/src/utils/api-client.ts`,
  шапка `apiGet`) при живой сессии;
- полоса предъявителя и полоса базового удостоверения уже отвечают на этот случай `503`
  (`gateway/internal/middleware/auth.go` — ветки `revocationUnanswerable` и
  `ErrCredentialStateUnknown`), то есть расходится одна полоса из трёх;
- довод одобренного F4d-23 («различимый ответ — оракул исправности соседа») не держится в
  этом дереве: та же величина опубликована общедоступным путём `/readyz`
  (`gateway/internal/middleware/authz_util.go` — `/readyz` в `isPublicHTTPPath`;
  `gateway/docs/content/install/deploy.mdx` — «`/readyz` возвращает `503` только при
  недоступности критичного backend»). Скрывать в ответе отказа то, что отдаётся проверкой
  живости, значит платить за ничто — и платить арендатором, уведённым на вход.

Текст выбран тот, что уже производит полоса базового удостоверения: он верен для всех трёх
вопросов (о сессии, об отсечке, об отзыве), а текст `revocation check unavailable` верен
только для одного. Потребителей у заменяемого текста вне `gateway/internal/middleware/` — 0
(`git grep -l -F 'revocation check unavailable' e801c0f7844 | grep -v 'gateway/internal/middleware/'` → пусто).

**Р2. Удостоверение не принято → один отказ `401`, побайтово одинаковый для всех причин на
своей поверхности.**

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json
WWW-Authenticate: Bearer realm="kacho", error="invalid_token"

{"code":16,"message":"authentication failed","details":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","reason":"AUTHN_REQUIRED","domain":"kaname.cloud.iam.v1"}]}
```

`metadata` у `ErrorInfo` нет (сегодня там имя глагола и причины отказа). Нативная поверхность —
`UNAUTHENTICATED`, текст `authentication failed`, деталь — ровно одна `ErrorInfo` с теми же
`reason` и `domain`, без `metadata`.

Выбор вызова и `domain` — здесь, не отложен:

- **Вызов** соединяет две сегодняшние формы: `realm="kacho"` (отказ «удостоверения нет»,
  `writeHTTPUnauth`) и `error="invalid_token"` (отказ проверки, `writeHTTPUnauthorized`), а
  `error_description`, нёсший причину, снят. `error="invalid_token"` сохранён, потому что у него
  есть читатель: консоль по нему повторяет вопрос о сессии
  (`ui-future/shared/src/api/login-lane.ts`, `sessionIdentity`) и выбирает действие
  (`refusal-action.ts`); разбор `step-up.ts` (`/(?:^|[\s,])error="([^"]*)"/`) берёт его и после
  `realm`. Этим ответ отступает от «SHOULD NOT» RFC 6750 §3.1 для запроса без удостоверения:
  неразличимость причин (`security.md`, `sec-authn-failures-byte-identical`) здесь весит больше.
- **`domain`** — `kaname.cloud.iam.v1`: это значение сегодня несут все четыре места, строящие
  `AUTHN_REQUIRED` и `AUTHZ_DENIED` края (`permission_denied_response.go`;
  `git grep -c '"kaname.cloud.iam.v1"' e801c0f7844 -- gateway/internal/middleware/permission_denied_response.go`
  → 4). Смена значения — предмет `sub-phase-XC-1-error-reason-token-acceptance.md` (S5) и
  делается там одновременно для `401` и `403`; KA1 её не предрешает и не ждёт.

Сравнение «побайтово одинаково» идёт по статусу, телу и **каждому** заголовку ответа, кроме
двух, различных у любых двух ответов по построению: `Date` и `X-Request-Id`.

Причина отказа на полосе нашей браузерной сессии одна по смыслу — носитель не годен — и
вместе с отказом край **заканчивает носитель**: каждый `401` этой полосы несёт один и тот же
набор `Set-Cookie`, гасящий носитель (`gateway/docs/content/architecture/authn.mdx`,
«Отказ выдаёт окончание носителя»). Набор зависит от полосы, которую вызывающий выбрал сам, а
не от причины отказа.

Причина остаётся в журнале края и только в нём.

**Р3. Исключение одно, и оно не отказ, а указание: вызов повышения уровня.** Ответ `401` с
`WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="<N>"` выдаётся
только удостоверению, уже признанному годным, и называет следующий шаг его держателю — тот же
единственный различимый исход, который сохраняет путь отказа `403`
(`gateway/internal/middleware/permission_denied_response.go`, `safeDenyDescription`). Под Р2
он не попадает и не меняется. Полоса, у носителя которой церемонии повышения нет, этого
указания не получает и отвечает по Р2 (как сегодня — `auth_stepup.go`, `enforceStepUpHTTP`).

**Р4. Бюджет вызова края к соседу объявлен ручкой, судится стражем старта, умолчания нет.**

| ручка | что ограничивает | профили поставки объявляют |
|---|---|---|
| `KACHO_API_GATEWAY_IDENTITY_CALL_BUDGET` | каждый вызов края к внутреннему слушателю службы доступа на пути запроса: вопрос о сессии, об отсечке, об отзыве по идентификатору, о годности базового удостоверения, а также отзыв сессий при выходе | `1s` |
| `KACHO_API_GATEWAY_BACKEND_CALL_BUDGET` | каждый вызов REST-моста к бэкенду домена | `30s` |

Значение — длительность в форме Go (`1s`, `250ms`). Незаданное, пустое, неразбираемое, нулевое
или отрицательное — **отказ в старте** в любом режиме, текстом, который называет ручку и
различает «не объявлено» и «объявлено, но не годится». Бюджет не расширяет более ранний срок,
пришедший с запросом.

Исход превышения: вопрос службе доступа на пути аутентификации → Р1 (`503`); вызов моста к
бэкенду → `504` / `DEADLINE_EXCEEDED` (`4`). Код моста — `DEADLINE_EXCEEDED`, а не
`UNAVAILABLE`, потому что исход вызова бэкенда при истечении срока неизвестен (мутация могла
быть закоммичена), и `UNAVAILABLE` предлагал бы повтор как безопасный. Статус `504` край
производит своей таблицей (`runtime.HTTPStatusFromCode`), собственного `WithErrorHandler` у
края нет.

Величина `1s` совпадает с соседними вопросами того же адресата: бюджетом читателя отзыва
нашей чеканки (`KACHO_INTROSPECTION_TIMEOUT_MS`, `1000` во всех профилях) и прежними
константами `BasicCredentialCallBudget` / `OwnRevocationCallBudget`
(`gateway/internal/middleware/basic_credential_lane.go`, `revocation_local.go` — `time.Second`),
которые ручка заменяет. Расхождения между тремя вопросами одного адресата нет.

**Р5. Издатель сравнивается в канонической форме, и канон один.** Каноническая форма значения
издателя — абсолютный URL со схемой `http` или `https`, в котором: схема и хост в нижнем
регистре; порт по умолчанию схемы (`:443` для `https`, `:80` для `http`) снят; завершающая
точка хоста снята; процентное кодирование **незарезервированных** символов (RFC 3986 §2.3)
раскрыто, а шестнадцатеричные цифры остальных кодов — в верхнем регистре; завершающая `/`
пути снята (пустой путь и `/` — одно). Путь, запрос и всё прочее регистра не теряют.
Канон применяется **в одном месте**, через которое проходят: перечень издателей
(`KACHO_API_GATEWAY_TOKEN_ISSUERS`), ключи привязки к наборам
(`KACHO_API_GATEWAY_TOKEN_ISSUER_KEYSETS`), наш издатель
(`KACHO_API_GATEWAY_PLATFORM_TOKEN_ISSUER`) и `iss` предъявленного токена. Канон выбирает
**запись**; ключ проверки подписи по-прежнему берётся только из набора выбранной записи, так что
канон не расширяет круг подписантов.

Объявленное значение, не являющееся абсолютным `http(s)`-URL, — отказ в старте с названием
ручки. Два объявленных издателя с одной канонической формой — отказ в старте с названием обоих.

## Что НЕ входит

- Ретранслируемые ответы службы доступа на записях объявления (вход, выход, признак формы,
  регистрация, восстановление) — их исход судит служба; край их тело не переписывает.
- `UNIMPLEMENTED` **только** на вопрос об отсечке при живой сессии — проход, громко, со
  счётчиком (окно раската, `ErrSessionCutoffUnsupported`) остаётся как есть.
- Закрытие открытых потоков при молчании авторитета (перепрос на потоке, `authn.mdx`) — своё
  окно и своя полоса.
- Смена значения `domain` у `ErrorInfo` отказов `401` и `403` края — предмет `XC-1` (S5); KA1
  сохраняет нынешнее (Р2).
- Правка текстов документов, перечисленных в Р6: одобрение каждого привязано к его отпечатку, и
  замена объявлена здесь, таблицей Р6, а не переписыванием их; в части ответа края действует этот
  документ.
- Отказ `403` и его форма — без изменений.
- `kacho#2740` (клетки прибора у полосы предъявителя), `#2741` (классификация чужого отказа;
  ответ арендатору по её же DoD не меняется), `#2742` (перепись точек чтения вердикта) —
  наблюдаемого ответа не меняют; приёмка им не требуется.
- `kacho#2760`: пункт 1 — предмета в дереве нет: в нетестовом коде конфигурации края разборов
  момента нет (`git grep -l 'time.Parse' e801c0f7844 -- 'gateway/internal/config/*.go' ':!*_test.go'` → пусто),
  окно перехода снято вместе с прежним издателем; пункт 2 — тип параметра, наблюдаемого нет.
- `kacho#2738` в части бюджета **HTTP-читателя** отзыва нашей чеканки
  (`KACHO_INTROSPECTION_TIMEOUT_MS`) — ручка уже объявлена и читается; здесь она только сверена
  по величине (Р4).
- Ответ края на исчерпание бюджета на путях, не названных в Р4 (проверка прав, чтение наборов
  ключей) — у них свои объявленные бюджеты.

## Сценарии

Общее «Дано» всех сценариев, если не сказано иное: край поднят в боевой посадке
(`authMode=production`), наш издатель объявлен; маршрут проб — `GET /iam/v1/accounts` (REST) и
`kaname.cloud.iam.v1.AccountService/List` (нативная поверхность). Строка каталога прав этого
глагола — `permission="iam.accounts.list"`, `scope_filtered=true`, без `required_acr_min`
(`gateway/internal/middleware/embed/permission_catalog.json`): край пропускает любого
признанного субъекта, выдачу сужает владелец (`authz.go`, `phaseScopeFiltered`). Поэтому на
этом маршруте положительный и отрицательный исходы отличаются ровно предъявленным, а не правами.

**Посев.** Каждое «Дано» берётся из посева, сделанного до первого запроса пробы; проба не
заводит состояние по ходу. Внутрипроцессные пробы края — из харнесса (база —
`newF1bStandWith`, `gateway/internal/e2e/f1b_two_issuer_e2e_test.go`: две записи приёма, две
поверхности, авторитеты отзыва с переключателями «не ответил» и «отозван»), дополненного
строками, помеченными «заводится»:

| ключ | что засеяно | есть / заводится |
|---|---|---|
