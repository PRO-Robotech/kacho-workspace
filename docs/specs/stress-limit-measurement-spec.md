## 1. Определение предела прочности по каждой операции

Предел прочности — **не** «когда станет медленно». Это состояние, в котором операция **перестаёт давать результат, оставаясь внешне исправной**. По каждой операции ломается разное, и наблюдается разным.

### 1.1 ЧТЕНИЕ — ломается мощность множества говорящих, а не объём облака

**Что ломается первым.** Не число объектов и не число чужих выдач (обе оси измерены плоскими), а **множество субъектов, за которых говорит спрашивающий**. В запросе оно входит **в обе** ветви одновременно:

- `speaker_pair` = сам + все свои группы + подстановка `user:*` (`relverdict/query.go:248-277`) → **M + 2** строк;
- `speaker` (текстовая форма для прямых фактов) = сам + `group:<id>` + `group:<id>#member` + `user:*` (`query.go:279-294`) → **2·M + 2** строк.

Предела на число членств в дереве **нет**: `group_members` ограничения мощности не несёт, а объявленное умолчание `iam.group = 64` (`migrations/0094_limit_kind_nested_form_and_seeds.sql`) — это предел числа **групп в аккаунте**, и он **не энфорсится** (см. §6.2).

**Второе, что ломается — отказ.** Ранний выход работает **только на «да»**: `LIMIT 1` стоит внутри ветви выдач (`query.go:348`), а цикл Go останавливается на первой безусловной строке. Ветвь фактов несёт **свой** `SELECT DISTINCT` (`query.go:360`) — блокирующий узел, — и внешний `LIMIT $8` её не подрезает; дерево записывает это **остатком, а не сделанным** (`relverdict/s2_blockers_integration_test.go`, шапка `TestR7_1_13_EarlyExitIsObservable`: «Ни то ни другое здесь не сделано, и это записано как остаток»).

**Третье — списочный вопрос.** `List` — не один заход: `for { … after = last }` (`relverdict/list.go:349-370`) повторяет заход, пока страница не наполнится **либо кандидаты типа не кончатся**. При доле доступных 0 % страница не наполняется никогда, и один вызов просматривает **весь тип**. Сверху это множится: теневой сравнитель зовёт `Objects` с `CompareSetLimit+1 = 201` (`shadowverdict/shadow.go:72,406`), а `Asker.Objects` (`relverdict/asker.go:181-201`) гоняет `List` **по каждому отношению**.

**Как наблюдается.** Строки плана + отброшенные + **число сканов**; исход вердикта (обязан быть `deny` на отказных точках); p99 против бюджета теневого вызова `DefaultTimeout = 50 ms` (`shadowverdict/shadow.go:61`).

### 1.2 ЗАПИСЬ — ломается не длительность, а СХОДИМОСТЬ прохода

**Что ломается первым — потолок отсоединённого прохода.** Материализация идёт `shared.GoPostCommit` с `PostCommitTimeout = 2 * time.Minute` (`shared/postcommit.go:49`); так отправлены и создание выдачи (`api/access_binding/create.go:446`), и веер правки роли (`api/role/update.go:388`). Проход, не уложившийся в 2 минуты, обрывается **молча** (ошибка только в журнал), остаток передаётся 30‑секундному обходу.

**Второе — постейтментный срок.** Быстрый путь пишет **пакетами**: `forwardWriteSet.flush` — три обращения на весь веер (`reconcile/forward.go:512-518`: `UpsertMembers` / `EmitTupleWrite` / `RecordEmittedTuplesBatch`). `statement_timeout = 30000` (`pkg/db/pool.go:46`) действует **на один стейтмент**; отмена одного пакетного `UpsertMembers` откатывает всю транзакцию форварда ⇒ материализуется **ноль**, и обход повторяет то же самое.

**Третье — объём, адресуемый произведением.** Ключ члена включает отпечаток правила: `PRIMARY KEY (binding_id, role_id, rule_fp, object_type, object_id)` (`migrations/0027_target_members_rule_rekey.sql:66-68`). Значит один объект, накрытый K правилами, даёт **K членов**; K ≤ `MaxRules = 64` (`domain/rule.go:50`).

**Четвёртое — утечка работы за пределы области.** Полоса меток кандидатов **не сужена областью**: `MatchByLabels` (`repo/kacho/pg/resource_mirror/reader.go:71-79`) — `WHERE m.object_type = ANY($1) AND m.labels @> $2::jsonb`, ни предиката области, ни `LIMIT`. Полный проход на каждый чужой объект пишет члена «отвергнут» **и** строку аудита (`reconcile/reconcile.go:1241`, `EmitContainmentAudit`). Быстрый путь создания этого **не делает** (пропускает не‑ACTIVE: `forward.go:219`, `forward.go:482`) — то есть кросс‑аккаунтный усилитель есть только у **полного** прохода.

**Как наблюдается.** Бинарная величина «проход сошёлся / оборван по сроку / откатился по стейтменту» — **первой строкой**, до всяких миллисекунд; затем члены по статусам, стейтменты, строки очередей.

### 1.3 УДАЛЕНИЕ — ломается ОКНО, а не стоимость акта

**Что ломается первым.** Время, в течение которого субъект, лишённый права, продолжает получать «разрешено». Оно складывается из шести слагаемых (§5), и объявленный политикой потолок **10 с** (`pkg/authz/revocation_policy.go:117`, `Ceiling: 10 * time.Second`) очереди пересведения не учитывает вовсе.

**Второе — форма отзыва зависит от ПУТИ, и пути неравноценны:**

| путь | форма работы | потолок |
|---|---|---|
| `AccessBinding.Delete` | одно чтение реестра + разделение + **один пакетный** `EmitRelationDelete`, члены сносит каскад (`api/access_binding/delete.go:211-242`) | дёшево |
| `ExpireBinding` (истечение срока) | **по члену**: чтение реестра + `ForgetEmittedTuples` + `DeleteMember`, всё под исключительной блокировкой (`reconcile/reconcile.go:769-818`) | **потолка времени НЕТ** — идёт на контексте воркера |
| удаление аккаунта | до **50 000** выдач в **одной** writer‑транзакции, все кортежи в **один** срез, один `EmitFGARelationDelete` (`api/account/delete.go:150-216`; `accountBindingRevokePageSize = 1000`, `accountBindingRevokeMaxPasses = 50`) | сверх — **отказ** `FailedPrecondition`, не частичное удаление |

**Третье — тихая потеря отзыва.** `revokeTuplesFor` на отказе чтения реестра возвращает `(nil,false)` и **только пишет WARN** (`reconcile/reconcile.go:1363-1386`), а `DeleteMember` в `ExpireBinding` исполняется **безусловно** (`reconcile.go:807`, вне ветки `if`). Итог: строка члена исчезла, кортеж жив, следующий проход члена не найдёт. Комментарий рядом утверждает «a later sweep re‑converges» — для этого случая это неверно.

**Как наблюдается.** Время до **первого отказа** (не до разрешения) плюс остаток: кортежи без строки реестра активной выдачи.

## 2. Таблицы точек прогона

Обозначения: **M** — членств самого спрашивающего; **L** — строк `access_binding_subjects`, совпавших с парой (говорящий, область); **S** — мощность CTE областей; **K** — правил роли, накрывших объект; **N** — объектов зеркала; **B** — чужих выдач.

**Важно про L (поправка к брифингу).** L ≠ «число ролей». `UNIQUE (subject_id, subject_type, role_id, resource_type, resource_id) WHERE revoked_at IS NULL` (`migrations/0003_access_bindings_unique_active_grant.sql:99-102`) ключуется **легаси‑субъектом строки** `access_bindings`; вторая таблица `access_binding_subjects` несёт `PRIMARY KEY (binding_id, subject_type, subject_id)` (`0028:42`) и обычный, **не уникальный** индекс `access_binding_subjects_subject_scope_idx` (`732001:206`). Привязка несёт до 32 субъектов (`domain/subject.go:65`). Значит L набирается **одной ролью**: k привязок вида `subjects=[болван_i, U]` дают k строк (U, область) и в UNIQUE не упираются.

**Важно про S.** `PRIMARY KEY (object_type, object_id, depth)` + `CHECK (depth BETWEEN 1 AND 4)` (`migrations/0082_resource_parent_edge.sql:58,70`) дают ≤4 ребра **на объект**. Обход рекурсивен и разворачивается с уровня 0 по уровень 4 (`query.go:237-250`, соединение вбок с `LIMIT $7`). Отсюда:

- **согласованное транзитивное замыкание** (объект знает всех предков, предок глубины d знает 4−d своих): S = 1+4+3+2+1 = **11** — это `S_гран` приёмки, и оно **подтверждено наблюдением**: при цепи глубины 3 отчёт даёт `S_набл = 7` = 1+3+2+1;
- **схемный потолок** (у каждого узла свои 4 ребра, не пересекающиеся): S = 1+4+16+64+256 = **341**. Схема этого не запрещает, а `RegisterResource` передаёт цепь **как есть** (`api/internal_iam/register_resource.go:348`, `ParentChain: in.GetParentChain()`), формы её не проверяя.

Обе величины идут в сетку **разными точками**, и 341 помечается «посевное состояние, производителями сегодня не создаётся».

### 2.2 ЗАПИСЬ — рамка B

Две полосы, **и они разные**; мерить обязательно обе, называя, какой операции отвечает каждая.

| полоса | что её запускает | точки |
|---|---|---|
| **аддитивная** (`ReconcileBindingForward`, без advisory‑блокировки — `forward.go:26,50,184`; три пакетных стейтмента — `forward.go:512-518`) | `AccessBinding.Create` (`create.go:446-448`) | членов на выдачу: 10² · 10³ · 10⁴ · 6.5·10⁴ · 6.55·10⁵ |

Форма роли для верхней точки: 64 правила (`MaxRules`), полоса — метки, у каждого правила ≤16 ключей (`maxMatchLabels`, `rule.go:48`), объект несёт 64 метки (`pkg/validate/validate.go:55`, `MaxLabels = 64`). Тогда членов = 64 × объектов.

**Контрольная точка «полоса имён»** — 64 правила × 256 имён (`maxResNames`, `rule.go:47`) = 16 384 члена, то есть **в 40 раз меньше** меточной. Её нельзя строить наивно: `CompileRules` разворачивает имена в `ресурсы × имена × глаголы` и отвергает свыше `MaxCompiledPermissions = 1024` (`rule.go:53,317,353`). Конструкция, которая проходит: 64 правила по 256 имён, **один** ресурс, **один** глагол.

**Веер выдач ограничен `MaxRoleFanoutBindings = 10000`** (`api/role/iface.go:61`, проверка `api/role/update.go:221-225`), и проверка **мягкая** — гонка её обходит (сказано в коде). Точка 10 000 **неисполнима** (см. §6.3); верхняя исполнимая — **512** (объявленное умолчание `iam.accessBinding`).

### 2.4 ТОЧКА «МАКСИМАЛЬНО ЗАГРУЖЕННЫЙ ПОТОК» — это РЕЖИМ, а не операция

Максимум работы в системе производит **фон**, а не акт. Точка ставится так:

1. **состояние**: 512 ACTIVE‑выдач, роль с 64 меточными правилами, 10 240 объектов зеркала в области, S = 11, M = 64, K = 227 на горячем объекте;
2. **фон 1** — периодический обход: `ListSelectorBindingIDs` возвращает **все** ACTIVE‑выдачи с меточным селектором **по всему кластеру, без `LIMIT` и без курсора** (`reconcile_adapter.go:1296-1303`), тик 30 с (`seed/reconcile_worker.go:98-100`);
3. **фон 2** — дренаж очереди пересведения: **та же горутина, тот же `select`** (`seed/reconcile_worker.go:152-161`), то есть длинный обход останавливает дренаж отзывов целиком;
4. **фон 3** — истечение сроков своим тикером (`runExpiry`), конкурирующее за те же исключительные блокировки;
5. **фон 4** — производитель событий 5–8/с;
6. **акт**: одно из трёх снятий §2.3 поверх всего этого;
7. **триггер постановки, стоящий ноль**: `kubectl rollout restart` — на старте идут **немедленный** обход (`reconcile_worker.go:150`, «Immediate sweep on boot») **и** немедленное истечение (`reconcile_worker.go:238`), оба до первого дренажа.

Именно эта точка отвечает на вопрос владельца «в максимально загруженном флоу»; отдельные акты §2.2–2.3 — её слагаемые.

## 3. Величины, приборы и контроли

### 3.1 Общие для всех операций

## 4. ОТКАЗНОЙ ПУТЬ ЧТЕНИЯ — отдельной строкой

Ни одна существующая проба его не касается: **24/24 точки — `allow`**. Требования к отказным точкам:

**4.1 Отказ бывает двух разных цен, и точка обязана назвать, какой из них она меряет.**
- **дешёвый отказ**: спрошенного глагола не несёт **ни одна** роль базы ⇒ соединение схлопывается на `role_verb`, до оснований запрос не доходит. Измерено в дереве: **25 против 19** строк, причём меньшее принадлежит отказу (`s2_blockers_integration_test.go`, шапка `TestR7_1_13`);
- **дорогой отказ**: у субъекта **есть** выдачи в области, их роли несут спрошенный глагол, и отвергает **последнее** звено — предикат ветви правила (`query.go:479-482`: `labels @> match_labels` ложно либо идентификатора нет в `resource_names`).

Сетка сеет **второй**. Первый ставится рядом контрольной точкой — иначе отчёт скажет «отказ дёшев», и это будет правдой про фикстуру.

**4.2 Ветвь фактов исполняется на ОБОИХ исходах.** Её `DISTINCT` блокирующий, внешний предел `LIMIT $8 = maxConditionRows` (`query.go:373`) её не подрезает. Значит каждая точка снимается **парой** `allow`/`deny` на одном и том же посеве, и в отчёт идёт **дельта**, а не только отказ; иначе вся дороговизна припишется отказу.

**4.3 Потолок «5.95 млн строк» на читающем пути НЕДОСТИЖИМ, и это результат замера, а не препятствие.** `maxConditionRows = 256` (`query.go:166`) считает выданные различные **условные** строки; при достижении вердикт — **«не знаю»** (`query.go:570-573`), третий исход, а не отказ. Но условное поле не пишет **ни один** производитель: `relation_fact.condition_name` заведено с `DEFAULT ''` (`migrations/0086_relation_fact_condition.sql:36`), а единственный писатель таблицы — триггер `relation_fact_from_journal` (`0100:59,110,172`) — вставляет **без** условных колонок. Предикат: `git grep -n condition_name origin/release/roles-new -- services/iam` даёт ровно `0086`, `expand.go:122-123` и `query.go:360` — **ни одного производителя**.

Отсюда: точка «усечение» ставится **как замер формы** и помечается «на продуктовых данных недостижимо; заведён предмет: кто и когда начнёт писать условие».

**4.4 Ветвь выдач на отказе НЕ исчерпывается целиком, если пара «субъект+область» пуста.** Индекс `access_binding_subjects_subject_scope_idx` (`732001:206`) отсекает чужого субъекта до чтения строк — это и объясняет, почему ось B плоская и **падает** (123→14→14). Поэтому отказная сетка обязана сеять субъекту **реальные** выдачи в области (ось L), иначе она меряет работу индекса.

**4.5 Отказной списочный вопрос.** Худшая страница — та, где доступных **ноль**: доступный кандидат замыкается рано, недоступный оплачивает **обе** ветви `EXISTS ... OR EXISTS` (`list.go:236,253`). Точка `Pg = 5000` законна для замера и **незаконна для края**: `List` верхнего предела не имеет (`list.go:322-325` — только подстановка `DefaultPageSize = 500`), а контрактный потолок `MaxPageSize = 1000` живёт в другом месте (`pkg/validate/validate.go:61`). В отчёте она помечается «сверх контракта».

## 5. ОКНО НЕБЕЗОПАСНОСТИ УДАЛЕНИЯ

**Определение.** От **коммита** акта снятия (транзакция, снявшая право, зафиксирована) до **первого** ответа `PERMISSION_DENIED` на публичном RPC по отозванному объекту. Не до «отзыв применён», не до «очередь пуста» — до наблюдаемого отказа, потому что именно это видит арендатор.

**Шесть слагаемых, каждое засекается порознь:**

| # | слагаемое | чем засекается | объявленное значение |
|---|---|---|---|
| 1 | кэш вердиктов **края** | разница «опрос через край» и «прямой `Check`» | 5 с (`pkg/authz/revocation_policy.go`, ключ `api-gateway KACHO_API_GATEWAY_AUTHZ_CACHE_TTL_SECONDS`) |
| 2 | кэш вердиктов **сервиса‑владельца** | опрос его публичного RPC | 5 с у шести, 2 с у registry (там же) |
| 3 | ожидание в `resource_reconcile_outbox` | `sent_at − created_at` строки | предела нет; ряда метрик нет |
| 4 | время прохода пересведения | обёртка вокруг вызова + `pg_stat_activity` | 2 мин у веера, без предела у истечения и обхода |
| 5 | ожидание в `kacho_iam.fga_outbox` | `sent_at − created_at` строки | голова партиции + `MaxAttempts = 10`, `WedgeWarnAfter = 60s` (`cmd/kacho-iam/fga_outbox_drainer.go:100,126`) |
| 6 | применение к движку | журнал доступа движка / счётчик клиента | пропускная способность дренажа **448 строк/с** при `ApplyConcurrency = 16` (`fga_outbox_drainer.go:68,83`) |

**Потолок политики ложен для этого пути и это надо сказать числом.** `Ceiling: 10 * time.Second` (`revocation_policy.go:117`) сложен из «срок записи + дренаж + запас» и слагаемых 3–4 не содержит вовсе. Перепись окон: ключей в карте **11**, процессов **7** (предикаты: `sed -n '145,182p' | grep -cE '^\s+"'` → 11; `grep -oP '^\s+"\K[a-z-]+' | sort -u | wc -l` → 7). Комментарий карты называет «8 площадок, 7 процессов» — он сам устарел.

**Обязательные усилители окна (ставятся отдельными точками):**
- отравленная строка **выдачи** на том же ключе партиции, что у отзыва: отзыв встаёт за ней, и это видно только по `..._by_direction`;
- отравленный **отзыв**: возвращает его в работу только смена версии модели прав (`fga_outbox_redrive_backstop.go`) — значит за время замера версия модели меняться **не должна**, иначе окно схлопнется искусственно;
- обход в разгаре: пока он держит пообъектные исключительные блокировки, синхронный форвард правки метки выбирает свой бюджет и падает в очередь, которую тот же обход голодает.

## 6. Что НЕДОСТИЖИМО на стенде и почему — с числами

### 6.1 Пределы приёмки L = 128 и L_m = 32 в дереве отсутствуют
Предикат: `git grep -nE 'maxBindingsPerSubject|MaxBindings|maxMemberships|MaxGroupMembers' origin/release/roles-new -- services/iam` → пусто; единственное попадание на «32» в домене — `MaxSubjectsPerBinding` (`domain/subject.go:65`), это другая величина. **Следствие:** формулы приёмки R7‑1 описывают состояние, которого код не держит. Точки L и M ставятся **сверх** заявленного и помечаются «предел объявлен приёмкой, в дереве отсутствует».

### 6.2 Пределы iam объявлены и НЕ энфорсятся
Объявлены: `iam.user 128`, `iam.serviceAccount 128`, `iam.group 64`, `iam.role 64`, `iam.accessBinding 512` (`migrations/0094:102-108`). Энфорсинга нет: таблицы учёта для видов iam в дереве **нет** (предикат: `git grep -lE 'resource_usage|usage_counter' -- services/iam/internal/migrations` → пусто), триггеры `0092` стоят на самой таблице `limits` (ревизия, ссылочная целостность, снятие при удалении области), а не на `access_bindings`/`groups`/`roles`; в use‑cases обращений к пределам нет (`git grep -ln 'limits\.\|usage\|Limits(' -- .../api/{access_binding,group,role,user}` → пусто).
**Следствие:** точки M = 1024 и L = 512 физически посеваются, но описывают состояние, **которое продукт объявил невозможным и не проверяет**. Это обязано стоять в отчёте — иначе «потолок продукта» окажется числом про непризнанное состояние.

### 6.3 Веер 10 000 выдач на роль — неисполним по времени посева
10 000 ACTIVE‑выдач одной роли требуют 10 000 **различных** субъектов (частичный UNIQUE, `0003:99-102`). При 10 140 членах и 5 глаголах: членов 1.014·10⁸, строк реестра 5.07·10⁸, столько же различных кортежей в движке. При измеренной пропускной способности дренажа **448 строк/с** это ≈1.13·10⁶ с ≈ **13.1 суток** только на посев кортежей — без них нет «разрешено», а значит у несущей величины «время до первого отказа» **нет предмета**.
**Решение:** верхняя точка веера — **512**; поведение выше утверждается **наклоном** по трём точкам и называется экстраполяцией.

### 6.4 Точка отказа отвечать (256 условий) — недостижима на продуктовых данных
См. §4.3. Ставится как замер формы, помечается.

### 6.5 S = 341 — состояние ВЛАДЕЛЬЦА, не арендатора
Форму цепи никто не проверяет: `RegisterResource` передаёт `ParentChain` как есть (`register_resource.go:348`), ограничивает только `CHECK (depth BETWEEN 1 AND 4)`. Производители сегодня шлют одно‑два звена (наблюдаемое `S_набл = 7`). Точка помечается «посевная»; если решат, что состояние недостижимо, предметом становится не замер, а **гейт на форму цепи, которого нет**.

### 6.6 Верхние уровни прав сегодня не находятся
Рёбер `project→account` и `account→cluster` не пишет никто (предмет заведён, `kacho#740`; сказано в шапке `query.go:215-234`). Значит атомы фактов на предках типов `account` и `cluster` ищут в пустоте, и сегодняшний замер даёт стоимость **неполного** вердикта. Чтобы точки не устарели в день закрытия #740, цепь фикстуры **обязана** нести оба ребра, а отчёт — назвать это состоянием **после** #740.

### 6.7 N > 10⁴ у движка недостижимо
L1 линеен по N: 45.3 мс (10) → 434.1 (100) → 4809.1 (1000) → 45 656.6 (10⁴) (`REPORT-XC-12-F5-labelpath-2026-08-12.raw.txt`). Экстраполяция: 10⁵ ≈ 7.6 мин на один повтор L1 плюс столько же на L5; 10⁶ ≈ 12.7 ч. Верхняя точка рамки B остаётся **10⁴**.

### 6.8 Что нельзя сеять «дословными стейтментами производителя»
`resource_mirror` и `resource_parent_edge` сеять напрямую **можно**: они **вход**, стейтменты скопированы дословно и держатся построчной сверкой (`scalegrid/seed.go:152-155`, проба `TestScaleGridSeeder_RowForRowMatchesTheProducer`). `access_binding_target_members` и `access_binding_emitted_tuples` сеять напрямую **нельзя**: они **выход материализатора**, то есть ровно то, что меряет сторона записи. Досеяв их, замер описал бы представление фикстуры о материализации.

**Три правила порядка, каждое стоило прогона:**
- **полный прогон рамки A идёт ПОСЛЕДНИМ по правкам кода**: отпечаток предмета снимается в начале прогона, и правка любого файла под ним после старта делает отчёт несвежим **в момент рождения** (`Makefile:477-484`). Под отпечатком — все не‑тестовые `.go` каталогов `relverdict` и `scalegrid` плюс миграции, называющие читаемые вердиктом таблицы (`scalegrid/fingerprint.go:51-53`); тестовые файлы и Makefile — **нет**;
- **`ANALYZE` внутри посева каждой точки** обязателен: без него оси прибора расходятся на одной фикстуре;
- **оси нельзя гонять по одной ключом `-run`**: полная сетка — **один** тест `TestScaleGrid_FullGridReport`, оси идут циклом внутри, отчёт один. Разделение требует правки кода под отпечатком.

### 8.2 Артефакты результата

- **`REPORT-R7-2-strength.txt`** рядом с существующим отчётом сетки: провенанс, отпечаток предмета пофайлово, сетка со всеми осями и её отпечаток, строка воспроизведения дословно, объём осмотренного, перепись по каждой таблице в каждой точке, доля неотнесённого, исход вердикта в каждой точке.

- **Оба отчёта — файлы дерева**, а не вывод прогона: иначе число нельзя оспорить.

### 8.3 Что попадает в конвейер, а что остаётся ручным

| | конвейер | ручной |
|---|---|---|
| рамка A | `make scale-grid-small` — **отсутствие деградации**: отношение верхней точки к нижней против потолка, объявленного константой до прогона, плюс положительный контроль по оси, которая обязана расти | `make scale-grid-full` (`-timeout 120m`) |
| гейт свежести | `TestScaleGridFullReportIsFreshAndItsSubjectHasNotMoved` (`scalegrid/freshness_test.go:157`) — **без build‑тега и без skip по `-short`**, то есть красит `go test ./... -short`; его способность падать и молчать доказана `TestScaleGridFreshnessGateCanFailAndCanStaySilent` (там же, :197) | — |
| рамка B | ничего: требует стенда и часов | всё |
| гейт производимости посева | **новый**: посеянное отношение факта обязано быть таким, какое пишет триггер `0100` (неглагольным). Сегодня `QueueRaw`‑посев ни с одним производителем не сверяется — именно туда попали непроизводимые `v_*`‑строки | — |

### 8.4 Три утверждения, которые отчёт обязан нести дословно

1. **«Числа рамки A описывают путь, который сегодня решения не принимает».** Иначе они будут прочитаны как характеристика продакшена.
2. **«Точки L ≥ 512, M ≥ 128 и S = 341 описывают состояние, которое продукт объявил невозможным (0094) либо не проверяет (0082 + RegisterResource) и не энфорсит».** Иначе «потолок продукта» окажется числом про непризнанное состояние.
3. **«Ноль отказов, ноль доставленных строк, ноль осмотренного — это ТРЕТИЙ исход»**, а не успех: перепись объёма осмотренного печатается всегда, и «не выполнилось» никогда не вычитается из вердикта и не зачитывается в него.
