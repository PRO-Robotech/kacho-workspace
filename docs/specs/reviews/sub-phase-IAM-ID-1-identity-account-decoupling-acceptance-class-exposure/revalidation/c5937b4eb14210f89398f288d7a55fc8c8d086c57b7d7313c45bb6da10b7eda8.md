## Что изменил механизм (дельта f4ffbd08 → c5937b4e)

Редакция 18 называла аккаунт «из контекста вызывающего (сессия)». Разведка это опровергла деревом:
`HumanSession` несёт только `UserID`, поля аккаунта у сессии нет (§1.5), «активный аккаунт» при N
членствах не определён by construction (§В-7) — назвать аккаунт из сессии было **нечем**. Редакция
19 (решение владельца, делегировано диспетчеру): аккаунт берётся из **явного скоупа запроса** (путь
`GET /iam/v1/accounts/{accountId}/users/{userId}` для `v_get` и аналог для `v_list`, как IAM-ID-2
§1301), вызывающий (субъект `Check`) — из проверенной сессии (`UserID`), гейт = вызывающий
`super_admin` **названного** аккаунта. Объект `iam_membership:(<скоуп-аккаунт>, user)` — **сохранён**.

**Что смена источника СНЯЛА (классы ред.18, растворённые ред.19):**

- **A2 «пустой/невыбранный аккаунт сессии → fail-closed»** — исчез: аккаунт больше не выбирается из
  сессии, он — обязательный сегмент пути; его отсутствие даёт **промах маршрута** (путь не совпал),
  а не fail-closed решение авторизации на неоднозначной сессии;
- **контракт канала «аккаунт из сессии»** — исчез: из сессии не наследуется ничего, кроме `UserID`
  (§В-7 соблюдён), отдельного транспорта аккаунта не требуется;
- **B3 «схема ключа не названа → опорный `mbr-id` → резолв → новое runtime-ребро kacho→kaname → новая
  пересверка»** — **разрешён**: ключ назван композитом `(аккаунт, user)`, край собирает объект
  локально из пути и запроса **без резолва**, значит **нового runtime-ребра нет** и новой пересверки
  этот механизм не требует.

**Что смена источника ВНЕСЛА (см. C1/C2 ниже) и что ПЕРЕНЕСЛА без изменения (B1, самочтение, hide-existence).**

## Чего измерить нельзя (доказательство на пункт, не число)

- **C1 — извлечение аккаунта из скоупа-пути без реинтродукции поля.** Предиката нет: приёмка
  называет СЕМАНТИКУ («скоуп-путь — форма, не фильтр»; поле `account_id` не добавляется) и делегирует
  ТРАНСПОРТ предфазе S3.1. Замер показал стык: IAM-ID-2 (образец, на который ссылается врезка) делает
  аккаунт-скоупный путь, **биндя аккаунт как ПОЛЕ** запроса (`account_id`); для USER это ровно снятое
  §2.3 поле. Текущий scope_extractor края читает **поле запроса**, а не сегмент пути, не ставший
  полем. Значит «ровно по образцу IAM-ID-2 §1301» **не переносится буквально**: перенос образца
  воскресил бы `account_id` в `GetUserRequest`. Как именно `{accountId}` доедет до сборки объекта, не
  став полем backend-запроса, — **не измерить, обязано быть НАЗВАНО** приёмкой предфазы S3.1 до кода
  края. Класс `code-authoring §«Контракт, который нельзя выразить»` (снятое поле не воскрешать) +
  `§«Унификация и стоимость»` (перенос образца берёт его биндинг-как-поле — узкую семантику).
- **B1 — когерентность строкового ключа композита край↔reconciler.** Схема пары НАЗВАНА (ред.19
  сняла B3 ред.18), но конкретная СТРОКА композита `iam_membership:<X>` не названа. Край собирает
  `<X>`, реконсайлер материализует `<X>`; расхождение проходит структурную красную полосу и в рантайме
  даёт fail-closed — админу НАЗВАННОГО аккаунта тоже отказ. Держатель — только сквозная проба
  (реальный `Check` на реально материализованном членстве). Заказ integration-tester.
- **C2 — аналог REST-пути для `v_list`.** Врезка называет путь `v_get`
  (`…/accounts/{accountId}/users/{userId}`), но «аналог для `v_list`» (сегодня
  `…/users/{user_id}/operations`) буквально не выписан. Точная РЕСТ-форма обоих — предмет приёмки
  предфазы S3.1.
- **Истинность целевой формы модели** (разрешение относительно НАЗВАННОГО аккаунта) — форма оставлена исполнителю, проверяется ИСХОДОМ; держатель — IAM-ID-1-31 и близнец
  (модель × каталог), стенд не нужен. Заказ integration-tester.

  - **kaname-волна ✅ «к коду»** — model+catalog · migration · reconciler: условия названы, держатели
    есть (гейты дрейфа/паритета/покрытия + красная полоса), и все они **материализуют композит-членство,
    не завися от источника аккаунта**; красный B1/B2 честен (`iam_membership` = 0 в модели, каталоге,
    миграциях и реконсайлере). Единственное сквозное условие — строковая схема композита `iam_membership:<X>`
    как контракт когерентности с краем (B1): реконсайлер вправе стартовать, зафиксировав её.
  - **полоса КРАЯ ⛔** — блокер до приёмки предфазы S3.1: C1 (извлечение из скоупа-пути без поля,
    §2.3), C2 (точная РЕСТ-форма `v_get` и аналог `v_list`), строковая схема композита (B1).
- **вернуть-в-приёмку ∅** — неизмеренных утверждений о дереве, ложных на dd66b5be/ac33f733, нет:
  §2.3 соблюдён на уровне контракта (`GetUserRequest`/`ListUserOperationsRequest` несут только
  `user_id`), IAM-ID-2 §1301 — валидный СЕМАНТИЧЕСКИЙ прецедент (форма, не фильтр), транспорт законно
  делегирован предфазе S3.1 (§2.5/§6а). Given, запрещённых схемой, нет (31/57 — зависимость предфазы).
- **блокер** — для моего разбора нет. Для landing полосы КРАЯ — приёмка предфазы S3.1 (её нет: ни
  одного файла S3.1 в `docs/specs/`). kaname-волна блокера не имеет.

### Вернуть в приёмку

Пусто. §2.3 соблюдён на уровне контракта; ссылка на IAM-ID-2 §1301 — семантический прецедент, не
утверждение о дереве; точная РЕСТ-форма и извлечение из пути без поля — предмет ПОЛОСЫ КРАЯ и приёмки
предфазы S3.1, а не пробел этой приёмки. Риск doc-truthfulness («ровно по образцу IAM-ID-2 §1301»
может увести исполнителя к биндингу `account_id`-полем) назван заказом предфазе S3.1, не блокером.

### Полоса КРАЯ — нужна ОТДЕЛЬНАЯ приёмка предфазы S3.1: ДА

Контракт **не достаточен** для кода края. Приёмка предфазы S3.1 обязана назвать три вещи:
1. **точную РЕСТ-форму** аккаунт-скоупного пути USER для `v_get` (`GET /iam/v1/accounts/{accountId}/users/{userId}`)
   И его аналог для `v_list` (сегодня `…/users/{user_id}/operations` — форма аккаунт-скоупного варианта не выписана);
2. **как `{accountId}` доезжает до сборки authz-объекта на крае, не становясь полем backend-запроса**
   (§2.3: `account_id` снят с `GetUserRequest`; образец IAM-ID-2 биндит аккаунт полем — буквальный
   перенос воскресил бы снятое поле). Требуется назвать режим: чтение сырого сегмента пути на слое
   авторизации / новый режим scope_extractor «сегмент пути» / код-ведомое извлечение, привязанное к FQN;
3. **строковую схему композитного объекта** `iam_membership:(account, user)` — байт-совпадение края и
   реконсайлера (B1).

### Заказы (адресат · предмет · основание)

- **owner / диспетчер → acceptance-reviewer предфазы S3.1** · завести приёмку предфазы S3.1 и назвать
  три вещи выше (РЕСТ-форма обоих путей · извлечение из пути без реинтродукции поля · строковая схема
  композита) ДО кода полосы КРАЯ · `change-graph.md §4`, `api-conventions §«Принято-и-проигнорировано»`/§2.3,
  `code-authoring §«Контракт, который нельзя выразить»`.
- **integration-tester** · сквозная проба СКВОЗЬ край (сверх структурной): (а) реальный `Check` на
  реально материализованном КОМПОЗИТНОМ членстве — ключ края == ключ реконсайлера, иначе fail-closed
  админу названного аккаунта (B1, `security-hardening §«Разрыв, невидимый ни с одной стороны»`); (б)
  чужой аккаунт в пути → отказ, побайтово как промах (hide-existence #6); (в) отсутствующий сегмент
  аккаунта → **промах маршрута** (не оракул авторизации); (г) близнец самочтения — `iam_membership.v_get`
  несёт `subject`; (д) положительный близнец IAM-ID-1-31 (админ названного аккаунта проходит) +
  IAM-ID-1-57 (облако — в обоих контекстах). Структурная красная полоса этого не держит by construction.
- **go-implementer (kaname: model/catalog · migration · reconciler)** · после одобрения ред.19 —
  стартовать НЕ дожидаясь края: тип `iam_membership` (обе копии байт-идентичны, `account: [account]`,
  `super_admin: admin from account`, `v_get = … or subject or super_admin`, `v_list = … or super_admin`);
  смена `object_type` двух записей; ветвь `resource_scope_edge`; материализация композита реконсайлером
  (не на create-path, ban #9), зафиксировав строковую схему `iam_membership:<X>` как контракт B1 · условия
  таблицы выше, `security.md §«Авторизация живёт в МОДЕЛИ»`, ban #14.

### Направление рёбер

- `kacho (gateway/край) → kaname (AuthorizeService.Check)` — **существующее, направление не меняется**.
  Аккаунтная ось теперь **край-локальна** (из сегмента пути), не из канала сессии. **Нового runtime-ребра
  нет** (резолва `(account,user)→mbr-id` ред.19 избегает композитным ключом). Асинхронный путь
  (reconciler → outbox → FGA) — тот же, что был в ред.18, не новый.

### Петля накопления

Нового класса корпуса не завожу. Наблюдённое — экземпляры уже записанного: перенос аккаунт-скоупного
образца, биндящего скоуп ПОЛЕМ, туда, где поле снято = `code-authoring §«Унификация и стоимость»`
(узкая семантика образца) + `§«Контракт, который нельзя выразить»` (снятое поле не воскрешать);
когерентность композитного ключа край↔reconciler = `security-hardening §«Разрыв, невидимый ни с одной
стороны»`; структурная проба, слепая к рантайму = `gate-authoring §«распознаватель обязан знать все
формы»`. Цена C1 (воскрешение §2.3-поля через биндинг пути) пока **потенциальна**, не материализована —
это находка/заказ, не запись класса (порог `code-authoring §«Механизм накопления»` не достигнут).
Однофайлового признака для `class-guard` нет: предмет — когерентность каталога, модели, реконсайлера,
края и REST-маршрута (пять фрагментов пяти деревьев), а не одна строка.
