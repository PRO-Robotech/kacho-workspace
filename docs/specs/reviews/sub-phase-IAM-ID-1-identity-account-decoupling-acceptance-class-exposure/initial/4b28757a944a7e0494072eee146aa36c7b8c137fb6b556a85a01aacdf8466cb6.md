## Решения, которые вносит замысел (S3.1 «одним изменением», §666)

1. **Тип членства в модели прав** — ввести тип `iam_membership` в `fga_model.fga`.
2. **Перевыраженный источник каскада для личности** — вопрос о доступе к объекту личности
   разрешается относительно НАЗВАННОГО аккаунта (через членство); прежний источник каскада
   снимается тем же изменением.
3. **Смена объекта гейта** — у записей каталога прав на аккаунт-скоупный вопрос о личности
   меняется `object_type` (`iam_user` → тип членства), у края меняется, из какого поля берётся
   объект, вместе с ними — строка таблицы форм ответа края, ключуемая типом.
4. **Префикс `mbr` в платформенном каталоге дефис-префиксов** (§2.1а).
5. **Глаголы ресурса членства** сверх посаженного исключения из аккаунта: создание и два
   чтения (§5.0 п. 0); снятие уже есть (§1.9), `Delete` у ресурса членства не заводится.
6. **Записи каталога прав на новый тип** (плюс согласованность копий модели/каталога).
7. **Порядок/атомарность**: модель и её замена приземляются ВМЕСТЕ, до переезда приглашения
   (S3.2), иначе половина изменения отнимает доступ (fail-closed).

## Чего измерить нельзя (доказательство на пункт, не число)

- **Верна ли целевая форма модели** (условие §2.3а: разрешение относительно НАЗВАННОГО аккаунта) — предиката нет: форму замысел оставляет исполнителю, а истинность разрешения проверяется ИСХОДОМ (вердикт по закоммиченным строкам), а не грепом. Держатель — сценарий IAM-ID-1-31 и модельные гейты семейства `authzmap/*_test.go`; их конструирует автор проб.
- **Свежесть `origin/main` kaname** — `git fetch` не прошёл (ssh-agent). Все числа — на последнем известном `f8fc5a37` (2026-09-18 19:36). Более свежий ствол мог бы сдвинуть их; перемерить после успешного fetch.
- **Каков сегодняшний исход разрешения на объекте личности** — предикатом по дереву не устанавливается: разрешение проверяется ИСХОДОМ, а не грепом, и подтверждается только прогоном различающего сценария **IAM-ID-1-31**. Это заказ integration-tester (честный красный), не мой замер; цепочка разрешения здесь не воспроизводится (`security-disclosure §«Проверяемый признак…»`).

**вернуть-в-приёмку** ⛔ **непусто** (раздел ниже) — обесценивает вердикт приёмки и требует
перебазировки её S3.1-предикатов на субъект-дерево до пересверки замысла.

**блокер** — для МОЕГО разбора нет; для следующих по контуру: если integration-tester и

## Петля накопления

Наблюдённый класс (кандидат, порог «один раз с измеренной ценой»): **«приёмка меряет предикатами
одного дерева, а субъект переехал в другое (репозиторий фундамента + вынесенная служба) —
перечень работ описывает несделанное, которое сделано вне субъект-дерева»**. Цена измерена: 4 из
6 пунктов S3.1 приёмки уже исполнены в kaname/corelib, чего монорепо-предикат не показывает.
Противоядие — «объявить субъект-дерево и перемерить по нему» → владелец `measurement-discipline`
(§«Радиус по имени механизма», §«Разбор совпадений по референту»). Предложение записи — не мой
акт: возвращается диспетчеру строкой «нужен следующий: tooling-maintainer».
