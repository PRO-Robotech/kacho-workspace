> **Effective acceptance verdict:** `APPROVED`, по bootstrap-review artifact того же SHA и

> **Ревизии:** `workspace@eafd100fc911dcf6759d72337e038b258c310948`,
> `kacho@b59191a90bfd2fba52f8c143977dfe0142a7d67a`
> **Снимок рабочего дерева:** `2026-09-02T00:19:46Z`

Это initial-анализ **до кода**. Он связывается с acceptance SHA, а не с будущим
design. После появления design каждый пункт `CGX-*` должен получить exact mapping в
решение design и отдельную revalidation на SHA design. Здесь нет verdict по design и
нет разрешения писать implementation.

Осмотрено: acceptance и его 196 case IDs; bootstrap review artifact; четыре
обязательных rule-модуля; `ai-tooling.md`, `vault.md` и узкая vault-записка о CI;
контракты семи участвующих ролей; все 65 tracked-файлов `.claude`; четыре
authoritative caller-файла в двух репозиториях; 71 существующий candidate derived
file на диске. Состав tracked-деревьев читался по указанным ревизиям; untracked и
dirty state — отдельный датированный снимок, не свойство этих ревизий.

## Решения, которые вносит замысел

1. `D1` — acceptance subject остаётся static `DRAFT`; effective verdict живёт во
   внешнем event и append-only artifact, связанном с exact subject hash.
2. `D2` — новый change описывается package из раздельных truth owners:
   acceptance, design, tasks, manifest, holders, reviews и evidence.
3. `D3` — вводится обязательный lifecycle с последовательными stages и
   направленной invalidation downstream-артефактов при изменении upstream bytes.
4. `D4` — class exposure становится двухтактным durable предметом: initial на
   acceptance hash и revalidation mapped design на design hash.
5. `D5` — applicability профильных review задаётся реестром predicate IDs; свободный
   текст `N/A` перестаёт быть доказательством.
6. `D6` — integration-tester единолично производит pre-RED tests/fixtures и первый
   доказанный RED; implementation начинается только после `RED_PROVEN`.
7. `D7` — machine/human holders получают точную provenance и ровно один из трёх
   исходов: `GREEN`, `RED`, `NOT_EXECUTED`.
8. `D8` — acceptance, design, tasks, evidence, actual diff, specialist reviews,
   convergence и landing связываются exact sets и content identity.
9. `D9` — cutover определяется отдельно в двух Git DAG; active legacy changes
   фиксируются свежим внешним census и получают route `legacy|migrate`.
10. `D10` — `.claude` остаётся единственным canonical input, а `AGENTS.md`,
    `.agents/**` и `.codex/**` становятся tracked deterministic adapter outputs.
11. `D11` — authority обеспечивают ровно четыре blocking caller: pre-push и CI в
    workspace и product; session hooks остаются advisory.
12. `D12` — convergence принадлежит отдельной роли и связывается с canonical
    repo/path/mode/blob/deletion set; landing судит applied content, а не один SHA.
13. `D13` — SDD-1 остаётся единственным bootstrap; закрытые historical acceptance
    не backfill-ятся, а активный legacy contract мигрирует только явно.

## Классы дефектов, которые замысел может задеть

1. Approval как самодекларация: строка статуса или имя роли подменяет внешнюю
   authority.
2. Hash-цикл и stale approval: artifact включает себя в digest либо downstream
   остаётся действующим после изменения upstream.
3. Объявленное состояние оторвано от оснований: `change.yaml` говорит `CONVERGED`,
   а eligibility по текущим bytes уже ложна.
4. Третий исход слит с одним из двух: недоступный GitHub/ref/sibling/tool читается
   как успех или как дефект продукта.
5. Default-ветка внешнего ответа выбирает политику: неизвестный ответ API молча
   становится retryable, terminal либо approved.
6. Ложный RED: crash, отсутствующая команда или synthetic ответ harness принимается
   за отсутствие production capability.
7. Неполная входная поверхность: один из четырёх caller получает иной набор
   repo/base/head/policy coordinates или вообще не вызывает gate.
8. Два написания одной истины: prose, lifecycle state, case IDs или authority живут
   одновременно в нескольких нормативных местах.
9. Унификация расширяет семантику: новый общий role/adapter/gate ослабляет более
   узкое существующее правило или оставляет двух владельцев RED.
10. Производная оснастка существует без читателя либо читатель понимает другой
    диалект, путь или формат.
11. Принадлежность судится по имени: repo/branch/role/path label используется вместо
    repo identity, immutable event identity и content digest.
12. Cutover начинается с contract-фазы: старые producers/active changes ещё живы,
    а прежний route или consumer уже снят.
13. Backfill изобретает историю: закрытые acceptance переписываются либо active
    change классифицируется по локальной памяти вместо внешнего census.
14. Стоимость проверки принадлежит строке/case, а не одному candidate invocation:
    196 fixtures умножают одинаковые GitHub fetch/hash/generation действия.
15. Specialist applicability допускает свободное `N/A`, перезапись verdict другого
    role либо пропуск повторного review после изменения relevant surface.
16. Convergence связывается с commit name, но не с фактически применёнными bytes в
    обоих репозиториях.
17. Generator/gate читает грязный общий checkout и присваивает либо перезаписывает
    работу другого writer.
18. Public evidence захватывает host paths, credentials, API headers или лишний
    operational output вместо минимальной проверяемой provenance.

## Числа, которые надо получить повторно перед соответствующим шагом

1. **Перед design approval:** exact inventory всех canonical input references и
   всех adapter-owned outputs; по каждому из 18 disk skill packages — явная
   классификация и полный nested file set. Снимок выше не заменяет решение ownership.
2. **Перед RED:** planned fixture set должен exact-set совпасть с 196 acceptance IDs;
   у каждого negative/NOT_EXECUTED fixture — один named fact и существующий positive twin.
3. **Перед первой implementation-записью:** fresh dirty baseline отдельно для обоих
   repos и path ownership; текущие 34/1 — датированный ориентир, не разрешение трогать их.
4. **Перед cutover:** независимый GitHub census open PR и live in-progress Issues в
   обоих repos с query, ETag/revision, timestamp и response digest. Получать его сейчас
   как durable истину нельзя: к landing он протухнет.
5. **Перед policy finalization:** оба выбранных cutover objects должны уже существовать
   в своих repos; проверить object membership и ancestry в обе стороны. Future/self SHA
   не является допустимой координатой.
6. **Перед convergence:** actual changed repo/path/mode/blob/deletion exact set,
   applicable role set и review-record set; counts без members не принимаются.
7. **Перед landing:** пересчитать applied content по landed commits и re-read dirty
   state; SHA новой посадки не переносит старый verdict автоматически.

## Чего измерить нельзя

- Semantic duplication, open decision и качество truth ownership не имеют надёжного
  текстового предиката. Их разбирает authorized human semantic holder; machine gate
  проверяет только наличие, authority, binding и verdict.
- Какие из пяти disk-only skill packages должны стать adapter-owned, нельзя вывести из
  происхождения или наличия. Нужна явная design-классификация по потребителю каждого.
- Реальный active legacy set нельзя доказать локальным деревом и нельзя долговечно
  зафиксировать ранним snapshot. Его производит landing-time GitHub census.
- Cutover SHA и landed SHA ещё не существуют как предмет решения. Записывать placeholders
  или угадывать будущие hashes запрещено; staged protocol обязан сначала создать objects.
- Принадлежность нынешних untracked файлов конкретному writer нельзя вывести из bytes.
  Поэтому законный исход — сохранить их и работать только в явно назначенных paths.

## Заказы соседям

- `design-author`: exact-map-ить `CGX-01..CGX-22`; закрыть digest DAG, trusted-policy
  epoch, staged two-repo cutover без self/future SHA, единый CLI input schema,
  deterministic validation order, adapter ownership и runtime exclusions.
- `class-exposure-analyst` revalidation: после design проверить тот же item set на
  exact design SHA; новый external call, async path, sentinel или output namespace
  добавляет новый item, а не прячется в существующий.
- `integration-tester`: построить 196 pre-RED fixtures и отдельные birth probes;
  дополнительно обязаны краснеть self-authorizing policy, digest self-cycle, partial
  two-repo landing, foreign/runtime adapter capture, dirty-tree overwrite и каждый из
  четырёх real caller paths.
- `system-design-reviewer`: до кода проверить partial-order посадки двух repos,
  authority epoch, cross-repo pinning и отсутствие циклических зависимостей; после diff
  повторить review на exact content digest.
- `security-surface`/security reviewer: проверить public evidence minimization,
  permission trust root, отсутствие credentials/host paths и безопасную обработку API
  unavailable/rate-limit outcomes.
- `landing-reviewer`: получить fresh census, выбрать только уже существующие cutover
  commits, сохранить чужой dirty work, сверить applied content обоих repos и только
  затем выпустить LANDED/ARCHIVED.
- `migration-writer`, `db-architect-reviewer`, `proto-api-reviewer`: по текущему scope
  предмета нет; это не свободный `N/A`. Design обязан сослаться на registered predicate
  и evidence, что diff действительно не трогает SQL/proto/schema.
