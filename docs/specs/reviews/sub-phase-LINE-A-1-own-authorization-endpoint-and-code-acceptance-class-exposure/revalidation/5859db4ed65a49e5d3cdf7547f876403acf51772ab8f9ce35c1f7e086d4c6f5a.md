## Что делает эта пересверка

меняет **ИСТОЧНИК** реализации: церемония портируется из fosite (`ory/hydra@v26.2.0/fosite`), а не

  трёх строк атрибуции ЛИБО без `THIRD-PARTY-NOTICES`/копии `LICENSE`.
- **Что должно быть верно в коде:** каждый ported/derived файл несёт `// Copyright © <год-ИЗ-ШАПКИ-ИСХОДНИКА> Ory Corp` + `// SPDX-License-Identifier: Apache-2.0` + `// Adapted from github.com/ory/hydra/v2/fosite@v26.2.0, modified by PRO-Robotech`; год берётся **пофайлово** (перемерено: `storage.go` = 2025, `x/fosite_storer.go` = 2022 — **НЕ единая константа**); заведён `THIRD-PARTY-NOTICES` (перечень ported-файлов и происхождение) + копия `LICENSE` (Apache-2.0, есть в корне И в `fosite/LICENSE` клона — перемерено).

Файл, живущий **только в kaname**, пары не образует ⇒ гейту нечего судить. При появлении пары (тот же файл во втором нашем стволе) применяется `vendored` (владелец вне наших репозиториев). Порт **и не go-зависимость**: `fosite/go.mod` **ОТСУТСТВУЕТ** (перемерено — fosite встроен в модуль `github.com/ory/hydra/v2`), вносится адаптированный ИСХОДНИК, не модуль в `go.mod`. Пары fosite/ory в стволах сегодня **нет** (перемерено: `grep -niE 'fosite|ory|hydra' docs/crossrepo-pairs.yaml` → пусто; в kaname есть лишь `hydra_urls_test.go` и newman-selftest — артефакты СУЩЕСТВУЮЩЕЙ Hydra-фасадной интеграции, не ported-исходник).

Это честно названо замыслом (L0 held-by). crossrepo-gate сработал бы только на ПАРЕ, а это другой класс. → **заказ ратификации** ниже.

Порога §6 на новую запись скила не достигает (один порт, цена необратима лишь при публикации без атрибуции — ловится ДО посадки ратификацией). ### Класс B — поверхность реализации fosite storage-интерфейсов (§2 З5, §4.1)

- **Признак (виден при вводе).** Мы реализуем на pgx/sqlc интерфейсы, чей контракт задаёт **чужой upstream** (fosite): `AuthorizeCodeStorage`, `AccessTokenStorage`, `RefreshTokenStorage` (с `RotateRefreshToken`), `PKCERequestStorage`, `TokenRevocationStorage`. Наборы методов **перемерены на клоне** (§«Числа»).
- **Что должно быть верно в коде:**
  1. **Хранение по СИГНАТУРЕ (хэш), не по значению** — секрет не хранится by construction (`security-hardening §Hardening п.2`); подтверждено: все `Create*Session` принимают `signature string`. Совпадает с §8.10 приёмки.
  2. **Одноразовость** — `InvalidateAuthorizeCodeSession` = одностатементный атомарный CAS (`UPDATE … WHERE active … RETURNING`), 0 строк → `fosite.ErrInvalidatedAuthorizeCode`; срок — предикат БАЗЫ (`code-authoring §2.1`, ban #10).
  3. **Ротация** — `RotateRefreshToken(requestID, signature)` помечает предшественника `active=false` ТОЙ ЖЕ транзакцией, что создаёт преемника, тот же `request_id` (`code-authoring §2.1`).
  4. **Флаг `active`/`invalidated` — ОТДЕЛЬНО от области значений** (не перегрузка легального значения; `code-authoring §1.3` sentinel).
  5. **НАШ storage обязан возвращать ИМЕННО те sentinel-ошибки, на которые переключается порт** (`ErrInvalidatedAuthorizeCode`/`ErrInactiveToken`/`ErrNotFound`) — иначе портированные reuse-detection и анти-оракул ломаются молча. Это `code-authoring §6.1` (реализация чужого интерфейса берёт **точную** его семантику, не более широкую) и `§3.1` (нет корзины «прочее» в трансляции наших SQL-ошибок в контракт fosite).
- **Держится:** integration-проба конкуренции (ровно один успех CAS — заказ `integration-tester`); `db-architect-reviewer` (схема бэкит интерфейсы); **tree-gate на ban #10 для нового хранилища НЕТ** → держится пробой. **НОВОЕ против bespoke:** проба-**соответствие** нашей реализации контракту интерфейсов fosite (правильные sentinel-ошибки) — у bespoke upstream-контракта не было, у порта он несущий. → заказ ниже.

### Класс C — край-адаптация под stateless-JWT (§2 З4; НАША, не из fosite)

- **Признак.** fosite `RevokeAccessToken(requestID)` инвалидирует строки **в хранилище** (модель интроспекции/opaque-токена — подтверждено godoc интерфейса и сигнатурой). Наш предъявитель доступа — **stateless JWT**, который край проверяет подписью + чтением отсечки БЕЗ похода в хранилище на предъявлении. Порт fosite сам по себе отзыв на нашем крае **не энфорсит**.
- **Что должно быть верно в коде:**
  1. Наш `TokenRevocationStorage` пишет family-отзыв ключом `request_id`; край на предъявлении **читает** его по `request_id`-claim (штампуется нашей выдачей в JWT), рядом с уже работающим субъект-читателем, **тем же** внутренним вызовом, один round-trip (`code-authoring §6.2`).
  2. **Обе проверки fail-closed, ни одна не подменяет другую** (`security-hardening §Контроль на ВЫДАЧЕ, но не на ПРЕДЪЯВЛЕНИИ` + `§Разрыв, невидимый ни с одной стороны`). Субъект-отсечка (`user_token_revocations`, ключ `user_id`) и family-отзыв (`request_id`) — **две полосы одного механизма** (энфорсмент отзыва на крае): свойство fail-closed обязано держаться в ОБЕИХ, и это сверка полос, а не проверка каждой отдельно (`architecture §Параллельные полосы одного механизма обязаны сверяться МЕЖДУ СОБОЙ`).
  3. **Кросс-репо атомарность L5↔L6 одной волной** (порядок expand→migrate→contract): kaname штампует `request_id`-claim (L5, край игнорирует неизвестный claim), затем край-читатель (L6). Пока L6 не сел — отзыв «пишется, но не энфорсится» (ban #11 / `security-hardening`). Машинные токены без `request_id`-claim края не затрагивают.
  4. **НОВОЕ под портом: номинальный ОВЕРЛОУД `request_id` на крае.** Ключ семейства fosite называется `request_id` (= `fosite.Requester.GetID()`, перемерено). У края **уже есть** несвязанный `request_id` — HTTP/gRPC-корреляция (`gateway/internal/middleware/request_id.go`: `x-request-id`, `X-Request-ID`, перемерено). Два написания одного имени в одном процессе с РАЗНЫМ смыслом — `code-authoring §5.1`: family-claim обязан читаться краем однозначно (namespace/иное имя claim), чтобы читатель не спутал его с корреляционным `request_id`. У bespoke этого не было (`family_id` отсутствовал везде). **Не блокер и не новое ребро — условие реализации.**
- **Держится:** e2e-проба сквозь обе стороны (записали отзыв → предъявили → отказ — заказ `integration-tester`); ратификация fail-closed + один round-trip `system-design-reviewer`/`security-auditor`. З4 явно **НЕ из fosite** — сохранена из прежней редакции; порт даёт reuse-detection и запись отзыва, край-энфорсмент — наш.

## 3. Наблюдаемый контракт неизменен — ПОДТВЕРЖДЕНО замером

- **Приёмка `304d545e` не тронута** (перемерено `sha256sum`, совпала).
- **Смена внутреннего ключа `family_id`→`request_id` невидима приёмке.** `grep -nEi 'family_id|request_id|predecessor|origin_code'` по приёмке → **0** (exit 1). И bespoke, и порт штампуют output-only claim семейства (bespoke `family_id`, порт `request_id`) — приёмка не ограничивает имя claim, оба равно (не)наблюдаемы клиентом.

## 4. Рёбра — нового рантайм-ребра НЕТ, подтверждено замером

- **family-читатель края = дополнение к существующему пути край→kaname**, НЕ новое ребро: тот же вызывающий (край), тот же адресат (`InternalIAMService`), то же направление, тот же round-trip, что субъект-отсечка. Перемерено: `sessionCutoffCheck` живёт на пути запроса (`gateway/internal/middleware/auth.go:1183`, kacho `ac33f733`) — читатель на предъявлении УЖЕ есть, family-читатель к нему пристраивается. Смена ключа `family_id`→`request_id` топологию ребра не меняет.
- **`LoginAuthority` = внутрисервисный шов kaname** (оба конца в kaname), не ребро.
- **browser → `GET /iam/v1/authorize` / `.well-known/…` = новая ВНЕШНЯЯ поверхность**, не рантайм-ребро (вызывающий — арендатор/браузер, не наш сервис; `polyrepo.md` ноты F2). Однонаправленно, ацикличность держится.
- **Порт fosite = derived-work в kaname**, не go-зависимость и не копия между нашими стволами (класс A). Рантайм fosite (интроспекция, opaque-storage-модель) в наш край не приезжает — край остаётся stateless-JWT (класс C).
