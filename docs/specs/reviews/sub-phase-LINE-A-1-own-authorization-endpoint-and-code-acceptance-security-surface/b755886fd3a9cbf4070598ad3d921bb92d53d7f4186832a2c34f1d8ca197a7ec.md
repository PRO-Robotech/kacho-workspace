## 0. Почему эта запись существует и чем она НЕ является

**Записи разбора поверхности безопасности в дереве не было ни одной.** Предикат:

```sh
git ls-files docs/specs/reviews | grep -icE 'security|surface|auditor'   # → 0
```

При этом замысел стоит на находках такого разбора целым разделом (§2а — 21 находка, 8 высоких
и 13 средних) и называет их **вторым входом** наряду с первичным разбором классов. У первого
входа запись есть (`…-class-exposure/initial/b755886f….md`, 316 строк), у второго — не было.
Утверждение, полученное со слов, нечем перепроверить: эталон лежал **внутри** проверяемого.

**Эта запись — самостоятельный разбор, а не пересказ §2а.** Каждая находка ниже получена обходом
наших деревьев и чтением двух документов; числа сняты **мной** командой, названной у находки.
Сверка с 21 находкой замысла стоит отдельным разделом (§3) и сделана **после** того, как
собственный перечень был закрыт, — иначе он оказался бы производным от того, что проверяет.

**Чем она не является — три вещи, названные прямо:**

1. **не вердикт по приёмке** и не вердикт по замыслу. Замысел на момент разбора — DRAFT,
   действующая пересверка по нему ⛔ (`…-class-exposure/revalidation/ff573dd9….md`);
2. **не обладает внешним полномочием, и это измерено.** Реестр полномочий
   (`docs/changes/policy.yaml` → `review_authority`) перечисляет **10** ролей
   (`grep -cE '^  [a-z-]+:' ` по блоку → 10), и роли `security-auditor` среди них **нет**.
   Значит запись — **свидетельство разбора**, а не ратификация: ратификация по §9.3 замысла
   назначена роли, которой реестр полномочий не знает. Это само по себе находка о контуре, и
   она названа в §3 как `SS-X1`;
3. **не заменяет пересверку классов.** Её предмет — отображение классов первичного разбора в
   решения замысла; здесь предмет другой: поверхность, которую заводит сама церемония.

## 1. Метод: что считается находкой и почему разбор идёт ПО ИЗМЕРЕНИЯМ

**Единица находки — свойство поверхности, у которого назван сценарий отказа.** Класс без сценария
находкой здесь не считается: «бывает уязвимость такого рода» не отличимо от «я посмотрел
оглавление». Поэтому у каждой записи ниже четыре обязательные части, и ни одна не пропущена:

| часть | что в ней |
|---|---|
| **признак** | как я узнал, что свойство отсутствует, — команда и её вывод на объявленных базах |
| **сценарий отказа** | что именно и в какой последовательности перестаёт работать; не «класс», а ход |
| **чем закрывается** | конкретное решение: колонка, предикат, ручка, порядок, величина числом |
| **чем держится впредь** | гейт по дереву · регрессия в точке · страж старта · честное «вниманием» |

**Планка тяжести.** Высокая — свойство, чьё отсутствие делает объявленный контроль
неисполнимым либо оставляет объявленное поведение без единого держателя. Средняя — свойство,
чьё отсутствие даёт расхождение, наступающее молча. Низких эта запись не поднимала; «ноль
находок» был бы находкой сам по себе, здесь их **14**: **7 высоких + 7 средних**.

**Измерения задания покрыты все семь**, и по каждому сказано, что найдено и что признано
исправным (§4 — положительные контроли; «смотрел, чисто» отличимо от «не смотрел» только
сказанным).

## 2. Находки

### 2.1 Ключи подписи

#### `SS-H1` (высокая) — у ключа подписи нет ни одного достижимого перехода состояния

**Признак.** Ключница объявляет пять глаголов жизненного цикла; вызывающих у каждого вне самого
файла ключницы, в непробном коде, — ноль:

```sh
for v in Compromise Retire Activate Generate Rotate; do
  git grep -l "\.$v(" -- '*.go' ':!*_test.go' | grep -v 'signingkeys/keystore.go' | wc -l
done            # kaname@cbbac984 → 0 · 0 · 0 · 0 · 0
```

Вызывающие есть ровно у трёх операций — `EnsureSigningKey` (подъём службы), `ActiveSigningKey`
(подписант), `PublishedSet` (публикация набора), и у `SweepRemovable` (см. `SS-M1`).

**Сценарий отказа.** Оператор узнаёт об утечке приватной половины. Пути закрыть её нет: глагол
«объявить утёкшим» существует, но ни одна обслуживаемая поверхность его не зовёт, а перевод в
другое состояние — единственное, что вывело бы ключ из подписи и из публикуемого набора.
Остаётся ровно одно действие — править строку в базе руками; оно не проходит ни через контракт,
ни через аудит, ни через стража состояний, и после него служба продолжает работать с тем
представлением, которое прочитала при старте. **Ключ, выданный при первом подъёме установки,
подписывает всё её время жизни**: ротации не происходит никогда, потому что звать её некому.

**Чем закрывается.** У «объявить утёкшим» и у «вывести из обращения» — не менее одного
вызывающего в непробном коде, достижимого с обслуживаемой поверхности (внутренний слушатель с
записью каталога прав, как у всякой операции смены состояния безопасности). Ротация —
запланированное действие с собственным вызывающим, а не следствие подъёма.

**Чем держится впредь.** Гейт по дереву в `internal/check/`: у каждого глагола ключницы, меняющего
состояние, есть вызывающий вне пакета ключницы; перечень глаголов **выводится** разбором
(объявления методов типа), а не выписывается — выписанный переживёт появление шестого. Гейт
печатает объём осмотренного и падает на пустом обходе.

#### `SS-H2` (высокая) — объявленный срок ключа не наступает никогда: `not_after` пишут и не читают

**Признак.** Колонка срока ключа участвует ровно в трёх непробных файлах, и ни в одном — как
условие отбора:

```sh
git grep -l 'not_after\|NotAfter' -- '*.go' ':!*_test.go' | wc -l    # → 3
```

`keystore.go` — вычисление значения при порождении и печать в журнал; `domain` — поле структуры;
`signing_key_repo.go` — перечень колонок, вставка и разбор строки. Отбор подписывающего ключа
идёт **по состоянию**: `WHERE state = 'ACTIVE'`. Предиката по сроку нет ни в одном запросе.

**Сценарий отказа.** Оператор объявляет срок ключа (ручка есть, значение доезжает до колонки).
Срок проходит. Выдача продолжает подписывать тем же ключом: отбор его не исключает, потому что
смотрит на состояние, а состояние никто не менял (`SS-H1`). Величина, ради которой ручка
заведена, наблюдаемого следствия не имеет **ни при каком значении** — это в точности
«значение, которое пишут и не читают» (`api-conventions.md` §«Поле контракта не выходит наружу»,
врезка о третьем признаке семейства).

**Чем закрывается.** Отбор подписывающего исключает истёкший: условие срока стоит **в запросе**,
рядом с условием состояния. Выбрано именно это, а не «ротатор успевает заранее»: первое
проверяется одним предикатом по выдаче, второе — только наблюдением за временем.

**Чем держится впредь.** Регрессия в точке: интеграционная проба подаёт ключницу с единственным
ключом, чей срок истёк, и требует **отказа выдачи**, а не подписи; положительный близнец — тот
же ключ с неистёкшим сроком подписывает. Плюс гейт: колонка, объявленная сроком, читается хотя бы
одним предикатом отбора.

#### `SS-M1` (средняя) — из публикуемого набора ключ не выходит ни при каком исходе

**Признак.** Набор отбирается `WHERE state IN ('PUBLISHED','ACTIVE','RETIRED')`; сметатель
(`SweepRemovable`) обходит набор и снимает **только** записи в состоянии «выведен из обращения»
по истечении отсрочки. Переводящих в это состояние вызывающих — ноль (`SS-H1`).

**Сценарий отказа.** Ветка сметателя «снял N записей» не исполняется **ни разу за жизнь
установки**: предмета, который она снимает, не возникает. Набор растёт монотонно; всякий
когда-либо порождённый ключ остаётся публикуемым и, значит, принимаемым проверяющими подпись —
включая тот, который оператор считает выведенным. Наблюдаемого сигнала нет: сметатель отрабатывает
успешно и возвращает ноль, а ноль здесь неотличим от «предмета не было» и от «механизм сломан».

**Чем закрывается.** Сметатель несёт **наблюдаемый счётчик срабатываний**, и ноль за всё время
жизни читается как сигнал, а не как тишина (`security-hardening.md` §Hardening-инварианты, п. 8
и п. 9 — контроль, не отказавший ни разу, обязан быть заметен). Вместе с `SS-H1` это даёт предмет,
который сметателю есть что снимать.

**Чем держится впредь.** Регрессия наблюдаемая — счётчик, а не «вызвана ли функция»; плюс
утверждение, что набор, отданный после вывода ключа из обращения, **не содержит** его записи
(положительный близнец: до вывода — содержит).

---

#### `SS-M2` (средняя) — страж срока ключа судит только отрицательное, а ноль подставляется молча ДВАЖДЫ

**Признак.** Страж настройки чеканки отвергает срок ключа при значении **меньше нуля**
(`internal/apps/kaname/config/token_signing.go:157`); ноль проходит. Незаданное значение
подставляется в **двух** местах сразу: умолчанием загрузчика
(`internal/apps/kaname/config/defaults.go:238` → `2160h`) и разрешителем внутри самой структуры
настройки (`ResolveKeyLifetime` → 90 суток). Обе подстановки дают одну и ту же величину.

**Сценарий отказа.** Профиль развёртывания, не объявивший срок, поднимается — страж молчит, потому
что судит не сырое поле, а знак. Дальше два места об одном предмете расходятся ровно тогда, когда
одно из них поправят: величина сменится у одного читателя и не сменится у другого, и различить это
нечем — оба ответа правдоподобны. Классический признак: **ненулевое умолчание означает, что страж
по этой величине мёртв** — незаданной она не бывает никогда.

**Чем закрывается.** Страж судит **сырое** поле и отказывает в пуске при нулевом — тем же порядком,
каким соседняя величина того же стража (путь публикуемого набора) уже судится правильно. Обе
молчаливые подстановки снимаются; величина, которую судит страж, не имеет ненулевого умолчания ни
в одном месте.

**Чем держится впредь.** Декларативная проба профилей, читающая **объявления** (образец в дереве
платформы — проба формы токена у края), плюс страж старта, падающий на незаданном.

### 2.2 Секреты клиентов

#### `SS-H3` (высокая) — «конфиденциальный клиент» невыразим схемой: хранить проверочное значение негде

**Признак.** Таблица клиента церемонии несёт **12 колонок**
(`id`, `created_at`, `name`, `description`, `labels`, `redirect_uris`,
`post_logout_redirect_uris`, `client_id`, `audiences`, `grant_types`,
`token_endpoint_auth_method`, `status`). Колонок под проверочное значение секрета —
**ноль**; колонок арендатора — **ноль**. Поле метода аутентификации объявлено
`text DEFAULT ''::text NOT NULL`, и сужающего его `CHECK` в схеме нет ни одного.

**Сценарий отказа.** Приёмка (Р3, сценарий 12) требует, чтобы обмен отвергал клиента без
аутентификации кодом `invalid_client` **до** именования кода. Посев стенда заводит клиента
единственным доступным способом — без метода аутентификации, потому что колонки под секрет нет;
пустая строка в поле метода означает «не сужаем», а не «конфиденциальный». Сценарий 12 при этом
**зелёный**: он подаёт дефектную форму запроса и проверяет порядок отказов, а не то, что
посеянный клиент вообще способен предъявить секрет. То есть проба утверждает форму и молчит о
существе — ровно класс «проверка, зелёная при отсутствующем предмете».

**Чем закрывается.** Миграция A-1 заводит колонку с **проверочным значением** секрета клиента и
`CHECK` базы, запрещающий пустой метод аутентификации у клиента, которому разрешён вид выдачи
`authorization_code` (инвариант внутри сервиса — на уровне БД, ban #10). Признак
конфиденциальности **выводится из колонки**, а не получается нулевым значением поля
(`api-conventions.md` §«Пустое значение обязано означать пусто»). Алгоритм и его параметры
объявляются так же, как уже объявлены параметры проверяющего пароля, — перечнем обязательных
настроек со стражем старта, а не литералом; проверочное значение несёт свою соль по построению
формата.

**Чем держится впредь.** `CHECK` в схеме (второй путь записи его не обойдёт) плюс интеграционная
проба: клиент, которому разрешён `authorization_code`, не вставляется с пустым методом
аутентификации; положительный близнец — с объявленным методом вставляется.

#### `SS-M3` (средняя) — равнозатратность отказа аутентификации клиента не объявлена нашей нормой

**Признак.** Форма, закрывающая этот класс, в дереве **есть** и работает: вход паролем держит
огибающую по потолку — всякий исход после ворот частоты уходит не раньше калиброванной стоимости
самого дорогого класса, и «адреса нет» стоит столько же, сколько «пароль не тот»
(`internal/apps/kaname/api/humansession/login.go`, шапка файла, Ф3-31). У полосы обмена церемонии
аналога нет: ни приёмка, ни замысел не называют равнозатратность **нашим** требованием — она
приходит условием находки о движке, то есть как свойство чужого кода, а не как норма нашего
контракта.

**Сценарий отказа.** Реализация идёт естественным путём: неизвестный `client_id` отвергается сразу,
известный — после сверки проверочного значения. Разница во времени ответа отделяет
зарегистрированного клиента от незарегистрированного; единый тон отказа, которого требует Р10,
при этом соблюдён **побайтово** — и не значит ничего, потому что различие ушло в другую ось.
Это тот же класс, что и различимый текст (`security-hardening.md` §Hardening, п. 6), применённый
ко времени.

**Чем закрывается.** Сверка выполняется **всегда**, включая заведомо неизвестного клиента
(против фиксированного значения-пустышки), и требование записано как **наше**, в контракте пакета
церемонии, а не как пересказ свойства чужой библиотеки.

**Чем держится впредь.** Проба, утверждающая **распределение** времени ответа, а не одно
измерение; положительный близнец — валидная аутентификация проходит. Образец калибровки в дереве
есть (огибающая входа), и он переиспользуется, а не переизобретается.

### 2.3 Поток авторизации

> Пять требований этого измерения — обязательность кода подтверждения ключа, точная сверка адреса
> возврата, одноразовость и срок кода, запрет неявной выдачи, ротация обновляющего токена с
> обнаружением повтора — **закрыты приёмкой и первичным разбором**, и это сказано в §4 как
> положительный контроль. Ниже — то, чего не закрывает ни один из двух документов.

#### `SS-H4` (высокая) — у браузерной поверхности нет НИ ОДНОГО потолка входа, и замысел закрывает вопрос выводом «потолок не нужен»

**Признак.** Замысел (§6, строка неточности N2) заключает: у `GET /iam/v1/authorize` тела нет,
значит потолок не нужен; потолок объявляется только для полосы обмена и переиспускает
существующую ручку тела токен-эндпоинта. Потолка на **строку запроса** и на **отдельный
параметр** нет ни в одном из двух документов:

```sh
grep -ciE 'потолок строки|длин[аы] state|максим' <приёмка> <замысел>   # → 0 · 0
```

Пол значения `state` объявлен приёмкой числом (22), потолка у него нет. Для сравнения, у соседнего
значения той же поверхности потолок объявлен и продублирован базой: запись списка адресов возврата
— **512 байт**, записей — **16** (`internal/domain/interactive_client.go`, те же числа в `CHECK`).

**Сценарий отказа.** Запрос авторизации приходит с параметром `state` в десятки килобайт.
Обработчик обязан: разобрать строку запроса, сверить клиента, сверить адрес возврата,
проконсультировать шов авторитета входа (обращение к хранилищу сессии) и собрать значение
заголовка перенаправления, **включив в него присланную строку дословно** (приёмка 02, 30 требуют
вернуть `state` дословно). Ни один шаг не ограничен сверху. Дальше это не «медленно», а
**объявленная стоимость без объявленного предела**: у поверхности, к которой по построению
обращается неаутентифицированный браузер, цена одного обращения задана вызывающим.

**Чем закрывается.** Три величины, каждая — ручка с нулевым умолчанием под стражем старта:
потолок **строки запроса** эндпоинта авторизации — **8 КиБ на запрос**; потолок значения
`state` — **512 байт** (дословный паритет с уже объявленным потолком записи адреса возврата:
одна форма непрозрачного значения клиента — одна величина); потолок числа параметров запроса —
**32**. Отказ по потолку — **отдельный исход до именования клиента**, со своим счётчиком в
закрытом словаре исходов; с отказом формы он не сливается (корзины «прочее» нет).

**Чем держится впредь.** Регрессия наблюдаемая, утверждающая **три** величины сразу: код ответа,
число вызовов обработчика за ограничителем и число реально прочитанных байт; законная половина
(запрос в пределах потолков проходит и возвращает `state` дословно) закрепляется там же.

---

#### `SS-M4` (средняя) — порядок проверок на эндпоинте АВТОРИЗАЦИИ не назван ни одним документом

**Признак.** Для полосы обмена порядок назван дословно и в приёмке (Р10: различимы ровно отказы
**до** того, как назван код), и в замысле (форма → аутентификация клиента → именование кода →
единый тон). Для эндпоинта авторизации порядок назван **частично**: приёмка Р13 п. 3 говорит
только, что `state` судится **после** сверки клиента и адреса возврата. Где в этом порядке стоит
консультация шва авторитета входа — не сказано нигде.

**Сценарий отказа.** Реализация ставит консультацию шва первой (это естественно: «сначала узнаем,
кто пришёл»). Тогда каждый запрос с заведомо негодным `client_id` — то есть запрос, который будет
отвергнут — **сначала** оплачивает обращение к хранилищу сессии. Обратный порядок даёт обратную
беду: отказ по `state`, наступающий **до** консультации шва, становится различим по времени от
отказа по адресу возврата, и анти-оракульный паритет 04↔05, которого требует первичный разбор,
теряется в оси времени. Ни то, ни другое прочтение текстом не запрещено, и выбор достанется
исполнителю полосы без единого держателя.

**Чем закрывается.** Порядок объявляется полностью, ровно как у обмена: форма и потолки (`SS-H4`)
→ клиент и адрес возврата → `state` и код подтверждения ключа → **консультация шва** → выдача.
Консультация шва стоит **после** всех проверок, решаемых по самому запросу: это и делает
стоимость отвергнутого запроса меньше стоимости принятого.

**Чем держится впредь.** Проба порядка уровня модуля: вызывающий подаёт запрос, негодный по
раннему условию, и утверждает, что производитель шва **не был вызван** (счётчик вызовов), плюс
положительный контроль — на годном запросе вызван ровно один раз.

### 2.4 Сессии

#### `SS-H5` (высокая) — завершение сессии человека не завершает refresh-семейство, выданное из неё

**Признак.** Механизмы завершения сессии в дереве есть и работают: выход завершает сессию и пишет
отсечку субъекта (`…/humansession/logout.go` — `EndSession` + `UpsertCutoff`); смена пароля
завершает **прочие** сессии, пишет отсечку и **ротирует предъявителя** текущей
(`…/humansession/change_password.go` — `EndOtherSessions` + `UpsertCutoff` + `RotateBearer`).
Связи этих событий с семейством токенов OAuth нет ни в одном документе:

```sh
grep -icE 'выход|logout' <приёмка>   # → 3, и все три относят выход к предмету Ф1
```

Замысел упоминает выход ровно один раз — в перечне предметов субъект-широкой отсечки («админ
force-logout, блок, восстановление»), и семейство отзывается у него **только** обнаружением
повтора обновляющего токена.

**Сценарий отказа.** Человек выходит. Сессия завершена, отсечка записана. Обновляющий токен,
выданный из этой сессии, остаётся действующим: полоса обновления читает своё хранилище, а не
сессию, и повтора не было — значит отзыв семейства не срабатывает. Дальше развилка, и **обе
её ветви допускаются текстом**:

- если момент аутентификации переносится из кода по цепочке ротации (как требует Р6 для первой
  выдачи), новый предъявитель отвергается краем по отсечке — но обмен при этом **отвечает
  успехом**, и владелец обновляющего токена бесконечно получает удостоверения, негодные у края.
  Наблюдаемо это как «выход сработал», хотя семейство живо;
- если момент аутентификации на ротации берётся **текущим** (естественное прочтение: выдали
  новую пару — новый момент), отсечка перестаёт отсекать вовсе, и **выход перестаёт действовать**
  на всё семейство целиком.

Ни приёмка, ни замысел не называют, откуда берётся момент аутентификации **при ротации**.

**Чем закрывается.** Два решения, и оба записываются:
(а) момент аутентификации по цепочке ротации **переносится**, а не переназначается, — величина
принадлежит сессии, из которой семейство рождено;
(б) завершение сессии человека (выход, смена пароля, административное завершение) **отзывает
семейства, рождённые из этой сессии**, — для чего строка семейства несёт идентификатор породившей
сессии рядом с ключом семейства.

**Чем держится впредь.** Проба **сквозь обе стороны**, одним прогоном: вошли → получили код →
обменяли → вышли → предъявили обновляющий токен → получили отказ. Двух проб по половине
недостаточно (`security-hardening.md` §«Части, исправные по отдельности, не сходятся в целое»);
положительный близнец — семейство другой, не завершённой сессии того же человека продолжает
ротироваться.

---

#### `SS-M5` (средняя) — достигнутый шагом вверх уровень: не сказано, поднимается ли САМА сессия

**Признак.** Приёмка (сценарий 08) и замысел (`LAX-7`) говорят об одном и том же: при успешном
шаге вверх **код несёт достигнутый уровень**. Что происходит с уровнем самой сессии, не сказано
ни в одном из двух документов.

**Сценарий отказа.** Два прочтения, оба защитимы:

- уровень остаётся свойством **кода** — тогда человек, прошедший второй фактор для одного
  клиента, проходит его заново при каждом следующем запросе авторизации, в том числе от того же
  клиента через минуту. Церемония работает, продукт неудобен настолько, что первый же отчёт
  назовёт это дефектом;
- уровень поднимается у **сессии** — тогда достигнутый уровень переживает церемонию, и следующий
  клиент, обратившийся из того же браузера, получает код уровня «2», **не проведя своего шага
  вверх**. Повышенный уровень аутентификации распространяется на предмет, который его не
  запрашивал.

Второе прочтение опаснее и выглядит «работающим лучше», поэтому выбирается чаще.

**Чем закрывается.** Решение называется явно, в приёмке (величина наблюдаема, значит принадлежит
ей) либо возвратом в неё: уровень сессии поднимается, и у поднятия есть **собственное окно
свежести**, за пределами которого шаг вверх требуется заново; окно — величина посадки со стражем
старта, по образцу уже объявленного окна свежести правки своих данных.

**Чем держится впредь.** Пара сценариев с отличием ровно в одном факте: второй клиент в пределах
окна получает код уровня «2» без своего шага вверх; он же за пределами окна — не получает.

### 2.5 Арендатор

#### `SS-H6` (высокая) — интерактивный клиент есть объект уровня КЛАСТЕРА, и аудитория выданного токена объявляется им

**Признак.** У таблицы клиента нет ни одной колонки арендатора (счёт колонок — 12, совпадений с
`account|project|tenant|owner` — **0**). Уникальность объявлена **глобально**: уникальный индекс
по имени и уникальный индекс по внешнему идентификатору клиента, без сужения по владельцу.
Колонка `audiences text[] DEFAULT '{}'::text[] NOT NULL` не сужена ни одним `CHECK`.

**Сценарий отказа.** Клиент церемонии — общий для всей установки. Человек любого аккаунта проводит
церемонию с любым зарегистрированным клиентом: связки «этот клиент принадлежит этому арендатору»
не существует, и проверить её негде. Дальше вопрос аудитории: приёмка требует, чтобы предъявитель
нёс аудиторию края и чтобы она штамповалась нами (output-only). Пока это так, беда ограничена
согласием; как только проекция области и аудитории начнёт читать объявленный клиентом перечень —
а он в схеме уже есть, пуст по умолчанию и ничем не сужен, — адресат выданного удостоверения
станет величиной, которую объявляет глобально зарегистрированный объект без владельца.

**Чем закрывается.** Три решения, и первые два — прямо в A-1:
(а) аудитория выданного предъявителя штампуется **нами** и не читается из строки клиента —
записывается инвариантом, а не подразумевается формулировкой «output-only»;
(б) перечень аудиторий клиента, пока у него нет владельца, объявляется **принятым-и-непрочитанным**
и получает один из трёх законных исходов (прочитать · отвергать явно · снять с контракта), а не
остаётся молча;
(в) владение клиентом (колонка арендатора и сужение уникальности по ней) — предмет LINE-A-2, где
регистрация переезжает к нам; до него отсутствие владельца названо **принятым остатком с
радиусом**, а не пробелом.

**Чем держится впредь.** Гейт «поле контракта имеет читателя» уже существует как класс и
применяется к перечню аудиторий; плюс проба: предъявитель, выданный по коду, несёт аудиторию
края **независимо** от содержимого перечня в строке клиента (отрицательный близнец — строка с
посторонней аудиторией не меняет ответа).

---

#### `SS-M6` (средняя) — у клиента ДВЕ идентичности, и документы адресуют его разными

**Признак.** Схема несёт первичный ключ `id` формы `^ic-[0-9a-hjkmnp-tv-z]{17}$` **и отдельную**
колонку `client_id` с собственным уникальным индексом. Приёмка в сценарии 02 передаёт в параметре
церемонии `client_id = ic-…`, то есть значение **первичного ключа**. Какой из двух колонок
резолвится клиент на эндпоинте авторизации и на обмене, не сказано ни в приёмке, ни в замысле.

**Сценарий отказа.** Реализация выбирает `client_id` (имя параметра совпадает с именем колонки —
самое естественное прочтение). Сценарии приёмки при этом написаны с `ic-…`, то есть со значением
другой колонки: проба, написанная по приёмке дословно, получает «клиента нет» на **положительном**
сценарии, и её автор чинит пробу, а не расхождение. Обратный выбор даёт зеркальную беду: колонка
`client_id` остаётся принятой-и-непрочитанной при живом уникальном индексе по ней, то есть
занимает пространство имён, ничего не адресуя.

**Чем закрывается.** Адресация — по неизменяемому `id` (ban #15: внешне адресуемая идентичность
одна), а колонка `client_id` получает свой исход из трёх законных. Решение записывается там, где
оно наблюдаемо, — то есть в приёмке либо возвратом в неё, а не выбором исполнителя.

**Чем держится впредь.** Проба резолва обеими формами: значение `id` резолвится, значение второй
колонки — либо резолвится осознанно, либо отвергается названным отказом; «работает и так, и так»
исходом не является.

### 2.6 Внутренний слушатель

#### `SS-M7` (средняя) — три новые поверхности церемонии лежат ВНЕ механизма «authN+authZ на каждом методе»

**Признак.** Требование нормы `security.md` («authN и authZ на каждом запросе обоих листенеров»)
держится в этом дереве двумя вещами: цепочками интерсепторов обоих gRPC-слушателей
(`cmd/kaname/serve.go`) и гейтом полноты каталога прав
(`internal/check/catalog_covers_contract.go`), который требует строки каталога **у каждого RPC,
объявленного контрактом службы**, и судит строку без источника как находку. Церемония по решению
замысла (З1) заводит **три** сырых HTTP-обработчика — эндпоинт авторизации, эндпоинт обнаружения
и новую ветвь токен-эндпоинта. У них нет контракта, значит нет и строки каталога: гейт молчит о
них **by construction**, а не потому, что они исправны.

**Сценарий отказа.** Завтрашняя полоса добавляет к церемонии четвёртую сырую координату —
административную либо отладочную. Она не попадает ни в одну цепочку интерсепторов, ни в каталог
прав, ни в перепись поверхностей; всё, что о ней знает дерево, — строка монтажа в композиционном
корне. Ретроактивность запрета («ни один запрос без проверки») держится там, где есть контракт; у
сырых обработчиков её не держит ничто, и заказанная замыслом врезка-исключение в норму (H8) этого
не заменяет: врезка **разрешает** названное исключение, а держателя не заводит.

**Чем закрывается.** Перечень сырых координат церемонии **утверждается перечислением**, а не
запретом одного имени: гейт выводит перечень мест регистрации из исходника композиционного корня и
требует, чтобы каждая зарегистрированная координата была либо в объявленном перечне церемонии с
названным режимом доступа, либо находкой. Врезка-исключение в норму называет **ровно две**
неаутентифицированные координаты и живёт как исключение, истекающее вместе со своим предметом.

**Чем держится впредь.** Гейт по дереву в `internal/check/`: перечень **выводится**, печатает
объём осмотренного, падает на пустом обходе; доказан инъекцией в обе стороны — новая координата
вне перечня краснеет с именем, законный близнец (координата в перечне) молчит.

### 2.7 Экспозиция

#### `SS-H7` (высокая) — браузерной достижимости у новой поверхности нет, и её появление есть ВТОРОЙ внешний вход

**Признак.** Внешних входов в дереве платформы ровно один, и он принадлежит краю; у службы
доступа их нет:

```sh
git grep -rl 'kind: Ingress' -- 'deploy/**'      # kacho@f445aaaa554 → 1 файл (край)
git grep -rl 'kind: Ingress' -- 'deploy/**'      # kaname@cbbac984  → 0
```

Поверхность выдачи службы, на которой замысел монтирует церемонию (§5.1 — тот же слушатель, где
уже живёт токен-эндпоинт), снаружи не опубликована. Первичный разбор классов назвал это и адресовал
**ровно этой роли** (запись `initial/b755886f….md`, строка о ингрессах: «браузерная достижимость
новых координат существующим развёртыванием не обеспечена → заказ `security-auditor`»).

**Сценарий отказа.** Исход один из двух, и оба — отказ:

- поставка не меняется: браузер до эндпоинта авторизации не доходит, церемония непроверяема
  сквозной пробой браузером (DoD п. 16 приёмки), и «зелёный стенд» означает, что предмет не
  исполнялся;
- поставка меняется: у установки появляется **второй внешний вход**, и он ведёт не на край, а
  прямо на слушатель выдачи службы доступа — то есть в обход всего, что край делает на каждом
  запросе. Посадка этого входа — периметр, завершение TLS, ограничение темпа, потолки тела и
  строки, заголовки ответа — не объявлена **ни одной строкой** ни в приёмке, ни в замысле.

Второй исход наступает тихо: он выглядит как «добавили ингресс, чтобы проба прошла».

**Чем закрывается.** Форма экспозиции объявляется **до** посадки полосы эндпоинта: какой вход,
какое имя, какое завершение TLS, какие величины темпа и потолков (`SS-H4`), какие заголовки
ответа. Объявление — в приёмке либо в профиле развёртывания со стражем, а не в чьей-то памяти;
решение «второй вход заводится» либо «церемония публикуется через край» принимается явно и
записывается с основанием.

**Чем держится впредь.** Декларативная проба профилей, читающая **объявления** значений: у
объявленного внешнего входа церемонии есть все названные величины; плюс гейт посадки, читающий
живой процесс, а не отрендеренный шаблон (`security.md` §Production-mode).

### 2.8 Ограничение скорости и защита от подбора — числами

#### Сводка величин (входит в `SS-H4`, `SS-M4`, `SS-H7` и названа отдельно, потому что задание требует чисел)

**Что в дереве уже объявлено — измерено:**

| величина | значение | координата |
|---|---:|---|
| пол публичного чтения, запросов/с на вызывающего | **100** | `corelib/grpcsrv/admission_posture.go:47` |
| пол публичных мутаций, запросов/с на вызывающего | **20** | там же, `:49` |
| кратность всплеска, раз | **×5** | там же, `:52` |
| одновременных запросов на вызывающего | **16** | там же, `:54` |
| вход паролем: попыток на адрес за окно | **5 / 15 мин** | `kaname/internal/apps/kaname/config/required_settings.go:375,377` |
| вход паролем: попыток на источник за окно | **50 / 15 мин** | там же, `:379,381` |
| допуск регистрации | **3 / 1 ч** | там же, `:385,387` |
| потолок тела токен-эндпоинта | ручка, `≤ 0` валит старт | `…/config/client_token.go:58–60, 172–176` |

**Чего нет.** Все величины допуска принадлежат **gRPC**-слушателям; до HTTP-поверхности выдачи они
не доходят ни одним вызовом, и ограничителя темпа уровня HTTP в дереве нет. Монтаж
токен-эндпоинта (`cmd/kaname/serve.go:1295`) не обёрнут ничем, кроме самого обработчика.

**Предлагаемые величины церемонии — четыре оси, у каждой своя единица и своё основание:**

| ось | единица счёта | величина | основание |
|---|---|---:|---|
| запрос авторизации | запросов/с на источник | **10**, всплеск **×5** | вдвое ниже мутационного пола (20): полоса браузерная, один человек делает один запрос за церемонию |
| обмен на токен | обменов/с на идентификатор клиента | **20**, всплеск **×5** | паритет с мутационным полом — обмен есть мутация |
| неудавшиеся обмены | отказов за окно 15 мин на источник | **50** | дословный паритет с уже объявленной величиной входа паролем: одна форма злоупотребления — одна величина |
| одновременность | одновременных запросов церемонии на источник | **16** | паритет с публичным потолком одновременности |

Каждая — ручка с **нулевым** умолчанием и отказом старта при незаданной (тот же порядок, каким уже
судится потолок тела). Отказ по темпу — **отдельный исход до именования клиента**, со своим
счётчиком в закрытом словаре исходов; с отказом аутентификации он не сливается.

**Числа — предложение разбора, а не решение.** Наблюдаемого в них ровно столько, сколько видит
вызывающий (какой запрос отвергается), поэтому решение принадлежит владельцу приёмки; здесь они
названы, чтобы «ограничить» не читалось как величина.

### 3.2 Разошлось — и каждое расхождение есть находка о замысле

**`SS-X1` (высокая, о контуре) — ратификация назначена роли, которой нет в реестре полномочий.**
Замысел в §9.3 (пп. 3 и 9) назначает ратификацию находок роли `security-auditor`; §2а.0 делает
её **условием** открытия полос L0b и L2. Реестр полномочий знает **10** ролей, и этой среди них
нет. Следствие: вердикт, который замысел объявил предусловием, **невыразим** — запись такой роли
не имеет внешнего события, которое машина сверяет, и предикат «ратификация проведена» не имеет
производителя. *Чем закрывается:* либо роль вносится в реестр (предмет `tooling-maintainer`, дом
— воркспейс), либо предусловие переписывается на роль, полномочие которой существует.
*Чем держится:* гейт контура уже сверяет роль записи с реестром — находка появится сама, как
только запись с этой ролью будет предъявлена как вердикт.

**`SS-X2` (средняя, о замысле) — §6 N2 закрывает вопрос о потолке браузерной поверхности выводом,
а не решением.** «У `GET /iam/v1/authorize` тела нет → потолок не нужен» верно ровно про тело и
неверно про вход: строка запроса — тоже вход, и она ничем не ограничена (`SS-H4`). Вывод, закрывший
вопрос, опаснее открытого вопроса: он снимает предмет с повестки.

**`SS-X3` (средняя, о замысле) — восемнадцать условий §2а адресуют дерево, которого нет, и это
названо самим замыслом.** §2а.0 снимка честно объявляет: 18 из 21 условия координированы парой
«файл:строка» на клоне движка, которого нет ни в одном стволе, и потому **перемеренными не
считаются**. Отсюда следствие для счёта: заявление «21 находка внесена» верно про **три** находки
(`H4`, `H8`, `M9`) и про половину четвёртой (`H7`). Моя запись этого не чинит и не может:
её предмет — наша поверхность, а не чужая. Она лишь фиксирует, что **второй** вход замысла до
ратификации остаётся утверждением со слов, и что первый вход (первичный разбор классов) в этом
смысле в другом положении — у него есть запись в дереве.

### 3.3 Чего нет у замысла — семь находок

`SS-H4` (потолки браузерной поверхности, сверх тела), `SS-M4` (порядок проверок на эндпоинте
авторизации), `SS-H5` (завершение сессии не завершает семейство; источник момента аутентификации
при ротации), `SS-M5` (область действия достигнутого уровня), `SS-H6` (клиент без арендатора и
аудитория из его строки), `SS-M6` (две идентичности клиента), `SS-H7` (экспозиция и второй внешний
вход).

**Почему их там нет — механизм назван, а не приписан небрежности.** §2а построен **от источника**
(чужой движок), §2г — **от нашего сегодняшнего кода**. Оба смотрят на то, что уже написано. Семь
находок выше — о **шве между** написанным и объявленным: о том, что приёмка называет наблюдаемым,
а дерево ещё не производит. Такой шов не виден ни одному из двух разборов **by construction**, и
это довод в пользу того, чтобы запись разбора поверхности существовала отдельным файлом, а не
разделом внутри проверяемого.

### 3.4 Чего нет у меня

Находок §2а о **внутреннем устройстве движка** (`H1`, `H2`, `H3`, `H5`, `H6`, `M1`, `M2`, `M5`,
`M6`, `M7`, `M8`, `M11`, `M12`, `M13`, сквозное `S1`, класс `N-8`) эта запись **не перепроверяла**:
их предмет — исходники, которых в наших стволах нет (предикат `git grep -c 'ory/fosite' -- go.mod
go.sum` по трём стволам → `0 · 0 · 0`). Повторить их чтением текста замысла значило бы произвести
второе утверждение со слов; это и есть то, чего запись избегает. Их ратификация остаётся
предусловием и наступает **на дереве** после внесения поддерева, как и требует §2а.0.

Находки §2г снимка, которых нет у меня: `LA1-SEC-H3` (это внесение §2а.0, а не самостоятельное

перемерена мной независимо — и потому здесь они названы как **чужое измерение**, а не как мой

## 6. Публичные формулировки — по одной на находку

Обе стороны репозитория публичны, поэтому **вся эта запись** написана так, чтобы выдерживать
публикацию: ни одна находка выше не собирает в одном месте «координата + условие, при котором
защита не действовала + следствие для постороннего». Сценарии отказа сформулированы от **оператора
и продукта** («оператор не имеет пути закрыть утечку», «истёкший ключ продолжает подписывать»), а
не от того, что получает посторонний; предикаты названы командами над публичным кодом и рецептом
не являются.

Столбец ниже — **ещё более короткая** форма, пригодная для тела задачи в трекере: предмет и
следствие для контракта, без координат и без чисел о нашей посадке.

| id | формулировка для публичного трекера |
|---|---|
| `SS-H1` | Жизненный цикл ключа подписи объявлен глаголами, у которых нет ни одного достижимого вызывающего: смена состояния ключа не выражена ни одной обслуживаемой операцией. Завести операции смены состояния и держать их наличие гейтом по дереву |
| `SS-H2` | Срок ключа подписи хранится и не участвует ни в одном отборе: объявленная величина не имеет наблюдаемого следствия. Включить срок в условие отбора подписывающего и закрепить регрессией |
| `SS-M1` | Публикуемый набор ключей растёт монотонно: состояние, которое снимает сметатель, не производится ничем, и его нулевой исход неотличим от исправной работы. Завести наблюдаемый счётчик снятий |
| `SS-M2` | Страж срока ключа судит только отрицательное значение; незаданное подставляется молча в двух местах сразу. Судить сырое поле, снять обе подстановки |
| `SS-H3` | Конфиденциальность клиента интерактивной церемонии невыразима схемой: проверочного значения секрета хранить негде, метод аутентификации не сужен ограничением базы. Завести колонку и ограничение базы, вывести признак из них |
| `SS-M3` | Равнозатратность отказа аутентификации клиента не объявлена требованием нашего контракта, хотя форма калибровки в продукте уже есть. Объявить требование и закрепить пробой распределения |
| `SS-H4` | У браузерной поверхности церемонии не объявлено ни одного потолка входа: ограничены тело (которого нет) и не ограничены строка запроса, число параметров и длина непрозрачного значения клиента. Объявить три потолка ручками со стражем старта |
| `SS-M4` | Порядок проверок эндпоинта авторизации объявлен частично: не сказано, где стоит обращение к авторитету входа. Объявить порядок целиком и закрепить пробой, утверждающей отсутствие обращения на рано отвергнутом запросе |
| `SS-H5` | Завершение сессии человека не завершает семейство обновляющих токенов, рождённое из этой сессии; источник момента аутентификации при ротации не назван, и оба прочтения допустимы текстом. Назвать перенос момента и связать завершение сессии с отзывом семейства |
| `SS-M5` | Не сказано, поднимается ли уровень самой сессии при повышении уровня аутентификации: одно прочтение делает повторную проверку обязательной каждый раз, другое распространяет достигнутый уровень на предмет, который его не запрашивал. Назвать решение и окно его свежести |
| `SS-H6` | Клиент интерактивной церемонии — объект уровня установки без владельца, а перечень адресатов объявляется его строкой и ничем не сужен. Штамповать адресата самим, дать перечню исход, владение отнести к следующей под-фазе записанным остатком |
| `SS-M6` | У клиента две идентичности — первичный ключ и отдельное внешнее имя; документы адресуют его разными, и выбор достаётся исполнителю. Адресовать по неизменяемому идентификатору, второй колонке дать исход |
| `SS-M7` | Три новые координаты церемонии обслуживаются вне механизма, которым держится «проверка личности и полномочий на каждом методе»: у них нет контракта, значит нет и записи каталога прав. Утверждать перечень координат перечислением, держать гейтом |
| `SS-H7` | Браузерная поверхность церемонии существующей поставкой недостижима; её публикация означает второй внешний вход в установку, посадка которого нигде не объявлена. Объявить форму экспозиции до посадки полосы |
| `SS-X1` | Ратификация разбора поверхности назначена роли, которой нет в реестре полномочий контура: объявленное предусловие не имеет производителя. Внести роль либо переписать предусловие |
| `SS-X2` | Вывод «потолок не нужен» закрыл вопрос о потолках браузерной поверхности шире, чем его основание: отсутствие тела не означает отсутствия входа |
| `SS-X3` | Восемнадцать из двадцати одного условия разбора движка адресуют дерево, которого в стволах нет, и перемеренными не считаются до его внесения — это названо самим замыслом и здесь только зафиксировано |
