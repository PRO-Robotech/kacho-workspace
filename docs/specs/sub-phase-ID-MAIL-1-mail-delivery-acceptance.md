## §0 Обзор — и решение, вынесенное первым

**Две задачи, один пробел: у продукта нет доставки почты.** Приглашение отвечает «отправлено» и не
отправляет; вход после выхода требует подтверждённого адреса, а подтверждать некому. Каждая
половина по отдельности защитима — требование подтверждённого адреса разумно, код по почте разумен,
профиль называет почтовый узел. Неверна их **совместимость**: узла не создаёт ни один шаблон
развёртывания, а поле ссылки приглашения не заполняет ни одна строка кода службы.

**РЕШЕНИЕ ВЛАДЕЛЬЦА (принято; приёмка его ОПИСЫВАЕТ и делает проверяемым, а не выбирает заново):**

1. **В поставке есть работающий путь доставки** — служба личности отправляет письмо (подтверждение
   адреса, приглашение, восстановление доступа) через настраиваемого отправителя.
2. **Профиль развёртывания ОТКАЗЫВАЕТСЯ СТАРТОВАТЬ**, если доставка нужна, а её настройка не задана
   (адрес отправителя, узел, удостоверение). Молчаливое указание на несуществующий узел запрещено —
   это класс `security.md` §«Контроль, у которого нет МЕХАНИЗМА исполниться».
3. **Стенд не исключение** (ban #16): узел-приёмник писем объявляется частью профиля стенда и
   работает в production-posture. Режим «в проде ничего, на стенде как-нибудь» запрещён.
4. **Консоль показывает ссылку приглашения тогда и только тогда, когда она есть.** Обещание в
   тексте, не подкреплённое полем, снимается.
5. **Сквозная проба обязательна:** вход → выход → вход целиком, без ручных шагов; и приглашение,
   проходящее **до** появления второго человека в аккаунте.

**Круг 1б (2026-08-28) добавил к этому три решения владельца** — ссылка приглашения вызывающему не
возвращается, готовность операции на доставку не гейтится, ограничение частоты действует всегда с
непустым умолчанием, — и шесть решений автора по остальным вопросам. Все девять разобраны
построчно в §13; **открытых вопросов документ не несёт**.

### Главное следствие — оно НЕ в письмах, письма лишь средство

Продукт сегодня **не даёт войти второй раз**, и это не деградация под нагрузкой и не редкий край:
это первый рабочий день каждого сотрудника. Всё остальное — приглашения, восстановление, вторые
администраторы — стоит **за** этой дверью. Поэтому несущий сценарий фазы не «письмо ушло», а
**MAIL-02: вход → выход → вход**, и порядок работ §11 ставит его первым.

Второе следствие названо отдельно, потому что его легко принять за косметику: **возможность,
объявленная и неисполнимая** (`api-conventions.md` §«Неисполнимая возможность»), дороже
отсутствующей. Отсутствующую заводят; объявленную считают сделанной — консоль обещает ссылку,
четыре страницы документации учат ею пользоваться, провайдер инфраструктуры про неё знает, и никто
не замечает, что производителя у неё нет.

## §1 Что верно в дереве — измерено, а не предположено

Ревизия всех замеров — `6339b2f0b`. Где предикат мог дать ложный ноль, рядом стоит **контроль**:
тот же предикат на предмете, который в дереве заведомо есть.

### 1.1 Отправителя почты в коде продукта — ноль

```
git grep -in 'smtp' -- '*.go' ':!*_test.go'                        → 0
git grep -l  '"net/smtp"' -- '*.go'                                → 0
git grep -c  'SendMail|Mailer|MailSender|Courier' -- '*.go' ':!*_test.go' → 0 по каждому
```

**Контроль (объём осмотренного):** файлов Go, содержащих `func `, в не-тестовом дереве — **1647**;
файлов Go в `services/` — **3106**, из них не-тестовых — **1200** (сверено вторым предикатом:
`git ls-files` и `find` дают одно и то же число). То есть «ноль находок» здесь отличимо от «ноль
прочитанного».

**Что это значит.** Письма отправляет **не наш код**: это делает почтовый процесс внешнего
поставщика личности, настраиваемый нашей конфигурацией. Отсюда следует форма работы фазы —
предмет в **настройке, страже старта, профиле стенда и контракте**, а не в новом Go-отправителе.

### 1.2 Профили называют почтовый узел — и не создаёт его ни один шаблон

```
git grep -ril 'mailhog|mailslurper|mailpit|maildev|smtp4dev' -- .   → 5 файлов
из них шаблонов, СОЗДАЮЩИХ объект (kind: Service/Deployment/StatefulSet) → 0
```

Пять файлов — это **записи адреса** (два слоя умолчаний и два встроенных блока профилей) плюс один
шаблон, который **пишет адрес в конфигурацию**, а не поднимает узел.

**Контроль:** предикат находит имена узлов там, где они объявлены; объектов с этим именем в
`deploy/**/templates/*` — ноль при том, что объектов вообще в этих каталогах много.

### 1.3 НАШИ почтовые ручки не объявляет ни один профиль — включая боевой

Величины `connectionURI` / `fromAddress` / `fromName` (ручки продукта, из которых рендерится
конфигурация) объявлены ровно в **двух** местах, и оба — **слои умолчаний**: базовые значения
зонтичного чарта и их копия в значениях подчарта личности.

Перепись по каждому профилю — **обе** формы записи сразу, потому что их две: наша ручка
(`connectionURI`) и встроенный блок поставщика (`connection_uri`).

| профиль | называет службу личности | наша ручка | встроенный блок |
|---|:--:|:--:|:--:|
| `values.dev.yaml` | да | 0 | **1** |
| `values.fe3455-ory-posture.yaml` | да | 0 | **1** |
| `values.dev-prod.yaml` | да | 0 | 0 |
| `values.prod.yaml` | да | 0 | 0 |
| `values.fe3455.yaml` | да | 0 | 0 |
| `values.fe3455-prod.yaml` | да | 0 | 0 |
| `values.a8f60d.yaml` | да | 0 | 0 |
| `values.prorobotech.yaml` | нет | 0 | 0 |
| `values.digests.example.yaml` | нет | 0 | 0 |

Предикат: `for f in $(git ls-files 'deploy/helm/umbrella/values*.yaml'); do grep -c
'kratos\|connectionURI\|connection_uri' "$f"; done` — по каждому профилю отдельно.

**Читается это так, и разница существенна:**

- профилей посадки, поднимающих службу личности, — **7**; восьмой файл со словом о личности —
  базовый слой значений, девятый и десятый её не поднимают вовсе;
- **нашу** ручку не объявляет **ни один из семи**. Величина приезжает только из умолчания;
- **два** из семи высказываются о почте своим **встроенным блоком** — то есть вторым местом об
  одном предмете (§1.6), и называют тот же узел, которого никто не создаёт;
- **пять** из семи о почте не высказываются вовсе — включая **боевой**.

> [!note] Здесь у меня была ошибка, и она записана, а не заметена
> Первая редакция таблицы называла «0 из 7» по обеим формам сразу и включала в перечень профиль,
> который службы личности не поднимает, а профиль, который её поднимает и о почте **высказывается**,
> — пропускала. Причина ровно та, от которой предостерегает `measurement-discipline`: перечень
> собран одним предикатом, значения — другим, и множества не совпали. Перемер обеими формами по
> одному списку дал таблицу выше.

**Класс назван прямо:** умолчание **всегда непусто**, поэтому настройка выглядит выполненной в
каждом профиле, и ни один профиль не обязан ничего задавать, чтобы это заметить. Это тот самый
признак из `security.md` §Hardening п. 9 — «адрес зависимости не выводится и не подставляется
молча». Плюс **две копии одного умолчания** — два места об одном предмете, которые сегодня
совпадают и разойдутся молча.

### 1.4 Полоса до почтового узла объявлена НЕШИФРОВАННОЙ

```
git grep -c 'disable_starttls' -- deploy/   → 4 файла (2 слоя умолчаний + 2 встроенных блока)
```

Величина стоит в самом адресе узла. Под ban #16 («production-mode ВЕЗДЕ, включая стенд») незашифрованная
полоса — не «дев-удобство», а посадка, которой на поднятом стенде существовать не должно.

### 1.5 Обещание «в боевой посадке ретранслятор приезжает внешними секретами» предмета не имеет

Единственное место в дереве, где внешние секреты названы рядом с почтой, — **комментарий в том же
шаблоне**. Объектов `kind: ExternalSecret` в шаблонах развёртывания — **0** (единственное вхождение —
пример в README подчарта). Комментарий описывает намерение как факт (`architecture.md`
§doc-truthfulness): следующий читатель решит, что боевой профиль почту получает, и не станет искать.

### 1.6 Обе полосы входа требуют подтверждённого адреса — а поток подтверждения объявлен ДВАЖДЫ и по-разному

```
git grep -rn 'require_verified_address' -- deploy/   → 2 вхождения, обе полосы входа
```

Требование стоит на обеих полосах (ключ доступа и пароль). Поток подтверждения при этом объявлен
**двумя** источниками, и они расходятся:

| источник | поток подтверждения | полосы входа |
|---|---|---|
| наша конфигурация (шаблон подчарта) | **включён**, доставка кодом | требуют подтверждённого адреса |
| встроенные блоки двух профилей | **выключен** | без этого требования |

Оба файла доезжают до процесса, и какая величина победит, решает **порядок слияния**, которого
никто не выбирал. Это сказано не мной: так объясняет свой собственный блок один из этих профилей —
«процесс получает оба файла и сливает их по порядку, то есть какая из двух величин победит, решал
ПОРЯДОК». Что наша конфигурация в этом порядке **последняя**, подтверждается с двух сторон: комментарий
профиля `values.a8f60d.yaml` называет её вторым источником, впервые читаемым процессом, а
`architecture.md` §«Конфигурация, впервые ставшая ЧИТАЕМОЙ» описывает уже наступившее следствие —
объявленный нами раздел заместил умолчание поставщика целиком, и полоса регистрации паролем
потеряла выдачу сессии, пока это не починили.

**Кому верить — вопрос, который приёмка НЕ решает чтением.** Приёмка требует, чтобы двух источников
не осталось (Р11), и тогда вопрос исчезает вместе с ними. Сценарий MAIL-18 утверждает именно это, а
не «побеждает такой-то».

Тот же класс уже чинился один раз соседним предметом: перечень методов входа из встроенных блоков
**убран**, и держит это гейт дерева `deploy/identity_second_factor_reachable_test.go` — профиль,
доводящий наши настройки до процесса и при этом высказывающийся о методах, объявлен находкой. Поток
подтверждения под тот гейт не подпадает и остался.

**Это и есть механизм #1234, названный целиком:** вход требует подтверждённого адреса → подтверждение
доставляется письмом → письмо шлёт почтовый процесс → он настроен на узел, которого нет.

### 1.7 Поле ссылки приглашения объявлено контрактом и не заполняется никем

```
git grep -c 'MagicLink' -- 'services/'                → 0 файлов
git grep -l 'MagicLink' -- 'pkg/' ':!pkg/api/**'      → 0 файлов
```

**Контроль в обратную сторону — решающий.** Тем же предикатом по соседнему имени:

```
git grep -n 'InviteUserMetadata' -- 'services/'       → 3 файла, среди них место сборки метаданных
```

Метаданные операции приглашения **собираются** — в них кладут идентификатор человека и
идентификатор аккаунта. Третье поле, ссылка, не кладётся никогда. Значит предикат различает
«не ищет» и «не находит»: он находит соседа и не находит предмет.

Дополнительно: **проб, утверждающих это поле, тоже ноль** — среди **96** файлов кейсов чёрного ящика
(`tests/newman/cases/*.py`) приглашение упоминают **19**, ссылку — **0**. У возможности нет ни
производителя, ни утверждения о ней.

### 1.7а Выкупаемой ссылки приглашение НЕ выпускает вовсе — шаг снят вместе с клиентом

Замер круга 1б, решивший вопрос о судьбе уже созданных приглашений (Р17).

```
зависимости use-case приглашения (поля его структуры)
  → хранилище · журнал операций · проверка прав · клиент движка прав ·
    реконсайлер · логгер            — клиента поставщика личности НЕТ
совпадений с именем поставщика в файле → 3, все ТРИ в комментариях
```

Комментарий самого use-case говорит это прямо: шаг выпуска ссылки **снят вместе с клиентом**, а
чем именно активируется строка, оставлено вовне. Значит поле метаданных (§1.7) не просто не
заполняется — **заполнять его нечем**: величины, которую туда кладут, не производится ни на одном
пути.

**Следствие, которое дороже самого замера:** среди строк в состоянии ожидания **нет ни одного
невыкупленного предъявителя**. Вопрос «что делать с уже выданными ссылками» не имеет предмета — и
это установлено замером, а не предположено. Требование отзыва (Р19) остаётся **вперёд**: механизм
заводится этой фазой.

**Контроль:** тот же способ чтения зависимостей находит у этого же use-case четыре других клиента и
порта — то есть предикат видит зависимости, когда они есть.

### 1.8 Консоль обещает ссылку письменно, и ветка показа недостижима

Два места консоли читают поле и рисуют по нему блок; текст на экране выдачи прав **обещает**, что
ссылка появится после сохранения. Поскольку поле не заполняется (§1.7), обе ветки — мёртвый код, а
обещание — ложь на продуктовой поверхности.

К этому же принадлежит наблюдение задачи #1233 о повторном нажатии: форма не закрывается, а второе
нажатие идёт по пути, где контракт объявляет **идемпотентное** повторное приглашение. Форма отказа
на повторе — предмет сценария MAIL-35, а не следствие доставки.

### 1.9 Четыре страницы продукта учат пользоваться тем, чего нет

```
git grep -rl 'magicLinkUrl' -- services/   → 4 страницы
```

Все четыре объявляют ручную передачу ссылки администратором и прямо говорят, что автоматической
отправки нет. Утверждение верно про отсутствие отправки и **неверно** про доступность ссылки.

> [!note] Предикат этого замера с первого раза дал ЛОЖНЫЙ НОЛЬ — и это записано намеренно
> Форма `git grep -rl … -- 'services/*/docs/'` вернула **0** при живых четырёх страницах: путь
> с шаблоном в середине этой формой не сопоставился. Ноль выглядел как находка («ни одна страница
> не обещает»), и вывод из него был бы противоположен истине. Правило `measurement-discipline`
> здесь сработало ровно так, как написано: число проверяется вторым предикатом (`-- services/`),
> и только сошедшееся идёт в документ.

### 1.11 Сквозная проба ни разу не заходит на страницу входа


Фикстура доводит арендатора до рабочей сессии **регистрацией**, на которой сессия выдаётся сразу.
Полоса входа не исполняется ни одной пробой **ни разу**. Именно поэтому разрыв #1234 дожил: он
лежит там, куда сквозной корпус не заходит.

Рядом — уже признанный долг в самом корпусе проб: фикстуры второго человека в аккаунте нет, и
комментарий пробы называет это остатком с предикатом снятия. То есть вторая половина #1233
(«приглашение проходит до появления второго человека») сегодня не проверяется тоже.

Его в дереве нет, и назвать его сегодня значило бы выдумать; величина снимается при посадке и
обязана уместиться в названный запас.

## §2 Решения — ратифицировать явно

Решения владельца §0 сформулированы как принципы; ниже они превращены в требования, у каждого
назван признак нарушения. Где решение владельца молчит, решение принято здесь и помечено
**(решение автора)** — по non-negotiable #18 («все решения принимаешь ты»).

**Круг 1б закрыл открытые вопросы решениями.** Р14–Р20 внесены им: три ответа рассмотрены владельцем
(один уточнён), шесть решены автором. Построчный разбор — §13; **открытых вопросов в документе
не осталось**.

### Р1. Доставка — часть поставки, и путь ровно один

Продукт умеет отправлять письмо трёх видов: **подтверждение адреса**, **приглашение**,
**восстановление доступа**. Отправитель настраивается; второй, «обходной», путь не заводится.

*Признак нарушения:* в дереве два способа доставить одно и то же письмо, и какой сработает,
решает не решение, а порядок.

### Р2. «Нужна ли доставка» — НЕ ручка: величина ВЫВОДИТСЯ из включённых полос **(решение автора)**

Владелец сказал «если доставка объявлена нужной». Отдельной ручки «нужна/не нужна» не заводится:
ручка, отключающая доставку, немедленно означает либо неработающий вход (сегодняшнее состояние),
либо снятое требование подтверждённого адреса — то есть **смену посадки безопасности**, а такой
режим запрещён ban #16 и #14.

Поэтому: **надобность доставки выводится** — если включён хотя бы один поток, который доставляется
письмом, настройка почты обязана быть полной. И зеркально: профиль, требующий подтверждённого
адреса на входе, обязан иметь **включённый** поток подтверждения.

*Признак нарушения:* профиль, у которого требование подтверждённого адреса стоит, а поток
подтверждения выключен, — тот самый #1234, и он обязан не рендериться, а не «работать до первого
выхода».

### Р3. Встроенного умолчания у почтовых величин НЕТ

Умолчание почтового узла, адреса отправителя и удостоверения — **пустое**. Пусто ⇒ отказ старта
(Р4), а не «разумное значение». Обе сегодняшние копии умолчания снимаются вместе.

*Признак нарушения:* величина, которую построение подставляет молча, предметом стража быть не
может — он зелен при любом входе, потому что незаданной величина не бывает.

### Р4. Отказ старта — по КАЖДОЙ величине и по ПОЛОВИНЕ пары

Страж отказывает в пуске, называя **ручку** и **профиль**. Отдельно требуется отказ на **половине**:
узел задан, удостоверение — нет. Половина настройки хуже отсутствия обеих, потому что выглядит
настроенной.

Вырожденные значения (пустая строка, пробел, одинокая запятая, схема без узла) считаются
**незаданными**, а не «непустыми»: страж и потребитель обязаны применять **один** предикат, иначе
они разойдутся ровно там, где расхождение опасно (`security.md` §«Кто вправе говорить за
пользователя», подкласс про вырожденное значение).

### Р5. Полоса до почтового узла шифрована — и на стенде тоже

Транспорт до узла — с шифрованием и проверкой сертификата по объявленному якорю доверия. Величина,
снимающая шифрование, стражем **отвергается**. Исключения для стенда нет (ban #16); узел-приёмник
стенда обязан нести сертификат внутреннего удостоверяющего, как всё остальное на этом стенде.

### Р6. Удостоверение приезжает из СЕКРЕТА, не из карты настроек **(решение автора)**

Сегодня удостоверение выразимо только внутри адреса узла, а адрес попадает в карту настроек —
то есть в объект, который читается шире, чем секрет, и попадает в рендер чарта. Удостоверение
выносится в отдельную величину, приезжающую из секрета и подставляемую до старта процесса —
**тем же приёмом**, каким уже подставляется учётная величина обратных вызовов; второго механизма не
заводится.

*Признак нарушения:* рендер карты настроек содержит удостоверение почтового узла.

### Р7. Узел-приёмник писем — часть профиля стенда, объявленная чартом

Стенд получает приёмник писем **объявлением**, а не руками: он поднимается тем же развёртыванием,
что и всё остальное, и работает в production-posture (Р5). Пробе он даёт способ прочитать
доставленное письмо и извлечь код/ссылку.

*Признак нарушения:* «поднимите почтовый узел сами» в инструкции. Это ровно «условие не создано»,
поднятое до обязанности читателя.

### Р8. Ссылка и код — ПРЕДЪЯВИТЕЛЬ, и обращаются с ними соответственно

Одноразовость · ограниченный срок · привязка к потоку · снятие невыкупленных при выходе отовсюду и
при смене способа входа · отсутствие в журналах, метриках, трассах и ответах API · ограничение
частоты выдачи.

*Признак нарушения:* любое из перечисленного «предполагается свойством поставщика» без пробы,
которая это утверждает.

### Р9. Ответ на «отправить письмо» не различает существование адреса

Ответ поверхности, отправляющей письмо неаутентифицированному вызывающему (восстановление,
повторная отправка подтверждения), **одинаков** для существующего и несуществующего адреса — код,
тело и форма. Различимый ответ здесь — оракул существования учётной записи.

Отдельно: **ограничение частоты не вправе становиться оракулом** — отказ по частоте обязан быть
неотличим по тем же осям.

### Р10. Поле ссылки снимается с контракта **(круг 1б: ПРИНЯТО владельцем)**

`api-conventions.md` §«Принято-и-проигнорировано» знает три исхода. Здесь выбран **третий** — снять
с контракта с резервированием номера и имени:

- **реализовать** отвергнуто: возвращать ссылку вызывающему значит выдавать приглашающему
  предъявителя, которым тот войдёт **за** приглашённого. Это делегирование без согласия, области и
  срока — ровно то, что `security.md` §«Авторизация живёт в модели» запрещает называть
  олицетворением по умолчанию;
- **отвергать явно** неприменимо: поле выходное, а не входное;
- **снять** — исход. Вместе с ним снимается обещание в консоли (решение владельца, п. 4) и правятся
  четыре страницы продукта (§1.9).

Взамен консоль получает то, что действительно есть: **состояние приглашения** и **повторную
отправку письма**.

**Исход законен ТОЛЬКО потому, что доставка становится обязательной** — и это несущая часть
обоснования, а не оговорка. Профиль отказывается стартовать без настроенного отправителя (Р2, Р4)
⇒ развёрнутого стенда без доставки **не существует** ⇒ у ссылки, отданной вызывающему, **нет
законного потребителя**: некому её передавать вручную, потому что письмо уходит само. Снимается не
«неудобное поле», а поле, у которого исчез предмет.

**Цена отзыва названа прямо, потому что шаг необратим.** Если продукт когда-нибудь решит, что
доставка **не** обязательна — что оператор вправе поднять посадку без отправителя, — ручная передача
ссылки становится единственным путём приглашения, и поле придётся вернуть. Вернуть его под **тем же
номером нельзя**: номер и имя зарезервированы. Значит цена — **новый номер поля и второе имя для
одного предмета** в публичном контракте, то есть ровно тот шов, которого конвенции велят избегать.

Отсюда практическое следствие для ревизии решения: **отзывать надо не Р10, а Р2.** Пока доставка
обязательна, Р10 из неё выводится; спорить с Р10 отдельно — спорить со следствием вместо посылки.

### Р11. Одно объявление настройки личности; второе — находка

Настройка потоков доставки объявляется **одним** местом. Профиль, который доводит нашу конфигурацию
до процесса и при этом сам высказывается о потоках доставки, — находка гейта. Это продолжение уже
принятого решения по перечню методов входа, распространённое на потоки.

### Р12. Переход уже зарегистрированных — восстановлением, без миграции данных **(решение автора)**

Человек, зарегистрировавшийся до появления доставки, имеет неподтверждённый адрес и после этой фазы
войти по-прежнему не сможет. Ему открыт путь **восстановления доступа**, который теперь доставляется;
успешное восстановление обязано оставить адрес **подтверждённым**.

Массовая простановка «подтверждён» существующим строкам **отвергнута**: она утверждает факт, которого
никто не наблюдал, и делает это для всех сразу.

*Признак нарушения:* миграция, проставляющая признак подтверждения.

### Р13. Сквозная проба входа существует и ходит ЧЕРЕЗ выход

Фикстура получает второй способ доведения арендатора до сессии — **через полосу входа**, а не только
регистрацией. Существующая фикстура регистрации сохраняется: она нужна другим пробам и служит
положительным контролем.

*Признак нарушения:* «вход проверен» при нуле переходов на страницу входа.

### Р14. Ограничение частоты действует ВСЕГДА; профиль вправе его изменить, но не снять **(круг 1б: решение владельца)**

Величина ограничения замеряется и объявляется профилем — но **умолчание непусто и консервативно**.
Незаданное ограничение означало бы «не ограничиваем», а это в точности класс
`api-conventions.md` §«Пустое значение обязано означать пусто»: пустая величина утверждала бы о
продукте то, чего он не делает.

| требование | признак нарушения |
|---|---|
| ограничение действует при **молчащем** профиле | профиль ничего не сказал — писем уходит сколько угодно |
| профиль вправе **изменить** величину | величина зашита в код и профилем не читается |
| профиль **не вправе снять** ограничение | существует значение, при котором ограничения нет: ноль, отрицательное, «выключено» |
| страж старта требует **положительного** значения | ноль и отрицательное принимаются молча |

**Величина умолчания назначается РЕШЕНИЕМ, а не замером — и это сказано прямо.** Замера у нас нет и
не будет до эксплуатации: сегодня писем не уходит ни одного, мерить нечего. Поэтому рядом с
величиной стоит **предикат пересмотра**: доля законных обращений, отвергнутых ограничением,
превысила названную профилем долю ⇒ величина пересматривается. Без предиката умолчание стало бы
числом, которое никто никогда не оспорит.

### Р15. Арендатору показывается «ОТПРАВЛЕНО», никогда «ДОСТАВЛЕНО» **(круг 1б: решение автора)**

Граница честности фазы названа в §13.2: продукт видит **сдачу письма ретранслятору**, а не его
получение. Значит консоль вправе сказать «письмо отправлено» и назвать **время отправки** — и не
вправе сказать «доставлено» ни одним словом.

*Признак нарушения:* любая формулировка, утверждающая, что письмо **получено**. Это ровно
«возможность объявлена и неисполнима» — тот же класс, что снимаемое обещание ссылки, только
изнутри.

### Р16. Адрес отправителя — один на установку **(круг 1б: решение автора)**

Адрес отправителя объявляется профилем и одинаков для всех арендаторов установки. Арендатор его не
выбирает, и **поля под этот выбор в контракте не заводится**.

**Почему не арендаторский:** выбор адреса арендатором тянет за собой подтверждение владения доменом
— отдельный механизм со своей поверхностью, своими записями в чужой зоне и своим сроком. Завести
поле, не заведя подтверждения, значит принять величину и позволить отправлять от чужого имени;
завести подтверждение — это другой домен работы, и он не эта фаза (§7 п. 3).

*Признак нарушения:* поле запроса, похожее на адрес отправителя, в любом глаголе, отправляющем
письмо.

### Р17. Уже созданным приглашениям письма НЕ досылаются **(круг 1б: решение автора, после перемера)**

**Перемер решил вопрос до того, как его пришлось решать.** Шаг, выпускавший выкупаемую ссылку,
**снят вместе со своим клиентом** — это сказано комментарием самого use-case приглашения, и его
зависимости этого клиента не содержат (§1.7а). Следовательно **невыкупленных предъявителей среди
строк в состоянии ожидания — ноль по построению**: ссылок не выпускалось.

Отсюда решение распадается надвое, и обе половины проще, чем вопрос:

- **миграции не требуется вовсе** — отзывать нечего. Предикат: у глагола приглашения нет клиента
  поставщика личности, значит выпуска ссылки нет ни на одном пути;
- **автоматическая рассылка по существующим строкам отвергнута.** Это была бы рассылка по адресам,
  владельцы которых о приглашении могли забыть, инициированная не человеком, а выкаткой.
  Администратор отправляет письмо повторно **сам** — глагол для этого заводится тем же объёмом
  (MAIL-38), и это действие человека, а не побочный эффект развёртывания.

*Признак нарушения:* миграция или разовая работа, рассылающая письма по существующим строкам.

### Р18. Приёмник писем — часть ЯДРА стенда, а не шлюзуемый компонент **(круг 1б: решение автора, после перемера)**

Первоначально предполагалось отдать приёмник тому шарду, что уже поднимает службу личности. Перемер
это **опроверг**, и опроверг дважды:

1. **шардов семь, и службу личности поднимают все** — она объявлена нужной каждому («всем без
   исключения нужны: iam, край, поставщик личности»). Значит «отдать одному шарду» невыразимо;
2. **шлюзуемый приёмник воспроизводит ровно тот дефект, который фаза снимает.** Страж старта
   (Р4) проверяет, что настройка **задана**, а не что узел **поднят**, — и правильно делает: узел
   может лежать и подниматься позже, отказ старта из-за этого был бы отказом на временной причине.
   Значит шард, снявший приёмник и оставивший настройку, стартует и молча не доставляет — то самое
   состояние, которое сегодня и чинится. А снять вместе с приёмником настройку он не вправе: тогда
   служба личности не стартует вовсе (Р2, Р4).

Поэтому приёмник входит в **ядро** стенда — то, что поднимается всегда и не выключается ручкой.
Под ban #16 это же следует и по посадке: всякий **развёрнутый** стенд работает в боевой посадке, а
посадка, в которой письма не уходят, боевой не является.

> [!note] Рассмотренная и отвергнутая альтернатива — назвать её обязательно
> Можно было оставить приёмник шлюзуемым и завести **гейт**, требующий: шард, объявивший почтовый
> узел, обязан этот узел поднимать. Это исполнимо, и предикат у него есть. Отвергнуто по цене:
> такой гейт обязан уметь сопоставлять **адрес** узла с **набором компонентов** шарда — то есть
> знать, как имена внутри кластера отображаются в объявления, — а выигрыш ограничен аппетитом
> приёмника, который заведомо мал на фоне раскладки. Гейт со сложным предикатом ради малой
> экономии — плохой размен; если аппетит окажется велик (Р18, абзац о цене), альтернатива
> возвращается вместе с этим замером.

**Цена названа и ограничена, а не предположена:** запросы приёмника объявляются в тех же единицах,
что и остальная раскладка стенда, и обязаны оставить **самый тяжёлый** шард ниже доступного
раннеру. Число снимается **при посадке**, а не сейчас: приёмника ещё нет, и назвать его аппетит
сегодня значило бы выдумать. Если оно не влезет — решение пересматривается целиком, а не
«подпирается» поднятым пределом (`testing.md` §«Подпорка зеленит вердикт»).

### Р19. Невыкупленное письмо обесценивается ГЛАГОЛОМ, снимающим участие **(круг 1б: решение автора)**

Отзыв невыкупленных предъявителей (Р8, MAIL-24) распространяется на **все** глаголы, снимающие
участие или личность, — как бы они ни назывались. Требование формулируется по **исходу**, а не по
имени: если человек перестал быть участником, письмо, выданное ему и не выкупленное, перестаёт
действовать **немедленно**, а не по истечении срока.

**Сегодня класс пуст** (Р17: ссылок не выпускалось), поэтому это требование **вперёд**, а не
починка. Именно поэтому оно записано здесь: механизм заводится этой фазой, и завести его без отзыва
значит завести предъявителя, переживающего снятие участия.

> [!note] Находка по дороге, которая этой приёмке не принадлежит
> Контракт советует читателю «отозвать приглашение» и **не называет глагола**: службы пользователей
> с таким именем в контрактах личности нет, а действие выразимо двумя разными глаголами. Читателю
> оставлен выбор из двух кандидатов там, где текст говорит об одном. Это предмет **своей** задачи
> (`multi-agent-flow.md` §«Находка по дороге»), а не этой фазы: чинить чужой предмет в своём
> изменении значит сделать вердикт непрослеживаемым.

### Р20. Порог «пора заводить свою очередь» опирается на НАБЛЮДАЕМОЕ, а не на новую ручку **(круг 1б: решение автора)**

§7 п. 5 откладывает собственную очередь писем. Предикат его возврата обязан быть адресуем — иначе
пункт не отложен, а забыт. Решение: предикатом служит **счётчик отказов доставки** (MAIL-31),
который эта фаза и заводит; величина, выше которой мы действуем, — **эксплуатационное решение**,
записываемое в задаче, а не ручка продукта.

**Ручка отвергнута осознанно.** Настройка «при какой доле недоставленных строить очередь» не
читается ни одной строкой кода: она описывает **наше** будущее решение, а не поведение продукта.
Завести её значило бы принять величину и никогда её не прочитать — ровно «принято-и-проигнорировано»
(`api-conventions.md`), только заведённое собственными руками и заранее.

*Признак нарушения:* ручка в профиле, которую не читает ни один путь исполнения.

## §3 Пять вопросов владельца (non-negotiable #18) — письменно

Каждый вопрос отвечается **признаком отказа**, а не признаком одобрения.

### 3.1 Благо продукта

*Отвергается, когда единственный выигрыш — меньше работы сейчас.*

Выигрыш не в работе исполнителя: **второй вход в продукт становится возможным**. Сегодня
последовательность «зарегистрировался → вышел → вошёл» не проходит, а выхода без неё не существует.
Работы это решение **добавляет** — узел в профиле стенда, страж, гейты согласия полос, две сквозные
пробы, снятие поля с контракта и правка четырёх страниц.

### 3.2 Конкурентоспособность — по своей оси

*Отвергается, когда выигрыш формулируется как «как у …».* Сравнения запрещены (ban #2); ось своя:

| ось | сегодня | после фазы |
|---|---|---|
| **предсказуемость контракта** | глагол приглашения объявляет поле, которого не бывает; консоль обещает ссылку | контракт не объявляет того, чего не производит; обещание снято вместе с полем |
| **время до первого успешного вызова** | не определено: второй вход не проходит; приглашённый не получает ничего | регистрация → письмо → подтверждение → вход; приглашение → письмо → вход приглашённого — **без участия администратора вручную** |
| **цена эксплуатации** | профиль молчит о почте и стартует; неработающая доставка обнаруживается обращением в поддержку | профиль без почты **не стартует**; «ноль писем за всю жизнь» видно счётчиком, а не жалобой |

### 3.3 Перспективность — что придётся отозвать, если решение неверно

*Отвергается, когда ошибка необратима.*

| элемент решения | обратимость |
|---|---|
| узел-приёмник в профиле стенда | обратим: профиль правится, данных арендатора не касается |
| страж старта | обратим: правка условия; ни одна внешне-адресуемая координата не затронута (ban #15) |
| **снятие поля ссылки с контракта** | **ломающее**: номер и имя резервируются, вернуть поле под тем же номером нельзя. Это единственный необратимый шаг, и он назван вслух |
| перенос удостоверения в секрет | обратим правкой профилей |
| требование шифрованной полосы | обратимо, но откат = понижение посадки, то есть отдельное решение владельца |

Миграции данных арендатора решение **не требует ни в одном пункте** (Р12, Р17 — по последнему это
не выбор, а замер: отзывать нечего, §1.7а).

**Круг 1б необратимых шагов не добавил**, и это проверено по каждому из шести решений автора
(§13.3): текст консоли, адрес отправителя, отказ от досылки, приёмник в ядре, отзыв по исходу и
отсутствие лишней ручки — все обратимы, причём два из них (Р16, Р20) обратимы **аддитивно**: поле и
ручка заводятся позже, ничего не отзывая. Необратимый шаг в документе остаётся **один** — Р10, и он
принят владельцем.

### 3.4 Безопасность — что расширяется

*Отвергается, когда решение расширяет поверхность, и расширение не названо.* Названо в §4 целиком.
Кратко: заводится **исходящее соединение** службы личности к внешнему ретранслятору и **канал**,
по которому наружу уходит предъявитель.

Круг 1б **сузил** две стороны этой поверхности, а не расширил: ограничение частоты действует при
молчащем профиле и снятию не подлежит (Р14), а адреса отправителя арендатор не выбирает вовсе —
поля под это в контракте нет (Р16).

### 3.5 Производственность

*Отвергается, когда есть режим, годный только для стенда, либо часть, отложенная «на потом».*

Режима «только для стенда» нет: стенд получает **тот же** путь доставки в той же посадке (Р5, Р7),
меняется лишь адресат — приёмник внутри кластера вместо внешнего ретранслятора. Отложенного «на
потом» внутри объёма нет; отложенное **вынесено** в §12 с предикатом возврата по каждому пункту, а
не оставлено маркером.

### 3.6 Узнаваемость — четыре направления

| направление | что спрашивает | ответ этой фазы |
|---|---|---|
| **архитектор** | чей это домен; что отзывать, если неверно; какое ребро заводится | домен — личность; отзывать — §3.3; ребро — исходящее к ретранслятору, к перечню рёбер оно **не добавляется**: вызываемый не наш сервис (§4.1) |
| **разработчик** | сколько шагов до первого успешного вызова; говорит ли отказ, что делать | регистрация → письмо → подтверждение → токен; отказ входа называет следующий шаг и даёт переслать письмо (MAIL-03) |
| **девопс/SRE** | по чему в три часа ночи отличить «сломан продукт» от «не создано условие» | профиль без почты **не стартует** и называет ручку; недоступность узла даёт классифицированный отказ и счётчик, а не тишину (MAIL-30, MAIL-31) |
| **продакт** | какой шаг клиент делает первым; чем платит | первый шаг — регистрация и подтверждение адреса; платит одним письмом и одним экраном; за приглашение больше не платит **ручной передачей ссылки** |

## §4 Расширение поверхности безопасности — названо явно

### 4.1 Новое исходящее соединение

Служба личности (её почтовый процесс) получает **исходящее** соединение к почтовому ретранслятору.
Требования: шифрованный транспорт с проверкой сертификата (Р5) · удостоверение из секрета (Р6) ·
собственный предел времени на попытку · ограниченное число повторов · классифицированный отказ
вместо тихого мягкого прохода (`security.md` §Hardening п.8).

**В перечень межсервисных рёбер (`polyrepo.md`) это НЕ добавляется, и причина названа:** перечень
описывает, кто из наших зовёт кого из наших на пути запроса. Ретранслятор — не наш сервис, а
арендатор в этом соединении не участвует. Ацикличность не затрагивается: входящих вызовов у службы
личности не появляется ни одного.

### 4.2 Наружу уходит ПРЕДЪЯВИТЕЛЬ

Письмо несёт ссылку либо код, обладание которым даёт вход. Отсюда весь Р8 и, отдельно, две вещи,
которые легко упустить:

- **отзыв обязан действовать на ПРЕДЪЯВЛЕНИИ, а не только на выдаче** (`security.md` §«Контроль,
  действующий на выдаче, но не на предъявлении»): невыкупленная ссылка, выданная до блокировки
  участника или до выхода отовсюду, обязана перестать работать, а не дожить до истечения срока;
- **срок — объявленное решение, а не следствие удобства**: величина названа в профиле и проверяется
  пробой, а не «получилась».

### 4.3 Оракулы

Три поверхности отвечают неаутентифицированному вызывающему и потому обязаны быть неразличимы по
существованию адреса: восстановление доступа · повторная отправка подтверждения · отказ по частоте
(Р9). Четвёртая — приглашение — аутентифицирована, но **межаккаунтна**: приглашение адреса, у
которого уже есть личность в **чужом** аккаунте, обязано быть неотличимо от приглашения свежего
адреса (MAIL-36). Иначе администратор одного аккаунта перечисляет пользователей другого.

### 4.4 Внедрение в письмо

Адрес получателя приходит **из ввода**. Требование: адрес проверяется единой формой продукта до
формирования письма; управляющие символы и переводы строки отвергаются с именем поля. Адрес
отправителя берётся **только** из настройки и никогда не выводится из ввода.

### 4.5 Что письмо не несёт

Инфра-чувствительного в письме нет (`security.md` §«Инфра-чувствительные данные»): ни внутренних
имён служб, ни адресов узлов, ни идентификаторов подов, ни следов отладки. Письмо адресовано
человеку и содержит только то, что ему нужно для следующего шага.

### 4.6 Продукт как средство рассылки

Поверхность, отправляющая письмо по вводу неаутентифицированного вызывающего, — это способ слать
письма **чужим адресатам** от нашего имени. Ограничение частоты (Р8) здесь не удобство, а условие
того, чтобы продукт не стал ретранслятором для постороннего и не потерял репутацию домена
отправителя.

Общий довод по каждому пункту (ban #14): фаза полна **в своих границах** — путь доставки, который
она заводит, заведён целиком и безопасно; отложенное не оставляет в нём ни одной незакрытой стороны.

## §8 Уровни проб

| уровень | что означает |
|---|---|
| **E** | сквозная проба на поднятом стенде (браузером либо через край) |
| **I** | интеграционная проба службы |
| **D** | декларативная проба профилей развёртывания — читает **объявления**, не рендер, поэтому не умеет пропуститься |
| **G** | гейт дерева |
| **U** | юнит |

## §9 Сценарии (Given-When-Then)

Отрицание везде стоит **в паре** с положительным контролем: без пары «отвергнуто» неотличимо от
«ничего не произошло».

### А. Доставка существует и работает

#### MAIL-01 · Подтверждение адреса доставляется и принимается (E, положительный)
**Given** стенд поднят профилем, объявляющим полную почтовую настройку, и узел-приёмник писем поднят
**When** человек проходит регистрацию с адресом `mail-01-<runId>@<домен стенда>`
**Then** приёмник писем получает **ровно одно** письмо на этот адрес в пределах объявленного бюджета
**And** письмо несёт код подтверждения
**And** ввод кода на странице подтверждения завершается успехом
**And** после этого адрес человека объявлен подтверждённым

#### MAIL-02 · ВХОД → ВЫХОД → ВХОД целиком, без ручных шагов (E, положительный, несущий)
**Given** человек прошёл MAIL-01 и имеет подтверждённый адрес
**When** он выходит из продукта, затем открывает страницу входа и входит тем же способом
**Then** сессия установлена **повторно**
**And** консоль показывает его аккаунт
**And** ни один шаг последовательности не выполнен вручную и ни один не пропущен

#### MAIL-03 · Отрицание в паре: неподтверждённый адрес входа не даёт, и отказ называет следующий шаг (E, отрицательный)
**Given** человек зарегистрирован и **не** подтвердил адрес
**When** он выходит и пытается войти
**Then** вход отвергается
**And** текст отказа называет причину и **следующий шаг** — подтвердить адрес
**And** на том же экране доступна повторная отправка письма
**And** после подтверждения (MAIL-01) вход проходит — то есть отказ был состоянием, а не тупиком

#### MAIL-04 · Восстановление доступа доставляется и снимает прежние сессии (E, положительный)
**Given** человек с подтверждённым адресом и живой сессией в другом браузере
**When** он запрашивает восстановление доступа
**Then** приёмник получает письмо восстановления
**And** после завершения восстановления доступ восстановлен
**And** прежняя сессия в другом браузере более не действует

#### MAIL-05 · Приглашение доходит ДО появления второго человека в аккаунте (E, положительный, несущий)
**Given** в аккаунте ровно один человек — администратор — и он подтвердил свою личность повторно там,
где этого требует глагол приглашения
**When** он приглашает адрес `mail-05-<runId>@<домен стенда>`
**Then** глагол возвращает `Operation`; полл до `done=true` без ошибки
**And** приёмник получает письмо приглашения на этот адрес
**And** приглашённый проходит по ссылке из письма и заводит способ входа
**And** он появляется в списке участников аккаунта
**And** администратор не выполнил **ни одного** действия по передаче ссылки

#### MAIL-06 · Отрицание в паре к MAIL-05: ссылки в ответе нет и консоль её не обещает (E + G, отрицательный)
**Given** та же посадка
**When** администратор приглашает адрес
**Then** тело ответа поля ссылки **не несёт**
**And** на экране выдачи прав нет ни блока со ссылкой, ни текста, обещающего её появление
**And** гейт дерева: в консоли нет ни одного чтения снятого поля
**And** положительный контроль: экран показывает состояние приглашения и кнопку повторной отправки

### Б. Отказ старта — каждая величина и половина пары

**Then** страж считает её незаданной и отказывает

#### MAIL-11 · Положительный контроль к MAIL-07…MAIL-10 (E, положительный)

**When** посадка поднимается
**Then** служба стартует
**And** самоотчёт о посадке называет почтовую настройку как **заданную**, не воспроизводя
удостоверения

#### MAIL-12 · Встроенного умолчания почтовых величин в дереве нет (G, отрицательный)
**Given** дерево развёртывания после снятия встроенных умолчаний (§10 п. 2)
**When** гейт обходит объявления развёртывания

отправителя или удостоверения
**And** гейт печатает объём осмотренного — сколько объявлений прочитано
**And** положительный контроль: величина, которая **обязана** иметь умолчание, гейт не роняет

#### MAIL-13 · Нешифрованная полоса отвергается стражем (D + U, отрицательный)
**Given** профиль объявляет почтовый узел с отключённым шифрованием
**When** посадка поднимается
**Then** служба не стартует; текст называет ручку и требование
**And** **положительный контроль:** шифрованная полоса с проверяемым сертификатом
принимается, и служба стартует

#### MAIL-14 · Удостоверение не попадает в карту настроек (G + E, отрицательный)
**Given** удостоверение вынесено в секрет по Р6
**When** карта настроек рендерится профилем, объявляющим удостоверение
**Then** в рендере удостоверения нет
**And** положительный контроль: процесс всё же им пользуется — MAIL-01 на этом же профиле зелен

### В. Согласие полос — класс #1234 закрывается ПО ПОСТРОЕНИЮ

> **Единица, которую судят гейты этого раздела, — «профиль» как ЭФФЕКТИВНЫЙ набор объявлений**,
> то есть объединение всех источников, доезжающих до процесса этого профиля: наша конфигурация
> **и** встроенные блоки самого профиля. Пофайловая проверка здесь зелена на обеих сторонах
> **by construction** — каждый файл внутренне согласован, — и потому не измеряет ничего: расходятся
> не файлы, а их сумма. Гейт, читающий по файлу, был бы формой без содержания.


#### MAIL-15 · Профиль, включивший полосу с доставкой, обязан нести полную настройку (G, отрицательный)
**Given** эффективный набор профиля включает хотя бы один поток, доставляемый письмом
**When** гейт читает объявления всех источников этого профиля и складывает их
**Then** профиль без полной почтовой настройки — находка, названная поимённо
**And** гейт печатает: профилей прочитано · из них с полосой доставки · из них с полной настройкой

#### MAIL-16 · Зеркало: требование подтверждённого адреса без включённого подтверждения — находка (G, отрицательный)
**Given** эффективный набор профиля требует подтверждённого адреса хотя бы на одной полосе входа
**When** гейт читает объявления **всех** источников этого профиля и складывает их
**Then** выключенный поток подтверждения в том же эффективном наборе — находка
**And** это ровно #1234, и гейт обязан находить его **на состоянии до фикса**: сегодня требование
приходит из одного источника, а выключение — из другого, и **ни одна** пофайловая проверка этого не
видит
**And** доказательство — инъекцией в обе стороны: расхождение найдено с именем профиля, согласованный
эффективный набор (MAIL-17) — молчание

#### MAIL-17 · Положительный контроль к MAIL-15/16: согласованный профиль молчит (G, положительный)
**Given** профиль, у которого полосы согласованы и настройка полна
**When** гейт читает объявления профилей
**Then** гейт молчит
**And** без этого контроля гейт, краснеющий на всём, был бы неотличим от исправного

#### MAIL-18 · Второе место, высказывающееся о потоках доставки, — находка (G, отрицательный)
**Given** профиль доводит нашу конфигурацию личности до процесса
**When** он **сам** высказывается о потоке подтверждения, восстановления или почтовой полосе
**Then** это находка: два места об одном предмете, и какое победит, решал бы порядок слияния
**And** положительный контроль: профиль, о потоках молчащий, гейт не роняет

## §12 Definition of Done

1. **Приёмка APPROVED** от `acceptance-reviewer` до первой строки кода (ban #1); запись в ведомости
   приёмок дерева продукта заведена **вместе с миграцией, если та появится**, а не вперёд неё.
2. Каждый сценарий §9 реализован пробой названного уровня; для **MAIL-02** и **MAIL-16** показана
   пара **RED → GREEN** фактическим выводом (ban #12).
3. Отказ старта (Р4) **меняет исход старта** и доказан на **вырожденном** входе, а не только на
   отсутствующем.
4. Каждый гейт §9 доказан **инъекцией в обе стороны**: возвращённый дефект — находка с координатой;
   законный близнец — молчание. Инъекция роняет **только** проверяемое (`testing.md` §«Гейт на
   класс», п. 2в): прогонов три — контроль, инъекция нового свойства, инъекция существующего.
5. Каждый гейт печатает **объём осмотренного**, и «ноль находок» отличимо от «ноль прочитанного».
6. Профиль стенда **реально поднимается** (не только рендерится) и MAIL-19 зелена на поднятом
   стенде.
7. Ни одно послабление (повтор пробы, поднятый предел, `continue-on-error`) не внесено ради
   зелёного; внесённое — объяснено рядом и несёт предмет (`testing.md` §«Подпорка зеленит вердикт»).
8. Ни одна проба не повторяется целиком и не ждёт временем (`e2e-flow.md` §4).
9. Снятие поля объявлено ломающим изменением; номер и имя зарезервированы; потребителей не осталось.
10. Четыре страницы продукта и записка задачи в vault обновлены **тем же изменением**.
11. Величины, которые фаза вводит (срок ссылки, окно и предел частоты, бюджет попытки, число
    повторов, запросы приёмника), **названы замером или решением**, а не выбраны наугад; каждая
    читается пробой из объявления, а не выписана в пробе. Величина, назначенная **решением**
    (умолчание частоты — Р14), несёт рядом **предикат пересмотра**: без него она превращается в
    число, которое никто никогда не оспорит. Величина, которая описывает НАШЕ будущее решение, а не
    поведение продукта, ручкой не становится вовсе (Р20).
12. Ни одно умолчание, введённое этой фазой, не означает «не ограничиваем» и не означает «не
    доставляем»: пустое значение обязано означать пусто, а не отсутствие контроля.

### 13.2 Граница честности фазы — не вопрос, а факт

Продукт видит **сдачу письма ретранслятору**, а не его получение адресатом. На стенде проба читает
приёмник и потому утверждает доставку **в границах стенда**; в боевой посадке дальше ретранслятора
наш вердикт не идёт.

Это **не откладывается «на потом»** — этого у нас нет **по построению**, пока не заведён обратный
канал от ретранслятора (§7 п. 3). Сказано прямо, чтобы «письма работают» не читалось шире, чем
есть, и чтобы Р15 не выглядел осторожничаньем: он следствие этой границы, а не вкус.

перемером от 2026-08-24: монтируют **два** профиля — разработки и **боевой**, у обоих и довод
`--config`, и том, и путь. Два места об одном предмете, из которых верно одно; неверное стоит в
**страже**, то есть в том самом файле, рядом с которым сядет почтовый страж (Б3).

Это подтверждает §1.6 и Р11 и **не должно чиниться этим изменением** (`multi-agent-flow.md`
§«Находка по дороге попадает в СВОЙ релиз»). Предлагаю завести задачу; в приёмку достаточно
добавить строку, что предмет известен и адресован.
