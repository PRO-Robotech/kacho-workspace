### 2.1. Две находки сверх переписи — обе меняют постановку

**Находка 1. Раскол УЖЕ НАЧАТ: в дереве ДВА модуля, а не один.**

```sh
git ls-files '*go.mod'        # go.mod · services/iam/go.mod
head -1 services/iam/go.mod   # module github.com/PRO-Robotech/kacho-iam
grep PRO-Robotech services/iam/go.mod | head -1
#   github.com/PRO-Robotech/kacho v0.0.0-20260905181354-89d72c19c271
grep -c '^replace' services/iam/go.mod   # 0
```

Служба — **отдельный модуль**, который требует **весь** модуль платформы
версионной зависимостью. То есть ребро `kaname → kacho` существует сегодня не как
импорт, а как **требование модуля**, и это сильнейшая форма того самого цикла,
который целевая раскладка запрещает. Директив замены — ноль, и это устоявшая норма.

Следствие для корпуса правил: утверждение `polyrepo.md` §«Build-граф — ОДИН Go-модуль»
(«`go.mod` в дереве **1**») на этой ревизии **ложно**. Оно снято не будет этим
документом — предмет чужой; заведено задачей-преемником (§11, З5).

**Находка 2. Прод-файлов `pkg/`, привязанных к контракту доступа, ДЕВЯТЬ, а не один.**

```sh
git grep -l 'pkg/api/kacho/cloud/iam/v1' -- 'pkg/' ':!pkg/api/' | grep -v '_test\.go'
```
даёт `listnarrow/{client,narrower,object}.go`, `listnarrow/narrowtest/narrowtest.go`,
`ownerregister/ownerregister.go`, `quota/quotaiam/delta.go`, `quota/quotapb/convert.go`,
`servicehost/serve.go`, `subjectchange/reader.go`.

Число «два прод-ребра» **не воспроизвелось**. Полный обход по обеим осям — привязка
к контракту **и** импорт между каталогами `pkg/` — даёт **5** прод-файлов
запрещённого направления и **0** рёбер `pkg → pkg`. Разбор — §7; итог 2 → 5
складывается из −1 (ребро словаря растворено переклассификацией) и +4 (`listnarrow`,
чей класс исправлен замером).

Из девяти файлов, привязанных к контракту доступа, законны **четыре**
(`ownerregister`, `subjectchange`, `quota/quotaiam`, `quota/quotapb` — все в `kaname`,
там привязка `kaname → kaname`), и **пять** остаются ребром.

## 3. Правило классификации — признак, а не перечень

Читатель обязан классифицировать **52-й** каталог, не спрашивая автора. Правило —
четыре вопроса в жёстком порядке; первый сработавший даёт класс.

**Вопрос 1 — ЧТО ПАКЕТ ПОЛУЧАЕТ НА ВХОД.** Запрос, соединение, данные арендатора —
или **дерево исходников, индекс git, поднятый для пробы контейнер**? Второе →
**`оснастка сборки`**.

**Классифицирует ВОПРОС, а признак его подтверждает — не наоборот.** Признак
(«пакета нет в замыкании импортов ни одного поставляемого двоичного») читается как
тест **только** вместе с вопросом: сам по себе он объявил бы оснасткой всякий
каталог, которого ещё никто не импортировал, а 52-й каталог в день заведения не лежит
в замыкании **by construction**. Если пакет питается запросом, а в замыкании его нет —
это новый или мёртвый пакет, а не оснастка. Если пакет питается деревом исходников, а
в замыкании он **есть** — это **находка** (F5), а не переклассификация.

**Вопрос 2 — ПЕРЕЖИВЁТ ЛИ ПЕРЕЧЕНЬ РАЗДВОЕНИЕ.** Задаётся пакету, чьё содержимое —
перечень, словарь, схема или контракт; остальным не задаётся. Раздвой перечень по
продуктам мысленно и спроси **две вещи, в этом порядке**:

1. **несёт ли он записи ОБОИХ продуктов?** Записи одного — вопрос закончен: перечень
   принадлежит этому продукту (**`kacho`** либо **`kaname`**);
2. **обязан ли КАКОЙ-ТО ОДИН читатель видеть перечень ЦЕЛИКОМ?** То есть существует ли
   точка, куда приходит вход **любого** продукта и которая обязана по нему ответить.

**Оба «да» → перечень обязан быть ОДИН, и его дом — модуль, от которого зависят оба:
`corelib`.** Раздвоив такой перечень, мы получим не две меньшие верные таблицы, а
точку, которая на законный вход отвечает «не знаю» — либо отвечает не то же, что
соседняя половина. Смысл такого перечня в том и состоит, чтобы быть единственным.

**Первое «да», второе «нет» → половины РАЗЪЕДИНИМЫ:** каждая полна для своего продукта
и читается его же кодом. Перечень **расщепляется**, и каждая половина едет к своему
продукту. Класс СТРОКИ в §4 при этом — дом **остатка** (каталог помечается **†**, а
отделяемое названо в §5): у `api` остаток `kacho`, у `quota` и `authz` — `corelib`.

Разбор всех перечней дерева — по обоим вопросам, чтобы правило было применимо, а не
проиллюстрировано:

| перечень | записи обоих? | один читатель обязан видеть целиком? | класс |
|---|---|---|---|
| `ids` — 11 приставок доступа + 26 платформы | да | **да**: классификатор разбирает **любой** предъявленный идентификатор | **`corelib`** (§6) |
| `platformmodules` — `iam` + 6 служб платформы | да | **да**: правило `proxytuple` резолвит домен **любого** вызывающего | **`corelib`** (§7.1) |
| `pkg/api` — контракты обоих | да | **нет**: каждый контракт читает код своего домена, `cloud/vpc` и `cloud/iam` не соперничают | **расщепляется** (§5.1) |
| `quota/refusal.go` — `iam` + 5 платформы | да | **нет**: читают гейт и инструмент, каждый по своему дереву | **расщепляется** (§5.3) |
| `authz.RevocationPolicy.Windows` — 1 доступа + 11 платформы | да | **нет**: гейт сверяет окна со **своим** деревом | **расщепляется** (§5.2) |
| `tokenpolicy` — алгоритмы и обязательные клеймы | **нет**: записи одного продукта | вопрос не задаётся | **`kaname`** |
| `modulemanifest` — ключ чарта и правило адреса | **нет**: раскладка чартов платформы | вопрос не задаётся | **`kacho`** |

> [!warning] Прежняя редакция Q2 давала на `platformmodules` ОБРАТНЫЙ ответ — и это было
> не расхождение с таблицей, а расхождение правила с самим собой
> Первая ветвь звучала «раздвоение даёт **два ответа об одном имени** („как называется
> модуль балансировщика“) → перечень принадлежит тому, чей это модуль». Иллюстрацией
> служила **дословно та самая строка** словаря, который таблица относит к `corelib`:
>
> ```sh
> grep -n 'Service: "nlb"' pkg/platformmodules/platformmodules.go
> #   {Service: "nlb", CatalogModule: "loadbalancer", ObjectDomain: "nlb"}
> ```
>
> То есть читатель, применивший правило к 52-му каталогу, получил бы `kacho` там, где
> таблица говорит `corelib`, — а гейт З1, построенный по такому правилу, отверг бы
> **собственную** таблицу. Противоречие завёл круг 1: класс `platformmodules` сдвинули,
> а правило, из-под которого его сдвинули, оставили нетронутым.
>
> **Чинилось правило, а не классификация.** Довод второй ветви на этом словаре

> модуль». Недоставало **второго** вопроса: прежняя формулировка спрашивала, о чём
> перечень, тогда как решает — **кто обязан прочесть его целиком**.
>
> Урок ровно тот, от которого в этом же круге чинился Вопрос 1: правило и таблица —
> два места об одном предмете, и сдвинув одно, правь второе тем же заходом.

**Вопрос 3 — ЧТО ЗАСТАВИТ ПАКЕТ ИЗМЕНИТЬСЯ.**

* добавление или изменение **ресурса, сервиса, профиля платформы** → **`kacho`**;
* изменение **контракта доступа** — глагол, тип модели, форма удостоверения,
  политика токена, клиентская полоса к службе → **`kaname`**.

**Вопрос 4 — иначе `corelib`**: пакет, чей смысл не меняется от того, какой продукт
его исполняет.

### Ограничение, которое СИЛЬНЕЕ всех четырёх вопросов

**Пакет, от которого зависит прод-код `corelib`, обязан быть в `corelib`.** Иначе
целевое направление невыразимо: `corelib` не вправе зависеть ни от `kaname`, ни от
`kacho`, и никакой ответ вопросов 2–3 этого не отменяет.

```sh
# для каталога <d>: зависит ли от него прод-код corelib ВНЕ его самого
git grep -ln '"github.com/PRO-Robotech/kacho/pkg/<d>"' -- <каталоги corelib> \
  | grep -v _test | grep -v '^pkg/<d>/'
```

Непусто — каталог **`corelib`**, и спорить не о чем. Если он при этом несёт привязку
запрещённого направления, это **дефект** (ребро §7), а не класс: класс говорит, где
пакет живёт, ребро — что в нём чинить. Смешение этих двух вопросов и есть способ
получить цикл, который Go не отвергнет.

**Ограничение решает ровно один случай из 51 — `listnarrow`**, и без него Вопрос 3
дал бы `kaname` (пакет меняется при изменении контракта доступа), то есть правило
разошлось бы с таблицей второй раз. Замер по всем 51: не-`corelib` пакетов, от
которых зависит прод-код `corelib`, — **один** (`pgtest`, и он уже живёт в `corelib`
как оснастка, см. врезку §4), то есть новых принуждений ограничение не создаёт.

**Проверочный вопрос владельца** («это имя, которым продукт себя называет, или код,
который он исполняет?») стоит **над** вопросами 2 и 3 и разрешает их спор: имя —
своё, код — берётся как есть.

### Правило проверено против таблицы — на всех 51, а не на примерах

Правило и таблица — два места об одном предмете, поэтому связь между ними обязана быть
**замерена**, а не подразумеваться. Порядок применения: **Ограничение → В1 → В2 → В3 →
В4**, первый сработавший даёт класс.

| что сработало | каталогов | какие |
|---|---:|---|
| Ограничение (зависит прод-код `corelib`) | 1 | `listnarrow` |
| **В1** — вход есть дерево исходников | 6 | `gitenv listcursorplan listfiltergate nameformdb pgtest treecorpus` |
| **В2** — перечень | 7 | `api modulemanifest ids platformmodules quota authz tokenpolicy` |
| **В3** — меняется с контрактом доступа | 4 | `credsecret identityposture ownerregister subjectchange` |
| **В4** — остальное | 33 | — |

**Проверено вслепую на 51 каталоге, расхождений правила с таблицей — 0.** Разбивка,
выведенная **правилом**, совпала с разбивкой, прочитанной **из таблицы**:
`corelib` 38 · `kaname` 5 · `kacho` 2 · `оснастка сборки` 6.

Честная граница проверки названа: **В1 и Ограничение машинно проверяемы** (замыкание
двоичного · зависимость прод-кода `corelib`), **В2 и В3 — суждение**. Поэтому это
адъюдикация 51 случая, а не предикат; но она полная, а не выборочная, и её результат
воспроизводится сопоставлением двух разбивок.

**Чего правило НЕ обещает.** Вопросы 1 и 2 машинно проверяемы (замыкание · раздвоение
перечня). Вопрос 3 — суждение: «что заставит измениться» предиката не имеет, и
называть его проверяемым значило бы обещать несуществующий гейт. У каждой строки
таблицы §4 предикат назван, и там, где он есть только у части утверждения, это
сказано буквой **В** (вопрос, не команда).

**Обозначения предикатов в таблице:**

| буква | предикат |
|---|---|
| **З** | замыкание импортов поставляемого двоичного (`go list -deps` над `cmd/`) |
| **И** | прод-импорт **любого** контракта: `git grep -ln 'pkg/api/kacho/' -- 'pkg/<d>/' \| grep -vc '_test\.go'` |
| **И-дост** | прод-импорт **контракта доступа**: то же с `'pkg/api/kacho/cloud/iam/'` |
| **С** | раздвоение перечня (вопрос 2) — исход проверяется чтением содержимого |
| **В** | машинного предиката нет; назван вопрос |

> [!warning] Легенда `И` была ШИРЕ своих значений, и это маскировало находку
> В первой редакции `И` определялся как `pkg/api/kacho/cloud/`, а величины в таблице
> давались по `pkg/api/kacho/cloud/iam/v1`. Под широким чтением `subscription` даёт
> **4**, `operations` — **2**, а не 0, и ровно это расхождение прятало §5.1: общие
> примитивные контракты уезжали в `kacho`, заводя `corelib → kacho`. Определение,
> вдобавок, не покрывало `pkg/api/kacho/iam/` — то есть **и широкое чтение было узким**:
> `pkg/authz/catalogderive/derive.go` привязан к `kacho/iam/authz` и не попадал ни под
> одну из двух форм. Чинилось **определение**, а не значения.
>
> Замер по всем 51: `И` ненулевой у **девяти** каталогов
> (`api` 164 · `subscription` 4 · `listnarrow` 4 · `operations` 2 · `quota` 2 ·
> `authz` 1 · `ownerregister` 1 · `servicehost` 1 · `subjectchange` 1); у остальных
> **42** он равен нулю в обоих чтениях.

### 5.1. `api` — контракт доступа отделяется от контрактов платформы

**Контракт едет туда, где живёт пакет, который его РЕАЛИЗУЕТ.** Это правило, а не
перечень, и оно разрешает все четыре случая одинаково.

| что | куда | файлов | реализует |
|---|---|---:|---|
| `cloud/iam` | `kaname` | 83 | `services/iam` |
| `cloud/operation` · `cloud/subscription` · `cloud/quota` · `iam/authz` | **`corelib`** | 14 | `pkg/operations` · `pkg/subscription` · `pkg/quota` · `pkg/authz` |
| всё остальное (`cloud/vpc compute storage loadbalancer registry geo reference api`) | `kacho` | 167 | `services/*` платформы |

Сумма 83 + 14 + 167 = **264** =
`git ls-files pkg/api/ | wc -l`.

Довод для первой и третьей строк: контракт — имя, которым продукт себя называет.
Стабы генерированные, руками их не правят, поэтому расщепление сводится к разделению
дерева `proto/` и настройки генерации.

> [!important] Вторая строка — ПОПРАВКА: «всё остальное → `kacho`» ломало направление трижды
> Первая редакция отправляла в `kacho` **всё**, кроме контракта доступа. Это захватывало
> три общих примитива, и каждый заводил запрещённое ребро:
>
> | пакет | контракт | направление |
> |---|---|---|
> | `pkg/operations` (2 прод-файла) | `cloud/operation` | `corelib → kacho` |
> | `pkg/subscription` (4 прод-файла) | `cloud/subscription` | `corelib → kacho` |
> | `pkg/quota/quotapb` (1) | `cloud/quota` | `kaname → kacho` |
>
> ```sh
> git grep -ln 'pkg/api/kacho/cloud/' -- 'pkg/subscription/' | grep -vc '_test\.go'   # 4
> git grep -ln 'pkg/api/kacho/cloud/' -- 'pkg/operations/'   | grep -vc '_test\.go'   # 2
> ```
>
> **Документ держал обе позиции сразу**: §4 объявлял у `operations` и `subscription`
> «`И` → 0», а §7.3 насчитывал три пробных ребра — и оба утверждения верны **только**
> если примитивы остаются на стороне `corelib`. То есть собственная арифметика уже
> исходила из поправки, которой в тексте не было. Замер: пробных файлов
> corelib-каталогов, привязанных к контракту, **21**, и лишь **6** из них говорят на

> домену.

> `cloud/`, поэтому мимо него прошли **обе** формы предиката. Нашёлся переписью по
> `pkg/api/kacho/`, то есть после починки определения `И`, а не до неё.

### 5.2. `authz` — карта окон отзыва отделяется от механизма

`pkg/authz` остаётся в `corelib` целиком, **кроме карты `RevocationPolicy.Windows`**.

Замер, из-за которого расщепление именно такое: прод-код читает у политики **только**
`Default` (`pkg/authz/cache.go:162`), а карту из 12 записей не читает **ни одна строка
прод-кода** — её единственный потребитель гейт `internal/repohygiene/revocationwindow_test.go`.

```sh
grep -n 'RevocationPolicy' pkg/authz/*.go | grep -v _test   # Default — одно чтение
git grep -n 'RevocationPolicy.Windows' -- 'services/' 'gateway/'   # пусто
```

Исход: `Default`, `Ceiling` и потолки доставки остаются в `corelib` — это величины
механизма. Карта расходится **по владельцу ручки**: 11 записей платформы → `kacho`,
1 запись службы доступа (`"iam authz.cache-ttl"`) → `kaname`. Каждый модуль объявляет
окна **своих** ручек, и его собственный гейт сверяет их со **своим** деревом. Иначе
получилось бы одно объявление о двух деревьях, которое ни один обход не проверит
целиком.

| `quota/quotaiam` | `kaname` | тяга дельты величин **у владельца прав** — клиентская полоса к службе |
| `quota/quotapb` | `kaname` | перевод строк учёта в контракт; стоит на `iamv1.Limit_Scope` |
| `refusal.go`: перечень шести владельцев учёта со схемами | `kacho` | перечень **сервисов платформы**; раздвоение дало бы два ответа об одной схеме |
| остальное (`projection.go`, `states.go`, `start.go`, `limitsync.go`, `quotaread`, `quotadetail`) | `corelib` | механизм учёта, продукта не знающий |

Ни один из двух отделяемых подпакетов **не имеет потребителя в `corelib`** — проверено
по форме импорта, а не по слову:

```sh
git grep -ln '"github.com/PRO-Robotech/kacho/pkg/quota/quotapb"'  -- '*.go' | grep -v _test  # 6, все services/
git grep -ln '"github.com/PRO-Robotech/kacho/pkg/quota/quotaiam"' -- '*.go' | grep -v _test  # 5, все services/
```

Поэтому переезд не заводит нового **входящего** ребра: обращения идут из `services/*`,
то есть `kacho → kaname`, а это разрешённое направление.

**Но у ребра две стороны, и первая редакция смотрела только на одну.** Вопрос «кто
импортирует `quotapb`» ничего не говорит о том, **что импортирует сам `quotapb`**:
`convert.go` привязан к `cloud/quota` **и** к `cloud/iam`. Под первой редакцией §5.1
(`cloud/quota` → `kacho`) это давало `kaname → kacho` — то есть переезд заводил
**исходящее** ребро. Поправка §5.1 его снимает: `cloud/quota` остаётся в `corelib`,
и обе привязки `quotapb` законны (`kaname → corelib`, `kaname → kaname`).

Урок, ради которого абзац переписан, а не поправлен: **направление проверяется у обеих
сторон**. Предикат «кто меня зовёт» не заменяет предиката «кого зову я».

> [!warning] Здесь первый предикат солгал, и назвать это стоит дороже, чем починить
> Поиск `git grep -l 'quota/quotapb'` давал среди потребителей `pkg/operations/operationspb`
> и `pkg/quota/quotaread` — то есть **два потребителя внутри `corelib`**, и по ним
> выходило, что расщепление заводит третье ребро цикла. Оба вхождения оказались
> **комментариями**, объясняющими сам приём. Предикат судил по слову, а не по тому,
> что код делает (`testing.md` §«Гейт на класс», п. 4), и ошибся в **опасную** сторону:
> он назвал бы работу невозможной. Форма с кавычками различает импорт и прозу
> by construction; ею и снят замер выше.

Перечень шести владельцев (`RefusalOwners()`) читают гейты и **инструмент сборки** —
службы платформы и служба доступа его не читают:

```sh
git grep -n 'RefusalOwners' -- '*.go' | grep -v '^pkg/quota/refusal.go' | grep -vc '^internal/'   # 3
#   pkg/quota/refusalbody_test.go:83            — проба самого пакета
#   tools/quota-refusal-migration/main.go:32    — ЖИВОЙ вызов инструмента
#   tools/quota-refusal-migration/main.go:58    — комментарий
```

> [!warning] Здесь стояло «прод-потребителя нет · предикат → 0» — число было неверным
> Это **второй экземпляр того же класса**, который я поймал во врезке выше: предикат
> отсекал `internal/`, но не `tools/` и не пробу самого пакета, и я прочитал его вывод
> как «ноль», не перепроверив. Вывод раздела при этом **выживает**: ни одна служба
> обоих продуктов перечень не читает, поэтому переезд в `kacho` ничего у `corelib` не
> отнимает. Неверным было число, а не решение — и именно поэтому его надо было
> перемерить, а не дописать «ноль» ещё раз.

Инструмент `tools/quota-refusal-migration` — оснастка сборки по вопросу 1 (вход —
дерево миграций), и он переезжает вместе с перечнем.

## 6. `pkg/ids` — словарь приставок НЕ расщепляется

**Решение: словарь один, он целиком едет в `corelib`, и ни одна приставка не меняет
значения.**

### 6.1. Почему не расщепляется

Приставка — **внешне-адресуемая координата**: она стоит в публичном URL, в пути
образа, в cross-service ссылке, в цели гранта (запрет #15). Она присваивается при
создании и неизменяема на всю жизнь ресурса; операции смены не существует.

Словарь несёт **37** приставок обоих продуктов:

```
go run: len(ids.KnownPrefixes()) → 37   ·   len(ids.KnownHyphenPrefixes()) → 34
```

Из них службе доступа принадлежат **11** (`acc prj usr sva grp rol acb iop uoc cnd soc`),
платформе — **26** (включая наследственную `e9b`).

Расщепление отвергнуто по **вопросу 2** правила классификации. Раздвоив словарь, мы
получаем не два взгляда на одно имя, а **две независимые выдачи одной координаты**:
ничто не помешает платформе однажды выдать `acc` своему ресурсу, потому что в её
половине словаря этой записи не будет. Столкновение обнаружится не при сборке и не
при пробе, а у арендатора — на разборе чужого идентификатора, и оно **необратимо**:
починка означала бы смену приставки, то есть слом URL, грантов и ссылок.

Смысл этого словаря в том и состоит, чтобы быть **единственным**. Расщепив его, мы
уничтожаем предмет, а не делим его.

### 6.2. Что при этом НЕ меняется — названо поимённо

| не меняется | почему это важно |
|---|---|
| **значение ни одной из 37 приставок** | иначе ломается всякая уже выданная координата |
| **идентификатор ни одного существующего ресурса** | переезд словаря — перемещение файла, а не миграция данных |
| **форма идентификатора** (3 символа + крокфорд; дефисная форма) | приёмная сторона маршрутизатора продолжает принимать обе |
| **классификация чужой приставки** | словарь общий, поэтому оба продукта видят полный список |
| **право продукта завести НОВУЮ приставку** | заводится записью в общий словарь `corelib` |

### 6.3. Цена решения, названная честно

`corelib` знает **имена ресурсов обоих продуктов**. Это противоречит букве «фундамент
не привязан ни к одному продукту» и принято сознательно: альтернатива — не независимость
фундамента, а **возможность коллизии координат**, которую нечем ни обнаружить, ни
исправить. Из двух зол выбрано наблюдаемое.

**Тот же довод принят и для второго словаря** — `pkg/platformmodules` (§7.1). Решение
об обоих одно: продукт не вправе решать одну задачу двумя разными способами, и два
словаря с разной судьбой были бы противоречием продукта самому себе. Цена
(«`corelib` знает словари обоих продуктов») платится один раз, а не дважды.

Отсюда граница, за которую это решение **не распространяется**: в `corelib` едет
**реестр занятых строк**, а не семантика ресурсов. Комментарий, объясняющий, какому
ресурсу приставка принадлежит, — прозаический и правится в любую сторону; поведение
от него не зависит.

## 7. Рёбра будущего цикла — их ПЯТЬ прод-файлов, и это ОДИН класс

Направления, запрещённые целевой раскладкой: `corelib → kaname`, `corelib → kacho`,
`kaname → kacho`.

**Замер по всему дереву, а не по `pkg/`:**

| | прод | проб |
|---|---:|---:|
| привязок к контракту из каталогов `pkg/` | 17 | 30 |
| из них **запрещённого направления** | **5** | **11** |
| файлов, их несущих | **5** | **6** |
| рёбер `pkg → pkg` запрещённого направления | **0** | 0 (после §4) |

> [!important] Здесь стояло «прод-рёбер два» — набор был НЕПОЛОН, и полнота его не проверялась
> Первая редакция называла два ребра — `proxytuple → platformmodules` и
> `servicehost → контракт доступа` — и не спрашивала, есть ли третье. Полный обход по
> **обеим** осям (привязка к контракту · импорт между каталогами `pkg/`) даёт **5**

>
> Одно из двух прежних рёбер при этом **исчезло** — не почини́лось, а перестало быть

### 7.1. Словарь модулей платформы — ребро РАСТВОРЕНО, а не заперто портом

```
pkg/authz/proxytuple/policy.go:38   import  pkg/platformmodules
                            :342   platformmodules.ObjectDomainOfService(callerDomain)
                            :396   platformmodules.CatalogModuleOfService(callerDomain)
```

**Решение: `pkg/platformmodules` уезжает в `corelib`** — тем же приёмом и с той же
ценой, что уже применены к `pkg/ids` (§6). После переклассификации обе стороны ребра
лежат в `corelib`, и запрещённого направления не остаётся **by construction**.

**Довод — тот же, что у `ids`, и это главное.** `platformmodules` — **словарь**.
Раздвоение даёт не два взгляда на один предмет, а **две независимые выдачи одного
имени**, и столкновение всплывает у арендатора, а не при сборке. Продукт не вправе
решать одну задачу двумя разными способами: два словаря с разной судьбой — это
противоречие продукта самому себе. Цена — `corelib` знает словари обоих продуктов —
названа в §6.3 и принята один раз на оба словаря, а не дважды по отдельности.

**Отвергнутые исходы, с причиной у каждого:**

| исход | почему отвергнут |
|---|---|
| **порт**: `proxytuple` объявляет интерфейс, реализацию подаёт владелец | **недостижим**: единственный прод-вызов `ValidateTuple` — `services/iam/…/internal_iam/handler.go:185`, то есть в `kaname`. Подать реализацию обязан тот, кто правило исполняет, значит `kaname` импортировал бы `platformmodules`. При `platformmodules ∈ kacho` это `kaname → kacho` — цикл **переставлен**, а не снят |
| порождать соответствие «служба ↔ модуль» в таблицу `kaname` манифестом | заводит **второго издателя** одного словаря — ровно то, против чего словарь и объявлен единственным |
| спрашивать соответствие на проводе | вопрос о **статическом** словаре становится сетевым вызовом, со сроком, отказом и посадкой |

**Порт при этом НЕ вводится вовсе.** `policy.go:271` уже несёт `TypeOwner` для другого
предмета («чей это тип»), и он остаётся; второй порт ради вопроса, на который отвечает
пакет из того же модуля, был бы мёртвым объявлением (LEAN, запрет #11).

Замер, объясняющий, почему порт казался годным: `platformmodules` в прод-коде
импортируют **три** файла на всё дерево — два гейта `internal/repohygiene`
(не поставляются) и само ребро. Ни одна служба платформы `ValidateTuple` не зовёт и
`platformmodules` не импортирует, поэтому «реализацию подаёт `kacho`» звучало
правдоподобно и не имело исполнителя.

### 7.2. `corelib` говорит на контракте доступа напрямую — 5 прод-файлов, два пакета

| файл | что берёт | пакет |

### 7.4. Предикат направления — по ВСЕМУ дереву источника, не по `pkg/`

**Предикат первой редакции был слеп к тому исходу, ради которого заведён.**
`git grep -c 'kacho/pkg/platformmodules' -- 'pkg/'` сужен до `pkg/` и даёт **0** в двух
разных мирах: когда ребро снято — и когда оно **переехало** в `services/iam`. Проверка,
не различающая «сделано» и «перенесено», не является проверкой.

Годная форма сверяет **направление** и обходит **всё дерево модуля-источника**:

```sh
# перечень каталогов класса — выводится из таблицы §4, а не выписывается
corelib_dirs() { awk -F'|' '/^\| `/ && $3 ~ /corelib/ {gsub(/[ `]/,"",$2); print "pkg/"$2"/"}' "$DOC"; }

# ребро corelib -> kaname: контракт доступа в любом файле любого corelib-каталога
git grep -ln 'pkg/api/kacho/cloud/iam/' -- $(corelib_dirs) | grep -v '_test\.go'

# ребро kaname -> kacho: словарь модулей в ЛЮБОМ файле дерева kaname,
# включая services/iam — иначе переезд ребра остаётся невидимым
git grep -ln '"github.com/PRO-Robotech/kacho/pkg/platformmodules"' \
  -- 'services/iam/' $(kaname_dirs) | grep -v '_test\.go'
```

Три свойства, без которых предикат не годен, и каждое проверяется инъекцией:

1. **обход по дереву источника целиком** — иначе переезд ребра читается как его снятие;
2. **перечень каталогов выводится**, а не выписывается — выписанный разойдётся с §4 молча;
3. **пустой обход — отказ**: ноль осмотренных каталогов обязан отличаться от нуля находок.

### 9.4. Форма предиката направления — и доказательство, что он способен упасть

Предикат обходит **дерево модуля-источника целиком**, а не каталог `pkg/`. Разница не
стилистическая: узкая форма не различает «ребро снято» и «ребро переехало».

Инъекция в три мира, синтетическое дерево, `git grep --no-index`:

| мир | узкий (`-- 'pkg/'`) | широкий (`-- 'pkg/' 'services/iam/'`) |
|---|---:|---:|
| **A** — ребро на месте, в `pkg/` | 1 | 1 |
| **B** — ребро **переехало** в `services/iam` | **0** | **1** |
| **C** — ребро снято совсем | 0 | 0 |

Узкая форма отвечает **одинаково** на B и C — то есть на «сделано» и на «перенесено».
Широкая различает их и при этом **молчит на C**, значит не является вакуумно-красной.
Это и есть требование к предикату каждого ребра: он обязан падать на исходе «ребро
переехало в другой модуль».
