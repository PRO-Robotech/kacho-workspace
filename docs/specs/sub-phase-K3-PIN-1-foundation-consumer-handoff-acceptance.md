# Sub-phase K3-PIN-1 — перевод потребителей фундамента в Kaname

> Статус: DRAFT. Действующий вердикт задаёт независимый `acceptance-reviewer`
> внешним событием на SHA-256 документа; шапка после ревью не меняется.
> Дата: 2026-09-09.
> Задачи: [kacho#2416](https://github.com/PRO-Robotech/kacho/issues/2416),
> [kacho#2398](https://github.com/PRO-Robotech/kacho/issues/2398).

## Обзор и граница

Kaname обновляет пин фундамента и продолжает исполнять проверки помеченных ответов
операций и читателей материализуемых отношений. Проверка читателей исполняется и
в самостоятельной поставке модуля, где исходников платформы нет.

Это дополнение к [K3-1](sub-phase-K3-1-foundation-boundary-acceptance.md): оно
устанавливает специальные сценарии двух задач, сохраняя исторический документ
неизменным. Одна стадия охватывает атомарный перевод зависимости, потребителей
аннотаций, исключения границы и источников проверки читателей. Полный разрез
`corelib`/Kaname, смена модульных путей будущего фундамента и публикация трёх
отдельных продуктов принадлежат K3-1 и последующим стадиям. Runtime API, модель
прав, перечень материализуемых отношений и поведение подметальщика эта стадия
не меняет.

Нормативные основания: K3-1 §«Рёбра ПРОБ — шесть файлов, одиннадцать привязок»,
K3-16; правила воркспейса
`.claude/rules/polyrepo.md` §«Правило зависимостей при полирепо-топологии» и
`.claude/rules/change-graph.md` §«Вердикт привязан к ОТПЕЧАТКУ, а не к документу».
Конвенции API, целостности данных и безопасности остаются в соответствующих
модулях правил; новых RPC, полей и миграций здесь нет.

## Сценарий 01: зависимость и её потребители переводятся одной поставкой

**ID:** K3-PIN-01.

**Given** B и опубликованная целевая версия из раздела «Опоры сценариев».
**And** C содержит согласованные `services/iam/go.mod` и `go.sum`, оба новых
импорта пробы дескрипторов и снятие точной записи
`services/iam/cmd/kaname → pkg/api/kacho/cloud/api` с маркером `З3` вместе с
комментарием, объясняющим временную жизнь именно этого ребра.
**When** модуль Kaname разрешают и собирают при `GOWORK=off`, без локального
`replace`, из монорепо и из самостоятельной отслеживаемой поставки модуля,
и запускают `go build ./...`, `go vet ./...` из корня Kaname.
**Then** команды завершаются успешно и разрешённый модуль совпадает с целевой
версией и полным SHA; исходные `go.mod`/`go.sum` не требуют дозаписи.
**And** в отслеживаемом источнике `services/iam` отсутствует прежний импорт
`pkg/api/kacho/cloud/api`, включая объяснявший его текст; существуют обращения
к своей `iamv1.E_SecretBearing` и нейтральным `E_Operation`/`Operation`.
**And** `TestNoModuleEdgeRunsAgainstTheTargetLayout` исполняется на C в дереве
платформы и не требует новой или расширенной записи вместо снятой.

## Сценарий 03: обе аннотации продолжают производить вход держателя

**ID:** K3-PIN-03.

**Given** непустые наборы помеченных полей и ответов операций, полученные из
реальных дескрипторов на B, и непустое их пересечение.
**When** тот же дескрипторный обход и реальный держатель выполняют на C.
**Then** отсортированные множества полных имён полей, типов ответов и их
пересечения совпадают с B; каждый элемент пересечения проверен против
действительного `secretSweepTargets`; держатель проходит.
**And** отчёт различает число помеченных сообщений, ответов операций и реально
проверенных полей; одна успешная компиляция не заменяет исполнение.

**Given** законный вход C с помеченным полем ответа операции, названным в
перечне подметальщика.
**When** в изолированном близнеце убирают только запись этого поля из входа
перечня, сохраняя реальные дескрипторы обоих производителей.
**Then** тот же держатель называет точное полное имя сообщения и поля;
возвращённая запись делает близнеца законным.
**And** отдельный законный помеченный синхронный ответ, не названный ответом
операции, не требует записи в перечне: граница пересечения сохраняется.

## Сценарий 04: потеря одного производителя дескрипторов видна

**ID:** K3-PIN-04.

**Given** законный C из K3-PIN-03 с непустым пересечением.
**When** в отдельных изолированных близнецах меняют ровно один вход: первый
производитель выдаёт пустое множество пометок; либо второй выдаёт пустое
множество ответов; либо множество ответов остаётся непустым, но перестаёт
пересекаться с неизменными пометками.
**Then** каждый запуск полного держателя завершается отказом с названным
пустым входом или пересечением; ноль находок не считается успехом.
**And** законный близнец с исходным входом проходит через тот же путь.
Инъекция должна дойти до вызывающего держателя: проверка одной чистой функции,
которая лишь возвращает `checked=0`, этого сценария не закрывает.

## Сценарий 05: перепись отношений сохраняет состав при переводе источника

**ID:** K3-PIN-05.

**Given** B и C с одинаковыми канонической моделью, каталогом прав,
материализуемыми отношениями и прод-кодом сервисов.
**When** полную `TestEveryMaterializedVerbRelationHasAReader` выполняют на B
со старым пином, а затем на C с целевым пином.
**Then** множество написанных пар `(тип, отношение)` сохраняется;
для множества найденных пар без читателя предъявлена точная дельта, а не
только сравнение мощностей. При одинаковых действительных свидетелях дельта
пуста. Содержимое действующих `knownUnread` не подгоняется под результат.
**And** у C чужая полоса читателей поступает из `moduleselfgating.Relations`,
своя — из отслеживаемого состава IAM. Каталог и модель сохраняют свои
самостоятельные полосы. Свидетельство называет происхождение каждой полосы,
пин, SHA, состав прочитанных файлов и фактические счётчики.
**And** полнота собственного обхода измеряется отдельно от числа объявленных
чужих модулей: уменьшение количества прочитанных Go-файлов не означает потери
пар и не маскируется старым числом платформенного обхода.

Исключения источников записи проверяются по их действительной роли, а не
копированием старых имён. В частности, генерируемая `typeVerbRelations` не
является читателем своего содержимого. Разница свидетелей после снятия такого
самозачёта должна быть названа; если она меняет итоговый набор пар без читателя,
кандидат требует отдельной адъюдикации дельты независимым ревью до GREEN.
Если обнаружен ранее замаскированный случай, требующий изменения договора
о допустимых находках, он возвращается на разбор приёмки.
Сама эта стадия не разрешает скрыть новую находку в `knownUnread`.

Числа «109 пар, 3 без читателя» происходят из исторического текста #2398.
Они не являются новым замером B. Исполнитель снимает B реальным производителем
этой пробы и сохраняет полный набор вместе с выводом; на C обязан сохранить
написанный набор и объяснить дельту читателей по правилу выше.
Если B отличается от исторического числа, расхождение
получает объяснение по элементам до verdict, а не новое исключение.
Наблюдение полного набора пока **ожидает держателя сравнения**: текущая проба
на B печатает агрегаты; машинное сохранение состава для B/C ещё не предъявлено.

## Сценарий 06: самостоятельная поставка исполняет весь маршрут

**ID:** K3-PIN-06.

**Given** законная самостоятельная отслеживаемая поставка ровно `services/iam`
из C со своим `go.mod`/`go.sum`, поставляемыми каталогом и моделью.
**And** дерева платформы, соседних `services/`, `gateway/`, `proto/`, внешнего
`go.work` и локальных подмен зависимостей в доступном окружении пробы нет.
**When** из корня модуля при `GOWORK=off` запускают
`go test ./internal/authzmap -run '^TestEveryMaterializedVerbRelationHasAReader$' -count=1 -v`.
**Then** именованная проба действительно исполняется, проходит и выдаёт те же
написанные пары и пары без читателя, что C в K3-PIN-05; `SKIP` недопустим.
**And** прочитанные каталог, модель и собственные Go-файлы находятся внутри
этой поставки; чужие Go-файлы не требуются, их заменяет объявление из пина.
**And** пустой выбор тестов, ненайденный бинарный файл, ошибка получения
зависимости или недействительная самостоятельная фикстура — «не выполнилось»,
а не доказанный дефект читателей и не успех.

Этот сценарий относится к названной пробе. Он не превращает разрешённое
отсутствие второго операнда у отдельной проверки тождества копий модели в
успех и не требует копировать платформенное дерево ради такого операнда.

## Сценарий 07: чужое объявление остаётся проверяемым с обеих сторон

**ID:** K3-PIN-07.

**Given** законная пара `(registry, v_list)`: объявление пина и соответствующий
читатель прод-кода платформы согласованы; полный платформенный гейт проходит.
**When** в изолированном близнеце убирают только наблюдаемого читателя этой
пары из прод-кода, оставляя объявление.
**Then** `TestModuleSelfGatingMatchesTheProdCodeOfEachModule` отвергает
объявление без читателя и называет `(registry, v_list)`; исходный близнец проходит.

**Given** законный вход C, в котором `registry_repository#v_list` читается
только полосой владельца, что подтверждено переписью его свидетелей.
**When** в отдельном близнеце из входа объявления удаляют только
`registry → v_list`, сохраняя модель, каталог и написанные пары.
**Then** держатель IAM называет `registry_repository#v_list` новой парой без
читателя; с исходным объявлением он проходит.
**And** неисправное объявление не выдают за факт о чужом прод-коде: его
истинность проверяется платформой, а IAM доказывает, что реально его читает.
Уже имеющиеся `TestSelfGatingInjection_*` проверяют предикат на входных
множествах; опыт через реальный производитель прод-кода и полный маршрут
потребителя **ожидает предъявления**, их имена не означают готового покрытия.

## Сценарий 08: свои читатели происходят из собственного отслеживаемого состава

**ID:** K3-PIN-08.

**Given** явно синтетический мир **W**, построенный из источников B по
нижеследующему правилу, и целевая пара `iam_role#v_get`.
**And** полный держатель C читает W через настоящий индексный обход,
полные загрузчики каталога/модели и объявление целевого пина; набор написанных
пар по-прежнему дают `authzmap.Catalog`, `ObjectType`, `VerbRelationsOfType`.
**When** выполняют `positive` и отдельные близнецы из таблицы.
**Then** `positive` проходит; каждый отрицательный близнец выдаёт названный
исход, сохраняя остальных производителей и действующие `knownUnread`.

**Определение W.** В новом временном git-репозитории отслеживаются собственный
`go.mod` и следующие файлы; пути относительно корня IAM:

| Вход W | Детерминированный производитель |
|---|---|
| `internal/apps/kaname/seed/embedded/permission_catalog.json` | Побайтовый файл B по этому же пути |
| `internal/authzmodel/fga_model.fga` | Побайтовый поставляемый файл B по этому же пути |
| Три источника записи: `internal/authzmap/fga_types.go`, `internal/authzmap/tables_gen.go`, `internal/apps/kaname/api/access_binding/reconcile/tuples.go` | Побайтовые файлы B; литералы записи сохраняются и исключаются именно как писатели |
| `internal/authzmap/catalog_resource_spelling.go` | Побайтовый файл B: непустой нетестовый корпус остаётся и после исключения читателя; в нём нет литерала `v_get` |
| `internal/authzguard/read_authz.go` | Директива `package authzguard` и точное объявление функции `AllowsVGet` из одноимённого файла B, без прилегающих комментариев и остальных объявлений; его единственный строковый литерал отношения — `v_get` |

Другие Go-файлы в W отсутствуют. Источник фрагмента определяется именем
функции в разобранном Go-файле, а не номером строки. Перед опытом фиксируются
SHA исходных файлов, состав индекса, полученный фрагмент и найденные свидетели
по всему W. Каталог и модель B не читают `iam_role#v_get`; это проверяется
производителями полного держателя, не объявляется константой фикстуры.
У фрагмента один служебный свидетель `v_get`, у сохранённых писателей есть
литералы этого отношения; за пределами них других свидетелей в W нет.

Это вход обхода исходников, не сборка уменьшенной службы: используется полный
скомпилированный держатель C с корнем W. Результат нельзя получить подменой
готовой карты `serviceReads` или второй копией проверяющего предиката.
Опыт доказывает прежнюю разрешающую способность до сервиса-владельца;
он не утверждает, что `AllowsVGet` в живом продукте вызывается для `iam_role`.

Посев использует настоящий `git init` и явный `git add` перечисленных путей;
существующий образец такого строителя — `newRepo` в
`pkg/treecorpus/treecorpus_test.go` (настоящий Git, без дублёра индекса).
Специализированный строитель `seedK3PIN08World` запланирован в
`services/iam/internal/authzmap/materialized_relation_handoff_test.go`;
он ещё не написан, но его вход и состав определены здесь полностью.

| Case | Единственное отличие от `positive` | Исход полного держателя |
|---|---|---|
| `positive` | Нет: все названные файлы отслеживаются | Успех; `iam_role#v_get` имеет одного допустимого служебного свидетеля |
| `reader_literal_removed` | В извлечённой `AllowsVGet` один литерал `v_get` заменён на `v_pin_unused`; имя не принадлежит написанным парам | Новая находка `iam_role#v_get`; индекс, каталог, модель и писатели прежние |
| `reader_untracked` | Только запись `internal/authzguard/read_authz.go` убрана из индекса; файл и его байты остаются на диске | Та же новая находка; неотслеживаемый файл не входит в объём осмотренного |
| `reader_test_only` | Тот же отслеживаемый файл с теми же байтами переименован в `internal/authzguard/read_authz_test.go` | Та же новая находка; тестовый файл не даёт прод-читателя |
| `emission_file_missing` | Только `internal/authzmap/tables_gen.go` отсутствует на диске при сохранённом индексе | Отказ по отсутствующему источнику записи с его координатой, не успех обхода |

Живое дерево B несёт несколько свидетелей `v_get` в разных IAM-файлах;
удаление одного произвольного файла в B не заменяет отрицательный опыт W.

## Сценарий 09: отсутствие данных отличается от отсутствия читателя

**ID:** K3-PIN-09.

**Given** законная самостоятельная поставка K3-PIN-06.
**When** в каждом отдельном близнеце меняют ровно один вход из таблицы.
**Then** полный держатель выдаёт указанный исход и называет источник;
возврат исходного входа восстанавливает законный результат.

| Case | Единственное изменение | Наблюдаемый исход |
|---|---|---|
| `own_corpus_empty` | Собственный отслеживаемый нетестовый Go-корпус пуст | Ненулевое завершение: осмотрено ноль файлов, предпосылка отсутствует; вердикта о читателях нет |
| `own_index_unreadable` | Индекс собственного дерева не удаётся прочитать | Ненулевое завершение с причиной недоступности; неизвестное не заменяется пустым составом |
| `catalog_missing` | Свой каталог отсутствует | Ненулевое завершение с путём и причиной отсутствия, без `SKIP` и соседней копии |
| `catalog_empty` | Свой каталог содержит ноль байт | Ненулевое завершение с причиной пустого входа, без успешной переписи |
| `catalog_invalid_json` | Свой каталог заменён на неразбираемый JSON | Ненулевое завершение с ошибкой разбора и координатой входа |
| `model_missing` | Поставляемая модель отсутствует | Ненулевое завершение с путём и причиной отсутствия, без `SKIP` и соседней копии |
| `model_empty` | Поставляемая модель содержит ноль байт | Ненулевое завершение с причиной пустого входа, без успешной переписи |
| `model_invalid` | Поставляемая модель не разбирается как модель | Ненулевое завершение с ошибкой разбора, без переписи по частичному результату |
| `foreign_declarations_empty` | Объявление чужой полосы целиком пусто | Ненулевое завершение: источник полосы отсутствует, «ноль находок» не выдаётся за согласие |
| `declared_module_unknown` | В `Modules` есть имя, для которого `Relations` возвращает `ok=false` | Ненулевое завершение с именем: объявленный источник противоречив |
| `written_type_owner_unknown` | Написанный тип не удаётся отнести к владельцу | Ненулевое завершение с типом: источник владельца неизвестен |

Законный case `positive` содержит исходные входы полной пробы и проходит;
каждый отрицательный case начинается заново с него. Полный case ID —
`K3-PIN-09/<Case>`, а не номер строки таблицы.

`Relations(имя)` с `ok=false` само по себе не доказывает ошибку: существующий
контракт также допускает, что про модуль без своих читающих литералов ничего
не объявлено. Для известного владельца вне `Modules` эта полоса не даёт
читателей; каталог и модель всё равно проверяются. Положительный близнец
с читателем в каталоге проходит; удаление только этого единственного читателя
даёт конкретную пару без читателя. IAM в чужое объявление не добавляется.
Эти случаи называются соответственно `known_owner_without_declaration` и
`known_owner_last_reader_removed`: они используют один и тот же вход,
различающийся единственной записью читающего каталога.

## DoD стадии и трассировка

Стадия завершена после независимого одобрения точного документа, экспозиции
классов, одобренного замысла, исполняемых однофактных опытов и проверки
фактического кандидата. Держатели сохраняют ID сценариев в свидетельствах.

Ниже **P** означает запланированный, ещё не созданный держатель; **E** —
существующий на B. Координата P задаёт будущий маршрут, а не свидетельствует
о его готовности. Для краткости пути именованы один раз:

- **D (P):** `scripts/kaname-foundation-handoff/run.py`, драйвер подготовки
  двух посадок, захвата процессов и сравнения B/C.
- **F (P):** `internal/repohygiene/foundation_pin_handoff_test.go`.
- **S (P):** `services/iam/cmd/kaname/secret_bearing_handoff_test.go`.
- **R (P):** `services/iam/internal/authzmap/materialized_relation_handoff_test.go`.
- **M (P):** `internal/repohygiene/moduleselfgating_handoff_test.go`.

Команда **D(ID)** из корня продукта означает
`python3 scripts/kaname-foundation-handoff/run.py --baseline "$K3_PIN_BASELINE" --candidate "$K3_PIN_CANDIDATE" --case ID`.
Переменные содержат полные SHA B и C. Драйвер требует обе координаты, сохраняет
реальные дочерние команды, их cwd, SHA входов, список выбранных тестов и исходы;
нулевой выбор не проходит. Это планируемая команда, до создания D она не
исполняется. Запуск пробы внутри контейнера или нового runtime-стенда не нужен.

Команда **IAM(pkg, test)** означает запуск из корня модуля Kaname:
`GOWORK=off go test ./pkg -run '^test$' -count=1 -v`; **ROOT(test)** — из
корня продукта: `GOWORK=off go test ./internal/repohygiene -run '^test$' -count=1 -v`.
В таблице `pkg` и `test` подставляются целиком указанными значениями. Для
отдельного подслучая применяется Go `-run '^TestName$/^case$'`; все case names

Ожидаемые дефекты инъекций, неисполненные пробы и успешные проверки фиксируются
раздельно. Сломанная сборка оснастки не открывает переход к реализации как RED.
До завершения стадии каждый запланированный выше держатель должен быть
реализован по своему именованному маршруту и предъявить захваченный исход;
данный DRAFT его существования не утверждает.
Изменение определения читателя или состава реальных отношений
возвращается в приёмку вместо правки исключений ради зелёного прогона.

Новых proto/regen, миграций, Newman-сценариев, UI и выкладки эта стадия не
порождает: наблюдаемый предмет — сборка и проверки источника, runtime API
не меняется. Соответствующие проверки всего релиза остаются в его собственном
DoD. После посадки инженерный trail связывает два issue, применённый SHA,
действительные свидетельства и снятое исключение; текущий документ не объявляет
ни посадку, ни закрытие задач.
