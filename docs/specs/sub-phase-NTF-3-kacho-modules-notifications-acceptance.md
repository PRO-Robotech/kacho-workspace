## §0 Обзор

### 0.1 Что реализуется

Модули kacho получают способ сообщать арендатору о событиях его ресурсов письмом — через
единственный почтовый шлюз `services/notify`, заведённый в NTF-1. Под-фаза делает четыре вещи:

1. **Переписывает все модули kacho** и по каждому принимает решение: подключается (с закрытым
   перечнем нотификаций) или не подключается (с причиной и предикатом пересмотра). Заглушек нет:
   модуль, не имеющий события, о котором стоит писать, не получает ни ленты, ни шаблонов.
2. **Заводит справочник подтверждённых адресов**: служба доступа по запросу `notify` отдаёт адрес
   субъекта, если адрес подтверждён и субъект сейчас имеет право читать ресурс, о котором письмо.
   Модуль kacho адреса не знает и не хранит — он называет субъекта.
3. **Подключает единственный модуль, у которого есть такое событие, — `storage`**: переход тома,
   снимка или образа из `CREATING` в `ERROR` по решению сверщика (без запроса арендатора и после
   того, как его операция уже завершилась) ставит письмо инициатору намерения, породившего строку.
4. **Вводит вторую локаль `en`** для всех шаблонов всех владельцев и собирает шаблоны модулей в
   `notify` шагом `bundle` без второй копии их содержимого в дереве.

### 0.2 Почему это не MVP

Каждый подключённый модуль подключается полностью: запись в транзакции перехода, право в модели,
отзыв, лимиты, наблюдаемость, обе локали, пробы. Модуль, которому писать не о чем, не подключается
вовсе — это решение с причиной (§3), а не «подключим позже». Ослаблений против NTF-1 нет.

### 1.6 Сигнал о новой строке ленты — предмет NTF-1, и его посылка опровергнута

Разведка диспетчера измерила: сервер подписки фундамента требует субъекта арендатора
(`corelib/subscription/server.go:230-234`), вид события обязан быть типом модели прав
(`journal.go:493-506`), метод несёт `permission` и `required_acr_min "1"`
(`subscription_service.proto:113-117`). Служба без субъекта арендатора поток не откроет, а вид
«нотификация» без типа модели сервер не примет. **Форму сигнала решает NTF-1**; этот документ её
не выбирает и утверждает только наблюдаемое свойство (сценарии NTF3-18, NTF3-19).

Задержка сигнала у storage измерена: сервер подписки ждёт уведомления с перепросом `IdlePoll`,
у storage — `KACHO_STORAGE_SUBSCRIPTION_IDLE_POLL`, `default:"2s"`
(`services/storage/internal/config/config.go:261` @`1d42a6728bf`). Окно ожидания кортежа
владения (`GrantSettlingWindow = 10s`, `corelib/subscription/grant.go:88`) наступает, только если
кортежа ещё нет; в G0 кортеж `reader` учётки `notify` на ленте storage посеян до открытия потока,
поэтому окно на путь сигнала не ложится (тот же довод — NTF-1 §1.4). Отсюда числа NTF3-18/19.

### 1.8 Какие переходы в `ERROR` сверщик storage производит — перепись по ветвям решения

Проход сверщика берёт **только** строки из рабочего списка `Drifted`: `WHERE r.state <> r.observed_state`
(`reconciler/store.go:127-135`, вызов — `loop.go:162`). Поэтому ветвь решения достижима, только
если у строки есть производитель пары `state/observed_state`, **различающихся**. Каждое Given о
сверщике в этом документе называет эту пару и её производителя (правило редакции 3, §14а).

Действие выбирает чистая функция `Decide` (`reconciler/decide.go:102`) по намерению строки и
наблюдению бэкенда. Намерение `Drifted` выводит из хранимого `state`: `Desired = DeriveStatus(state, false)`
(`store.go:170`), то есть `READY` приходит в `Decide` как выведенное `AVAILABLE`, и ветвь
«живой ресурс» — это `case VolumeStatusAvailable, VolumeStatusInUse` (`decide.go:135`). Снимок и
образ идут той же функцией; изменения размера у них нет (`snapshot.proto:21-30`, `image.proto:35-44`).

## §2 Решения — ратифицировать явно, ревьюер проверяет каждое

Требования владельца (дословно, 2026-09-29/30) обозначены ТВ1–ТВ4:
ТВ1 «единая точка у кого есть креды от почты»; ТВ2 «простой формат добавления шаблонов»;
ТВ3 «права доступа сервисов к их шаблонам (не должно быть возможности где сервис А может отправлять
нотификации от сервиса Б)»; ТВ4 «шаблоны … htmml + css и набор атрибутов». Плюс: «максимальная
безопасность», «максимальная простота», «общий макет + блоки», «вынести в корлиб»,
«нотификатор должен подписываться на события нотификации каждого модуля», «прода нет».

### Перенесённые решения диспетчера (приняты, не переоткрываются; здесь — их следствие для модулей)

**Р1 (дисп. 1). Креды почты — только у `notify`; модуль kacho ни SMTP, ни адреса не знает.**
Основание: ТВ1. Следствие для NTF-3: подключение модуля не добавляет ни секрета, ни исходящего
почтового соединения; держится гейтом NTF-1 «`net/smtp` ровно в одном пакете kacho»; NTF3-36.

**Р2 (дисп. 2). Модуль ставит намерение в свою ленту; `notify` реагирует на сигнал и забирает
порцию вызовом «взять порцию / подтвердить».** Основание: «нотификатор должен подписываться на
события … каждого модуля». Форма сигнала — NTF-1 (§1.6). NTF-3 утверждает: реакция без ожидания
периода опроса, а при потере сигнала — доставка опросом.

**Р3 (дисп. 3). Чей шаблон — определяется тем, чью ленту читает `notify`; права — отношение в
модели службы доступа, одна строка манифеста; решение «можно / права ещё нет / отозвано» — на
каждое письмо.** Основание: ТВ3 и «шлюз проверяет доступы у канаме». Поля «чей шаблон» в строке
ленты нет. Для модулей: строка `notifications:` в `services/<svc>/manifest.yaml`.

**Р4 (дисп. 4). Шаблон — каталог `<owner>/notifications/<name>/{notification.yaml, body.<locale>.yaml}`,
тело — только блоки, макет HTML с inline CSS — в `notify`; попадает в `notify` при сборке, не
регистрацией.** Основание: ТВ2, ТВ4, «общий макет + блоки». Для модулей kacho дом —
`services/<svc>/notifications/`.

**Р5 (дисп. 5). Запись в ленту, счётчик лимита, валидатор и генератор — в corelib
(`notify/feed`, `notify/spec`, `cmd/notifygen`).** Основание: «вынести в корлиб … что бы не
дублировать код». Модуль kacho не пишет своего кода ленты: `SendX(ctx, tx, XAttrs)` генерируется.

**Р6 (дисп. 6). Адресат модуля kacho — субъект; адрес — из справочника подтверждённых адресов,
который служба доступа отдаёт `notify` (ребро `notify→kaname`).** Основание: «максимальная
безопасность» — адрес не размножается по базам модулей. Раскрыто в Р10–Р11.

**Р7 (дисп. 7). Точный лимит — в базе источника при постановке; приблизительный тормоз — в
`notify`.** Для модулей раскрыто в Р14.

**Р8 (дисп. 9). Один отправитель на установку; белая метка вне предмета.**

**Р9-а (дисп. 10). Прода нет — переход прямым переключением.** Для NTF-3 это значит: таблицы
тома, снимка и образа получают колонку инициатора сразу `NOT NULL` с `CHECK` формы (Р13), без
expand/contract, без умолчания и без обратного заполнения. Строки без инициатора в живой установке
не существуют: на непустой таблице миграция отказывает штатным отказом базы («column … contains
null values») и не применяется, стенд поднимается заново посевом (решение владельца «прода нет
так что можно перестраивать все подряд»). Ветки «инициатора нет» у сверщика и у ленты **нет** —
ей не было бы производителя (NTF3-09 утверждает ограничение базы, а не ветку).

### Решения этой под-фазы

**Р9. Критерий подключения модуля — событие, о котором арендатор иначе не узнает.**
Модуль подключается, если в нём есть **производитель** перехода ресурса арендатора в состояние
сбоя, который (а) случается без запроса арендатора и (б) после того, как операция арендатора уже
завершилась (`done=true`). Всё, что арендатор узнаёт опросом своей операции, письма не заслуживает
(`.claude/rules/api-conventions.md` §«Подписки на операции не существует»: опрос — штатный путь).
Основание: ТВ2 и «максимальная простота» — письма там, где без них арендатор теряет факт, и нигде
больше. Состояние в контракте **без** производителя не подключается: письмо о событии, которого
никто не производит, — мёртвый шаблон (`.claude/rules/api-conventions.md` §«Принято-и-проигнорировано»).

**Р10. Справочник адресов отвечает адресом только при двух условиях сразу.**
Внутренний метод службы доступа (рабочее имя `InternalNotificationRecipientService.Resolve`) по
запросу `notify` `{namespace, subject, resource_ref{type,id}, relation}` отвечает:

Условия проверяются в этом порядке; первое невыполненное даёт исход:

| исход | условие | что делает `notify` | сценарий |
|---|---|---|---|
| `SUBJECT_NOT_FOUND` | субъекта нет (удалён между постановкой и доставкой) | терминально `NO_ADDRESS(subject_gone)`, 0 SMTP-сессий | NTF3-48 |
| `AUDIENCE_DENIED` | `Check(subject, relation, resource)` ложен | терминально `DENIED(audience)`, 0 SMTP-сессий | NTF3-24 |
| `NO_CONFIRMED_ADDRESS` | субъект — учётная запись службы, либо адрес не подтверждён | терминально `NO_ADDRESS`, 0 SMTP-сессий | NTF3-25, NTF3-26 |
| `ADDRESS{address}` | всё выполнено: субъект — пользователь, `Check` истинен, `email_verified_at` задан | рендер и отправка | NTF3-15, NTF3-23 |
| `UNAVAILABLE` / срок вызова | служба доступа не ответила | `DEFER(platform_unavailable)`, fail-closed, срок строки не продлевается; по истечении срока уборщик источника закрывает строку `EXPIRED(platform_unavailable)` и возвращает лимит (NTF-1 Р8) | NTF3-46, NTF3-47 |

`Check` идёт раньше адреса: адрес (и сам факт, подтверждён ли он) не выдаётся по субъекту, которому
ресурс не виден. Клетки `DENIED(audience)`, `NO_ADDRESS`, `NO_ADDRESS(subject_gone)` **дописываются
этой под-фазой** в закрытый словарь исходов NTF-1 Р9 (там адресат — только адрес, NTF-1 Р7);
`UNAVAILABLE` ложится в существующую клетку «kaname недоступна» того же словаря.

**Отказ вызова справочника — клетка на каждый код ответа, корзины «прочее» нет.** Таблица выше
отображает исходы, которые справочник **отвечает**; эта — коды, которыми вызов **не** дал исхода.
Порядок строк не значим: код попадает ровно в одну строку, и перечень кодов gRPC покрыт целиком.

| код ответа `Resolve` (либо ответ) | что это значит для `notify` | исход строки | тратит попытку | сигнал | сценарий |
|---|---|---|---|---|---|
| `PERMISSION_DENIED`, `UNAUTHENTICATED` | у `notify` нет выдачи `reader` на справочник, либо его идентичность не прошла сверку — неисправность **настройки**, а не адресата | `DEFER(platform_unavailable)` | нет | `misconfigured`; `notify_recipient_directory_refused_total{ns,code}` растёт, тревога **без окна** | NTF3-55, NTF3-56 |
| `INVALID_ARGUMENT` | запрос `notify` не прошёл проверку типа ресурса или отношения — дефект сборки шаблона, повтор того же запроса даст тот же ответ | `INVALID` (терминально), 0 SMTP-сессий | — | `notify_recipient_directory_refused_total{ns,code="InvalidArgument"}`, тревога без окна | NTF3-56 |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `CANCELLED`, `RESOURCE_EXHAUSTED`, `ABORTED`, `INTERNAL`, `UNKNOWN`, `DATA_LOSS` | служба доступа не дала ответа по своей причине | `DEFER(platform_unavailable)` (та же клетка, что «kaname недоступна» NTF-1 Р9) | нет | — | NTF3-46, NTF3-56 |
| `NOT_FOUND`, `ALREADY_EXISTS`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNIMPLEMENTED` | контракт справочника таких кодов не производит (исход по субъекту — в теле ответа, не кодом); код означает расхождение версий `notify` и службы доступа | `DEFER(platform_unavailable)` | нет | `misconfigured`; тот же счётчик с кодом, тревога без окна | NTF3-56 |
| `OK`, но значение исхода `notify` не знает (новое значение перечисления) | расхождение версий | `DEFER(platform_unavailable)` | нет | `misconfigured`; `notify_recipient_directory_refused_total{ns,code="UnknownOutcome"}` | NTF3-56 |

Почему отказ прав и аутентификации **не** терминален: он говорит о `notify`, а не о получателе.
Терминальное отображение при сломанной выдаче `notify` закрыло бы все письма всем арендаторам
без следа; отложенное — держит строки до восстановления выдачи в пределах их срока, а тревога без
окна называет неисправность сразу. По истечении срока строку закрывает уборщик источника
`EXPIRED(platform_unavailable)` с возвратом лимита (NTF-1 Р8), как у NTF3-47. `INVALID_ARGUMENT`,
наоборот, терминален: шаблон с неверной аудиторией отвергает валидатор при `bundle` (NTF3-29),
и до `Resolve` такой запрос дойти не должен; дошедший — дефект, повтор его не исправит.
Клетки этой таблицы дописываются в словарь исходов NTF-1 Р9 вместе с тремя клетками выше.

Запрос с `resource_ref.type` не из пространства имён `namespace` (для storage — только
`storage_*`) либо с `relation` вне закрытого набора → `INVALID_ARGUMENT` с именем поля.
Основание: ТВ3 — служба не может через шлюз узнать адрес или права по чужим ресурсам; «максимальная
безопасность» — адрес выдаётся только тому, кому уже можно видеть ресурс. Ответ не кэшируется
`notify` дольше одной доставки.

**Р11. Справочник — только внутренний, только для `notify`, с проверкой прав на каждый вызов.**
Метод на внутреннем слушателе (`.claude/rules/security.md` §«Internal-vs-external (ban #6)») и
**без HTTP-привязки** (`google.api.http` у метода нет): его зовёт только `notify` по gRPC, и маршрута
REST у него нет ни на одном слушателе — таблица маршрутов края генерируется из этих привязок
(`gateway/internal/middleware/rest_route_table_gen.go`, генератор `gateway/cmd/protoc-gen-kacho-rest-routes`);
статический набор вызывающих с точным SAN `notify` (пустой набор = запрет) **и** `Check`
отношения `reader` учётной записи `notify` на объекте справочника — отношение прямое, без
подстановки и без каскада (`.claude/rules/security-hardening.md` §«Отношение, выполнимое
подстановочным знаком, не сужает НИЧЕГО»). Выдача `reader` — строкой манифеста `notify`, и
**только его**: применитель манифестов службы доступа отвергает выдачу на объект справочника из
манифеста любого другого модуля (NTF3-50) — иначе служба выдала бы себе доступ к адресам одной
строкой своего же манифеста.
Основание: `sec-internal-trusted-assumption-banned` — периметр не доверенный.

**Р12. Локаль письма — локаль установки; набор локалей закрыт: `{ru, en}`; каждый шаблон каждого
владельца обязан иметь тело на каждой локали набора.**
Ручка `notify` `KACHO_NOTIFY_DEFAULT_LOCALE` ∈ `{ru, en}`, без умолчания: не задана или вне набора
→ отказ старта (`.claude/rules/security.md` §«Internal-vs-external», `sec-no-silent-default-for-guarded-knob`).
Предпочитаемой локали у субъекта нет (§1.4), поэтому выбор по получателю вне предмета (§6).
Единый валидатор `notify/spec` отвергает шаблон без тела на любой локали набора — **и у службы
доступа тоже**: её шаблоны (NTF-1, NTF-2) получают `body.en.yaml` тем же изменением.
Основание: ТВ4 («красивые» — это и понятные на языке установки); «максимальная простота
поддержки» — одна ось выбора, а не две.

**Р13. Получатель письма о сбое ресурса — инициатор намерения, породившего строку, и только он.**
Строка тома, снимка и образа получает колонку `intent_initiator` — субъект, захваченный из
проверенного субъекта запроса в момент приёма, в форме `user:<id>` либо `service_account:<id>`.
Ограничение — в базе: `NOT NULL` и `CHECK` на эту форму (непустой id, тип из двух), по одному на
каждую из трёх таблиц. Колонка пишется **только при вставке строки**, в той же транзакции:

| глагол (§1.9) | что пишет в `intent_initiator` |
|---|---|
| `VolumeService.Create`, `SnapshotService.Create`, `ImageService.Create` | субъект вызывающего |
| `SnapshotService.Copy`, `ImageService.Copy` | субъект вызывающего копию — в строку **копии**; строка источника не меняется |
| `InternalImageService.Register` | субъект оператора установки, вызвавшего регистрацию |
| все прочие глаголы, включая `VolumeService.Update` с ростом `size_bytes` и `ChangeDiskType` | не пишут |

Почему «породившего», а не «последнего»: в `ERROR` строка входит только из `CREATING` (§1.8, П1 и
П3), а `CREATING` пишет только вставка. Намерение, которое сверщик исполняет к моменту сбоя, — всегда
то, что строку родило. Перезапись колонки ростом размера или сменой класса была бы записью без
читателя: ни то, ни другое сверщик в `ERROR` не переводит (П5 недостижима, переезда в сверщике нет) —
а запись без читателя запрещена (`.claude/rules/api-conventions.md` §«Принято-и-проигнорировано»).
Предикат пересмотра — в дереве появился производитель перехода в `ERROR` не из `CREATING` (§6).

Письмо адресуется этому субъекту с аудиторией `{<тип ресурса>, v_get}`. Строка, внесённая
`Register`, рождается `READY/READY` вне рабочего списка сверщика (§1.9) и в `ERROR` не переходит;
значение её колонки обязано быть (`NOT NULL`), и честное значение — субъект того, чьё это намерение.
Письма о ней не бывает (NTF3-54).
Колонка — служебная: ни в публичную проекцию `Get`/`List`, ни во внутреннюю она не выходит
(`.claude/rules/security.md` `sec-two-projections`, `sec-public-surface-intent-and-result`); её читатель —
только функция перехода в `ERROR` при постановке в ленту (NTF3-51).
Рассылки «всем, кто видит проект» нет: она потребовала бы перечислять субъектов по модели
(`.claude/rules/security.md` §«Get/List: проверка прав постранично» — перечисление разрешённых
запрещено) и превратила бы сбой бэкенда в рассылку по всему проекту.
Основание: `hard-async-carries-initiator` (личность захватывается в момент запроса); ТВ3.

**Р14. Лимиты модулей объявлены в шаблоне и обязательны; превышение не мешает переходу.**
Каждый шаблон модуля объявляет `class: notice`, `ttl: 24h` и `limits`: на получателя — 20 писем в
час по всем шаблонам своего пространства имён; на проект — 200 в час. Валидатор отвергает шаблон
модуля без `limits`. Строка сверх лимита **не ставится**, переход ресурса **коммитится**, и растёт
счётчик `notify_suppressed_total{ns,template,reason="limit",scope="recipient"|"project"}` у источника
(`scope` называет исчерпанное окно; исчерпаны оба — `recipient`, он проверяется первым). Счётчик
**новый, его заводит эта под-фаза**: в NTF-1 `Put` сверх лимита отвечает сторожем «лимит исчерпан» и
строки не ставит, а счётчика подавления там нет (`grep -c notify_suppressed_total` по приёмке NTF-1 →
0). Счётчик заводится в corelib `notify/feed` рядом со сторожем, так что его получает всякий источник.
Ключ окна «проект» — **расширение** набора ключей `Put` из NTF-1 Р8 (там: адресат, инициатор,
аккаунт, `ns`, число адресов): у строки storage проект есть в самой строке ресурса, а аккаунта нет,
и добывать его вызовом на пути сверщика — сетевой вызов внутри транзакции перехода. Оба изменения
делаются в corelib этой под-фазой (§12). Основание: «максимальная
безопасность» — сбой бэкенда на сотню томов не превращается в почтовый шторм; письмо — следствие,
не условие перехода. `24h`: по истечении суток состояние ресурса и так видно в консоли, а старое
письмо о давно известном сбое — шум.

**Р15. Одно письмо на один переход из `CREATING` в `ERROR`.**
Постановка — только когда запись **изменила** состояние с `CREATING` на `ERROR`: прежнее состояние
определяется тем же оператором записи, под блокировкой строки, в той же транзакции, что постановка.
Это ровно те переходы, которые дерево производит (§1.8: П1, П3). Проход по уже ошибочной строке (П8)
и вторая из двух параллельных записей по одной строке писем не ставят (NTF3-07). Запись `ERROR`
поверх любого другого прежнего состояния письма **не** ставит (NTF3-53): сверщик такой записи сегодня
не делает (П4, П5, П6 недостижимы), и если исправление storage сделает её достижимой, решение о письме
для неё принимается приёмкой того исправления, а не молча этим кодом. Выход из `ERROR` (П7) письма не
ставит (NTF3-45). Основание: `.claude/rules/data-integrity.md`
§«Within-service инварианты — ТОЛЬКО на DB-уровне» (`db-cas`); без этого две реплики сверщика
давали бы два письма об одном переходе.

**Р16. У `storage` три нотификации, по одной на тип ресурса.**
`volume-error`, `snapshot-error`, `image-error`. Один параметризованный шаблон невозможен: аудитория
`{resource_type, relation}` статична в `notification.yaml`, а тип у трёх разный. Атрибуты закрыты:
`resource_id` (id), `resource_name` (DNS-метка), `project_id` (id), `reason` (перечисление из
словаря §1.2 с текстом на каждой локали), `occurred_at` (время). Ссылка — кнопка на путь страницы
ресурса в консоли; схема и хост — только из конфигурации установки. Секретных атрибутов нет.

**Р17. Перепись — машинная ведомость в `notify`, а не текст; шаблоны собираются без второй копии.**
`services/notify/sources.yaml` несёт по одной записи на каждый каталог `services/*` (кроме самого
`notify`) и на каждый внешний источник (служба доступа): `connected` с перечнем шаблонов либо
`not_connected` с причиной и предикатом пересмотра. Гейт сверяет ведомость с деревом в обе стороны
(§9, группа A). Шаг `make -C services/notify bundle` пишет в дерево `notify` только ведомость
сборки (имя, `schema_rev`, дайджест содержимого каждого шаблона); содержимое шаблонов собирается в
образ из их домашних каталогов (модулей kacho — из дерева, службы доступа — из модуля на пине).
Основание: `.claude/rules/polyrepo.md` `poly-services-no-code-dep` (`notify` не импортирует
`services/<svc>/`) и `poly-copy-ban` / `ban20-copy-ban` (копия с чужим владельцем в дереве не
лежит); «максимальная простота поддержки» — у текста шаблона одно место правки.

## §6 Что НЕ входит

- **NTF-1** (`PRO-Robotech/kacho#2915`, `PRO-Robotech/corelib#77`, `PRO-Robotech/kaname#484`):
  corelib `notify/*`, контракт ленты, форма сигнала, `services/notify`, макет и блоки, исходы шлюза,
  надгробие и `Revoke`/`Restore`, перевод службы доступа на ленту.
- **NS** (`PRO-Robotech/kacho#2916`): политика выпуска сертификатов.
- **NTF-2** (`PRO-Robotech/kacho#2917`): снятие почты поставщика личности.
- **NTF-4** (`PRO-Robotech/kacho#2919`): возвраты, жалобы, подавление, DKIM/SPF/DMARC.
- Уведомления домена прав (3.7, 3.9, W2.B) — предмет службы доступа, её приёмок.
- Выбор локали по получателю — появится, когда у субъекта будет предпочитаемая локаль в службе
  доступа (предикат: поле локали субъекта в её контракте).
- Иные каналы доставки (мессенджеры, веб-хуки) — предмет отсутствует; `notify` — почтовый шлюз.
- Подписка арендатора на категории писем и отписка — **NTF-4** (подавление).
- **Письмо о переходе в `ERROR` не из `CREATING`** (П4 — пропажа или неисправность объекта под
  готовой строкой; П5 — отказ роста размера; П6 — отказ снятия). Производителя у этих переходов в
  дереве нет (§1.8): готовая строка в рабочий список сверщика не попадает, рост размера пары
  состояний не трогает, `DELETING` не пишет никто. Это дефект корректности storage, и ведётся он
  отдельной задачей. Предикат пересмотра — в дереве появился производитель строки `READY` либо
  `DELETING` в `Drifted`; изменение, которое его заводит, несёт собственную приёмку письма и меняет
  Р15 и NTF3-53 явно.

## §7 Чего посеять нельзя — и чем это покрыто

Перевод ресурса storage в `ERROR` на поднятом стенде публичным API не конструируется: фейковый
бэкенд в не-тестовом коде не используется (§1.2), а заводить в прод-код ручку инъекции отказа
ради пробы запрещено (`ban13-test-only-pr`, `ban14-production-grade`). Поэтому:

- **связь «переход → строка ленты»** — интеграционные пробы storage (testcontainers + фейковый
  бэкенд с инъекцией отказа по имени глагола, уже в дереве);
- **связь «строка ленты → письмо»** — сквозная проба на стенде, где Given конструируется посевом:
  строка ставится **сгенерированной функцией** `SendVolumeError` той же сборки, против базы storage
  стенда, в транзакции посева (NTF3-38);
- **схождение половин** держится тем, что обе стороны пользуются одной сгенерированной функцией, и
  гейтом `notifygen -check` (NTF-1) на её равенство шаблону.

#### Группа B. Постановка в транзакции перехода

Переходы — по ветвям §1.8; «проход сверщика» — один вызов его цикла в пробе. Storage в обвязке поднят
**со сверщиком** (задан вид бэкенда — фейк), поэтому `Create`/`Copy` рождают строку `CREATING/ABSENT`
(§1.8, таблица писателей). Каждое Given о сверщике называет пару `state/observed_state` строки до прохода,
и проба **до** прохода утверждает, что `Drifted` этого вида возвращает строку (либо не возвращает — где
сказано): иначе «проход ничего не сделал» неотличим от «проход строку не видел».
