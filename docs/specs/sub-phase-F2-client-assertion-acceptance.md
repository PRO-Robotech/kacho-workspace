## §0 Обзор

Платформа заводит **свой токен-эндпоинт**: клиент предъявляет подписанное утверждение
(`private_key_jwt`, RFC 7523 §2.2), мы сверяем подпись **его открытым ключом из своей же
таблицы** и выдаём токен доступа по виду выдачи «учётные данные клиента». Токен чеканит
подписант F1.

Это вторая из четырёх фаз отказа от внешнего OAuth-сервера (эпик #896). Первая дала **чем**
подписывать; вторая даёт **кому** и **по какому предъявлению** выдавать.

**Фаза заводит принимающую сторону там, где сегодня у нас есть только предъявляющая.** Утверждение
этого вида в дереве уже подписывается и предъявляется — шестнадцатью не-тестовыми файлами (§1.5),
и все шестнадцать стоят на стороне **клиента**. F2 добавляет сторону **сервера**, и это меняет
цену ошибки на противоположную: у предъявителя неверное утверждение даёт отказ, видимый сразу;
у принимающего неверная проверка даёт **принятое чужое утверждение**, не видимое никогда.

**Три вещи, которые определяют объём и легко пропускаются**, — каждой посвящён свой раздел:

1. **Однократность — одна атомарная операция, а не две.** Проверка «не предъявлялось ли уже» и
   погашение идентификатора обязаны быть **одним** оператором базы. Раздельные проверка и запись
   под конкуренцией пропускают **оба** одновременных повтора (ban #10). Это не теория: образец
   правильного решения уже посажен в дереве работой #694 (§1.4), и F2 берёт его форму.
2. **Область однократности — флот, а не процесс.** Хранилище в памяти пода корректно ровно до
   второй реплики; со второй оно даёт защиту, которой нет, и при этом выглядит исправной.
3. **Потолок длительности утверждения.** Без него утверждение с очень далёким сроком занимает
   идентификатор однократности на всю эту длительность — то есть хранилище, ограниченное сроком,
   перестаёт быть ограниченным, а отказ в обслуживании становится дешёвым.

**Наблюдаемая цель фазы.** Клиент, зарегистрированный у нас, предъявляет нашему эндпоинту
утверждение, подписанное своим ключом, и получает токен, подписанный нашим ключом; тот же токен
проходит на поверхности, которой он адресован. Повторное предъявление того же утверждения
отвергается — и отвергается независимо от того, в какую реплику оно попало. Отозванный клиент не
получает нового токена **и** теряет уже выданный. Наш токен доступа не проходит как утверждение
клиента, а утверждение клиента не проходит как токен доступа.

## §1 Что верно в дереве — измерено, а не предположено

Каждое число — с предикатом и единицей счёта. Ревизия — `af1ce112f`.

### 1.1 Реестр клиентов — наш, и ключевой материал есть у ДВУХ таблиц из трёх

Задача называет три таблицы. Ключевой материал (`public_key_pem`, `key_algorithm`) лежит **не во
всех трёх**, и это различие несущее, а не педантизм.

```
git grep -n 'public_key_pem\|key_algorithm' -- 'services/iam/internal/migrations/0046_user_oauth_clients.sql'
git grep -n 'public_key_pem\|key_algorithm' -- 'services/iam/internal/migrations/0001_initial.sql'
git grep -n 'public_key_pem\|key_algorithm' -- 'services/iam/internal/migrations/0078_interactive_clients.sql'   # → пусто
```

| таблица | ключевой материал | что это за клиент |
|---|---|---|
| `user_oauth_clients` | **есть** | клиент под токен пользователя |
| `service_account_oauth_clients` | **есть** | клиент под ключ служебной учётки |
| `interactive_clients` | **нет ни одной колонки** | клиент, через которого **человек** входит интерактивно |

**Что из этого следует для объёма.** Третья таблица — не «ещё один клиент, у которого забыли
завести ключ»: у неё **нет способа доказать владение ключом by construction**, и требование
корпуса «публичный клиент по этому потоку токена не получает» (#22) выполняется не проверкой
поля, а тем, что такой строки в реестре, способном к утверждению, нет вовсе. Сценарий F2-44
требует именно этого — отказа по **отсутствию в реестре**, а не по пустому ключу; разница
объясняется в §2.9.

### 1.2 Словарь зарегистрированного алгоритма ЗАКРЫТ и допускает пустое значение

Ограничение обеих таблиц с ключевым материалом называет одно и то же множество:

```
git grep -n 'key_algorithm_check' -- 'services/iam/internal/migrations'
```

→ два ограничения, оба `IN ('', 'ES256', 'RS256', 'EdDSA')`.

**Пустое значение в этом множестве — законный вход, и оно означает «ключа нет», а не «любой
алгоритм».** Требование F2: проверяющий обязан читать его именно так; клиент с пустым
зарегистрированным алгоритмом аутентифицироваться утверждением **не может** (F2-10). Это тот же
класс, который F1 закрывал у себя (§4.3): значение, которое может быть пустым и не проверено на
непустоту, означает «не сужаем».

### 1.3 Зеркальная колонка читается ДВЕНАДЦАТЬЮ не-тестовыми файлами

```
git grep -l 'hydra_client_id\|HydraClientID' -- 'services/iam' ':!*_test.go' | wc -l   # → 12
```

Единица счёта — **файл индекса git** в дереве сервиса, без проб. Это единственная чужая колонка
в реестре, и её судьба — предмет решения §2.1: она **не участвует** в разрешении клиента у нашего
эндпоинта и снимается вместе с внешним сервером в F4. Двенадцать мест адъюдицируются в §9.4.

### 1.4 Образец однократности с областью «флот» уже посажен

Работа #694 — общее хранилище однократности края:

```
wc -l gateway/internal/idempotencypg/store.go            # → 485
ls    gateway/internal/idempotencypg/migrations/         # → 694001_idempotency_records.sql, migrations.go
```

Из него F2 берёт **форму**, а не код: ключ — первичный, и именно уникальность ключа делает допуск
атомарным одним оператором, а не программной парой «посмотреть — записать»; строка живёт до
объявленного срока и убирается сборщиком, иначе хранилище растёт без границы; домен гарантии —
**флот**, поэтому запись лежит там, где её видят все реплики.

**Чем предмет F2 отличается от #694, и почему это НЕ переиспользование той же таблицы:** там три
исхода (моё · чужой законченный ответ · чужая живая бронь) и аренда с держателем, потому что
предмет — повтор запроса, у которого есть **сохранённый ответ**. Здесь исходов **два** — первое
предъявление либо повтор, — ответа не сохраняется, аренды нет. Заводить трёхисходную машинерию
под двухисходный предмет значило бы унифицировать по более широкой семантике (`code-authoring`).
Общей делается **форма инварианта**, а не структура.

### 1.5 Утверждение этого вида в дереве живёт ТОЛЬКО со стороны предъявителя

```
git grep -l 'client_assertion\|ClientAssertion' -- '*.go' ':!*_test.go' ':!pkg/api/*' | wc -l   # → 16
```

Разложение по каталогам (тем же предикатом с `sed 's|/[^/]*$||' | sort | uniq -c`): выдача
токена узкого контура — 4, его обвязка — 2 + 1 + 1, клиенты внешнего сервера — 2, выдача токена
узкого контура (второй вид) — 2, конфигурация — 1, два глагола выдачи — по 1, провайдер
инфраструктуры — 1.

**Все шестнадцать — предъявляющая сторона.** Принимающей стороны в дереве нет, и F2 её заводит:
это не доработка существующего, а новая поверхность со своим периметром (`security-surface`).

### 1.6 Прецедент нашего HTTP-эндпоинта выдачи существует

```
wc -l services/iam/internal/handler/registrytokenhttp/handler.go   # → 194
```

Токен-эндпоинт узкого контура уже наш, отдельным слушателем, с собственным ответом-вызовом и
собственной формой отказа. F2 **не изобретает** форму HTTP-эндпоинта выдачи — она берёт
существующую и расширяет её вторым видом предъявления. Это же снимает вопрос «gRPC или HTTP»:
вид выдачи по учётным данным клиента задан стандартом как форма запроса, а не как наш выбор.

### 1.7 Дословный перенос чужого кода невозможен технически

Гейт лицензий (`internal/repohygiene`, `TestSPDXHeadersPresent`) требует наш SPDX-заголовок в
первом килобайте каждого исходного файла в области покрытия. Из чужих реализаций берётся
**перечень случаев** с комментарием, называющим источник и его ревизию.

**И предупреждение, ради которого перенос вообще разбирался.** Зрелая чужая реализация выбирает
проверяющего **по типу ключа**, а не по объявленному в заголовке алгоритму. У неё поэтому **нет**
пробы на подмену алгоритма — у неё нет и предмета. Перенеся её таблицу случаев на нашу
библиотеку, мы получили бы таблицу **без этой защиты**, и её отсутствие было бы неотличимо от
полноты: положительный путь работает, отрицательных утверждений просто нет.

**Сценарий на подмену алгоритма обязан быть НАШИМ** — F2-08, и он помечен как не имеющий
внешнего прообраза.

### 1.8 Библиотека одна — но СТЕКОВ разбора JOSE в дереве ТРИ

Объявленная зависимость одна:

```
grep -n 'golang-jwt' go.mod    # → github.com/golang-jwt/jwt/v5 v5.3.1
```

**Этим предикатом заявленный предмет не измеряется**, и это надо сказать прямо: он меряет
**объявленные модулем зависимости**, а рукописный стек зависимости не объявляет **by
construction**. Предикат, мерящий дерево:

```
git grep -l 'golang-jwt/jwt' -- '*.go' ':!*_test.go'                       # → 3, все в gateway/internal/middleware/
for f in $(git grep -l 'base64.RawURLEncoding' -- '*.go' ':!*_test.go'); do
  grep -q 'golang-jwt/jwt' "$f" || { grep -qE '"alg"|"typ"|"kid"' "$f" && echo "$f"; }
done
```

Второй обход даёт **три** файла. Один из них (`gateway/internal/middleware/jwk.go`) обслуживает
путь библиотеки и отдельным стеком не является; **два остальных независимы**, и каждый объявляет
независимость собственной шапкой: `services/iam/internal/registrytoken/assertion.go` —
**подписант**, `services/registry/internal/clients/jwks/verifier.go` — **проверяющий**.

**Что из этого следует для объёма — это не спор о числе.** F2 заводит **третьего** проверяющего,
и её решения (закрытый словарь алгоритмов, отказ на подмену алгоритма, дублирующееся имя члена
заголовка, член, помеченный обязательным к пониманию) доедут **только** до пути библиотеки.
Ровно тот класс, который §1.10 держит на потолке тела, и §9.4 даёт рукописным стекам ту же
строку с тремя исходами.

**Требование F2 при этом остаётся прежним и не отменяется:** **ни одной второй библиотеки**
разбора и проверки JWS ради «удобнее для утверждения»; разбор заголовка на дублирующиеся имена
членов (#5) и на члены, помеченные обязательными (§4.2), делается **над той же** библиотекой
дополнительным шагом, а не заменой её.

### 1.9 Параметр заголовка «обязательный к пониманию» в дереве не встречается

```
git grep -rn '"crit"' -- '*.go' ':!*_test.go' | wc -l   # → 0
```

Единица счёта — вхождение имени члена заголовка в не-тестовом Go-коде. Ноль означает, что **обе**
стороны пары требований (§4.2) — новая работа, и ни одна из них не приедет «сама собой» вместе с
библиотекой.

### 1.10 Ограничение размера тела в дереве реализовано ДВАЖДЫ

```
git grep -ln 'MaxBytesReader' -- '*.go' ':!*_test.go' | wc -l   # → 2
```

Два независимых места об одном предмете. Требование F2: новый эндпоинт **третьего не заводит**
(F2-12); предмет сводится к одной реализации, которой пользуются все, либо расхождение
объявляется решением с причиной. Иначе следующая правила ограничения доедет не всюду, а
пользователь прочитает разницу как другое место продукта.

### 1.11 Состояние владельца — закрытый словарь из трёх значений


→ `PENDING`, `ACTIVE`, `BLOCKED`. Требование #16 «отключённый владелец токена не получает»

### 1.12 Колонки адресатов у клиентов, способных к утверждению, НЕТ

```

```

Предикат намеренно обходит **весь каталог**, а не два файла создания: позднейший
`ALTER TABLE … ADD COLUMN` двухфайловый обход не увидел бы, и утверждение оказалось бы уже
своего предиката.

Следствие прямое и обязательное к соблюдению: **сценарий «запрошенный адресат обязан входить в
зарегистрированный у клиента перечень» написать нельзя** — состояние, которого схема не
допускает, не является Given (F1 §14 п. 2). Поэтому F2-38 сверяет запрошенный адресат с
**объявленным конфигурацией перечнем адресатов платформы**, а не с перечнем клиента.

Если продукт когда-нибудь заведёт перечень у клиента, это будет **сужением** поверх уже
объявленного, и сценарий добавится вместе с колонкой, а не раньше.

### 1.13 Соглашение об именовании миграции

```
ls services/iam/internal/migrations/*.sql | sed 's|.*/||' | sort -t_ -k1 -n | tail -1
```

→ `800001_…`. Форма — `<номер задачи><порядковый:3>_<имя>.sql`; миграции F2 именуются
`898001_…` и далее. Применённые не правятся (ban #5); всякий `DROP TABLE` — с ожидаемым числом
строк в ведомости дропов (`services/iam/internal/migrations/dropguard.json`).

## §2 Вопросы приёмки — ответы письменные

Молчание по любому из них — не «вне области», а пропуск. Ниже — решения, а не варианты. Вопрос,
получивший «зависит от», считается неотвеченным (F1 §14 п. 1).

### 2.1 Идентификатор клиента у НАШЕГО эндпоинта — наш собственный; зеркальное значение не разрешает

**Решение:** издатель и субъект утверждения равны **нашему** идентификатору строки реестра.
Зеркальное значение (идентификатор клиента во внешнем сервере, §1.3) на пути разрешения клиента
**не участвует вовсе** — ни как второй ключ поиска, ни как запасной.

**Почему не «принимаем оба на время перехода».** Два значения, разрешающих одного клиента у
одного эндпоинта, — это два правила об одном поле (`api-conventions.md`): одно из них неизбежно
окажется необязательным, и настройка, задавшая «не то», будет выглядеть исправной. Хуже того,
предмет здесь — **аутентификация**: субъект, у которого два имени, даёт две записи в журнале об
одном действии и два ключа однократности (§2.3) на одно утверждение.

**Почему это не ломает переход — и это главный довод.** Окна «два идентификатора у одного
эндпоинта» не возникает **by construction**: старый эндпоинт и новый — **разные** эндпоинты с
**разными** адресатами (§2.2). Клиент, настроенный на прежний, к новому не подходит и без смены
идентификатора — у него уже не тот адресат. Значит смена идентификатора не добавляет ни одного
ломающего изменения сверх того, которое переход и так требует.

**Цена названа:** глагол создания клиента отдаёт **наш** идентификатор как значение, которым
клиент себя называет; зеркальное значение остаётся в ответе отдельным, явно помеченным полем и
снимается в F4 вместе с внешним сервером. Двенадцать мест §1.3 адъюдицируются в §9.4, и исходов
у каждого ровно три: переписано на наш идентификатор · оставлено как путь к прежнему эндпоинту с
предикатом снятия в F4 · снято.

**Проверяемое следствие:** предъявление утверждения, называющего себя зеркальным значением,
нашему эндпоинту — **отказ** (F2-14), и отказ этот того же единого тона, что все прочие (§2.10).

### 2.2 Адресат утверждения — идентификатор нашего издателя, НЕ адрес эндпоинта

**Решение:** единственная принимаемая форма адресата утверждения — **идентификатор издателя**
(та же строка, которую подписант F1 ставит издателем выпускаемых токенов). Адрес токен-эндпоинта
в качестве адресата **отвергается**.

Основания, каждое самостоятельно достаточное:

- **адрес эндпоинта не одна строка, а несколько.** Один и тот же эндпоинт достижим по
  внутрикластерному адресу и по внешнему, с префиксом пути и без него; выбор «какой из них
  считать адресатом» пришлось бы делать при каждой новой посадке. Идентификатор издателя —
  **одна** строка, объявленная один раз и одинаковая во всех профилях;
- **значение выразимо ровно одним способом** (`api-conventions.md`). Принять обе формы значит
  завести два написания одного факта, а вместе с ними — вопрос, равны ли они, у каждого
  следующего читателя;
- **это композиция с уже принятым решением F1.** Привязка «издатель → путь» (F1 §2.8) делает
  идентификатор издателя ключом, по которому и так уже выбирается запись источника ключей.
  Второго ключа о том же предмете не заводится.

**Цена названа, и она больше, чем «чужие библиотеки».** Клиент обязан ставить в адресат наш
идентификатор издателя, а не тот URL, куда он стучится, — и это расходится не только с умолчанием
части клиентских библиотек, но и с **нашим собственным предъявителем**: в дереве значение адресата
утверждения выводится из адреса токен-эндпоинта (предикат: `git grep -n 'AssertionAudience' --
'services/iam' ':!*_test.go'` → **5** мест, из них не-описаний 3). Поскольку §9.1 п. 11 требует
приземления на живой путь, эти места приводятся к решению §2.2 **тем же изменением**, и §9.4
несёт под это отдельную строку. Отказ при расхождении громкий и мгновенный (§3), поэтому цена —
правка настройки, а не тихое расхождение.

**Обе стороны ожидания обязательны в конфигурации** (F2-16): незаданный ожидаемый адресат
означает «принимаем любой» (`security.md` §«Пустой список — это „не сужаем“»), поэтому пустое
значение — **отказ в старте**, а не умолчание.

### 2.3 Ключ однократности — СОСТАВНОЙ: клиент плюс идентификатор утверждения

**Решение:** ключ погашения — пара «идентификатор клиента + идентификатор однократности
утверждения». Не идентификатор утверждения сам по себе.

**Почему это не украшение.** Идентификатор однократности выбирает **предъявитель**. Если ключом
служит только он, то клиент A, предъявив утверждение с некоторым значением, **занимает это
значение у всех остальных клиентов**: у клиента B, чья библиотека выбрала то же значение,
законное первое предъявление отвергается как повтор. Отказ в обслуживании соседу получается
дешёвым и — что хуже — выглядит корректной работой защиты.

**Положительный контроль обязателен и он же закрывает класс:** тот же идентификатор
однократности, предъявленный **другим** клиентом, проходит (F2-26). Без этого утверждения проба
однократности зелена на реализации, отвергающей всё подряд.

**Сужать дальше — нельзя.** Ключ вида «клиент + идентификатор + адресат» или «+ момент выпуска»
делает повтор с изменённым сопутствующим полем законным, то есть отменяет однократность,
сохранив её форму.

### 2.4 Хранилище однократности — своя таблица iam по форме #694, и это решение против ДВУХ соблазнов

**Решение:** таблица в схеме сервиса, ключ — первичный, допуск — **один** оператор.

Отвергнуто, с причиной у каждого:

| вариант | почему нет |
|---|---|
| хранилище в памяти процесса | корректно ровно до второй реплики; со второй даёт защиту, которой нет, и при этом выглядит исправной. Область гарантии — **флот** (F2-25) |
| проверка чтением, затем запись | ban #10 дословно: два одновременных повтора проходят **оба**. Форма проверки есть, содержания нет |
| переиспользовать таблицу однократности края | другой домен, другая схема, другой предмет (§1.4): там три исхода и аренда держателя, здесь два исхода и ответа не сохраняется. Общей делается форма инварианта, а не структура |
| внешнее хранилище с истечением по ключу | завело бы зависимость на пути **аутентификации**, отказ которой пришлось бы классифицировать; при том что база сервиса на этом пути уже есть и её отказ уже классифицирован |

**Отдельно про «одну операцию»:** это требование к **коду**, а не только к результату. Гейт
F2-28 требует, чтобы функция допуска содержала ровно один вызов к базе, и несёт положительного
близнеца — функцию, которой два вызова законны (сборщик). Гейт, у которого нет места, которое он
обязан находить, молчит одинаково и когда предмет исчез, и когда сломался он сам.

### 2.5 Потолок длительности утверждения — объявлен числом; момент выпуска обязателен

**Решение:** утверждение обязано нести момент выпуска; разница между сроком и моментом выпуска
ограничена **объявленным числом**; превышение — отказ.

**Почему без этого хранилище перестаёт быть ограниченным.** Запись погашения обязана жить до
истечения утверждения — раньше снять нельзя, иначе повтор станет законным. Значит длительность
утверждения **и есть** срок жизни строки: утверждение со сроком в годы занимает свой ключ на годы.
Стоимость записи мала, но она умножается на число предъявлений, а число предъявлений выбирает
предъявитель.

**Почему отсчёт от момента выпуска, а не от «сейчас».** «Сейчас» у нас, момент выпуска — у
клиента; отсчёт от «сейчас» дал бы разный потолок при одном и том же утверждении в зависимости от
задержки доставки, то есть величину, которую нельзя ни объяснить клиенту, ни воспроизвести в
пробе. Отсчёт `срок − момент выпуска` — свойство самого утверждения.

**Решение по будущему моменту выпуска записано** (стандарт правила отказа не даёт): момент
выпуска в будущем **сверх объявленного допуска расхождения часов** — отказ; в пределах допуска —
приём. Иначе клиент со спешащими часами не смог бы аутентифицироваться вовсе, а допуск
расхождения, объявленный числом, существовал бы для одного поля и не действовал для соседнего.

**Граница задана стандартом асимметрично, и обе стороны — сценарий** (F2-21): ровно в момент
истечения — **отказ**; ровно в момент начала действия — **приём**.

### 2.6 Два вида подписанного разделяются ТРЕМЯ независимыми признаками, и ни один не назначен единственным

Предмет появился именно оттого, что один издатель начинает чеканить **два** вида подписанного:
токен доступа для наших поверхностей и — с этой фазы — принимать утверждение клиента. До F2
предмета не существовало.

**Решение:** признаков три, они независимы, и требование выполняется каждым по отдельности:

| # | признак | у токена доступа | у утверждения клиента |
|---|---|---|---|
| 1 | **объявленный тип** | тип токена доступа | тип аутентификации клиента, **иное значение** |
| 2 | **адресат** | адресат ресурсной поверхности | идентификатор нашего издателя (§2.2) |
| 3 | **чей ключ подписал** | ключ **ключницы** (F1) | ключ **клиента** из реестра |

**Почему три, а не «достаточно одного».** Каждый по отдельности защитим, и ровно поэтому опасен:
первый снимается клиентом, который тип не проставил; второй — совпадением адресатов при будущей
посадке; третий держится тем, что два множества ключей не пересекаются, — а это свойство дерева,
а не закон. Требование «ни один не назначен единственным» проверяется тем, что **каждое** из двух
направлений отвергается сценарием (F2-34, F2-35), а объявленные типы обоих видов живут **в одном
месте** и попарно различны (F2-36).

**Направлений действительно два, и оба обязательны:** выданный токен доступа, поданный как
утверждение клиента, и утверждение клиента, поданное как токен доступа **на каждой** поверхности
предъявления. Проба одного направления зелена при сломанном другом.

### 2.7 Адресат утверждения НЕ переносится в адресат выданного токена

**Решение:** адресат выпускаемого токена берётся из **запроса** (в пределах объявленного перечня,
§1.12) либо из объявленного умолчания — и **никогда** из предъявленного утверждения.

**Почему это отдельное решение, а не очевидность.** Перенос выглядит естественно («адресат уже
разобран, вот он») и **положительный путь при нём работает**: токен выпускается, подпись верна,
клиент доволен. Ломается он у **потребителя**: токен оказывается адресован нашему издателю, то
есть не той поверхности, которой предъявляется, — и обнаруживается это отказом на чужой стороне,
через несколько шагов после места ошибки.

**Положительный контроль здесь — контроль вреда** (F2-37): токен, чей адресат равен
идентификатору нашего издателя, обязан быть **отвергнут** всякой ресурсной поверхностью. Без него
сценарий утверждает про перенос, не показывая, чем перенос плох, — и следующий читатель снимет
требование как педантизм.

### 2.8 Что F2 берёт из отнесённого F1 к третьей фазе — одно расщепление и два переноса

Раскладка фаз F1 §12 и объём задачи #898 расходятся, и молчание об этом дало бы два места об
одном предмете, из которых верно одно.

F1 §12 относила к F3 три строки: выдачу по учётным данным клиента · «обмен утверждения на токен и
таблицу доверенных издателей» · обогащение утверждений на выдаче. **С ними происходит разное, и
называть всё «расщеплением» было бы неточно:** средняя строка расщепляется на два механизма,
крайние две **переносятся целиком** из F3 в F2 — то есть раскладка фаз в этих двух местах
пересматривается, а не уточняется. Основания переноса: у выдачи — §9.1 п. 11 (эндпоинт обязан
иметь живого вызывающего), у обогащения — §2.11. Оба надписываются в приёмке F1 по §9.4.

Расщепление средней строки — не уточнение формулировки, а два разных механизма под одним словом:

| механизм | что это | фаза |
|---|---|---|
| утверждение как **аутентификация клиента** (RFC 7523 §2.2) | клиент доказывает владение **своим зарегистрированным** ключом; доверие — из **нашего** реестра | **F2** |
| утверждение как **разрешение на выдачу** от внешнего доверенного издателя (RFC 7523 §2.1) | доверие — к **чужому** издателю и его субъектам; предмет — таблица доверенных издателей | **F3** |

Различие несущее: у первого источник доверия — наша строка, у второго — чужой издатель, чей набор
ключей мы не контролируем и чей субъект надо сопоставлять с нашим. Смешать их значило бы
унифицировать по более широкой семантике: правило про чужого издателя приехало бы туда, где
издатель наш.

**Итог раскладки после расщепления** (он же — вход в §12): F2 берёт выдачу по учётным данным
клиента, аутентификацию клиента утверждением и обогащение утверждений на выдаче (§2.11); F3
сохраняет разрешение на выдачу от внешних издателей, таблицу доверенных издателей и решение об
обновлении токена; F4 — снятие внешнего сервера, его базы, зеркальной колонки и обратного вызова.

**Клиентский реестр F1 §12 относила к F2 — и он уже есть** (§1.1). Работа F2 по реестру состоит
не в его заведении, а в двух вещах: чтении его на пути аутентификации и выводе зеркальной колонки
из этого пути (§2.1).

### 2.9 Публичный клиент — отказ ПО ОТСУТСТВИЮ в реестре, способном к утверждению

**Решение:** разрешение клиента идёт **только** по таблицам, несущим ключевой материал (§1.1).
Идентификатор интерактивного клиента не резолвится ни во что, и отказ наступает на том же шаге,
что и для несуществующего клиента.

**Почему не «нашли строку, ключ пуст, отказ».** Такая формулировка требует, чтобы третья таблица
участвовала в разрешении, — а значит, чтобы кто-то поддерживал в ней инвариант «ключа быть не
должно». Инвариант, который надо поддерживать, ломается; инвариант, выраженный отсутствием
таблицы на пути, — нет. Плюс различимость исходов «нашли, но без ключа» и «не нашли» — это
оракул: он сообщает предъявителю, существует ли клиент (`security.md` §Hardening п. 6).

**Требование #23 закрывается тем же порядком:** ручки, отключающей аутентификацию клиента, **не
существует** — ни одной. Ручка, которой нет, не может быть включена по ошибке. Проверяется гейтом
с положительным контролем (F2-44): гейт перечисляет **все** ручки эндпоинта и требует, чтобы ни
одна не влияла на решение об аутентификации, — а находить он обязан ту, которая влиять **должна**
(объявленный перечень допустимых алгоритмов).

### 2.10 Отзыв читается на пути ВЫДАЧИ и на пути ПРЕДЪЯВЛЕНИЯ, и проба ставит вопрос сквозь обе стороны

**Ответ письменно: да, на обоих, и это не два требования, а одно.**

> **ПРЕДПОСЫЛКА, на которой держится структурная замена контроля — названа, потому что без неё
> замена необоснованна.** Решение снять читателя с горячего пути в пользу формы срока верно
> ровно пока **срок клиента не двигается после создания**. Сегодня это так: единственные
> изменяющие операции по обеим таблицам, способным предъявлять утверждение, ставят отметку
> последнего использования; срок пишется один раз при создании.
>
> **Но это факт о дереве, а не свойство.** Заведи завтра глагол «сократить срок клиента» —
> операция правдоподобная и по смыслу равная отзыву — и токены переживут клиента: читателя на
> этот повод нет **по замыслу**, и не покраснеет ничто.
>
> Поэтому предпосылка обязана держаться, и предпочтительный способ — **выразить неизменяемость
> на уровне базы** (ban #10: инвариант держит оператор, а не память автора). Тогда она перестаёт
> быть фактом о дереве и становится свойством. Допустимая замена — гейт дерева «ни один писатель
> не двигает срок клиента» с переписью и инъекцией; он слабее, потому что стережёт **текущий**
> состав писателей.
>
> Структурная гарантия без названной предпосылки — это рантаймовый контроль, снятый в обмен на
> обещание. Обещание здесь и обналичивается: `testing.md` §«Гейт на класс» п. 3 требует, чтобы
> запрет нёс проверку **своей** предпосылки.

Контроль, действующий на выдаче и не действующий на предъявлении, отзывом **не является**
(`security.md` §«Контроль, действующий на ВЫДАЧЕ, но не на ПРЕДЪЯВЛЕНИИ»): он лишь не выдаёт
нового, а выданное продолжает проходить до истечения срока. Это состояние **не сходится само** —
в отличие от задержки распространения, у которой есть предел; здесь окно закрывает только срок
токена, и величина его от нагрузки не зависит.

Обратное тоже неверно: контроль только на предъявлении оставляет **выдачу** новых токенов
отозванному клиенту — то есть после отзыва он немедленно получает свежий и продолжает работать.

**Поэтому — две стороны и одна проба сквозь них:**

| сторона | требование | сценарий |
|---|---|---|
| **выдача** | отозванный ключ, истёкший клиент, не-`ACTIVE` владелец — токена не получают | F2-29, F2-30, F2-31 |
| **предъявление** | токен, выданный **до** отсечки, перестаёт проходить | F1-25 — предмет закрыт **приёмкой** F1; кода F1 на `af1ce112f` в дереве нет (§10) |
| **сквозь обе** | выдать → породить отсечку → предъявить **тот же** токен ⇒ отказ, по **каждому** из трёх поводов | **F2-32** |

**Механизм отсечки назван письменно — иначе исполнитель подставит соседний, и проба этого не
заметит.** Поводов три, и они доходят до предъявляющей стороны **по-разному**; молчание об этом
позволило бы закрыть F2-32 отзывом **субъекта** (существующий механизм, к клиенту отношения не
имеющий) и объявить требование выполненным:

| повод | что порождает | как доходит до предъявления |
|---|---|---|
| **отзыв ключа клиента** | запись отсечки, ключуемая **клиентом** | выданный токен несёт идентификатор клиента; читатель на пути запроса резолвит по нему — **второй ключ у существующего механизма, не второй механизм** |
| **владелец переведён в не-`ACTIVE`** | запись отсечки, ключуемая **субъектом** | существующим порядком, как сегодня; F2 требует лишь, чтобы переход её **порождал** |
| **истечение срока клиента** | **ничего** — закрыто by construction | срок выдаваемого токена **не превышает остатка срока клиента** (F2-29), поэтому токенов, переживших клиента, не существует, и читать на предъявлении нечего |

Третья строка — решение, а не наблюдение: читатель срока клиента на пути **каждого** запроса стоил
бы обращения к реестру на горячем пути ради величины, которая известна **в момент выдачи**.
Ограничение срока токена остатком срока клиента даёт то же свойство ценой одного вычисления при
выдаче. Цена названа: клиент, которому осталось меньше обычного срока токена, получает **укороченный**
токен — и обязан быть к этому готов, поэтому §9.4 требует назвать это на странице документации.

**Почему сквозная проба обязательна, а двух половин мало.** Две пробы по половине **зеленеют
обе** при неработающем целом: первая утверждает, что после отзыва не выдаётся новый (верно);
вторая — что отозванный токен не проходит (верно на токене, отозванном напрямую). Целое ломается,
если отзыв **клиента** не порождает отсечки для **уже выданных им** токенов — и ни одна из
половин про это не спрашивает. Это ровно класс «разрыв, невидимый ни с одной стороны по
отдельности» (`security.md`).

**Положительный контроль у F2-32 обязателен:** не отозванный клиент при доступном авторитете —
проходит. Иначе проба зелена на выдаче, которая не работает вовсе.

**Отказ авторитета отзыва — fail-closed.** Неполученный либо неопознанный ответ не есть «не
отозван».

**Нового межсервисного ребра это не заводит, но зависимость от F1 названа числом, а не словом.**
Читатель отзыва на пути запроса — предмет приёмки F1 (§2.2 там же); её **код на `af1ce112f` в
дереве не приземлён** (предикат в §10). F2 добавляет тому же механизму **второго вызывающего** (на
своём пути выдачи) и **второй ключ** (клиент, таблица выше) — но исполнима эта часть только после
приземления F1, и §10 говорит, с какого шага.

### 2.11 Состав утверждений выданного токена объявляется в ОДНОМ месте

Предикат задачи #898 п. 5 требует: утверждения в токене те же, что сегодня проставляет обратный
вызов. **Решение:** перечень утверждений и правила их вычисления объявляются в одном месте, и им
пользуются обе стороны — обратный вызов, пока он жив (до F4), и наша выдача.

**Почему одним местом, а не «сверили один раз».** Пока перечень живёт в двух местах, различие
между ними **не является ничьей находкой**: оно не выражено и потому не может покраснеть. Первая
же правка одной стороны разойдётся с другой молча, и разойдётся она у **принципала**, чей токен
выдан не тем путём.

**Проба сверяет множество имён и значений** на одном и том же принципале, а не присутствие
отдельных полей (F2-42): проверка «есть поле X» зелена на токене, потерявшем поле Y.

**Это уточняет F1 §12 п. 6**, относивший обогащение к F3 с доводом «проверяющий того контура
определяет принципала без предвыданных прав в токене». Довод верен **для контура F1** и
неприменим к контуру F2: здесь выдаётся токен для края, который права в токене читает.

## §3 Асимметрия цены: где отказ при сомнении ОБЯЗАТЕЛЕН

**Слишком строгая проверка даёт отказ, видимый сразу** — на первом же предъявлении, с именем поля
в журнале. **Слишком слабая даёт принятое чужое утверждение, не видимое никогда**: успешная
аутентификация выглядит одинаково независимо от того, что именно она проверила.

Для принимающей стороны это правило строже, чем для предъявляющей, и §0 объясняет почему: у
предъявителя обе ошибки громкие, у принимающего одна из двух — тихая.

**Правило работ:** на каждой развилке, где неясно, отвергать или пропускать, выбирается
**отвергать**; послабление вводится потом, отдельным решением, с предикатом снятия.

Места, где отказ при сомнении обязателен и закреплён сценарием:

| # | ситуация | обязательный исход | сценарий |
|---|---|---|---|
| 1 | вид предъявления не равен объявленному стандартом **точно** | отказ | F2-01 |
| 2 | утверждений больше одного, либо подписей больше одной | отказ | F2-02, F2-03 |
| 3 | имя члена заголовка встречается дважды | отказ **до** любого использования значений | F2-04 |
| 4 | неизвестный член заголовка, помеченный обязательным к пониманию | отказ | F2-05 |
| 5 | заголовок называет алгоритм, отличный от зарегистрированного у клиента | отказ **до** проверки подписи | F2-08 |
| 6 | алгоритм симметричного семейства либо «без подписи» | отказ отдельной явной веткой | F2-09 |
| 7 | зарегистрированный у клиента алгоритм пуст | отказ; пустое **не** означает «любой» | F2-10 |

## §4 Классы, невидимые на положительном пути

Каждый из четырёх невидим, пока всё идёт хорошо: клиент аутентифицируется, токен выдаётся, запрос
проходит. Ровно поэтому они формулируются требованиями, а не «проверим на ревью».

### 4.1 Обязательность поля не включается сама

Разбор, встретив срок, его проверит; **не встретив — не возразит**. То же относится к моменту
выпуска, к идентификатору однократности и к типу. Требование: обязательность каждого включается
**явным** параметром проверяющего, а сценарии F2-18, F2-19, F2-23 подают утверждение **без**
соответствующего поля и требуют отказа. Проба, подающая полное утверждение, это свойство не
измеряет вовсе.

### 4.2 Пара противоположных требований по неизвестным членам заголовка — и они стоят РЯДОМ

Требования два, они противоположны, и разлучать их нельзя:

| вход | исход | почему |
|---|---|---|
| неизвестный член заголовка, **помеченный обязательным к пониманию** | **отказ** | пометка означает «без понимания этого члена подпись нельзя считать проверенной»; принять — значит объявить проверенным то, чего не поняли |
| неизвестный член заголовка, **не помеченный** | **игнорируется**, утверждение принимается | заголовок открыт для расширения; отвергать всё незнакомое значит ломать совместимость с каждым клиентом, добавившим служебное поле |

**Почему они обязаны стоять рядом в документе и в пробах.** Ужесточение первого требования
естественно тянет за собой «а давайте вообще отвергать неизвестное» — и ломает второе. Обратно:
реализация, игнорирующая **всё** неизвестное, выполняет второе и молча теряет первое, оставаясь
зелёной на любой пробе, которая подаёт только известные члены. Сценарии F2-05 и F2-06 — пара, и
ни один из них не является положительным контролем другого: контроль у каждого свой (принимаемое
утверждение без расширений).

Обе стороны — **новая работа** (§1.9): ни одна не приедет вместе с библиотекой.

### 4.3 Дублирующееся имя члена заголовка не отвергается разбором само

Разбор объектной записи, встретив имя дважды, обычно берёт одно из значений и не возражает.
Стандарт (RFC 7515 §5.2) требует отказа, и причина не формальная: два значения одного члена
означают, что **проверяющий и подписант могли прочитать разное**, а значит проверенной оказалась
не та половина. Требование: дублирование обнаруживается **до** любого использования значений
заголовка (F2-04), положительный контроль — заголовок с уникальными именами принимается.

То же относится к повторению параметра формы (F2-02): «ровно одно утверждение» — не описание
намерения клиента, а требование к нашему разбору.

### 4.4 Потолок входа проверяется по ДВУМ признакам, а не по коду ответа

Требование #21 звучит как «объявленная длина сверх потолка ⇒ отказ до чтения тела», и проверка
только по коду ответа его **не измеряет**: тот же код возвращается и после того, как тело
прочитано целиком. Сценарий F2-11 утверждает **пару**: код ответа **и** число прочитанных байт
тела (ноль). Иначе «до чтения» остаётся словом в заголовке пробы.

## §5 Шов с соседним механизмом: доверие встроенному ключу законно РЯДОМ и недопустимо ЗДЕСЬ

Требование #4 — ключ берётся только из нашего реестра; встроенные в заголовок ключ и ссылки на
ключ (сам ключ, ссылка на набор, ссылка на цепочку сертификатов, сама цепочка) не выбирают ключ и
не участвуют в разрешении. Здесь это **обязательно**: доверять ключу, приехавшему вместе с
подписью, значит принимать любую подпись, потому что предъявитель приложит тот ключ, которым
подписал.

**И это же доверие в соседнем механизме дерева законно и является его сутью.** Доказательство
владения ключом (RFC 9449) устроено ровно наоборот: ключ приходит **в самом доказательстве**, и
проверяющий связывает его с токеном по отпечатку — там встроенный ключ не уязвимость, а предмет.

**Отсюда требование к работе, а не только к результату, и условным оно быть не может: общий
разборщик в дереве уже есть.** Предикат: `git grep -n 'RFC 7517' -- 'gateway/internal/middleware'`
— разбор JWK и вычисление отпечатка вынесены в отдельный файл, и его собственная шапка перечисляет
обоих потребителей: и тот, где ключ приходит из набора, и тот, где ключ приходит **в самом
предъявленном материале**. То есть конфигурация, ради которой §5 написан, — уже действительность,
а не гипотеза. Общий разборщик JOSE-заголовка **обязан нести явный запрет** на выбор ключа из
заголовка, а место, где такой выбор законен, обязано включать его **явно** и по своему решению. Умолчание «как получится» перенесёт
доверие туда, где оно недопустимо, — и перенесёт **тихо**: положительный путь при этом работает.

Проверяется двумя способами сразу:

- **сценарием** F2-07 — утверждение, несущее встроенный ключ, которым оно и подписано, при
  отсутствии соответствующей строки в реестре **отвергается**; положительный контроль — то же
  утверждение при наличии строки принимается, и принимается **по ключу из реестра**;
- **гейтом** — перечень членов заголовка, из которых ключ выбираться не может, объявлен **в одном
  месте**, а не выписан по месту употребления; положительный близнец гейта — место, где выбор
  ключа из предъявленного материала объявлен **намеренно**.

## §6 Инварианты однократности

### 6.1 Допуск — один оператор базы, и это инвариант, а не аккуратность

Требование: «не предъявлялось ли уже» и «погасить» — **одна** операция. Свойство держится
уникальностью ключа (ban #10), а не программной парой.

**Проба обязана быть конкурентной** (F2-24): последовательная проба зелена и на паре
«посмотреть — записать», потому что окна между ними при последовательном прогоне не существует.
`N` одновременных предъявлений одного утверждения — ровно одно проходит, остальные получают
ожидаемый отказ.

### 6.2 Область — флот, и проба обязана ставить вопрос о флоте

Проба, гоняющая один экземпляр, **не отличает** хранилище в памяти процесса от общего: оба дают
верный ответ. Требование: F2-25 поднимает **два независимых экземпляра** против одной базы, и
второй отвергает то, что погасил первый.

Это тот же класс, что «свойство композиции померено на одной части»: гарантия объявлена для
флота, а измерена на одном процессе.

### 6.3 Строка живёт ровно до истечения утверждения — не дольше и не короче

- **не короче**: снять запись раньше истечения значит сделать повтор законным. Срок жизни строки
  равен сроку жизни утверждения **by construction**, а не по совпадению настроек;
- **не дольше**: строка убирается сборщиком, иначе хранилище растёт без границы (требование #15).

**Проба утверждает возврат к исходному** (F2-27): после истечения и прохода сборщика число строк
возвращается к тому, что было до предъявления. Утверждение «сборщик вызвался» этого свойства не
измеряет.

**Повтор после истечения отвергается — по сроку.** Отказ есть в обоих состояниях, и наружу он
один и тот же (§7); различие видно в журнале и счётчиках. Проба обязана утверждать **исход**, а не
то, какая именно проверка сработала: утверждение о внутренней причине зафиксировало бы порядок
проверок как контракт.

### 6.4 Потолок длительности — арифметика, а не комментарий

Величина объявляется числом в одном месте и участвует в двух расчётах сразу: она ограничивает
разницу «срок − момент выпуска» (§2.5) и она же задаёт верхнюю границу жизни строки погашения
(§6.3). Гейт требует, чтобы число было объявлено **ровно один раз**; два объявления об одном
предмете разойдутся молча, и разойдутся они там, где расхождение не видно, — обе величины по
отдельности выглядят разумными.

### 6.5 Отказ хранилища — fail-closed

Недоступная база на пути аутентификации означает **отказ**, никогда «пропустить, погасим потом».
Отложенное погашение — это и есть та самая пара «проверить и записать», разнесённая на неопределённый
срок.

## §7 Единый тон отказа наружу — и различимость внутрь

Требование #17: все отказы аутентификации клиента **неразличимы** для предъявителя. Не различаются
между собой: нет такого клиента · клиент есть, но подпись не сошлась · алгоритм не тот · срок
истёк · утверждение уже предъявлялось · ключ отозван · владелец не `ACTIVE`.

**Почему это не «скрыть полезную диагностику».** Различимый отказ — оракул: по нему устанавливают,
существует ли клиент, жив ли он, какой у него алгоритм и какие идентификаторы однократности уже
заняты. Каждый из этих ответов сам по себе безобиден, а вместе они дают карту (`security.md`
§Hardening п. 6 — тот же принцип, что у побайтово одинакового отказа).

**Различимость обязана существовать — но с другой стороны провода:**

| носитель | что несёт | требование |
|---|---|---|
| ответ предъявителю | опознавательное слово стандартной формы | один и тот же для всех перечисленных исходов |
| журнал | какая проверка отказала, идентификатор клиента, корреляция запроса | никакого приватного материала и ни одного значения, приехавшего от предъявителя, без экранирования |
| счётчики | **свой счётчик у каждого исхода** | «ноль отказов за всю жизнь контроля» обязано быть **заметно** |

**Счётчик у каждого исхода — не наблюдаемость ради наблюдаемости.** Без него мёртвый контроль
невидим: проверка, не отказавшая ни разу за всё время жизни, неотличима от проверки, которая
работает и просто не встречала нарушителя (`security.md` §Hardening п. 8). Сценарий F2-33
утверждает **перепись**: у каждого исхода из §3 есть свой счётчик, и проба подаёт по одному входу
на каждый, требуя, чтобы двинулся **именно тот** счётчик.

**Приватный материал не покидает процесс** — ни в журнале, ни в тексте отказа, ни в счётчике, ни
в ответе. Требование F1 §6.10 действует здесь дословно и расширяется: **предъявленное
утверждение целиком** тоже не пишется наружу — это подписанный материал, из которого
восстанавливается предъявление.

## §8 Свойства, которые нельзя потерять при переписывании

Переписывание — самый вероятный способ потерять свойство, потому что новая задача выглядит проще
старой. У каждой строки есть исход, и «истекает вместе с предметом» — такой же исход, как
«сохраняется», только с обоснованием.

| свойство | исход | требование | сценарий |
|---|---|---|---|
| **«не настроено» ≠ «недоступно»** | **сохраняется** | отказ базы, сети, таймаут ⇒ недоступность, повтор осмыслен; ответ, доказывающий, что мы стучимся не туда, ⇒ **настройка**, наблюдаемо громко и никогда тихой записью | **обе ветви отказывают** — F2-32; **различимость** («громко») — F2-33, счётчик на исход |
| **исход по умолчанию для неопознанного отказа** | **сохраняется** | неопознанное падает в «недоступно», а не в «настройку»; обе ветви всё равно отказывают — спор только об имени | F2-32 |
| **свой предел времени на каждом внешнем вызове** | **сохраняется** | и на чтении реестра, и на допуске однократности, и на чтении отзыва; никогда клиент по умолчанию | **обязательство §9.4** — сценария у него нет намеренно: ни F2-32, ни F2-24 не утверждают, что предел выставлен, и приписывать им это значило бы объявить свойство закрытым пробой, которая о нём не спрашивает |
| **текст отказа не несёт наружу диагностики** | **сохраняется, усиливается** | §7; отдельно — предъявленное утверждение не уходит наружу целиком | F2-33 |
| **форма отказа стандартна** | **заводится** | предъявитель — чужая библиотека; ответ обязан быть тем, который она умеет прочитать, иначе отказ выглядит сбоем сети | F2-33 |
| **эндпоинт не выставлен шире, чем нужно** | **заводится** | поверхность выдачи объявляется решением: какой слушатель, какой периметр, что отвечает на прочие методы | F2-45 |
| **маршрут только на объявленный метод** | **заводится** | иной метод — отказ, несущий перечень допустимых | F2-45 |
| **потолок тела — одна реализация на дерево** | **сводится** | §1.10: третьей не заводится | F2-12 |
| **зеркальная колонка не на пути аутентификации** | **заводится с предикатом снятия** | §2.1; снимается в F4, и её самоистечение проверяемо | F2-14, F2-46 |
| **привязка токена к ключу владельца** | **сохраняется** (F1 §2.4) | значение берётся из предъявленного при выдаче **доказательства владения**, не из ключа утверждения и не выдумывается | F2-41 |
| **состав утверждений — одно объявление** | **заводится** | §2.11 | F2-42 |

## §9 Область фазы

### 9.1 В области

1. **Токен-эндпоинт платформы**: приём вида выдачи «учётные данные клиента» с аутентификацией
   клиента подписанным утверждением; форма запроса и форма ответа — стандартные; поверхность,
   метод и периметр объявлены решением (§8).
2. **Проверяющий утверждение**: форма предъявления (§4.2–§4.4), личность и адресат (§2.1, §2.2),
   время (§2.5), ключ **только** из реестра (§5), закрытый перечень алгоритмов, сверка алгоритма
   с зарегистрированным у клиента (§1.7).
3. **Однократность**: своя таблица, составной ключ, допуск одним оператором, область — флот,
   срок жизни строки равен сроку утверждения, сборщик (§6).
4. **Реестр на пути аутентификации**: чтение двух таблиц с ключевым материалом; вывод зеркальной
   колонки из пути разрешения с предикатом снятия в F4 (§2.1).
5. **Состояние субъекта на выдаче**: отозванный ключ, истёкший клиент, не-`ACTIVE` владелец —
   токена не получают (§2.10, первая половина).
6. **Отзыв сквозь обе стороны**: второй вызывающий уже посаженному F1 читателю отзыва — на пути
   выдачи; сквозная проба «выдать → отозвать → предъявить» (§2.10).
7. **Выдача токена подписантом F1**: адресат из запроса в пределах объявленного перечня, привязка
   к ключу владельца для машинного принципала, состав утверждений одним объявлением (§2.7, §2.11).
8. **Разделение двух видов подписанного** тремя независимыми признаками, оба направления (§2.6).
9. **Стражи старта** на всё, что при пустом значении означает «не сужаем» (§3 п. 11).
10. **Наблюдаемость**: счётчик у каждого исхода, единый тон наружу (§7).
11. **Настоящий вызывающий.** Эндпоинт приземляется на **живой путь**: тот же глагол, которым
    сегодня получают токен по ключу служебной учётки и по клиенту пользовательского токена, идёт
    через него — иначе эндпоинт есть подписант без производственного вызывающего, то есть тот же
    класс, из-за которого предшествующее хранилище оказалось нечитаемым (F1 §0). Требование, а не
    удобство (ban #11).

### 9.2 Явно НЕ в области — переносится в F3-F4 (§12)

Разрешение на выдачу от внешних доверенных издателей и их таблица; обновление токена; снятие
сессий входа; интерактивный вход и его церемония; снятие внешнего сервера, его базы, зеркальной
колонки и обратного вызова; выставление набора проверочных ключей наружу.

### 9.3 Почему фаза при этом production-complete (ban #14)

Каждый предмет §9.1 приземляется **целиком**: с инвариантом на уровне базы, стражем старта,
наблюдаемостью, отказом при сомнении, единым тоном и пробами названного уровня. Ни одного «пока
положительный путь», ни одного скелета, ни одной ручки «выключить проверку на время».

Сужен **объём** — какие виды выдачи переведены на наш эндпоинт, — а не **качество**: вид выдачи,
который F2 переводит, переведён полностью и безопасно в своих границах. Отложенное (§9.2) не
является частью этого вида и не оставляет в нём ни одной незакрытой стороны; по каждому пункту
довод назван отдельно в §12.

### 9.4 Обязательства перед документами и оснасткой — тем же изменением

- **12 мест зеркальной колонки** (§1.3) получают исход каждое: переписано на наш идентификатор ·
  оставлено как путь к прежнему эндпоинту с предикатом снятия в F4 · снято. Четвёртого исхода —
  «осталось как есть, потому что не заметили» — не существует;
- **два ограничения словаря алгоритма** (§1.2) сверяются с закрытым перечнем проверяющего: словарь
  базы и словарь кода обязаны совпадать, и совпадение держится гейтом, а не совпадением
  формулировок;
- **обе реализации потолка тела** (§1.10) сводятся к одной либо расхождение объявляется решением
  с причиной;
- **два рукописных стека разбора JOSE** (§1.8) получают исход каждый — тем же закрытым перечнем,
  что зеркальная колонка: сведены к пути библиотеки · оставлены как путь к прежнему контуру с
  предикатом снятия в F4 · сняты. Пропуск означает, что решения F2 (словарь алгоритмов, подмена
  алгоритма, дублирующееся имя члена, член, помеченный обязательным) доедут до одного из трёх
  проверяющих;
- **места, выводящие адресат утверждения из адреса эндпоинта** (§2.2, предикат там же), приводятся
  к решению «адресат — идентификатор издателя»; без этого §9.1 п. 11 неисполним: живой путь
  предъявляет адресат, который наш же эндпоинт обязан отвергнуть;
- **свой предел времени** выставляется на каждом внешнем вызове нового пути — чтение реестра,
  допуск однократности, чтение отзыва (§8); никогда клиент по умолчанию;
- **приёмка F1** надписывается по пунктам, чью раскладку F2 уточняет: §12 F1 строки «выдача по
  учётным данным клиента», «обмен утверждения на токен» и «обогащение утверждений» получают
  пометку со ссылкой на §2.8 настоящего документа. Пункт без пометки продолжает читаться как
  действующее утверждение против этой приёмки;
- **`polyrepo.md` и записка связи в vault**: ребро `край → iam` (и `реестр → iam`) остаётся одним
  ребром, но его предмет расширяется — по нему же идёт выдача токена. Ребро вне перечня не
  участвует ни в проверке ацикличности, ни в разборе при отладке;
- **`security.md`**: поверхность нового эндпоинта вносится в перечень поверхностей сервиса
  (`security-surface`) — какой слушатель, какой периметр, какой метод, что отвечает на прочие;
- **страница документации сервиса** описывает форму запроса, форму утверждения и **три** величины,
  которые обязан знать клиент: идентификатор издателя как адресат · потолок длительности
  утверждения · правило, по которому срок выданного токена не превышает остатка срока клиента
  (§2.10). О первых двух клиент иначе узнает отказом, о третьей — укороченным токеном, который
  примет за сбой;
- **миграции** именуются `898001_…` и далее; применённые не правятся (ban #5); всякий `DROP TABLE`
  — с ожидаемым числом строк в ведомости дропов;
- **неизменяемость срока клиента после создания** (§2.10) выражается **ограничением базы** либо,
  как допустимая замена, **гейтом дерева** с переписью и инъекцией. Без неё третья строка таблицы
  механизма возвращается к читателю на пути запроса: структурная гарантия, заменившая рантаймовый
  контроль, держится этой предпосылкой и ничем больше. До круга 3 предпосылка жила только прозой
  §2.10 — то есть у неё не было ни пробы, ни обязательства, ни строки в готовности, и фазу можно
  было объявить законченной, не построив ни того ни другого;
- **trail задачи** `obsidian/kacho/KAC/issue-898.md` заведён и обновлён; затронуты записки
  ресурсов, связей и пакетов.

## §10 Порядок работ: первым красным ложится ОДНОКРАТНОСТЬ ПОД КОНКУРЕНЦИЕЙ

Порядок не косметический. У F1 первым красным ложился **читатель**, потому что хранилище без
читателя выглядит исправным. Здесь первым ложится **конкурентная проба однократности**, и
причина того же рода: реализация «посмотреть, потом записать» **проходит все последовательные
пробы**. Написав её позже, мы построили бы поверх неё всё остальное и не заметили — положительный
путь, отказ на повторе и даже проба на двух экземплярах при последовательном прогоне были бы
зелёными.

| шаг | что | почему именно здесь |
|---|---|---|
| 1 | **красная конкурентная проба однократности** (F2-24) плюс её флотовый близнец (F2-25) | единственное свойство фазы, которое последовательная проба не отличает от сломанного |
| 2 | миграция таблицы погашения + допуск одним оператором + сборщик | схема появляется под уже красные пробы |
| 3 | красные пробы разбора формы предъявления (F2-01…F2-12) | не зависят ни от реестра, ни от выдачи |
| 4 | красные пробы личности, адресата, времени (F2-13…F2-22) | |
| 5 | разрешение клиента по реестру, вывод зеркальной колонки из пути (F2-14, F2-17) | |
| 6 | состояние субъекта и отзыв, включая сквозную пробу (F2-29…F2-32) | сквозная — после того, как выдача существует |
| 7 | выдача подписантом F1: адресат, привязка, состав утверждений (F2-37…F2-42) | |
| 8 | разделение двух видов подписанного, оба направления (F2-34…F2-36) | пишется последним намеренно: до появления **нашей** выдачи второе направление нечем произвести |
| 9 | приземление на живой путь (§9.1 п. 11), сквозные пробы, гейты, документы §9.4 | |

**Шаги 1-5 исполнимы независимо; шаги 6-9 требуют ПРИЗЕМЛЁННОЙ F1.** Это сказано числом, а не
словом: приёмка F1 несёт вердикт `✅ APPROVED`, но её **кода на `af1ce112f` в дереве нет** —
```
git grep -icl 'keyring\|signing_key\|token_signing' -- 'services/iam/internal/migrations'   # → 0
ls services/iam/internal/migrations/*.sql | sed 's|.*/||' | sort -t_ -k1 -n | tail -1        # → 800001_…, миграций 897 нет
```
Шагам 6-9 нужны наш подписант, наш `kid` и читатель отзыва на пути запроса — то есть предметы F1,
а не F2. **Предикат разблокировки:** в дереве есть миграция ключницы `897…`, подписант выпускает
токен с нашим издателем и `kid`, и сценарий F1-25 зелен. Пока предикат не выполнен, F2-32, F2-39,
F2-40 и F2-41 **неисполнимы**, и попытка объявить их зелёными означала бы зелёное о другом дереве.

Каждая пара RED→GREEN показывается фактическим выводом (ban #12). Красное обязано относиться к
**дельте**, а не к тому, что дерево уже держит.

## §11 Сценарии

Обозначения уровня пробы: **U** — модульная · **I** — интеграционная (Postgres в контейнере) ·
**E** — сквозная через край / живой контур · **G** — гейт по дереву · **B** — проба стража старта.
Каждый идентификатор трассируется в имя теста.

**Множители читаются по F1 §1.3, ось называется явно.** `E ×3` — по **поверхностям
предъявления** (REST края · нативная gRPC края · data-plane реестра); их три, и это число
принадлежит F1, а не заводится здесь заново. Множитель без оси не ставится.

**Каждое отрицание несёт положительный контроль.** Сценарий, все утверждения которого ждут
отказа, зеленеет на проверяющем, отвергающем всё, — и это не гипотеза, а способ, которым такие
пробы ломаются чаще всего.

### A. Форма предъявления и разбор

**ID: F2-01** · U
**Given** запрос на выдачу, несущий утверждение клиента
**When** объявленный вид предъявления не равен **точно** тому, что назван стандартом
**Then** запрос **отвергается**
**And** отличие только регистром либо только хвостовым пробелом — тоже отказ: сравнение
строк простое, без нормализации
**And** при точном равенстве запрос принимается — положительный контроль

**ID: F2-02** · U
**Given** запрос, в котором параметр с утверждением клиента встречается **дважды**
**When** запрос разбирается
**Then** он **отвергается** — «ровно одно утверждение» есть требование к нашему разбору, а не
описание намерения клиента
**And** отказ наступает **до** проверки подписи любого из двух значений
**And** запрос ровно с одним значением принимается

**ID: F2-03** · U
**Given** предъявленное значение, несущее **больше одной** подписи либо не являющееся компактной
последовательной формой
**When** оно разбирается
**Then** оно **отвергается**
**And** проба подаёт три разных входа: иная форма сериализации · число сегментов больше
объявленного формой · число сегментов меньше — и каждый отвергается
**And** компактная форма с ровно одной подписью принимается

**ID: F2-04** · U
**Given** заголовок утверждения, в котором имя члена встречается **дважды**
**When** заголовок разбирается
**Then** утверждение **отвергается**, и отказ наступает **до** использования любого значения
заголовка
**And** заголовок, все имена которого уникальны, принимается — положительный контроль
**And** проба подаёт дублирование **и** известного члена, **и** неизвестного: реализация,
проверяющая только известные, зелена на половине класса

**ID: F2-05** · U
**Given** заголовок, объявляющий член, помеченный **обязательным к пониманию**, которого мы не
понимаем
**When** утверждение проверяется
**Then** оно **отвергается**
**And** пометка, перечисляющая член, который мы понимаем, к отказу не приводит

**ID: F2-06** · U — **пара к F2-05, стоит рядом намеренно**
**Given** заголовок, несущий неизвестный член, **не** помеченный обязательным к пониманию
**When** утверждение проверяется
**Then** член **игнорируется**, и утверждение принимается
**And** ужесточение F2-05 до «отвергать всё неизвестное» роняет эту пробу — в этом её работа
**And** утверждение без расширений принимается — общий положительный контроль пары

**ID: F2-07** · U + G — §5, шов с соседним механизмом
**Given** утверждение, несущее в заголовке встроенный ключ (либо ссылку на набор, либо ссылку на
цепочку, либо саму цепочку) и подписанное **этим** ключом
**When** проверяющий разрешает ключ
**Then** утверждение **отвергается**: встроенный материал ключ не выбирает
**And** проба подаёт **каждый** из перечисленных членов отдельным входом, а не один за все
**And** то же утверждение, подписанное ключом, **зарегистрированным у клиента**, принимается — и
принимается по ключу из реестра
**And** гейт требует, чтобы перечень членов, из которых ключ выбираться не может, был объявлен
**в одном месте**; положительный близнец гейта — место, где выбор ключа из предъявленного
материала объявлен **намеренно** (соседний механизм доказательства владения)

**ID: F2-08** · U — **наш сценарий, внешнего прообраза не имеет** (§1.7)
**Given** клиент, у которого зарегистрирован алгоритм A (асимметричный, из закрытого словаря)
**When** предъявлено утверждение, заголовок которого объявляет алгоритм B — другой асимметричный
алгоритм того же закрытого словаря
**Then** утверждение **отвергается**, и отказ наступает **до** проверки подписи
**And** перечень допустимых алгоритмов проверяющего строится из **зарегистрированного у клиента**
значения, никогда из заголовка предъявленного утверждения
**And** утверждение, заголовок которого объявляет **зарегистрированный** алгоритм, принимается —
положительный контроль
**And** проба покрывает **обе** пары различий словаря: смена семейства и смена параметра внутри
семейства

**ID: F2-09** · U
**Given** утверждение, заголовок которого объявляет алгоритм симметричного семейства
**When** оно проверяется
**Then** оно **отвергается** отдельной явной веткой, а не общим «не нашли ключ»
**And** утверждение, объявляющее «без подписи», отвергается **своей** отдельной явной веткой
**And** утверждение, объявляющее строку вне закрытого словаря, **тоже отвергается** — «прочее»
не является корзиной приёма
**And** утверждение, объявляющее алгоритм из словаря и зарегистрированный у клиента, принимается

**ID: F2-10** · U + I
**Given** клиент, у которого зарегистрированный алгоритм — **пустое значение**
**When** предъявлено утверждение от его имени с любым алгоритмом
**Then** оно **отвергается**: пустое означает «ключа нет», а не «любой алгоритм»
**And** тот же клиент с непустым зарегистрированным алгоритмом и соответствующим ключом
аутентифицируется — положительный контроль
**And** утверждение проверяет **исход**, а не то, какая именно ветка сработала

**ID: F2-11** · U + I
**Given** запрос, объявленная длина которого превышает объявленный потолок
**When** он приходит на эндпоинт
**Then** он **отвергается**, и число прочитанных байт тела равно **нулю**
**And** запрос, объявленная длина которого в пределах потолка, читается и обрабатывается
**And** запрос, объявленной длины не несущий, но тело которого превышает потолок, **тоже
отвергается** — чтение ограничено потолком, а не только объявленной длиной
**And** утверждается **пара**: исход **и** число прочитанных байт; один код ответа этого
свойства не измеряет (§4.4)

**ID: F2-12** · G
**Given** дерево продукта
**When** гейт переписывает реализации ограничения размера тела
**Then** реализация **одна**, и новый эндпоинт пользуется ею
**And** гейт печатает **объём осмотренного** — сколько файлов прочитано, — чтобы «ноль находок»
было отличимо от «ноль прочитанного»
**And** гейт доказан инъекцией в обе стороны: возвращённая вторая реализация даёт красное с
координатой; законная единственная — молчание

### B. Личность, адресат, ключ

**ID: F2-13** · U + I
**Given** утверждение, у которого издатель и субъект **не совпадают между собой**
**When** оно проверяется
**Then** оно **отвергается**
**And** утверждение, у которого они совпадают, но не равны **нашему** идентификатору клиента,
тоже отвергается
**And** утверждение, у которого оба равны нашему идентификатору существующего клиента,
принимается — положительный контроль
**And** сравнение строк простое, без нормализации и без учёта регистра

**ID: F2-14** · U + I — §2.1
**Given** клиент, у которого в реестре есть зеркальное значение (идентификатор во внешнем сервере)
**When** предъявлено утверждение, называющее себя **этим зеркальным значением**
**Then** оно **отвергается**: зеркальное значение на пути разрешения клиента не участвует
**And** то же утверждение, называющее себя **нашим** идентификатором того же клиента, принимается
**And** отказ того же единого тона, что отказ для несуществующего клиента (§7)

**ID: F2-15** · U
**Given** утверждение, адресат которого — **адрес токен-эндпоинта**
**When** оно проверяется
**Then** оно **отвергается**: единственная принимаемая форма адресата — идентификатор нашего
издателя (§2.2)
**And** утверждение, адресат которого — идентификатор нашего издателя, принимается
**And** утверждение, несущее **несколько** адресатов, среди которых есть наш, — решение записано:
принимается, если наш среди них присутствует; проба подаёт и набор без нашего — он отвергается

**ID: F2-16** · B
**Given** конфигурация, в которой ожидаемый адресат утверждения **не задан** (пустое значение)
**When** сервис стартует в производственном режиме
**Then** старт **отвергается** с сообщением, называющим настройку и правило
**And** то же требуется при незаданном идентификаторе издателя
**And** с заданными значениями сервис стартует — иначе проба зелена на страже, не пускающем
никого
**And** сообщение не содержит ни одного значения секрета

**ID: F2-17** · I
**Given** утверждение, называющее идентификатор, которому в реестре, способном к утверждению, нет
строки
**When** оно проверяется
**Then** оно **отвергается** тем же тоном, что утверждение с несошедшейся подписью
**And** проба утверждает **побайтовое** совпадение ответа предъявителю в обоих случаях: различимый
ответ есть оракул существования (§7)
**And** утверждение, называющее существующего клиента и подписанное его ключом, принимается

### C. Время

**ID: F2-18** · U
**Given** утверждение **без** срока
**When** оно проверяется
**Then** оно **отвергается**; обязательность срока включена **явно**, а не оставлена умолчанию
библиотеки
**And** утверждение со сроком в будущем принимается — положительный контроль

**ID: F2-19** · U
**Given** утверждение **без** момента выпуска
**When** оно проверяется
**Then** оно **отвергается**: без момента выпуска потолок длительности не вычисляется (§2.5)
**And** утверждение, момент выпуска которого в будущем **сверх** объявленного допуска расхождения
часов, отвергается
**And** утверждение, момент выпуска которого в будущем **в пределах** допуска, принимается —
решение по будущему моменту выпуска записано и проверено обеими сторонами

**ID: F2-20** · U
**Given** объявленный **числом** потолок длительности утверждения
**When** предъявлено утверждение, у которого разница «срок − момент выпуска» превышает потолок
**Then** оно **отвергается**, и текст отказа во внутреннем журнале называет и потолок, и
предъявленную величину
**And** утверждение с разницей **ровно на потолке** принимается: без этого проба зелена на
проверяющем, отвергающем любую длительность
**And** утверждение с разницей меньше потолка принимается

**ID: F2-21** · U, часы — вход
**Given** управляемый источник времени
**When** он выставлен **ровно** в момент истечения утверждения
**Then** утверждение **отвергается** — граница включительно
**And** при источнике времени **ровно** в момент начала действия утверждение **принимается** —
асимметрия задана стандартом и обе её стороны утверждаются в одной пробе
**And** при источнике времени на один шаг раньше момента начала действия утверждение отвергается

**ID: F2-22** · B + G
**Given** допуск расхождения часов и потолок длительности утверждения
**When** гейт переписывает дерево
**Then** каждая величина объявлена **числом ровно в одном месте**
**And** страж старта отвергает пуск при незаданной величине и стартует при заданной
**And** ни одна ветвь проверяющего не читает системные часы напрямую: источник времени —
переданный вход (F1 §6.9)
**And** гейт доказан инъекцией в обе стороны: второе объявление той же величины даёт красное с
координатой; **две разные** величины, объявленные каждая по одному разу, — молчание

### D. Однократность

**ID: F2-23** · U + I
**Given** утверждение **без** идентификатора однократности
**When** оно проверяется
**Then** оно **отвергается**: обязательность объявлена нашей политикой явно
**And** утверждение с идентификатором однократности принимается — положительный контроль

**ID: F2-24** · I, с конкуренцией — **первая красная проба фазы** (§10)
**Given** утверждение, ещё ни разу не предъявлявшееся
**When** оно предъявляется **N параллельными** запросами
**Then** проходит **ровно один**, остальные получают ожидаемый отказ
**And** свойство держится **инвариантом базы** — уникальностью составного ключа, — и проба
подтверждает это тем, что попытка обойти прикладной путь и записать второе погашение того же
ключа напрямую тоже отвергается
**And** последовательное предъявление того же утверждения второй раз отвергается — но эта
половина **не является** доказательством: она зелена и на паре «посмотреть — записать»

**ID: F2-25** · I, два экземпляра
**Given** два **независимо построенных** экземпляра проверяющего — у каждого своё состояние в
памяти — против **одной** базы
**When** утверждение предъявляется первому, затем **второму**
**Then** второй **отвергает** его как погашенное
**And** проба строит именно два экземпляра, не переиспользуя ни одного разделяемого поля:
одноэкземплярная проба не отличает хранилище в памяти процесса от общего (§6.2)
**And** утверждение, предъявленное второму экземпляру **первым**, проходит — положительный
контроль
**And** **ответ второго экземпляра привязан к базе, а не к его памяти**: после снятия строки
погашения **напрямую в базе**, в обход прикладного пути, второй экземпляр то же утверждение
**принимает**. Без этого утверждения проба зелена на хранилище в **переменной уровня пакета** —
она не поле экземпляра, её видят оба экземпляра одного процесса, и второй отвергает погашенное
при реализации, которая ломается со второй репликой ровно так, как описывает §2.4
**And** сценарий конструируем на одном процессе пробы: предмет — **разделяемость хранилища**, а
не число операционных процессов, поэтому поднимать два пода ради него не требуется

**ID: F2-26** · I — §2.3, положительный контроль и закрытие класса сразу
**Given** клиент A предъявил утверждение с идентификатором однократности X
**When** клиент B предъявляет **своё** утверждение с тем же идентификатором X
**Then** утверждение клиента B **проходит**: область однократности сужена клиентом
**And** повтор утверждения клиента A с идентификатором X отвергается
**And** без этого сценария однократность зелена на реализации, отвергающей всё подряд, а клиент,
выбравший чужое значение, получал бы отказ в обслуживании

**ID: F2-27** · I
**Given** утверждение предъявлено и погашено
**When** его срок истекает и проходит сборщик
**Then** число строк погашения возвращается к тому, что было **до** предъявления
**And** утверждение утверждается о **числе строк**, а не о том, что сборщик вызвался
**And** повторное предъявление того же утверждения после истечения **отвергается** — по сроку;
проба утверждает исход, а не то, какая проверка сработала (§6.3)
**And** **вторая сторона §6.3 — «не короче» — утверждается тем же прогоном**: строка погашения
утверждения, срок которого **ещё не истёк**, проход сборщика **переживает**, и повторное
предъявление этого утверждения по-прежнему отвергается **как повтор, а не по сроку — различает **счётчик исхода** (§7, F2-33), а не текст ответа: ответы двух отказов побайтово совпадают by design, и попытка утверждать по ответу заканчивается снятием дискриминирующей половины**. Без второго
полупредложения «пережила» неотличимо от «истекла раньше», а все прочие утверждения сценария
проходят на сборщике, опустошающем таблицу целиком — то есть на реализации, делающей повтор
законным

**ID: F2-28** · G
**Given** функция допуска однократности
**When** гейт разбирает её
**Then** она содержит **ровно один** вызов к базе
**And** гейт находит **законного близнеца** — функцию сборщика, которой два вызова законны, — и
на ней молчит
**And** гейт печатает объём осмотренного и доказан инъекцией: возвращённая пара «посмотреть —
записать» даёт красное с координатой

### E. Состояние субъекта и отзыв

**ID: F2-29** · I
**Given** клиент, срок которого **истёк**
**When** он предъявляет корректное во всём прочем утверждение
**Then** токен **не выдаётся**
**And** клиент, срок которого не истёк, токен получает — положительный контроль
**And** клиент, у которого срок **не задан вовсе**, токен получает: незаданный срок означает
«бессрочно», и это состояние законно (§1.1)
**And** утверждается **НЕРАВЕНСТВО, а не прилагательное**: момент истечения выданного токена
**не позже** момента истечения клиента. Проба сравнивает две величины, а не характеризует одну
- на остатке **ровно равном** обычному сроку токена — граница включительно, равенство законно;
- на остатке **на шаг меньше** обычного срока — токен обязан быть укорочен ровно до остатка;
- на остатке **больше** обычного срока и у клиента без срока — выдаётся обычный срок (контроль
  против выдачи, укорачивающей всё подряд).

  Прежняя редакция утверждала «выдаётся **укороченный**» / «выдаётся **обычный**», и на этом
  зеленела **любая реализация с полем допуска**: `min(обычный, остаток) + запас`, округление
  вверх, «грация», добавленная через полгода. При малом остатке токен всё ещё «укороченный», при
  большом — «обычный», обе половины зелены, а токен, переживший клиента, существует — то самое
  состояние, которое §2.10 объявляет несуществующим. Прилагательное описывает **направление**
  величины; требуется **граница**.
**And** неравенство утверждается по **каждому** из двух путей выдачи — клиент пользовательского
токена и клиент ключа служебной учётки: пути разные (§1.1, F2-40), это разные пакеты use-case, и
ограничение, поставленное в одном, оставляет второй без него. Молчание здесь читалось бы как
«один» по конвенции самого документа, который пишет «оба» везде, где имеет в виду оба (F2-30,
F2-32, F2-40)
**And** этим закрывается предъявляющая сторона истечения клиента: токенов, переживших клиента,
**сверх допуска часов проверяющего**, не существует. Оговорка не косметическая — допуск живёт у
проверяющего на стороне предъявления, это чужой контур, и утверждение «не существует» без неё
сильнее, чем фаза способна обеспечить

**ID: F2-30** · I
**Given** словарь состояний владельца из трёх значений (§1.11)

выдаётся
**And** положительный контроль: **не** отозванный клиент при доступном авторитете и выдаёт, и
предъявляет успешно
**And** недоступный либо неопознанный ответ авторитета отзыва даёт **отказ** (fail-closed), а не
«не отозван»
**And** проба ставит вопрос **сквозь обе** стороны одним прогоном: две пробы по половине зеленеют
обе при неработающем целом

## §12 Out-of-scope: что откладывается на F3-F4 и почему это не делает F2 неполной

Общий довод применён к **каждому** пункту отдельно, а не один на всех: F2 полна **в своих
границах** (ban #14) — вид выдачи, который она переводит на наш эндпоинт, переведён целиком и
безопасно. Отложенное не является частью этого вида и не оставляет в нём ни одной незакрытой
стороны.

| # | отложено | фаза | почему F2 без этого полна |
|---:|---|---|---|
| 1 | **разрешение на выдачу от внешнего доверенного издателя** и таблица доверенных издателей | **F3** | это **другой механизм** под тем же словом (§2.8): источник доверия там — чужой издатель и его набор ключей, а не наша строка реестра. Он **потребляет** проверяющего и подписанта F2, но ничего в них не меняет: в контуре F2 всякий принимаемый ключ — наш зарегистрированный, и множества «наши клиенты» и «чужие издатели» не пересекаются by construction |
| 2 | **обновление токена** | **F3** | решение «нужно ли оно вовсе» само по себе не принято (эпик #896): возможен отказ в его пользу короткого срока и повторной выдачи. Принимать это решение внутри F2 значило бы решать вопрос **жизненного цикла** токена в фазе про **аутентификацию** предъявителя. Контур F2 при этом закрыт: клиент, у которого токен истёк, предъявляет новое утверждение и получает новый токен — путь существует и работает |
| 3 | **снятие сессий входа** | **F4** | F2 выдаёт токен **клиенту**, доказавшему владение ключом, и сессий входа не создаёт: сессия появляется у интерактивного входа, который в §9.2. Незакрытой стороны в контуре F2 не остаётся — отзыв **выданного им** токена в области и закрыт F2-32 |
| 4 | **интерактивный вход и его церемония** | **не планируется в этой линии** | вход человека идёт своим путём, API — по токену. Клиент этого вида ключевым материалом не располагает by construction (§1.1), и F2 явно отвечает на вопрос, что с ним происходит на нашем эндпоинте: отказ по отсутствию в реестре, способном к утверждению (F2-44) |
| 5 | **снятие внешнего сервера, его базы и обратного вызова** | **F4** | пока хоть один вид выдачи обслуживается прежним эндпоинтом, снятие ломает продукт. F4 последняя **по построению**, а не по остатку сил. F2 при этом не создаёт нового долга: зеркальная колонка выведена с пути аутентификации (§2.1) и несёт предикат снятия (F2-46) |
| 6 | **снятие зеркальной колонки из схемы** | **F4** | колонка остаётся **путём к прежнему эндпоинту**, а он живёт до F4. Снять её раньше значило бы сломать работающий контур ради опрятности; оставить без предиката — завести долг. Выбран третий исход: остаётся, помечена, самоистекает |
| 7 | **выставление набора проверочных ключей наружу** | **отдельное решение владельца** | F1 §2.3: обоснование исключения из требования аутентификации на слушателе опирается на **внутренность** поверхности. Это решение о **поверхности**, а не о публикаторе, и F2 его не касается ни в одну сторону — она ничего не строит в расчёте на внешнюю выставленность и ничего не делает невозможным |
| 8 | **сведение двух подписей к одной реализации** | **не планируется** | решение F1 §2.6 действует без изменений: форму диктуют разные стороны. F2 добавляет **третью** роль — проверку чужой подписи — и она тем более не сводится к чеканке своей. Общей делается **политика** (закрытый словарь алгоритмов, запрет «без подписи», требование `kid`), а не подписывающая функция |
| 9 | **перечень адресатов у самого клиента** | **вместе с колонкой, не раньше** | §1.12: колонки в схеме нет, и сценарий, требующий состояния, которого схема не допускает, не является Given (F1 §14 п. 2). Сужение поверх объявленного перечня платформы (F2-38) добавится тогда, когда появится колонка |

**Чего в этих фазах не будет вовсе:** полноценного провайдера с экраном согласия и динамической
регистрацией клиентов.

## §14 Критерии для `acceptance-reviewer`

Помимо обычных (покрытие, полнота, трассируемость, область) прошу проверить именно это:

1. **§2 отвечает на все одиннадцать вопросов решениями**, а не перечислением вариантов. Вопрос,
   получивший «зависит от», считается неотвеченным.
2. **§11 не содержит сценария, состояние которого схема не допускает.** Особо прошу проверить
   F2-38: колонки адресатов у клиентов, способных к утверждению, в схеме нет (§1.12), и сценарий
   намеренно сверяет запрос с перечнем **платформы**. Если в документе осталось хоть одно место,
   требующее перечня **у клиента**, — это неконструируемое Given, и оно возвращается автору.
3. **Каждое отрицание имеет положительный контроль.** Сценарий, где все утверждения ждут отказа,
   зеленеет на проверяющем, отвергающем всё. Прошу переписать это по документу, а не оценить
   впечатлением.
4. **§2.3 — составной ключ однократности.** Прошу судить именно решение: ключ из одного
   идентификатора утверждения выглядит проще и позволяет клиенту занимать значение у соседа.
   Сценарий F2-26 — единственное место, где это проверяется; если он покажется избыточным, довод
   §2.3 обязан быть опровергнут явно, а не сценарий снят как педантизм.
5. **§10 — порядок работ.** Прошу подтвердить, что первой красной обязана быть **конкурентная**
   проба однократности. Довод: реализация «посмотреть, потом записать» проходит **все**
   последовательные пробы, и написанная позже проба легла бы поверх уже построенного.
6. **§2.8 — расщепление предмета, а не пересмотр раскладки фаз.** Прошу подтвердить либо
   опровергнуть, что «утверждение как аутентификация клиента» и «утверждение как разрешение на
   выдачу от внешнего издателя» — два разных механизма, и что первый принадлежит F2, а второй
   остаётся F3. Если это один предмет, объём фазы меняется, и документ возвращается.
7. **§2.1 — идентификатор клиента.** Прошу судить решение «зеркальное значение не разрешает
   вовсе». Приемлемых исходов два: подтвердить либо назвать переходное окно и его предикат
   снятия. Неприемлемый исход один — «принимаем оба и разберёмся позже»: у аутентификации субъект
   с двумя именами даёт две записи журнала об одном действии и два ключа однократности на одно
   утверждение.
8. **§2.2 — адресат утверждения.** Решение отвергает адрес эндпоинта, что расходится с умолчанием
   части клиентских библиотек. Прошу подтвердить либо назвать другую единственную форму;
   неприемлемо принимать обе (`api-conventions.md` — значение выразимо ровно одним способом).
9. **§2.11 и §12 п. 2 — уточнения текста F1.** Обогащение утверждений F1 относила к F3,
   обновление токена — тоже. Первое F2 забирает (довод — контур F2 выдаёт токен для края, который
   права в токене читает), второе оставляет. Прошу судить оба уточнения именно как уточнения:
   молчаливое расхождение с приземлённой приёмкой было бы двумя местами об одном предмете.
10. **§5 — шов с соседним механизмом.** Прошу проверить, что запрет выбора ключа из заголовка
    сформулирован как требование к **общему** разборщику, а не только к нашему проверяющему:
    именно перенос доверия туда, где оно недопустимо, и есть класс, ради которого раздел написан.
11. **Документ выдерживает публикацию**: он должен читаться как перечень требований, а не как
    разбор состояния. Место, по которому посторонний восстановит уязвимое состояние, —
    **блокирующее** замечание, а не стилистическое.
12. **F2-08 помечен как наш.** Прошу проверить, что сценарий подмены алгоритма не выведен из
    чужой таблицы случаев: у реализации, выбирающей проверяющего по типу ключа, такого сценария
    нет, потому что нет предмета, — и перенос её перечня дал бы таблицу без этой защиты (§1.7).
