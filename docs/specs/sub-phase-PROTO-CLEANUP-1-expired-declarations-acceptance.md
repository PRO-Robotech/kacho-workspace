## Обзор и граница

Прогон `main`, успешно установивший отсутствие разрывов `buf` при непустом корректном
перечне, сам создаёт один PR, удаляющий истёкшие объявления из
`proto/declared-breaks.yaml`. PR сохраняет причины снятых записей и проходит обычные
проверки. До его вливания обязательная адъюдикация остаётся красной.

Принятое решение допускает окно красного ствола между вливанием исходного изменения
и вливанием cleanup PR. Автоматизируются обнаружение, подготовка PR и запуск его CI;
право слияния остаётся у существующего процесса. Автоматическое одобрение, слияние,
прямой push в `main`, изменение защиты ветви и ослабление адъюдикатора в scope не входят.
После штатного слияния cleanup PR новый main-run проверяет пустой перечень обычным
шагом. Успех этой проверки не утверждает успех остальных ярусов CI.

Это одна стадия S1, один производитель в существующей цепочке CI продукта. Новых RPC,
REST-маршрутов, схем БД, пользовательских экранов и универсальной платформы автоматизации
нет. Конвенции API и целостности применимы при появлении соответствующей поверхности;
в этой стадии проверяется наблюдаемое поведение CLI, GitHub PR и check-run.

## Проверенные входы и будущий исполнитель

На названной ревизии продукта прочитаны:

| Предмет | Существующий источник и наблюдаемая граница |
|---|---|
| Производитель находок | `.github/workflows/ci.yaml`, job `proto`, шаг `adjudicate breaking (vs main)`: `buf` 1.72.0 запускается из `proto`, сравнение с `main` репозитория GitHub, JSONL и stderr раздельно |
| Вердикт | `tools/declaredbreak/cmd/adjudicate-declared-breaks`: код 0 — согласованные находки/объявления, 1 — содержательные нарушения, 2 — проверка не смогла выполниться |
| Локальный маршрут | `./scripts/ci-local.sh proto`: тот же адъюдикатор, база `origin/main`; локальный запуск PR не создаёт |
| Реальные образцы | `tools/declaredbreak/testdata/buf-breaking-real.jsonl`; перечень на ревизии чтения содержит пять записей переноса аннотаций #2395 |
| Обязательный контекст | job `buf lint · breaking · generate-diff`; присутствие в защите `main` отдельно прочитано через GitHub API 2026-09-09 |
| События | `ci.yaml` принимает `pull_request` в `main`, `push` в `main`, `workflow_dispatch`; cleanup выполняется только для `push` в `refs/heads/main` основного репозитория |
| Текущие права | У `ci.yaml` объявлены `contents: read`, `actions: read`; API workflow permissions 2026-09-09: `default_workflow_permissions=read`, `can_approve_pull_request_reviews=false` |

Наличие уже настроенной личности, способной создать PR и запустить его CI, не
подтверждено. Это предпосылка поставки S1, которую реализация должна предъявить внешним
событием. Read-only чтение имён repository secrets 2026-09-09 вернуло пустой список;
перечень organization secrets не прочитан из-за HTTP 403. Из этого не следует
отсутствие доступной организационной личности. Значения секретов не запрашивались.
Предоставление подходящего credential — внешняя предпосылка; личный токен локального
`gh` не переносится в CI, новая система выдачи токенов в этой стадии не создаётся.
Нужны чтение репозитория, запись в служебную ветвь и создание/обновление PR
(`contents: write`, `pull-requests: write` у выбранной личности); доступ к управлению
защитой ветвей и право обходить её не нужны. Права записи доступны только производителю
cleanup на доверенном main-run, а не исполняемому содержимому входящего PR.

По [документации GitHub о GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token),
создание/обновление PR этим токеном может запустить workflows в состоянии, ожидающем
одобрения. Для требуемого автоматического запуска без дополнительного человеческого
шага допустима отдельно настроенная GitHub App installation identity либо уже
разрешённая личность с подходящим токеном. Наличие секрета не выводится из имени
переменной; значение в отчёт не попадает. Approval-required без запуска — незавершённая
поставка S1. Способ предоставления личности не меняет политику merge и защиты `main`.

Производитель cleanup добавляется рядом с существующей адъюдикацией: её ожидаемый
код 1 при истечении не должен пропускать cleanup. Код 2, невыполненный `buf`, отменённый
прогон или недоступный исходный файл не дают оснований для удаления. Предыдущий
красный check-run не переписывается успехом после создания PR.

## Входы, исходы и фикстуры

Каждая попытка называет repository, событие/ref, SHA проверяемого дерева `H`, SHA базы
сравнения `B`, SHA-256 прочитанных байтов перечня, код завершения `buf`, число разобранных
находок `F` и число прочитанных объявлений `D`. Отсутствующая величина помечается
«не получена»; вместо неё нельзя печатать 0. Отдельно фиксируются исход cleanup,
адъюдикатора и URL существующего/созданного PR.

| Исход cleanup | Условие и внешний результат |
|---|---|
| `NO_CHANGE` | Достоверно прочитаны `F=0`, `D=0`, перечень содержит `declared: []`; ветвь/PR не создаются |
| `CREATED` | `buf` завершился кодом 0, `F=0`, `D>0`, все записи корректны; создан и повторно прочитан один PR со снятием |
| `REUSED` | Подходящий открытый PR уже существует; возвращён его URL, новый PR не создан |
| `INELIGIBLE` | Получены реальные находки, либо событие не main-push; записи не удаляются |
| `INVALID_INPUT` | Вход прочитан, но форма перечня/записи некорректна; записи не удаляются |
| `CLOSED_BY_USER` | Для того же перечня найден закрытый без слияния cleanup PR; возвращены его URL и причина остановки, новый PR не создаётся |
| `NOT_EXECUTED` | Отказ производителя входа, чтения GitHub, прав, записи, проверки результата или несогласованные свидетельства; успех/нулевые находки не объявляются |

Имена исходов — контракт отчёта будущего производителя, а не существующий CLI.
Существующие exit codes адъюдикатора сохраняются. `buf` с кодом 100 и пустым JSONL,
либо с кодом 0 и непустыми находками, не служит доказательством `F=0`.

Содержательные фикстуры снимаются настоящим `buf` версии CI. `H` строится из названной
ревизии продукта. `B-old` — `d1065452d814c4a26ca460cc9d7f5cc3506cc54b`, до переноса
аннотаций. Для истёкшего близнеца база содержит те же proto, что `H`; меняется только
база, а пять объявлений и проверяемое дерево остаются прежними. Фикстура должна
показать пять сопоставленных находок на старой базе и ноль на новой; если текущий
`buf` этого не произвёл, кейс не подготовлен и не получает содержательного вердикта.
Это инструкция к подготовке RED, не отчёт о выполненном здесь прогоне.

Фикстура GitHub содержит события/ref, refs/commit SHA, список PR с head/base/state,
их тела и наблюдаемый журнал запросов. Она читает реальные схемы ответов GitHub,
не подменяет «PR создан» напечатанной строкой. Ошибки транспорта инъецируются на
границе вызова. У каждого отрицательного варианта ниже меняется один названный факт
относительно его положительного близнеца; драйвер считает эту дельту.

## Сценарии S1

### Сценарий 01: истёкший перечень получает PR, обязательный шаг остаётся красным

**ID:** PROTO-CLEANUP-1-01.

**Given** main-push основного репозитория указывает на `H`, текущий `main=H`, `B=H`;
**And** настоящий `buf` завершился кодом 0, `F=0`, корректный перечень содержит пять
записей #2395, открытого/закрытого cleanup PR для этого предмета нет;
**And** настроенная личность может создать служебную ветвь и PR, CI PR запускается.

**When** завершается шаг адъюдикации этого main-run.

**Then** адъюдикатор возвращает 1 и перечисляет пять истёкших записей;
**And** независимо от этого ожидаемого отказа cleanup получает `CREATED`: существует
ровно один PR в `main` из принадлежащей автоматике ветви того же репозитория;
**And** diff PR меняет только `proto/declared-breaks.yaml`, заменяет содержимое
`declared` на `[]`, сохраняет все комментарии и байты вне этого значения;
**And** дерево `main` до штатного merge остаётся прежним, обязательный check-run красен.

### Сценарий 02: причины снятия переживают записи, PR проходит обычный CI

**ID:** PROTO-CLEANUP-1-02.

**Given** создан PR из сценария 01.

**When** оператор читает его тело, diff и check-runs.

**Then** тело называет исходные `H`, `B`, отпечаток перечня, перепись `F=0`, `D=5`,
URL исходного main-run и permalink исходного файла на полном SHA;
**And** цитирует снятые записи со всеми `rule/path/symbol/reason/issue` и поясняющими
комментариями исходного файла: разбор последствий, которых `buf` не моделирует,
не заменён словами «устарело» или одним номером issue;
**And** причиной снятия названо отсутствие находок на новой базе, а не закрытие issue;
**And** событие создания/обновления PR действительно запустило обычный `pull_request`
CI, включая обязательный proto-контекст; ожидание approval или отсутствие check-run
не выдаётся за зелёную проверку;
**And** после штатного merge этого PR новый main-run с `F=0`, `D=0` получает код 0
адъюдикатора и `NO_CHANGE`, не создавая следующий cleanup PR.

### Сценарий 03: пустой перечень не производит пустую правку

**ID:** PROTO-CLEANUP-1-03.

**Given** мир сценария 01, единственное отличие — значение перечня `declared: []`.
**When** выполняется main-run.
**Then** `F=0`, `D=0`, адъюдикатор возвращает 0, cleanup — `NO_CHANGE`;
**And** нет нового commit, ветви или PR.

### Сценарий 04: живые и смешанные разрывы не удаляются

**ID:** PROTO-CLEANUP-1-04.

**Given** проверяемые proto и перечень сценария 01, единственное отличие входов
сравнения — база `B-old`;
**And** подготовка настоящим `buf` подтверждает пять находок, сопоставленных пяти
объявлениям, с кодом 100. Это контроль классификации результата до публикации через
GitHub; он не объявляет невозможное состояние «актуальный main одновременно H и B-old».
**When** cleanup рассматривает результат сравнения.
**Then** исход `INELIGIBLE`, весь перечень сохранён, PR не создан; адъюдикатор возвращает 0.

**Given** предыдущий живой контроль, единственное отличие — добавлена корректная запись
`FILE_NO_DELETE`, `path=symbol=kacho/cloud/validation.proto`, с причиной
«Историческое снятие разметки, уже присутствующее в обеих сравниваемых ревизиях»
и `issue=kacho#1255`; подготовка подтверждает отсутствие отдельной находки по ней.
**When** выполняется тот же вызов.
**Then** `F>0`, часть записей истекла, адъюдикатор возвращает 1;
**And** cleanup остаётся `INELIGIBLE` и не удаляет даже истёкшее подмножество.

### Сценарий 05: необъявленный разрыв не превращается в cleanup

**ID:** PROTO-CLEANUP-1-05.

**Given** живой контроль сценария 04; единственное отличие — из перечня снято одно
объявление `FIELD_SAME_TYPE` для `corelib/api/v1/operation.proto`, `symbol="87334"`.
**When** рассматривается тот же реальный вывод `buf`.
**Then** адъюдикатор возвращает 1 с необъявленным разрывом;
**And** cleanup получает `INELIGIBLE`, PR не создан, оставшиеся записи сохранены.

### Сценарий 06: негодный вход не считается пустым

**ID:** PROTO-CLEANUP-1-06.

**Given** положительный близнец — сценарий 01.
**When** в отдельном прогоне изменён ровно один вход из таблицы.
**Then** cleanup не создаёт/не обновляет ветвь или PR и называет указанный исход.

| Единственная дельта | Исход cleanup |
|---|---|
| Файл перечня отсутствует или недоступен для чтения | `NOT_EXECUTED`, `D` не получено |
| Синтаксически повреждённый YAML вместо перечня | `INVALID_INPUT`, `D` не подменяется нулём |
| Нет ключа `declared`, его значение `null`, либо ключ повторён | `INVALID_INPUT`; пустота законна только как `declared: []` |
| У одной записи отсутствует `reason`, либо он короче действующего порога Validate | `INVALID_INPUT`, запись названа |
| `buf` завершился кодом 2 с пустым stdout | `NOT_EXECUTED`, `F` не получено |
| JSONL `buf` обрезан или содержит неразбираемую строку | `NOT_EXECUTED`, `F` не получено |
| `buf` вернул 100 при пустом stdout | `NOT_EXECUTED`, противоречие кода и вывода |
| `buf` вернул 0 при непустом валидном JSONL | `NOT_EXECUTED`, противоречие кода и вывода |
| Шаг `buf` не запущен или был отменён | `NOT_EXECUTED`, `F` не получено |

Это проверка пригодности входа для автоматического удаления. Она не предполагает,
что существующий загрузчик YAML уже отвергает каждую перечисленную структурную форму.

### Сценарий 07: повторяющиеся корректные записи сохраняют свой разбор

**ID:** PROTO-CLEANUP-1-07.

**Given** мир сценария 01; единственное отличие — одна полная корректная запись
продублирована в последовательности `declared` (ключ YAML не повторён).
**When** выполняется cleanup при подтверждённом `F=0`.
**Then** прочитано шесть записей, удалены все шесть, создан один PR;
**And** его разбор содержит обе исходные записи, включая их причины, без потери
данных из-за совпадения координат; полный исходный файл доступен на названном SHA.

### Сценарий 08: последовательные и параллельные повторы сходятся к одному PR

**ID:** PROTO-CLEANUP-1-08.

**Given** PR сценария 01 открыт, текущие `main` и байты перечня прежние.
**When** main-run повторён, а затем две допустимые попытки получают один предмет
одновременно, включая случай одновременного первого создания без открытого PR.
**Then** после завершения существует ровно один открытый cleanup PR этого предмета;
**And** остальные завершившиеся попытки дают `REUSED` с тем же URL;
**And** идентичная попытка не добавляет пустые коммиты и повторные комментарии;
**And** ответ «уже существует» проверяется чтением совпадающего PR, не считается
успехом только по статусу ошибки API.

### Сценарий 09: продвижение базы требует нового доказательства

**ID:** PROTO-CLEANUP-1-09.

**Given** рассчитан кандидат сценария 01, но перед публикацией текущий `main`
продвинулся с `H` на `H2` — единственная дельта относительно обычного создания.
**When** производитель проверяет актуальность кандидата.
**Then** результат для `H` не применяется к `H2`; попытка повторно читает дерево,
перечень и сравнение для `H2`, либо завершается `NOT_EXECUTED` с причиной устаревания;
**And** при новом достоверном `F=0`, `D>0` создаётся или обновляется тот же открытый
cleanup PR на свежем основании, без второго PR и без потери новых записей/комментариев;
**And** при `D=0` новая правка не создаётся, при `F>0` снятие не выполняется;
**And** изменение head самой служебной ветви после чтения также требует повторной
сверки: чужая правка не перезаписывается принудительным push.

### Сценарий 10: закрытый PR не открывается повторно без нового предмета

**ID:** PROTO-CLEANUP-1-10.

**Given** положительный близнец — повтор из сценария 08; единственная дельта — PR
закрыт без merge, перечень и его причины побайтово прежние.
**When** тот же main-run повторён, в том числе после не затронувшего перечень commit.
**Then** `CLOSED_BY_USER` содержит URL закрытого PR; новый PR не создан и старый не
переоткрыт, обязательный адъюдикатор по-прежнему красен.

**Given** тот же закрытый PR, но перечень изменился новым содержательным объявлением.
**When** новый main-run самостоятельно подтверждает корректный перечень и `F=0`.
**Then** это новый предмет: допускается один новый cleanup PR с новым отпечатком
и ссылкой на предшествующий закрытый PR, без автоматического merge.

### Сценарий 11: чужой PR или ветвь не становятся служебными по похожему имени

**ID:** PROTO-CLEANUP-1-11.

**Given** мир сценария 01; единственная дельта — API возвращает существующий PR
с похожим заголовком, но другим base/head/репозиторием либо не принадлежащей
cleanup-автоматике ветвью (каждый вариант отдельно).
**When** производитель ищет PR перед созданием.
**Then** чужой PR не обновлён и не объявлен `REUSED`; поиск учитывает repository,
`base=main`, служебный head и проверяемое происхождение предмета;
**And** при конфликте с чужой ветвью, который нельзя безопасно разрешить в пределах
этого механизма, исход `NOT_EXECUTED`, чужие коммиты сохранены.

### Сценарий 12: отсутствие прав и неопределённость результата видны

**ID:** PROTO-CLEANUP-1-12.

**Given** положительный близнец — сценарий 01 или повтор сценария 08.
**When** один вызов чтения списка PR, записи ветви, создания PR или чтения созданного
PR возвращает отказ прав, недоступность либо неоднозначный транспортный исход.
**Then** попытка не печатает `CREATED`/`REUSED`, пока не прочитан соответствующий PR;
**And** невозможность проверки даёт `NOT_EXECUTED`, а следующий запуск сначала
ищет уже созданный PR и не дублирует его;
**And** отсутствие личности с правом записи, ожидание ручного approval CI, превышение
допустимого размера полного разбора PR или невозможность подтвердить его diff также
видны как незавершённое действие, а не как успешная очистка;
**And** секреты, токены и их содержимое в вывод не попадают.

### Сценарий 13: граница события и отсутствие запуска не публикуют cleanup

**ID:** PROTO-CLEANUP-1-13.

**Вариант `executed-check`: выполняющийся маршрут.**

**Given** входы `buf` и перечня из сценария 01, но единственная дельта — маршрут:
`pull_request` в `main`, `workflow_dispatch` либо локальный запуск
`./scripts/ci-local.sh proto` (каждый вариант отдельно);
**And** предпосылки запуска проверки выполнены, её шаг действительно исполняется.
**When** этот маршрут передаёт адъюдикатору достоверные `F=0`, `D=5`.
**Then** адъюдикатор возвращает код 1 по истёкшим записям;
**And** producer cleanup не делает запросов записи в GitHub и не получает права
записи для исполнения содержимого входящего PR; локальный маршрут не требует токена.

**Вариант `push-other-ref-no-workflow`: событие вне триггера.**

**Given** содержимое `H` сценария 01 отправлено push-событием, единственная дельта
относительно main-push — ref `refs/heads/test-cleanup-boundary`;
**And** сохранён действующий фильтр `.github/workflows/ci.yaml`: `push.branches: [main]`.
**When** GitHub обрабатывает этот push.
**Then** workflow `ci` для этого события не запущен, cleanup не публикует ветвь/PR;
**And** адъюдикатор этим событием не исполнялся: его код возврата отсутствует,
содержательный отказ или успешная проверка не объявляются.

**Вариант `entrypoint-other-ref`: самостоятельная проба входной границы.**

**Given** входы будущего entrypoint cleanup из сценария 01; единственная дельта
его аргументов — ref `refs/heads/test-cleanup-boundary` при `event=push`.
**When** тест самостоятельно вызывает этот entrypoint.
**Then** исход `INELIGIBLE`, запросов записи в GitHub ноль;
**And** отчёт называет самостоятельный вызов тестом и не выдаёт его за запуск
workflow из предыдущего варианта. Расширение push-триггеров не требуется.
