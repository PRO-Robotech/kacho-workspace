## §0 Обзор

### 0.1 Что реализуется

Оператор установки получает способ известить арендаторов о событиях, которые меняют их ресурсы
или отношения с оператором без их участия: плановые работы, аварии, вывод из эксплуатации,
приостановка, инцидент безопасности, изменение условий. Под-фаза делает шесть вещей.

1. **Ресурс «извещение» (`Notice`) в службе `notify`.** Закрытый перечень видов, жизненный цикл
   `SCHEDULED → IN_PROGRESS → COMPLETED` и ветка `SCHEDULED → CANCELLED`. Мутации возвращают
   `Operation`. Создаёт и ведёт извещение только оператор, через внутренний API.
2. **Класс писем OB («обязательство оператора»).** Письма этого класса не отключаются, не несут
   ни отписки, ни пользовательского текста, ни свободного текста оператора. Текст каждого письма
   фиксирован шаблоном вида и этапа.
3. **Контакты по категориям.** Три категории на аккаунте с переопределением на проекте, по
   умолчанию — владелец аккаунта. Хранилище, публичный API и резолвер «проект → аккаунт →
   владелец» живут в `notify` и заводятся **этой** под-фазой (Р21; основание переноса — §3 З10).
4. **Адресацию по контактам.** Получатель — действующий контакт категории вида на области
   аудитории; право получателя проверяется в момент отправки; контакт, не давший адреса,
   заменяется следующим по цепочке (Р8).
5. **Этапы писем по видам:** публикация, напоминание, перенос, отмена, начало, завершение — одна
   почтовая нить на извещение для каждого адресата.
6. **Чтение арендатором.** Арендатор читает извещения своих аккаунтов и проектов через публичный
   API, с учётом вложенности «проект ∈ аккаунт»; затронутые ресурсы он видит только те, которые
   вправе читать. Экраны консоли — NTF-6 по контракту Р22.

### 0.2 Почему это не MVP

Каждый вид извещения доведён до писем, чтения и наблюдаемости. Урезаний «пока без напоминаний»
или «пока без проверки прав» нет. Границы объёма названы в §4 со ссылкой на под-фазу, которая
держит соседний предмет.

| # | требование (дословно, 2026-09-29/30) | куда ведёт |

## §2 Решения — ратифицировать явно, ревьюер проверяет каждое

### Перенесённые решения диспетчера (приняты; здесь — их следствие для извещений)

**Д1.** `services/notify` — единственный держатель кредов почты. *Следствие:* письма извещений
идут тем же путём доставки, что и письма модулей; своего SMTP-клиента у извещений нет (Р1).

**Д2.** Звено «проверенный сертификат службы → служебный принципал `service:<имя>`» на закрытом
перечне методов. *Следствие:* метод справочника `DescribeScope` (Р10) входит в перечень звена
службы доступа; его вызывающий субъект — `service:notify`, и только он имеет прямое отношение
`reader` на объекте справочника адресов (объект — NTF-3 Р11). Учётной записи
(`service_account`) у `notify` для этого нет.

**Д3.** Подписка — единственный потоковый контракт. *Следствие:* извещение рождается в самой
`notify`, ленты источника у него нет, потока подписки не заводится (Р1).

**Д4.** Право на отправку — отношение `service:<модуль> sender на notification_namespace:<модуль>`,
вопрос на каждое письмо. *Следствие:* письма извещений идут в пространстве имён `notify`; кортеж
`service:notify sender notification_namespace:notify` — одна строка манифеста `notify` (Р1).

**Д5.** Шаблоны `<owner>/notifications/<name>/…`, общий макет, попадают в `notify` сборкой;
кастомных шаблонов установки нет. *Следствие:* 19 шаблонов извещений лежат в
`services/notify/notifications/` и собираются тем же шагом `bundle` (Р11).

**Д6.** Фундамент — в corelib. *Следствие:* класс `obligation` и правило «только владелец
`notify`» — в едином валидаторе `notify/spec`; префикс `ntc` — в `ids` (Р12, Р3).

**Д7.** Флаг генерации почтовых запросов — на прикладную службу. *Следствие:* `notify` —
не прикладной модуль; её собственное пространство имён флагом не выключается. Установка без
`notify` не имеет и API извещений (Р17).

**Д8.** Модель получателей E. *Следствие:* извещение — письмо класса «аккаунт»; адресат — контакт
категории на аккаунте с переопределением проектом, по умолчанию владелец; право получателя —
`v_get` на область в момент отправки; адресат — только `ACTIVE` пользователь с подтверждённым
адресом; внешних адресов нет. Контакты хранит `notify`, служба доступа отдаёт только права и
владельца (Р8, Р10, Р21).

**Д9.** Обязательный набор; отписка только от отключаемых видов; в письмах S и OB нет
пользовательского текста; каналы — почта и лента консоли, прочие интерфейсом. *Следствие:* Р5,
Р7, Р13; консольный канал извещения — Р20.

**Д11.** Лимиты — поставляемые значения с границами, которые проверяет страж старта. *Следствие:*
Р15, ручки Р17.

**Д12.** Прода нет — прямое переключение. *Следствие:* миграции `notify` для извещений и
контактов — сразу в итоговой форме, без обратного заполнения.

**Д13.** Порядок NTF-1 → … → NTF-5 после NTF-1. *Следствие и уточнение:* адресация извещений и
проверка пригодности контакта стоят на справочнике `Resolve` NTF-3, а правило класса `obligation`
против подавления — на NTF-4, поэтому стадия S2 садится после них; стадия S4 — после владельца
API настроек (§5). Спор о порядке — строкой возврата, не отступлением.

**Д10** (журналы модулей) к извещениям не относится: источник извещения — оператор, а не журнал.

### Решения этой под-фазы

**Р1. Извещение — ресурс `notify`; письма идут общим путём доставки в пространстве имён `notify`.**
Этап извещения (Р4) порождает строки доставки той же формы, что строки ленты источника (NTF-1),
в базе `notify`, в той же транзакции, что фиксирует этап. Дальше — общий конвейер: `ResolveSend`
(Д4), справочник адресов (NTF-3), рендер, SMTP, словарь исходов.
*Основание:* ТВ1 (одна точка отправки), ТВ4 (поддержка: один путь, не два).

**Р2. Поверхности три и не пересекаются.**
- `kacho.cloud.notify.v1.InternalNoticeService` — только внутренний слушатель `:9091`, REST —
  только блоком `*InternalAddr` края: `Create`, `Get`, `List`, `Update`, `Start`, `Complete`,
  `Cancel`. Метода `Delete` нет (Р14).
- `kacho.cloud.notify.v1.NoticeService` — публичный, только чтение: `List` (по проекту),
  `ListByAccount`, `Get` (по проекту), `GetByAccount`.
- `kacho.cloud.notify.v1.ContactService` — публичный: `List`, `Set`, `Delete` (Р21).
- Пути: внутренние `POST /notify/v1/internal/notices`, `GET|PATCH /notify/v1/internal/notices/{noticeId}`,
  `GET /notify/v1/internal/notices`, `POST /notify/v1/internal/notices/{noticeId}:start|:complete|:cancel`;
  публичные `GET /notify/v1/notices?projectId=`, `GET /notify/v1/notices:listByAccount?accountId=`,
  `GET /notify/v1/notices/{noticeId}?projectId=`, `GET /notify/v1/notices/{noticeId}:getByAccount?accountId=`;
  `GET /notify/v1/contacts?accountId=|?projectId=`, `PATCH /notify/v1/contacts`,
  `DELETE /notify/v1/contacts?accountId=|?projectId=&category=`.
- Мутации возвращают `Operation`; `done` = изменение закоммичено, и только это (письма не ждут).
*Основание:* ban06, ban09; `.claude/rules/security.md` §«Internal-vs-external (ban #6)».

**Р3. Идентификатор `ntc-<17 символов crockford>`.** Префикс `ntc` вносится в
`hyphenFormPrefixes` corelib; `notify` чеканит `ids.NewHyphenID`. Неверная форма в публичном и
внутреннем `Get` — `INVALID_ARGUMENT` `invalid notice id '<X>'` первым стейтментом.
*Основание:* `api-id-newid`, `api-hyphen-prefix`, `api-malformed-id-sync`.

**Р4. Виды, поля, начальное состояние и этапы писем — закрытая таблица.**

| вид `kind` | `startsAt` | `endsAt` | начальное состояние | категория контакта | этапы с письмом |
|---|---|---|---|---|---|
| `MAINTENANCE` | обязателен, `> now` | обязателен, `> startsAt` | `SCHEDULED` | `OPERATIONS` | `scheduled`, `reminder`, `rescheduled`, `cancelled`, `completed` |
| `OUTAGE` | запрещён (ставит сервер = момент создания) | запрещён | `IN_PROGRESS` | `OPERATIONS` | `started`, `resolved` |
| `DECOMMISSION` | обязателен (срок), `> now` | запрещён | `SCHEDULED` | `OPERATIONS` | `scheduled`, `reminder`, `rescheduled`, `cancelled`, `completed` |
| `SUSPENSION` | запрещён (ставит сервер) | запрещён | `IN_PROGRESS` | `ACCOUNT_LEGAL` | `started`, `lifted` |
| `SECURITY_INCIDENT` | запрещён (ставит сервер) | запрещён | `IN_PROGRESS` | `SECURITY` | `opened`, `closed` |
| `TERMS_CHANGE` | обязателен (вступление в силу), `> now` | запрещён | `SCHEDULED` | `ACCOUNT_LEGAL` | `scheduled`, `rescheduled`, `cancelled` |

- `now` — часы `notify` в момент обработки запроса; «`> now`» строго.
- **Тексты отказов формы — закрытый перечень, все `INVALID_ARGUMENT`, синхронно, до записи:**
  - поле, запрещённое видом: `"<field>: not allowed for kind <KIND>"`;
  - обязательное и незаданное (включая `kind`): `"<field>: required"`;
  - `startsAt` не в будущем (на `Create` и `Update`): `"startsAt: must be in the future"`;
  - `endsAt` не позже `startsAt`: `"endsAt: must be after startsAt"`;
  - больше 50 затронутых ресурсов: `"affectedResources: at most 50 items"`;
  - тип затронутого ресурса вне перечня: `"affectedResources[<i>].type: <type> is not a tenant resource type"`;
  - формы аудитории — Р10.
- `affectedResources` (не больше 50 ссылок `{type, id}`, порядок значим — как в запросе) допустимы
  только у `MAINTENANCE`, `OUTAGE`, `DECOMMISSION`. Тип — из **закрытого перечня 18 типов ресурса
  арендатора** (§1.3): `vpc_network`, `vpc_subnet`, `vpc_security_group`, `vpc_route_table`,
  `vpc_address`, `vpc_gateway`, `vpc_network_interface`, `vpc_cidr_group`, `compute_instance`,
  `compute_placement_group`, `nlb_network_load_balancer`, `nlb_target_group`, `nlb_listener`,
  `registry_registry`, `registry_repository`, `storage_volume`, `storage_snapshot`,
  `storage_image`. Перечень — константа контракта; новый тип ресурса арендатора дописывается в
  него правкой контракта, префиксом он не выводится.
- Письмо этапа `started`/`opened` уходит при создании; этапа `scheduled` — при создании; `reminder`,
  `completed`, `resolved`, `lifted`, `closed`, `cancelled`, `rescheduled` — по Р5.
*Основание:* ТВ4 (простота: вид задаёт всё остальное, выбора у оператора нет), `api-accepted-ignored`
(поле, которое вид не читает, отвергается, а не игнорируется).

**Р5. Переходы, их отказы и их письма.**

| глагол | из | в | допустим для | письмо этапа | поле момента |
|---|---|---|---|---|---|
| `Start` | `SCHEDULED` | `IN_PROGRESS` | `MAINTENANCE`, `DECOMMISSION`, `TERMS_CHANGE` | нет | `startedAt` |
| `Complete` | `IN_PROGRESS` | `COMPLETED` | все виды | `MAINTENANCE`/`DECOMMISSION` → `completed`; `OUTAGE` → `resolved`; `SUSPENSION` → `lifted`; `SECURITY_INCIDENT` → `closed`; `TERMS_CHANGE` → нет | `completedAt` |
| `Cancel` | `SCHEDULED` | `CANCELLED` | `MAINTENANCE`, `DECOMMISSION`, `TERMS_CHANGE` | `cancelled` | `cancelledAt` |
| `Update` | `SCHEDULED` | `SCHEDULED`, `revision + 1` | `MAINTENANCE`, `DECOMMISSION`, `TERMS_CHANGE` | `rescheduled` | — |

- **Канал отказа перехода — синхронный статус вызова.** Переход — один оператор записи с условием
  на ожидаемое состояние в транзакции самого запроса; эта же транзакция записывает `Operation`
  (сразу `done=true`). Ноль затронутых строк — ответ вызова `FAILED_PRECONDITION`
  `"Notice <id> is <STATE>, expected <EXPECTED>"`. Закрытый словарь `reason` (`api-reason-token`)
  токена для состояния **своего** ресурса не содержит, и эта под-фаза его не заводит: отказ
  перехода `reason` не несёт, проба утверждает тройку «HTTP `400` + `code = 9` + точный
  `message`». **`Operation` при отказе не создаётся**, и ни `Operation.result.error`, ни поллинг
  в этом отказе не участвуют. Глагол,
  недопустимый для вида, — так же синхронно `FAILED_PRECONDITION`
  `"Notice <id> of kind <KIND> does not support <Verb>"`.
- Поле момента заполняется сервером в той же записи часами `notify`, с точностью до секунды;
  у вида, рождённого в `IN_PROGRESS`, `startedAt` = моменту создания. Незаполненное поле момента
  означает «такого перехода не было», и только это (`api-empty-means-empty`).
- `Update`: изменяемы только `startsAt`, `endsAt` (по таблице Р4); `kind`, `audience`,
  `affectedResources` в маске → `INVALID_ARGUMENT` `"<field> is immutable after Notice.Create"`;
  неизменяемые проверяются **до** известного набора; неизвестное поле маски → `INVALID_ARGUMENT`
  через `corevalidate.UpdateMask`. Пустая маска — полная правка: применяются все изменяемые поля
  тела, неизменяемые поля тела игнорируются (`api-mask-empty-full-patch`). Правка без изменения
  значений ревизию не повышает и этапа `rescheduled` не даёт.
- **Напоминания.** `MAINTENANCE` — одно, в `startsAt − KACHO_NOTIFY_NOTICE_REMINDER_LEAD`;
  `DECOMMISSION` — в `startsAt − 30d`, `− 7d`, `− 1d`. Моменты, уже прошедшие к публикации
  (или к переносу), не назначаются. Перенос пересчитывает несостоявшиеся напоминания; отмена и
  начало снимают их.
- Письма этапа, не отправленные к моменту, когда этап стал неактуален (отмена, начало, перенос
  до напоминания), закрываются исходом `SUPERSEDED` и не отправляются.
*Основание:* ban10 (CAS на уровне базы), `api-mask-*`, ТВ6 (ни одного устаревшего письма);
синхронный отказ — чтобы у отказа был один канал и одна форма на всех пяти глаголах.

**Р6. Письмо несёт минимум: вид, этап, моменты, ссылку.**
- Атрибуты письма: `startsAt`, `endsAt` (тип `timestamp`), `link` (тип `path`). Момент выводится в
  UTC в форме `YYYY-MM-DD HH:MM UTC` на любой локали: у получателя нет часового пояса в профиле, а
  однозначная запись важнее привычной (§3 З9).
- `link` = `/notices/<noticeId>?accountId=<A>` либо `/notices/<noticeId>?projectId=<P>`, где
  область — та, по которой этот адресат прошёл справочник на этом этапе (Р8). Идентификатор
  области в ссылке — единственный идентификатор арендатора в письме; адресат вправе её читать
  (`v_get` проверен справочником).
- Имени аккаунта или проекта, идентификаторов затронутых ресурсов, имени оператора и свободного
  текста в письме нет: `notify` имён не получает, а шаблон класса `obligation` иных атрибутов не
  объявит (Р12).
- Причина письма — фиксированная строка шаблона: «Вы получили письмо как контакт категории
  «<категория>» аккаунта или проекта, либо как владелец аккаунта, если контакт не назначен».
- Затронутые ресурсы арендатор видит только в `NoticeService.Get`, с сужением по `v_get` (Р16).
*Основание:* ТВ4 и Д8 («письма аккаунта несут минимум сведений»): письмо пересылают, консоль —
нет; письмо без перечня ресурсов не требует проверки прав на каждый ресурс при каждой отправке.

**Р7. Класс OB не отключается — и это держат два места, каждое своим построением.**
- **Доставка.** Раскрытие этапа извещения (Р8) порождает строки доставки без обращения к
  настройкам отключения: у раскрытия нет входа «настройки», и выключить письмо `obligation`
  настройкой нечем. Держит проба NTF5-80.
- **Настройки.** Шаблоны извещений объявлены классом `obligation`; отключаемость вида выводится из
  класса шаблона в сборке (NTF-4 Р6). От владельца API настроек эта под-фаза требует ровно одну
  клетку: правка ячейки `entries.notify.<шаблон>.<канал>` вида класса `obligation` →
  `INVALID_ARGUMENT` с этим путём в `message`; «отключить весь модуль `notify`» ячеек
  `obligation` не затрагивает. Форма пути — NTF-6 Р3. Держат пробы NTF5-78, NTF5-79 — на API
  владельца настроек, стадия S4 (§5).
- Заголовка `List-Unsubscribe` у письма класса `obligation` нет (замыкает NTF-4 Р6).
*Основание:* Д9, ТВ5: пользователь глушит отключаемое, а не обязательство оператора.

**Р8. Адресация: область → цепочка кандидатов → субъект → адрес.**
- Область получателя — элемент аудитории извещения: аккаунт, проект либо каждый аккаунт при
  «все аккаунты» (Р10).
- **Цепочка кандидатов области** для категории вида (Р4): для проекта `P` аккаунта `A` —
  контакт `P`, затем контакт `A`, затем владелец `A`; для аккаунта `A` — контакт `A`, затем
  владелец `A`. В цепочку входят только **заданные** контакты; владелец — всегда (Р10, Р21).
- Кандидаты проверяются по порядку справочником адресов NTF-3:
  `Resolve{namespace=notify, subject, resource_ref=<account:A | project:P>, relation=v_get}`.
  Первый кандидат с исходом `ADDRESS` — адресат области. Кандидат с терминальным исходом
  (`AUDIENCE_DENIED`, `NO_CONFIRMED_ADDRESS`, `SUBJECT_NOT_FOUND`) получает закрытую своим исходом
  строку доставки, и проверяется следующий. Исход `UNAVAILABLE` и отказы вызова — клетки NTF-3 Р10
  без изменений: строка откладывается, к следующему кандидату раскрытие не переходит.
- Область, в которой ни один кандидат не дал адреса, увеличивает
  `notify_notice_unaddressed_total{kind,stage}` (Р19): обязательство, не дошедшее ни до кого,
  видно оператору.
- Адресат одного этапа — субъект, а не пара «субъект × область»: субъект, ставший адресатом хотя
  бы одной области аудитории, получает **одно** письмо на этап (инвариант уникальности в базе
  `notify` по `(noticeId, stage, revision, subject)`); строка хранит область, по которой субъект
  стал адресатом первой, — она идёт в ссылку письма (Р6).
- Получатели пересчитываются на каждом этапе: контакт, пригодность и право — на момент отправки
  этапа (Д8).
- Адресат — только пользователь `ACTIVE` с подтверждённым адресом; учётная запись службы и группа
  адресатами не бывают (исход справочника `NO_CONFIRMED_ADDRESS`, §3 З8).
*Основание:* Д8; ТВ4 (безопасность: обязательство не теряется из-за устаревшего контакта —
следующий по цепочке владелец его получит).

**Р9. Извещение публикует только оператор, явно; из состояния инфраструктуры оно не выводится.**
Ни флаг зоны, ни событие обслуживания машины, ни метрика извещения не создают.
*Основание:* ТВ4 — автоматический вывод текста для арендатора из сырого флага администратора
даёт письма, которых оператор не видел; простота — один источник, оператор.

**Р10. Аудитория и справочник областей.**
- Аудитория — ровно одна из форм: `allAccounts=true`; `accountIds` (1…100); `projectIds` (1…100).
  Пустая → `INVALID_ARGUMENT` `"audience: required"`; больше 100 → `INVALID_ARGUMENT`
  `"audience.<field>: at most 100 items"`; две формы сразу → `INVALID_ARGUMENT`
  `"audience: exactly one of allAccounts, accountIds, projectIds"`.
- `allAccounts` запрещён для `SUSPENSION` → `INVALID_ARGUMENT` `"audience.allAccounts: not allowed for kind SUSPENSION"`.
- **`DescribeScope`** — новый метод справочника службы доступа
  `InternalNotificationRecipientService.DescribeScope{accountId | projectId}` →
  `{exists, accountId, ownerUserId}`: для аккаунта — он сам и его владелец (`owner_user_id`,
  §1.3); для проекта — его аккаунт и владелец этого аккаунта. Имён, меток и иных полей в ответе
  нет. Несуществующая область → `exists=false`, прочие поля пусты.
- Существование каждой области аудитории проверяется при `Create` вызовом `DescribeScope`. Нет →
  `FAILED_PRECONDITION`, `reason=PEER_RESOURCE_MISSING`, `metadata={resource_type, resource_id}`;
  служба доступа недоступна → `UNAVAILABLE`, `reason=PEER_UNAVAILABLE`, извещение не создаётся.
  Формы чужого идентификатора `notify` не проверяет (`api-format-check-own-only`). Для каждого
  проекта аудитории `notify` сохраняет его `accountId` вместе с извещением (Р16).
- **Кэш.** Пары «проект → аккаунт» и «аккаунт → владелец» неизменяемы (§1.3), поэтому `notify`
  хранит ответ `DescribeScope` без срока; промах — вызов. Удалённая область кэш не портит:
  письмо по ней закроет справочник `Resolve` (`SUBJECT_NOT_FOUND`/`AUDIENCE_DENIED`).
- **`ListAccounts`** — второй новый метод того же справочника,
  `ListAccounts{pageToken, pageSize}` → только идентификаторы аккаунтов, курсором. Им `allAccounts`
  раскрывается при каждом этапе. Позиция курсора этапа хранится в базе `notify`; недоступность
  службы доступа приостанавливает раскрытие, не теряя позиции.
- **Ограждение обоих методов.** Внутренний слушатель службы доступа, без HTTP-привязки, тем же
  ограждением, что `Resolve` (NTF-3 Р11): звено NTF-1 Р2 даёт субъекта `service:notify` только
  на точном SAN `notify` и только на методах перечня; затем `Check(service:notify, reader,
  <объект справочника адресов>)` — прямое отношение, без подстановки и каскада. Вызов с иным
  сертификатом → `PERMISSION_DENIED`.
*Основание:* §1.4 — перечисление всех аккаунтов пообъектным списком невозможно, а облачное чтение
для `notify` недопустимо; `consumer-validates-by-owner`, `crossdomain-refusal-codes`,
`api-lane-peer-validate`; Д2. Ответ без имён — минимум, нужный для адресации.

**Р11. Девятнадцать шаблонов — в `services/notify/notifications/notice-<kind>-<stage>/`.**
`MAINTENANCE` ×5, `OUTAGE` ×2, `DECOMMISSION` ×5, `SUSPENSION` ×2, `SECURITY_INCIDENT` ×2,
`TERMS_CHANGE` ×3 = 19. У каждого тело на каждой локали закрытого набора, действующего в
установке (NTF-1 / NTF-3); эталон `.eml` и превью — на каждую локаль.
*Основание:* Д5, ТВ2.

**Р12. Валидатор `notify/spec` знает класс `obligation` и его ограничения.**
- шаблон класса `obligation` у владельца, отличного от `notify`, → отказ сборки с именем владельца
  и шаблона;
- атрибут шаблона класса `obligation` типа, отличного от `timestamp` и `path`, → отказ сборки с
  именем атрибута;
- у класса `obligation` нет ключа `limits` отключения и нет отписки.
*Основание:* ТВ3 — модуль не может объявить неотключаемое письмо; ТВ4 — пользовательскому и
операторскому тексту в OB-письме неоткуда взяться.

**Р13. Почтовая нить — на пару «извещение × адресат».**
- Каждое письмо несёт **свой** `Message-ID`:
  `<ntc-…-<stage>-<revision>.<ключ строки доставки>@<домен отправителя установки>>`, где ключ
  строки доставки — непрозрачный идентификатор строки в базе `notify` (не адрес и не
  идентификатор субъекта). Двух писем с одним `Message-ID` не бывает.
- Корень нити адресата — первое **отправленное** (`SENT`) письмо этого извещения этому субъекту.
  Каждое следующее письмо того же извещения тому же субъекту несёт `In-Reply-To` = `Message-ID`
  корня и `References` с ним же. Письмо, у которого корня ещё нет, само становится корнем и этих
  заголовков не несёт.
- Тема — фиксированная для вида, без переменных частей.
*Основание:* ТВ4 для пользователя: одна нить «запланировано → напоминание → завершено»;
уникальный `Message-ID` — требование самой почты (RFC 5322 §3.6.4).

**Р14. Удаления нет; хранение ограничено сроком.** Извещение — запись обязательства оператора.
Извещение в `COMPLETED`, чей `completedAt`, либо в `CANCELLED`, чей `cancelledAt` старше
`KACHO_NOTIFY_NOTICE_RETENTION`, удаляет подметальщик `notify` вместе с этапами и строками
доставки; до этого оно видно в `Get`/`List`. Извещение в `SCHEDULED` или `IN_PROGRESS`
подметальщик не трогает при любом возрасте.
*Основание:* ТВ4 (поддержка: нет операции, стирающей след обязательства), ограниченный срок
данных.

**Р15. Лимиты OB: откладывают, не теряют.**
- Потолок писем класса `obligation` на адрес — `KACHO_NOTIFY_OB_PER_ADDRESS_DAILY` за скользящие
  24 ч, поперёк всех извещений; сверх потолка письмо **откладывается** до освобождения окна
  (исход `DEFER(ob_address_ceiling)`), а не отбрасывается. Сетка на адрес NTF-1/Д11 для классов
  `security` и `notice` письма `obligation` не считает и ими не расходуется; потолок `obligation`
  письма `security` и `notice` не задерживает.
- Темп потока писем `obligation` всей установки — `KACHO_NOTIFY_OB_STREAM_PER_MINUTE`; сверх
  темпа — `DEFER(ob_stream_pace)`.
- Подавление NTF-4: письмо `obligation` подавляется только записью области `ALL_CLASSES`
  (`HARD_BOUNCE`); записи областей `NOTICE` и `NOTICE_TEMPLATE` (жалоба, мягкие отказы, отписка)
  его не затрагивают.
*Основание:* ТВ6 (ограничение объёма при захвате учётки оператора — потолок на адрес), Д11,
Д9 (обязательство не глотается жалобой).

**Р16. Публичное чтение — с учётом вложенности «проект ∈ аккаунт».**
- `List` (`projectId=P`, `P ∈ A`): извещения, в аудитории которых `P`, **или** `A`, **или**
  `allAccounts`. `ListByAccount` (`accountId=A`): извещения, в аудитории которых `A`, **или** любой
  проект аккаунта `A`, **или** `allAccounts`. То же правило — у `Get`/`GetByAccount`.
- Аккаунт проекта `P` для `List`/`Get` `notify` берёт из кэша `DescribeScope` (Р10); промах при
  недоступной службе доступа → `UNAVAILABLE`, `reason=PEER_UNAVAILABLE`, HTTP `503`, пустой
  страницы вместо отказа нет. Аккаунт проектов аудитории сохранён при `Create` (Р10), поэтому
  `ListByAccount` службу доступа не зовёт.
- Край проверяет `viewer` на области запроса (`scope_extractor`), как у списков модулей.
- **Публичная проекция** (`List`, `ListByAccount`, `Get`, `GetByAccount`): `id`, `kind`,
  `category`, `state`, `startsAt`, `endsAt`, `startedAt`, `completedAt`, `cancelledAt`,
  `createdAt`, `updatedAt`; `Get`/`GetByAccount` — плюс `affectedResources`, суженные по `v_get`
  вызывающего на каждый ресурс (`InternalIAMService.Check`, не больше 50 проверок, параллельно в
  бюджете запроса), в порядке, заданном оператором. Аудитории, счётчиков доставки, автора и
  напоминаний в публичной проекции нет; `affectedResources` в `List` не заполняется. Всё это
  названо в комментариях полей контракта (`api-projection-says`, `api-field-two-questions`).
- Извещение, не видимое из области запроса по правилу выше, → `NOT_FOUND` `"Notice <id> not found"`,
  побайтно как несуществующее.
- Порядок — курсор `(createdAt, id)` по возрастанию; `pageSize` 0→50, максимум 1000; мусорный
  `pageToken` или `pageSize` вне `[0..1000]` → `INVALID_ARGUMENT` до любой иной работы.
*Основание:* Д8 (право чтения = `v_get`), `containment-transitive` (выдача на аккаунте видит
объект проекта этого аккаунта, и обратное для объекта аккаунта: читатель проекта видит
обязательство, адресованное его аккаунту), `sec-page-then-check`, `api-pagination-*`.

**Р17. Посадка.** `notify` с API извещений и контактов — боевая посадка NTF-1 (mTLS,
`sslmode=require`, RS256, ≥2 реплики, PDB). Ручки этой под-фазы — без умолчаний, со стражем старта:

| ручка | граница | поставляемое значение (values установки) |
|---|---|---|
| `KACHO_NOTIFY_NOTICE_REMINDER_LEAD` | `[1h, 168h]` | `24h` |
| `KACHO_NOTIFY_OB_PER_ADDRESS_DAILY` | `[4, 50]` | `10` |
| `KACHO_NOTIFY_OB_STREAM_PER_MINUTE` | `[60, 6000]` | `600` |
| `KACHO_NOTIFY_NOTICE_RETENTION` | `[2160h, 43800h]` | `9600h` |

Не задана либо вне границы → отказ старта с именем ручки (`sec-no-silent-default-for-guarded-knob`).
*Основание:* Д11, ban16.

**Р18. Оператор — `system_admin` на `cluster:cluster_root`; мутации — со ступенью `acr ≥ 2`.**
- Мутации `InternalNoticeService` — `required_relation = system_admin` на `cluster`,
  `required_acr_min = "2"`; чтения — `system_viewer`.
- **Внутренняя проекция** (`InternalNoticeService.Get`/`List`) — публичная плюс `audience`,
  `affectedResources` без сужения, `createdBy` (субъект оператора), `revision`, `reminders` и
  счётчики доставки по этапу и исходу. `reminders` — несостоявшиеся назначенные напоминания
  `{at, stage}`, упорядочены по `at` по возрастанию; состоявшиеся и снятые в поле не входят;
  у вида без напоминаний и у извещения не в `SCHEDULED` поле пусто.
*Основание:* `sec-read-viewer-mutation-admin`, `sec-both-listeners-same-rules`; ТВ4 — публикация
массового письма от доверенного отправителя требует второго фактора.

**Р19. Наблюдаемость.**
- `notify_notice_letters_total{kind,stage,outcome}` — счётчик исходов писем;
- `notify_notice_fanout_pending{kind,stage}` — этапы, раскрытие которых не завершено;
- `notify_notice_overdue{kind}` — извещения в `SCHEDULED`, чей `startsAt` прошёл; тревога при `> 0`
  дольше 15 минут;
- `notify_notice_unaddressed_total{kind,stage}` — области этапа, в которых ни один кандидат не дал
  адреса (Р8); тревога при росте;
- `notify_ob_deferred_total{reason}` — отложенные письма `obligation` (`ob_address_ceiling`,
  `ob_stream_pace`).
*Основание:* ban14 (observability), `intent-observability`.

**Р20. Консольный канал извещения — само извещение, а не строка личной ленты.**
Этап извещения строк в личной ленте консоли не порождает. Консоль показывает извещения чтением
`NoticeService` (баннер области и страница извещения, Р22). Одно извещение адресовано многим
арендаторам сразу; копия в ленте каждого получателя — второе хранилище того же факта, у которого
свой срок, своё сужение и свой способ разойтись с первым. Лента консоли остаётся каналом событий
ресурсов (Д8) и извещений лимитов (NTF-6, NTF6-19).
*Основание:* ТВ4 (один источник правды на факт); Д9 (канал «лента консоли» для OB исполнен
консольным представлением самого извещения). Спор с буквой Д9 — строкой возврата.

**Р21. Контакты по категориям — хранилище, API и резолвер в `notify`.**
- **Категории** — закрытый перечень `SECURITY`, `ACCOUNT_LEGAL`, `OPERATIONS`. Контакт — настройка
  области, не ресурс: своего идентификатора нет, адресуется парой «область × категория», обе
  части неизменяемы. На паре — не больше одной записи (уникальность в базе `notify`); `Set` —
  одна запись со вставкой-или-заменой по этой паре, без чтения перед записью.
- **Чтение.** `List{accountId | projectId}` → `contacts[]{category, userId, source}` — всегда ровно
  три элемента, упорядоченных по номеру категории в перечислении (`SECURITY`, `ACCOUNT_LEGAL`,
  `OPERATIONS`); `source` ∈ `PROJECT` (задан на проекте), `ACCOUNT` (задан на аккаунте),
  `DEFAULT_OWNER` (не задан — владелец аккаунта). Для проекта действующий контакт — по цепочке
  Р8 без проверки пригодности (показывается заданное, а не доставляемое). Владелец — из
  `DescribeScope` (Р10); промах кэша при недоступной службе доступа → `UNAVAILABLE`,
  `PEER_UNAVAILABLE`.
- **Правка.** `Set{scope: {accountId | projectId}, category, userId}` и
  `Delete{scope, category}` → `Operation`. `Delete` снимает заданный контакт области (для
  проекта — переопределение, для аккаунта — возврат к владельцу); снятие незаданного — успех без
  изменений.
- **Пригодность назначаемого** проверяется на `Set` у владельца: `Resolve{namespace=notify,
  subject=user:<userId>, resource_ref=<scope>, relation=v_get}`. Исход `ADDRESS` — назначение
  проходит; **любой** иной исход (субъекта нет, не пользователь, не `ACTIVE`, адрес не
  подтверждён, нет `v_get` на области) → синхронно `FAILED_PRECONDITION`,
  `reason=PEER_RESOURCE_STATE`, `message = "User <userId> cannot be a contact for this scope"` —
  одно тело для всех причин, чтобы ответ не различал «нет такого пользователя» и «не член
  аккаунта». Служба доступа недоступна → `UNAVAILABLE`, `PEER_UNAVAILABLE`, контакт не меняется.
  Адрес, полученный в ответе `Resolve`, `notify` не сохраняет.
- **Форма входа** — `INVALID_ARGUMENT`, синхронно: `"category: required"`;
  `"scope: exactly one of accountId, projectId"`; `"userId: required"`.
- **Права — у края, по области запроса** (`scope_extractor`): `List` — `viewer` на области;
  `Set`/`Delete` — `admin` на области и `required_acr_min = "2"` (подмена контакта безопасности —
  способ заглушить письма перед атакой). Отказ по ступени — `403` с вызовом
  `insufficient_user_authentication` (§1.4).
- **Со временем контакт может стать непригодным** (заблокирован, лишён права). Запись не
  снимается: при отправке такой кандидат закрывается своим исходом, а письмо уходит следующему по
  цепочке (Р8).
*Основание:* Д8 («контакты и подписки хранит notify; kaname — только права»); форма пути и ответа —
заказ консоли NTF-6 Р3, принятый без переименований; `db-unique`, `api-reason-token`,
`sec-authn-failures-byte-identical` (одно тело на все причины отказа пригодности).

**Р22. Контракт для консоли и ссылки письма; экраны — NTF-6.**
Консоль (NTF-6) строит из API этой под-фазы четыре представления. Эта под-фаза отвечает за их
данные, форму пути и тексты отказов; разметку, маршрутизацию и пробы браузера ведёт NTF-6.

| представление консоли | что читает | что гарантирует эта под-фаза |
|---|---|---|
| страница извещения `/notices/<noticeId>?accountId=` \| `?projectId=` (цель ссылки каждого письма, Р6) | `GetByAccount` / `Get` | ссылка любого письма ведёт на извещение, видимое адресату из области ссылки (Р8, Р16); недоступное — `404` побайтно как несуществующее |
| баннер области (проект или аккаунт) | `List` / `ListByAccount`, элементы в `SCHEDULED` и `IN_PROGRESS` | вложенность «проект ∈ аккаунт» учтена сервером (Р16) |
| экран ведения извещений оператора (консоль администратора, внутренняя поверхность края, как `ui-future/shared/src/api/cluster.ts`) | `InternalNoticeService.*` | внутренняя проекция Р18, переходы и отказы Р5 |
| контакты по категориям `/notifications/contacts` | `ContactService.*` | Р21 в форме NTF-6 Р3 |

*Основание:* ТВ7 (один ресурс кормит письма и консоль); граница «данные — здесь, экран — в
консоли» совпадает с разделением NTF-6 Р3 для прочих API `notify`.

## §5 Стадии и порядок

| стадия | что | после чего |
