## Обзор

Платформа умеет выдавать токен **машине** и не умеет выдать его **человеку**. Служебная
учётка получает предъявителя, который край принимает; человек — нет. Это не дефект
отдельного RPC: у продукта **отсутствует возможность** — интерактивный вход, в конце
которого человек держит предъявителя, пригодного для вызова API.

Следствие видно на двух уровнях. Продуктовый: тенант не может позвать API от своего имени
— ни из браузера с предъявителем, ни из CLI. Проверочный: часть e2e-набора описывает
поведение, которое **никем не предъявляется**, поэтому её утверждения либо не исполняются,
либо исполняются не от того принципала (§1.7).

Под-фаза вводит эту возможность **через iam**, потому что iam — единственный фасад к
провайдеру личности (#16). Она **не меняет модель прав**, **не понижает ни одного пола
аутентификации** и **не вводит ни одного нового решения о доступе**.

Работа делится на четыре стадии; каждая **production-complete в своих границах** и
мержится отдельно:

| Стадия | Что становится возможным | Кто это видит |
|---|---|---|
| **S1** | клиент интерактивного входа заводится, живёт и снимается **через iam** | администратор облака |
| **S2** | церемония входа паролем доводится до предъявителя, который край принимает | человек-тенант |
| **S3** | второй фактор поднимает уровень аутентификации; пол считается для **каждого** носителя | человек-тенант, чувствительные операции |
| **S4** | e2e предъявляет человека по-настоящему, и **исполнение** утверждений доказывается числами | инженер, читающий вердикт |

### 1.2 Что несёт машинно-выданный токен пользователя

`UserTokenService.Issue` (`proto/kacho/cloud/iam/v1/user_token_service.proto:34`) заводит у
провайдера клиента с `grant_types=["client_credentials"]`
(`services/iam/internal/apps/kacho/api/user_tokens/usecases.go:376`). Обогащение claims
провязано в прод (`services/iam/cmd/kacho-iam/hooks_mux.go:66`) и штампует
`kacho_principal_type = "user"` (`services/iam/internal/service/token_enrichment_service.go:532`).

Уровень аутентификации берётся из сессии
(`services/iam/internal/handler/iamhooks/token_hook_handler.go:262`), а у обмена
`client_credentials` сессии **нет** — церемонии не было. Значит уровень пуст by construction.

Освобождение от пола — ровно и только машинный принципал
(`pkg/grpcsrv/acr.go`, ветка `PrincipalTypeServiceAccount`); `user` не освобождён **никогда**.

**Итог:** признак типа принципала у такого токена **есть**; отсутствует **уровень**, и
именно он закрывает 236 записей.

### 1.3 Аудитория

Край ожидает `https://<APIDomain>` (`gateway/internal/config/config.go:597`) и отвергает
несовпадение (`gateway/internal/middleware/jwt_verifier.go:359-362`); послабление
`AllowMissingAudience` в composition root **не выставляется**
(`gateway/cmd/api-gateway/main.go:138-146`) и ключа окружения для него в дереве нет.

Аудитория выдаваемому пользователю клиенту выводится из `AudiencePrefix`
(`services/iam/internal/apps/kacho/api/user_tokens/usecases.go:428-433`), а `AudiencePrefix`
**нигде не присваивается** — в `services/iam/cmd/**` и `services/iam/internal/apps/kacho/config/**`
вхождений нет. Поля аудитории в запросе `IssueUserTokenRequest` тоже нет.

```

# пусто
```

Отсюда наблюдаемая пара: запросить аудиторию края при обмене — провайдер отвергает
(«не в белом списке», тон зафиксирован в `services/iam/internal/apps/kacho/api/sa_keys/usecases.go:177`

Единственный путь, где аудитория края прописывается явно, — bootstrap-выдача
(`services/iam/internal/apps/kacho/api/bootstrap_token/mint.go:207`), и она машинная.

### 1.4 Кто заводит клиента у провайдера

Клиент заводится **только** внутри трёх use-case'ов iam (`sa_keys`, `user_tokens`,
`bootstrap_token`), и все три жёстко задают набор: `client_credentials` либо `jwt-bearer`.
Умолчание адаптера — тоже `client_credentials`
(`services/iam/internal/clients/hydra_oauth_clients.go:139-141`).

```
git grep -n "authorization_code" 6de6bc1d -- services/ proto/ | grep -v _test | grep -v testdata
# ни одного вхождения в прод-коде iam
```

**RPC, заводящего клиента интерактивного потока, не существует.** Это и есть предмет S1.

Уточнение к постановке: набор отвергается **не** терминатором административного хопа.
Терминатор решает транспорт и поверхность не сужает; авторизации у административного API
провайдера нет by design. Отвергается набор потому, что **создателя такого клиента нет
вовсе**.

### 1.5 Чем проводится церемония

Согласие и вход проводит консоль входа (`kratos-selfservice-ui`). Её состояние по профилям:

```
git show 6de6bc1d:deploy/helm/umbrella/values.yaml            | grep -A2 "kratos-selfservice-ui:"   # enabled: false
git show 6de6bc1d:deploy/helm/umbrella/values.fe3455-prod.yaml | grep -c "selfservice\|oidc"        # 0
```

| Профиль | Консоль входа | Адрес административного хопа |
|---|---|---|
| `values.yaml` (умолчание зонта) | **выключена** | — |
| `values.dev.yaml` | включена | прямое имя провайдера, plaintext |
| `values.dev-prod.yaml` | включена | **терминатор**, https, внутренний CA |
| `values.prod.yaml` | включена | объявлен |
| `values.fe3455-prod.yaml` (боевая посадка) | **блока нет вовсе** → умолчание `false` | — |

То есть на боевой посадке церемонию **некому провести**, даже если клиент появится. Это
второй независимый разрыв, и он лечится объявлением в профиле, а не кодом.

Отдельно: у края есть обработчик интерактивного входа, но он адресован путям **другого**
провайдера, выключен во всех профилях, а секрет его клиента должен был наполнять Job,
которого в дереве **нет** (`deploy/helm/umbrella/values.dev.yaml:1064` — «удалён»). Живой
отказ ссылается на несуществующий Job. Это класс «гейт, у входа которого нет производителя»:
контроль выглядит провязанным и не может сработать ни разу. S2 обязана либо привести этот
обработчик к действующему провайдеру, либо снять его с контракта — «оставить как есть»
исходом не является (`api-conventions.md`, «принято-и-проигнорировано запрещено»).

### 1.7 Что именно не исполняется в e2e

Критерий (механический): шаг требует человеческого вызывающего, если его предъявитель —
переменная, которую боевой посев **по собственному объявлению** не может выковать машинным
путём (`tests/authz-fixtures/prodseed_all.py:38-40`, `prodseed_matrix.py:18-27`).

| Класс | Шагов | Кейсов | `pm.test` | Из них гарантированно красных |
|---|---:|---:|---:|---:|
| незасеиваемый предъявитель ступени (`jwtAccountAdminAStepUp`) | 16 | 9 | 63 | 16 |
| незасеиваемый истёкший предъявитель (`apiTokenExpired`) | 1 | 1 | 3 | 1 |
| **подытог (незасеиваемые)** | **17** | **10** | **66** | **17** |
| владелец аккаунта обязан быть человеком (`POST /iam/v1/accounts`) | 23 | 23 | 75 | — |
| **итого широкий критерий** | **40** | **33** | **141** | — |

Команда пересчёта — в §7.4.

**Три поправки к постановке, обе стороны которых проверены:**

1. «14 утверждений требуют ступени» — 14 это число **литералов** `auth="jwtAccountAdminAStepUp"`
   в исходниках кейсов; исполняемых **шагов** 16 (одна строка внутри переиспользуемого
   блока даёт три шага), утверждений в них **63**, из них 16 падают гарантированно.
2. «1 — истёкшего токена» — 1 это число **стражей**; утверждений в шаге **3**, а сама
   запись посева (`prodseed_matrix.py:27`) говорит «две», считая только тело.
3. «161 утверждение в 68 сигнатурах» — **воспроизвести не удалось ни одним критерием**
   (ближайшие срезы дают 141 и 166; 68 не получается ни как число шагов, ни как число
   кейсов). Отчёта прогона с парой 14 858/319 в дереве нет; ближайшая пара, названная
   телом коммита `032c80a7`, — 12 823 исполнения / 1090 упавших, и она относится к более
   раннему прогону. **Числами этой приёмки считаются 17/10/66 и 23/23/75**, а не 161/68.

**Отдельная находка, определяющая S4.** Страж пустого предъявителя запрос **не отменяет**:
он даёт одно падающее утверждение, снимает заголовок и **отправляет шаг анонимно**. Поэтому
остальные 49 утверждений класса (66 − 17) исполняются против **другого** принципала, а
негативные из них при этом ещё и зеленеют — анонимный вызов даёт тот же код отказа, который
кейс и ждал.

Существенно, что это **не недосмотр**: комментарий рядом со стражем сам называет этот эффект
(«проходит по неверной причине») и всё равно оставляет отправку — ради детерминированности
запроса. То есть выбран размен, у которого одна сторона названа, а вторая — нет: слот занят,
вердикт зелёный, содержания нет. S4 меняет размен, а не чинит опечатку.

## §2 Решения (ратифицировать явно — ревьюер проверяет каждое)

**Р1. Возможность выражается через iam, новым Internal-ресурсом.** Клиент интерактивного
входа заводится RPC iam, а не обращением к административному API провайдера. Обоснование —
#16 (единственный фасад) и `security.md` (административный API провайдера не аутентифицирует
никого; всякий, кто до него дотянулся, заводит клиентов). Ресурс admin-only ⇒ живёт на
`Internal*`-сервисе (:9091), REST — только на внутреннем mux, префикс `/iam/v1/internal/`
(как `internal_cluster_service.proto:52`). Ban #6.

**Р2. Аудитория — не поле запроса.** Вызывающий её не задаёт; iam штампует аудиторию края из
своей конфигурации и **эхает output-only**. Обоснование: поле, которое можно задать, но
нельзя задать неправильно, — это поле без читателя; а поле, которое можно задать
неправильно, ломает край молча. Запрет «принято-и-проигнорировано» соблюдён by construction
— принимать нечего.

**Р3. Пол аутентификации вычисляется для КАЖДОГО носителя человеческой личности.** Исход
одного и того же RPC не зависит от того, чем человек предъявился. Иначе пол — форма без
содержания на том носителе, который его не проходит.

**Р4. Ни один пол не понижается.** 26 / 210 / 64 (§1.1) — измерение, а не предмет правки.
Если после посадки церемонии какой-то пол окажется недостижим, чинится **церемония**, а не
пол. Понижение пола ради зелёного набора — запрещённый исход (`step-up-acr-sensitive-only`
уже зафиксировал, что ступень **сужена** до чувствительного набора осознанно).

**Р5. Второй фактор заводится без браузера.** Не ради удобства проверки: без этого
чувствительный набор из 26 записей не проверяется автоматически **никогда**, а оператор не
может заскриптовать ни восстановление доступа, ни заведение служебного человека. Требование
продуктовое, проверочное — следствие.

**Р6. Профиль, разворачивающий уровень личности, обязан объявлять консоль входа.** Проверка
**декларативная** — читает файлы значений, а не отрендеренный шаблон (эталон —
`gateway/deploy/token_shape_test.go`), поэтому не может пропуститься. Консоль адресует
терминатор, а не снятое имя провайдера.

**Р7. Шаг без предъявителя не отправляется.** Отсутствие креденшала делает шаг
**неисполненным**, а не «исполненным анонимно». Его утверждения попадают в вердикт как
**не исполненные** и никогда — как пройденные (§1.7).

**Р8. Что не решается здесь — не решается молча.** Открытые вопросы владельца вынесены в §6
поимённо, с числом и с двумя взаимоисключающими исходами каждый. Догадкой не заполняются.

### S1 — Клиент интерактивного входа заводится, живёт и снимается через iam

Вводится ресурс **`InteractiveClient`** (пакет `kacho.cloud.iam.v1`), плоский message:
`id` (`ic-<17 crockford>`, immutable, ban #15), `created_at`, `name`, `description`, `labels`,
`redirect_uris[]`, `post_logout_redirect_uris[]`, `client_id` (output-only, сторона
провайдера), `audiences[]` (output-only, Р2), `grant_types[]` (output-only),
`token_endpoint_auth_method` (output-only), `status`.

Сервис **`InternalInteractiveClientService`**: `Get`/`List` — sync; `Create`/`Update`/`Delete`
— `Operation` (ban #9). Только :9091, только внутренний mux.

**Сценарий 10: снятый клиент больше не проводит церемонию**

**Then** церемония **не** доходит до предъявителя: обмен отвергается
**And** предъявитель, выданный **до** снятия, край перестаёт принимать не позднее истечения его срока — что именно наступает раньше, фиксируется измерением в S2 и записывается в контракт (см. §6, вопрос 3)

**Сценарий 11: метод не виден снаружи**

**And** (положительная пара) тот же путь на внутреннем mux с машинным принципалом отвечает `200` со списком
**And** (перечислением, не образцом) перепись смонтированных маршрутов публичного mux не содержит **ни одного** пути с сегментом `/internal/`; перепись называет число осмотренных маршрутов

**Сценарий 12: человек без ступени не заводит клиента, машина заводит**
**ID:** IAM-INT-1-12

**When** он вызывает `Create` клиента интерактивного входа
**Then** `401`, тело `{"code":16,"message":"insufficient_user_authentication"}`
**And** заголовок `WWW-Authenticate` содержит `error="insufficient_user_authentication"` и `acr_values="2"`

**And** (положительная пара) машинный принципал на внутреннем листенере тот же `Create` выполняет успешно — освобождение машины от пола не даёт ему никаких прав сверх выданных, оно снимает **только** требование церемонии

> Этот сценарий доказывает отсутствие кольца: заведение клиента интерактивного входа
> не требует интерактивного входа.

### S2 — Церемония доводится до предъявителя, который край принимает

---

**Сценарий 13: личность с паролем заводится и зеркалится в iam**
**ID:** IAM-INT-1-13

**Given** посаженный стенд в production-посадке

**When** посев заводит личность с паролем у провайдера личности и выполняет вход паролем

**Then** вход завершается успешно
**And** в течение ограниченного окна `GET /iam/v1/users/{id}` находит зеркало этого человека — то есть провижининг-хук отработал
**And** (отрицательная пара) вход с неверным паролем не создаёт ни сессии, ни зеркала

---

**Сценарий 14: церемония даёт предъявителя, пригодного краю**
**ID:** IAM-INT-1-14

**Given** заведённый клиент интерактивного входа `{{icId}}` (сценарий 01)
**And** личность с паролем (сценарий 13)

**When** посев проводит церемонию: запрос авторизации → вход паролем → согласие → код → обмен кода на предъявителя

**Then** обмен возвращает предъявителя
**And** предъявитель, отправленный краю на RPC из набора с полом `1` (например `GET /vpc/v1/networks?projectId=…`), даёт `200`
**And** тот же предъявитель на RPC из набора с полом `2` (например `POST /iam/v1/serviceAccounts/{id}/keys`) даёт `401` с телом `{"code":16,"message":"insufficient_user_authentication"}`

> Пара обязательна: `200` без парного `401` не отличает «уровень доехал» от «пол не считается».

---

**Сценарий 15: принципал — именно этот человек**
**ID:** IAM-INT-1-15

**Given** предъявитель из сценария 14, принадлежащий человеку `{{userId}}`

**When** он вызывает RPC, чей ответ называет вызывающего (`GET /iam/v1/users/{{userId}}`)

**Then** `200`, и ресурс — тот самый `{{userId}}`
**And** (отрицательная пара) тот же предъявитель на `GET /iam/v1/users/{{otherUserId}}` из **чужого** аккаунта получает отказ, а не чужие данные

---

**Сценарий 16: аудитория проверяема на краю**
**ID:** IAM-INT-1-16

**Given** предъявитель из сценария 14

**When** он предъявляется краю
**Then** край его принимает (сценарий 14) — то есть аудитория совпала

**And** (отрицательная пара) предъявитель, полученный **машинным** путём выдачи персонального
токена (`UserTokenService.Issue` → обмен), краю предъявленный, получает `401` с телом
`{"code":16,"message":"token validation failed"}`
**And** этот исход зафиксирован как **сегодняшний контракт**, а не как дефект: персональный
токен не является предъявителем края до отдельного решения (§6, вопрос 1)

---

**Сценарий 17: человек создаёт свой аккаунт**
**ID:** IAM-INT-1-17

**Given** свежеаутентифицированный человек с предъявителем из сценария 14, ещё не владеющий аккаунтом

**When** он вызывает `POST /iam/v1/accounts`

**Then** `Operation.done` без `error`; последующий `Get` отдаёт аккаунт, чей владелец — **он**
**And** он же может этот аккаунт удалить (владелец — структурный источник прав на своём аккаунте, `security.md`)
**And** (отрицательная пара) машинный принципал, вызывающий `POST /iam/v1/accounts`, аккаунт **не** создаёт: у служебной учётки нет «себя-человека», и отказ приходит с названным полем, а не молча

---

**Сценарий 18: профиль без консоли входа не проходит гейт**
**ID:** IAM-INT-1-18

**Given** декларативный тест, читающий **файлы значений** профилей (не рендер)

**When** он исполняется на профиле, разворачивающем уровень личности, но **не объявляющем** консоль входа

**Then** тест краснеет и называет профиль поимённо
**And** (положительная пара) на профиле, где консоль объявлена и адресует терминатор, тест молчит
**And** тест **утверждает объём осмотренного**: печатает число прочитанных профилей и их имена — «ноль находок» отличимо от «ноль прочитанного»

---

**Сценарий 19: консоль адресует терминатор, а не снятое имя**
**ID:** IAM-INT-1-19

**Given** перепись потребителей административного хопа

**When** консоль входа объявлена адресом снятого имени провайдера
**Then** перепись краснеет и называет координату объявления

**And** (положительная пара) та же консоль, объявленная адресом терминатора, переписью пропускается
**And** запись реестра потребителей ссылается на значение, которое **реально объявлено** в профиле, — запись без объявления есть находка

---

**Сценарий 20: обработчик интерактивного входа на краю приведён к исходу**
**ID:** IAM-INT-1-20

**Given** обработчик интерактивного входа края, сегодня адресующий пути другого провайдера и выключенный во всех профилях (§1.5)

**When** выбран исход «реализовать»
**Then** обработчик адресует действующего провайдера, включён хотя бы в одном профиле, и его путь доводит человека до предъявителя из сценария 14
**And** отказ при незаполненном клиенте больше не ссылается на несуществующий Job — сообщение называет действующую причину

**When** выбран исход «снять с контракта»
**Then** обработчик и его маршрут удалены, а профильные ключи зарезервированы; ни один профиль их не объявляет
**And** (в обоих случаях) гейт перечисляет маршруты края, чей вход не имеет производителя, и краснеет на находке; проверен инъекцией: возвращённый обработчик-без-производителя ловится, законный обработчик с производителем — молчит

> Третьего исхода нет. «Оставить как есть» — это обещание возможности, которой нет
> (`api-conventions.md`).

### S3 — Ступень второго фактора и симметрия носителей

---

**Сценарий 21: второй фактор заводится без человека за экраном**
**ID:** IAM-INT-1-21

**Given** личность с паролем (сценарий 13)

**When** посев заводит ей второй фактор через публичный API провайдера личности — без браузера

**Then** заведение завершается успехом, и посев **предъявляет** его: вход с паролем и вторым фактором проходит
**And** (отрицательная пара) вход только с паролем той же личности по-прежнему проходит, но даёт **другой** уровень — что проверяется сценарием 22

> Если заведение без браузера окажется неконструируемым, **сценарий неверен, а не продукт**:
> тогда S3 не зеленеет, а 16 шагов / 63 утверждения (§1.7) остаются открытым долгом с числом
> (§5). Маска не полагается.

---

**Сценарий 22: ступень открывает чувствительный набор и не открывает лишнего**
**ID:** IAM-INT-1-22

**Given** два предъявителя одного и того же человека: `T1` (вход паролем) и `T2` (вход со вторым фактором)

**When** оба по очереди предъявляются на RPC из набора с полом `2`
**Then** `T1` → `401`, тело `{"code":16,"message":"insufficient_user_authentication"}`, заголовок `WWW-Authenticate` с `acr_values="2"`
**And** `T2` → `200`

**When** оба по очереди предъявляются на RPC из набора с полом `1`
**Then** **оба** → `200` — ступень не является платой за рутину

---

**Сценарий 23: пол не бланкетный — перечислением**
**ID:** IAM-INT-1-23

**Given** каталог прав на посаженном стенде

**When** гейт перечисляет записи по полу

**Then** числа совпадают с §1.1: `26` записей с полом `2`, `210` с полом `1`, `64` без пола, всего `300`
**And** гейт краснеет, если число записей с полом `2` **выросло** без сопровождающего решения — расширение чувствительного набора есть продуктовое решение, а не побочный эффект
**And** гейт печатает **перечень** записей с полом `2`, а не только их число

---

**Сценарий 24: исход не зависит от носителя (отказ)**
**ID:** IAM-INT-1-24

**Given** один и тот же человек **без** второго фактора, представленный краю двумя разными носителями личности

**When** каждым носителем вызывается один и тот же RPC из набора с полом `2`

**Then** оба получают **один и тот же** отказ: `401`, тело `{"code":16,"message":"insufficient_user_authentication"}`
**And** оба ответа несут заголовок `WWW-Authenticate` с одинаковым `acr_values`

---

**Сценарий 25: исход не зависит от носителя (проход)**
**ID:** IAM-INT-1-25

**Given** тот же человек **со** вторым фактором, представленный краю теми же двумя носителями

**When** каждым носителем вызывается тот же RPC из набора с полом `2`

**Then** оба получают `200`

> 24 и 25 — обязательная пара. Одно «отвергнуто» неотличимо от «носитель мёртв»; одно
> «принято» неотличимо от «пол не считается».

---

**Сценарий 26: свежесть — заявленное состояние**
**ID:** IAM-INT-1-26

**Given** каталог прав на посаженном стенде

**When** гейт перечисляет записи, объявляющие окно свежести аутентификации

**Then** их **ноль** — и это зафиксировано как сегодняшнее состояние, а не как упущение
**And** механизм свежести в коде края существует и не имеет ни одной записи-потребителя;
поэтому гейт краснеет в **обе** стороны: и когда запись появляется без решения, и когда
механизм снимают, пока запись есть

> Заявление отрицательное, поэтому оно парное по построению: обе стороны названы. Введение
> окна свежести — вне объёма (§5).

### S4 — E2E предъявляет человека по-настоящему, и исполнение доказывается

---

**Сценарий 27: посев получает человеческого вызывающего церемонией**
**ID:** IAM-INT-1-27

**Given** посаженный стенд с клиентом интерактивного входа (S1) и консолью входа (S2)

**When** боевой посев исполняется

**Then** он заполняет предъявителя человека, вошедшего паролем, и предъявителя со вторым фактором — **церемонией**, а не подделкой
**And** если церемония не прошла, посев завершается **ненулевым кодом** и называет стадию, на которой встал
**And** (отрицательная пара) посев **не** записывает ни одного значения предъявителя, полученного иначе как церемонией: гейт перечисляет источники каждого значения и краснеет на любом, чей источник — литерал или ковка харнессом

---

**Сценарий 28: шаг без предъявителя не отправляется**
**ID:** IAM-INT-1-28

**Given** кейс, чей шаг требует предъявителя, которого в окружении нет

**When** набор исполняется

**Then** шаг **не отправляется**
**And** его утверждения попадают в вердикт как **не исполненные**
**And** ни одно из них не засчитывается пройденным
**And** (положительная пара) тот же кейс с заполненным предъявителем отправляет шаг и исполняет все свои утверждения

> Это прямая правка находки §1.7: сегодня такой шаг уходит анонимно, и его негативные
> утверждения зеленеют от чужого отказа.

---

**Сценарий 29: класс исполняется, и это видно числом**
**ID:** IAM-INT-1-29

**Given** прогон боевой посадки до и после S1-S3

**When** вердикт печатается

**Then** он называет: коллекций **исполнено из скольких**, запросов, утверждений, **упавших** утверждений, **неотвеченных** запросов
**And** число **исполненных** утверждений в 10 кейсах человеческого вызывающего растёт с `0` до `66`
**And** это утверждение **отдельно** от «ноль упавших»: суита без отчётов провалена, а не зелена

---

**Сценарий 30: своя волна, а не маска**
**ID:** IAM-INT-1-30

**Given** кейсы, которым нужна церемония

**When** набор планируется

**Then** они идут **своей волной**, создающей условие (посев церемонии до старта волны)
**And** ни один из них не исключён списком, маской, `skip`, закомментированным утверждением или потерей кода возврата
**And** гейт перечисляет все механизмы исключения в дереве набора и краснеет на находке; он проверен инъекцией в обе стороны: внесённая маска ловится и называется координатой, законная конструкция той же формы — молчит

---

**Сценарий 31: взаимоисключающие исходы — не утверждение**
**ID:** IAM-INT-1-31

**Given** набор кейсов человеческого вызывающего

**When** гейт перечисляет утверждения, принимающие одновременно успех и отказ там, где заголовок кейса обещает отказ

**Then** их **ноль**
**And** гейт краснеет на внесённом таком утверждении и молчит на законной толерантности к порядку проверок (отказ по правам вместо отказа по форме) — различие проверено инъекцией обеих форм

---

**Сценарий 32: исключение живёт, пока у него есть предмет**
**ID:** IAM-INT-1-32

**Given** запись об известном красном (если она заведена)

**When** предмет записи исчез — кейс зеленеет

**Then** гейт **краснеет на самой записи**: исключение, которому больше нечего исключать, есть находка
**And** предикат снятия привязан к **внешнему** факту (исход кейса), а не к тому, что изменяет само изменение

---

**Сценарий 33: истёкший предъявитель — своя волна или счётный долг**
**ID:** IAM-INT-1-33

**Given** кейс, требующий предъявителя с истёкшим сроком

**When** волна, создающая условие (выпустить и переждать срок), существует
**Then** кейс исполняется в ней, и его 3 утверждения попадают в вердикт исполненными

**When** такой волны нет
**Then** его 3 утверждения объявлены **открытым долгом с числом** в отчёте прогона

## §4 Инварианты (MUST hold — для ревьюера)

1. **iam остаётся единственным фасадом.** Ни одна нагрузка, кроме iam и уже объявленных
   потребителей административного хопа, не заводит клиента у провайдера. Новых прямых
   потребителей под-фаза не вводит.
2. **Ни один `Internal*`-метод не появляется на публичном крае** (ban #6, сценарий 11).
3. **Ни один пол не понижен** (Р4, сценарий 23).
4. **Мутации возвращают `Operation`** (ban #9); `done` означает durability предмета мутации
   и не гейтится на видимость чего-либо ниже по течению.
5. **Уникальность имени клиента — на DB-уровне** (`UNIQUE`), не программной проверкой
   (ban #10); отказ по гонке приходит как `ALREADY_EXISTS`, а не как второй успех.
6. **Ни одного секрета в ответе, кроме одноразовой выдачи.** Клиент интерактивного входа
   публичный (обмен по коду с доказательством владения), поэтому секрета у него нет вовсе;
   если выбран конфиденциальный вариант — секрет отдаётся ровно один раз и затирается в
   `Operation.response`, как уже сделано для персональных токенов.
7. **Тон сообщений — часть контракта.** Тексты §3 меняются только тикетом.
8. **Каждый гейт под-фазы несёт проверку своей предпосылки** и утверждает объём осмотренного
   (`testing.md`).
9. **Ни один e2e-кейс не пропущен** (сценарии 30-33).

## §6 Что эта приёмка НЕ покрывает (открытые вопросы владельца)

Заполнять догадкой запрещено. По каждому — два взаимоисключающих исхода; выбор за владельцем.

**Вопрос 1. Является ли персональный токен предъявителем края?**
Сегодня `UserTokenService` выдаёт креденшал, которым **нельзя позвать API**: аудитории нет
(§1.3), уровня нет (§1.2) — закрыто 236 записей из 300. То есть выданная возможность инертна.
Исходы: **(а)** персональный токен получает аудиторию края, и владелец решает, засчитывается
ли владение долгоживущим ключом за уровень `1` (это ослабление: церемонии не было); либо
**(б)** сервис снимается с контракта с резервированием, и человек зовёт API только
предъявителем церемонии. Приёмка **не выбирает** и фиксирует сегодняшнее поведение
сценарием 16.

**Вопрос 2. Какой набор проходит обмен по коду — публичный клиент с доказательством владения
или конфиденциальный?** От выбора зависит, есть ли у клиента секрет и появляется ли ещё один
одноразовый секрет в ответе. Приёмка описывает оба варианта в инварианте 6 и не выбирает.

**Вопрос 3. Что наступает раньше при снятии клиента — отказ края уже выданному предъявителю
или истечение его срока?** Ответ измеряется в S2 и записывается в контракт (сценарий 10).
Приёмка не постулирует его заранее, потому что он зависит от настроек срока жизни, а не от
кода.

**Вопрос 4. Числа замера боевой посадки.** Пара 14 858/319 и разбивка «161 в 68 сигнатурах»
**не воспроизведены** (§1.7). Приёмка опирается на собственные измерения 17/10/66 и 23/23/75.
Если отчёт того прогона существует вне дерева — его следует приложить к тикету, и §1.7
пересчитывается **до** старта S4, а не после.

Кроме того, приёмка **не покрывает**: производительность церемонии, поведение при недоступности
провайдера личности дольше окна кэша сессии, миграцию уже выданных предъявителей, UI-часть
входа и восстановление доступа.
