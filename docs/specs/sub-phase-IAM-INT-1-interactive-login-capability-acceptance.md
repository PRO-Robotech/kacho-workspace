## Обзор

Платформа умеет выдавать токен **машине** и не умеет выдать его **человеку**. Служебная
учётка получает предъявителя, который край принимает; человек — нет. Это не дефект
отдельного RPC: у продукта **отсутствует возможность** — интерактивный вход, в конце
которого человек держит предъявителя, пригодного для вызова API.

Следствие видно на двух уровнях. Продуктовый: тенант не может позвать API от своего имени
— ни из браузера с предъявителем, ни из CLI. Проверочный: часть e2e-набора описывает
поведение, которое **никем не предъявляется**, поэтому её утверждения либо не исполняются,
либо исполняются не от того принципала (§1.7).

Под-фаза вводит эту возможность **через iam**, потому что iam — единственный фасад к
провайдеру личности (#16). Она **не меняет модель прав**, **не понижает ни одного пола
аутентификации** и **не вводит ни одного нового решения о доступе**.

**Откуда взят предмет — названо прямо.** Дорожная карта (`docs/specs/04-roadmap-and-phasing.md`,
277 строк) об интерактивном входе **молчит**: слов «интерактивный», «вход», `authorization_code`
в ней нет. Предмет выведен **из замера**, а не из плана. Это законный источник — замер боевой
посадки показывает, чего продукту недостаёт, — но он обязан быть назван, иначе под-фаза
выглядит выполнением плана, которого не существует. Следствие для координации: дорожную карту
надо дополнить этой под-фазой (§10), иначе следующий читатель сочтёт её самоволкой.

Работа делится на четыре стадии; каждая **production-complete в своих границах** и
мержится отдельно:

| Стадия | Что становится возможным | Кто это видит |
|---|---|---|
| **S1** | клиент интерактивного входа заводится, живёт и снимается **через iam** | администратор облака |
| **S2** | церемония входа паролем доводится до предъявителя, который край принимает | человек-тенант |
| **S3** | второй фактор поднимает уровень аутентификации; пол считается для **каждого** носителя | человек-тенант, чувствительные операции |
| **S4** | e2e предъявляет человека по-настоящему, и **исполнение** утверждений доказывается числами | инженер, читающий вердикт |

**RPC, заводящего клиента интерактивного потока, не существует.** Это и есть предмет S1.

Уточнение к постановке: набор отвергается **не** терминатором административного хопа.

провайдера нет by design. Отвергается набор потому, что **создателя такого клиента нет
вовсе**.

### 1.5 Чем проводится церемония — и почему единица измерения здесь решает

Согласие и вход проводит консоль входа (`kratos-selfservice-ui`). **Консоль на боевой
посадке включена и настроена.**

Свойство принадлежит **сложенному релизу**, а не отдельному оверлею. Посадка складывается
из четырёх файлов значений — три в дереве, четвёртый намеренно вне его:

```
git show bb26d905:deploy/helm/umbrella/cutover-fe3455.sh | sed -n '158,164p'
#   helm upgrade … -f values.prod.yaml -f values.fe3455.yaml -f values.fe3455-prod.yaml -f values.fe3455-ory.yaml
git check-ignore -v deploy/helm/umbrella/values.fe3455-ory.yaml   # .gitignore:22 — вне дерева by design
```

Слияние **аддитивно** (`gateway/deploy/revocation_endpoint_test.go:69` — `mergeInto`
«overlays src onto dst the way helm merges values files»), поэтому молчание позднего оверлея
ключ **не сбрасывает**. Результат складывания трёх committed-членов:

| Стек | `…kratosSelfServiceUI.enabled` | адрес административного хопа |
|---|---|---|
| `prod` | `true` | `https://…-hydra-admin-tls:4445` (терминатор) |
| `fe3455` (боевая посадка) | **`true`** | `https://…-hydra-admin-tls:4445` (терминатор) |
| `dev-prod` | `true` | терминатор |

Стек `fe3455` объявлен в дереве явно: `deployableStacks["fe3455"] = {values.prod.yaml,
values.fe3455.yaml, values.fe3455-prod.yaml}` (`gateway/deploy/revocation_endpoint_test.go:55-61`).
`values.prod.yaml:1176` включает консоль, `values.fe3455.yaml:222-224` настраивает её под хост
посадки, `values.fe3455-prod.yaml` о ней молчит — и молчание ничего не отменяет.

**Второго независимого разрыва нет.** Ранняя редакция этого документа утверждала обратное,
и ошибка была не в факте, а в **единице измерения**: свойство сложенного релиза измерялось
грепом по одному оверлею.

**Урок, который дороже правки.** В `gateway/deploy/` живут **две** идиомы, и обе честны:

- `resolveStackAt` — «merges a stack's profiles in order (the way helm does)»
  (`admin_hop_transport_test.go:38,44`) — отвечает на вопрос **«что получится у релиза»**;
- `token_shape_test.go:21-23` — «The profiles are NOT layered — `values.prod.yaml` renders
  standalone and never on top of the dev file» — отвечает на вопрос **«объявляет ли профиль
  своё сам»**, и для *его* вопроса это верно: `dev` и `prod` — альтернативы, не слои.

Выбор не той идиомы **молча отвечает на другой вопрос**. Всякая проверка этой под-фазы,
касающаяся посадки, обязана назвать свою единицу — оверлей или сложенный стек — и выбрать
идиому под неё (Р6).

Всего файлов значений в зонте — **восемь**:

```
git ls-tree --name-only bb26d905 deploy/helm/umbrella/ | grep values | wc -l   # 8
```

**Что в §1.5 действительно остаётся разрывом.** У края есть обработчик интерактивного входа,
адресованный путям **другого** провайдера; он выключен во всех профилях, а секрет его клиента
должен был наполнять Job, которого в дереве **нет**
(`deploy/helm/umbrella/values.dev.yaml:1064` — «удалён»). Живой отказ ссылается на
несуществующий Job. Это класс «гейт, у входа которого нет производителя»: контроль выглядит
провязанным и не может сработать ни разу. S2 обязана либо привести обработчик к действующему
провайдеру, либо снять его с контракта — «оставить как есть» исходом не является
(`api-conventions.md`, «принято-и-проигнорировано запрещено»). Сценарий 20.

### 1.6 Носители человеческой личности — перемерено редакцией 2

> **Редакция 1 утверждала:** «У края **два** носителя человеческой личности. Пол
> аутентификации вычисляется на одном из них. Выравнивание — предмет S3 (сценарии 24-25).»
> Это было верно на базе `bb26d905` — перемерено: у REST-входа там три метода-полосы,
> `tryKratosSession`, `tryHydraJWT` и `tryDevSecretJWT`
> (`git show bb26d905:gateway/internal/middleware/auth.go | grep -c 'func (a \*AuthInterceptor) try'`
> → 3), и последняя в боевой посадке отвергается целиком; базового удостоверения не было вовсе.
> Верным быть перестало к `0dafb250a7` (2026-08-25): пол спрашивает каждая полоса (#1201,
> #1215), а полос, устанавливающих личность, стало три (#1142). Цитата оставлена, а не снята:
> она — основание сценариев 24-25 и входного гейта S3, и без неё их правку нечем объяснить.

**Единиц две, и путать их нельзя.** *Полоса* — метод точки входа края, достижимый от неё и
записывающий личность вызывающего; её перечень выводит из дерева проба-перепись. *Носитель* —
КЛАСС удостоверения, которым человек предъявляется. Полос больше, чем носителей: одна полоса
устанавливает личность только вне боевой посадки. И у носителя меняется поставщик, не меняя
класса.

**Носители названы КЛАССОМ, а не поставщиком, — это решение, а не стиль.** У двух классов из
трёх поставщик сменяется прямо сейчас. Сессию браузера сегодня выдаёт внешний поставщик
личности; эпик `#1266` переводит её на нашу, и его подзадача `#1275` прячет носителя сессии за
порт. Подписанного предъявителя край принимает от набора издателей, куда вошёл наш (`#926`,
Ф1б). Имена методов-полос в дереве поставщика ещё называют (`tryKratosSession`, `tryHydraJWT`):
сценарий, написанный по такому имени, истёк бы вместе с поставщиком — ровно так, как редакция 1
истекла вместе с появлением третьего класса.

| класс носителя | полоса края | поверхности | уровень, который он несёт | церемония повышения |
|---|---|---|---|---|
| **сессия браузера** | `tryKratosSession` | REST | уровень сессии, объявленный её поставщиком | **есть** |
| **подписанный предъявитель** | `tryHydraJWT` | REST, нативный gRPC | уровень из утверждения токена | **есть** |
| **базовое удостоверение** — однострочный секрет; владелец человек (персональный токен вида `SECRET`) либо служебная учётка | `tryBasicCredential` | REST, нативный gRPC | константа вида `"1"` — `BasicCredentialLevel` в `gateway/internal/middleware/basic_credential_lane.go` | **нет**: уровень не поднимает ничто |
| *симметричный токен разработки* — **носителем в боевой посадке не является** | `tryDevSecretJWT` | REST, нативный gRPC | — | — |

Последняя строка не декларация: в production-посадке эта полоса отвергается целиком, и проба
это **доказывает** — требует, чтобы личность до владельца RPC не дошла, а не принимает на веру.

**Персональный токен службы доступа отдельным классом НЕ является — он приходит на край двумя
классами, по виду** (редакция 3). Выдача одна — `UserTokenService.Issue`
(`PRO-Robotech/kaname:proto/kaname/cloud/iam/v1/user_token_service.proto`, поле `credential_kind`),
а выдаваемых личности видов **два** — `SECRET` и `KEYPAIR` (редакция 4; почему не три — абзац после
таблицы):

| вид | чем предъявляется краю | класс носителя таблицы выше | уровень | чьё решение |
|---|---|---|---|---|
| `SECRET` | сама строка, `Authorization: Bearer` | базовое удостоверение | константа `"1"` | одобренная приёмка `sub-phase-BAT-1-basic-access-token-acceptance.md`: §0 («предъявляется как есть — в `Authorization: Bearer` на крае») и §2.3 («уровень удостоверения — «1», и следствие названо»); посажено `0dafb250a7`, задача #1142 закрыта |

**Третьего вида у личности нет — это запрет схемы, а не пробел посева** (редакция 4). Словарь вида
один на оба глагола выдачи и несёт `FEDERATED` (приёмка BAT-1, §2.5: «выдаваемых видов три»), но
разбит по владельцам: «федеративного вида у личности нет by construction — в её контракте нет поля,
которым он задаётся» (BAT-1, §4.1). Перечня доверенных субъектов в запросе выдачи личности нет;
он есть только у ключа служебной учётки (`trusted_subjects` в
`PRO-Robotech/kaname:proto/kaname/cloud/iam/v1/sa_key_service.proto`). Держат запрет три места
службы, сверено на `37ee8509`, `6e9b94ab` и `5303cebd`:

- **выдача** — вид личности разрешается вызовом `domain.ResolveIssuedKind(in.CredentialKind, false,

  `FEDERATED` отвергается синхронно, до записи, `INVALID_ARGUMENT` с именем поля `credential_kind`, а
  вид не названный разрешается в `KEYPAIR`. Сам отказ держит
  `TestBAT1_14_ExplicitLegacyKindIsRefusedWithTheFieldName`

- **хранилище** — ограничение `user_oauth_clients_credential_kind_ck`

- **федеративная полоса эндпоинта выдачи** — запись доверия ссылается только на ключ служебной

  (там же, `0001_initial.sql`), и разрешение пары «издатель, субъект» отдаёт клиента вида
  `AssertionClientServiceAccount` (`PRO-Robotech/kaname:internal/repo/kaname/pg/trusted_issuer_repo.go`).

§1.2 и §1.3 описывают путь этого токена на базе `bb26d905` — клиент у внешнего поставщика, пустой

поставщика у строк, выпущенных прежде, жив и описан после опыта E1–E6 (редакция 4). Прежний §6

зеркалом не остаётся либо снимается поставщик (эпик #2564); предикат остатка назвал #1121 —

**Перепись края, REST-вход — ствол платформы `41c75cb678`, прогон 2026-09-15, код 0:**

```sh

#   перепись вывода: файлов прочитано 43 · методов AuthInterceptor 37 · достижимо от HTTP 17 · полос 4

#   перепись: полос аутентификации 3 · спрашивают пол 3 (глагол kaname.cloud.iam.v1.UserTokenService/Issue, пол "2")
```

Перечень полос **выводится** обходом синтаксического дерева пакета, а не выписывается
(`gateway/internal/middleware/stepup_lane_census_test.go`): предикат смотрит, достижим ли метод
от точки входа и пишет ли он личность, и на имя метода не смотрит. Контроль в обе стороны у
переписи свой: полосы сессии и базового удостоверения обязаны выводиться; снятие подделываемых
заголовков и сам пол, достижимые от той же точки входа, полосами не признаются. Чем предикат
узнаёт «пишет» и «достижим» — третья граница, ниже; «четвёртая полоса роняет пробу своим именем»
верно только внутри неё.

**Вторая граница переписи — ТИП** (редакция 3). Перепись обходит методы `*AuthInterceptor`,
поэтому функция записи личности другого типа в её население не входит, и такая функция в дереве
есть: `(*DPoPMiddleware).injectVerifiedTokenHeaders`
(`gateway/internal/middleware/dpop_http_middleware.go`) пишет личность на REST-входе по
подписанному предъявителю с привязкой к ключу. Класса она не добавляет — это подписанный
предъявитель — и в боевой посадке не смонтирована: её включает ручка `authn.enableDpop` чарта края,
а незакомментированных объявлений этой ручки в профилях дерева **ноль**
(`grep -rln -E '^\s*enableDpop:' deploy/helm gateway/deploy | wc -l` → 0 на `41c75cb678`).

**Третья граница переписи — ФОРМА записи и вызова** (редакция 4; нашёл оппонент до рецензента).
Запись личности предикат узнаёт двумя формами и только в теле самого метода: вызов
`setPrincipalHeaders(…)` либо имя константы `principalmeta.HeaderPrincipalID` /
`HeaderGRPCMetaPrincipalID` (`laneEstablishesPrincipal`). Достижимость — только прямыми вызовами на
получателе, `a.Метод(…)` (`laneReceiverCalls`). Отсюда три расхождения с «пишет личность и
достижим»:

- метод, пишущий личность **через функцию пакета**, полосой не признаётся. Опыт на `41c75cb678` в
  собственной копии, повторён вторым проходом доводки на `45d1719fe8` с тем же исходом: метод
  `*AuthInterceptor`, вызванный из `HTTP` перед полосой подписанного предъявителя. V0 — прямой вызов
  `setPrincipalHeaders` в теле: обе пробы паритета красны с «Should be empty, but was
  [tryInjectedLane]», перепись «… достижимо от HTTP 18 · полос 5». V1 — близнец, отличается одним
  фактом, тот же вызов вынесен в функцию пакета: код 0, все три пробы зелены, перепись «… достижимо
  от HTTP 18 · полос 4». Откат — `git status --porcelain` пуст;
- метод, вызванный **значением метода** (`runLane(a.lane, …)`), обходу недостижим — так читается
  `laneReceiverCalls`. V2 — метод V0, вызванный через функцию, принимающую значение метода: все три
  пробы зелены, перепись «… достижимо от HTTP 17 · полос 4» (нашёл оппонент, повторено вторым
  проходом на `45d1719fe8`);
- метод, который константу заголовка лишь **упоминает** — читает, а не пишет, — полосой
  признаётся: предикат судит упоминание, а не запись. Так читается `laneEstablishesPrincipal`.
  Опыт второго прохода на `45d1719fe8`: достижимый от `HTTP` метод, читающий заголовок принципала, —
  обе пробы паритета красны с «Should be empty, but was [observeInboundPrincipal]», перепись «…
  полос 5».

Поэтому «четвёртая полоса роняет пробу своим именем» верно для метода `*AuthInterceptor`, вызванного
из `HTTP` прямо на получателе и пишущего личность в своём теле одной из двух форм, — и только для
него. Держатели Р3 на REST-входе (строки 24.1 и 24.4 §1.8) утверждают о тех полосах, которые
перепись выводит; полосу вне этой формы они не видят. Полоса V1, проведённая через слой приёма края
с полом и каталогом дерева (стенд пробы паритета) на глагол с полом `2`, получает `200` и доходит до
владельца со своей личностью, а перепись пола в том же прогоне печатает «спрашивают пол 3» (нашёл
оппонент, повторено вторым проходом на `45d1719fe8`). Все опыты этой границы откачены —
`git status --porcelain` пуст.

**Граница переписи названа ею самой: она судит REST-вход, нативный gRPC не перечисляет.** Там
классов носителей **два** из трёх — сессия браузера до нативного входа не доходит by
construction. Предикат с контролем в обе стороны ищет **вызов** полосы сессии в исполняемых
строках, а не слово:

```sh
# дом: PRO-Robotech/kacho; тело нативного входа против тела REST-входа, строки комментария сняты
for fn in authorize HTTP; do
  awk "/^func \\(a \\*AuthInterceptor\\) $fn\\(/,/^}/" gateway/internal/middleware/auth.go | grep -v '^\s*//' | grep -c 'tryKratosSession('
done
#   authorize → 0 · HTTP → 1
```

Единственная совпавшая строка тела `HTTP` — сам вызов (`injected, handled := a.tryKratosSession(w, r)`),
поэтому снятие вызова даёт `HTTP → 0`, и контроль способен упасть. Две другие ветви нативного
входа — `a.basicLane.Owns(bearer)` и `isAsymmetricJWT(bearer)` — стоят в теле `authorize` по одной;
клиентский сертификат проверенного пира даёт там личность **машины**, а не человека.

*Своя ошибка названа первой, и форм у неё две.* Первая редакция этого предиката искала слово
`session` и нашла его в теле `authorize` внутри слова `possession`. Вторая искала слово `Kratos` и
давала `HTTP → 2`, из которых одно — строка комментария «Kratos path suppresses the JWT paths»:
сними вызов — контроль всё равно показал бы `1` (нашёл рецензент круга по редакции 2). Обе ошибки
одного рода — предикат судил слово, а не исполняемое (`testing.md` §«Гейт на класс», п. 4).

**Второй дом — служба доступа.** Её внутренний замок
(`PRO-Robotech/kaname:internal/authzguard/acr_floor.go`) читает уровень, который донёс край, и
доносят его все три полосы — строка «доносят … 3» переписи выше. Сверх того у службы есть **своя**
публичная дверь: она принимает подписанного предъявителя нашего издателя без края
(`PRO-Robotech/kaname:internal/presentedcred/reader.go`; в боевом профиле
`PRO-Robotech/kaname:deploy/values.prod.yaml` — `presentedCredential.enabled: true`). Пол там
спрашивает то же общее правило (`grpcsrv.EvaluateStepUp` в
`PRO-Robotech/kaname:internal/authzguard/public_caller_policy.go`), а отказ — единый отказ этой
двери, `PERMISSION_DENIED` с текстом `permission denied`. Поведение этой двери закрепляет
`sub-phase-KAN-AUTHN-1-presented-credential-on-public-listener-acceptance.md`, а не эта приёмка:
сценарии §3 говорят о **крае**, и Р9 форму отказа этой двери не определяет.

**Что из этого следует для документа.** Р3 и Р9 переписаны под три класса (§2), входной гейт S3
и сценарии 24-25 — тоже (§3). Разбор прежней асимметрии в git по-прежнему не идёт: здесь предмет,
решение и следствие, а разбор — в диффе фикса `0dafb250a7` (`security-disclosure.md` §«Где такой
разбор ЖИВЁТ на самом деле»).

### 1.7 Что именно не исполняется в e2e

Критерий (механический): шаг требует человеческого вызывающего, если его предъявитель —
переменная, которую боевой посев **по собственному объявлению** не может выковать машинным
путём. Объявления — блок «Deliberately NOT minted» в `tests/authz-fixtures/prodseed_all.py`
и перечень `prodseed_matrix.py:18-27`.

> **Координата дана якорем-текстом, а не только номером строки, и это не педантизм.** Номер
> у первого объявления сдвигался дважды за трое суток: `:38` на базе сверки `bb26d905`, `:40`
> на `8e132d0b`, `:47` после правки заголовка того же файла. Второй перечень (`:18-27`) на
> обеих ревизиях не двигался — перемерено `git show <rev>:<path>`. Номер строки в приёмке
> живёт ровно до следующего коммита в тот файл; якорь переживает его.

**Единица измерения называется у каждого числа.** Их три, и они не взаимозаменяемы:
**литерал в исходнике** · **исполняемый шаг / утверждение в дереве** · **упавшее утверждение
живого прогона**. Сведение чисел разных единиц в одну строку — тот же класс, который эта
приёмка ловит в коде.

**Единица A — дерево (воспроизводима командой, §7.4):**

| Класс | Шагов | Кейсов | `pm.test` | Стражей в дереве | Коллекций (из 82) |
|---|---:|---:|---:|---:|---:|
| незасеиваемый предъявитель ступени (`jwtAccountAdminAStepUp`) | 16 | 9 | 63 | 16 | 3 (все iam) |
| незасеиваемый истёкший предъявитель (`apiTokenExpired`) | 1 | 1 | 3 | 1 | 1 (iam) |
| **подытог (незасеиваемые)** | **17** | **10** | **66** | **17** | **4** |
| владелец аккаунта обязан быть человеком (`POST /iam/v1/accounts`) | 23 | 23 | 75 | — | 4 |
| **итого широкий критерий** | **40** | **33** | **141** | — | **8** |

> **Колонка коллекций считается по ОБЪЕДИНЕНИЮ, и ранняя редакция ошиблась в ней ровно тем,
> что документ полицирует у отчёта.** Наборы узкого и широкого критериев **не пересекаются**
> (проверено явно: узкий — `authz-sa-apitoken`, `iam-authz-grant-check-propagation`,
> `iam-service-account`, `iam-user`; широкий — `authz-deny`, `iam-account`,

> **4 + 4 = 8**, а не 7. Итоги 40/33/141 были верны; неверна была одна ячейка. Команда
> пересчёта обеих строк — §7.4.

«Стражей в дереве» — это **сколько их объявлено**, а не сколько сработает. Сколько сработает
— свойство **прогона**: шаг может не дойти до исполнения, если кейс встал раньше. Слово
«гарантированно» здесь было бы деривацией, выдаваемой за замер, и ранняя редакция этого
документа его допустила.

**Единица B — прогон (отчёт прочитан, сведение выполнено).** Замер боевой посадки
2026-07-31 даёт **14 858** исполненных утверждений, **319** упавших; из них **161 упавшее
утверждение в 68 сигнатурах** (все — iam) требует человеческого вызывающего. Это **прогонная**
единица: упавшие утверждения живого прогона, сгруппированные по сигнатуре. **По дереву она
невоспроизводима by construction** — отчёты прогонов лежат вне git (`out/` под `.gitignore`).
Ранняя редакция объявила это расхождение опровержением; это была ошибка сравнения **разных
единиц**, и она снята.

**Сведение A↔B сходится на стражах.** В дереве объявлено **17** стражей (единица A); на
прогоне сработало **15** — `jwtAccountAdminAStepUp` ×14 в трёх коллекциях
(`iam-service-account` 7, `iam-user` 4, `iam-authz-grant-check-propagation` 3) и
`apiTokenExpired` ×1. Разница `17 → 15` — **два шага, до которых прогон не дошёл**: кейс встал
раньше. Именно поэтому «гарантированно красных» было деривацией, а не замером.

**Находка о самом отчёте (не о продукте).** Перечисление по коллекциям даёт **160 в 67**
против объявленного итога **161 в 68** — недостаёт ровно одного утверждения в одной сигнатуре,
и недостача уходит в корзину «прочие». Проверено пересчётом обеих колонок. Прочие итоги
отчёта сходятся (`0 + 150 + 169 = 319`; `135 + 15 = 150`; `8 + 161 = 169`), поэтому дефект
локален: он в **перечислении**, а не в измерении. Это измерение, чьи части не складываются в
собственный итог, с недостачей, спрятанной в остаточной корзине, — тот же класс, который эта
приёмка запрещает в коде: **корзины «всё остальное» не бывает**. Пересчёт перечисления —
пункт 0 координации (§10); он **не блокирует** S1-S3, поскольку итог 161/68 подтверждён
независимо (`169 − 8`).

Единицы A и B **не конкурируют**: A измеряет, сколько проверок класса **объявлено** в дереве
и потому подлежит правке; B измеряет, сколько их **упало** на конкретной посадке. Цель S4
формулируется в единице B (сценарий 29), объём правки — в единице A.

**Почему класс НЕ БЫЛ виден на локальном стенде.** Единственный набор отчётов, лежащий в

**Две поправки к постановке (обе стороны проверены):**

1. «14 утверждений требуют ступени» — 14 это число **литералов**
   `auth="jwtAccountAdminAStepUp"` в исходниках кейсов (проверено пересчётом: ровно 14 в трёх
   файлах). Исполняемых **шагов** — 16: одна строка внутри переиспользуемого блока
   раскрывается в несколько шагов. Утверждений в них — **63**.
2. «1 — истёкшего токена» — 1 это число **стражей** (`authz-sa-apitoken.py:383`); утверждений
   в шаге — **3**, а сама запись посева (`prodseed_matrix.py:27`) говорит «две», считая только
   тело. Три числа, три единицы, ни одно не неверно.

**Отдельная находка, определяющая S4.** Страж пустого предъявителя запрос **не отменяет**:
он даёт одно падающее утверждение, снимает заголовок и **отправляет шаг анонимно**. Поэтому
остальные 49 утверждений класса (66 − 17) исполняются против **другого** принципала, а
негативные из них при этом ещё и зеленеют — анонимный вызов даёт тот же код отказа, который
кейс и ждал.

Существенно, что это **не недосмотр**: комментарий рядом со стражем сам называет этот эффект
(«проходит по неверной причине») и всё равно оставляет отправку — ради детерминированности
запроса. То есть выбран размен, у которого одна сторона названа, а вторая — нет: слот занят,
вердикт зелёный, содержания нет. S4 меняет размен, а не чинит опечатку.

### 1.8 Перепись производителей редакции 2 — до правки сценариев, с двумя знаменателями обхода

Сделана **до** того, как правились сценарии: каждое «Тогда/И» правленных сценариев сопоставлено
тому, что в дереве его **производит** — печатает этот текст, возвращает этот код, несёт это
значение, — и тому, что его **держит**, то есть пробе, которая покраснеет. Сценарий, у «Тогда»
которого производителя нет, правке не подлежал бы вовсе, а переписывался бы под производимое.
Таких не нашлось: производитель есть у каждой клаузы, недостаёт **держателей** — и это названо
построчно.

**Редакция 3 повторила перепись ДО правки сценариев 16 и 24 — в две оси.** Ось «Тогда» — таблица
ниже: у каждой клаузы производитель и держатель. Ось «Дано» — вторая таблица: производит ли
названный дом условие сценария, и не строже ли «Тогда» того, что производитель реально даёт.
Население расширено по предмету (знаменатель A). Производитель нашёлся у каждой клаузы, включая
новые 16.1–16.4 и 24.5; держателя нет у 24.5 — это названо строкой таблицы с состоянием
«не начат», а не растворено в «наполовину».

**Редакция 4 открыла два сценария вне прежнего населения — 04 и 05 — и прошла их по обеим осям.**
Их открыли находки оппонентов: производитель их «Тогда» посажен (S1) и расходится с ним. Поэтому
население — сценарии, отобранные по предмету (знаменатель A), плюс открытые находками; вторые
названы перечнем, потому что отобраны не текстом, а находкой.

**Знаменатель A — население сценариев.** Сценарий входит в население, если его тело утверждает
форму отказа по полу, носителя, число чувствительного набора **либо называет носителя другим
именем того же предмета** — персональный токен, выдача `UserTokenService`, базовое удостоверение,
вид удостоверения, предъявитель края, отказ проверки токена, единый отказ полосы (редакция 3).
Население **выводится** из документа, а не выписывается:

```sh
# дом: воркспейс, корень дерева; прогнано на редакции 4
python3 - docs/specs/sub-phase-IAM-INT-1-interactive-login-capability-acceptance.md <<'PY'
import re, sys
t = open(sys.argv[1]).read().split('\n')
heads = [i for i, l in enumerate(t) if re.match(r'^\*\*Сценарий \d+', l)]
P = re.compile(r'insufficient_user_authentication|носител|(?<![-\d])(26|29|305)(?![-\d])'
               r'|персональн|UserTokenService|базов\w*\s+(удостоверени|секрет|токен)'
               r'|предъявител\w*\s+края|token validation failed|credential refused|KEYPAIR|SECRET')
OPENED = {'04', '05'}   # открыты находками оппонентов OPP-1, OPP-2 (редакция 4), а не словарём
subj, pop = [], []
for i in heads:
    j = i + 1
    while j < len(t) and t[j].strip() != '---' and not t[j].startswith('#'):
        j += 1

      '· в населении', len(pop), ':', ' '.join(pop))

#   сценариев 34 · по предмету 7 : 12 14 16 22 23 24 25 · в населении 9 : 04 05 12 14 16 22 23 24 25
```

*Своя ошибка названа первой.* Первая редакция предиката контроль в обе стороны **провалила**: без
исключения строки `**ID:**` и дат в население попадали 26 и 29 — номер сценария в его же строке
идентификатора — и 32, где «29» оказалось днём даты `2026-07-29`. Предикат считал собственную
разметку документа — тот же класс, что §1.7 называет у отчёта прогона. После правки перемерено
всё население, а не дельта. И обратный контроль: на редакции 1 (`git show origin/main:<этот
файл>` до правки) тот же предикат даёт то же население — оно не подогнано под новый текст.

*Ошибка редакции 2 — второго рода, и она дороже первой.* Предикат отбирал по **словарю**, а не по
**предмету**: сценарий 16 говорил о том же носителе словами «персональный токен» и
`UserTokenService`, и распознаватель этой законной формы записи не знал (`testing.md` §«Гейт на
класс», п. 7) — нашёл рецензент круга по редакции 2. Расширение проверено в обе стороны и на двух
формах. **Широкая** форма рецензента
(`персональн|UserTokenService|базов|предъявител[ья] края|token validation failed`) добавляет к
прежним шести **два** сценария: 16 — настоящее попадание, 18 — ложное, «базового профиля» и
«базовом профиле» профиля helm; адъюдицировано чтением обеих совпавших строк. **Узкая** форма
выше (`базов\w*\s+(удостоверени|секрет|токен)`) даёт то же население без ложного. Имена классов
носителей — «сессия браузера», «подписанный предъявитель» — стоят в сценариях 16, 24 и 25 (в 16
второе внесла редакция 3); все три уже в населении, и новых кандидатов имена не дают. Обратный
контроль: на редакции 1 (`git show 433b47f2:<этот файл>`) узкая форма даёт население
`12 14 16 22 23 24 25` — то же, что на редакции 3, то есть оно не подогнано под правленный текст.

Правлены редакцией 2 **три** сценария — 23, 24, 25; редакцией 3 — **два**: 16 (отрицательная пара,
её близнец и контракт вида — клаузы 16.1–16.4) и 24 (клауза 24.3 утверждает равенство отказов,
литерал вынесен клаузой 24.5). У **трёх** — 12, 14, 22 — перемерена одна клауза, форма отказа: их
предъявитель получен церемонией, то есть это класс «подписанный предъявитель», у которого по Р9
форма шлюзовая, и правка им не нужна. Редакцией 4 — **два** сценария вне прежнего населения, 04 и
05: «Тогда» приведено к производимому (Р11). Остальные двадцать пять сценариев не открывались ни
одной из редакций 2–4, и о них здесь не утверждается ничего.

## §2 Решения (ратифицировать явно — ревьюер проверяет каждое)

**Р1. Возможность выражается через iam, новым Internal-ресурсом.** Клиент интерактивного
входа заводится RPC iam, а не обращением к административному API провайдера. Обоснование —
#16 (единственный фасад) и `security.md` (административный API провайдера не аутентифицирует
никого; всякий, кто до него дотянулся, заводит клиентов). Ресурс admin-only ⇒ живёт на
`Internal*`-сервисе (:9091), REST — только на внутреннем mux, префикс `/iam/v1/internal/`
(как `internal_cluster_service.proto:52`). Ban #6.

**Р2. Аудитория — не поле запроса.** Вызывающий её не задаёт; iam штампует аудиторию края из
своей конфигурации и **эхает output-only**. Обоснование: поле, которое можно задать, но
нельзя задать неправильно, — это поле без читателя; а поле, которое можно задать
неправильно, ломает край молча. Запрет «принято-и-проигнорировано» соблюдён by construction
— принимать нечего.

**Р3 (редакция 2). Пол аутентификации вычисляется для КАЖДОГО носителя человеческой личности,
и вердикт зависит от предъявленного УРОВНЯ, а не от класса носителя.** Один глагол, один пол
каталога, один уровень — один вердикт, каким бы из трёх классов (§1.6) человек ни предъявился.
Иначе пол — форма без содержания на том носителе, который его не спрашивает.

*Что изменилось против редакции 1 и почему.* Редакция 1 говорила: «исход одного и того же RPC
не зависит от того, чем человек предъявился». С третьим классом это неверно буквально: у
базового удостоверения уровень — константа вида `"1"`, поэтому человек со вторым фактором,
предъявивший его, получает на поле `2` отказ, а тот же человек сессией — `200` (сценарий 25).
Инвариант — равенство вердикта **при равном уровне**; класс носителя решает только одно:
**какой уровень он способен нести**.

**Р4. Ни один пол не понижается.** 26 / 210 / 64 (§1.1) — измерение, а не предмет правки.
Если после посадки церемонии какой-то пол окажется недостижим, чинится **церемония**, а не
пол. Понижение пола ради зелёного набора — запрещённый исход (`step-up-acr-sensitive-only`
уже зафиксировал, что ступень **сужена** до чувствительного набора осознанно).

**Р5. Второй фактор заводится без браузера.** Не ради удобства проверки: без этого
чувствительный набор из 26 записей не проверяется автоматически **никогда**, а оператор не
может заскриптовать ни восстановление доступа, ни заведение служебного человека. Требование
продуктовое, проверочное — следствие.

**Р6. Всякая проверка посадки называет свою ЕДИНИЦУ и выбирает идиому под неё.** Единиц две,
и обе живут в `gateway/deploy/`:

- вопрос **«что получится у релиза»** → складывать профили в порядке helm
  (`resolveStackAt` / `mergeInto` / `deployableStacks`);
- вопрос **«объявляет ли профиль своё сам»** → читать профиль в одиночку
  (`token_shape_test.go`, который **сам** оговаривает, что профили не слоятся).

Проверка остаётся **декларативной** (читает файлы значений, не рендер), поэтому не может
пропуститься. Ранняя редакция этого решения требовала «профиль обязан объявлять консоль» —
формулировка **воспроизводила** ошибку §1.5, меряя оверлей вместо релиза, и снята. Требование
теперь: **сложенный стек** production-класса резолвит консоль входа (сценарий 18), а её адрес
административного хопа проверяет **уже существующий** гейт (сценарий 19 снят).

**Р9 (РЕШЕНИЕ, редакция 2). Вердикт по полу ОДИН для всех носителей; форм отказа ДВЕ, и
выбирает между ними один признак — достижима ли у носителя церемония повышения.** Сессия
браузера и подписанный предъявитель получают шлюзовую форму: `401` +
`{"code":16,"message":"insufficient_user_authentication"}` + `WWW-Authenticate` с `acr_values`
(RFC 9470). Базовое удостоверение получает единый отказ своей полосы: `401` +
`{"code":16,"message":"credential refused"}` + `WWW-Authenticate: Bearer error="invalid_token",
error_description="credential refused"` — побайтово тот же ответ, что на негодный секрет той же
марки.

*Редакция 1 выбирала ОДНУ форму «для обоих носителей»* и обосновывала выбор тремя доводами: (а)
правило остаётся в одном месте и не расходится между носителями; (б) форма машинночитаема,
поэтому её проверяет e2e; (в) перенаправление на повторный вход — работа консоли, а не края.
Альтернатива «носителю-сессии — перенаправление» была рассмотрена и отклонена ими же. **Все три
довода остаются в силе**: вердикт выносит одно место (`stepUpVerdictHTTP` → общее правило
`grpcsrv.EvaluateStepUp`), рендеринг решает одна функция признака (`stepUpCeremonyReachable`),
обе формы машинночитаемы и различимы кодом ошибки в заголовке. Третий носитель добавил **два
довода против** распространения шлюзовой формы на него, и каждый решающий сам по себе:

1. **оракул годности.** Вызов RFC 9470 говорит «предъявленное годно и лишь недостаточно
   сильно» — по глаголу, который вызывающему недоступен. Для долгоживущего предъявительского
   секрета это даровое подтверждение, что строка годна, — без единого авторизованного действия и
   без следа в аудите; ровно ради закрытия этого все отказы полосы сведены в один;
2. **совет невозможного.** `acr_values="2"` предлагает поднять уровень, а у этого носителя
   поднять его нечем: уровень — константа вида. Средство у вызывающего в обоих случаях одно —
   взять интерактивное удостоверение.

Решение принято продуктом (`#1215`; разбор — раздел «ПОЧЕМУ ОТКАЗ ПО ПОЛУ НА ЭТОЙ ПОЛОСЕ — НЕ
ВЫЗОВ RFC 9470, А ЕЁ СОБСТВЕННЫЙ ЕДИНЫЙ ОТКАЗ» в `gateway/internal/middleware/auth_basic_stepup.go`;
шапка файла отвечает на другие вопросы) **после** вердикта этой приёмки и в неё не
вносилось. Редакция 2 вносит его в контракт, а не опровергает. Альтернативы названы и отвергнуты:
требовать шлюзовой формы и от базового удостоверения — завести оракул; оставить Р9 в редакции 1
— держать контракт, по которому сценарий 24 краснел бы на исправном продукте. Решение записано
здесь, чтобы сценарии 24-25 читались как следствие, а не как обнаруженный факт.

*Несущее в решении — РАВЕНСТВО, а не текст* (редакция 3). Контракт базовой полосы — «отказ по полу
неотличим от отказа в удостоверении»; `credential refused` — сегодняшний текст этого единого
отказа. Равенство держит проба (§1.8, клауза 24.3), текст — пока ни одна (клауза 24.5), и держатель
литерала — требование DoD S3. Сменить текст можно только тикетом (инвариант 7), и тогда у обоих
отказов сразу: их производит одна функция.

*Поверхность* (редакция 3; держатели разведены редакцией 4). Формы выше — формы **REST-края**. На
нативном gRPC края вердикт тот же, а форма иная, и классов носителей там два (§1.6). Подписанный
предъявитель ниже пола получает `UNAUTHENTICATED` с сообщением `insufficient_user_authentication` и
без `acr_values`: заголовка вызова у gRPC нет (`enforceStepUpGRPCAssurance` в
`gateway/internal/middleware/auth_stepup.go`). Базовое удостоверение получает `UNAUTHENTICATED` с
сообщением, побайтово равным отказу на негодный секрет той же марки.

Держатели у двух половин разные и держат разное. Базовую полосу держит
`TestBasicLaneStepUp_FloorRefusalIsIndistinguishableFromCredentialRefusal_GRPC`
(`gateway/internal/middleware/basic_lane_stepup_oracle_test.go`): код `Unauthenticated` у обоих
отказов и их равенство. У подписанного предъявителя
`TestStepUpAlwaysOn_GRPC_SensitiveRPC_BelowFloor_Refused`
(`gateway/internal/middleware/stepup_alwayson_test.go`) держит **сообщение, а не код**. Инъекция
редакции 4 в собственной копии `41c75cb678`: `enforceStepUpGRPCAssurance` возвращает
`codes.PermissionDenied` вместо `codes.Unauthenticated` — проба зелёная, и все пакеты края тоже
(`go test ./gateway/... -count=1` — код 0, пакетов `ok` 24, `FAIL` 0); откат — `git status
--porcelain` пуст. Код этого отказа несёт его смысл — «аутентифицируйтесь сильнее», а не
«запрещено», — и сегодня его не держит ни одна проба, как и литерал клаузы 24.5. Держатель кода —
требование DoD S3. Сценарии §3 утверждают формы REST; дверь службы — отдельный предмет (§1.6).

*Цена решения названа* (редакция 3). Единый отказ базовой полосы несёт `error="invalid_token"` и на
**годное** удостоверение, а RFC 6750 (§3.1) определяет этот код как «истёк, отозван, искажён или
негоден по иной причине». Клиент, построенный по стандарту, вправе счесть строку мёртвой и
выбросить её. Размен принят ради закрытия оракула годности и **объявлен клиенту** страницами
службы: `PRO-Robotech/kaname:docs/content/first-credential.mdx` — «`401` означает, что строка не
принята, и причин **четыре**», среди них недостаточный уровень, «Исход у всех четырёх **один и
неразличимый**», и врезка «Базовый токен даёт уровень `1` — часть глаголов ему недоступна НАВСЕГДА»
с советом «смотрите порог, а не строку»; `PRO-Robotech/kaname:docs/content/api/tokens.mdx` —
«уровень аутентификации базового токена — `1`. Им нельзя ни выпустить, ни отозвать удостоверение».

**Р10 (РЕШЕНИЕ). Перевод стража в форму «утвердил и не отправил» оплачивается учётом — и
закрывает уже записанный долг, а не заводит новый.** Форма санкционирована
(`exec-coverage.py`), и популяция «объяснённых пропусков» **уже** насчитывает 135 шагов от
стража адреса, из-за чего текст проверки исполняемости **уже** неверен — замер 2026-07-31
объявил это открытым долгом. S4 добавляет к популяции до 17 шагов и потому **обязана долг
закрыть**: удержать различимость записанного пропуска от немого (правило 1b — страж несёт
утверждение, называющее переменную) либо объявить остаток **счётным долгом с числом**. Молча
увеличить популяцию, оставив текст проверки неверным, — запрещено: это ровно тот приём,
который под-фаза запрещает другим.

**Р7. Шаг без предъявителя не отправляется.** Отсутствие креденшала делает шаг
**неисполненным**, а не «исполненным анонимно». Его утверждения попадают в вердикт как
**не исполненные** и никогда — как пройденные (§1.7).

**Р8. Что не решается здесь — не решается молча.** Открытые вопросы владельца вынесены в §6
поимённо, с числом и с двумя взаимоисключающими исходами каждый. Догадкой не заполняются.

**Р11 (РЕШЕНИЕ, редакция 4). Машинный признак полосы у отказов `Get` клиента интерактивного входа
эта приёмка не утверждает — ни присутствием, ни отсутствием.** Сценарии 04 и 05 утверждают код, текст
и порядок проверок — ровно то, что производит посаженная S1.

*Что в дереве службы.* На несуществующий идентификатор `Get` отвечает `NOT_FOUND` с текстом
хранилища (`PRO-Robotech/kaname:internal/repo/kaname/pg/interactive_client_repo.go`) через общий
отображатель `shared.MapRepoErr` (`PRO-Robotech/kaname:internal/apps/kaname/shared/errors.go`), на
испорченный — `INVALID_ARGUMENT` из проверки формы фундамента. Деталей отказа не несёт ни тот, ни
другой. Признаков `RESOURCE_NOT_FOUND` и `INVALID_RESOURCE_ID` в дереве службы не производит ни один
ресурс: поиск по именам признаков и их констант находит два вхождения в одном файле — комментарий
набора `PRO-Robotech/kaname:tests/newman/cases/iam-interactive-client.py`, объявляющий, что эти
признаки не утверждаются (контроль разборщика: те же константы в платформе производят geo и vpc).
Признак служба ставит отказам квот, ссылок, членства и ролей модулей и отказу в правах —
производителей деталей отказа в её не-тестовом дереве шесть (перепись — довод 3). Её страница для
арендатора (`PRO-Robotech/kaname:docs/content/api/overview.mdx`) различает `NOT_FOUND` и `INVALID_ARGUMENT`
кодом и тоном, а признак обещает только полосам квот.

*Почему признак не утверждается.* Три довода, каждый достаточен сам:

1. **у `Get` полосу называет код.** Признак нужен там, где один код приходит двумя полосами —
   своей и соседской (`api-conventions.md` §«By-lane code-split»). У `Get`
   соседа на пути нет, и признак различал бы то, что код уже различает;
2. **признак полос прямого чтения и формы — свойство общего отображателя службы, а не ресурса.**
   Заведённый у одного ресурса, он разделил бы ресурсы службы надвое, и этого различия никто бы не
   решал — продукт противоречил бы себе (ban #18);
3. **значение домена у признака службы решено не здесь.** Решение W3 приёмки WIRE-1 объявляет
   суффикс службы `kaname.cloud`, сценарий WIRE-3-01 — домен `iam.kaname.cloud`. Держит это гейт
   домена отказа службы: у объявления домен берут четыре производителя из шести, а два прощены его
   ведомостью, у каждой записи свой предикат снятия, — отказ квот с доменом прежнего бренда до
   выпила модуля (kacho#2117) и отказ в правах с именем пакета контракта, одинаковым с краем
   (kacho#2133). Перепись на `5303cebd`, в корне службы:
   `go test ./internal/refusaldomain/ -run '^TestRefusalDomainComesFromTheDeclaration$' -count=1 -v` —
   «производителей `errdetails.ErrorInfo` найдено 6 (берут у объявления 4), ведомость прощений:
   2 записей, из них сработало 2, находок 0». Второе место об этом значении здесь не заводится; до
   этой правки сценарий 04 держал домен прежнего бренда. Первый проход доводки писал «где служба
   признак ставит, домен — `iam.kaname.cloud`» — шире переписи; сужено вторым проходом.

*Почему не утверждается и отсутствие.* Клауза «деталей нет» закрепила бы пробел как контракт и
покраснела бы на исправлении службы. Сценарии 04 и 05 верны при обоих исходах вопроса 5 §6.

*Отвергнутые исходы.* Оставить признак в «Тогда» — одобрить договор, который посаженный продукт не
выполняет, и без задачи на производителя: §8 обещал модульный замок «тон + признак», а такой пробы в
дереве службы нет. Завести признак только у `InteractiveClient` — довод 2. Сам вопрос о признаке у
всей службы — вопрос 5 §6.

### S1 — Клиент интерактивного входа заводится, живёт и снимается через iam

Вводится ресурс **`InteractiveClient`** (пакет `kacho.cloud.iam.v1`), плоский message:

### S3 — Ступень второго фактора и равенство вердикта по классам носителей

> **ВХОДНОЙ ГЕЙТ СТАДИИ (редакция 2): одного человека обязан ПРЕДЪЯВИТЬ ПОСЕВОМ всеми тремя
> классами носителей до того, как сценарии 24-25 будут написаны в красное.** Редакция 1
> требовала «обоими» — носителей тогда считали двумя (§1.6).
>
> У сценария 21 отходной путь назван прямо: «если заведение без браузера окажется
> неконструируемым, **сценарий неверен, а не продукт**». У сценариев 24-25 такого пути в тексте
> не было, потому что редакция 1 держала раздел о носителях без координат — асимметрия тогда
> была открытой, а оба репозитория публичны. Асимметрия закрыта (`0dafb250a7`), классы и их
> производители теперь названы (§1.6, §1.8), и ревьюер может проверить сценарии по документу.
> Конструируемость **на стенде** документ этим не доказывает: её по-прежнему доказывает посев.
>
> Требование прежнее, расширенное на третий класс: посев предъявляет одного и того же человека
> краю сессией браузера, подписанным предъявителем и базовым удостоверением, выданным ему
> самому, и показывает, что все три доходят до принципала. Один человек — не формальность: он
> делает класс носителя **единственным** различающимся фактом пары, и тогда разный исход нечем
> объяснить, кроме класса.
>
> **Состояние гейта — замерено редакцией 2: НЕ ПРОЙДЕН.** Посев церемонии предъявляет человека
> **одним** классом из трёх:
>
> ```sh
> # дом: PRO-Robotech/kacho, корень дерева
> python3 -c "import runpy; m=runpy.run_path('tests/authz-fixtures/ceremony_credentials.py'); e=m['CEREMONY_ONLY_ENV']; print(len(e), sorted({'jwt*' if k.startswith('jwt') else k for k in e}))"
> #   20 ['apiTokenExpired', 'jwt*']
> ```
>
> Все двадцать записей — подписанные предъявители: `jwt*` девятнадцать и `apiTokenExpired` один.
> Сессии браузера посев не кладёт ни одной, базового удостоверения человеку — ни одного.
>
> Предъявить каждый класс **по отдельности** на стенде в деревьях умеют — но **разные**
> производители и **разные** люди, поэтому гейта это не проходит:
>
> | класс | кто предъявляет его на стенде | кого |
> |---|---|---|
> | сессия браузера | браузерная проба `ui-future/e2e/specs/stepup.spec.ts` | арендатора, которого проба регистрирует сама |
> | подписанный предъявитель | посев `tests/authz-fixtures/prodseed_ceremony.py` | людей церемонии |
> | базовое удостоверение | набор службы `PRO-Robotech/kaname:tests/newman/cases/basic-access-token.py` — секрет добывает сам | человека фикстуры `userAAAId` |
>
> **Если предъявить всеми тремя не удаётся** — исход прежний: сценарии 24-25 в набор **не
> пишутся**, равенство вердикта по классам объявлено **открытым долгом с числом**, и S3 **не

## §4 Инварианты (MUST hold — для ревьюера)

1. **iam остаётся единственным фасадом.** Ни одна нагрузка, кроме iam и уже объявленных
   потребителей административного хопа, не заводит клиента у провайдера. Новых прямых
   потребителей под-фаза не вводит.
2. **Ни один `Internal*`-метод не ДОСТИЖИМ на публичном крае** (ban #6, сценарий 11): маршрут смонтирован на обоих mux, изоляцию даёт диспетчер.
3. **Ни один пол не понижен** (Р4, сценарий 23).
4. **Мутации возвращают `Operation`** (ban #9); `done` означает durability предмета мутации
   и не гейтится на видимость чего-либо ниже по течению.
5. **Уникальность имени клиента — на DB-уровне** (`UNIQUE`), не программной проверкой
   (ban #10); отказ по гонке приходит как `ALREADY_EXISTS`, а не как второй успех.
6. **Ни одного секрета в ответе, кроме одноразовой выдачи.** Клиент интерактивного входа
   публичный (обмен по коду с доказательством владения), поэтому секрета у него нет вовсе;
   если выбран конфиденциальный вариант — секрет отдаётся ровно один раз и затирается в
   `Operation.response`, как уже сделано для персональных токенов.
7. **Тон сообщений — часть контракта.** Тексты §3 меняются только тикетом.
8. **Каждый гейт под-фазы несёт проверку своей предпосылки** и утверждает объём осмотренного
   (`testing.md`).
9. **Ни один e2e-кейс не пропущен** (сценарии 30, 31, 33); пропуск стражем допустим ТОЛЬКО в санкционированной форме «утвердил и не отправил» (сценарий 28, Р10).

## §6 Что эта приёмка НЕ покрывает (открытые вопросы владельца)

Заполнять догадкой запрещено. По каждому — два взаимоисключающих исхода; выбор за владельцем.

**Вопрос 1 — ЗАКРЫТ для вида `SECRET`; для вида `KEYPAIR` ОТКРЫТ только вопрос об уровне** (редакции 3 и 4). Прежняя
формулировка «является ли персональный токен предъявителем края?» задавала один вопрос о двух
разных носителях (§1.6); редакция 2 держала его открытым, одновременно утверждая ответ для одного
из них, — это и было противоречие, отмеченное кругом по ней.

*Вид `SECRET` — закрыт.* Персональный токен этого вида — предъявитель края: строка предъявляется как
есть (`Authorization: Bearer`), уровень — константа `"1"`. Решение принято одобренной приёмкой
`sub-phase-BAT-1-basic-access-token-acceptance.md` (§0; §2.3 — «уровень удостоверения — «1», и
следствие названо») и посажено (`0dafb250a7`, задача #1142 закрыта). Для этого вида выбран исход
(а), исход (б) отвергнут. Следствия закрепляют клаузы 24.3–24.5 и 25.2.

*Вид `KEYPAIR` — открыт только вопрос об уровне* (редакция 4). Утверждение ключевой пары
обменивается у эндпоинта выдачи платформы, и краю предъявляется подписанный предъявитель нашего
издателя. **Предъявитель ли он краю — решено**: одобренная приёмка
`sub-phase-F2-client-assertion-acceptance.md` (§0; F2-39 — «этот токен проходит на поверхности,
которой он адресован» для клиента пользовательского токена), и это закрепляют клауза 16.3 и кейс
края `F1B-D-PLATFORM-USER-TOKEN-ACCEPTED` с приоритетом P0. Голова редакции 4 держала открытым и
это, с исходом «предъявителем края не является», — такой исход молча отменил бы F2-39, клаузу 16.3 и
кейс. Здесь он не предлагается: пересмотр F2 — предмет F2. Сегодня (опыт на стволе, §1.6): с
адресатом края этот предъявитель проходит проверку издателя и адресата, но **уровня не несёт** — обмен
`client_credentials` церемонии не проводит. Уровень `0` по общему правилу пола не проходит ни
одного порога, то есть закрыты все **311** записей с порогом из 338, а проходят 27 записей без
порога; опыт показал это на одной записи с порогом `1` и одной без порога (E3, E2), остальное —
вывод из правила, а не прогон. Без названного адресата предъявитель получает адресат посадки по
умолчанию, и край отвергает его ещё до пола. Исходы: **(а)** владелец решает, что владение ключевой
парой засчитывается за уровень `1` (это ослабление: церемонии не было), — тогда эндпоинт
выдачи обязан проставлять уровень **там, где край его читает**: стандартным `acr` либо `kaname_acr`
внутри карты обогащения; `kaname_acr` на верхнем уровне — там, куда подписант службы кладёт
утверждения обогащения, — край не читает (опыт E4, §1.6); либо **(б)** не засчитывается: вид
остаётся предъявителем края уровня `0` — проходит 27 записей без порога и ни одной с порогом, — и
это объявляется клиенту: сегодня страница службы `PRO-Robotech/kaname:docs/content/api/tokens.mdx`
называет выпущенные ключевые пары действительными «на крае платформы» и об уровне молчит. Оба
исхода оставляют F2-39 в силе. Приёмка **не выбирает** и фиксирует сегодняшнее поведение клаузой
16.4.

*Третьего вида у персонального токена нет, и в вопрос он не входит* (редакция 4). `FEDERATED`
личности не выдаётся (§1.6). Токен федеративной полосы эндпоинта выдачи принадлежит служебной
учётке, а служебную учётку правило пола освобождает от порога целиком, поэтому вопроса об уровне у
этого токена нет.

*Путь поставщика у строк личности с зеркалом в вопрос не входит* (редакция 4). Это строки вида
`KEYPAIR` прежнего выпуска и вида `LEGACY` (§1.6). Их токен до пола не доходит: адресата у него нет,
и край отвергает его проверкой адресата (опыт E7). Уровня он не несёт по той же причине, что вид
`KEYPAIR`, но исход (а) его не касается: уровень проставлял бы наш эндпоинт выдачи, а этот токен
чеканит поставщик. BAT-1-25 требует, чтобы строки проходили прежним способом; на крае прежний способ —
отказ по адресату, и эта приёмка его не меняет. Путь закрывается вместе с поставщиком (эпик #2564)
либо с последней строкой; предикат остатка — `hydra_client_id IS NOT NULL` (#1121).

## §9 DoD по стадиям

**S1** — proto + регенерация (`buf lint`/`breaking` зелёные) · миграция (уникальность имени) ·
use-case + handler · регистрация маршрута (одним циклом по обоим mux, изоляция — диспетчером)

`go test ./services/iam/... -race` (полный, не `-short`) + `golangci-lint` + `govulncheck` ·
vault: `resources/iam-interactive-client.md`, `rpc/iam-internal-interactive-client-service.md`,
правка `edges/iam-to-hydra-admin.md`.

**Плюс два пункта, без которых стадия ЛОМАЕТ существующие гейты — названы явно:**

1. **Регистрация префикса идентификатора `ic`.** От неё зависят сценарии 01 (форма
   `ic-<17>`) и 05 (испорченный id → `INVALID_ARGUMENT` первым стейтментом): роутер
   классифицирует дефисную форму по **канону** `ids.KnownHyphenPrefixes()`
   (`pkg/ids/ids.go:318`), и незарегистрированный префикс до `corevalidate.ResourceID` просто
   не доедет. Два законных пути: внести `ic` в канон corelib (тогда обязательна и правка
   сторожа согласованности `pkg/ids/hyphenid_test.go:55`) **либо** объявить его через
   config-extra `KACHO_EXTRA_RESOURCE_ID_HYPHEN_PREFIXES` во всех профилях, где сервис
   поднимается. Выбор фиксируется в PR явно. Двухсимвольный префикс допустим:
   `NewHyphenID` принимает 2-3 символа.
2. **Обновление чувствительного набора каталога** (сценарий 23, редакция 2): поимённый
   `sensitiveACR2Set()` получает три FQN категории I, поимённое дополнение рутины — `Get`/`List`;
   обе копии каталога — края и службы — порождены заново, пять записей дельты в них одинаковы, а
   прочее расхождение копий — только записи ведомости объявленных переименований фундамента, у
   каждой свой предикат снятия (редакция 4: «побайтово» сверка не держит, §1.8). Абсолютный
   расклад держит гейт (`TestPermissionCatalog_ACR_Counts`) на своей ревизии, и здесь он не
   выписывается: редакция 1 выписала `26 → 29` и `300 → 305`, и оба числа устарели прежде, чем
   дельта села. Без этого пункта `TestPermissionCatalog_ACR_SetInvariant` и страж
   over-inclusion краснеют **на самой стадии** — генератор проставит новым RPC пол `2` по
   умолчанию. *Посажено — §1.8, строки `IAM-INT-1-23`.*
