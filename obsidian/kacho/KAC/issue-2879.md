## Что и зачем

**Признак.** `make assert-production-posture` судит части A–C по живым процессам любого
кластера, а часть D (административный переход к провайдеру личности, при посадке `own` —
отсутствие провайдера) зовёт `deploy/scripts/assert-admin-hop-transport.sh`, чья кластерная
половина пинит цель по kind: контекст обязан называться `kind-$CLUSTER_NAME` и вести в кластер,
который знает `kind`. На любом другом кластере — `ABORT`, код 2, и итог «посадка не
подтверждена» при чистых A–C. По телу задачи вердикт `own` на стенде прочитан вручную теми же
запросами, а провенанс стенда (`stand-provenance.sh --expect 7190c3e527`) вернул 0 — часть D
принадлежит гейту посадки, а не провенансу. Пин по кластеру заведён намеренно (одноимённый
контекст однажды вёл в другой кластер), поэтому снимать его нельзя — нужен пин для стенда вне
kind.

**Предмет.** Гейт посадки исполним на стенде вне kind. Цель пинится по кластеру объявленного
стенда — адресом apiserver'а из объявления стенда, а не именем kind. На кластере, не
совпадающем с объявлением, — отказ «условие не создано» с обоими именами, а не частичный
вердикт. Части A–D исполняются одной целью, и стенд вне kind получает полный вердикт.

## DoD

Из тела задачи, раздел «ПРЕДИКАТ» (перечислено как есть):

1. на стенде вне kind с объявленным кластером гейт выходит с кодом 0 при посадке `own` и
   печатает вердикт части D;
2. инъекция: активный кластер не совпадает с объявленным — отказ с обоими именами; на
   kind-стенде поведение прежнее;
3. `--self-test` покрывает ветку «не kind» синтетическими наблюдениями и печатает число
   случаев.

DoD — предикаты 1–3, п.1 на живом стенде вне kind. Артефакт — PR с `Closes` этой задачи; вывод
гейта на стенде вне kind — комментарием.
