# kacho#2697: поле есть, производителя нет — исход 1, поле снимается с контракта

**Предмет.** Найдено при реализации Ф5 ([[issue-1271]]). Три одобренные приёмки описывают
сессию, выданную восстановлением, с `passwordChangeRequired: true` и последующей сменой пароля
из неё (Ф3 Р8 и Ф3-23; Ф5-03, Ф5-23/24; Ф1 §4.2). Реализация Ф5 выдаёт сессию **после** записи
нового пароля тем же обращением (`POST /iam/v1/auth/recovery/complete` несёт `email`, `code`,
`newPassword`), поэтому значение `true` ставит только посев проб Ф3-23 — в прод-коде
производителя нет. Класс «принято-и-проигнорировано» на уровне поля контракта: клиент пишет
обработку состояния, которого не бывает.

Форма одного обращения выбрана из противоречия между теми же документами: Ф5-17 и Ф1-59 требуют
у **заблокированной** личности сменённых учётных данных **без** выданной сессии — значит шага
«задать пароль из сессии» у неё быть не может; а глагол смены пароля Ф3 (Р6) требует
**текущего** пароля, которого восстанавливающий по определению не знает.

## Решение — оркестратор, 2026-09-17 (владелец делегировал решения 2026-09-16)

Комментарий задачи, дословно в существенной части:

> **Исход 1 — завершение восстановления остаётся ОДНИМ обращением; поле
> `passwordChangeRequired` и его читатели снимаются с контракта.**
>
> По пяти вопросам ban #18:
> - **благо продукта / удобство** — у клиента два шага вместо трёх (запрос кода → завершение с
>   новым паролем); сессия выдаётся уже полноправной, промежуточного состояния «сессия с
>   требованием» нет, и нет читателя, который обязан его исполнять на каждом запросе.
> - **безопасность** — код одноразовый и сверяется в том же обращении, что записывает пароль;
>   сессия появляется только после того, как новый пароль стал durable. Заблокированная личность
>   (Ф5-17, Ф1-59) получает сменённые учётные данные **без** сессии — форма одного обращения это
>   выражает напрямую, двухшаговая — нет.
> - **перспективность** — двухшаговая форма при необходимости заводится **аддитивно** новым
>   глаголом со своей приёмкой; обратный ход (снять состояние сессии, которое клиенты уже
>   обрабатывают) дороже. Внешне-адресуемых координат решение не трогает.
> - **производственность** — поле без производителя `true` в прод-коде есть класс
>   «принято-и-проигнорировано» (`api-conventions.md`): клиент пишет обработку состояния,
>   которого не бывает. Исход по умолчанию там назван — снять с контракта с `reserved` номера и
>   имени; вместе с полем уходят отказ края `PASSWORD_CHANGE_REQUIRED` и
>   `ClearPasswordChangeRequired`.
> - Ф3 Р6 (смена пароля требует текущего) **не правится** — это и есть довод против исхода 2.
>
> Что делается:
> 1. Новые редакции в своих домах с записью ревью на новый отпечаток: Ф3 Р8 и Ф3-23; Ф5-03,
>    Ф5-23/24; Ф1 §4.2 — сессия восстановления требования не несёт, сценарии с ним снимаются
>    вместе с предметом (не ослабляются).
> 2. Снятие поля и читателей: служба (`reserved` в контракте, `ClearPasswordChangeRequired`,
>    посев проб Ф3-23) → край (отказ `PASSWORD_CHANGE_REQUIRED`) — один change-set, пин края на
>    ревизию `main` службы.
> 3. Предикат снятия задачи — из тела: `git grep -c PasswordChangeRequired -- '*.go' ':!*_test.go'`
>    → 0 в обоих деревьях.
>
> PR kaname#200 (Ф5) этим не блокируется: посаженная форма и есть выбранная.
