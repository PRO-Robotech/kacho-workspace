# issue-561 — перепись веток по продукту: посылка опровергнута, `comm` снят четырьмя часами раньше

Задача просила снять `comm` из `census_file()` и завести под этот класс инъекцию.
**И то и другое уже стояло в стволе** — посажено `fdc873ec` (PR #552, `Closes #540`)
за 4 ч 25 мин до заведения #561. Признак воспроизводился потому, что прогон шёл из
рабочей копии, отставшей от ствола на 21 коммит; фикс — среди них.

Ниже — замеры, которыми это установлено, и вердикт переписи, которого задача ждала.

## Исход проверки посылки: ОПРОВЕРГНУТА, и доказывается одной командой

Посылка задачи называла координату `scripts/branch-audit.sh:439-440`. Она принадлежит
**копии**, а не стволу:

```sh
git hash-object scripts/branch-audit.sh          # da95975d… — рабочая копия
git rev-parse origin/main:scripts/branch-audit.sh # 298a33a9… — ствол
git rev-parse fdc873ec^:scripts/branch-audit.sh   # da95975d… — ДОФИКСОВАЯ редакция
```

Первое и третье совпадают **побайтово**: в копии лежит ровно та редакция, из которой
`comm` был снят. Разделяет их один коммит:

```sh
git log --oneline main..origin/main -- scripts/branch-audit.sh
# fdc873ec fix(branch-audit): разность мультимножеств считает awk, не comm (#552)
```

Ствол зовёт `comm` **ноль раз**: `grep -cE 'comm -(23|12)' scripts/branch-audit.sh` даёт
`0` на `origin/main` и `2` на `fdc873ec^`. Счёт ведут `ba_mset_extra`/`ba_mset_common` —
хэш `awk`, ключ которого есть точная байтовая строка.

## Что оказалось неверно и во второй половине посылки

Задача (и тело #561) утверждали, что из-за `comm` **вердикта нет вовсе**. Это неточно, и
различие существенно, потому что называет другой предмет:

```sh
bash -c 'set -euo pipefail; x=$(LC_ALL=C comm -23 u1 u2 | grep -c . || true); echo $x'
# comm: input is not in sorted order   ← диагностика в stderr
# 1                                    ← и скрипт продолжается, rc=0
```

`|| true` в дофиксовой строке гасил код возврата, поэтому `set -e` не срабатывал.
Подтверждено прогоном: **дофиксовый скрипт под текущей инъекцией доходит до конца** —
краснеют `AB`/`AC`/`AE`, а `G` («чистый репозиторий: код 0») в том же прогоне зелёное,
то есть переписи печатались. Значит дофиксовое поведение — не «нет вердикта», а
**вердикт, утонувший в диагностике и посчитанный неверно** (#540: 11151 строка шума;
дамп первой находки — 6 верных строк против 8 у `comm` из PATH).

Мой собственный прогон дофиксовой копии по продукту оборвался на 96-й строке **моим**
пределом времени, а не отказом скрипта, — то есть у него вердикта нет по третьей
категории, и списывать это на `comm` было бы той же ошибкой.

## Почему класс не вернётся — сильнее, чем «`comm` заменён»

Фикс снял не вызов, а **зависимость от упорядоченности**. В стволе остался ровно один
потребитель порядка:

```sh
grep -n 'sort\|uniq\|join ' scripts/branch-audit.sh   # одна строка: ba_norm
```

`ba_norm` сортирует **для читаемости дампа при отладке**, не для корректности счёта:
хэш `awk` даёт тот же ответ на любом порядке входа. Поэтому реализация `coreutils` в
`PATH` на корректность переписи больше не влияет вовсе.

## Инъекция, которую задача просила завести, уже есть — и она различает

`scripts/branch-audit-inject.sh`, оси **AA–AE** (34 утверждения против прежних 29).
Три прогона, как того требует `testing.md` §«Гейт на класс» п. 2в:

| прогон | вход | исход |
|---|---|---|
| контроль | инъекция ствола × скрипт ствола | `rc=0`, **34/34**, находок нет |
| новый дефект | инъекция ствола × **дофиксовый** скрипт | `rc=1`, красны `AB`, `AC`, `AE` — по имени класса |
| предпосылка | `AD` в обоих прогонах | зелёная в обоих: `comm` из PATH ломается на этом входе **сегодня** |

`AD` — не различитель, а **контроль предпосылки**: он утверждает, что старый подход
негоден на этой машине, и печатает «БЕЗ ПРЕДМЕТА» там, где `comm` вход не путает.
Различают редакции `AB` («ни одной жалобы на порядок во всём выводе»), `AC` (починка
даёт верный счёт) и `AE` (вердикт дословно совпадает под `LC_ALL=C` и `LANG=ru_RU.UTF-8`).

`comm` из PATH здесь — `uutils coreutils 0.8.0`; на неотсортированном входе он выходит
кодом **1**, и его собственная проверка упорядоченности расходится с `LC_ALL=C sort -c`
на тех же байтах (замер — в [[issue-540]]).

## Опытом установлено: фикс НЕ двигает числа переписи

Задача ставила условие — «починка, сдвинувшая числа воркспейса, починкой не является».
Проверено **одно-фактным опытом**: дофиксовый и стволовой скрипты прогнаны по воркспейсу
с разницей в 81 секунду.

```sh
diff <(grep -v 'branch-audit: замер' stale-workspace.log) \
     <(grep -v 'branch-audit: замер' fresh-workspace.log)
```

Различий по существу **ноль**: все тринадцать величин переписи совпали, совпала и
классификация каждой ветки. Разошлись только отметки свежести («коммит 42 мин назад»
против «40 мин назад») — то есть ровно те 81 с, что прошли между прогонами.

**Числа при этом отличаются от названных в теле #561** (90/54/22/14/13 против 85/62/13/10/13),
и причина не в скрипте, а в дереве: между замером задачи (`17:00Z`) и моим (`17:28Z`)
воркспейс двигали пятнадцать одновременных рабочих копий соседних сессий. Опыт выше
разделяет эти две причины, чего сравнение с записанным числом сделать не может.

**И воркспейс никогда не был различающим замером:** дофиксовый скрипт даёт на нём
**ноль** жалоб на порядок. Вход, ломающий `comm` из PATH, живёт на дереве продукта
(#540: 120 веток воркспейса — чисто, 467 веток продукта — 67 жалоб из 72 строк).

## Находка по дороге

Отставание рабочей копии не называется ничем: прогон из копии, отставшей на 21 коммит,
внешне неотличим от прогона из ствола, и цена этого — дубль P1 и полная задача агента.
Заведена задачей [#565](https://github.com/PRO-Robotech/kacho-workspace/issues/565), здесь
не чинится (`multi-agent-flow.md` §«Находка по дороге»).
