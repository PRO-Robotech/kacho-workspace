# #514: ствол не требовал ни одной зелёной проверки перед вливанием

**Type**: fix

**Состояние на момент записи**: done — настройка выставлена в обоих репозиториях
2026-08-17, инъекция проведена в обе стороны. Правки дерева задача не потребовала.

**Где ведётся**: настройка защиты ветки `main` (GitHub), оба репозитория. Файлов
продукта и воркспейса изменение не касается.

## Что и зачем

Защита `main` держала **как** попадает изменение (прямой push отвергается,
force-push и удаление запрещены) и не держала **что** попадает: поля
`required_status_checks` в ответе не было вовсе. PR с полностью красным конвейером
сливался кнопкой без возражения сервера.

Опаснее это тем, что пустая сводка проверок читается как «замечаний нет», хотя
означает «конвейер не запускался»: без обязательного набора эта ловушка действовала
на стволе без предохранителя.

## Что выставлено

| | продукт | воркспейс |
|---|---:|---:|
| обязательных контекстов | **45** | **8** |
| `strict` (актуальность ветки) | `false` | `false` |
| обязательное ревью | не вводилось (0) | не вводилось (0) |

Остальные поля защиты сохранены ровно теми, какими были измерены до правки.

**`strict` не включён осознанно.** Замер по 96 влитым PR: медиана отставания при
вливании 0, влитых с нулевым отставанием 54 из 96, возраст точки расхождения 0.9 ч.
Требование актуальности заставляло бы догонять там, где догонять нечего, а каждая
догонка стоит полного прогона при нехватке ранеров.

**Обязательное ревью не вводилось** — разработка автономная, обязательный читатель
заблокировал бы её целиком.

## Как выбирался набор — и чем это проверяемо

Имена контекстов взяты из **фактических прогонов**, а не из YAML. Предикат:

```sh
gh api "repos/<repo>/commits/<sha>/check-runs?per_page=100" --paginate \
  -q '.check_runs[] | select(.app.slug=="github-actions") | .name' | sort -u
```

Набор сверен на пяти PR продукта (изменения от 1 до 441 файла) и шести PR
воркспейса (от 1 до 5 файлов): **перечень контекстов совпал побайтово во всех
одиннадцати случаях**, расхождений ноль. Это и есть проверка требования «контекст
производится при любом составе изменения»: фильтров по путям ни один конвейер не
несёт, и это записано в самих файлах как осознанное решение.

Исключены из обязательных:

- **пять имён шардов сквозных проб** — они порождаются динамической матрицей из
  манифеста шардов, то есть меняются вместе с ним. Вместо них обязателен
  **сводный вердикт**: у него постоянное имя, он исполняется при любом исходе
  предшественников и считает неотчитавшийся шард **отказом**, а не пропуском;
- **два контекста от постороннего приложения** (результаты разбора кода) — их
  производит не наш конвейер; обязательными объявлены наши собственные джобы;
- **конвейеры без триггера на PR** (сборка образов, посадка production, фаззинг по
  расписанию, разведка ранера) — контекст, объявленный обязательным и не
  производимый прогоном, повесил бы PR навсегда.

## Ловушка, которая едва не сработала

Имя джобы длиннее **100 байт** GitHub **обрезает** в имени проверки и дописывает
многоточие. В продукте такая джоба одна, в воркспейсе две. Их имена в YAML и в
прогоне **не совпадают**, и набор, выписанный из YAML, не сошёлся бы с
производимым ни при каком прогоне — то есть PR оказался бы заперт навсегда именно
тем механизмом, который призван его защищать.

Отсюда правило, ради которого запись и сделана: **имя обязательного контекста
берётся из ответа API о фактическом прогоне, и ниоткуда больше.**

## Инъекция — в обе стороны

Проведена на живом PR воркспейса:

- **красное обязательное** → сервер слияния не предлагает, а прямой запрос на
  слияние отвергает;
- **всё зелёное** → PR сливается как прежде.

Без первой половины настройка неотличима от отсутствующей.

## Предикат снятия

```sh
gh api repos/PRO-Robotech/kacho/branches/main/protection \
  -q '.required_status_checks.contexts'
```

Список непуст; каждое имя встречается в сводке последнего прогона ствола;
`strict` — `false`. То же для `kacho-workspace`.

## Что осталось за границей задачи

- набор придётся **править вслед за переименованием джобы**: имя джобы — это и
  есть контракт с защитой ветки, и молчаливого сигнала о расхождении нет;
- переименование, из-за которого контекст перестал производиться, запирает PR;
  выход — правка защиты, а не обход;
- смена базовой ветки у уже открытого PR не перезапускает конвейеры (событие не
  входит в набор по умолчанию) — такому PR нужен новый коммит.
