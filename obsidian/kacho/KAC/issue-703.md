## Что и зачем

Фоновая работа — дренаж очередей, сверка, уборка, синхронизация — поднимается в
КАЖДОЙ реплике: у процесса нет способа узнать, что он не один. Пока реплика одна,
разницы не видно; вторую поднимает автомасштабирование по загрузке, то есть под
нагрузкой, когда дублирование дороже всего, и между «работает» и «начало
дублировать» нет ни решения человека, ни записи в журнале.

Задача просила перепись «50 из 50 с исходом по каждой». Единица счёта объявлена
заново и сделана механической: **фоновая петля — `for` прод-кода развёрнутого
процесса, движимая тиком таймера, ожиданием уведомления базы либо паузой**. По
этой единице петель **39**, и каждая теперь несёт в шапке своей функции запись

```
// РЕПЛИКИ: <вид> — <причина>
```

из закрытого словаря: клейм · одиночка · разбиение · на-реплику · запрос.

Разведены четыре прохода, каждый по существу своего предмета: добиватель удалений
compute и сверка объектов прав registry — замком прохода (бэкстоп, ускоряться от
числа реплик не обязан); сверщик storage — замком **на каждый вид ресурса**
(естественный ключ разбиения: таблицы разные, строки не пересекаются);
синхронизатор величин `pkg/quota` — клеймом строки курсора условной правкой.
Отдельно снят класс «проигрыш гонки записывается отказом»: подтверждение сверщика
storage больше не считает нулевую условную запись ошибкой.

Свойство держит гейт дерева, а не память: петля без записи об исходе — находка.

## Затронутые сущности vault

- `[[packages/corelib-grpcsrv]]` — рядом заведён новый пакет `pkg/singlepass`
  (замок прохода поверх сессионного `pg_try_advisory_lock`).
- `[[checks-with-form-but-no-substance]]` — «идемпотентность» как намерение автора,
  а не свойство оператора: два прохода несли записанное решение «блокировка не
  нужна», верное про корректность и неверное про цену.
