# issue-540 — branch-audit: `comm` из PATH расходится с `sort -c` под той же LC_ALL=C

**Status:** test — фикс и проба в ветке, локально зелено; ждёт PR и подтверждения
полным прогоном на дереве продукта (467 веток, начат `2026-09-07T11:35Z`, к моменту
записи — 20+ минут без единой жалобы на порядок при исходном необработанном прогоне,
дававшем первую жалобу за секунды).

## Признак, с которым заведена задача

Перепись веток на дереве продукта работала 77 минут и выдала 11151 строку `not in
sorted order` вместо вердикта. Первый круг диагностики (закрытый до находки ниже)
установил: сортировка (`ba_norm`) и оба сравнения (`comm -23`/`comm -12`) уже пиннуты
`LC_ALL=C` в дереве. Предикат «пиннинг обеих сторон» казался выполненным.

## Второй круг: пиннинг был выполнен и был НЕДОСТАТОЧЕН

Коллега воспроизвёл признак на дереве продукта (`--prune-merged project/kacho`, 467
локальных веток) при **обоих** пиннингах на месте: 67 строк `not in sorted order` из
72, «полезных» строк — только шапка. Дерево воркспейса (120 веток) в тот же час
жалоб не давало — значит расходится не локаль, а **вход**.

Прямая проверка на дампе первой же упавшей пары (`internal/repohygiene/sqlstatehome.go`,
364 добавленных строки против 590 строк ствола):

```sh
LC_ALL=C sort -c c.add   # rc=0 — файл ОТСОРТИРОВАН
LC_ALL=C sort -c c.tr    # rc=0 — файл ОТСОРТИРОВАН
LC_ALL=C comm -23 c.add c.tr
# comm: file 1 is not in sorted order
# comm: file 2 is not in sorted order
# ...8 строк вместо верных...
# comm: input is not in sorted order
LC_ALL=C /usr/bin/gnucomm -23 c.add c.tr
# 6 строк — верно, молча
```

`sort -c` под той же `LC_ALL=C` подтверждает: файлы отсортированы. GNU `comm` над
теми же байтами отвечает молча и верно. `comm`, разрешаемый из `PATH` на этой машине
(`uutils coreutils 0.8.0`, пакет `coreutils-from-uutils`, диверсия системных
`/usr/bin/comm`/`/usr/bin/sort`), — нет: собственная проверка упорядоченности
расходится с фактом, независимо от `LC_ALL`, переданного самому `comm` (проверено:
`LC_ALL=ru_RU.UTF-8 comm` на тех же ru-сортированных файлах жалуется так же, как под
`LC_ALL=C` — проверка не читает локаль, которую ей передают).

**Вывод: пиннинг обеих сторон необходим, но недостаточен.** Он не может исправить
проверку упорядоченности ВНУТРИ стороннего `comm`.

## Починка — не третий пиннинг, а снятие зависимости от `comm`

`census_file()` считал разность двух мультимножеств (`comm -23`/`comm -12` +
`grep -c .`). Заменено на подсчёт хэшем `awk`: ключ — байтовая строка, вход читается
как есть, упорядоченность не требуется вовсе. Локаль не участвует ни в сравнении
ключей (точное байтовое равенство в любом POSIX `awk`), ни в производителе входа
(`ba_norm` по-прежнему сортирует под `LC_ALL=C` — для читаемости дампа при отладке, не
для корректности счёта).

`scripts/branch-audit.sh`: две новые функции `ba_mset_extra`/`ba_mset_common`,
`miss`/`stay` в `census_file()` считаются ими, не `comm`.

## Проба — issue #540 просил проверку в ДВЕ половины, обе закрыты

1. **Первая половина** (пиннинг сортировки и сравнения к одной раскладке) была
   закрыта до находки выше и остаётся верной как общая гигиена — предикат «оба конца
   пиннуты» по-прежнему держит `ba_norm`.
2. **Вторая половина** (`branch-audit-inject.sh`, оси **AA–AE**, 34 утверждения
   вместо прежних 29):
   - **AA** — содержимое, доказанно ломающее `comm` из `PATH` (34+35-строчный
     минимальный найденный вход; эмпирически — 30 строк ещё чисто, 32 уже ломает),
     после починки классифицируется ВЕРНО («отсутствует 1»);
   - **AB** — во всём выводе прогона нет ни одной строки `not in sorted order`;
   - **AC** — изолированный `ba_mset_extra`, извлечённый из `$AUDIT` текстовым
     разбором (не копия — тот же код), даёт верный счёт на триггерном входе;
   - **AD** — контроль в ОБРАТНУЮ сторону: СТАРЫЙ подход (`comm`, оба конца
     `LC_ALL=C`, как было до фикса) на ТОМ ЖЕ входе завершается диагностикой
     `not in sorted order`, доказывая, что одного пиннинга было мало;
   - **AE** — буквальный предикат из тела задачи: прогон под `LANG=ru_RU.UTF-8`
     (`LC_ALL` пуст — ровно окружение из тела issue) и прогон под `LC_ALL=C` дают
     **дословно совпадающий** раздел по крафченной ветке, без единой жалобы под
     любой из двух локалей.

   Предпосылка (что вход СЕГОДНЯ ломает `comm` из `PATH`) проверяется как отдельное
   условие (`LOCALE_FIXTURE_TRIGGERS_COMM_BUG`); не подтвердись она на другой
   машине — AC/AD печатают «БЕЗ ПРЕДМЕТА», а не подделывают зелёное.
