### Отсечка анонимности владельца операции ловит только ПУСТУЮ строку — а платформенный аноним непустой ({system, anonymous} / {system, bootstrap})
`pkg/operations/owner.go:69`

Дано: стенд vpc/compute в dev-режиме (productionMode=false, т.е. anti-anon в services/vpc/internal/handler/tenant_interceptor.go:76 выключен); `OperationService/Get` и `/Cancel` помечены `{Public: true}` (services/vpc/.../permission_map.go:641-642, services/compute/.../permission_map.go:538-539), т.е. per-RPC Check для них не делается вовсе и предикат владельца — ЕДИНСТВЕННЫЙ контроль (это прямо записано в комментарии рядом: «Access is instead bound to the operation's creating principal INSIDE the OperationHandler … a non-owner gets NotFound»).

Когда: неаутентифицированный клиент A шлёт `POST /vpc/v1/networks` без заголовка Authorization. Шлюз в режимах dev и production (не strict) отвечает `injectAnonymous` → Principal{Type:"system", ID:"anonymous"} (gateway/internal/middleware/auth.go:414-415) и форвардит его заголовками. Use-case делает `operations.NewFromContext(ctx, …)` (services/vpc/internal/apps/kacho/api/network/create.go:139) → строка операции пишется с principal_type='system', principal_id='anonymous'.

Затем неаутентифицированный клиент B (другой человек, другая машина) шлёт `GET /operations/{opId}` и `POST /operations/{opId}:cancel`. У него точно такой же principal {system, anonymous}. `OwnerFromContext` (owner.go:50) видит непустые Type и ID → ok=true; `Owner.IsAnonymous()` (owner.go:69) проверяет только `PrincipalType == "" || PrincipalID == ""` → false; отсечка в repo.go:358/533/557 пропускает; `ownerPredicateSQL` матчит `principal_type='system' AND principal_id='anonymous'`.

Наблюдаемый результат: B получает 200 с операцией A и успешно её ОТМЕНЯЕТ (done=true, error 'operation cancelled') — вместо задекларированного `NotFound`. Ключ владения общий для всех анонимов сразу. Шлюз этот путь не перехватывает: его собственная проверка (gateway/internal/opsproxy/proxy.go:243) отвергает только пустой callerID и связку system+bootstrap, а пару system+anonymous сравнивает как обычного тенанта — и она совпадает.

### Отсутствие принципала превращается в ЯВНО установленный system:bootstrap — ветка «владельца нет» становится недостижимой
`pkg/grpcsrv/cert_identity.go:274`

`withTrustedPrincipal` заводит `p := operations.SystemPrincipal()` (строка 255) и на доверенной ветке безусловно кладёт его в штатный носитель: `ctx = operations.WithPrincipal(ctx, p)` (строка 274) — ДАЖЕ когда `principalFromIncomingMetadata` вернул ok=false, т.е. заголовков принципала не было вовсе. Снятие (`WithoutPrincipal`) выполняется только на НЕдоверенной ветке (строка 270).

Последствие: `PrincipalFromContextOK` отдаёт ok=true, и `operations.OwnerFromContext` (pkg/operations/owner.go:50) отдаёт hasOwner=true с Owner{system, bootstrap}. Проверка `if !hasOwner { NotFound }`, добавленная в services/vpc/internal/handler/operation_handler.go:55/82 и services/compute/internal/handler/operation_handler.go:63/91 ровно против анонимного доступа к операциям, на доверенной ветке НЕ СРАБАТЫВАЕТ НИКОГДА.

Конкретный отказ: слушатель compute/nlb с выключенным mTLS — `principalIsTrusted` возвращает true уже на строке 282 (`if !tlsPresent { return true }`), список доверенных форвардеров при этом даже не читается. Любой peer, дозвонившийся до порта и НЕ пославший ни одного `x-kacho-principal-*`, получает Owner{system, bootstrap}. Этот ключ совпадает с principal_type/principal_id КАЖДОЙ строки операций, записанной системным fallback'ом — а это все операции фоновых воркеров/реконсайлеров и все операции, созданные через `operations.New` без ctx-принципала (pkg/operations/repo.go:260 и 291 явно подставляют туда `SystemPrincipal()`). `GetOwned` возвращает такую операцию, `CancelOwned` её отменяет — вместо `NotFound`.

### «Отравленный предшественник НИКОГДА не применится, поэтому пропуск не даёт над-гранта» — он применяется: RedrivePoisoned возвращает его в очередь ПОСЛЕ уже доставленных преемников
`/home/dk/Documents/03.07.2026/workspace/github/PRO-Robotech/cloud-demo/kacho-workspace/project/kacho/pkg/outbox/drainer/internal.go:212`

Годок buildClaimQuery утверждает: «A POISONED predecessor (attempt_count = MaxAttempts) is excluded from the blocking set (`p.attempt_count < $1`): it will never apply, so it must not wedge its partition forever; a poisoned write creates no tuple, so skipping it introduces no over-grant» (то же по-русски в drainer.go:160-167: «Leak это НЕ реинтродуцирует: отравленный WRITE не создаёт tuple»). Утверждение «it will never apply» неверно: pkg/outbox/reconciler/reconciler.go:201 RedrivePoisoned делает `UPDATE … SET attempt_count = 0 … WHERE sent_at IS NULL AND attempt_count >= MaxAttempts`, и этот бэкстоп заведён в КАЖДОМ сервисе с register-outbox (services/{vpc,compute,nlb}/cmd/*/backstop.go, services/{storage,registry}/cmd/*/redrive_backstop.go). Более того, classify.go:126-131 прямо продаёт отравление как безопасное ИМЕННО потому, что redrive его переиграет («a cause that was temporary succeeds on a later pass»).

Конкретный прогон (партиция = resource_id, PartitionColumn задан во всех пяти сервисах):
1. Создан ресурс X → строка id=5, event `fga.register`.
2. Apply строки 5 отвергнут PermissionDenied (реальный класс — см. pkg/outbox/drainer/permission_denied_terminal_integration_test.go:30-35: «198 rows, all refused on authorization grounds»); Classify → ClassPermanent → attempt_count=MaxAttempts.
3. Ресурс X удалён → строка id=9, event `fga.unregister`. Предикат claim'а исключает отравленную 5 → 9 клеймится, применяется, sent_at проставлен: iam делает жёсткий DELETE строки mirror (resource_mirror.DeleteTx — DELETE без tombstone-строки).
4. Оператор чинит причину отказа (грант fga_writer / роль). Периодический RedrivePoisoned ставит строке 5 attempt_count=0 → она снова единственная pending в своей партиции → клеймится и ПРИМЕНЯЕТСЯ.
5. iam выполняет register удалённого ресурса: строки в resource_mirror нет, ON CONFLICT не срабатывает, source_version-LWW гейтит только ветку DO UPDATE → берётся ветка INSERT → mirror-строка удалённого ресурса ВОСКРЕШЕНА. Level-triggered binding-reconciler читает mirror как источник истины и вечно ре-материализует owner-tuple.

Наблюдаемый неверный результат: после удаления ресурса его владелец сохраняет материализованные права на `<type>:X` бессрочно, самоисцеления нет — ровно тот over-grant, ради предотвращения которого PartitionColumn и вводился (drainer.go:132-137 описывает этот же сценарий как то, что фича закрывает). Для iam fga_outbox (партиция = tuple_key) картина ещё прямее: отравленный WRITE(grant), отозванный DELETE(revoke) применён, redrive возвращает WRITE → отозванный tuple записан обратно.

### Курсор ленты жизненного цикла двигается по sequence_no, назначенному до коммита — событие конкурентной транзакции с меньшим номером теряется навсегда

### Периодический redrive воскрешает отравленную регистрацию ПОСЛЕ того, как её снятие уже доставлено — партиционный порядок обходится
`services/storage/cmd/storage/redrive_backstop.go:59`

Партиция дренажа = resource_id (`register_drainer.go:67`, `PartitionColumn: "resource_id"`). Отравленная строка НАМЕРЕННО исключена из блокирующего набора claim-запроса (`p.attempt_count < MaxAttempts`, pkg/outbox/drainer/internal.go:240), и leak-safety этого исключения обоснована ровно одним допущением, записанным в corelib: «отравленный WRITE не создаёт tuple». Redrive это допущение отменяет — `RedrivePoisoned` делает безусловный `UPDATE … SET attempt_count = 0 WHERE sent_at IS NULL AND attempt_count >= MaxAttempts` (pkg/outbox/reconciler/reconciler.go:201), без какого-либо взгляда на партицию и на то, доставлены ли уже БОЛЕЕ ПОЗДНИЕ строки того же ресурса.

Последовательность (все шаги — существующие пути кода, никакой гонки не требуется):
1. Create Volume V → строка #1 `fga.register` (партиция resource_id=V). iam отвечает PermissionDenied — ровно причина, которую redrive_backstop.go:37 называет ожидаемой («не досеянный грант fga_writer на свежем стенде»). classifyRegisterErr (iam_register_applier.go:144) → ErrPermanent → markPoisoned: `attempt_count = MaxAttempts`, `sent_at` ОСТАЁТСЯ NULL (internal.go:336).
2. Delete Volume V → строка #2 `fga.unregister` в той же партиции (volume_repo.go:383). Строка #1 отравлена ⇒ из блокирующего набора исключена ⇒ #2 клеймится и применяется. Грант fga_writer к этому моменту досеян → UnregisterResource проходит; iam делает ЖЁСТКИЙ `DELETE FROM resource_mirror … WHERE source_version <= $tombstone` (services/iam/.../resource_mirror/emitter.go:131) — строки нет, tombstone не остаётся. #2 помечается sent_at.
3. Тик redrive (каждые 5 минут, redrive_backstop.go:18) сбрасывает #1 в attempt_count=0. #1 — минимальный id своей партиции, предшественников нет ⇒ клеймится и применяется. Грант уже есть → RegisterResource проходит → mirror-строка УДАЛЁННОГО тома создаётся веткой INSERT (сравнивать не с чем — эмиттер, строка 96 `ON CONFLICT … WHERE source_version < EXCLUDED.source_version`, до ветки UPDATE дело не доходит).

Наблюдаемый результат: в kacho-iam живёт resource_mirror-строка `storage_volume:<id>` тома, которого нет, а level-triggered реконсайлер iam бесконечно ре-материализует по ней owner/v_*-tuple'ы. Самоисцеления нет by construction: строка #2 уже `sent_at`, второго unregister никто не выпустит, а iam тома storage не перечисляет и осиротевшую строку зеркала снять не может. Это дословно тот сценарий, который миграция 0008 (services/storage/internal/migrations/0008_fga_register_outbox_partition_head_idx.sql:12-20) объявляет причиной существования PartitionColumn — «RESURRECTS the mirror row of a DELETED resource — permanently … There is no self-healing».

### Доверенный слушатель СОЗДАЁТ системного принципала из ничего — запрос без личности проходит owner-гейт операций
